## 3. Reachability and dead ends: the standard I recommend

**Every declared state must have at least one feasible finite run from a valid construction. From every reachable configuration in a non-terminal state, at least one feasible finite continuation must reach a different state.** A configuration includes data as well as the state name. Both runs use legal arguments, first-match selection, actual writes, legal edits and their access windows; an arbitrary assignment to a stored field is not an input. A refusal or an unchanged self-transition is not an exit. A preparatory operation in the *same* state can be part of the route. “Can” does not mean the caller is obliged to act, an approval will arrive in real life, every event succeeds, or every run eventually terminates.

The first clause follows Want:151. The second is my reading of Want:152, supported by `philosophy.md:44`: “no dead end an entity enters and cannot leave.” It protects an individual application, not just the label *Review*. It does **not** silently add “can always reach a terminal”; `graph-analyzer.md:439` checks “no structural path to any terminal,” and Plan:991 correctly isolates the two-state-cycle question. Keep a separate test for genuinely dead or shadowed rows (Want:155); passing a state test does not make every row usable.

Here are candidate standards, tested against the same small workflows. In the first three, assume an independent valid route from Intake to Done; an unreachable terminal is not the reason for rejection. A and B are insufficient; C shows why even real examples alone are not enough.

| Candidate and what the author must supply | Review always entered unapproved; only exit needs approval; no way to change it | Two legal entries, approved and unapproved; still no way to change it | Add a legal Approve operation **in Review** that changes false to true, then allow Finish |
|---|---|---|---|
| **A. State-name graph.** Write a chain of transition rows to each state and draw an outgoing arrow. | Accepts: the Finish arrow exists. | Accepts. | Accepts, but not because it understands Approve. |
| **B. Rule-consistent guards.** Write rows whose guards can hold in some assignment satisfying local rules; find paths among those rows. | Accepts if no declared Review rule forbids true: it invents an approval nobody can produce. An established Review rule excluding true would expose the defect, not fix it. | Accepts: true is legal and reachable for *someone*. | Accepts. |
| **C. One real entry and one real exit per state.** Write actions and argument constraints admitting at least one executable path for each. | Rejects: no executable exit. | **Accepts:** one approved application really can exit; the unapproved one is trapped. | Accepts: approve, then finish. |
| **D. Real entry; a possible exit for each reachable configuration (recommended).** Write actual operations covering every admitted case. The author need not supply traces or proof syntax. | Rejects. Supply Approve, add a legitimate cancellation route, or only admit approved applications. Merely declaring approval true is not a fix unless every entry establishes it. | **Rejects** until the false case has a way forward or is genuinely excluded at entry. A terminal elsewhere does not help. | **Accepts:** true can finish immediately; false can approve and then finish. It is unnecessary to add an artificial immediate exit or make the field arbitrarily editable. |

Two other distinctions keep D usable. **Immediate exit from every configuration** would reject the repaired third column just because approval needs a preparatory step. **A route to a terminal from every configuration** would reject a subscribed account that can alternate Active ↔ Paused but has no route out of that pair. D accepts that pair for the *exit* test; a separate requirement for completion would demand a genuine Close or Cancel operation. In contrast, *inevitable* termination would reject even an account that can close but whose customer chooses to keep it active. Want:152 does not require inevitable termination. Mark `terminal` only for an intentional endpoint, not to silence a missing business operation.

**What the compiler must show, rather than what the author must spell.** Use a graph search to exclude disconnected states; eliminate guards contradicted by established facts and rows preempted by earlier rows. For positive answers require independently checkable evidence: a feasible construction and transitions, an exact finite analysis for finite choices, or a checked argument covering multiple data values and steps. For example, start a counter at 0, increment only below 1,000, and allow completion at 1,000. A search cut off after 50 events cannot decide this case. A short proof shows each permitted increment is in range, can actually be taken, and decreases the nonnegative number of increments remaining by one. It proves arrival **and** an available exit from every intermediate value without a thousand-line trace or a new author annotation. A guard checking an immutable false flag gets no such proof.

There is no general promise to accept every “reasonable” definition under arbitrary unbounded data. Separate **proved**, **proved impossible** (explain the contradiction or show a reachable trapped configuration and why no exit is possible), and **not proved** (say which route or enabling condition is missing). The last cannot certify a definition, but it must not accuse the author of an actual dead end. First try the ordinary multi-step business cases above, without making the author constrain away valid data or lower a threshold to fit a search cap. If a realistic case remains outside the design, present that case, the best checkable argument tried, and what change it would cost the author. That is a feasibility decision worth the owner's time; changing the meaning of “reachable” by default is not.

## 4. A paper test for the revised plan

**How to run it.** Give a reader the revised plan, its proposed finish procedure and the four inputs below. No compiler runs. For each, record the owning canonical statement (file, section, actual words), what obligation the compiler generates, how any certificate evidence is independently checked or another trusted step enforces it, and the caller's outcome. Follow pointers to the one owning statement. First run the intact example. Then strike the specified statement **and its derived row**, leaving the remaining rows complete and counts green. Run the finish procedure again from the original inputs, not from the surviving list. **Pass** only if it refuses sign-off, identifies the missing decision or obligation and reopens the correct work. If only a reviewer already told about the omission can detect it, the procedure fails this test. An equivalent sound design can pass without using these words or inventing a diagnostic code.

Do not “fix” the test by adding unconditional revalidation to same-definition hydration. |

The paper exercise succeeds only if all four intact cases give the stated outcomes **and all four omissions block sign-off for the stated reason**. A count of recorded walks, by itself, answers neither question.
