# Confirmation of the process findings

**Scope.** This file checks every outside-review finding about how the design-completion plan runs, finishes and stops: the finish conditions, the completeness checks, the stop rules, the order of steps, the one-line starts, the parallel lines of work, citations, records, and the count of times the plan reaches Shane. The sources checked are the second reviewer's report (`outside-review-report-2.md`, section "Where the work can finish falsely or repeat", lines 67-129), the second reviewer's verdicts on the first reviewer's sections 1, 2 and 4 (`outside-review-report-2-followup.md` lines 9-90), and the second reviewer's cut list (`outside-review-report-2-followup-2.md` lines 117-160). Each finding was checked against the plan as it stands at `5c4269bc`. The plan file has not changed since commit `b177ce69`, so line numbers quoted by both reviewers refer to the same text, although the first reviewer's line numbers are often offset and were re-located by hand.

"Plan" below means `docs/working-reset/design-completion/design-completion-plan.md`. A finding is confirmed only when it is true of the current plan and would affect whether the design actually gets finished, finished correctly, or finished with little of Shane's time.

## Confirmed

### 1. The finish checks count bad rows in lists they built themselves, so an omitted fact passes (critical)

Condition 5 builds its table from the list it is meant to check: `dedup/pairs.jsonl` "holds one row for every pair of a canonical document and a fact on the ownership list, generated by script" (Plan:76-77). The script then counts "rows not filled, and rows where a document other than the owner states the fact in full. Both must be zero" (Plan:80-81). Nothing counts a fact whose owning document has marked it "does not mention". Mark the owner's row that way and both counts are zero while the fact has no full statement anywhere. A fact missing from the ownership list has no row at all.

The ownership list itself has no stated origin. No step is given the job of producing `ownership.jsonl`; the only other mention is "the ownership table and the document-by-document pass in step 14" (Plan:896). By contrast the contents list is drafted twice independently and the two drafts compared item by item (Plan:122-125). The ownership list gets no such cross-check.

The coverage table has the same shape. Step 6 counts "coverage rows with a step or a permitted refusal" (Plan:482), one row per member of each extracted list (Plan:476-477). The old plan required every case either to refuse by construction "or names the properties it splits on and closes that split the same way, recursively" (`compiler-readiness-plan.md:1714-1715`). The new plan drops the check one level down. A comparison row that cites a numeric proof step can pass while date ordering, which needs its own proof, has no answer.

Step 15 then sets "Every canonical document's maturity row set to 'Full' by script from the check results" (Plan:638), so a check that passed over an incomplete list marks the documents complete.

**Change required.** Require exactly one full statement per fact, at a checked location in the owning document; zero full statements must fail. Add a reverse check: from each normative passage in the original canonical documents, find its retained full statement, its pointer, or a justified replacement. Give the ownership list an origin and an independent comparison like the contents list's. For proof rules that vary by type or action form, require each applicable case to be followed to an answer. Test the finish procedure on a made-up completed inventory with one omission each (the sole owner marked "does not mention", the dequeue's ordering-value destination, one applicable comparison case) and require each to be rejected.

### 2. Step 0 builds all the machinery before the first design paragraph (major)

Step 1 needs step 0 (Plan:365). Step 0 is finished only when all eleven tests have an outcome (Plan:329-331), and it builds fifteen scripts first (Plan:318-320), four workflow scripts and the start command (Plan:324-325), and seeds `rulings.jsonl` with 121 rows and the other fixed-form files (Plan:312-317). Its guard allows up to ten runs and 4,000 script lines before stopping with a notice that "Only his words clear" (Plan:303-305). The history file records that "about 5,700 lines" of tooling were built to manage a design document before (`inputs/history-failures.md:556`, cited by the plan itself at Plan:306), and that tracking produced "about 18,000 lines of records" (`history-failures.md:549-556`).

The bound is a ceiling, not a forecast, and tests can finish by adopting a fallback (Plan:329-330), so step 0 is not certain to stall. The defect is the ordering: none of this is needed to write the first ordinary operation section, and all of it is required before that section can start. The second reviewer's cut list (followup-2:121-139) is a sound reduction: a small start-and-status gate, the attack check before the first round is credited, the other checks at their first use, and `locked-write` deferred until there are actually two writers.

**Change required.** Shrink step 0 to what the first section needs: the authorized revision, one author, allowed files and tools, the authority order, one independent reader, and one record of the last committed piece and any blocking finding. Move each checker to the first piece that uses it and test it there. Keep the twelve attack rounds; nothing in this cut touches them.

### 3. Several stop rules halt successful work or have no way to clear (major)

- **Records outgrow the design.** "From a step's third run on, lines of record written for it exceed ten times the lines it has changed in canon" halts the step, cleared by "His words" (Plan:800). Step 13 writes only `handoff.jsonl` and changes no canon (Plan:587-594). Three runs of it meet the condition with any positive record count, since anything exceeds ten times zero. Step 15 is mostly recorded walks (Plan:629-638) and is in the same position. For proof steps the rule is not certain to fire, as the first reviewer claimed, but it is likely: one argument requires at least 48 agent outputs before any repair (Plan:1169-1170), so an argument of 50 canonical lines trips the ratio once those outputs average more than about ten lines each.
- **Tidying runs ahead.** Step 14 pauses when its canon lines "exceed twice the lines changed in the proof-model sections" and clears only "when the proof-model lines catch up" (Plan:792). After step 11 the proof-model sections are hashed and changes to them are exceptional (Plan:562-565), so a paused step 14 may never clear. No owner route is given for this rule.
- **Found faster than closed.** Fires when "rows found and not yet worked have risen across three runs in a row" (Plan:799). Three runs that each find two defects and close one raise the backlog 1, 2, 3 and halt the step, although every run made real repairs. The rule's own justification is phase 2's moving finish line (Plan:805-808), which is a different pattern: the same defects being rediscovered.
- **Cascading repairs** halts a section on two refutations caused by repairs and needs "His words" (Plan:796), even if both are locally repairable proof errors.
- **Whole model** halts steps 1 to 11 when "at least three arguments and more than a third of those that have finished their first author's rounds went to a second author" (Plan:797). Three unrelated failures among eight arguments meet it. It counts escalations, not a shared false premise.
- **Tests only on prepared inputs.** Step 0's test 2 checks that each rule "fires on a prepared input, stays fired" and clears (Plan:334-336). No test runs a successful trace to check that it does not fire.

**Change required.** Measure each kind of work in its own unit (handoffs verified per claim, walk cases finished, repairs confirmed). Release the step-14 throttle at the proof-model sign-off. Replace the raw backlog trigger with a check for the same requirement failing on successive attempts. Require a demonstrated common counterexample before the whole-model halt. Run every stop rule on a record-only step and a normal discovering step, and require it to stay quiet.

### 4. The parallel schedule, the one-line start and the worktrees describe different executions (major)

The order table and text run steps side by side: "Steps 1 and 2 are written side by side", and after step 6 "step 7 and the pieces of steps 10 and 11 that do not need step 9 run side by side" (Plan:255-257); step 14 "Runs beside steps 1 to 12 in its own worktree" (Plan:599). Step 6 needs a piece of step 9 that runs "as soon as step 4 has passed" (Plan:516-518, 468). But "A new step begins only after he types the line following the notice that the previous one finished, so nothing starts that he did not start" (Plan:1144-1146). Nothing says which start line authorizes a step that runs beside another, or authorizes step 9's early piece while step 9 has not been started. A strict reading waits on a start that never comes; a runner that starts the later step itself does something Shane did not authorize. The first reviewer's claim that steps 6 and 9 form a cycle is wrong: the early piece needs step 4, not step 7.

Each line of work has its own Git worktree and shared files go through `locked-write` (Plan:1135-1137). The plan never says how the worktrees' commits are combined; a search for merge, integrate or rebase in the plan finds only fact merges. Test 9 asks whether "Two lines of work commit at the same moment from two git worktrees without damage" (Plan:351-352). Two commits from the same parent can each be correct on their own copy and still disagree; a lock on writes does not make either see the other's commit. `trailer-check` also requires "the lines the commit adds to canon are in" the agent's output (Plan:838-839), which a conflict resolution cannot satisfy.

**Change required.** Assign step 9's early piece to step 4, or say that the start of step 4 authorizes it. State which pieces one start authorizes to run concurrently. Name one integration point that accepts results against a stated revision and recomputes status on the combined tree. Test a stale result, a stop and restart between commits, and a whole run with one start per step.

### 5. The owner budget counts envelopes, not the decisions inside them, and omits some owner-only clearances (major)

Plan approval "also adopts the starting values in § 4.5" (Plan:296-297), but the reading aid does not state the record ratio or the backlog thresholds; it mentions only step 14's twice-the-lines pause and "Stop rules clear only on his words or an independent repair" (`plan-summary.md:33,66`). The summary says "where they differ, the plan stands" (`plan-summary.md:3`), so he would be adopting numbers he was not shown.

Owner-only clearances missing from § 6.5: the step-0 guard ("Only his words clear it", Plan:305); a rule that fires again within three runs of a repair clearance (Plan:778-779); the reopened-work rule (Plan:798); a change to the list of flaw kinds (Plan:691); a refusal on "earns its place" (Plan:748). The second-author sheet is bounded as "One per step at most" (Plan:1090) but asks for "His choice for each" argument (Plan:1054), so one sheet can hold many decisions. The two conversations are counted as two items (Plan:1076), though `CLAUDE.md` says such a conversation "might converge in one turn or run for several". The proof-model sign-off includes "the refused list with the reason for each refusal" with no bound on its length; only the untraced changes are "capped" (Plan:1039-1041).

The fallback estimate understates combined fallbacks. It assumes "an attack run moves eight arguments three rounds" (Plan:1096). If test 7 fails, "Every run is cut to one piece" (Plan:1195), and one piece is "one round of one argument" (Plan:1131). Under the five-run fallback session (Plan:1156-1157), eight arguments at twelve rounds need at least 96 runs, about 20 sessions: one start and at least 19 restarts for attacks alone, against the roughly four attack runs the published formula gives.

Separately, canon itself calls some caller-visible choices undecided: `result-types.md:123` says the shape of `InvalidArgs` "is an API-shape decision neither the want document nor the specification settles", and `precept-builder.md:641` leaves open "Whether a verification failure throws or returns a structured result". Neither is among the fifteen candidate sheets (Plan:974-995). The first reviewer's claim that at least eight hidden decisions follow is not supported; some may be settled by existing canon. But the cap was set without them.

**Change required.** Put the actual thresholds in what he approves. Count decisions inside sheets, conversation turns, and estimated reading from one real packet, separately from operational interruptions. List every owner-only clearance in § 6.5. Show the combined-fallback cost before approval. Give exhausted retries a technical disposition so that clearing a count threshold is not his job.

### 6. A canonical edit cannot meet both citation rules (major)

Each canon edit "that rests on his words cites the row" (Plan:667-668), and `lint` reports "locked", "ratified", "owner decision", "settled" and "ruled" in any canon change "unless the line cites a row of `answers.md` or `rulings.jsonl`" (Plan:664-666). Both files live under `docs/working-reset/design-completion/` (Plan:92-93). But "Canon cites nothing under `docs/Working/` or `docs/working-reset/`" (Plan:849). An author recording a ruling either adds the citation and breaks the canon rule, or omits it and fails the width check. The want document is under `docs/Working/` too, so canon may not cite it either. Separately, `cite-check` opens evidence "with `git show HEAD:path`" by line number (Plan:656-657), and condition 4 records each ruling's canonical line (Plan:68); step 14's deduplication moves lines without changing a decision, so recorded lines go stale.

**Change required.** Keep the link between a canonical edit and the ruling in a separate change record outside canon. Record the ruling and its quotation at a fixed revision, and check the current owning statement separately.

### 7. Acceptance criteria are written during design, and the handoff check cannot find a missing one (major)

Shane's order is "A completed and consistent design first, then acceptance criteria, tests, code reviews" (Plan:43, quoting rulings:40). Yet each of steps 1 to 11 "adds its acceptance criteria to `handoff.jsonl`" (Plan:283), and step 0 seeds that file with "the fourteen mutations of the bank example as the first acceptance criteria" (Plan:315). Step 13 needs only "steps 3 to 11 finished" (Plan:587), not steps 12, 14 or 15, and its finish condition counts "rows of `handoff.jsonl` without an owner or of a kind condition 7 does not allow" (Plan:593-594). A diagnostic designed in step 12, or a behaviour changed after a step-15 walk finding, can end with no criterion and every existing row still passes. The old plan built its criteria from the union of all claims, including "phase 5's discharge claims and checker obligations" (`compiler-readiness-plan.md:2055-2057`), and checked in both directions (`:2044`).

The old plan's bounded search also had a stated purpose: it "runs over every numeric discharge rule in the closed list" to find unsound rules (`compiler-readiness-plan.md:1807-1810`). The new plan keeps "A bounded counterexample search is in scope" (Plan:1247) and designs it in step 8 next to "how the concrete case is found, re-checked and shown" for rejection messages (Plan:502-505). It does not say which of the two jobs the search does. A rule that wrongly accepts an unsafe operation produces no rejection to search from.

**Change required.** Keep the bank cases as design evidence. At design sign-off hand over the exact revision and the complete claim list; in the following stage check both a claim with no criterion and a criterion with no claim. Name both searches and their purposes.

### 8. The fourteen bank rows are not fourteen independent demonstrations (major)

The want document's table has a row "Remove `PlanRepayment`'s cap conjunct" and another "Guard `PlanRepayment` on `Balance < 0.0` alone, dropping the restating conjunct" (`what-i-want-2026-07-16.md:121,123`). Both remove the same conjunct. `MonthlyRepayment` is optional (want:35) and is read without a presence test in `ReduceLimit`'s guard and again in its last refusal message (want:75, want:81). The spec says "An interpolation hole is a read: an `optional` field read at a hole enrolls a presence obligation" (`precept-language-spec.md:1561`). The plan notes the guard (Plan:206, 1025-1026) but not the message. Step 8 counts "rows of the want document's rejection table with a named diagnostic, of fourteen" (Plan:509-510). If the original definition is rejected for the unguarded optional read, every mutation is rejected too and the count says nothing about whether each deleted premise is what failed.

**Change required.** Keep all fourteen rows and the historical original unedited. Beside them, state the intended accepted baseline, including which row handles an absent repayment and its message. For each distinct edit, give the changed obligation and the expected diagnostic, and link the two rows that describe one edit. An unrelated rejection is not a pass.

### 9. A step-15 finding makes `status` fail with no defined reopen (minor)

`status` fails "on every run and not only at the finish, any open row in any of the five files whose owner step has already finished" (Plan:84-85). Step 15 runs after the others finish and "Every defect becomes a row in `findings.jsonl` and is worked like any other" (Plan:634-635). The plan never says that recording the finding reopens the owning claim. The first reviewer's quotation ("which reopens that step") is not in the current text, and its claim that all downstream steps lose passed status is wrong: reattack applies to the changed arguments and their recorded dependents (Plan:563-565, 794).

**Change required.** Make recording a finding and reopening its owning claim one action.

### 10. The plan's paths and revision lines are stale (minor)

The short-name table maps `v2` to `inputs/design-completion-plan-v2.md` and `review` to `inputs/plan-vs-old-review.md` (Plan:32-33), and says the inputs "sit in the session scratchpad" until step 0 commits them (Plan:35-37). Both files are committed under `lineage/` (`lineage/design-completion-plan-v2.md:1`, `lineage/plan-vs-old-review.md:1-4`), and the inputs folder is already committed (commit `b177ce69`). The plan says it was written against `spike/Precept-V2-Radical-reset` at `2f126a3b` (Plan:7); the work is on `spike/Precept-V2-Radical-design-completion`. The summary calls the plan `design-completion-plan-v3.md` (`plan-summary.md:3`). A literal `cite-check` over these short names fails to open the cited files.

**Change required.** Point the short names at the committed files, drop the scratchpad step, and name the revision Shane is approving.

### 11. Pending markers do not keep the later steps moving (minor)

The plan says an unanswered question "holds back only the step's finish, never the work that can be done without it" (Plan:261-262). But each later step needs its prerequisite step "passed" (Plan:236, 239-253), and "Text behind a pending marker may not be cited" (Plan:710). So step 3 waits for step 2's finish, which waits for the overflow answers, and step 4 waits for step 1's state-action answers. This is a wait, not the deadlock the first reviewer described: all seven sheets and both conversations go out in the first batch (Plan:971-972, 1005), and step 14 and the step-4 checkpoint can still run. But writing each pending sub-item in every option and attacking each form for twelve rounds buys little downstream progress.

**Change required.** State plainly that later steps wait for the answers, and test the schedule with one answer delayed. Write both options only where independent work actually needs both.

## Rejected

- **First reviewer 1.1, record rule halts every proof step "mathematically".** The rule is likely to fire on proof steps but is not guaranteed; the review's own low figures (1,440 record lines against 150 canon lines) give 9.6 to 1. The real defect is kept as finding 3.
- **First reviewer 1.2, deadlock until all answers arrive.** It is a wait, not a deadlock (finding 11).
- **First reviewer 1.4, cycle between steps 6 and 9.** Step 9's early piece needs step 4, not step 7 (Plan:516-518). The start-authority problem is kept as finding 4.
- **First reviewer 1.5, 10,000 to 33,000 rows.** Nothing measures the number of facts. The real defect, an incomplete inventory passing, is finding 1.
- **First reviewer 1.6, line endings, formatting and pointer edits block commits.** No step requires normalized text to be byte-identical to an agent's output in a way that would fail on these. The same-commit and merge-resolution problems are kept in findings 4 and 6.
- **First reviewer 1.7, all downstream steps lose passed status.** Reattack is limited to changed arguments and their dependents. The reopen gap is finding 9.
- **First reviewer 2.1, exponential cascading halts.** It needs two refutations, and a dependency reopen is "Not a halt" (Plan:794). The owner-only clearance is kept in finding 3.
- **First reviewer 2.5, width check is a non-converging gate.** It clears by an independent reader's confirmation or by reverting the use (Plan:801).
- **First reviewer 2.6, frozen-list growth guarantees revert churn.** A revert happens only when an edit does not hold (Plan:820-823). The twice-the-lines throttle is kept in finding 3.
- **First reviewer 4.3, conversations disguised as single items.** The plan names both openly (Plan:997-1005). Their cost is kept in finding 5.
- **First reviewer 4.5, at least eight additional owner decisions.** Not established; the narrower point is in finding 5.
- **First reviewer 4.6, permission approval uncounted.** It is counted (Plan:1073).
- **Second reviewer, step 12 depends on `pointer-check`, which may not exist.** Step 14 builds it as its first piece and starts as soon as step 1 has a section (Plan:322-323, 601-602), long before step 12; the throttle cannot pause step 14 before it has changed any lines.
- **Second reviewer's cut list, one-page write-ups precede every section.** The plan requires one page per hard problem, not per section (Plan:276).
