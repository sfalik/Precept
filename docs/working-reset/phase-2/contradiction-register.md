## How to read a row

- **ID** — `S*`, `P*`, `R*`, `C*`, `SC-1` are the 2026-07-19 canon report's own identifiers, kept so
  the two documents can be joined. `N*` are new in this phase.
- **Grep** — run against `docs/language docs/compiler docs/runtime docs/philosophy.md` unless the row
  is marked **WIDE**, in which case add `README.md docs/compiler-and-runtime-design.md docs/tooling`.
  *(`docs/tooling` added 2026-07-28 by the condition-3 re-run. The fifth pass added the folder to
  `$CANON_WIDE` in `search-procedure.md` § 0 and to the resolver in its § 7, and did not add it to
  this sentence — which is the copy a row-by-row re-runner reads. Rows `N103` and `N104` correct
  files in `docs/tooling/`; run under the sentence as it stood, both patterns returned zero because
  the folder was not in the file set, which is zero for the wrong reason.)* Finish-line
  condition 3 is this pattern returning zero hits after the row is executed. It is self-refereed: it
  catches a forgotten file, not a resolution done wrong. **A row that corrects one document scopes its
  grep to that document** — scoping it across the whole canonical set makes it fail forever on text that
  belongs to a different, unexecuted row, which is what happened to `N36`.
- **The pre-correction test.** *Added 2026-07-27, fourth pass.* A pattern returning zero at HEAD proves
  nothing unless it returned more than zero in the tree the correction landed on top of. Run every pattern
  against `git show <commit>^` over the same files before recording it. Six patterns in this register were
  written from memory of a sentence rather than copied from it, and each returned zero in both trees. This
  test is the only one that catches that.
- **`OWNER APPROVAL REQUIRED`** — every `docs/philosophy.md` row. Project rule: no philosophy edit
  without Shane's explicit approval. These rows are recorded and **never executed** until he approves
  the wording, which goes to him as a diff.
- **`INTRA-CANON`** — canon contradicting canon rather than contradicting the want document. A
  different kind of disagreement, the same repair. Carried because the phase's second input is made
  of exactly these.
- **`ADDITION`** — the want document requires something canon does not say at all. Nothing to delete;
  something to write. The grep pattern for an addition row is inverted: it must return **more than
  zero** hits once executed, and the row says so.
- **`CONFIRM`** — *added 2026-07-27, fourth pass.* The row's resolution is to confirm the canonical text
  already agrees with the want document and change nothing. A confirm row has no removed phrase, so a
  deletion-shaped pattern on one returns zero in every tree it can be run against and tests nothing. The
  pattern for a confirm row asserts the **aligned text is present** and must return more than zero, in the
  pre-correction tree and at HEAD alike. `R8` and `N67` carried deletion-shaped or absent patterns for three
  passes and each read to a mechanical checker as unexecuted work.
- **`RE-SCOPE`** — *added 2026-07-27, third pass.* The resolution keeps the canonical words and
  changes what they are scoped to, so the phrase the row quotes was never going to disappear and a
  "returns zero" test on that phrase can never pass. The pattern for a re-scope row greps the phrase
  **plus the reading that was removed** and must return zero, or it names the exact lines that
  legitimately survive. Five rows recorded as executed carried the wrong kind of pattern for two
  passes — `S7`, `N9`, `N40`, `N41`, `N43` — and each read as a failure of condition 3 where the
  correction was in fact right.

**Honest note on completeness.** Nobody can prove this list complete and this register does not claim
to. What is claimed: the procedure is written down, it was run at `b93d1db1`, and this is what it
found. The procedure's § 6 names four things it will miss.

# 1. The post-mutation constraint sweep

**want:199** — "Once the compiler has proven every rule, the runtime does **not** re-evaluate them
against the post-mutation configuration." **want:165** — what runs at runtime is "the declared
premises … and nothing beyond them."

This is the largest family in the register and the correction list's largest single item. The
atomicity guarantee survives everywhere — multi-action writes stay all-or-nothing and no partial
state is observable. What goes is *constraint evaluation as the commit condition*.

## 1.0 The family test, and why each row's own pattern is not enough

**Added 2026-07-27, third pass.** Every pattern in this family was originally written as one noun
phrase lifted from the sentence being deleted — `constraint evaluation`, `Constraint plans
evaluated`, `Run constraint plans against the working copy`. All of them returned zero while three
runtime documents went on specifying the same model in the verb form: `evaluates constraints`,
`evaluate all constraints on every operation`, `evaluate constraints from prebuilt buckets`. A
pattern that only knows one inflection cannot find the idea, and this failed twice.

**Widened again 2026-07-27, fourth pass.** The three-inflection version was still one word short. It
matches `evaluat*` and nothing else, so it never saw `constraint re-check` — a *third* spelling of
the same idea, sitting in `proof-engine.md` at `:2237` and `:2249` with no row in the register
covering it. The axis to widen along is synonyms, not only inflections: an idea needs its verb, its
noun, its passive form **and** the other words a writer would reach for. `re-check`, `re-evaluate`,
`re-validate` and `re-verify` are now in the test.

Every row in § 1 now carries its own site pattern *and* cites this family test. Run both.

grep -rniE 'constraint (evaluation|plans? evaluated)|evaluat(e|es|ed|ing) (all |every |the |each )?constraints?|constraints? (are |is )?evaluat(e|es|ed|ing)|re-?(check|evaluat|validat|verif|govern|prov)[a-z]*[^.]{0,60}(constraint|rule|ensure)|(constraint|rule|ensure)[a-z]*[^.]{0,60}re-?(check|evaluat|validat|verif|govern|prov)' \
