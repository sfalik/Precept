# §6 slice design — constant rules participate in bound checks (`IntervalContainment` learns `rule X <= 100`)

**Plain-language summary.** Today, if an author writes `rule Score <= 900 because "…"`, the proof engine uses that fact when checking *signs* (is a divisor nonzero?) and it uses *field-to-field* rules (`rule X <= Cap`) when checking bounds — but it ignores the field-vs-constant rule when checking whether a computed value stays inside a declared `min`/`max` band. So `set Projected = Score + 100` into a `max 1000` field rejects with an overflow error even though the author already declared the fact that makes it safe. This slice closes that asymmetry: the bound checker folds declared constant rules (and their `ensure` siblings) into the field's known range, exactly the way it already folds field-to-field rules — with the same contradiction (⊥) suppression, the same staleness discipline, and without becoming a two-hop reasoner. No new syntax, no new diagnostics, no new certificate vocabulary.

**Terms used below (defined once).**
- *Fold* — the loop that intersects known facts into a field's narrowed range inside `BuildNarrowedIntervals` (the architecture doc's term).
- *⊥ (bottom)* — the empty range: a contradiction, "no value can satisfy this". Load-bearing because `NumericInterval.Contains` returns `true` for an empty argument (`NumericInterval.cs:127`) — an unsuppressed ⊥ would prove *everything*.
- *Constant fact* — a parsed record `subject op value` (`ScopedNumericFact`, `ProofEngine.cs:88-93`) extracted from a rule or ensure condition of shape `Field <= 100` (either orientation), with quantity/price values normalized to base units at parse (`Composition.cs:323-343`).
- *Half-line* — the one-sided range a single comparison licenses (`<= 100` licenses `(−∞, 100]`).
- *Blocked* — a rule/ensure that must contribute no fact (guarded, self-unsatisfiable, or own-obligation-unresolved — the discipline in `CollectBlockedConstraints`, `Composition.cs:128-168`).
- *Stale* — a fact about a field that was reassigned earlier in the same action chain (`ReassignedBefore`, `ProofLedger.cs:38-55`); the pre-state fact no longer describes the value being read.
- *Single-hop* — the engine reads a cross-field relation exactly once and never chases a third field through it (spec:256, ledger #3).

## Goal

When this slice lands, an unconditional field-vs-constant `rule` (or in-scope unguarded `ensure`) narrows the subject field's interval in `IntervalContainment` bound checks — the worked example below flips from PRE0078 to `Proven` with a certificate citing the rule — while every cell of the enumerated fact family has the disposition this document assigns it, the three cross-cutting invariant cells (⊥ suppression, single-hop, certificate re-checkability) hold with failing-test-first coverage, and the satisfiability scans' behavior is byte-for-byte unchanged.

## Worked example (validated live, 2026-07-13 — syntax oracle)

A domain-plausible renewal tracker; compiles at HEAD with **exactly one** Error, the §6 gap:

```precept
precept RenewalTracker

field RenewalScore as integer default 0 min 0
rule RenewalScore <= 900 because "Scores above 900 indicate a sync fault upstream — the source system caps at 900"

field ProjectedScore as integer default 0 min 0 max 1000

state Active initial
state Closed terminal

event SyncScore(Score as integer min 0 max 900)
event Reproject
event Close

from Active on SyncScore
    -> set RenewalScore = SyncScore.Score
    -> no transition

from Active on Reproject
    -> set ProjectedScore = RenewalScore + 100
    -> no transition

from Active on Close -> transition Closed
```

**At HEAD** (probe): `set ProjectedScore = RenewalScore + 100` → PRE0078, computedInterval `[100 .. 79228162514264337593543950335]` — the rule is ignored; `RenewalScore`'s interval is read as `[0, +∞)` from its declared `min 0` only. **After this slice**: the fold narrows `RenewalScore` to `[0 .. 900]` from the rule, the add computes `[100 .. 1000]`, which fits `ProjectedScore`'s declared `[0 .. 1000]` → `Proven`, with this certificate (Slice-0 vocabulary only):

```
Proven — ProjectedScore stays within its declared 0 to 1000.

Premises
  P1  ProjectedScore declares min 0, max 1000                    (line 6)
  P2  RenewalScore declares min 0                                (line 3)
  P3  rule declares RenewalScore <= 900                          (line 4)

Steps
  S1  ConditionNarrowing   RenewalScore: [0..+∞) restricted by P3 → [0..900]
  S2  IntervalArithmetic   [0..900] + 100 = [100..1000]   (integer +, from P2-narrowed)
  S3  BandContainment      [100..1000] fits ProjectedScore's declared [0..1000] ✓   (P1)
```

The relational twin of this example (`rule RenewalScore <= ScoreCap` with `ScoreCap` declared `max 900`) already proves at HEAD — the ledger §6-scope probe verified that asymmetry, which is the whole finding this slice closes.

## Semantic Rules

**No reduction or typing change.** The fold changes no expression evaluation rule and no typing rule; it adds one proof-obligation *discharge* refinement.

**The constant-fact fold (proof-obligation rule).** For an `IntervalContainment` obligation *o* discharged via `TryIntervalContainmentProofNarrowed`:

```
Facts(o) = { (F, op, v, anchor) parsed from unguarded rules and unguarded ensures
             |  not Blocked(source)                        — Decision 3
             ,  Subject kind = Field                       — arg cells decline, Decision 6
             ,  InScope(anchor, o.Context)                 — Decision 4 (hook contexts decline ALL
                                                             facts, anchored and unanchored, pending
                                                             OQ2; ConstraintContext declines, cell 24;
                                                             elsewhere FactAppliesToContext semantics)
             ,  F ∉ o.ReassignedBefore }                   — Decision 4 (staleness)

for each f = (F, op, v) in Facts(o), in the pinned order (Decision 8):
    seed    = dict[F]  if present, else ExtractFieldInterval(F)     — builder-or-bare seed,
                                                                      mirroring the relational fold
    narrow  = NarrowByConstraint(seed, op, v, type(F))               — existing applier, existing
                                                                      integer/decimal boundary dispatch
    dict[F] = narrow   if ¬narrow.IsEmpty                            — Decision 2 (⊥ suppression:
              (else dict[F] unchanged — the fact contributes nothing) an empty intersection is a
                                                                      contradiction, never a pass)
```

`IntervalOfNarrowed` then reads `dict[F]` at each `TypedFieldRef` leaf exactly as today (`Intervals.cs:67-76`); nothing downstream changes.

**Soundness argument (why every admitted fact is true of the value read).** The fold's claim is: *at the obligation site, the value read from F lies in the fact's half-line.*
- **Unconditional rule** — governance: every *committed* configuration satisfies every unconditional rule (philosophy § hierarchy: "enforced structurally on every operation"; defaults are covered by the rule-vs-default fold, proof-engine.md:483). A site read is a committed-pre-state read **unless** F was reassigned earlier in the chain — exactly the case the staleness gate excludes. Without that gate the fold would be circular through sequencing: `rule X <= 100`; `set X = X + 50` (provable from pre-state) followed by `set Y = X * 2` must NOT re-narrow the *new* X by the rule — the new value's rule-compliance is the pending commit check, not an established fact, and the arithmetic in Y executes before commit rejection (fault prevention is compile-time, P7/10/11; governance rejection at commit does not prevent the fault). **This argument stops at the row-to-hook boundary**: `ReassignedBefore` is stamped per action chain (`ProofEngine.cs:509-523`), and each state hook's actions are walked as their own chain (`ProofEngine.cs:229-233`), so a field reassigned by the triggering transition row's actions is *absent* from an entry hook's obligations' staleness sets — while by this design's own hook-execution model (next bullet) the hook executes pre-commit and can read the candidate value (`rule X <= 100`; row `set X = X + 50`; target-state entry hook `set H = X * 2` would otherwise narrow candidate X = 150 back to ≤ 100 inside the hook). Unanchored rule facts therefore **decline on hook contexts** in this slice (Decision 4, cell 6), pending the same runtime-ordering ruling OQ2 requests for anchored ensures.
- **Unguarded event-precondition ensure** (`on E ensure X <= 100`) — the ensure must hold *before E runs* (spec § ensures; `TryGetNumericEnsureFact` anchors it to E, `Composition.cs:287`); rows/handlers of E read pre-state satisfying it. Scoped by anchor-event match; same staleness gate.
- **Unguarded state-resident ensure** (`in S ensure X <= 100`) — holds for configurations *committed resident in S*; a transition row `from S` reads such a configuration. Scoped by anchor-state = row `FromState`. **Hook contexts are excluded** in this slice: an entry hook into S executes while S-residency is being *established*, so the target state's resident ensure is not yet a fact about the values the hook reads — see Open Question 2 (the shipped sign path's `FactAppliesToContext` hook arm, `Composition.cs:752-760`, applies it; a candidate hole routed to the Slice-0 §2.2 sweep).

**Soundness-preservation naming (principles 7 / 10 / 11).**
- *P7 (compile-time-first)*: the fold only moves obligations from `Unresolved` to `Proven` when an intersection of true facts contains the site's computed range — no check is weakened, no verdict authority moves.
- *P10 (totality)*: narrowing can only shrink an operand's interval toward its true value set (each admitted fact is true of the read value, above), so a discharge under the fold implies a discharge under the true semantics — no fault path becomes reachable.
- *P11 (static completeness)*: the two ways a narrowing fold can breach P11 are both railed: (a) the over-prove direction — an empty intersection discharging everything via `Contains(⊥) ⇒ true` (`NumericInterval.cs:127`) — is closed per-contribution by Decision 2, with the reader-side `IsEmpty` backstop (`Intervals.cs:509`) retained as second line, never the only line; (b) the false-rejection direction — feeding rule-narrowed intervals to the satisfiability scans, whose emit condition fires *more readily* on tighter intervals — is structurally impossible because the scans call the bare `ExtractFieldInterval`/`BoundedFieldInterval` and never the discharge dict (proof-engine.md:487-489; `Satisfiability.cs:316-320`), and this slice does not change that call graph (Decision 5).

**Certificate linkage (settled vocabulary, no growth).** Each *applied* fact mints one `ConditionNarrowing` step citing a `RuleCondition` (rule-sourced) or `EnsureCondition` (ensure-sourced) premise, span-cited per the Slice-0 provenance obligation (certificate doc, Architecture Grounding obligation 2 — `ScopedNumericFact` carries no span today, `ProofEngine.cs:88-93`; Slice 0 widens the record at collection time and this slice's facts ride the same widened record). A suppressed (⊥), blocked, out-of-scope, or stale fact mints **no premise and no step** — mirroring the settled `SignResolution` empty-meet posture ("an empty meet never mints a step"). `ConditionNarrowing`'s settled recompute rule (`[a,b] ∩ range(cond)`, single condition, integer-vs-decimal boundary dispatch) covers the fold's every applied contribution including the `==` point case; `!=` contributes nothing (below), so no step arises.

## Architecture Grounding

### Precept-internal placement

**Layer placement.** Entirely pipeline code in `ProofEngine` (`src/Precept/Pipeline/`). No catalog change: the fold introduces no per-member language knowledge — operators dispatch through the existing `NarrowByConstraint` (which the guard fold already uses), facts parse through the existing extractors, and the certificate kinds are existing Slice-0 catalog members. There is nothing here the catalog could own that it does not already own.

**Reuse verification (thin wiring, not a parallel definition).** Verified present at HEAD, at file:line:
- **Parse**: `TryGetNumericConstraintFact` (`Composition.cs:293-321`) — both orientations (`X <= 100` and `100 >= X` via `InvertOp`), field *and* arg subjects, static-magnitude RHS with quantity/price base-unit normalization (`TryGetStaticNumericValue`, `:323-343`). `TryGetNumericEnsureFact` (`:277-291`) — unguarded-ensure filter, event/state anchors. The guarded-rule filter (`:255-261`) and the ensure counterpart (`:281-283`) exist and are reused as-is.
- **Discipline**: `RulePredicateSelfUnsatisfiable` (`:177-185`), reusing the same `ComposeRulePredicateWithFieldBounds` emptiness computation the PRE0159 scan uses, "so the block and that scan agree" (code doc `:171-176`).
- **Apply**: `NarrowByConstraint` (`Satisfiability.cs:256-279`) — the exact integer/decimal strict-boundary dispatch and sentinel safety the guard fold defers to (`Intervals.cs:567-571` comment).
- **Seed + suppression pattern**: the relational fold (`Intervals.cs:633-654`) — builder-or-bare seed (`:640-644`), per-contribution empty-intersection suppression (`:645-653`). The constant fold copies this shape verbatim in behavior.
- **Scoping**: `FactAppliesToContext` (`Composition.cs:740-763`) — anchor-event/anchor-state matching (with the hook-arm divergence stated in Decision 4).
- **Staleness carrier**: `ProofObligation.ReassignedBefore` (`ProofLedger.cs:38-55`) — available on the obligation the fold already receives. (At HEAD, *nothing* in `ProofEngine.Intervals.cs` consults it — that is Slice-0 Hole 3; this design assumes the post-Hole-3 base and adds the same gate to its own facts.)

Net-new computation: the fold loop itself and the fact-collection call — no re-implementation of parsing, narrowing arithmetic, blocking, or scoping.

**Cross-component propagation.**
- *Pipeline*: `ProofEngine.Intervals.cs` (the fold), `ProofEngine.Composition.cs` (a semantics-only constant-fact collector sharing the existing parse helpers — Decision 3), certificate-builder wiring (Slice-0 files).
- *Runtime*: **None** — no descriptor, result-type, fault-system, or evaluator change; the compile/runtime boundary is untouched.
- *Language server*: **None structural** — hover already renders `ComputedInterval` and (post-Slice-0) certificates; the fold only changes which verdicts/intervals appear.
- *MCP*: **None structural** — `precept_compile`/`precept_proofs` DTOs unchanged; outputs change only in verdict/interval content. (Build-time check: formatters render the new certificates through the Slice-0 projection with no code change.)
- *Diagnostics*: **None** — no code added, removed, or reworded; PRE0078/PRE0159 emission *sites* unchanged; some definitions stop emitting PRE0078 because their obligation now proves (the `# EXPECT:` corpus reconciliation absorbs this).
- *Catalogs*: **None**.

**Breaking changes.** None beyond outcome changes on newly-provable definitions (Error → clean), which is the slice's purpose; the corpus/`# EXPECT:` reconciliation is the inherited acceptance-frame obligation.

### External architectural precedent

### Decision 1 — Fold placement and seam (CONFIRMS ruled seam, architecture §1.6)

A new fold inside `BuildNarrowedIntervals`, beside the shipped relational fold, seeded builder-or-bare (`builder.TryGetValue(F) ?? ExtractFieldInterval(F)`), applied via `NarrowByConstraint`, writing only `builder[F]` for field subjects.

**Stakes**: medium (ruled seam; the confirmation work is verifying the seam still matches source).
- **Rationale**: the seam is where every other per-field narrowing already composes (guard branches `:547-607`, sibling rejects `:616-627`, relational `:633-654`) and where the Slice-0 rails (staleness Hole-3 fix, any dict-write ⊥ rail) will already stand — one fold family, one rail surface. Verified at HEAD: the dict is read at exactly one leaf kind (`TypedFieldRef`, `Intervals.cs:67-76`), so a field-keyed write is the complete integration.
- **Alternatives rejected**: (a) *teaching `ExtractFieldInterval` to fold rules* — explicitly rejected by the ruled architecture ("silently becomes §1b", §1.6) and would also leak rule narrowing into the satisfiability scans (a false-rejection vector, proof-engine.md:487); (b) *a separate post-cascade pass* (like `ApplyTrustedRuleFacts`) re-running containment with constant facts — duplicates the containment reader and forfeits composition with guard/sibling/relational narrowing in a single intersection.
- **Precedent**: the relational fold itself — same seam, same seed policy, same write discipline (`Intervals.cs:633-654`).
- **Tradeoff accepted**: `BuildNarrowedIntervals` grows a fourth fact source and its activation condition (`:543`) must be extended — one more thing the function does; accepted because splitting the function is a refactor the build slice may do mechanically without design impact.

### Decision 2 — Mandatory per-contribution ⊥ suppression (CONFIRMS ruled rail, architecture §1.6; verbatim copy of the relational suppression)

An intersection that comes back empty contributes **nothing** — the fact is skipped and the field's interval stays what it was; ⊥ is never written to the dict.

**Stakes**: high (soundness rail — the single vector by which this slice could over-prove everything).
- **Rationale**: `NumericInterval.Contains` returns `true` for an empty argument (`NumericInterval.cs:127`, verified) — an unsuppressed contradictory contribution (`rule Source <= 100` on `min 200`, or rule × guard disjointness) would discharge *every* obligation reading that field. The reader-side backstop (`Intervals.cs:509`) exists but "must not be the only line of defense" (architecture §1.6): it protects only the final result interval, not a ⊥ dict entry consumed mid-expression by interval arithmetic (where `Union` has no empty special-case, `NumericInterval.cs:131-135`, and the §1.5 kernel guard deliberately launders ⊥ to Unbounded — architecture §1.8's conflict resolution places infeasibility detection at write time). Suppression-not-propagation is also semantically right for this fold: a ⊥ here means *this row/config is infeasible under the rule* — a positive unreachability claim this slice has no machinery to assert (that is §2's ⊥-arm work), so the conservative posture is "the fact contributes nothing."
- **Alternatives rejected**: (a) *write ⊥ and rely on the reader backstop* — leaves the mid-expression path open (above) and was the exact shape of the relational bug class the shipped suppression closed; (b) *treat ⊥ as proof of row-unreachability and mark obligations vacuous* — a positive claim needing §2's infeasibility machinery; asserting it from one fold would be a new soundness surface this slice doesn't own.
- **Precedent**: the relational fold's suppression, verbatim (`Intervals.cs:645-653`, comment: "writing ⊥ here would let the containment reader discharge every obligation via Contains(⊥) => true"); `RelationContradictsSubjectBounds` withholding sign facts on the same signal (`Composition.cs:601-614`).
- **Tradeoff accepted**: a genuinely contradictory rule/guard combination narrows nothing rather than flagging the contradiction — the row keeps its honest `Unresolved`/reject; surfacing the infeasibility as a diagnostic is deliberately left to the structural scans and §2. Forward-compatibility note: when the dict-write ⊥ rail (F7, §1.8) lands, this fold's write goes through it like every other — the per-contribution skip and the uniform rail are the same check at the same moment.

### Decision 3 — Fact-admission discipline: guard-null + self-unsatisfiability, semantics-only (CONFIRMS ruled posture, architecture §1.6 tradeoff leg) — with the owed circularity argument stated

Admitted sources: **unguarded rules** and **unguarded ensures** whose parsed condition is `field-or-arg op static-constant`. Excluded at collection: guarded rules (`Composition.cs:255-261` filter, reused), guarded ensures (`:281-283`, reused), self-unsatisfiable rules (`RulePredicateSelfUnsatisfiable`, `:177-185`, reused). The per-obligation *unresolved-own-obligation* block (`CollectBlockedConstraints` `:136-155`) is **not** threaded into this mid-cascade fold — the ruled "not-per-obligation-blocked-set posture" the relational fold already carries (architecture §1.6: "the §6 constant case owes its own circularity argument in the slice's adversarial review, not an assumed transfer").

**Stakes**: high (this is where the fold could trust an untrustworthy fact).
- **Rationale** (the owed circularity argument): a fact parses only from a condition of the exact shape `subject op static-constant` (`TryGetNumericConstraintFact` requires a `TypedBinaryOp` comparison with a field/arg ref on one side and a static magnitude on the other, `Composition.cs:293-321`). Such a condition contains **no fault-prone operation** — no division, no arithmetic, no access — so for plain integer/decimal subjects the rule/ensure generates **no own proof obligation** whose unproven status a trusted fact could circularly launder; there is nothing for the per-obligation block to block. The self-unsat block covers the remaining self-referential failure (a rule contradicting its own field's declared bounds), and the ⊥ rail (Decision 2) independently covers the same vector plus rule-×-guard contradictions. The one family cell where a constant-shape condition CAN carry its own obligation is a **qualified comparison** (`rule Weight <= '900 kg'`, `rule Price <= '100.00 USD'` — a qualifier-compatibility obligation on the rule's own comparison). Because this fold is the first *magnitude-sensitive* consumer of these facts (the sign path consumed them unit-insensitively — a sign is a sign in any unit; a magnitude is not), an unresolved compatibility obligation there means the normalized magnitude may not live in the subject's value space. In any such definition the compile **already rejects** on the qualifier Error, so no false-safe can *ship* — but the ledger would carry a dishonest `Proven` inside a failing compile. Resolution of that residual is **parked as Open Question 1** (three neutral options); until ruled, the acceptance criteria carry the vector so the build cannot silently pick a posture.
- **Alternatives rejected**: (a) *thread the per-obligation blocked set into the mid-cascade fold* — `CollectBlockedConstraints` reads obligation dispositions, which mid-cascade are order-dependent (obligations after the current one still carry their initial disposition), so the fact stream would vary with obligation ordering — deterministic but order-sensitive semantics for no gain on the cells where the block is vacuous (above), and a signature change through `TryDischarge` that Slice 0's reshape would immediately churn; kept available as OQ1 option (c) with a sequencing fix. (b) *no discipline at all (fold every syntactic constant rule)* — folds guarded rules as unconditional facts (a false "safe" on guard-false paths — the exact failure the guarded-rule filter comment names, `Composition.cs:255-260`) and lets a self-unsatisfiable rule's ⊥ ride solely on one rail.
- **Precedent**: the shipped relational fold uses exactly this posture — its collector `CollectUnconditionalRelationalFacts` (`Composition.cs:539-548`) applies the guard-null filter without the per-obligation block, with a stated structural-circularity argument (`:531-538`); the blocked variant `CollectRelationalFacts` (`:197-216`) exists and has **zero callers** (grep-verified — drift ledger item 6). Caveat: for *these exact fact records* the closer precedent — the sign path (`ApplyTrustedRuleFacts` → `CollectTrustedNumericFacts`, `:81`/`:248`) — DOES apply the per-obligation block; the resulting sign-fold/interval-fold divergence on the same fact stream in the qualified-rule residual compile is priced into OQ1, not hidden behind the relational precedent.
- **Tradeoff accepted**: the fold trusts a constant rule regardless of the disposition of unrelated obligations elsewhere in the definition — acceptable because (per the argument above) the rule's own truth at committed state is a *runtime governance* guarantee, not a function of other obligations' proofs; the qualified-cell residual is the one place this reasoning thins, and it is parked, not swallowed.

### Decision 4 — Scoping and staleness applied at fold time (slice-level; derives from spec §0.6 item 7 and the anchor semantics)

Each fact is applied only when (a) its anchor matches the obligation's context — unanchored rule facts apply to `TransitionRowContext`, `EventHandlerContext`, and `FieldExpressionContext`; event-anchored ensure facts apply only to rows/handlers of that event; state-anchored ensure facts apply only to `TransitionRowContext` with matching `FromState`; `StateHookContext` receives **no facts of any kind** (anchored or unanchored) pending OQ2; `ConstraintContext` receives none (N/A at HEAD — cell 24) — and (b) its subject field is not in `obligation.ReassignedBefore`.

**Stakes**: high (both gates are soundness-load-bearing — see the Semantic Rules soundness argument).
- **Rationale**: scoping is the existing `FactAppliesToContext` semantics (`Composition.cs:740-763`) **minus hook contexts entirely** — both the state-hook arm (`:752-760`) and the unanchored pass-through (`:762`, which returns `true` in *every* context). The anchored half: a state-anchored ensure matched to `StateHookContext` would apply the *target* state's resident ensure to an entry hook that executes while residency is still being established — values violating the ensure can reach the hook's arithmetic before commit-time rejection, and compile-time fault prevention (P7/10/11) cannot lean on a rejection that happens after the fault. The unanchored half fails for the *staleness* reason: the staleness carrier does not cross the row-to-hook boundary — `ReassignedBefore` is stamped per action chain (`ProofEngine.cs:509-523`) and each hook is walked as its own chain (`ProofEngine.cs:229-233`) — so a field the triggering row reassigned is invisible to the hook's staleness gate, and an unanchored rule fact would narrow the candidate value the hook reads (the cross-boundary vector in the Semantic Rules soundness argument, mandatory failing-test row in cell 6). Whether runtime hook ordering makes any hook read committed pre-state is exactly the canon gap OQ2 records; until ruled, hooks decline everything, and the fold-local applicability wrapper **gates contexts positively** — it does not inherit the shared helper's unanchored `true`. Whether the shared helper's hook behavior (both arms) is itself a live hole for the *sign* path is routed to the Slice-0 fail-open sweep and parked as Open Question 2. Staleness is spec law: "When a field is reassigned, prior proof facts about that field are invalidated before the new assignment's facts are stored" (spec §0.6 item 7, quoted in `ProofLedger.cs:42-45`) — and the Semantic Rules section shows the concrete false-safe (`rule X <= 100`; `set X = X + 50`; `set Y = X * 2`) the gate prevents. This gate **depends on Slice-0 Hole 3** (at HEAD, `BuildNarrowedIntervals` consults `ReassignedBefore` nowhere — grep-verified); the constant fold lands on the corrected base and must go through the same rail, not a private copy.
- **Alternatives rejected**: (a) *reuse `FactAppliesToContext` unmodified* — inherits both questioned hook behaviors (the anchored arm AND the unanchored pass-through) before OQ2 is ruled; a magnitude-sensitive consumer must not adopt a questioned arm by default. (b) *skip ensure facts entirely (rules only)* — forfeits the family's ensure half for no soundness gain; the anchor semantics are precisely what makes scoped ensures sound, and the ruled family axes name "rules-vs-ensures" explicitly. (c) *apply state-anchored facts to wildcard rows* (`FromState == null`) — unsound (the wildcard fires from states the ensure doesn't govern); the existing string-match semantics already declines this correctly (null ≠ "S"). (d) *extend the staleness carrier across the row-to-hook boundary* (stamp hook obligations with the triggering rows' reassignment sets) so unanchored facts could stay admitted on hooks with the same gate rows get — not settled here: it is a ledger/collection reshape adjacent to Slice 0, it still needs the same runtime-ordering canon statement to define which rows "trigger" which hooks, and this design must not settle that mechanism unilaterally; kept available as OQ2 option (d).
- **Precedent**: the sign path applies the same anchor semantics for these same fact records (`ApplyTrustedRuleFacts` → `FactAppliesToContext`) — *except* that it also applies facts on hook contexts (both arms), which is exactly the behavior this design declines and routes to the sweep via OQ2; every guard-narrowing strategy already honors `ReassignedBefore` (`Strategies.cs:423/:678/:771/:1105`, `QualifierNarrowing.cs:141-142`) — this fold joins the shipped discipline rather than inventing one.
- **Tradeoff accepted**: hook-context obligations get **no fact-sourced narrowing at all** — neither ensure-sourced nor rule-sourced — until OQ2 resolves (a precision loss on a narrow cell, never a soundness loss); a fold-local applicability wrapper diverges from the shared helper by two behaviors (the anchored hook arm and the unanchored pass-through) until the sweep rules on them (the divergence is documented here and in the certificate coverage — a reviewable seam, not a silent fork).

### Decision 5 — Single-hop rail: `ExtractFieldInterval` stays rule-blind; the mixed chain stays undischarged (CONFIRMS ruled rail — architecture §1.6, spec:256, ledger #3)

The constant fold writes only the discharge dict. `ExtractFieldInterval` (`Intervals.cs:202-220`) — the bare-interval read used by the relational half-line (`:635`), the sign relation (`Composition.cs:633`), the contradiction check (`:584-588`), and every satisfiability scan — learns nothing.

**Stakes**: high (a locked spec decision sits directly on this rail).
- **Rationale**: the spec locks it — "The mechanism is single-pass and depth-bounded (no transitive chasing of a third field), per §0.4. This single-hop bound is deliberately retained: the engine never combines two separately-declared facts to derive a bound neither states alone" (`precept-language-spec.md:256`); ledger #3 rules the §1b override NOT authorized. Concretely: with `rule X <= Y` and `rule Y <= 100`, the relational half-line for X reads Y via bare `ExtractFieldInterval(Y)`; if that function folded constant rules, X would silently inherit `<= 100` through Y — a two-hop derivation. The mixed chain therefore **stays undischarged**, by construction, and gets an explicit acceptance cell. The scan-isolation invariant (proof-engine.md:487) is the same rail seen from the rejection direction: scans keep reading bare intervals, so the fold can never manufacture a false rejection.
- **Alternatives rejected**: *fold constant rules into `ExtractFieldInterval`* — simpler wiring (one function, every reader benefits), rejected as the exact silent-§1b vector the architecture names ("`ExtractFieldInterval` must not learn to fold constant rules, or the relational fold silently becomes two-hop", §1.6), and it would additionally feed rule narrowing to the satisfiability scans (false-rejection vector).
- **Precedent**: the shipped relational fold's own one-hop-by-construction read (proof-engine.md:1427: "read via the bare `ExtractFieldInterval(Y)` … never via the `narrowed` dictionary").
- **Tradeoff accepted**: authors with a genuine chained bound must state the consequence as one rule (`rule X <= 100` directly) — the spec's own prescribed, legible fix (spec:256 final sentence); the rejection message for the undischarged mixed chain should keep naming the direct-rule shape (existing residual-message behavior, verified acceptable at build).

### Decision 7 — Certificate mapping: existing Slice-0 vocabulary only (CONFIRMS settled membership — certificate doc Decision 6)

Applied fact ⇒ one `ConditionNarrowing` step citing one `RuleCondition` or `EnsureCondition` premise (span-cited). Suppressed/blocked/stale/out-of-scope facts ⇒ nothing. No new step kind, no new premise kind, no payload widening.

**Interval-input citation rule (normative).** A `ConditionNarrowing` step's conclusion must recompute from its cited children (`[a,b] ∩ range(cond)` — the input `[a,b]` comes from the cited children, certificate doc's recompute table). When the fold's seed for F is the bare declared interval, the step cites the `DeclaredBound` premise as its interval child; when the seed came from the accumulated dict (guard/sibling/relational/prior-constant contributions), the step cites **the step that produced the accumulated interval** as its interval child — never `DeclaredBound` by default. A build that defaulted every `ConditionNarrowing` input to the declared interval would emit certificates whose conclusions do not recompute from their cited children. (The worked example's S1 cites only P3 with the declared seed because `RenewalScore` has no other narrowing source at that site — the bare-seed case, not the general one.)

**Stakes**: medium (public vocabulary — but the membership decision is already settled upstream).
- **Rationale**: the settled membership names this slice explicitly ("§6 constant-rules is `ConditionNarrowing` citing a `RuleCondition` — both ship at Slice 0", certificate doc Decision 6), and the settled recompute rule (`[a,b] ∩ range(cond)`, half-line/point, integer-vs-decimal dispatch) is *exactly* `NarrowByConstraint`'s semantics — the step's independent recomputation and the engine's computation are the same bounded operation. `EnsureCondition` (Decision 1 item 7) covers the ensure half. The no-step-on-suppression posture mirrors the settled `SignResolution` empty-meet rule, keeping "the certificate never claims a narrowing that didn't happen."
- **Alternatives rejected**: (a) *a distinct `RuleNarrowing` step kind* — vocabulary growth with an identical recompute rule; trips the settled growth accounting (certificate doc Falsifier 2) for zero information gain (the premise kind already distinguishes rule from guard from ensure); (b) *recording suppressed facts as annotated steps* — a step whose conclusion was discarded fails the recomputable-conclusion contract.
- **Precedent**: the settled coverage table's interval-containment row already lists `RuleCondition` among that path's premises and `ConditionNarrowing` among its steps.
- **Tradeoff accepted**: a reader of a certificate cannot see that a contradictory rule was *considered and suppressed* — the certificate shows only the derivation performed; the infeasibility story stays with the structural scans (PRE0159) and §2. Consistent with the settled format's posture; noted so nobody adds a "suppressed-fact annotation" ad hoc.

### Decision 8 — Fold order pinned: after the relational fold, as the last contribution source; intra-fold, facts apply in collection order (rules then ensures, declaration order within each) (slice-level)

**Stakes**: low-medium (all orders are sound; both levels must be pinned because ⊥ suppression makes order observable).
- **Rationale**: with facts about the same field, non-⊥ intersections commute (F9: "the intersection of half-lines is order-independent"). Order becomes observable exactly when one contribution empties against the accumulated seed and is suppressed: relational-first (`[50,200]` from `X >= Y`) then constant `X <= 40` → ⊥ → constant suppressed → keep `[50,200]`; the reverse keeps `[0,40]`. Both are sound supersets of the (actually empty) feasible set. Pinning **constant last** (i) leaves the shipped relational fold's code and behavior byte-identical — the slice is a pure append, minimizing re-review surface; (ii) preserves the shipped relational fold's own suppression semantics unchanged (its seed never contains constant contributions, so no shipped behavior shifts); (iii) matches the single-hop reading order (relational half-lines read *bare* intervals regardless of this fold, so mutual contamination is impossible either way — the pin is for suppression asymmetry only). **Intra-fold order is pinned by the same argument**: the same suppression asymmetry is observable *inside* the constant fold when two constant facts on one field are mutually contradictory (cell 21a — `rule X <= 10` + `on E ensure X >= 20`: the first-applied half-line survives, the second empties and suppresses). The pin is the collection order `CollectTrustedNumericFacts` already produces — rules in declaration order, then ensures in declaration order (`Composition.cs:250-272`) — so the fold iterates the fact list as collected, with no re-sort. Rule-vs-rule mutual ⊥ is separately diagnosed (PRE0155 pair scan), but the scans are rule-only, so for rule-vs-ensure and ensure-vs-ensure pairs the pinned iteration is the only thing standing between the semantics and nondeterminism-by-omission.
- **Alternatives rejected**: (a) *constant fold first* — changes what the relational fold's suppression sees, silently altering shipped relational outcomes on mixed-⊥ definitions; (b) *iterate to a joint fixpoint* — spec §0.4 forbids fixpoints ("single-pass"); (c) *detect the mixed-⊥ case and reject as contradictory* — a positive infeasibility claim owned by the scans/§2, not this fold (Decision 2 rationale); (d) *intra-fold: re-sort facts (e.g. tightest-first or ensures-first)* — any re-sort is an extra semantics to specify and defend for zero soundness gain (all orders yield sound supersets); the collection order is already deterministic, already shipped for the sign path, and costs nothing.
- **Precedent**: the existing source order in `BuildNarrowedIntervals` is already a pinned pipeline (guard → sibling → relational); appending is how the relational fold itself arrived. Intra-fold: `CollectTrustedNumericFacts`'s rules-then-ensures declaration-order collection is the shipped order the sign path already consumes.
- **Tradeoff accepted**: on mixed-⊥ definitions the surviving narrowing is the relational one, which may be the looser of the two — a precision asymmetry on infeasible configurations only (which reject on their own obligations anyway); intra-fold, the surviving half-line of a mutually-contradictory pair is the earlier-declared/rule-side one, same character of asymmetry. The behavior-pinning test rows (family cells 21 and 21a) freeze both so a future reorder is a visible semantic change, and the F9 caveat is re-inherited by §1a exactly as the architecture flags (§2.4).

## Open questions (all parked — neutral framing; nothing here is settled by this design)

1. **Qualified constant rules — the first magnitude-sensitive consumption of trusted facts.** A rule like `rule Weight <= '900 kg'` or `rule Price <= '100.00 USD'` carries a qualifier-compatibility obligation on its own comparison. The fold consumes the *normalized magnitude* (`Composition.cs:330-339`); if that own-obligation is unresolved (incomparable units/currencies), the magnitude may not live in the subject's value space. In every such case the compile already rejects on the qualifier Error, so no false-safe ships — but the ledger would carry a wrong `Proven` inside the failing compile (an inspectability/honesty cost, not a shipped-soundness one). The residual also contains an intra-compile *divergence*: the sign path consumes the same `ScopedNumericFact` stream WITH the per-obligation blocked set (`ApplyTrustedRuleFacts` → `CollectTrustedNumericFacts`, `Composition.cs:81`, `:248`) while this fold consumes it WITHOUT (Decision 3) — so in the qualified-rule residual compile one consumer trusts a fact the other blocks, and the two certificates disagree about the same declaration inside one compile. Outcome-safe for the same reason, but a second inspectability cost the ruling should price when weighing options (b)/(c) — and a caveat on Decision 3's relational-fold precedent framing, since the closer precedent for these exact fact records applies the block. *Canonical area checked*: `proof-engine.md:1522-1528` (constraint-fact scoping) and architecture §1.6's tradeoff leg — neither addresses magnitude-sensitive consumption; the sign path's shipped posture is unit-insensitive-safe and thus silent on this. *Options (neutral)*: **(a)** keep the semantics-only posture and accept the failing-compile-only ledger residual, documented; **(b)** add a unit-space gate at the fold (admit a qualified fact only when the rule's own comparison discharged qualifier-clean — statically checkable per definition, order-independent); **(c)** sequence rule-condition obligations ahead of row obligations and thread the per-obligation blocked set (strongest discipline; a cascade-ordering guarantee plus signature threading that Slice 0's reshape could carry). Also routed to the Slice-0 §2.2 sweep as a *candidate* pattern ("magnitude consumers of facts whose producing comparison is unproven").
2. **Fact application on hook contexts — rules AND ensures (and the sign path's existing behavior).** Two distinct admissions are in question, and this design's fold excludes **both** (Decision 4 — conservative, precision-only cost). *Anchored*: `FactAppliesToContext` matches a state-anchored fact to `StateHookContext` by `AnchorState == Hook.StateName` (`Composition.cs:752-760`) — for an *entry* hook this applies the target state's resident ensure to expressions that execute before that residency is committed. *Unanchored*: the same helper returns `true` for unanchored facts in every context (`:762`), but the staleness carrier does not cross the row-to-hook boundary — `ReassignedBefore` is stamped per action chain (`ProofEngine.cs:509-523`) and each hook is walked as its own chain (`:229-233`) — so `rule X <= 100`; row `set X = X + 50`; entry hook `set H = X * 2` would narrow the candidate X = 150 the hook can read. Both admissions hinge on the same unstated canon: whether runtime ordering guarantees hook reads see committed pre-state (ensures checked before hook evaluation? hooks before or after row actions apply? entry-vs-exit distinction?) — spec §0.6 item 7 covers reassignment sequencing, not hook ordering. *Open for the owner*: (a) confirm the exclusion as the end-state rule for all magnitude/sign consumers and treat the sign path's hook behavior (both arms) as a candidate fail-open (route to the §2.2 sweep — where this design has already sent it); (b) establish the runtime-ordering guarantee in canon and re-admit hook contexts (the statement must cover both what hooks read relative to row effects AND when ensures are checked relative to hooks); (c) split by hook direction if entry/exit hooks are distinguishable in the typed model; (d) extend the staleness carrier across the row-to-hook boundary (stamp hook obligations with the triggering rows' reassignment sets — a ledger/collection reshape, stated as a Slice-0/build dependency if chosen) so unanchored facts could re-admit under the same gate rows get; (a)–(d) are combinable per-arm. *Canonical area checked*: `proof-engine.md` (no hook-ordering statement found), spec §0.6.
3. **Inexpressible / unexploited cells — future engine-capability scope, not syntax.** Three cell groups decline because the reuse parse cannot (or deliberately does not) represent them: **compound conditions** (`rule X >= 0 and X <= 100` — top-level `And`, `Composition.cs:301-302`); **length/count-measure subjects** (`rule Q.count <= 10`, `rule Name.length <= 50` — member-access subjects, `TryGetNumericSubjectRef` `:719-733`); and the two **state-boundary ensure kinds** (`to S ensure` / `from S ensure` — `TryGetNumericEnsureFact`'s `_ => false` arm, `:285-290`, cells 9a/9b), of which `from S ensure` is the semantically adjacent one (it must hold for a `from S` transition to proceed) but its check-vs-row-action ordering is unstated in canon (the OQ2 gap class). All are *already-authorable syntax*; the question is whether a later slice widens the fact parse (an AND-of-leaves split is bounded and single-pass; a member-access subject would need a measure-tagged fact record feeding the length/count paths; the state-boundary kinds need the ordering canon first) or the declines stand with an author-facing rewrite hint (two rules; bounds on the declaration; a `StateResident` restatement). No option is recommended here. *Canonical area checked*: architecture §1.6/§1.7 (the §1a multi-term fact is the only ruled fact-shape widening; neither cell is claimed by it), certificate doc Decision 6 (growth accounting would need updating if a new inference shape arrives).
4. **Ensure-side self-unsatisfiability asymmetry.** `RulePredicateSelfUnsatisfiable` and the PRE0159 scan cover **rules only**; a self-unsatisfiable *unguarded ensure* (`in S ensure X <= 100` on `X min 200`) reaches this fold guarded solely by the ⊥ rail (sufficient for soundness — family cell 12's mandatory test) and, separately, appears to have no PRE0159-analogue diagnostic. *Open for the owner*: whether the diagnostic gap is (a) routed to the structural-severity/scan family as a candidate new scan, (b) accepted as covered by initial-state satisfiability + runtime governance, or (c) folded into the §2.2 sweep's remit. This slice's rail posture is safe under any answer. *Canonical area checked*: `proof-engine.md` § satisfiability scans (rule-pair and rule-self scans only), `diagnostic-system.md` not re-read for ensure-unsat codes — verify at build before treating the gap as confirmed.
