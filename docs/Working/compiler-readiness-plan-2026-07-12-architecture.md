# Stage 0b — Proof-Engine Architecture

**What this is.** Three independent architects proposed this foundation through distinct lenses — soundness-first, legibility-first, reuse-first. They converged on ~90%; that convergent core is **locked** below (with four-leg rationale). All four owner decisions are now ruled (2026-07-12): the three-way verdict is a **discriminated union** (Decision A); the independent re-checker is **retracted from the MVP** — deferred to a later phase, so the MVP produces a certificate *format* that is re-checkable in principle but runs no live checker (Decision B); the certificate step-vocabulary's **source** is a spec-enumerated **`CertificateSteps` catalog** (Decision C, C1 — its *membership* is unruled, owing the §5a design pass); and the dead-end→dead-end disposition is resolved by the **dead-end = Error** severity ruling (F5) — which makes relabeling the dead-end→dead-end suppression outcome-neutral (the full owner-ruled structural-severity family lives in `compiler-readiness-plan-2026-07-12-structural-severity.md`). **No *blocking* architecture decision remains** — but three slice-level items are open or unstated: the owner-choosable Presence/KeyPresence configuration-witness cell (§1.4), the `CertificateSteps` catalog membership (§5a design pass), and the length-witness interval plumbing (§1.4 F8). Decision A (the DU) is CLAUDE.md-mandated by the "DU over nullable fields" rule, so it is a confirmation, not a genuinely open owner gate. An adversarial pass over the current engine found **four live fail-open soundness holes** (the design previously named one); all four are written up in the soundness section as Slice-0, failing-test-first fixes — because with the re-checker deferred, MVP soundness comes from fixing the engine directly, not from an independent replay.

**Terms (defined once).** *Verdict* = the outcome of a proof obligation. *Certificate* = the show-your-work note attached to every verdict, re-checkable by hand (ledger `:11`). *Witness* = one concrete set of values that breaks a rule, shown on a proven-violating rejection. *⊥ (bottom)* = the empty interval. *Single-hop / anti-transitivity* = the engine reads a cross-field relation exactly once and never chases a third field through it (spec:256, ledger #3). *Fold* = a loop that intersects facts into a field's narrowed interval.

## 1. LOCKED — the convergent core

### 1.1 Three-way verdict, certificate on every verdict

The verdict is a **discriminated union** — `ProofVerdict` — with three cases (ruling #6, and **Decision A RULED by the owner 2026-07-12: the DU**): **`Proven`** (carries its certificate); **`ProvenViolating(witness)`** (rejected, Error per #10, carries a certificate + a validated witness); **`Unresolved(condition)`** (rejected, carries a certificate + the printed missing condition). Each case carries **only its own evidence** — no case can hold another's payload, so "a witness on an unresolved verdict" is structurally unrepresentable. **Every** verdict carries a certificate (ruling #2 is universal). Today the disposition is binary — `ProofDisposition { Proved = 1, Unresolved = 2 }` (`ProofLedger.cs:94–98`) — with the "how" smeared across nullable siblings (`Strategy?`, `EmittedDiagnostic?`, `ComputedInterval?`, `ProofLedger.cs:24–32`); the DU replaces both the enum and the nullable siblings. The three-way split is mostly a **re-labeling of distinctions the cascade already computes**: `TryLengthContainmentProof` already returns three-valued `bool?` (`ProofEngine.cs:1093–1100`), and a computed interval entirely outside its band is already knowable at discharge.

**RULED (owner, 2026-07-12).** The representation is the `ProofVerdict` DU, not an enum extension with nullable evidence fields. The three cases and their non-overlapping payloads (certificate on all; witness only on `ProvenViolating`; missing-condition only on `Unresolved`) are the varying-shape case CLAUDE.md's "DU over nullable fields" rule names directly.

- **Rationale.** The evidence payloads *are* varying shapes: a witness belongs to violation, a missing-condition to non-proof, nothing to a clean proof beyond the certificate. A DU makes the illegal combinations unrepresentable (no runtime invariant to enforce by hand at construction sites); an enum-plus-nullables would leave "Witness set on a Proven verdict" expressible and guarded only by convention. Ruling #6 requires three distinct author-facing outcomes with distinct payloads; ruling #10 makes the always-violating case a hard Error.
- **Alternatives rejected.** (a) Enum extension (`ProvedViolating = 3`) + nullable `Certificate?`/`Witness?` on `ProofObligation` — minimal churn and every existing `Disposition` scan keeps working, but weaker typing: the "witness ⇒ violating" invariant is enforced by construction sites, not the type. Rejected: the owner weighted structural correctness over migration cost (pre-release, one-time fixture churn). (b) Keeping the binary disposition and expressing violation only in diagnostics — loses the machine-readable verdict the LS/MCP (`precept_proofs`, hover) must carry (pipeline-eval §5).
- **Precedent.** CLAUDE.md's Catalog/DU rule ("use discriminated unions for varying shapes; don't paper over shape differences with nullable fields"). Internally, the count-containment path already emits an obligation-shaped, guard-naming message (`ProofEngine.Diagnostics.cs:141–168`) that the DU's `ProvenViolating` case generalizes.
- **Tradeoff accepted.** A breaking reshape of the ledger surface — every consumer (MCP DTOs, hover) + ~3,600 test fixtures migrate in one slice. Accepted: the churn is one-time and pre-release (solo-dev), and pipeline-eval §5/§6 budgets it.

### 1.2 Spec-enumerated certificate step vocabulary, built during discharge

A certificate is a small derivation: **premises** (each quoting an author declaration — a bound, a guard, a rule, a reject-row-above — with its source line) and **steps** (each applying one primitive inference from a closed, spec-enumerated vocabulary, carrying its own recomputable conclusion). Certificates are **built during discharge from values the folds already hold** — bookkeeping, not a second analysis pass. Every step renders to one author-readable line ("`Amount` declares `max 100` (line 5)"; "`[0..900] + [0..100] = [0..1000]`"; "`[0..1000]` fits `Total`'s declared `[0..1000]` ✓").

*(The vocabulary source was **Decision C**, now **RULED (owner, 2026-07-12): the source is a new spec-enumerated `CertificateSteps` catalog** (C1), not the existing `ProofStrategy` enum — see §3. The catalog's **membership** — the actual step kinds — is **not** ruled; it owes the §5a certificate-format `/design` pass, and the step kinds named in this doc are illustrative sketches for that pass. What is locked regardless of membership: the vocabulary is closed and spec-owned; steps carry recomputable conclusions; premises quote the author's declarations verbatim by span.)*

- **Rationale.** Ruling #2 leg 1 requires a legible, independently re-checkable certificate from a small spec-enumerated vocabulary. Recomputable-conclusion steps are the only shape a genuinely independent checker can replay.
- **Alternatives rejected.** A free-text explanation string (legible once, not re-checkable, drifts silently); a strategy-name-only label (not a derivation — nobody can replay "proved by FlowNarrowing"); an SMT-style proof term (checkable but unreadable — fails the legible leg and the right-sized leg).
- **Precedent.** Proof-carrying code and SMT proof formats (Alethe/LFSC) where a small replayer validates a large prover; internally, the interval message already surfaces the computed interval (`ProofEngine.Diagnostics.cs:119–126`) and `AuthoredMin/Max` exist so display uses the author's own numbers (`ProofRequirement.cs:184–197`).
- **Tradeoff.** Certificates are built for every obligation including proven ones — allocations the boolean cascade doesn't pay. Accepted: hover/`precept_proofs` showing *why safe* is half the product, and certificate length is bounded by expression size (no search), so there is no blow-up.

### 1.3 Certificate format, re-checkable in principle — no live re-checker in the MVP

**Decision B RETRACTED — the independent re-checker is not an MVP decision.** The phases doc already scoped it out: §5a — the certificate *format* — is the MVP prerequisite ("**Verdict: PREREQUISITE — for half (a) only.**", `proof-engine-mvp-and-proof-phases-2026-07-12.md:285`), whereas §5b — the independent *re-checker* — is a separate, later item ("*(b) The independent re-checker* — honestly priced, this is **Large**, not a bolt-on … a second checking implementation", `:280`), whose value is "builder-side drift defense, not author unblocking" ("the deeper benefit of half (b) is to the *builder*: an independent re-check that fails loudly whenever a strategy drifts", `:283`), and which the roadmap places as a later phase, not a gate ("**Recommended but deferrable** — value is builder assurance, not author unblocking", `:503`). There was never a live-re-checker decision for this architecture to make in the MVP; the earlier framing overreached.

**What the MVP ships.** A certificate *format* that is **legible and re-checkable in principle** — by hand, or by the future §5b checker when it lands. Every step carries its own recomputable conclusion from cited children, and every premise cites the source span where the author's declaration actually appears, so a reader (human now, `CertificateChecker` later) can replay the derivation without trusting the engine. **What the MVP does NOT ship:** no live re-checker module, no always-on production replay, and **no checker-gated mint** — a `Proven` verdict is minted by the discharge cascade, not by passing an independent replay first. The format's re-checkability is a property of its *shape* (recomputable steps, span-cited premises), designed in now so the §5b checker is a later addition rather than a retrofit.

- **Rationale.** With no live checker in the MVP, MVP soundness cannot lean on replay — it comes from fixing the engine directly (see the soundness section). The certificate format still earns its place: it makes hover/`precept_proofs` show *why safe*, and it is the artifact the future §5b checker replays, so laying its shape down now avoids a costly retrofit.
- **Alternatives rejected.** (a) An always-on checker-gated mint in the MVP — retracted: §5b is Large ("a second checking implementation", `:280`) and deferrable (`:503`); minting through a replay the MVP doesn't build is not on the table. (b) A free-text or strategy-name-only justification — not re-checkable even in principle (nobody can replay "proved by FlowNarrowing"); drifts silently.
- **Precedent.** Proof-carrying code and SMT proof formats (Alethe/LFSC), where a small replayer *can* validate a large prover — the format is designed for replay whether or not a replayer is running yet. The phases doc's own §5a/§5b split (`:285` vs `:280/:283/:503`).
- **Tradeoff accepted.** No independent confirmation runs in the MVP — a strategy bug that also corrupts its own certificate would ship uncaught until §5b lands. Accepted: the phases doc rates §5b's value as builder-side drift defense, not author unblocking (`:283`), and the Slice-0 engine fixes (soundness section) close the *known* holes directly rather than relying on a replay to catch them.

### 1.4 Witness with a mandatory validation gate

A `ProvenViolating` verdict requires a witness that is **concretely re-evaluated against every collected fact and actually violates**. Construction: pick each free input's narrowed-interval corner in the violating direction, then evaluate the site expression exactly (collapsing interval arithmetic to point arithmetic by binding each leaf to a point interval — reusing `IntervalOfNarrowed` itself, so witness-verifier and prover cannot disagree on arithmetic semantics), and re-check the assignment against every guard/rule/reject-row fact. **Unvalidated ⇒ demote to Unresolved.** No nullable "witness pending"; no corner presented as a proven violation unless it was executed. Hard cap on corners (k ≤ 6 leaves per ruling #2 leg 3); over cap ⇒ Unresolved.

**The 12-family witness grid** (closing the open cells from pipeline-eval §4):

| Family | Verdict | Witness on ProvenViolating |
|---|---|---|
| IntervalContainment, LengthContainment, CountContainment | three-way | **value witness** (concrete breaking value + violating result; length/count endpoints already carried, `ProofRequirement.cs:227–235`) |
| Numeric (divisor / sqrt / default-bound) | three-way | **value witness** (the value-at-fault) |
| IndexBounds | three-way | **value witness** where index/count static; else Unresolved |
| Presence, KeyPresence | three-way | **configuration witness** (the path/scenario admitting the bad state) — or N/A for MVP, see Decision note |
| QualifierCompatibility, QualifierChain, AssignmentQualifier, Dimension, DimensionalProduct | three-way | **N/A** — category mismatch (every value violates); the existing narrowed-vs-required rendering (`ProofEngine.cs:961–1048`) *is* the witness-equivalent |

*Presence/KeyPresence: the value witness is a configuration, not a number, and needs new (non-interval) machinery. Locked position: they get the three-way verdict + certificate now; the configuration-witness is **deferred to a post-MVP cell** (the diagnostic already names the unguarded subject) unless the owner wants it in-MVP. This is the one grid cell the reuse and soundness lenses split on — flagged, low-stakes, defaulting to deferred.*

*Two grid caveats the adversarial pass surfaced (F8), stated so the value-witness rows are not over-promised:*
- *Point-binding reaches only **field** leaves in the MVP. The witness constructor collapses interval arithmetic to point arithmetic by binding each leaf to a point interval — but `IntervalOfNarrowed` resolves a field-element leaf directly (`ProofEngine.Intervals.cs:92`) while an arg leaf routes through `ExtractArgInterval` (`:99`), which the point-binding does not thread. So a **value witness whose corner depends on an event-arg leaf or an element read cannot be point-evaluated until §2** wires arg/event-input narrowing. Until then those sites **demote to `Unresolved`** — the mandatory validation gate (§1.4) keeps this sound: an un-point-evaluable corner fails validation and is never presented as a proven violation. The grid's value-witness cells therefore degrade to `Unresolved` on arg/element leaves, not to a false `ProvenViolating`.*
- *The **length-witness** needs plumbing the earlier draft assumed present: only the **count** path carries a computed interval today (length/count endpoints are carried per `ProofRequirement.cs:227–235`, but the length leaf does not yet surface a computed interval the corner picker can read). LengthContainment's value-witness therefore ships only once that interval is plumbed; absent it, LengthContainment `ProvenViolating` demotes to `Unresolved` under the same gate.*

- **Rationale.** A witness the compiler hasn't executed is a claim, not evidence; one false "breaking example" destroys author trust in every future rejection. Validation-at-mint makes a wrong witness a caught bug, not a shipped lie. Interval corners are not always realizable (e.g. `X − X`, repeated variables the four-corner `Multiply` treats as independent, `NumericInterval.cs:85–92`), so validation is mandatory.
- **Alternatives rejected.** Emitting the unvalidated interval corner (over-claims exactly when the author declared the most rules); searching inward for a witness when the corner fails (a capped search — Unresolved-with-missing-condition is the honest, free verdict there).
- **Precedent.** Model checkers replay counterexample traces; property-based testing always concretely re-runs a reported counterexample.
- **Tradeoff.** Some genuinely-violating sites (violation hidden mid-interval) report Unresolved (numbers only, still rejecting) rather than ProvenViolating — under-claim accepted over ever over-claiming.

### 1.5 §3 money — pure catalog wiring + one kernel guard

Attach `IntervalTransfer` to the **whole** money/quantity/price op-meta family (`Operations.cs:437–559`, enumerated not tripped-over: `MoneyTimesDecimal`, `MoneyDivideDecimal`, `MoneyDivideMoneySameCurrency`/`CrossCurrency`, `MoneyDivideQuantity/Price/Period/Duration`, and the quantity siblings), reusing the existing delegate slot (`Operation.cs:108`), the shared `Multiply/Divide/Add/SubtractTransfer` helpers (`Operations.cs:1332–1349`), four-corner `NumericInterval.Multiply/Divide` with divisor-spans-zero → Unbounded safety (`NumericInterval.cs:85–102`), and the generic dispatch (`Intervals.cs:102–112`) — **zero engine code**. Any transfer whose result-space is unverified (the price-space `USD/h × h` cells, period/duration magnitude space) is **omitted** — no transfer = Unbounded = conservative reject, never over-prove.

**Kernel guard (the one place the MVP touches the interval kernel):** corners computed over the `Empty` sentinel (`Empty = new(0m, -1m)`, i.e. `[0, -1]`, `NumericInterval.cs:29`) produce *non-empty garbage* (e.g. `Empty × [2,3] = [-3,0]`) that sails past the `IsEmpty` backstop (`Intervals.cs:509`) and could discharge falsely. The `Divide` divisor-spans-zero guard does **not** catch it: `other.Min <= 0m && other.Max >= 0m` (`NumericInterval.cs:97`) is `0 <= 0 && -1 >= 0` = **false** for `Empty=[0,-1]`, so an empty divisor falls through to the four-corner path and crashes/garbages rather than returning Unbounded. Add an `IsEmpty ⇒ Unbounded` (or propagate-Empty) guard **inside the `NumericInterval` methods themselves** so no call site can forget — and the guard must cover **`Scale`** as well, not just `Multiply/Divide/Add/Subtract`: `Scale` (`NumericInterval.cs:110`) today guards only `IsUnbounded`, so an `Empty` operand flows straight into `ScaleBound` and produces the same non-empty garbage. The ⊥-guarded kernel surface is therefore `Multiply/Divide/Add/Subtract/Scale`.

- **Rationale.** Catalog-before-code: money arithmetic is a catalog gap, not an engine gap; the machinery exists. The kernel guard makes ⊥-in-arithmetic structurally impossible rather than convention-dependent.
- **Alternatives rejected.** A money-specific interval type (a forked parallel definition of interval arithmetic — the reuse rule prohibits it).
- **Precedent.** Every pure numeric op already carries its transfer (`Operations.cs:1332–1349`); operand magnitudes already normalize to one space on every read path (`GetFieldBounds`, `ApplyStaticUnitScaling` `Intervals.cs:423`).
- **Tradeoff.** Period/duration and cross-space divides need magnitude-space verification before shipping — wire them last; omission costs only precision, never soundness.

### 1.6 §6 — field-vs-constant rules in bound checks

The ledger-verified fold (`ledger:37`): a new fold in `BuildNarrowedIntervals` (`Intervals.cs:519`), beside the shipped relational fold (`:633–654`), reusing the parser `CollectTrustedNumericFacts`/`TryGetNumericConstraintFact` (`Composition.cs:243/293`, with unit normalization) and the applier `NarrowByConstraint` (`Satisfiability.cs:256`). **Mandatory ⊥ suppression** (copy the relational fold's empty-intersection suppression verbatim, `Intervals.cs:650–653`): `NumericInterval.Contains` returns `true` for an empty argument (`NumericInterval.cs:127`, verified), so an unsuppressed contradictory rule (`rule Source <= 100` on `min 200`) would discharge *every* obligation on that field. The reader-side backstop (`:509`) must not be the only line of defense. Honor the blocked-rule/self-unsatisfiability discipline (`RulePredicateSelfUnsatisfiable`, `Composition.cs:177`). **Family enumeration owed by the slice**: `>=`/`>`/`<`/`<=`/min-max shapes × rules-vs-ensures × arg-subject × mixed relational+constant, each cell an explicit disposition with a failing-test-first ⊥-vector row.

**Single-hop rail (locked):** the mixed chain `rule X <= Y` + `rule Y <= 100` stays **undischarged** — the relational half-line continues to read `Y` only via its bare declared interval (`ExtractFieldInterval`, per `Intervals.cs:629–632`), and `ExtractFieldInterval` must **not** learn to fold constant rules, or the relational fold silently becomes two-hop (that is §1b, deferred, spec:256 override *not authorized*, ledger #3).

- **Rationale/Alternatives/Precedent/Tradeoff.** Rationale: the ledger probe verified bound checks read field-to-field rules but not field-vs-constant; this closes that asymmetry by reuse. Alternatives rejected: teaching `ExtractFieldInterval` to fold rules (silently becomes §1b). Precedent: the owner pulled this into the MVP on the Fable probe (ledger §6-scope). Tradeoff: the fold inherits the relational fold's not-per-obligation-blocked-set posture (`Composition.cs:531–538`) — the §6 constant case owes its own circularity argument in the slice's adversarial review, not an assumed transfer.

### 1.7 §1a — multi-term single-fact + guard-sum matching

One new fact record (a linear-term fact: coefficient/term pairs + operator + bound, reusing the existing `NumericSubjectRef`), a new leaf arm in `ExtractGuardLeafConstraints` (`Strategies.cs:886`) recognizing `A + B op literal` (and rule shape `A + B <= C` normalized), and one **syntactic term-multiset matcher** (commutative/associative normalization only — no algebraic rearrangement in the MVP) used at two seams: the interval-containment result (`Intervals.cs:489`, intersect the result interval with the fact's bound when the site *is* the guarded sum) and flow-narrowing (`Strategies.cs:1078/1250`, generalize the two single-leaf reads to term multisets). **Staleness:** a composite-term fact is stale if **any** constituent appears in `ReassignedBefore` (`ProofLedger.cs:51`) — memberwise. **One-hop preserved**; the fact narrows the composite term, not the individual fields (splitting `A+B<=100` into per-field bounds is unsound).

- **Rationale/Alternatives/Precedent/Tradeoff.** Rationale: the flagship idiom (`guard on Total + Amount`) needs one richer fact shape, not a solver. Alternatives rejected: algebraic rearrangement (`Cap - Total >= Amount` matching `Total + Amount <= Cap`) — illegible "the engine does algebra sometimes"; deferred, with a rephrase hint. (Synthesis note: one move-all-terms-left normalization pass is small and both reuse and legibility lenses would support it — left to the slice.) Precedent: extends `GuardRelationImpliesObligation`'s single-term truth-table (`Strategies.cs:1250`). Tradeoff: syntactic matching forfeits some sufficient guards, with an actionable rephrase message.

### 1.8 §2 — case-by-case (conditional arms + event-input narrowing)

Extend the existing guard-branch DNF union (`Strategies.cs:794`, `Intervals.cs:549–606`) to (a) conditional-expression arms — split the condition, fold each branch into a copy of the narrowed dict via `NarrowByConstraint`, evaluate each arm under its assumption, union across **all** arms including the implicit else (negate single-leaf conditions via `NegateConstraintToInterval` `Intervals.cs:819`; forfeit narrowing on multi-leaf negations, the sound forfeit `BuildSiblingRejectExclusions` already uses); and (b) event-input narrowing — scope the narrowed dict by subject kind and mirror the three-line `TypedFieldRef` dict lookup into the `TypedArgRef` case (`Intervals.cs:99–100`), plus fold arg flag-modifiers via `FlagLowerBoundFromMeta`. **Note (reclassified — F1):** the current unscoped arg handling is not a *latent* bug that §2 incidentally fixes — it is a **live fail-open hole** (a guard on an arg narrows a same-named field's interval, discharging obligations falsely; `Intervals.cs:559` has no arg/field discriminator). It is pulled to **Slice 0** as a failing-test-first fix (soundness §2.1, Hole 2); the §2 event-input narrowing here then *adds* sound arg narrowing on top of the corrected base, rather than being the first place the collision is addressed.

**⊥-arm rail (soundness-critical, locked):** an arm whose narrowing intersects to empty is **unreachable** — its interval must be **skipped**, never unioned. `NumericInterval.Union` does not special-case empty (`NumericInterval.cs:131–135`, verified), so `Union(⊥, x)` corrupts the result. Excluding an arm is a positive claim; absent an explicit infeasibility step, a ⊥-arm conservatively contributes its **un-narrowed base interval** (⊥ is never an ambient default in either direction). Owed a failing-test row.

**Where the ⊥ rail lives — one ownership statement (F7).** The rail belongs at **dict-write time, uniformly** — every site that writes a narrowed interval into the dict checks emptiness at that write — **not** per-fold and **not** inside the interval arithmetic. Today ⊥ can leak through **two unguarded dict-write sites**: the guard-branch narrowing write (`ProofEngine.Intervals.cs:571`) and the sibling-reject write (`:625`), neither of which special-cases an empty result before storing it. A dict-write rail covers both (and any future fold) in one place; scattering the check per-fold guarantees the next fold forgets it.

**The §1.5-vs-§1.8 conflict, resolved.** These two rails pull in opposite directions and must not be conflated. §1.5's kernel guard turns `IsEmpty ⇒ Unbounded` **inside arithmetic** (so a ⊥ operand can't produce non-empty garbage). But that same conversion **hides** the infeasibility the ⊥-arm rail needs to *see*: if an arm's narrowing collapses to ⊥ and arithmetic has already laundered it to Unbounded, the union can no longer tell the arm is unreachable. Resolution: the ⊥ signal is detected and acted on **at dict-write time** (before arithmetic consumes the narrowed interval), where emptiness still means "this arm is infeasible — skip it." The kernel guard is the *last-resort backstop* against a ⊥ that nonetheless reaches an arithmetic call; the dict-write rail is the *primary* infeasibility detector. Neither replaces the other, and infeasibility is never inferred from an Unbounded that arithmetic produced.

- **Rationale/Alternatives/Precedent/Tradeoff.** Rationale: case-by-case is the corpus's most common idiom (guarded rows); the union scaffold exists. Alternatives rejected: a general CFG (over-built; the DNF union suffices); a per-fold ⊥ check (drifts — the next fold forgets it, which is exactly how `:571`/`:625` came to leak). Precedent: OR-branch union (`Intervals.cs:584–606`). Tradeoff: multi-leaf negation forfeits narrowing (sound, sometimes weaker) — matches shipped sibling-reject behavior.

### 1.9 The `Literal // vacuously proved` mislabel — two arms, two honest fixes

`IncorporateForwardingFacts` stamps `Literal` on two distinct suppressions that need **different** fixes:

- **Unreachable-from-state arm** (`ProofEngine.cs:~1178–1184`, the `// vacuously proved` comment): genuinely **Proven** — the row can never execute. Fix: an honest verdict rendered "**never runs — nothing to prove**", with the graph's reachability fact as its certificate premise (the premise cites the produced `StateGraph`, so a reader — or the future §5b checker — can confirm the state appears there). Never labeled "Literal" (a lie about method) nor "vacuously proved" (Latin logic the author doesn't speak).
- **Dead-end→dead-end arm** (`ProofEngine.cs:~1186–1196`): **not vacuous** — dead-end states are *reachable*; the row runs, its obligations were merely left unanalyzed to avoid piling diagnostics on rows the dead-end report already covers. Fix: verdict is **Unresolved** with a plain certificate ("not analyzed — this row moves between dead-end states already reported; resolve the dead-end first"); only the *diagnostic emission* is suppressed. The ledger stops recording a proof that never happened.

  **Correction (F5) — the earlier "no compile-outcome change" claim was FALSE, and is now resolved by the severity ruling.** It asserted the dead-end error already rejects, so relabeling these rows costs nothing. But `DeadEndState` was **`Severity.Warning`**, not Error (`src/Precept/Language/Diagnostics.cs:726`) — a dead-end did **not** reject the compile. So these reachable rows compiled *clean* with their obligations suppressed-as-`Literal`-proved, and switching them to `Unresolved` would have changed the compile outcome. That made the disposition a real decision.

  **RESOLVED (owner, 2026-07-12): dead-end = Error.** The owner ruled `DeadEndState` (and its process-topology siblings) flips `Severity.Warning → Error` — option (c) below. This makes the "already rejects" premise **true**: a definition with a dead-end→dead-end row now rejects on the `DeadEndState` Error regardless of what these obligations do, so relabeling their false `Proved` to the honest `Unresolved` is once again **outcome-neutral** (the compile already fails on the dead-end). The Slice-0 action is unchanged — stop stamping false `Proved`, render the honest `Unresolved` — but it no longer carries a compile-outcome risk. The full owner-ruled severity family (which codes flip, which stay Warning, four-leg rationale, and the 0/77 corpus impact) lives in **`compiler-readiness-plan-2026-07-12-structural-severity.md`**.

## 2. SOUNDNESS — Slice-0 fixes the engine needs before prove-or-reject is sound

**Why this section grew.** With the independent re-checker deferred (§1.3, Decision B retracted), the MVP cannot lean on an independent replay to catch a strategy that accepts something it didn't prove. **MVP soundness therefore comes from fixing the engine directly.** An adversarial pass over the current engine — every finding below **verified live via `precept_compile`** and re-verified against source here — found holes the earlier draft either under-counted or filed for later. They are pulled forward to **Slice 0**, each **failing-test-first**.

### 2.1 The fail-open inventory grew from one to four

The earlier draft named a single fail-open hole. The adversarial pass found **four** — all the same defect shape: a discharge path that returns a proved/clean verdict on an input it has not actually proven. Under ratified prove-or-reject (ruling #1), unprovable must **reject**, never pass. Each is a Slice-0 fix.

**Hole 1 — undecidable-magnitude default bound** (`ProofEngine.cs:1060–1066`, the originally-named hole):

```csharp
return TryNumericDefaultBoundProof(obligation, semantics) == false
    ? (ProofDisposition.Unresolved, null)
    : (ProofDisposition.Proved, ProofStrategy.Literal);
```

`TryNumericDefaultBoundProof` returns `true` (proved) / `false` (violated → Unresolved) / **`null` (undecidable magnitude)** — and `null` falls into the `else`, stamping **`(Proved, Literal)`**. An *undecidable* bound check that silently passes is fail-open. **Fix:** `null ⇒ Unresolved` with a residual ("the default's magnitude could not be statically evaluated against bound `max …`"). Behavioral change (previously-clean definitions with undecidable-magnitude defaults now reject) that the corpus/fixture reconciliation (pipeline-eval §6) must absorb. **Not** bundled into the Literal-label swap.

**Hole 2 — arg/field name collision (F1), reclassified from "latent, deferred to §2" to a Slice-0 fail-open fix.** The guard-branch narrowing loop keys purely on `gc.Field` with **no arg-vs-field discriminator**: `if (gc.IsPresenceCheck || gc.Value is null) continue;` (`ProofEngine.Intervals.cs:559`) then narrows a dict entry under that bare name — unlike the count/sibling/satisfiability paths, which filter args out. When an event arg shares a name with a field, a guard on the *arg* narrows the *field's* interval (and vice versa), and an obligation on that field can discharge against a constraint that never applied to it — a **live false `Proved`** (verified live). This is not merely "new power arriving in §2"; it is a present soundness hole. **Fix at Slice 0**, failing-test-first, with an explicit arg/field discriminator at the narrowing site (the §2 event-input work then *adds* sound arg narrowing on top of a corrected base).

**Hole 3 — sequential staleness ignored (F2).** `BuildNarrowedIntervals` (`ProofEngine.Intervals.cs:519`) **never consults `obligation.ReassignedBefore`**, though every other narrowing path does (`ReassignedBefore` is read in `ProofEngine.cs`, `ProofEngine.Strategies.cs`, `ProofEngine.QualifierNarrowing.cs` — the GuardInPath / FlowNarrowing / IndexBounds paths — but **not** in `ProofEngine.Intervals.cs`, verified by grep). So a guard fact that has gone stale because its field was reassigned earlier in the same handler still narrows the interval the bound check reads — a **live false `Proved`** (verified live). **Fix at Slice 0**, failing-test-first: `BuildNarrowedIntervals` drops (or refuses to apply) any fact whose subject appears in `ReassignedBefore`, matching the discipline the sibling paths already enforce.

**Hole 4 — dead-end→dead-end suppression stamped as proved (F5).** The `Literal`-labeled suppression on dead-end→dead-end rows is a false `Proved` on obligations that were never analyzed, and — because `DeadEndState` was only `Severity.Warning` (`Diagnostics.cs:726`) — those rows **compiled clean**. Detailed in §1.9; the honest verdict is `Unresolved`. **Resolved (owner, 2026-07-12): dead-end = Error** (the severity flip in `compiler-readiness-plan-2026-07-12-structural-severity.md`), so the row now rejects on its own `DeadEndState` Error and relabeling the false `Proved` to `Unresolved` is outcome-neutral. This hole's Slice-0 action is "stop stamping false `Proved`"; the corrected verdict no longer carries a compile-outcome risk.

### 2.2 The systematic fail-open sweep is owed (F6)

No evidence was found that a *systematic* fail-open audit was ever run — the four holes above were found by hand, which is exactly why the count moved from one to four. **Slice 0 owes a deliberate sweep** of (a) every `bool?`-returning discharge path (does `null` route to reject, never to proved?) and (b) every **dict-write site** into the narrowed-interval dictionary (does it guard ⊥ before storing — see §1.8's F7 ownership statement?). The four named holes are the found instances, not a closed set; the sweep is the finding-the-rest obligation, and each additional hole it turns up gets the same failing-test-first Slice-0 treatment. (Enumerate the whole family, not just the instances tripped over.)

### 2.3 Kernel and rail fixes carried in their home sections

Three further adversarial findings are soundness-critical and fixed at Slice 0, but their home is the locked section they modify — cross-referenced here so the soundness inventory is complete:

- **F4 — `Empty`-sentinel arithmetic** (crashes/garbages `NumericInterval.Divide`; kernel ⊥-guard must include `Scale`): fixed inside the `NumericInterval` methods, **§1.5**.
- **F7 — ⊥ leaks at two unguarded dict-write sites** (`ProofEngine.Intervals.cs:571`, `:625`); the ⊥ rail belongs at dict-write time uniformly, and the §1.5-vs-§1.8 conflict is resolved there: **§1.8**.
- **F8 — witness point-binding reaches only field leaves** (not arg leaves/element reads, `ProofEngine.Intervals.cs:92/:99`); value-witness rows demote to `Unresolved` until §2, length-witness needs interval plumbing: **§1.4**.

### 2.4 A latent-not-live caveat to carry forward (F9)

The §6 reuse of `CollectTrustedNumericFacts` (§1.6) carries an **order-sensitivity** in how facts are collected and folded. For the **constant-rule shape §6 actually builds** it is **moot** — a `field op constant` fact contributes the same narrowing regardless of collection order (the intersection of half-lines is order-independent, and no fact depends on another's already-narrowed result in the single-hop constant case). So there is no Slice-0 action. But the caveat **returns the moment the fact shape widens** (multi-term facts that read a partially-narrowed sibling, or any fold where one fact's applicability depends on another's result): then collection/fold order becomes semantically load-bearing and must be pinned. Flagged so the §1a multi-term work (§1.7) inherits it as a known constraint rather than rediscovering it.

### Decision A — RULED: the `ProofVerdict` discriminated union

Ruled by the owner 2026-07-12. The verdict is a DU (`Proven` / `ProvenViolating(witness)` / `Unresolved(condition)`), each case carrying only its own evidence — not an enum extension with nullable `Certificate?`/`Witness?`. **This choice is CLAUDE.md-mandated**: the "use discriminated unions for varying shapes; don't paper over shape differences with nullable fields" rule dictates the DU directly (the three cases' non-overlapping payloads are exactly the varying-shape case it names), so the owner's ruling **confirms** the mandated shape rather than settling a genuinely open design fork. Full four-leg rationale (why the DU, why not the enum-plus-nullables reuse option, precedent in CLAUDE.md's DU-over-nullable rule, the one-time fixture-churn tradeoff accepted) is in **§1.1**. No longer open.

### Decision B — RETRACTED: resolved by prior scope, not an MVP call

The independent re-checker was already scoped **out** of the MVP by the phases doc, so there is no MVP decision to make here. The MVP prerequisite is §5a — the certificate *format* ("**Verdict: PREREQUISITE — for half (a) only.**", `proof-engine-mvp-and-proof-phases-2026-07-12.md:285`). The independent *re-checker* is §5b, which that doc rates **Large** ("a second checking implementation", `:280`), scopes as **builder-side drift defense, not author unblocking** ("the deeper benefit of half (b) is to the *builder* … an independent re-check that fails loudly whenever a strategy drifts", `:283`), and places as **a later phase, not a gate** ("**Recommended but deferrable** — value is builder assurance, not author unblocking", `:503`). The earlier B1/B2 fork (always-on checker-gated mint vs. staged replay) is therefore void: both options presuppose an MVP re-checker the phases doc already deferred. What the MVP does build — a re-checkable-*in-principle* certificate format with **no live re-checker and no checker-gated mint** — is settled in **§1.3**.

### Decision C — RULED (source only): C1, a spec-enumerated `CertificateSteps` catalog — membership owes the §5a design pass

**RULED — the *source*, not the *contents*.** The certificate step vocabulary's **source** is a new spec-enumerated `CertificateSteps` catalog (C1), not a reuse of the `ProofStrategy` enum (C2). Rationale: CLAUDE.md's catalog-before-code rule — a closed, spec-owned step vocabulary is language surface, and the catalog is where language surface lives; the certificate builder and any future §5b checker derive from it. Tradeoff accepted: a new catalog surface to build and keep in sync (C2's minimality was the only thing it bought, and it forfeits catalog-derivation discipline). The reframe below is retained for the record — it is why the soundness stakes that once tilted this call were removed, leaving it a clean catalog-discipline-vs-reuse choice that catalog-before-code settles.

**Not ruled: the catalog's membership.** What step kinds the catalog actually contains — its members, their shapes, and the certificate format they render into — is **not** ruled here. Those are the substance of the **§5a certificate-format `/design` pass** the ledger reserves ("Certificate format (§5a) — a design pass on the show-your-work record; first coding slice, laid down before the new proof strategies," `proof-engine-decision-ledger-2026-07-12.md:93`). This doc's illustrative step kinds (`Arithmetic`, `CaseSplit`, the premise/step split in §1.2) are sketches for that pass to settle, not a locked vocabulary. C1 fixes only *where the vocabulary lives*; *what is in it* is the §5a design pass's to determine.

**The reframe.** The earlier C carried a "rails-as-grammar, enforced by the checker" argument — encode the single-hop and ⊥ rails into the step vocabulary's *type structure* so an unsound transitive derivation is unrepresentable and **the checker enforces it by construction**. With the re-checker deferred (Decision B retracted), **that argument no longer applies**: there is no live checker in the MVP to enforce anything by construction, so the single-hop rail (§1.6) and the ⊥ rails (§1.5/§1.8) must be enforced **in engine code**, not by a checker reading the certificate's grammar. C is therefore reduced to its remaining, still-live question: **what is the source of the certificate format's step vocabulary?**

- **C1 — a new spec-enumerated `CertificateSteps` catalog.** Catalog-before-code (CLAUDE.md): the step vocabulary is language-shaped metadata, declared in a catalog, from which the certificate builder and any future §5b checker derive. Downside: a new catalog surface to build and keep in sync.
- **C2 — reuse the existing `ProofStrategy` enum** as the vocabulary (`ProofLedger.cs:100–115`). Minimal; each member already has a documented meaning. Downside: it's a code enum, not a catalog — it does not participate in the catalog-derivation discipline the rest of the language surface follows.
- **The lean, minus the void argument.** CLAUDE.md's catalog-before-code rule still points toward **C1** — a closed, spec-owned step vocabulary is language surface, and the catalog is where language surface lives. What C1 **no longer buys** is checker-enforced rails-as-grammar (that leg is gone with the re-checker). So C1's case now rests solely on catalog-before-code discipline and the future-§5b-checker's derivation source, not on any MVP soundness enforcement. The rails themselves are engine-enforced regardless of which way C goes. With the soundness stakes removed, the call reduced to catalog-discipline (C1) vs. reuse-minimization (C2) — **ruled C1** (above) on catalog-before-code.
