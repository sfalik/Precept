# Reshape stage-6 `/review` into the engineering-lifecycle umbrella reviewer

## Goal

When done, a single `/review` entry reviews **any** lifecycle artifact — a research doc, a design doc, a plan, a code change/PR, a promotion, or a whole work item — by dispatching to the discipline/tool that already owns that surface and folding the results into one verdict; the bare invocation `/review <work-item>` still runs today's end-of-lifecycle completion check unchanged, and `/review <pr-or-diff>` **does the PR-review job** the shadowed built-in `/review` would have done — via `/code-review` + `precept-reviewer`. The built-in `/review` is intentionally subsumed and is **not invoked** by any branch (Decision 2); what the code branch reaches is a Precept-aware *substitute* that strictly dominates the generic built-in for this repo, not the built-in itself.

## Scope

- **In scope**:
  - Reshape `.claude/skills/review/SKILL.md` from a one-shot whole-item completion check into a six-branch dispatcher: `research`, `design`, `plan`, `code`, `promote`, and `whole-item` (the preserved completion check). The `promote` branch reviews a single promotion-artifact (a design carrying a freshly-added `**Promoted to:**` header plus the canonical-doc edits it cites) as a standalone single-artifact review — the per-artifact mirror of the cross-stage Stage-5 ledger the whole-item branch already runs.
  - A hybrid dispatch grammar (explicit subcommand > target-type inference > whole-item default) with a precise **precedence-ordered** parse rule (filename/location signals outrank content-section signals, first match wins) and a no-modal ambiguity fallback whose "inferred branch" is well-defined by that precedence.
  - A per-branch orchestration map: each branch spawns/invokes the existing owner (`precept-reviewer`, built-in `/code-review`) and the skill itself adds only the router, the result-fold, the lifted plan-quality check, the promote doc-update-faithfulness fold, and the preserved completion ledger.
  - A severity-folding contract that normalizes each child tool's native severities into one scale + one verdict line.
  - Collision resolution by subsumption: the `code` branch dispatches PR/diff targets to `/code-review` + `precept-reviewer`, so shadowing the built-in `/review` is intentional.
  - Migration / back-compat: today's `/review <work-item> [--design][--plan][--strict][--accept-debt]` invocation lands on the identical code path.
  - Preservation of the high/ultra modes already added to the skill this session, propagated to children.
  - The doc-update obligations this reshape itself incurs (the skill, CONTRIBUTING.md, cross-refs).

- **Out of scope**:
  - Implementing the reshaped SKILL.md (this is the design only; `/plan` + `/execute` build it).
  - Changing `precept-reviewer.md`, the `/code-review` built-in, the `/security-review` built-in, or any of the other five lifecycle skills' bodies (the umbrella *uses* them; it does not edit them).
  - Re-implementing any review discipline already owned by `precept-reviewer` §§1-14, by `/code-review`, or by the research/design skill guards.
  - Adding `--security` auto-chaining into `/security-review` (left a directly-invokable sibling).

- **Deferred to future**:
  - Decoupling the high/ultra effort axis so the author can dial bug-hunt depth and catalog-audit depth independently (currently coupled).
  - A frontmatter-marker emitted by `/plan` to make the plan-vs-design inference robust without filename heuristics.
  - `/audit` (deferred to Phase 9 per CONTRIBUTING.md:17) owning committed-canonical-doc drift; until it ships, the `code` branch's doc-sync lens is the interim path with a concern-flag toward audit.

## Architecture Grounding

This is dev-tooling architecture (the skill/agent landscape), not Precept pipeline/catalog architecture, so the Precept-internal-placement / cross-component-propagation sub-sections do not apply. The relevant landscape:

**The tool landscape this reshape sits in (grounded in the files):**

- **`precept-reviewer` (sub-agent, `.claude/agents/precept-reviewer.md`)** — the read-only critic. It already owns: catalog/doc-sync/language-propagation/MCP/test/rationale review of changes (§§1-8); design-doc review (§§9-13 + the Independent-re-statement preamble + mandatory source/comparator tables); and — verified against the file — a **Stage-1 Research-Doc Review Path (§14, lines 217-269)** that mechanizes the research skill's 10 guards via grep and is reachable through its "Review file X" scope grammar (line 38). It is a sub-agent, not a slash command; the skill *spawns* it.
- **Built-in `/code-review`** — effort-leveled bug-hunting + reuse/simplification/efficiency cleanups, with opt-in `--comment`/`--fix`. Verified: there is **no project `.claude/skills/code-review/`** — it is a built-in/marketplace command.
- **Built-in `/security-review`** — security pass over pending changes; a distinct discipline with its own command.
- **Built-in `/review`** — generic PR review. The project skill named `review` **shadows** it (empirically confirmed this session: the project skill wins when `/review` is typed).
- **The research / design / plan skills** — the disciplines a reviewer *applies* when judging a research, design, or plan artifact. Their guards are the criteria; their enforcement (for research and design) already lives operationalized inside `precept-reviewer`.

**The current `/review` skill** already establishes the orchestrate-don't-duplicate pattern this reshape generalizes: it **spawns `precept-reviewer`** for the catalog/doc-sync spot-check (SKILL.md:84-87) and explicitly **defers** per-stage content review to other tools, routing mid-execution code review to `/code-review` and drift to `/audit` (SKILL.md:20-22, 111-114). The reshape lifts that single deferral ("code → other tools") into a six-way dispatch ("every lifecycle stage → its owner"): the whole-item branch's existing per-stage ledger already names a check for each of Stages 1–5, and the reshape promotes each of those ledger checks into a standalone single-artifact branch (research / design / plan / code / promote) so any one stage's output can be reviewed on its own — not only as part of a whole-item closure.

**External precedent for unified-vs-specialized dispatch:** git's porcelain is a single `git` entry point that dispatches by subcommand verb (`git commit`, `git diff`) to specialized handlers, with an inference layer (`git <sha>` is rejected, `git <path>` is not a verb) — a single front door over specialized engines, with an explicit-verb override when the target is ambiguous. Precept's `precept-reviewer` already mirrors this at the agent level with its explicit scope grammar ("Review file X" / "Review PR #N", lines 37-40) rather than sniffing. The reshape lifts that same explicit-named-scope-over-inference model up one level to the `/review` skill. Divergence from git: git verbs are mandatory; here inference makes the verb optional for the common case, with the verb retained as the override — chosen because the artifact's path usually already declares its discipline and the owner's stated goal is zero-ceremony (`just types /review <thing>`).

## Decisions

### Decision 1: Hybrid dispatch — explicit subcommand > target-type inference > whole-item default

**Stakes**: high — `/review` is the dev surface's review verb; the grammar is the thing every other decision hangs off and is awkward to change once muscle memory forms.

- **Rationale**: Three tiers each carry their weight. (i) **Whole-item as the no-stage-target default** is the entire back-compat mechanism — every current `/review <work-item> [--design][--plan][--strict][--accept-debt]` call has no leading branch verb and resolves to no single artifact path, so it lands on the preserved completion check unchanged. (ii) **Target-type inference** delivers the owner's stated zero-ceremony goal: paste a `research/*.md` or `docs/Working/*.md` path and get the right discipline without naming it, because the path already declares the artifact kind. (iii) **Explicit subcommand** (`research|design|plan|code|item|promote`) is the escape hatch when inference would mis-route.

  **The precise parse rule.** After stripping a leading `high|ultra` token, inspect token[0]; if token[0] ∈ {research, design, plan, code, item, promote} **and** is not an existing path, treat it as the subcommand and the remainder as target+flags; else classify the positional target by path-shape, evaluating the clauses **in this fixed precedence order** (first match wins — filename/location signals outrank content-section signals, because a plan doc legitimately *contains* a `## Decisions` section per the plan skill, so a `## Decisions`-presence test is not a safe discriminator):

  1. **`research/` path → research branch.** (Location is unambiguous.)
  2. **Plan-filename `*-plan-*.md` / `*readiness-plan*.md`, OR a Working-doc whose dominant structure is `## Phase` rows → plan branch.** The plan-filename heuristic is tested **before** any `## Decisions` check, because — verified against the real tree (`docs/Working/*plan*.md`) — **every** in-repo plan doc carries both a `*-plan-*` filename and a `## Decisions` section (compiler-readiness-plan has 7; most have 1) alongside `## Phase` rows. Keying design-vs-plan on `## Decisions`-presence would route every real plan doc to the design branch and make the plan branch's lifted exit-criteria check unreachable for the common case. Filename is the strong signal.
  3. **`#N` / `PR N` / `diff` / `HEAD` / a dirty tree → code branch.**
  4. **A `docs/Working/*.md` that did not match clauses 1–3 → design branch** — i.e., a Working-doc that is *not* a plan-filename and *not* a research path is a design **by elimination of location+kind**, regardless of whether a `## Decisions` section is present yet. (Keying on location, not on `## Decisions`-presence, means an in-progress design that has not yet written its `## Decisions` section still routes to the design branch — where "missing `## Decisions`" becomes a *finding the branch reports*, not a router input that drops the doc through to whole-item.)
  5. **A committed `docs/*.md` outside `Working/` → routed per the `promote`/audit handling below** (see Decision 7).
  6. **Else (no recognized target, or a slug resolving to no single file) → whole-item.**

  **Tiebreak when two path-shape clauses still co-match.** The clause order above is itself the tiebreak: lower-numbered clause wins, and within that, **filename/location signals outrank content-section signals**. So a `docs/Working/foo-plan-2026-XX.md` that also has a `## Decisions` section resolves to plan (clause 2) over design (clause 4); a non-plan Working-doc that embeds `## Phase` rows but is dominantly a decisions doc resolves to design only if it is *not* a plan-filename and its structure is not dominantly phase-rows. This makes "the inferred branch" in the ambiguity fallback **well-defined** rather than undefined.

  **Ambiguity fallback (no modal):** when two clauses genuinely co-match (e.g., a design-doc that embeds a `## Phase` block) or the target resolves to nothing, state **which** clause was inferred (per the precedence above) **and** the runner-up in one plain-text line, and proceed with the inferred branch unless the author's phrasing contradicts it — never block on a modal (a nonexistent path is announced and treated as a work-item slug → whole-item). Because the precedence order resolves the *selection* deterministically, the fallback line only *announces* it; it never has to invent a winner.

  **Known-weak case, documented in the skill body:** bare-path inference on a plan doc relies on the `*-plan-*` filename convention. A plan doc that does *not* follow the filename convention (or a design doc a user wants reviewed *as* a plan) should be reviewed via the explicit `/review plan <path>` subcommand; the skill calls this out so the author reaches for the subcommand rather than trusting inference on an off-convention plan. This is the interim measure until `/plan` emits a frontmatter `lifecycle-stage:` marker (Deferred-to-future), at which point the design/plan disambiguation keys on the marker, not on filename or `## Decisions`-presence.
- **Tradeoff accepted**: A three-tier grammar is more surface to document and get right than a single rule, and inference can still mis-route an off-convention plan doc (one not following `*-plan-*`). Accepted because the explicit-subcommand escape hatch makes every mis-route one keyword away from correction, the precedence-ordered clauses resolve the common plan-vs-design and in-progress-design cases deterministically (filename/location > content-section), and the announce-and-proceed fallback makes each inference visible and one-line-correctable.
- **Alternatives considered**:
  - *Key design-vs-plan on `## Decisions`-presence (the original draft of this clause):* rejected after verification — every in-repo plan doc carries a `## Decisions` section, so a content-section discriminator routes all of them to the design branch and silently strips the plan branch's exit-criteria check. Replaced with filename/location-first precedence.
  - *Inference-only (no subcommand):* rejected — no escape hatch for the genuinely ambiguous `docs/Working/` design-that-embeds-phases case; a silent mis-route to the wrong reviewer is a real failure (a design judged as research, or vice versa).
  - *Subcommand-required (no inference):* rejected — re-introduces a verb the author must type for the common single-artifact case, contradicting the zero-ceremony goal and the no-ceremony preference; also breaks the bare `/review <work-item>` back-compat unless whole-item stays the default anyway.
  - *Separate top-level skills (`/review-design`, `/review-research`):* rejected — fragments the umbrella into N names to remember, contradicts the just-completed bare-name rename of all six skills, and does not resolve the built-in `/review` collision.
- **Precedent**: `.claude/agents/precept-reviewer.md:37-40` — "*'Review file X' → focus on that file… 'Review PR #N' → fetch via `gh pr diff N`*" — the reviewer already takes an explicit named scope rather than inferring it; the hybrid lifts that model up a level and adds inference as the ergonomic default. All six lifecycle skills already parse a leading `high|ultra` positional (`.claude/skills/review/SKILL.md:26`, `design/SKILL.md:25`, `research/SKILL.md:14`), so `mode-then-branch` is consistent with the existing family. git porcelain (Architecture Grounding) is the external precedent for single-front-door + verb-dispatch + ambiguity-rejection.
- **Sources consulted for this decision**: `.claude/skills/review/SKILL.md:38` — "`/review <work-item> [--design <design-doc>] [--plan <plan-doc>] [--strict]`" (the invocation the default must preserve); `.claude/agents/precept-reviewer.md:35-40` — the scope grammar; `.claude/skills/design/SKILL.md:25` — "`/design high <args>` or `/design ultra <args>`" (leading-mode-token precedent).
- **Strongest counter-evidence**: candidate explicit-subcommand-only framing (judge candidate 2) argues a wrong silent route is a worse failure than one extra keyword and that the owner is the only user. Response: the escape hatch is retained as a first-class tier (subcommand always wins), so the safety the counter-argument wants is present; inference is additive on top, not a replacement, and the announce-and-proceed line makes inference auditable.
- **Reversibility**: Hard — once the author's muscle memory forms around bare-path inference, removing it to force subcommands is a retraining cost. But the grammar is additive (subcommands already work as the override), so tightening toward subcommand-required later is mechanically simple even if ergonomically disruptive.
- **Blast radius**: One file (`.claude/skills/review/SKILL.md`); one cross-ref (CONTRIBUTING.md lifecycle row's one-line description); no catalogs, no `.precept` samples, no external consumers (solo-dev/pre-release).

### Decision 2: Resolve the built-in `/review` collision by subsuming, not renaming

**Stakes**: high — verb-ownership on the dev surface; shadowing a built-in is a maintenance trap unless the intentionality is legible.

- **Rationale**: The owner wants `/review` to stop colliding by accident and start being the umbrella. The `code` branch dispatches PR/diff targets to `/code-review` + `precept-reviewer`, which is a strict superset of the generic built-in `/review` for this repo (bug-hunting **plus** Precept's catalog/doc-sync/language-propagation/MCP/test/rationale discipline). Because the project skill now legitimately does the PR-review job — and does it better here — the shadow is correct-by-construction. An in-skill `## Collision: intentional subsumption` note records this so a future maintainer does not "fix" the shadow by renaming, and the `code` branch emits a one-line banner at point-of-use ("umbrella /review: dispatching to /code-review + precept-reviewer; the built-in PR-review is intentionally subsumed") so the subsumption is discoverable.
- **Tradeoff accepted**: A user wanting the *generic* non-Precept built-in PR review can no longer reach it via `/review`. Accepted because in this repo a Precept-aware review strictly dominates a generic one, and (solo-dev/pre-release) no external consumer relies on the generic built-in.
- **Alternatives considered**:
  - *Rename the skill (e.g. `/lifecycle-review`) to vacate the built-in:* rejected — cedes the `review` verb the owner explicitly wants as the umbrella, contradicts the just-completed bare-name rename of all six skills, and loses discoverability.
  - *Leave the collision unmanaged (skill exists but `code` is not a branch):* rejected — then `/review` shadows the built-in while *not* doing its job, the worst outcome (silent capability loss); and the brief requires resolving it.
  - *Absorb `/code-review` and `/security-review` entirely into the skill:* rejected — duplicates tools the skill should orchestrate (the reuse-not-duplicate constraint); `/security-review` stays a directly-invokable sibling because security review is a distinct discipline and folding it in would re-implement logic.
- **Precedent**: Empirically confirmed this session the project skill wins when `/review` is typed (the built-in is already shadowed in practice). `CONTRIBUTING.md:16` already lists `/review` as the stage-6 skill name. The current skill already spawns `precept-reviewer` (`SKILL.md:84-87`) rather than re-implementing catalog review — the orchestrate-don't-duplicate precedent lives inside this very skill.
- **Sources consulted for this decision**: `.claude/skills/review/SKILL.md:114` — "`/code-review`, `/security-review` — focused on code, not lifecycle process"; `.claude/agents/precept-reviewer.md:7-9` — "*a critic, not a fixer… Read-only*"; the `.claude/skills/` + `.claude/commands/` listing — confirmed no project `/code-review` skill, so the `code` branch dispatches to the built-in.
- **Strongest counter-evidence**: shadowing a built-in is normally a smell and a future maintainer may "fix" it by renaming (the legibility risk). Response: the explicit in-skill `## Collision` note + the point-of-use banner make the intentionality legible; the falsifier below catches it if they don't.
- **Reversibility**: Hard-but-not-irreversible — renaming the skill to vacate the built-in is mechanically a one-line frontmatter change, but it would re-fragment the umbrella; the cost is conceptual, not migration.
- **Blast radius**: `.claude/skills/review/SKILL.md` (the `code` branch + collision note); `CONTRIBUTING.md` (note the subsumption relationship to `/code-review`); no catalogs, no samples.

### Decision 3: Preserve the completion check verbatim as the whole-item branch (the no-stage-target default)

**Stakes**: medium — losing or weakening the completion check would re-open the Stage-4→5 skip CONTRIBUTING.md:21 documents as the most common failure mode (16 historical instances).

- **Rationale**: The completion check is the one discipline no other tool owns — the cross-stage "did every transition happen" ledger. Demoting it to one branch of an umbrella must not weaken it, so its entire body moves under the whole-item branch unchanged: the 5-stage verification (research three honest exits incl. `research-status: not-applicable`; design locked + four-leg + spec-first; plan exit-criteria four-element format; execute tests + clean build; promote canonical-touch + `**Promoted to:**` archive header), the acceptance-criteria evidence check, the `precept-reviewer` catalog spot-check spawn, and the behavioral guards (no "complete" with any 🔴; ⚠️ surfaces owner-judgment questions; `--strict` treats ⚠️ as 🔴; `--accept-debt "reason"` recorded to `docs/Working/lifecycle-debt-log.md`; read-only). Making it the **no-stage-target default** is what gives the existing `/review <work-item>` invocation a free, identical code path. `--strict`/`--accept-debt`/debt-log are scoped to this branch — a single artifact has no "lifecycle debt" to defer, so wiring those flags into the per-stage branches would be semantically empty. The whole-item branch *may* re-use the per-stage branches for present artifacts, but **defaults to today's lighter presence+gate checks** and only deep-dispatches the per-stage branches under `--strict` or `high`/`ultra` — this neutralizes the fan-out cost (spawning `precept-reviewer` once per artifact plus `/code-review` on a routine sign-off).
- **Tradeoff accepted**: `--strict`/`--accept-debt`/debt-log become whole-item-only concepts, a slight asymmetry across branches that must be documented so an author doesn't expect `--accept-debt` on `/review design`. Accepted because "lifecycle debt" is meaningful only for a work-item closure.
- **Alternatives considered**:
  - *Fold the completion check into a generic "review everything" pass:* rejected — conflates PROCESS completeness (the 5-stage ledger) with single-artifact CONTENT review, which the current skill explicitly keeps separate (`SKILL.md:20-22`).

- **Sources consulted for this decision**: `.claude/skills/review/SKILL.md:84-101` — the precept-reviewer spot-check + `--strict`/`--accept-debt`/debt-log guards; `CONTRIBUTING.md:21` — "*The most common failure mode is Stage 4 → 5 transition skipped… 16 instances*".
- **Strongest counter-evidence**: keeping whole-item able to call the per-stage branches couples it to their correctness. Response: the branches are independently testable, and the default stays today's lighter check, so the coupling is only exercised under explicit `--strict`/high/ultra opt-in.

### Decision 4: Back-compat — today's invocation lands on the identical whole-item path

**Stakes**: medium — a behavior change to the existing sign-off invocation would be felt immediately by the only caller (the owner).

- **Rationale**: The current `/review <work-item> [--design <doc>] [--plan <doc>] [--strict] [--accept-debt "reason"]` continues to work unchanged: `<work-item>` is a slug, not a leading branch verb and not a single-artifact path, so the parse rule (Decision 1) routes it to whole-item; `--design`/`--plan` remain anchors/context for the whole-item branch (and now additionally seed the design/plan sub-branch dispatch under `--strict`/high/ultra); `--strict`/`--accept-debt` remain whole-item flags. Genuine behavior *changes* for callers, all strict improvements: (i) `/review <single-artifact-path>` now does single-stage review instead of treating the path as an ill-fitting work-item string; (ii) `/review #N` now routes to the `code` branch (the intended subsumption) instead of misfiring as a work-item; (iii) the built-in `/review` is now reached only via the `code` branch's dispatch. The one genuinely new ambiguity — a work-item literally named `research`/`design`/`plan`/`code`/`item` — is handled by the explicit `/review item <name>` escape and documented.
- **Tradeoff accepted**: A file-path target that an author previously (mistakenly) passed as a work-item now routes to a per-stage branch — a behavior change. Accepted because it is strictly better (the per-stage branch is the right review for a single artifact) and `/review item <x>` restores the old behavior if ever needed. Solo-dev/pre-release means no deprecation cycle is owed.
- **Alternatives considered**:
  - *Add a `--legacy`/version flag to pin old behavior:* rejected — ceremony for a back-compat that the default rule already provides for free; no downstream consumer needs it.
  - *Default bare `/review` to the `code` branch (match the built-in's meaning):* rejected — silently drops the completion check as the default and contradicts the stage-6 identity and the hard constraint to preserve it.
- **Precedent**: `.claude/skills/review/SKILL.md:38,107` — the exact invocation + `--design`/`--plan`/`--strict`/`--accept-debt` flag semantics being preserved.
- **Sources consulted for this decision**: `.claude/skills/review/SKILL.md:38` and `:105-109` (Composability — input flags); `CONTRIBUTING.md:329` — "`/review` — one-shot end-of-lifecycle completion check before declaring a work item closed".
- **Strongest counter-evidence**: silently changing what `/review #N` means could surprise a caller expecting the old (misfiring) behavior. Response: the old behavior on a PR ref was already wrong (the completion check needs a work-item, not a PR), so the change can only improve outcomes.
- **Reversibility**: Easy — the default rule is one parse branch; pinning old behavior is adding a flag.
- **Blast radius**: `.claude/skills/review/SKILL.md`; no external consumers.

### Decision 5: A severity-folding contract normalizes child outputs into one verdict; dedup the two-tool code branch; a per-branch valid-flag matrix

**Stakes**: medium — this is the one piece of genuinely-new glue the skill owns; getting the fold wrong produces a noisy or incoherent verdict.

- **Rationale**: Once `/review` dispatches to tools with three native severity vocabularies, "fold into one verdict" needs a defined contract — no existing tool owns this merge. The map: `precept-reviewer` BLOCKER → 🔴, CONCERN → ⚠️, NIT → note; `/code-review` issue at high confidence → 🔴 if a correctness bug / ⚠️ if a cleanup; completion-check 🔴/⚠️/✅ pass through. Output is one 🔴/⚠️/✅ scale plus a single verdict line reusing the current skill's three verdicts (Ready to sign off / Remediation required / Owner judgment needed, `SKILL.md:89`). `--strict` **generalizes**: it promotes every ⚠️ → 🔴 across the whole folded output, not only the whole-item branch (extending the current single-branch `--strict` cleanly). Cross-cutting rules the fold must carry: (a) **dedup with a degrade-gracefully fallback** — on the `code` branch, `/code-review` (correctness) and `precept-reviewer` (catalog/doc-sync) can flag the same location from two lenses; the fold collapses same-`file:line` + finding-equivalence into one entry showing both lenses, so one underlying issue is not double-reported. **This dedup is contingent on `/code-review` emitting `file:line`-keyed findings** — `precept-reviewer`'s `file:line` format is verified (`precept-reviewer.md:347`), but `/code-review` is a built-in command whose exact finding schema (single-line vs range vs message-only; whether it exposes a confidence field and a bug-vs-cleanup tag) is **not yet inspected against a real sample**. **Fallback rule:** if `/code-review`'s findings cannot be `file:line`-keyed, the fold **does not merge** — it prints the two lenses in separate labelled sections rather than attempting a dedup the interface can't support; and if `/code-review` does not tag bug-vs-cleanup, the 🔴/⚠️ split for its findings defaults to ⚠️ (surfaced for human triage) rather than guessing 🔴. The execution slice MUST capture one real `/code-review` output sample and record its observed schema (line-keying, confidence field, bug/cleanup tag) before wiring the merge; the dedup key and severity map are then specified against the **observed** schema, not the assumed one. (b) **per-branch valid-flag matrix** — `--fix`/`--comment` valid only on `code`; `--strict`/`--accept-debt` valid only on `whole-item`; `--design`/`--plan` valid only on `whole-item`; the `promote` branch takes no special flags (a single artifact has no lifecycle debt and applies no fixes); an inapplicable flag is **rejected with a one-line message**, not silently swallowed (silent-ignore is a usability trap).
- **Tradeoff accepted**: The fold is the one place the skill carries original logic rather than pure delegation, and the dedup heuristic (file:line + equivalence) can occasionally merge two genuinely-distinct findings on one line. Accepted because the alternative — three unmerged severity scales and double-reports — is worse, and the merged entry shows both lenses so nothing is lost.
- **Alternatives considered**:
  - *No fold — print each child's native report separately:* rejected — defeats the "one verdict" point of an umbrella; the author would re-triage three reports by hand.
  - *No dedup on the code branch:* rejected — guarantees double-reporting on doc-sync surfaces both tools touch.
  - *Silently ignore inapplicable flags:* rejected — a `--fix` typed on a `design` review that does nothing is a silent surprise; reject loudly.
- **Precedent**: `.claude/skills/review/SKILL.md:86,89` — the current skill already "*Fold[s] its findings into the report*" and emits the three-verdict summary line; this decision generalizes that fold from one child (precept-reviewer) to several. `precept-reviewer.md:358-362` — the BLOCKER/CONCERN/NIT severities being mapped.
- **Sources consulted for this decision**: `.claude/skills/review/SKILL.md:86-89` (fold + verdict line); `.claude/agents/precept-reviewer.md:347` (`file:line` finding format — verified); `.claude/agents/precept-reviewer.md:358-362` (severity definitions); the `/code-review` command description (effort levels + `--comment`/`--fix`) — **note: this is the command's self-description, not an inspected output sample; the actual finding schema (line-keying, confidence field, bug/cleanup tag) is unverified and the execution slice must capture a real sample before wiring the merge.**
- **Strongest counter-evidence**: two distinct risks. (1) A dedup heuristic risks merging two real findings — Response: the merged entry preserves both lenses' text, so the author still sees both; equivalence is keyed conservatively on identical `file:line` + matching rule reference, not fuzzy text. (2) The dedup and the bug-vs-cleanup severity split both rest on an **unverified assumption** about `/code-review`'s output shape (the one tool the skill doesn't control) — Response: the degrade-gracefully fallback (section-don't-merge when not line-keyed; default-to-⚠️ when untagged) makes the branch correct even if the assumption is false, and the falsifier below forces the sample-capture before lock-in.
- **Reversibility**: Easy — the fold is internal skill text; tuning the dedup key or severity map is a doc edit.
- **Blast radius**: `.claude/skills/review/SKILL.md` only.

### Decision 6: The skill is read-only on every branch; `--fix`/`--comment` are opt-in pass-throughs

**Stakes**: low — a default-mutation reviewer would break the established read-only contract, but the fix is a one-line default.

- **Rationale**: The current skill is read-only (`SKILL.md:103`) and `precept-reviewer` is read-only (`precept-reviewer.md:9`). A reviewer that silently edits the tree or posts PR comments violates that contract and surprises the author. The `code` branch invokes `/code-review` **without** `--fix`/`--comment` by default; those are opt-in pass-throughs the author requests explicitly (`/review code <pr> -- --fix`), and per Decision 5's flag matrix they are valid only on the `code` branch.
- **Tradeoff accepted**: To apply fixes the author re-runs with an explicit `-- --fix`, one extra step. Accepted — explicit mutation is the safe default for a review umbrella.
- **Alternatives considered**:
  - *Default the code branch to `/code-review --fix`:* rejected — turns a review into an edit, breaking the read-only contract and the "see findings before changes land" expectation.
  - *Default to `--comment` on PRs:* rejected — posts to GitHub without the author's explicit ask.
- **Precedent**: `.claude/skills/review/SKILL.md:103` — "*Skill is read-only. Produces report; doesn't apply fixes*"; `.claude/agents/precept-reviewer.md:9` — "*a critic, not a fixer*".
- **Sources consulted for this decision**: `.claude/skills/review/SKILL.md:103`; `.claude/agents/precept-reviewer.md:9`; the `/code-review` skill description (lists `--comment`/`--fix` as opt-in flags).
- **Tradeoff/Reversibility**: Easy — read-only is the default; enabling a different default is a one-line change.

### Decision 7: A dedicated `promote` branch reviews a promotion artifact standalone (Stage-5 per-artifact)

**Stakes**: medium — Stage 4→5 (promote) is the lifecycle stage `CONTRIBUTING.md:21` names as the **most common failure mode** (16 historical instances of canonical docs lagging their archived designs). The umbrella exists to review any stage output; omitting a promote target would leave the highest-failure-rate transition with no standalone per-artifact reviewer.

- **Rationale**: The whole-item branch's Stage-5 ledger check only verifies *that* a promotion happened (canonical-touch + `**Promoted to:**` header present) **as part of a full work-item closure**. It gives an author no way to run `/review` against a *promotion in isolation* — to verify, mid-promotion, that the why-content actually transferred faithfully to canonical and that the archive cross-link resolves, before declaring the whole item done. A dedicated `promote` branch fills exactly that seam: given a design doc carrying a freshly-added `**Promoted to:** <link>` header plus the canonical edits it cites, it spawns `precept-reviewer` scoped to the canonical diff under the **§3 doc-sync lens** (the existing owner of why-content-faithfulness and stale-doc findings — *not* re-implemented), folded with a **promote-specific check the skill owns**: every entry in the source design's `## Doc-update enumeration` was actually touched by the promotion, the `**Promoted to:**` link resolves, and the archive cross-link from the canonical doc back to the archived design resolves. This is the single-artifact mirror of the whole-item Stage-5 ledger — same checks, different unit (one promotion vs. the whole work item). The branch is reached by `/review promote <design>` explicitly, or by inference when the target is a design doc carrying a fresh `**Promoted to:**` header, or (parse clause 5) when the target is a committed `docs/*.md` outside `Working/` whose change is a promotion landing.
- **Tradeoff accepted**: The promote-specific doc-update-enumeration cross-check is the **second** piece of original logic the skill owns (alongside the fold), so the skill is not pure delegation here. Accepted because no existing tool cross-references a design's enumeration against the actual canonical touches — `precept-reviewer`'s §3 doc-sync lens checks faithfulness of *what was touched* but does not own the *design-enumeration-to-touch* completeness check; that small bridge is the branch's reason to exist.
- **Alternatives considered**:
  - *No promote branch — fold promotion review into whole-item + the code-branch doc-sync lens (the original five-branch draft):* rejected — leaves the highest-failure-rate transition with no standalone per-artifact reviewer; an author mid-promotion cannot check faithfulness without running the whole 5-stage completion check (which needs a finished work item, not an in-flight promotion). The seam would be silent rather than named — exactly the gap the umbrella is meant to close.
  - *Route a promotion target to the `code` branch's doc-sync lens (option b in the finding):* rejected as the primary path — the code branch's bug-hunting `/code-review` invocation is wrong for a docs-only promotion diff, and the code branch does not carry the design-enumeration-to-touch completeness check. (Parse clause 5's committed-`docs/*.md`-outside-`Working/` case still defers to this branch's doc-sync lens for the *audit-overlap* sub-case until `/audit` ships — see Decision 4 / Open question 4 — but a *promotion* with a source design and an enumeration goes to the dedicated promote branch.)
  - *Absorb the promote check into `precept-reviewer` (extend §3):* rejected — that edits a sibling agent the umbrella is supposed to *use*, not modify (out-of-scope per Scope), and the design-enumeration cross-check is umbrella-orchestration logic, not a general catalog/doc-sync rule.
- **Precedent**: `.claude/skills/review/SKILL.md:75-78` — the existing Stage-5 ledger ("Canonical doc(s) updated with why-content from the design per design's doc-update enumeration; Archive header `**Promoted to:**`; 🔴 if any enumerated canonical doc not touched OR archive header missing") — the promote branch lifts this exact check to a standalone single-artifact target. `.claude/skills/promote/SKILL.md` — the `/promote` skill produces the diff and the archive header this branch reviews. `CONTRIBUTING.md:21` — the 16-instance Stage-4→5 failure-mode evidence that motivates a dedicated reviewer.
- **Sources consulted for this decision**: `.claude/skills/review/SKILL.md:75-78` (Stage-5 ledger being lifted); `CONTRIBUTING.md:21` — "*The most common failure mode is Stage 4 → 5 transition skipped … 16 instances*"; `CONTRIBUTING.md:376` — "*Archived design (Stage 5 complete) → `docs/Working/Archive/<original-filename>` with `**Promoted to:**` header*" (the artifact shape the branch keys on).
- **Strongest counter-evidence**: a sixth branch is more dispatch surface, and the promote check overlaps the whole-item Stage-5 ledger. Response: the overlap is intentional and identical-in-substance (same checks, different unit); the standalone branch is strictly additive — it does not change whole-item, it gives the same discipline a single-artifact entry point for the in-flight case the whole-item branch can't serve.
- **Reversibility**: Easy — the promote branch is a thin orchestration of the §3 doc-sync lens + one enumeration cross-check; removing it collapses promotion review back into whole-item (the pre-revision state).
- **Blast radius**: `.claude/skills/review/SKILL.md` (the `### promote` branch + parse clause 5 + AC9); `CONTRIBUTING.md` (note the promote-artifact review entry point); no catalogs, no samples.

5. **Whole-item branch (back-compat)** — bare `/review <work-item> --strict` runs the unchanged 5-stage completion check, treats ⚠️ as 🔴, refuses a "Lifecycle complete" verdict with any 🔴, and writes `docs/Working/lifecycle-review-<work-item>-YYYY-MM-DD.md`; `--accept-debt "reason"` records to `docs/Working/lifecycle-debt-log.md`. 8. **Flag rejection** — `/review design <path> -- --fix` is rejected with a one-line "`--fix` applies to the code branch only" message (not silently ignored). The skill applies no fixes on any branch by default.
9. **Promote branch** — `/review <design-doc-with-fresh-Promoted-to-header>` (or `/review promote <design>`) dispatches to the doc-sync lens over the cited canonical diff and surfaces a 🔴 when an enumerated canonical doc in the design's `## Doc-update enumeration` was **not** actually touched by the promotion, or when the `**Promoted to:**` link / archive cross-link does **not** resolve. A clean promotion (every enumerated doc touched, link resolves, why-content present in canonical) returns ✅.
10. **Plan-misroute regression (the precedence guard)** — `/review docs/Working/<x>-plan-2026-XX.md` on a real in-repo plan doc (which carries both a `*-plan-*` filename and a `## Decisions` section) routes to the **plan** branch and runs the exit-criteria check — **not** to the design branch. ## Falsifiers

(Required because this design locks dev-surface behavior; per design-skill discipline for behavior-visible changes.)

1. If an author types `/review <single-artifact-path>` and the inferred branch is wrong more than rarely on real in-tree artifacts (design↔plan or code↔doc mis-routes in normal use), path-based inference is too weak — collapse to subcommand-required + whole-item-default, or add a `/plan`-emitted frontmatter marker for the plan branch.
2. If the announce-and-proceed ambiguity fallback is experienced as noisy (author wants silent dispatch) or as unsafe (author wants a confirm before proceeding on ambiguous targets), the conversational-but-decisive posture is falsified and the fallback should change.
3. If subsuming the built-in `/review` loses functionality an author actually needed — someone wants the generic non-Precept PR review and the `/code-review` + `precept-reviewer` composition can't substitute — the subsume-don't-rename resolution is falsified; expose an escape or rename.
4. If maintainers "fix" the intentional shadow by renaming/disabling the skill (the intentionality wasn't legible despite the `## Collision` note and the point-of-use banner), the legibility axis of the subsumption failed and the note/banner must be louder or the name reconsidered.
5. If the whole-item completion check's `--strict`/`--accept-debt`/debt-log behavior changes observably for an existing `/review <work-item>` caller (different output path, lost debt-log entry, altered 🔴 gating), the "fully preserved" claim is falsified — a back-compat regression check must show identical behavior to the pre-reshape skill.
6. If `precept-reviewer`'s Research-Doc Review Path turns out not to cover a research guard the research skill requires (a divergence between the two), the "reuse the path, don't duplicate" decision for the research branch is falsified — either the path is extended or the branch supplements it with the inlined-grep contingency.
7. If the whole-item branch under `--strict`/high/ultra spawns so many sub-agents (precept-reviewer per artifact + /code-review) that sign-off becomes prohibitively slow, the deep-dispatch-on-escalation choice is wrong and whole-item should keep a single consolidated precept-reviewer spawn even under escalation.
8. If `/code-review`'s real output **cannot be `file:line`-keyed**, the dedup contract on the code branch is **unbuildable as merge** and the fold MUST section-not-merge the two lenses (Decision 5's fallback); likewise if `/code-review` does not tag bug-vs-cleanup, the 🔴/⚠️ split is unimplementable and its findings default to ⚠️. The execution slice's sample-capture is the gate that decides which path is live; shipping the merge without that sample is the falsified state.
9. If a real plan doc (carrying both a `*-plan-*` filename and a `## Decisions` section) routes to the **design** branch instead of the plan branch, the filename/location-first precedence (clause 2 before clause 4) is not actually firing — the parse rule regressed to the content-section discriminator the revision removed. AC10 is the regression guard for this.
10. If `/review` on a faithful, complete promotion (every enumerated canonical doc touched, link resolves, why-content present) emits a 🔴, or on a promotion that *skipped* an enumerated canonical doc emits ✅, the promote branch's doc-update-enumeration cross-check is wrong and the §3 doc-sync-lens fold must be re-specified.
