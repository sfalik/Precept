# Frank's Go-Forward Posture Replay

Requested by Shane, verbatim: "ask frank to replay what he believes the go-forward posture is." No hedging. This is the record.

---

## 1. What Precept is

Precept is a domain integrity engine. You declare — in one file — what a business entity's data is, what it is allowed to become, and the rules that must always hold over it. Precept then makes every state of that data that violates those rules **structurally impossible to reach**, at compile time where it can and at runtime everywhere else.

## 2. What Precept guarantees

**No invalid configuration. Ever — across the guarantee's live surface.** Not "caught." Not "detected." Not "usually." A configuration that violates a declared rule cannot come into existence — there is no operation, no input, no code path, no bypass that produces one. "No operation can produce a result that violates a declared rule — the invalid configuration is not reachable" (`philosophy.md:51`). If Precept accepts a definition, then every value that definition can ever hold satisfies every rule declared over it, enforced structurally on every operation — unconditionally or under precise guard conditions.

**One disclosed carve-out, stated plainly because honesty is not hedging.** Representational overflow — a computed value exceeding what the *type itself* can represent (`NumericOverflow`) — is **owner-parked**: "a **disclosed, defense-in-depth known-fault backstop with no live compile-time guarantee** — *not currently prove-or-reject*, temporary, and **no doc may claim it prevented**" (`proof-engine-boundary-ruling-2026-07-06.md:25`; re-confirmed `:275`). Shane ratified that overflow-prevention **is** the intended end-state, sequenced **post-MVP** as GATE-O — "the gap is build-order, not a text defect" (`proof-engine-decision-ledger-2026-07-12.md` item #7). So the absolute holds over the entire **live-enforced** fault-and-rule surface today; representational overflow is the one lane where the guarantee is a declared *target* we are honest about not having built yet. This carve-out is **disclosed, not solved** — see ledger #7 and boundary-ruling:275.

## 3. What the compiler must prove, and of what

The compiler is **"total over the fault surface"** (`proof-engine-boundary-ruling-2026-07-06.md:25`) — **not** "every declared constraint, full stop." That distinction is load-bearing, and inverting it is exactly how this document went off the rails before.

**Two things must be kept separate: what the ratified design targets, and what is built today.**

**What the design targets (ratified).** Every fault-prone operation over a *definition-derived* value in the **live-enforced fault set** — "division, `sqrt`/`pow` non-negativity, empty-collection/index access, and the containment of a *computed result* within a declared `min`/`max` bound" (`boundary-ruling:25`) — is compile-time **prove-or-reject**: discharged from the constraints its inputs carry, or else the definition is rejected naming the carrier. The MVP engine that makes this honest on the corpus's own house style is the §1a/§2/§3/§6 package — prove-or-reject was ratified "as a package with #2 and the MVP engine work" (`decision-ledger` item #1). §6 — "the author states the consequence as one rule and the engine applies it" — is the principled fix for multi-fact cases, pulled **into** the MVP (`decision-ledger` item #1, MVP-scope note).

**What is built today.** The engine today "understands a relational rule only in its simplest shape: one field compared to one field (`rule X >= Y`)" (`proof-engine-linear-solver-feasibility-2026-07-12.md:22`) plus the live fault floor. §1a (multi-term linear facts, one at a time), §2, §3, and §6 are MVP **scope, not yet shipped**. So a claim that "the compiler proves everything decidable" describes neither today's build nor the ratified target — it overclaims both.

**A declared relational invariant is GOVERNED, not proven — by design, not by weakness, and the routing axis is provenance, not linearity.** A declared relational invariant over independently-set fields — whether nonlinear (`rule TotalInventoryCost == AverageCost * QuantityOnHand`, a ratio) or linear (`rule Balance == Deposits - Withdrawals`) — is "**Expressible — governed**," with "**Zero expressiveness loss**" (`boundary-ruling:226`, worked-pattern table). It is governed, not proven, because it *declares a relationship* rather than *computing a derived value* — there is no derived-value fault obligation to discharge, only a relationship to maintain; the linear identity is governed for the identical reason (`boundary-ruling:160`, worked row 11, which distinguishes *declaring a relationship* — governed — from *computing a value* — proven). The enforcing mechanism is the **post-mutation constraint sweep**, **not** ingress governance: after any mutation, the whole-entity invariant is re-evaluated against the resulting working copy at commit, and the operation is discarded (`ConstraintsFailed`) if the identity is violated (`result-types.md:114`/`:121`, Stage 9–10; `boundary-ruling:102`/`:106`). This is a **distinct mechanism** from the ingress governance of §4, which checks a *single incoming external value* against *its own carried constraint* at entry — a relationship spanning several independently-set fields is carried by no single incoming value, so only the sweep can enforce it (`boundary-ruling:159`, worked row 10: `TotalCost`'s own `max` "governs its own raw edits only and does not bound the product"; the identity itself is "enforced by the constraint sweep"). Routing is by **provenance, not linearity**: the linear-solver work (§1a/§1b, `feasibility`; `decision-ledger` item #3) is linear-only *and* concerns discharging fault obligations using facts as premises, not proving relational invariants hold — so it was never the reason this rule is unproven; the reason is that a relationship among independent fields has no derived-value obligation to discharge. "21 of 77 sample files use products" (`boundary-ruling:25`) and are honored this way. The invariant's fault-prone *sub*-operations (a division inside the formula) remain prove-or-reject over their derived operands (`boundary-ruling:130`). Precept does not pretend to prove what a linear engine cannot; it governs the relationship, structurally, with no bypass.

**Multi-fact composition (§1b) is deferred, not built.** Combining two or more linear facts is "the step §1a deliberately does not take" (`feasibility:54`); Shane ruled "**DEFER §1b — leave it OPEN, not in the MVP, not scheduled**" (`decision-ledger` item #3), on the ground that "combining linear facts is **never an *expressibility* gain**." Today, multi-fact cases are handled by the author stating the composite as one rule (§6), not by the engine deriving it.

**The discharge rule, precisely.** For an obligation in the live fault set over a derived value: if the constraints its inputs carry **decide** it safe, it discharges; otherwise the definition is **rejected**, naming the carrier that would discharge it. Decidability is "**the discharge-oracle for each prove-or-reject obligation**" — not the router (`boundary-ruling:39`). An obligation the engine's bounded strategies cannot decide is a **reject**, never a runtime shrug: "✅ CLOSE — **no escape hatch**" (`decision-ledger` item #9).

## 4. What happens at runtime, and why

Runtime governance exists for what compile-time proof cannot reach: **values the definition did not compute**, and **declared relationships among independently-set fields**. Neither is a computed derived-value fault obligation, so neither is prove-or-reject; both are enforced structurally at runtime, with no bypass. Runtime governance is delivered by **two distinct mechanisms** — **ingress governance** (a single incoming external value, checked against its own carried constraint, at entry, before any computation) and the **post-mutation constraint sweep** (all whole-entity invariants, checked against the resulting state, at commit, after computation). Keeping the two distinct is what makes the guarantee "precise rather than magical" (`precept-language-spec.md:264`). The relational invariants of §3 are enforced by the **sweep**, not the ingress arm — a relationship spanning several fields is carried by no single incoming value.

**Mechanism 1 — Ingress governance: an external value, checked against its own carried constraint, at entry.** A value is *externally-supplied* when the definition did not compute it — an outside actor handed it in. The spec names exactly three ingress points: "Every declared constraint is enforced on every value entering the entity from outside the definition — **event arguments, construction inputs, direct field edits** — at the moment it enters, before any computation derives from it" (`precept-language-spec.md:268`). Two author-facing surfaces produce these, and **both** are ingress-governed for the same reason (their value is supplied, not computed):

- **(a) Operation/event arguments** — the values a caller supplies when firing an event or constructing the entity (e.g. `v` in `on E(v: number in 0..1000)`, or the construction inputs). At the moment of invocation, before any action derives from them, `TypeRuntime`/`TypeRuntimeMeta` enforce each argument's declared constraints (qualifiers, bounds) on the incoming value (`runtime-api.md:656`; Fire pipeline "arg validation → … → constraint evaluation → commit or discard," `runtime-api.md:361`).
- **(b) Editable fields** — a field the entity declares directly settable from outside (`field C editable` — a write-access flag modifier, `boundary-ruling:166` row 17; access mode `Write`, `runtime-api.md:487`), mutated via a direct field edit (`Update`). Its edited value is externally-supplied for the identical reason — the definition did not compute it — so the **same** ingress governance enforces the field's declared constraint on the edit (`runtime-api.md:656`; `boundary-ruling:127`; Update pipeline "access mode check → type validation → … → constraint evaluation → commit or discard," `runtime-api.md:386`). A field that is *not* editable (`readonly` in the current state) rejects the edit outright — `FieldNotEditable`, before any value is considered (`result-types.md:138`/`:147`).

**What ingress governance checks, and when.** One incoming value, against *its own carried constraint* — the bound or qualifier declared on that very argument or field — at the instant the value enters, before any computation derives from it (`precept-language-spec.md:268`). It is **operation-blind**: it upholds the field's declared contract whether or not any fault-prone operation reads the field (`precept-language-spec.md:268`). "The compiler proves a structural fact — that the value carries its constraint — never the value itself; **the runtime enforcement is what makes that carried constraint true, not a second line of defense**" (`philosophy.md:55`).

**What happens on failure.** A structurally malformed argument (wrong type, unknown key) is rejected at arg validation — `InvalidArgs`, Stage 2 (`result-types.md:113`). An edit to a non-editable field is rejected — `FieldNotEditable` (`result-types.md:138`/`:147`). A value that violates its declared constraint feeds the working-copy discard path: the mutation executes on a working copy that is discarded if any constraint fails, so the operation returns `ConstraintsFailed` and nothing persists — "an invalid configuration never persists — this is prevention, not detection" (`precept-language-spec.md:268`; `result-types.md:114`/`:146`; `boundary-ruling:127`). No bypass, on every operation.

**Mechanism 2 — The post-mutation constraint sweep: all whole-entity invariants, checked against the resulting state, at commit.** Where ingress governance checks *one incoming value* against *its own* carried constraint at *entry*, the sweep re-evaluates **all whole-entity invariants** — global rules, state ensures (`in`/`to`/`from`), and event ensures — against the *resulting* working copy *after* the mutation is applied and computed fields are recomputed, discarding the operation (`ConstraintsFailed`) if any invariant is violated (`result-types.md:114`/`:121`, Stage 9–10). This is the mechanism that enforces the declared relational invariants of §3 — `rule TotalInventoryCost == AverageCost * QuantityOnHand`, `rule Balance == Deposits - Withdrawals` — because no single incoming value carries such a relationship; it is checkable only against the whole post-mutation state.

**The two mechanisms, crisply distinct.** **Ingress governance** = *one* incoming external value, checked against *its own* carried constraint, at *entry*, *before* any computation derives from it. **Post-mutation sweep** = *all* whole-entity invariants, checked against the *resulting* state, at *commit*, *after* computation. Both discard the working copy on failure so nothing invalid persists, but they check *different things* at *different points* — and a relationship among independently-set fields is reachable **only** by the sweep, never by ingress governance.

**There is NO "computed-but-undecidable ⇒ governed" case. This is the correction that matters most.** A value a Precept expression has **derived** is definition-internal; its fault obligation is **proven-or-rejected**, never routed to governance. "What a constraint's **decidability** decides is whether a prove-or-reject obligation **discharges or the definition is rejected**, never whether the obligation is proven or governed" (`boundary-ruling:25`). If a derived value's constraint exceeds the engine's bounded strategies, the definition is **rejected** — the author states the fact as a rule (§6) or bounds the source — it is **not** carried to runtime. The alternative (govern the undecidable computed case) is **Option B**, "the thesis's counter-position," which Shane **explicitly rejected**: "✅ **RULING (Shane, 2026-07-12): A — prove-or-reject, RATIFIED**" (`decision-ledger` item #1). Resurrecting it is precisely the error this replay exists to end.

**Runtime governance is not a weaker guarantee — for both governed cases it is the SAME guarantee, delivered by a different mechanism.** "No invalid configuration" holds identically whether a constraint was discharged by proof, enforced at ingress on an external value, or maintained by the post-mutation sweep over a whole-entity invariant. Governance is "not a second line of defense" (`philosophy.md:55`) — it is structural enforcement, on every operation, with no bypass, that closes the exact gaps proof cannot physically reach: the value is external, or the obligation is a declared relationship with no derived-value to prove. The entity cannot enter a governed-invalid state any more than it can enter a proof-invalid one.

## 5. The one discriminating axis (mechanical rule)

To route any declared constraint over any operand, ask **one question about provenance** — and it is a clean **TWO-WAY** routing rule, not three (the *govern* route is delivered by two enforcement mechanisms — ingress and the post-mutation sweep — but it remains one route):

> **Where did the operand's value come from?**
> - **Derived by a Precept expression from declared/proven facts → its FAULT OBLIGATIONS are PROVE-or-REJECT.** If the constraints its inputs carry decide the obligation, it discharges; if the engine's bounded strategies cannot decide it, the definition is **REJECTED** (the author adds the carrier via §6, or bounds the source). Decidability decides **discharge-vs-reject only** — it **never** routes to governance.
> - **Not a computed derived-value obligation → GOVERN it, structurally.** The govern route has **two mechanisms**, both governance, neither prove-or-reject: **(i)** a value *supplied externally at an operation boundary* — an event/construction argument or an editable-field edit — is unknowable at compile time; its own carried constraint is enforced **at ingress**, the instant it enters, before any computation derives from it (`precept-language-spec.md:268`; §4, Mechanism 1). **(ii)** a *declared relational invariant over independently-set fields* (linear or nonlinear) declares a relationship rather than computing a value; it is enforced by the **post-mutation constraint sweep** against the resulting whole-entity state at commit — **not** at ingress, since no single incoming value carries the relationship (`result-types.md:121`; §3; §4, Mechanism 2).
>
> **NEVER route by surface spelling.** "`max 100` and `rule x <= 100` are the same construct and get the same treatment" (`boundary-ruling:134`); a disposition keyed on *modifier-vs-rule* "is incoherent" (`boundary-ruling:37`). A fault-obligation and a business-rule obligation over the **same** provenance get the **same** disposition. The axis is **provenance**; decidability is the discharge-oracle *within* the prove-or-reject arm, not a third route.

Note what this rule is **NOT**: it is **not** the claim that "everything decidable is proven and the fault surface is irrelevant." The ratified model is organized *around* a **bounded fault surface** — division, `sqrt`/`pow`, empty/index access, declared-bound containment (`boundary-ruling:25`) — plus the author-stated-rule extension (§6) and the deferred multi-fact extension (§1b). Genuinely-nonlinear invariants outside that surface are **governed** (§3). The ban is narrow and exact: **do not route by how the constraint is spelled**, and do not route a *derived* value's obligation by how hard it is to prove (that would slide to Model A, rejected — `boundary-ruling:39`).

## 6. What must NEVER be said again (explicitly rejected)

These framings were produced, tried, and corrected. They are on the record as **banned** — each with its exact ratified ground:

- ❌ **"Govern, don't prove" (Option B) as the stance for derived values.** Shane ratified **A — prove-or-reject** and explicitly rejected Option B, "the thesis's counter-position" (`decision-ledger` item #1). A derived value whose obligation the engine cannot decide is a **reject**, not a runtime governance case. *(This is the exact error the prior version of this replay committed in its §4(b)/§5 middle arm — banned precisely because it keeps trying to come back.)*
- ❌ **Treating "unprovable" as "defer to runtime."** For a *derived* value, unprovable-when-it-should-be-provable is a **reject**: "✅ CLOSE — **no escape hatch**" (`decision-ledger` item #9). Runtime is not the amnesty for a failed proof of an internal value.
- ❌ **Presenting §1b (multi-fact linear composition) as rejected.** It was **DEFERRED** — "leave it OPEN, not in the MVP, not scheduled … A possibility to consider later" (`decision-ledger` item #3) — because combining linear facts is "never an *expressibility* gain," not because the posture excludes it. Do not conflate "deferred" with "not part of the design."
- ⚠️ **Routing by surface spelling** — e.g. "`min 5` is proven but `rule X >= 5` is governed," or the reverse. This is the real, narrow ban. "`min 5` and `rule X >= 5` are **interchangeable to the proof engine** … proof participation is a function of a constraint's **decidability**, not its syntactic form" (`boundary-ruling:37`, quoting `spec:1138`). Same construct, same disposition.

**What is NOT banned (correcting an earlier over-reach in this very document).** The general observation that *most of what the engine proves today is fault-shaped, and much of what governance enforces is nonlinear business-rule-shaped* is **neither false nor banned** — the ratified model IS built around a bounded fault surface (`boundary-ruling:25`) with nonlinear invariants governed (`boundary-ruling:226`), and the ledger itself uses "fault-scoped" language ("'no deferral' read as **fault-scoped**," `decision-ledger` item #1, folded-in note). Banning that phrase outright would contradict the ratified ledger's own words. What is banned is only the two **overstatements**: (1) routing a constraint's disposition by its **spelling** (modifier vs rule); and (2) claiming fault-status *causes* the disposition — a derived value's obligation is prove-or-reject because it is **derived**, not because it is a fault; an external value is governed because it is **external**, not because it is a non-fault.

## 7. Why this matters, existentially

We spent a month circling this — and the honest record says it was a **spiral, not a straight line** (`frank-retrospective-proof-engine-arc-2026-07-13.md` §4). The ratified answer was **not** "always" the position; it was **hard-won**. The arc genuinely swung through GOVERN (the identity thesis's counter-position, `retrospective` §1.2), through a band-split nadir (D2), through my own Error position, before landing where it did — and the landing carried **genuinely new material not present at the start**: the certificate criterion (ledger #2) and the proof that §1b "is never an expressibility gain" (ledger #3) — "the biggest single deposit of the whole detour" and "genuinely new" (`retrospective` §2).

The destination, stated once so it never has to be re-litigated: **provenance routes (external value or declared relational invariant → govern; derived value being computed → prove-or-reject), and decidability decides discharge-vs-reject only — never the route.** Governance itself runs by two mechanisms — ingress governance for an external value at entry, the post-mutation sweep for a whole-entity invariant at commit (§4) — but both sit on the one *govern* side of the routing axis. This was arrived at "through genuine debate and reversal," not held from the start (`retrospective` §1.2, §4). That is *exactly why* it must be stated this precisely now. Every time the wrong axis crept back — "fault vs non-fault as the router," "govern the undecidable computed case," "prove everything decidable, full stop" — it re-opened a debate already settled and cost real time. This posture exists to close that loop with an **accurate** boundary, not a bold-but-wrong one. Boldness that overclaims is how we got the contradiction that triggered this correction; boldness that states the caveats with confidence — "overflow is parked, not solved — see ledger #7"; "nonlinear invariants are governed, not proven, by design" — is the only kind worth keeping.
