# Relational-contradiction reject — a rule that contradicts the subject's own declared bounds must REJECT the dependent fault-prone op at Error (BUG-024, both arms)

> **Provenance.** This is the soundness amendment to Slice 2c-i (`relational-narrowing-core-design-2026-06-03.md`, Locked). The core design's representation (Decision 1), guarded-rule drop filter (Decision 2), and satisfiability-scan isolation *intent* (Decision 4) are correct and STAND. What its Decision-3 folds got wrong is a missing consistency check: they narrow `X` from `Y`'s interval without verifying the result is consistent with `X`'s *own* declared bounds. When the relation contradicts those bounds, the intersection is empty (⊥), and the discharge readers — by `NumericInterval.Contains(empty)=>true` — read ⊥ as "every obligation discharges." That is a false "proved safe," the worst outcome (Principle 1). The prior `relational-contradiction-discharge-guard-2026-06-04.md` correctly stated the defect but left three open questions (the diagnostic/severity, the magnitude-arm convergence, the sign-fold shape). **This doc settles all three from canon and locks them.**

## Goal

When done, a `Compiler.Compile` of a precept whose unconditional rule `rule X op Y` (relational arm) **or** `rule X op c` (magnitude arm) contradicts `X`'s own declared bounds (so `⟦X⟧₀ ⊓ narrowing = ∅`) **rejects at Error severity** — the dependent fault-prone operation on `X` (divisor / range / overflow / sqrt) emits its own existing `Severity.Error` obligation diagnostic (`DivisionByZero` / `OutOfRange` / `NumericOverflow` / `SqrtOfNegative`) and `HasErrors=True` — instead of compiling clean (relational arm) or compiling with only a Warning (magnitude arm) while the runtime fault is reachable; AND a relational rule that merely *tightens* `X` to a non-empty interval still compiles clean and still discharges, with the satisfiability scans (VacuousRule/ContradictoryRule/UnsatisfiableGuard/UnsatisfiableRule) byte-identical to today (Decision-4 isolation preserved).

## Scope

- **In scope**:
  - **The discharge contradiction guard (Decision 1).** A self-contradictory rule — one whose narrowing of `X` is empty against `X`'s own declared bounds — contributes **no discharge fact** (no entry into `narrowed[X]`, no sign into `signSet(X)`), and a discharge reader that nonetheless observes an empty narrowed interval treats it as **unprovable**, never `Contains`-true. Covers BOTH the interval fold (`RelationalHalfLine` → empty `narrowed[X]`) and the sign fold (`TryRelationalSignForField` → a sign the subject's own bounds forbid).
  - **The severity source (Decision 2).** The Error that closes BUG-024 is sourced from the **dependent fault-prevention obligation** (`DivisionByZero` / `OutOfRange` / `NumericOverflow` — all `Severity.Error` per §0.7 / §0.6 items 3/6), not from re-severitying a satisfiability diagnostic. `UnsatisfiableRule` (PRE0159) and the rest of the satisfiability family stay `Severity.Warning` (§0.6 items 7/8, "reports"). The contradiction is attributed to the rule as related metadata; the *blocking* signal is the dependent op's own Error.
  - **The magnitude/relational convergence (Decision 3).** Both arms converge on the same outcome — the dependent fault-prone op rejects at Error — under the same principle (*a self-unsatisfiable rule contributes no discharge fact*). The magnitude arm's fix is **in scope here**, not deferred to a sibling bug.
  - The soundness-preservation proof for each axis: the over-prove closes; no false rejection is introduced for a non-empty (legitimately satisfiable) relational narrowing; Decision-4 isolation is untouched; single-pass / depth-1 / determinism preserved.
- **Out of scope** (locked upstream — cited, not re-decided):
  - Core-design Decisions 1 (`FieldToFieldConstraint` reuse), 2 (guarded-rule DROP filter, BUG-023), 4 (satisfiability-scan isolation INTENT). This amendment preserves all three; it refines Decision 4's *completeness* claim and adds the missing discharge-side guard the folds lacked.
  - The subject-resolution amendment (`relational-subject-resolution-discharge-2026-06-04.md`, Decisions A/B) — orthogonal; untouched.
  - The `RelationalHalfLine` / `TryRelationalSignForField` *narrowing arithmetic itself* (how the half-line/sign is computed from `⟦Y⟧₀`) — correct; this amendment adds a consistency check on the *result*, it does not change how the half-line is derived.
  - **Surfacing field-op-field contradictions in the satisfiability scan (PRE0159 for relations).** A future enhancement could make the self-unsat pre-pass also recognize `rule X op Y` (today blind because `ExtractGuardConstraints` is field-op-constant only); that would give a *Warning-level attribution* to the relational contradiction. It is **not required** to close BUG-024 (the dependent-op Error already blocks), and is deferred — see Open Questions / Decision 2 tradeoff.
- **Deferred to future**: none for the single-relation, one-hop, declared-bounds contradiction. Detection, suppression, the reject outcome, and the severity are complete here. (Transitive contradiction — `X>=Y`, `Y>=Z`, `Z`-bounds making `X` impossible — is the depth-1 envelope's known incompleteness, inherited; it degrades to the dependent op staying Unresolved → still rejects, sound.)

**Tradeoff detail (Principles 1/10/11 — load-bearing).** This amendment sits on the prevention guarantee in BOTH soundness directions. (1) The over-prove it closes is a Principle-1 breach: a false "proved safe" lets a runtime divide-by-zero / overflow / out-of-range through a clean (or Warning-only) compile — the worst possible outcome, and the worst because §0.7 is explicit that fault prevention has "no deferral" to a runtime check. (2) The hazard it must NOT re-open is Decision 4's: feeding a tighter (even empty) relational interval into the `ExtractFieldInterval` the satisfiability scans read would make `VacuousRule`/`ContradictoryRule`/`UnsatisfiableGuard` fire on precepts whose *non-relational* bounds are satisfiable — a false REJECTION (Principle 11, opposite direction). The resolution: the genuine-contradiction case (empty intersection) is detected **on the discharge path** — where the narrowing already lives (the `narrowed` dict, the sign-set fold, the containment reader) — and converted to "no discharge → dependent op rejects," while the satisfiability scans continue to read the bare `ExtractFieldInterval` and stay byte-identical. The empty intersection is *not* "a tighter interval that might falsely flag a satisfiable rule" — it is a proven contradiction (the relation cannot hold given declared bounds), so rejecting the dependent op is prove-or-reject-correct, not a false rejection. This is exactly the octagon/DBM distinction: a *tighter non-empty* zone is a refinement; an *empty* zone is infeasibility (survey:84).

**Companion commitments.** *Stateless-first-class*: the contradiction is field-scoped (declared bounds vs a field-only rule), applies identically to stateless precepts. *Domain-expert-primary-author*: the author who writes `rule X >= Y` with `X max 5` and `Y min 10` has written a self-contradictory contract; the dependent op's rejection — "`X` can be zero" with the contradicting rule attributed — tells them so in their own terms, which is more honest than silently "proving" a division safe that will fault.

## Audience and Teachability

The amendment changes one author-observable behavior — a self-contradictory precept now rejects the dependent op instead of silently compiling (relational arm) or compiling-with-only-a-warning (magnitude arm) — so a brief audience note is warranted even though no language surface is added.

**Worked example (the contract a domain expert would write, and the contradiction they'd commit):**

```precept
precept DiscountTier
field Floor as integer min 0 max 5 default 0 editable
field Ceiling as integer min 10 max 20 default 10
field PerUnit as integer <- 100 / Floor
rule Floor >= Ceiling because "the per-unit base divides by the floor, which must reach the ceiling"
state Open initial terminal
```

`rule Floor >= Ceiling` with `Floor max 5` and `Ceiling min 10` is self-contradictory: no value of `Floor` in `[0,5]` can be `>= Ceiling ∈ [10,20]`. Today this compiles clean and `Floor` silently "proves" it is `>= 10` (hence nonzero), so `100 / Floor` discharges — and at runtime `Floor` holds its valid `default 0`, so `100/0` faults. After this amendment, the divisor `100 / Floor` rejects at Error because the contradicted rule contributes no discharge fact and nothing else proves `Floor != 0`.

**Error message (exact wording for this misuse):**

```
PRE0136 (DivisionByZero): Division is unsafe: 'Floor' can be zero in the computed expression for field 'PerUnit' — the rule 'Floor >= Ceiling' that would bound 'Floor' away from zero cannot hold under 'Floor's declared bounds (at most 5) and 'Ceiling's (at least 10). Bound 'Floor' nonzero, fix the contradictory rule, or guard the division.
```

Why this serves the domain expert, not the developer: it names the real fault ("`Floor` can be zero") in the author's vocabulary, and — critically — *attributes the failed safety carrier to the contradictory rule and the concrete bound conflict* ("at most 5 … at least 10") so the author fixes the real cause, never mentioning `narrowed` dictionaries, `Intersect`, or `⊥`. The three offered fixes are the real ones.

**10-minute teaching path:** (1) `docs/language/precept-language-spec.md §0.7` (fault prevention: prove-or-reject, no deferral) — 4 min; (2) the `samples/` reorder precept using `rule OnHand > Reserved` (the *valid* relational case, for contrast — a relation that makes a divisor provably-safe) — 3 min; (3) the `DivisionByZero` entry in `docs/compiler/diagnostic-system.md` — 2 min. Total ≤ 9 min.

## Semantic Rules

### S1 — The defect, stated precisely (verified, working tree)

For an unconditional `rule X op Y`, the core design's Decision-3 folds compute (verified at `Intervals.cs:628-640` and `Composition.cs:481-489`, working tree):

```
interval fold:  builder[X] := (builder[X] ?? ExtractFieldInterval(X)) ⊓ RelationalHalfLine(op, ExtractFieldInterval(Y), type(X))
sign fold:      signSet(X)  := signSet(X) & TryRelationalSignForField(rule, X)      # from ⟦Y⟧₀'s decidable-sign bound
```

Neither checks the result against `X`'s own declared interval for *consistency*. For the repro `rule X >= Y`, `X min 0 max 5`, `Y min 10 max 20`:

```
RelationalHalfLine(>=, ⟦Y⟧₀=[10,20]) = [10, +∞)
builder[X] = ⟦X⟧₀=[0,5] ⊓ [10,+∞) = [10,5]   ⟹  IsEmpty (Max 5 < Min 10) = ⊥
TryRelationalSignForField(X >= Y, ⟦Y⟧₀.Min=10 > 0) ⟹ Positive          # X claimed Positive
```

The discharge readers then read ⊥ / `Positive` as **safe** (verified at `Intervals.cs:489-512`, `NumericInterval.cs:125-128`):

```
TryIntervalContainmentProofNarrowed:  resultInterval=[10,5]; passes `Min >= DeclaredMin && Max <= DeclaredMax`
   vacuously for many targets, and NumericInterval.Contains(⊥)=>true — every containment obligation discharges.
sign-set divisor:  signSet(X)=Positive ⟹ X != 0 ⟹ 100/X discharged.
```

⟹ false "proved safe": `100/X` discharges, the precept compiles clean, and at runtime `X` holds `default 0`, so `100/0` faults. **The magnitude arm** is the same root one level up: `rule X >= 10` (`X max 5`) yields a self-unsatisfiable rule whose `ScopedNumericFact(X, >=, 10)` is **not blocked** (`CollectBlockedConstraints` blocks only rules whose *own obligation* is Unresolved — a self-unsat rule's obligation need not be), so it discharges the divisor; the precept emits only `UnsatisfiableRule/Warning` and *builds*, and `100/0` faults.

### S2 — Why this is a genuine contradiction (reject-correct), NOT a false rejection (the Decision-4 distinction)

The empty intersection `⟦X⟧₀ ⊓ narrowing = ∅` is a **proof that the rule cannot hold given declared bounds** — there is no value of `X` in its declared range that satisfies the rule for any value of the related field/constant the narrowing was derived from. Rejecting the dependent op is prove-or-reject-correct (Principle 10), the contradiction class §0.6 item 7 names and §0.7 mandates not be deferred.

This is categorically different from the case Decision 4 guarded. Decision 4 prevents a *non-empty but tighter* relational interval from reaching the satisfiability scans, where it would make a *satisfiable* guard/rule wrongly flag `VacuousRule`/`ContradictoryRule`/`UnsatisfiableGuard`. The distinction is exactly the octagon/DBM one (survey:84): a tighter non-empty zone is a *refinement* (must not trigger a rejection on its own); an *empty* zone is *infeasibility* ("the constraints are not satisfiable, and thus that the zone is empty"). The amendment acts only on the empty case, on the discharge path — so the satisfiability scans' inputs are unchanged and the non-empty refinement case is wholly unaffected (probe SAFE-REL confirms: `rule X >= Y`, X 1..20, Y 5..8 compiles clean today and must continue to).

### S3 — The discharge guard (the reduction rules)

```
  rule X op Y declared, guard(rule)=∅, X≠Y         (the Decision-2-filtered relational fact; magnitude analogue: rule X op c)
  h = RelationalHalfLine(op, ExtractFieldInterval(Y), type(X))      (or the magnitude ScopedNumericFact's half-line)
  ⟦X⟧₀ ⊓ h = ∅                                                      (empty — proven contradiction)
  ─────────────────────────────────────────────────────────────────────────────────────────── (R-CONTRA-NODISCHARGE)
        the rule contributes NO discharge fact: no entry into narrowed[X], no sign into signSet(X);
        a discharge reader that observes an empty narrowed[X] returns "unprovable" (never Contains-true).

  dependent fault-prone op on X (divisor / range / overflow / sqrt) has no other safe carrier
  ─────────────────────────────────────────────────────────────────────────────────────────── (R-CONTRA-REJECT)
        the op's obligation stays Unresolved → its existing Severity.Error diagnostic
        (DivisionByZero / OutOfRange / NumericOverflow / SqrtOfNegative) emits → HasErrors=True → reject.
```

The two reduction rules are coupled: **R-CONTRA-NODISCHARGE** removes the false carrier; **R-CONTRA-REJECT** is the *automatic consequence* — the dependent op falls back to its real proof state, finds no carrier, and emits its own Error. The amendment does not invent a new blocking diagnostic; it *stops masking* the one the engine already has. Three defense-in-depth points enforce R-CONTRA-NODISCHARGE so the empty result cannot leak through any reader:

1. **Fold suppression (primary).** In `BuildNarrowedIntervals`, after `seed.Intersect(hl)`, if the result `IsEmpty`, do **not** write it into `builder[X]`. (And symmetrically in the sign fold — S3-sign below.)
2. **Reader guard (backstop).** In `TryIntervalContainmentProofNarrowed`, an empty `resultInterval` returns `false` (unprovable), never a vacuous containment — closing the `Contains(⊥)=>true` vector even if a future fold path forgets the suppression.
3. **Self-unsat fact block (the magnitude arm + the shared root).** A rule whose own predicate is unsatisfiable against its field's declared bounds (`⟦X⟧₀ ⊓ predicate-narrowing = ∅`) is added to the blocked set in `CollectBlockedConstraints` (alongside the existing Unresolved-obligation block), so **neither** its magnitude `ScopedNumericFact` **nor** its relational `FieldToFieldConstraint` is collected as a discharge fact. This is the single mechanism that converges both arms (Decision 3).

**S3-sign.** `TryRelationalSignForField` must not contribute a sign that `X`'s own declared interval forbids: the relational sign for `X` is admitted only when `⟦X⟧₀ ⊓ h` is non-empty (the *same* emptiness computation as the interval fold, shared so the two cannot diverge). For `rule X >= Y`, `Y min 10`, `X min 0 max 5`: the relation claims `Positive`, but the combination is empty against `[0,5]`, so the sign is withheld and the divisor falls back to its real (failing) proof.

### S4 — Soundness preservation claim (named, per-axis)

Principles threatened: **1** (prevention), **10** (totality), **11** (static completeness, both directions).

- **Over-prove closed (Principle 1).** When `⟦X⟧₀ ⊓ h = ∅`, the rule contributes no narrowing/sign and the dependent obligation falls back to its real proof state; with no other safe carrier it stays Unresolved → the fault-prone op emits its Error. Both the `100/X` relational repro and the magnitude repro reject (`HasErrors=True`). Verified-baseline check: the no-rule control already rejects with `DivisionByZero/Error` — this amendment restores that outcome by removing the false carrier.
- **No false rejection for the non-empty case (Principle 11, reject-direction — the Decision-4 guarantee).** The emptiness test fires ONLY when the intersection is empty. A relation that tightens `X` to a non-empty interval (the reorder demonstrator: `rule OnHand > Reserved`, both `nonnegative`) produces a non-empty `narrowed[X]`, the guard does not fire, and the precept compiles clean and still discharges. The satisfiability scans never receive the relational interval (Decision 4 untouched), so no `VacuousRule`/`ContradictoryRule`/`UnsatisfiableGuard` is added on any precept.
- **Contradiction detection is discharge-path-local (Principle 11 + Decision 4).** The emptiness is observed in the `narrowed`-dict fold, the sign fold, the containment reader, and the fact-collection block — all discharge-time structures. `ExtractFieldInterval` is not modified; the satisfiability scans read it bare, byte-identical to today.
- **Single-pass / depth-1 / determinism (Principle 3, §0.4).** The guard is a pure `IsEmpty` test on an already-computed `Intersect`; `⟦Y⟧₀` is still read one hop via bare `ExtractFieldInterval(Y)`. No new iteration, no fixpoint. Inherits the core design's depth-1 envelope unchanged.
- **Severity soundness (Principles 1/7/11 — the settled question).** The block is the dependent op's own `Severity.Error` (`DivisionByZero`/`OutOfRange`/`NumericOverflow`), which makes `HasErrors=True` → "no Precept produced → evaluator never runs" (`diagnostic-system.md:707`). This is the §0.7 reject-not-defer outcome. PRE0159 and the satisfiability family stay `Warning` because they are §0.6-items-7/8 *structural* diagnostics ("reports"), not fault-prevention obligations; their severity is unchanged and correct (see Decision 2).

## Architecture Grounding

### Precept-internal placement

**Layer placement.** Pipeline code (the proof engine's discharge stage), not catalog metadata. The defect is that the discharge-time folds (interval at `Intervals.cs:628-640`, sign at `Composition.cs:481-489`) and the fact-collection block (`Composition.cs:120-150`) admit a contradicted fact; the fix is a consistency check on the fold's *result* and an extension of the existing blocked-set, co-located with each. The catalog already declares *what* must be proved (the fault-prone op's obligation) and *what* the field's bounds are; the contradiction is *reasoning over* that metadata, which is the proof engine's job. This respects the catalog rules: no enum-identity dispatch (the emptiness test is `NumericInterval.IsEmpty`, a value property; no `*Kind switch` to pick per-member behavior); no new record (reuses `FieldToFieldConstraint`, `ScopedNumericFact`, `NumericInterval`); the outcome is data-classified (proof outcome = "proved dangerous", §0.6 proof philosophy 5), not syntax-shape-classified, and no new diagnostic code (reuses the existing fault-prevention Errors).

**Cross-component propagation:**
- **Runtime (parser, type checker, evaluator, diagnostics):** Proof engine — the interval fold suppresses the empty contribution; the sign fold gates on the same emptiness; the containment reader returns unprovable on an empty interval; `CollectBlockedConstraints` blocks self-unsatisfiable rules so neither arm's fact is collected. Parser / type checker / evaluator — **None** (no new node, no new typing rule, no runtime path; the rule and field bounds already parse and bind). Diagnostics — **None new** (the rejection reuses the existing `DivisionByZero`/`OutOfRange`/`NumericOverflow`/`SqrtOfNegative` Errors; the contradicting rule is attributed via the existing related-diagnostic / message-arg surface, no new code, no severity change to any existing code).
- **Tooling (highlighting, completions, hover, semantic tokens):** Hover proof-attribution — a previously-(falsely)-Proved obligation becomes a rejected/Unresolved one; the contributing rule is recoverable for the witness (`FieldToFieldConstraint` names both fields). **None** structural.
- **MCP (vocabulary, DTOs, tool output):** **None.** No new diagnostic code, no DTO change, no formatter change. Both fact records stay private. Affirmed explicitly so a future audit does not re-investigate.

**Breaking changes.** None to public contract (no new code, no severity change to an existing code, no DTO). The *behavioral* change: a precept that compiled clean (relational arm) or Warning-only (magnitude arm) *because* a contradicted rule falsely discharged a fault-prone op will **newly REJECT** at Error severity — the §0.7 soundness tax (a latent over-prove surfaced), the same shape BUG-019's and BUG-023's fixes paid. Expected and correct; the corpus check triages each newly-red sample. No legitimately-safe precept newly-reds (the guard fires only on a proven empty intersection).

### External architectural precedent

The architectural problem: *a relational (or magnitude) constraint, narrowed into a variable's range, produces an empty (contradictory) result; should the engine treat the empty result as "everything proves" (vacuous truth) or as "infeasible" (reject)?*

The canonical answer in relational abstract domains is **empty = infeasible (⊥) = reject**, never "everything proves." The octagon/DBM literature is explicit (survey:84, *Difference bound matrix*, accessed 2026-06-02):

> "It suffices to apply the Floyd–Warshall algorithm to the graph and associates to each entry (a, b) the shortest path from a to b in the graph. If this algorithm detects a cycle of negative length, this means that **the constraints are not satisfiable, and thus that the zone is empty.**"

A negative-weight cycle in the constraint graph (the discrete analogue of `⟦X⟧ ⊓ half-line = ∅`) is *the* signal of unsatisfiability; the domain reports infeasibility, it does not silently admit every goal. **What Precept takes:** the empty-intersection-is-infeasible discipline — a contradictory constraint rejects, it does not vacuously discharge. **What Precept deliberately diverges from:** the DBM detects infeasibility by a global O(n³) negative-cycle search over the full closed matrix; Precept detects it locally, one relation at a time, by the `IsEmpty` test on the single `Intersect` the depth-1 fold already computes — "octagons minus the loop-widening step" (survey:76), restricted to the one-hop, one-pair (or field-op-constant) discharge. The divergence buys termination and a per-rule witness at the cost of completeness (no transitive contradiction detection).

**Precept-specific novelty (acknowledged, warranted).** Mainstream relational domains conflate narrowing and consistency-checking in one closed structure, so "empty zone" is *automatically* infeasible there. Precept's discharge readers, by contrast, inherited a *vacuous-truth* convention (`NumericInterval.Contains(⊥)=>true`, `:127`) — sound for the non-relational containment it was built for, but an over-prove vector once a relation can *make* the interval empty. The amendment's contribution is to reconcile the two: the contradiction must be observed and the fact suppressed at the fold, because the downstream `Contains`-true reader cannot distinguish "empty because contradictory" from "empty because trivially-true." This reconciliation has no off-the-shelf comparator (it arises from Precept's discharge-reader semantics combined with Decision-4's deliberate scan/discharge split) and is defended as warranted: it is the minimal change that re-imposes the universal ⊥-is-infeasible rule on a reader that locally violates it, *without* re-coupling narrowing and consistency-checking (which would re-open the Decision-4 false-rejection hazard).

## Decisions

### Decision 1: An empty relational/magnitude narrowing (`⟦X⟧₀ ⊓ narrowing = ∅`) is a proven contradiction — the rule contributes NO discharge fact, and the dependent fault-prone op rejects — never a vacuous "proved safe"

**Stakes**: high (the load-bearing soundness fix — the wrong call either leaves the over-prove open, a Principle-1 breach, or rejects a satisfiable precept, a Principle-11 breach).

- **Rationale**: The empty intersection is a *proof* the rule cannot hold given `X`'s declared bounds (S2) — the octagon/DBM "empty zone = unsatisfiable" signal (survey:84). §0.6 proof philosophy 1 is categorical: the proof layer "must never claim an expression is safe when it is not." A discharge that reads `Contains(⊥)=>true` does exactly that. §0.7 forbids deferring the resulting fault to runtime ("no deferral"; "not a second line of defense", `philosophy.md:55`). The fix is to detect the emptiness where it arises (the fold / the fact collection) and withhold the contradicted fact, so the dependent obligation is judged on its real proof state and — finding no carrier — rejects via its own existing Error. Detecting on the discharge path (not by feeding the relational interval to the satisfiability scans) is what preserves Decision 4: the empty case is a *proven contradiction* (reject-correct), categorically distinct from the *non-empty tighter* case Decision 4 protected (which must not trigger a rejection and is wholly unaffected because the guard tests only emptiness).
- **Tradeoff accepted**: The guard catches only the *single-relation, one-hop, declared-bounds* contradiction — a contradiction needing transitive closure (`X>=Y`, `Y>=Z`, `Z`-bounds making `X` impossible) is NOT detected (the depth-1 envelope, inherited from core Decision 4 / §0.4). Accepted: that is a *missed* contradiction (false negative on *detection*) that degrades to the dependent obligation staying Unresolved → the fault-prone op rejects anyway (sound — no over-prove, only less-precise attribution), never a false positive. The author cost is a worse message ("divisor unprovable" rather than "rule contradicts bounds"), not an unsound outcome.
- **Alternatives considered**:
  - *(Feed the relational narrowing into the satisfiability scans so the existing UnsatisfiableRule/ContradictoryRule machinery catches it)* — rejected: precisely the hazard Decision 4 isolated. The scans read the bare `ExtractFieldInterval`; routing the relational interval there would make a *non-empty tighter* relation flag a *satisfiable* guard/rule as `VacuousRule`/`ContradictoryRule`/`UnsatisfiableGuard` — a false rejection of a valid precept (Principle 11). The over-prove must be closed WITHOUT widening the scans' inputs.
  - *(Extend `ExtractGuardConstraints` to emit a constraint for `field op field`, so the self-unsat pre-pass catches `rule X >= Y` against `X`'s bounds)* — rejected as the *primary* mechanism: `GuardConstraint` carries a `decimal? Value` (field-op-*constant* shape); a `field op field` relation has no constant, so representing it there is nullable-shape-papering (CLAUDE.md-forbidden), and feeding it to the *satisfiability* scans re-opens the Decision-4 false-rejection hazard for the non-empty case. The contradiction belongs on the discharge path where the relational fact already lives. (A *Warning-level attribution* via that route is a deferred, separate enhancement under the same emptiness-only discipline — Open Questions.)
  - *(Leave the over-prove and rely on runtime governance)* — rejected: governance enforces declared constraints on *external input* (§0.7), but `X` here holds its *valid default 0* — governance does not fire, and `100/0` is an *internal computation*, not an ingress check. §0.7 is explicit: fault prevention is "established entirely at compile time … no deferral." A runtime check is the "second line of defense" `philosophy.md:55` forbids.
- **Precedent**: External — the octagon/DBM negative-cycle = empty-zone = unsatisfiable rule (survey:84); a relational domain reports infeasibility on an empty zone, never admits every goal. In-tree — the satisfiability self-unsat pre-pass already treats an empty composed interval as a contradiction (`proof-engine.md:483` / `Satisfiability.cs` `ScanRules`: empty composed interval ⇒ `UnsatisfiableRule`) — this amendment applies the *same* "empty interval ⇒ contradiction" judgment to the relational/magnitude *discharge* fold, restoring the rejection that scan can't reach for field-op-field. `NumericInterval.IsEmpty` (`:11`) is the existing emptiness primitive both use. The reassignment-invalidation precedent (`proof-engine.md:1245`: "`when X != 0 → set X = 0 → 100 / X` no longer discharges") is the exact in-tree shape of "remove a stale/false carrier so the dependent op re-rejects."

### Decision 3: The magnitude arm and the relational arm CONVERGE on the same outcome (dependent op rejects at Error) under one principle — "a self-unsatisfiable rule contributes no discharge fact" — and the magnitude fix is IN SCOPE here, not deferred to a sibling bug

**Stakes**: medium (a convergence + scope-boundary call the prior art left open as OQ2; reversible, no public-surface lock-in beyond what Decisions 1–2 already settle).

- **Rationale**: The probe established the two arms are the *same root* — a self-unsatisfiable rule whose narrowing of its field is empty against that field's declared bounds still folds as a discharge fact, because `CollectBlockedConstraints` (`Composition.cs:120-150`) blocks a rule only when its *own obligation* is `Unresolved`, and a self-unsat rule's obligation need not be. The relational arm folds an empty `FieldToFieldConstraint` half-line; the magnitude arm folds an unblocked `ScopedNumericFact` — *both* from a rule that cannot hold. The single fix in Decision 1's inventory (extend `CollectBlockedConstraints` to also block self-unsatisfiable rules) closes **both** facts at the shared collection point, so the two arms converge on the dependent op rejecting at Error (Decision 2). The §0.7 reject-not-defer mandate applies identically to both ("no deferral"); the `no-redefining-the-bar` discipline forbids treating the magnitude Warning-but-builds as "acceptable by-design" — a building precept that faults is a Principle-1/11 breach regardless of an accompanying warning. The prior art's Decision 3 *deferred* the magnitude arm to a sibling bug for scope-narrowing; that is overridden because the fix is *one shared mechanism* (the blocked-set extension), so splitting it would create two slices for one edit and leave a known soundness hole open across the gap — the opposite of the BUG-023 precedent, where the same recognition (one filter, both arms) kept them together.
- **Tradeoff accepted**: The magnitude fix touches the same `CollectBlockedConstraints` surface as the relational block, so the corpus soundness-tax (newly-red samples) may include magnitude-arm samples as well as relational — a slightly larger triage set in one slice. Accepted: triaging both arms together is cheaper than two passes, and the shared-mechanism fix is not meaningfully reviewable split.
