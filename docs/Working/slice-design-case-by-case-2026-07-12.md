# §2 case-by-case — slice design (conditional-expression arms + event-input narrowing + the ⊥ rails)

**How to read this document.** "Case-by-case" means: when a value is computed differently in different cases — the OR-branches of a guard, or the two arms of an `if C then T else E` expression — the proof engine analyzes **each case under the assumption that makes it run**, then combines the per-case results by taking the widest range that covers all of them (the *union*). Today the engine does this for guard OR-branches only; a conditional expression's two arms are analyzed **blind to the condition** (both arms see the full unrestricted ranges), and a guard about an **event input** (an event argument like `Reprice.Seats`) never narrows anything at the interval-proof site. This slice extends the existing case-by-case machinery to those two sources, and installs the two soundness rails the locked architecture assigns here: an infeasible case (one whose assumption contradicts the declared bounds — written "⊥", read "bottom", meaning the empty range) must never poison the combined result, and no narrowing step may ever *store* an empty range where a later reader would misread it as "trivially fine".

The seams are **ruled** (architecture §1.8, locked). This document is the DESIGN-REVIEW pass the readiness plan requires: each ruled seam is re-verified against engine source at file:line, the whole affected family is enumerated with an explicit disposition per cell, the certificate impact is checked against the settled Slice-0 vocabulary, and everything genuinely open is parked as a neutral question for the owner — nothing new is settled here.

## Goal

When this slice lands, a bound obligation whose site is a conditional expression is proven (or honestly rejected) **per arm**: each arm's range is computed under that arm's condition — including conditions over event arguments — and the union of the arm ranges is what containment checks. An infeasible branch never corrupts the union (and never discards a feasible sibling branch's narrowing), an empty range is never stored by any narrowing write, a negation is folded only when its extraction provably lost nothing, and every new verdict renders through the existing Slice-0 certificate vocabulary (`CaseSplit` with per-arm assumptions; no new step kind).

Concretely, on the corpus baseline verified live (2026-07-13): the `SeatBilling` worked example below moves from `Unresolved` with computed range `[9 .. 1000]` (PRE0078) to `Proven` with computed range `[10 .. 900]`, because the then-arm is finally allowed to know `Seats >= 10` and the else-arm to know `Seats <= 9`.

## Scope

- **In scope**
  - **(a) Conditional-expression arm narrowing** (ruled §1.8(a)): at the `TypedConditional` node of the interval walk (`IntervalOfNarrowed`, `ProofEngine.Intervals.cs:135-140` — today a condition-blind `Union`), split the condition, evaluate each arm under a copy of the narrowed environment folded with that arm's assumption, union across all arms including the implicit else (negating only *losslessly-extracted* single-leaf conditions; forfeiting narrowing on multi-leaf, multi-branch, or lossy negations — Rule 1).
  - **(b) Event-input narrowing** (ruled §1.8(b)): scope the narrowed-interval environment by subject kind (field vs. event arg), mirror the `TypedFieldRef` environment consult (`:67-69`) into the `TypedArgRef` case (`:99-100`), and fold arg flag-modifiers (e.g. `positive`) into the arg's base interval via the existing `FlagLowerBoundFromMeta` (`:253-267`). This **adds sound arg narrowing on top of** the Slice-0 Hole-2 base fix (the arg/field name-collision discriminator), which excludes arg facts from field entries; §2 re-admits them into their own scoped entries.
  - **(c) The ⊥ rule, per DNF branch** (ruled, §1.8 "⊥-arm rail"; branch granularity pinned in Rule 2): a branch whose assumption-fold collapses to the empty range is infeasible; its (empty) narrowed interval is never unioned; absent an explicit infeasibility derivation, that branch conservatively contributes the arm's evaluation under the un-narrowed (outer) environment, while feasible sibling branches keep their folded narrowing.
  - **(d) The dict-write ⊥ rail** (ruled, §1.8 F7 ownership statement): every write of a narrowed interval into a narrowing environment checks emptiness **at that write, uniformly** — one shared guarded-write mechanism, covering the two known unguarded sites (`Intervals.cs:571`, `:625`), the already-guarded relational site (`:651-653`, refactored onto the shared mechanism), and every new arm-fold write this slice adds.
  - **(e) Certificate wiring within the settled Slice-0 vocabulary**: the new arm sources render as `CaseSplit` arms with recorded assumptions and per-arm `ConditionNarrowing`/`ExclusionNarrowing` sub-derivations. No new step kind (verified below; the one evidence-form gap is parked as Open question 1).
- **Out of scope (verified against source; each cell dispositioned in the family table)**
  - Sign-set arm narrowing: the compositional sign path's conditional union stays condition-blind (`Composition.cs:438-439`) — condition-blind union is a sound superset; extending it is not in §1.8's ruled text.

  - The guard-decomposition policy for conditionals **in guard position** — `proof-engine.md:1219`'s "TypedConditional: do NOT decompose" stands unchanged; this slice touches conditional expressions at the *site* (the value being assigned), not in the guard grammar.
  - The Slice-0 items this slice builds on (not re-done here): the Hole-2 arg/field discriminator at the narrowing fold, the Hole-3 `ReassignedBefore` staleness gate in `BuildNarrowedIntervals`, the systematic fail-open/dict-write sweep (F6), the `ProofVerdict` DU + certificate builder.

- **Deferred**
  - Multi-leaf negation precision (an else-arm under a compound condition could narrow via per-leaf disjunction reasoning) — the same deliberate forfeit the sibling-reject path *intends* (`Intervals.cs:757-782`); revisit only on corpus evidence. **Caveat (found in this pass)**: the shipped sibling-reject judgment counts *extracted* leaves, not authored conjuncts, so its forfeit misfires when extraction drops an atom — a live false-`Proven` hole (Hole 5, below), not a sound forfeit.   - True infeasible-arm *exclusion* (skipping a ⊥ arm entirely, tightening the union) — requires an explicit infeasibility certificate step that the settled Slice-0 vocabulary does not contain; **parked** (Open question 2), the ruled conservative contribution is the shipping behavior.

## Language Design Grounding

**No new authored language surface.** This slice adds no keyword, type, operator, modifier, construct, or expression form — conditional expressions, event args, and their modifiers all exist. The public surface that *does* move is compiler-output vocabulary already settled at Slice 0 (`CaseSplit` and friends, `certificate-steps-membership-2026-07-12.md`), which this slice consumes without extending — with two candidate exceptions that are **parked, not settled** (Open questions 1 and 2: a possible new premise/evidence form for site-internal conditions, and a possible future infeasibility step). Per the pre-design consultation gate, both are owner decisions; the slice is designed to ship without either (the conservative forms need no new vocabulary).

## Legibility conventions

- *Arm* — one of the cases of a case split: a guard OR-branch, the then-arm, or the else-arm of `if C then T else E`.
- *Arm assumption* — the condition that must hold for that arm to be the one that runs (`C` for the then-arm; "not C" for the else-arm; the branch's AND-list for a guard OR-branch).
- *Narrowed environment* (in code: the "narrowed dict") — the per-subject table of tightened ranges the interval walk consults; today keyed by bare name (`ImmutableDictionary<string, NumericInterval>`), after this slice keyed by *subject* (field vs. event arg + name).
- *DNF split* — rewriting a compound condition into OR-alternatives, each an AND-list of simple comparisons (what `ExtractGuardBranches` already does, `Strategies.cs:789-855`).
- *⊥ (bottom)* — the empty range (`NumericInterval.IsEmpty`, `Max < Min`): no value can satisfy it; here it always means "this case cannot actually happen".
- *Forfeit* — deliberately not narrowing (keeping the wider, sound range) when the precise narrowing would need reasoning the engine doesn't do; always sound, sometimes weaker.
- *Lossless extraction* — a DNF split in which **every** atomic node of the condition produced its constraint; the split is *lossy* if any atom fell through unrecognized (`ExtractGuardLeafConstraints` handles only field/arg-vs-decimal-literal comparisons, `.count`, and presence — an atom like `B + C >= 10`, `A >= B`, or a text equality contributes **zero** leaves and today leaves **no marker** of the loss, `Strategies.cs:851-855`). Losslessness matters asymmetrically: dropping a conjunct only *widens* a positive fold (safe), but negating a condition whose atoms were dropped *excludes reachable values* (unsound).
- "§1.8", "F7", "F8", "Hole 2/3" — the architecture doc's labels for this slice's ruled seam and the adversarial-pass findings (`compiler-readiness-plan-2026-07-12-architecture.md`); spelled out where first used.

## Worked examples

All three compiled live 2026-07-13 (`precept_compile` as syntax oracle; current diagnostics quoted as observed baseline, not as design authority).

**Example 1 — the slice's flagship (arg condition + arg arms).** Syntax-valid; today: `Unresolved`, computed `[9 .. 1000]`, PRE0078.

```precept
precept SeatBilling

field AmountDue as decimal default 0 min 0 max 900

state Open initial
state Closed terminal

event Reprice(Seats as integer min 1 max 100)
event Close

from Open on Reprice
    -> set AmountDue = if Reprice.Seats >= 10 then Reprice.Seats * 9 else Reprice.Seats * 10
    -> no transition
from Open on Close -> transition Closed
```

Today both arms see `Seats ∈ [1, 100]` (and the arg's declared bounds only reach the walk through `ExtractArgInterval`): then-arm `[1,100]×9 = [9,900]`, else-arm `[1,100]×10 = [10,1000]`, union `[9,1000] ⊄ [0,900]` → rejected as unprovable. After this slice: then-arm under `Seats >= 10` → `[10,100]×9 = [90,900]`; else-arm under the negation `Seats <= 9` (exact integer half-step) → `[1,9]×10 = [10,90]`; union `[10,900] ⊆ [0,900]` → **Proven**. The certificate is one `CaseSplit` with two arms, each carrying its assumption, a `ConditionNarrowing`/`ExclusionNarrowing` on the arg subject, an `IntervalArithmetic`, then a single `BandContainment` on the union — every step a Slice-0 member.

**Example 2 — the ⊥-arm rail.** Syntax-valid; today: `Unresolved`, computed `[0 .. 999999]`, PRE0078.

```precept
precept OvertimeSheet

field HoursLogged as decimal default 0 min 0 max 80
field PayDue as decimal default 0 min 0 max 4000

state Open initial
state Closed terminal

event Reprice
event Close

from Open on Reprice
    -> set PayDue = if HoursLogged > 100 then 999999 else HoursLogged * 40
    -> no transition
from Open on Close -> transition Closed
```

The then-arm's assumption `HoursLogged > 100` intersected with the declared `[0, 80]` is ⊥ — the arm can never run. Under the ruled rail: the ⊥ is **never stored and never unioned** (raw `Union` with the `(0, -1)` empty sentinel would fabricate `[0, …]`, `NumericInterval.cs:131-135` — verified: no empty special-case); the arm conservatively contributes its evaluation under the outer environment (`[999999, 999999]`), so the union is `[0, 999999]` and the verdict stays honestly `Unresolved` — same *outcome* as today's baseline, now by rail rather than by luck, and pinned by a failing-test row. (Skipping the arm entirely would prove this example — that is precisely the precision this design does *not* take without an infeasibility certificate step; Open question 2.)

**Example 3 — a real corpus idiom this slice unlocks (with §3 money in place).** `samples/event-registration.precept:72`:

```precept
    -> set AmountDue = if UpdateSeats.Seats >= 10 then UpdateSeats.Seats * PricePerSeat * 0.9 else UpdateSeats.Seats * PricePerSeat
```

`Seats` is `integer positive max 100`. Event-input narrowing gives the then-arm `Seats ∈ [10,100]` and the else-arm `Seats ∈ [1,9]` (the `positive` flag folds a `≥ 0` floor via `FlagLowerBoundFromMeta`, and declared `min`-less `positive max 100` args stop being unbounded-below). ## Semantic Rules

Notation: `⟦e⟧N` = the interval of expression `e` under narrowed environment `N` (the `IntervalOfNarrowed` walk); `fold(N, A)` = a **copy** of `N` with assumption `A`'s leaf constraints intersected in via `NarrowByConstraint` (integer/decimal boundary dispatch as shipped, `Satisfiability.cs:256-279`), every write ⊥-railed (Rule 3).

**Rule 1 — conditional-arm evaluation (replaces the condition-blind union at the `TypedConditional` walk node).**

```
⟦if C then T else E⟧N  =  ThenVal ∪ ElseVal   where

  branches(C)      = DNF split of C (reuse the ExtractGuardBranches algebra), REVISED to
                       thread an extraction-completeness flag: any atomic node that yields
                       no recognized leaf marks the split LOSSY (today the fallthrough at
                       Strategies.cs:851-855 drops such atoms silently — see Hole 5 below)
  ThenVal          = ⋃ over b ∈ branches(C) of  ⟦T⟧fold(N, b)
                     — a branch contributing no extractable numeric leaf folds nothing
                       (fold(N, ∅) = N), and a LOSSY branch simply folds fewer conjuncts:
                       both are sound for the positive direction, because dropping a
                       conjunct only WIDENS the fold
  ElseVal          = ⟦E⟧fold(N, ¬C)   when ¬C is representable AND the split of C is
                       LOSSLESS: C is syntactically a single atomic comparison whose
                       extraction lost nothing — one DNF branch, one leaf, no dropped atom
                       (NegateConstraintToInterval, Intervals.cs:819-840 — integer exact
                       half-step; decimal closed-at-V sound superset; Equals not
                       representable ⇒ forfeit)
                   = ⟦E⟧N              otherwise (multi-leaf / multi-branch / LOSSY
                       negation FORFEITS — the forfeit the sibling-reject path intends,
                       Intervals.cs:757-782, corrected for the lossy case)
```

**The losslessness precondition is soundness-critical, not a precision detail.** Judging "single branch, single leaf" over *extracted* leaves — as the shipped sibling-reject path does — silently treats `A >= 10 and B + C >= 10` as the single-leaf condition `A >= 10` (the arithmetic-LHS atom extracts nothing and vanishes, `Strategies.cs:851-855` + AND cross-product `:836-848`), so folding `¬(A >= 10)` into the else-arm excludes reachable values: the else-arm also runs when `A = 50` and `B + C < 10`. **Hole 5 (live, shipped, confirmed by probe 2026-07-13)**: the identical defect in `BuildSiblingRejectExclusions` (`Intervals.cs:768-782` counts extracted leaves only) makes a success row under a compound-guarded reject sibling compile **`Proved` today with a reachable violation** (RejectProbe in the front-matter sources: `Proved [0 .. 100]` while `Amount = 500` with `Bonus + Fee < 10` reaches the row). This is a fifth fail-open hole of the same family as architecture §2.1 Holes 1-4, absent from that inventory and from the §2.2 F6 sweep list (which covers bool?-returns and dict-writes, not extraction-lossiness); it is flagged for routing to the Slice-0 fail-open inventory with a failing-test-first regression (ownership parked with Open question 3, which already governs the analogous F7 test ownership). Whichever slice owns it, the fix is the same losslessness precondition Rule 1 states, applied to the sibling-reject single-leaf judgment.

Nested conditionals recurse through the same rule (finite tree, no fixpoint — spec §0.4 property 1). Reduction/typing are untouched: the conditional's runtime semantics and result type are unchanged; only the compile-time abstraction of its value tightens.

**Rule 2 — the ⊥ rule, per DNF branch (ruled, architecture §1.8; granularity pinned here).** The unit of infeasibility is the **DNF branch**, not the whole arm: if a branch `b`'s assumption-fold produces an empty intersection for some subject, that *branch* is infeasible — its narrowed evaluation is discarded and it contributes `⟦arm⟧N` (the arm evaluated under the **outer** environment, assumption not applied) to the union; every *feasible* branch still contributes its folded evaluation. The arm's value is the union over branch contributions, so one contradictory disjunct never discards a sibling disjunct's sound narrowing (e.g. `if A >= 200 or A >= 10 then T else E` with `A` declared `[0, 100]`: branch `A >= 200` folds to ⊥ and contributes `⟦T⟧N`; branch `A >= 10` contributes `⟦T⟧fold(N, A >= 10)`). ⊥ itself is never an operand of `Union` — excluding a branch entirely would be a positive infeasibility claim that the certificate cannot currently record (Open question 2); contributing a superset is unconditionally sound. **Certificate granularity (pinned)**: one `CaseSplit` arm **per DNF branch** of the condition plus one arm for the else — matching the arm-per-branch shape the shipped guard OR-branch union already renders under the Slice-0 vocabulary; no nested branch sub-splits inside a single arm. (Both granularities are sound supersets; this pin exists so the implementation and criterion 5's certificate assertions target one shape.)

**Rule 3 — the dict-write ⊥ rail (ruled, architecture §1.8 F7).** Every write of a narrowed interval into a narrowing environment goes through one shared guarded write: if the value to be stored `IsEmpty`, the write is refused and the ⊥ signal is surfaced to the writing fold (which applies its conservative policy — Rule 2 for arm folds; keep-prior-value for the sibling and relational folds, generalizing the suppression the relational fold already ships at `Intervals.cs:646-653`). The rail lives **at write time, uniformly** — not per-fold (the drift that produced the `:571`/`:625` leaks) and not inside interval arithmetic (the §1.5 kernel guard's `IsEmpty ⇒ Unbounded` conversion *launders* the infeasibility signal the rail needs to see; the kernel guard remains the last-resort backstop, per the architecture's §1.5-vs-§1.8 resolution). The rail applies to narrowing environments consumed by containment reads; it deliberately does **not** apply to the satisfiability scans (`FoldConstraintsInto`, `Satisfiability.cs:295-314`), where an empty fold is the *sought contradiction signal*, not a leak.

**Rule 4 — event-input narrowing (ruled, architecture §1.8(b)).** The narrowed environment is keyed by **subject** — (kind: field | arg, name, and for args the owning event) — never by bare name (the Slice-0 Hole-2 discriminator made bare-name keying a fixed soundness bug; this rule is its positive counterpart). `fold` routes a leaf whose `GuardConstraint.IsArg` is true (extraction already stamps it — `Strategies.cs:923-942`) to the arg-scoped entry, seeded from the arg's base interval; a field leaf to the field-scoped entry, exactly as today. The walk's `TypedArgRef` case consults the arg-scoped entry before falling back to `ExtractArgInterval` — mirroring the three-line `TypedFieldRef` consult (`Intervals.cs:67-69` vs `:99-100`). An arg-scoped entry applies only when the walk's `TypedArgRef.EventName` matches the entry's event. The arg base interval is `ExtractArgInterval` (declared min/max, `Intervals.cs:312-330`) **tightened by the arg's flag modifiers** via the shared `FlagLowerBoundFromMeta` (`:253-267`) over `TypedArg.Modifiers` (`SemanticIndex.cs:492`) with the same applicability check the field path uses — closing the asymmetry where a field's `positive` reaches proofs but an arg's does not. (Args carry no `ImpliedModifiers` property — type-implied modifiers for args are dispositioned in the family table and Open question 4.)

**Rule 5 — staleness and same-instant soundness.** The arm assumption is **never stale**: a conditional expression's condition and arms are evaluated at the same instant over the same working values (expression purity, spec §0.4 property 6 — expressions cannot mutate), so the assumption provably holds exactly when the arm's reads happen. Staleness discipline applies where it already does — to the **outer** environment's guard facts (the Slice-0 Hole-3 fix makes `BuildNarrowedIntervals` respect `ReassignedBefore`), which the arm folds inherit by copying `N`. Arg subjects cannot be reassigned (assignment targets are fields; args are read-only event inputs), so arg facts are exempt from `ReassignedBefore` by construction — pinned by acceptance criterion 9 rather than assumed silently.

**Soundness-preservation claim (principles 7/10/11).** Every rule above only ever *intersects with conditions that provably hold on the arm's execution path* (Rules 1, 4, 5) or *widens conservatively* (Rules 1-forfeit, 2): no new inference can produce a range narrower than the true reachable set, so no false `Proven` is introduced (principle 11); the ⊥ rails close the one mechanism by which the new power could have over-proven (`Contains(⊥) ⇒ true`, `NumericInterval.cs:125-129`, plus `Union`'s empty-corruption, `:131-135`) (principles 10/11); all reasoning is compile-time, deterministic, and bounded by expression size (principle 7, spec §0.4). Single-hop is preserved: an arm fold intersects the *subject's own* entry with a constant-comparison leaf — it never chases a second field through a relation (the relational fold is untouched and keeps reading bare declared intervals only, `Intervals.cs:629-654`).

### External architectural precedent

This is a ruled-seam extension of an in-engine mechanism, not a new architecture, so no fresh comparator study was commissioned. The counter-pole guarded against is join-point precision loss: a conditional *expression* has no reconverging control flow (spec §0.4 properties 2-3), so per-arm evaluation plus union is exact case analysis, not a widened dataflow join.

### Decision 1 (confirmation): Conditional-expression arms evaluate under their assumptions via the existing DNF-union scaffold — no new fact records, no CFG

**Stakes**: high (the slice's proving power; a wrong assumption fold is a false-`Proven` machine).

- **Rationale**: the ruled seam (§1.8(a)) names exactly this shape, and source verification confirms every ingredient exists and composes: the walk's conditional node is a two-line condition-blind union (`Intervals.cs:135-140`); the split/fold/negate/union algebra is shipped and battle-tested on guard OR-branches (`Strategies.cs:789-855`, `Satisfiability.cs:256-279`, `Intervals.cs:819-840`, `:584-606`). A conditional expression has no reconverging control flow (spec §0.4 properties 2-3), so per-arm evaluation + union is *exact case analysis* over the abstraction — the else arm is structurally always present (`TypedConditional`, `SemanticIndex.cs:123-130`), so the union is total.
- **Alternatives considered and rejected**: (a) *a general CFG/path-sensitive framework* — rejected by the ruled seam itself ("over-built; the DNF union suffices", §1.8 rationale leg) and by spec §0.4 (no reconverging flow exists to model); (b) *narrowing only the then-arm and leaving the else blind* — rejected: the implicit else's negation is exactly where the flagship integer cases get their tightness (`[1,9]` in Example 1), and the sibling-reject path already ships the same negation machinery; (c) *decomposing conditionals in guard position too* — rejected: out of the ruled seam, and `proof-engine.md:1219` is a standing decision this slice must not silently override.
- **Precedent**: the shipped OR-branch union (`Intervals.cs:584-606` — the architecture's own precedent leg); the abstract-interpretation assume/test transfer (in-tree survey `:135/:158`, quoted under Architecture Grounding).
- **Tradeoff accepted**: multi-leaf, multi-branch, and lossy negations forfeit else-arm narrowing (sound, sometimes weaker) — matching the sibling-reject path's *intended* forfeit, with the losslessness precondition Rule 1 adds (the shipped extracted-leaf-count judgment is Hole 5, a live false-`Proven`, and is NOT the precedent being copied); per-arm × per-branch evaluation multiplies walk cost, bounded by expression size and priced by acceptance criterion 14.
- **Sources for this decision**: architecture §1.8(a) (ruled text + its four legs, `:104/:112`); `Intervals.cs:135-140`, `:819-840`, `:757-782`; `Strategies.cs:789-855`; spec §0.4 `:158-174`; live baseline probes (Example 1/2).

### Decision 2 (confirmation): Event-input narrowing = subject-scoped environment + `TypedArgRef` consult + arg flag fold, on top of the Slice-0 Hole-2 base

**Stakes**: high (this is where the Slice-0 fail-open fix and new power meet; a scoping mistake recreates the collision bug in reverse).

- **Rationale**: the ruled seam (§1.8(b)) names the three moves, all verified needed at source: the environment is bare-name-keyed and the walk's `TypedArgRef` case never consults it (`Intervals.cs:99-100` vs the field consult at `:67-69`); `ExtractArgInterval` reads declared min/max only — an arg's `positive`/`nonnegative` flag currently contributes nothing (`:312-330`, vs the field path's fold at `:202-220`); and the extraction layer already stamps `IsArg` (`ProofEngine.cs:31-39`, `Strategies.cs:923-942`) so no re-derivation is needed. Scoping the environment by subject kind is the *positive* half of the Slice-0 Hole-2 discriminator (which only *excludes* arg facts from field entries): the same discriminator that stops the collision routes each fact to its rightful subject. The engine's existing subject shape (`NumericSubjectRef(Kind, Name, EventName)`, `ProofEngine.cs:77-86`) is reused as the key notion — no parallel subject concept.
- **Alternatives considered and rejected**: (a) *keep bare-name keys and rely on the Slice-0 exclusion forever* — rejected: forfeits all arg narrowing, leaving the corpus's arg-conditioned discount idiom permanently unprovable (Example 3), and the exclusion-only posture was explicitly reclassified as the *base* §2 builds on, not the end state (architecture §1.8 F1 note); (b) *name-mangled string keys (e.g. `"arg:Event.Name"`)* — rejected: stringly-typed identity where a typed subject record exists (reuse rule; the nullable-field/encoded-shape smell); (c) *narrow args by rewriting arg refs to synthetic fields* — rejected: forks the subject model and breaks the arg-specific admissibility facts (args are never reassigned; args carry no implied modifiers).
- **Precedent**: the count path already scopes correctly by filtering `gc.IsArg` (`ProofEngine.cs:708`) and the satisfiability fold already seeds arg constraints away from field intervals (`Satisfiability.cs:307-310`) — this decision brings the value-interval path up to the discipline its siblings already ship.
- **Tradeoff accepted**: the environment key widens (a struct key instead of `string`), touching every consult site in one slice — mechanical but cross-cutting inside `ProofEngine.Intervals.cs`; arg narrowing applies only within the owning event's rows (an arg-scoped entry with a mismatched event never applies), which is the sound scope but means cross-event reuse of same-named args yields nothing (correct: different events' args are different subjects).
- **Sources for this decision**: architecture §1.8(b) + Hole-2 reclassification note (`:104/:151`); `Intervals.cs:67-69/:99-100/:312-330/:202-220/:253-267`; `ProofEngine.cs:31-39/:77-86/:708`; `Strategies.cs:923-942`; `SemanticIndex.cs:487-507` (`TypedArg.Modifiers` exists; no `ImpliedModifiers`).

### Decision 3 (confirmation): The ⊥ rails — arm-level conservative contribution + one uniform dict-write guard; kernel guard stays the backstop

**Stakes**: high (soundness-critical; the ruled §1.5-vs-§1.8 resolution depends on the rail sitting exactly here).

- **Rationale**: both rails are ruled verbatim (§1.8 "⊥-arm rail (soundness-critical, locked)" and the F7 ownership statement), and the source verification confirms both the vector and the leak sites: `Union` does not special-case empty (`NumericInterval.cs:131-135` — `Union((0,-1), [5,10]) = [0,10]`, fabricated coverage), `Contains(⊥) ⇒ true` (`:125-129`), and the two named writes store unchecked intersections (`Intervals.cs:571-572`, `:625`) while the relational fold suppresses (`:646-653`) and the containment read backstops (`:509`) — the per-fold scattering §1.8 predicts ("the next fold forgets it") is exactly the observed state. One shared guarded write makes the rail structural: every current site and every future fold (including this slice's own arm folds) inherits it by construction. The ⊥-arm policy (contribute the arm's outer-environment evaluation) is the ruled conservative default: excluding an arm is a positive infeasibility claim, and "⊥ is never an ambient default in either direction" (§1.8). The ruled phrase "un-narrowed base interval" (architecture `:106`) admits **two legal readings**, and this design *chooses* one rather than claiming the text forces it: **(reading A, chosen)** the arm evaluated under the outer environment `N` without the arm assumption — the tightest unconditionally-sound contribution (a superset of every feasible evaluation, still benefiting from sound outer guard facts); **(reading B, not chosen)** the arm evaluated under bare declared intervals with no outer facts at all — also sound, strictly wider, weaker for no benefit. Contributing nothing is not a reading (that is the exclusion the rule forbids). Reading A is surfaced for a one-word owner confirmation at the slice-boundary review (Open question 5) rather than presented as the unique interpretation.
- **Alternatives considered and rejected**: (a) *per-fold ⊥ checks* — rejected by the ruled text ("drifts — the next fold forgets it, which is exactly how `:571`/`:625` came to leak"); (b) *rely on the §1.5 kernel guard alone* — rejected by the ruled resolution: `IsEmpty ⇒ Unbounded` inside arithmetic launders the infeasibility signal before the union can see it; the kernel guard is the last resort, never the detector; (c) *skip ⊥ arms outright (tighter unions)* — not available without an infeasibility certificate step (Slice-0 vocabulary has none); parked as Open question 2, not taken silently.
- **Precedent**: the relational fold's shipped suppression (`Intervals.cs:646-653` — the same conservative policy, already reviewed and landed) and the containment read's backstop (`:509`); externally, the standard abstract-interpretation treatment of an infeasible branch (bottom propagates as "unreachable", never as "trivially safe").
- **Tradeoff accepted**: conservative ⊥-arm contribution forfeits provable tightness (Example 2 stays `Unresolved` though the offending arm is provably dead); one more indirection on every narrowing write (negligible; the helper is a branch on a struct property).
- **Sources for this decision**: architecture §1.8 `:106-112` (both rails + the resolution); §2.3 F7 `:166`; `NumericInterval.cs:125-135`; `Intervals.cs:509/:571-572/:625/:646-653`.

### Decision 4 (confirmation + one parked gap): No new certificate step kind — `CaseSplit` gains arm sources as payload; the evidence form for site-internal conditions is parked

**Stakes**: medium (public output vocabulary — the whole point is that it does NOT change).

- **Rationale**: verified against the settled Slice-0 vocabulary member by member: `CaseSplit` ships at Slice 0 as a compound step with per-arm labeled assumptions and nested sub-derivations, and its recompute rule already carries all three combiner forms — interval union, sign-set union, all-arms-establish (`certificate-steps-membership-2026-07-12.md:190-191`, Decision 7 `:458-466`); the certificate design's own growth accounting states this slice's exact case: "§2 case-by-case extends `CaseSplit` arm *sources* (conditional-expression arms, event-input narrowing) — the kind, its combiner semantics, and per-arm assumptions ship at Slice 0 … §2's ⊥-arm skip rule is engine behavior whose certificate effect is 'arm recorded as infeasible-contributes-base-interval' — payload, not a new kind" (Decision 6, `:450`). Per-arm narrowing renders through existing `ConditionNarrowing`/`ExclusionNarrowing`; arg evidence has legal premises — `DeclaredBound` explicitly covers "a bound modifier on a field **or arg**" and `GuardCondition` covers guard leaves including arg leaves (Decision 1 items 1/5, `:337/:341`). **The one gap found**: a conditional-*expression* condition is not a guard, rule, ensure, reject-row, or declaration — none of the eleven premise kinds quotes it. The certificate format offers a second legal route: the obligation's site expression is *shared context* ("literal leaves of the site need no premise — they are read from the site itself", `:158`), and the condition is a subexpression of the site. Whether the arm assumption is recorded as site-context (no premise) or needs a premise-kind change is **public-vocabulary surface — parked as Open question 1**, not settled here; the slice is buildable under the site-context reading without a *premise-kind* change — though even that reading touches Decision 7's assumption-form sentence, per Open question 1's blast-radius note — and the build must not silently widen `GuardCondition`'s settled meaning.
- **Alternatives considered and rejected**: (a) *a new `ConditionalArm`/`SiteCondition` step kind* — rejected: the split/union inference is exactly `CaseSplit`'s recompute rule; a second kind for the same inference is the parallel-vocabulary smell, and the certificate design's Falsifier 2 counts any §2 membership growth as a growth-accounting failure; (b) *silently widening the `GuardCondition` premise to cover site conditions* — rejected: changes a settled premise kind's meaning without owner ruling (that is Open question 1's option, to be *chosen*, not defaulted); (c) *no assumption recording (condition-blind certificates over condition-aware narrowing)* — rejected: the certificate would claim a union the recorded derivation cannot reproduce — dishonest under the recomputability contract.
- **Precedent**: the Slice-0 design's own §2 pre-accounting (Decision 6/7, cited above); the coverage table's interval-containment row already lists `CaseSplit` among that path's steps (`:317`).
- **Tradeoff accepted**: `CaseSplit` arm payloads grow richer (arm-source tag: guard-branch | conditional-arm | assumption-not-applied), which the Slice-0 DTO/hover rendering must carry — payload evolution inside a stable vocabulary, the exact growth path the certificate design chose. The ⊥-branch payload wording is deliberately derivation-honest ("assumption not applied — contributed evaluation under the outer environment") rather than asserting "infeasible": infeasibility is a positive claim the Slice-0 vocabulary cannot derive as a step (exactly Open question 2's gap), so it appears only as a non-load-bearing annotation until/unless OQ2(b) adds an infeasibility step. (The certificate design's own Decision 6 phrase "arm recorded as infeasible-contributes-base-interval" describes the *engine behavior* being recorded; the payload text chosen here avoids claiming what the recorded derivation cannot recompute.)
- **Sources for this decision**: `certificate-steps-membership-2026-07-12.md:158/:190-191/:317/:337/:341/:450/:458-466`.

### Decision 5 (scope confirmation): Value-interval domain only; every other domain × case-source cell stays as shipped, explicitly

**Stakes**: medium (scope honesty; prevents both silent scope creep and silent bar-lowering).

- **Rationale**: the ruled seam's text is specifically about the narrowed-interval environment and the interval walk (`NarrowByConstraint`, `NegateConstraintToInterval`, `TypedArgRef` interval consult — all value-interval machinery); the family table above gives every other cell an explicit disposition with its soundness argument (each non-extended cell is a sound superset today — condition-blind union or conservative decline — so leaving it is a completeness limit, not a hole). Enumerating the whole family is this project's standing discipline; the table is the enumeration.
- **Alternatives considered and rejected**: (a) *extend sign-set arm narrowing in the same slice* (fold arm assumptions into `ResolveNumericSignSet`'s conditional case, `Composition.cs:438-439`) — rejected: outside the ruled text; touches the compositional strategy's fact plumbing (a different seam); nothing in the corpus baseline shows a sign-blind conditional as a live rejection driver; available to a future slice through the normal design path; (b) *extend length/count conditional arms* — rejected on the same grounds (and the count domain's integer seed machinery is structurally separate, `ProofEngine.cs:690-740`).
- **Precedent**: the per-slice capability boundaries the plan board draws (each proof capability lands as its own designed slice); the certificate design's same-shaped scope note for §3 ("adds transfers, not inference forms").
- **Tradeoff accepted**: a conditional site whose obligation is sign-shaped (e.g. a divisor that is conditionally assigned) gains nothing from this slice even though its value-interval sibling does — an asymmetry the family table documents rather than hides.
- **Sources for this decision**: architecture §1.8 (ruled text names only interval machinery); `Composition.cs:438-439`; `ProofEngine.cs:690-740`; family table above.

## Acceptance criteria (design-level; the failing-test `# EXPECT:` matrix derives from corrected canon at build time, gated on owner sign-off)

All proof-stage assertions full-compile (`Compiler.Compile` — never type-checker-only `Check*`), per the plan's acceptance frame. The three inherited invariant cells (⊥-suppression, single-hop/anti-transitivity, certificate re-checkability-in-principle) are mandatory rows.

1. **Flagship arm narrowing (arg condition + arg arms)**: the `SeatBilling` example compiles with the obligation `Proven`, computed interval `[10 .. 900]` (baseline today: `Unresolved`, `[9 .. 1000]`, PRE0078 — verified live).
2. **Field-condition arms**: an equivalent example whose condition is over a *field* (e.g. `if HoursLogged >= 10 then … else …` with bounded fields) proves per-arm identically — the arm fold is subject-kind-agnostic.
3. **Implicit-else boundary dispatch**: integer subjects get the exact half-step (`>= 10` negates to `<= 9`); decimal-backed subjects close at V (sound superset) — mirroring `NegateConstraintToInterval`'s shipped dispatch; one test row per domain.
4. **Multi-leaf negation forfeit**: a compound condition (`A >= 10 and B >= 5`) narrows the then-arm per its AND-leaves but leaves the else-arm un-narrowed; the verdict never over-proves (no false `Proven` on a case only the forfeited negation could license).
4b. **Lossy-negation forfeit (the Hole-5 cell, at the conditional site)**: a compound condition with an *unextractable* conjunct (`A >= 10 and B + C >= 10` — the arithmetic-LHS atom drops during extraction and the condition *presents* as single-leaf) must NOT narrow the else-arm: the else-arm evaluates under `N`, and no `¬(A >= 10)` fold is applied. Same assertion for a text-equality conjunct (`A >= 10 and Name = "x"`) and a field-op-field conjunct (`A >= 10 and B >= C`). The then-arm may still fold the extracted `A >= 10` (loss-tolerant direction).
5. **⊥-branch conservative contribution**: the `OvertimeSheet` example stays `Unresolved` with a finite, uncorrupted computed interval (`[0 .. 999999]` shape — never an interval whose lower edge was fabricated by unioning the empty sentinel); the certificate's `CaseSplit` records the ⊥-branch arm with the derivation-honest payload ("assumption not applied — contributed evaluation under the outer environment").
5b. **Per-branch ⊥ granularity (multi-branch, one infeasible)**: for `if A >= 200 or A >= 10 then T else E` with `A` declared `[0, 100]`, the infeasible branch (`A >= 200`) contributes `⟦T⟧N` while the feasible branch's narrowing (`A ∈ [10, 100]`) is retained — the whole then-arm does NOT revert to `⟦T⟧N`; the certificate carries one `CaseSplit` arm per DNF branch plus the else arm (Rule 2's pinned granularity).
6. **Dict-write rail (the inherited ⊥-suppression cell)**: unit tests on the guarded-write helper plus per-site tests for every enumerated write site (the `:571`/`:625` shapes reproduced as failing-first regressions if the Slice-0 sweep has not already pinned them); no path lets `Contains(⊥) ⇒ true` discharge.
7. **Arg/field name collision (regression on the Slice-0 base)**: an event arg sharing a field's name — a guard/condition on the arg never narrows the field's entry and vice versa, *and* each subject's own scoped entry works (the positive counterpart the base fix lacked).
8. **Arg flag fold**: an arg declared `positive` (no explicit `min`) contributes a `≥ 0` floor to its base interval (today: contributes nothing — `ExtractArgInterval` reads declared min/max only).
9. **Staleness discipline**: (a) outer guard facts about a field reassigned earlier in the chain do not narrow arm folds (inherits the Slice-0 Hole-3 fix through the copied environment); (b) the arm assumption itself narrows even when outer facts are stale (same-instant soundness, Rule 5); (c) build-time verification that args are structurally unassignable (no `set` target can be an arg) — if that check fails, arm-fold arg exemption is wrong and the design returns to review.
10. **Certificate contents**: an arm-narrowed `Proven` verdict carries exactly one `CaseSplit` whose arms hold recorded assumptions and nested `ConditionNarrowing`/`ExclusionNarrowing` + `IntervalArithmetic` steps, concluded by one `BandContainment` — every premise span-cited, every step a Slice-0 member, zero uncataloged content (the inherited re-checkability cell).
11. **Single-hop / anti-transitivity (inherited cell)**: a conditional arm whose condition relates two fields (`if A >= B then …`) does not chase `B`'s guard-narrowed value into `A`'s arm entry — relational reading stays bare-declared-interval, one hop (the two-hop case stays undischarged).
12. **Nested conditionals**: a conditional inside a conditional arm produces nested `CaseSplit`s and terminates by structure (no fixpoint; expression-tree depth bounds recursion).
13. **No new rejections (with the false-`Proven`-correction carve-out)**: the full `samples/` corpus compiles with no obligation flipping from `Proven`/clean to rejected as a result of this slice, **except** flips that correct a false `Proven` (the Hole-5 lossy-negation shape, and — if F7 ownership lands in §2 before §3's kernel guard per Open question 3 — any stored-⊥ shape the `:509` read backstop did not already catch); such flips are corrections, itemized in the slice report under the architecture §2.1 Hole-1 reconciliation posture, not regressions. Sign-path conditional behavior is regression-pinned unchanged (`Composition.cs:438-439` semantics). The unqualified claim holds given the `Intervals.cs:509` read backstop plus the §3 kernel guard (or the Slice-0 F6 sweep) in place — the dependency is stated, not silent.
14. **Corpus reconciliation + budget**: full-corpus compile stays within the interactive budget (~44 ms baseline, no user-visible regression); `samples/event-registration.precept`'s conditional rows (with §3 money transfers in place) get strictly narrower computed intervals and no false `Proven`; all touched `# EXPECT:` contracts reconciled in the same commit.
15. **Hole-5 sibling-reject regression (failing-test-first; ownership per Open question 3, idempotent)**: the RejectProbe shape (compound-guarded reject sibling with an unextractable conjunct above a success-row assignment) must NOT compile `Proved` — the sibling single-leaf judgment applies the same losslessness precondition as Rule 1. If Slice 0 has already landed this fix, this row is the passing regression pin; if not, this slice installs it failing-test-first.

## Open questions (parked for owner — neutral framing; nothing settled here)

1. **Evidence form for the conditional-expression arm assumption in the certificate** *(public output vocabulary — the settled Slice-0 premise set has no member for it)*. A conditional-expression condition is authored text inside the obligation's own site expression — not a guard, rule, ensure, reject-row, or declaration, so none of the eleven settled premise kinds quotes it (`certificate-steps-membership-2026-07-12.md` Decision 1), while the settled format also says the site is shared context needing no premise for its own leaves (`:158`). Canonical areas checked: the certificate design's premise vocabulary + site-context rule; `proof-engine.md` certificate section (Slice-0-authored; no answer). Options, neutrally:
   - **(a) Site-context, no premise**: the `CaseSplit` arm payload records the condition (with its span inside the site) as site-derived context, like literal leaves. No premise-kind change (but see the blast-radius correction below — Decision 7's assumption-form sentence still needs a one-sentence revision); the assumption is not a first-class quotable premise (slightly weaker uniformity for a §5b checker, which must read it from the arm payload instead of the premise list).
   - **(b) Widen the `GuardCondition` premise kind** to "a leaf condition of the governing guard *or of a conditional expression at the site*". One settled kind's meaning changes (a revision to Slice-0's settled vocabulary — owner-gated by definition); renders uniformly.
   - **(c) A new premise kind** (e.g. a site-condition premise). Honest and narrow; grows the settled eleven — the exact kind of membership change the certificate design routes to owner ruling (its Falsifier 2 accounting).
   The slice is buildable under (a) with zero *premise-kind* change; the build must not silently do (b) or (c). **Blast-radius correction (review pass)**: option (a) is not quite "zero vocabulary change" — the settled Decision 7 states "The arm assumption is either a cited premise's condition or its negation" (`certificate-steps-membership-2026-07-12.md:462`), and a conditional-expression arm assumption under (a) is *neither* (it is site-derived, not a cited premise). So even (a) requires a one-sentence revision of Decision 7's assumption-form wording; the owner ruling on this question should cover both the evidence form and that sentence.
2. **True infeasible-arm exclusion (precision upgrade — new certificate surface)**. The ruled ⊥-arm rail makes an infeasible arm contribute its base evaluation because excluding it is a positive claim needing an explicit infeasibility derivation, and the settled step vocabulary has no infeasibility step. Consequence verified live: Example 2 stays `Unresolved` though its offending arm is provably dead. Canonical areas checked: architecture §1.8 (locks the conservative default), certificate membership (no infeasibility member; growth is owner-gated). Options, neutrally: **(a)** keep the conservative contribution (ruled default; zero new surface; some provable definitions stay rejected with an honest weakest-precondition message); **(b)** add an infeasibility step kind in a future slice through the catalog's normal growth path, enabling arm exclusion (tighter unions; one more public step kind; trips the certificate design's growth accounting, hence owner ruling). This design ships (a); (b) is logged, not proposed.
3. **F7 sequencing — Slice 0 or §2?** The locked architecture says the three §2.3 findings incl. F7 are "soundness-critical and **fixed at Slice 0**, but their home is the locked section they modify … F7 — ⊥ leaks at two unguarded dict-write sites … : **§1.8**" (`architecture §2.3, :163-166`), and Slice 0 owes the dict-write sweep ("every dict-write site … does it guard ⊥ before storing — see §1.8's F7 ownership statement", `:159`); the plan's slice board instead lists "the ⊥-arm skip rail + the dict-write ⊥ rail (F7)" under **§2** (`plan :88/:341`, architecture §4 table `:214`). Both readings are workable and the design is idempotent under either (if Slice 0's sweep already guarded `:571`/`:625`, this slice refactors those guards onto the uniform helper; if not, this slice installs them failing-test-first). Needs the owner because it decides **which slice's failing-test matrix owns the two known leak regressions** — the same test must not be double-owed or fall between slices. **Scope extension (review pass)**: the same ownership ruling should cover the **Hole-5 lossy-negation regression** (criterion 15) — a fifth fail-open hole confirmed live in this pass (`BuildSiblingRejectExclusions`' extracted-leaf single-leaf judgment, `Intervals.cs:768-782`; RejectProbe compiles `Proved [0 .. 100]` with a reachable violation), absent from architecture §2.1's Holes 1-4 inventory and from the §2.2 F6 sweep list. It has the same shape as F7: soundness-critical, naturally home in the Slice-0 fail-open inventory, idempotent under either owner (this design fixes it via Rule 1's losslessness precondition if Slice 0 has not). Routing it into the architecture doc's inventory is a proposed doc correction (not applied here — that doc is not this design's to edit).
4. **Type-implied modifiers for event args**. Fields get type-implied modifiers from the Types catalog (`TypedField.ImpliedModifiers`, populated at `TypeChecker.cs:689-693`); `TypedArg` has no `ImpliedModifiers` property (`SemanticIndex.cs:487-507`), so an arg declared as e.g. `exchangerate` would not fold its type-implied `positive` into the arg base interval under this slice (authored modifiers only — sound, weaker). Canonical areas checked: `proof-engine.md:1786` ("no type-level implied-qualifier pass for args" — the *qualifier* statement; no statement found for implied *modifiers* on args), Types catalog implied-modifier design (fields-focused). Options, neutrally: **(a)** authored-arg-modifiers only in this slice (zero TypeChecker change; documented asymmetry); **(b)** populate `TypedArg.ImpliedModifiers` from the Types catalog symmetrically (small TypeChecker + record change; removes the asymmetry; touches a Slice-0-adjacent surface — the certificate's `CatalogFact` third arm would then also fire for args). Default under silence is (a) (the weaker, sound posture); (b) is a scope question for the owner.
5. **Reading of the ruled "un-narrowed base interval" (one-word confirmation)**. The locked ⊥-rail text says a ⊥-branch "conservatively contributes its **un-narrowed base interval**" (architecture §1.8, `:106`) — genuinely ambiguous between two sound readings: **(A)** the arm evaluated under the *outer environment* `N` (assumption not applied; keeps sound outer guard facts — the tightest unconditionally-sound contribution) and **(B)** the arm evaluated under *bare declared intervals* (no outer facts; strictly wider, weaker for no benefit). This design proceeds under (A) (Decision 3) and asks for a one-word owner confirmation at the slice-boundary review; if the owner intended (B), Decision 3's contribution rule and criterion 5's expected payload change, nothing else does.
