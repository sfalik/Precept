## Language Design Grounding

### General language design — occurrence typing / flow-sensitive narrowing

The construct is **path-sensitive (occurrence / flow-sensitive) narrowing**: a predicate appearing in a position that *guards* a sub-expression's evaluation refines the type/value-environment of that sub-expression. This is a well-established field technique, and its soundness universally rests on the language's actual short-circuit / single-branch evaluation semantics.

**Typed Racket — occurrence typing** (Tobin-Hochstadt & Felleisen, "Logical Types for Untyped Languages", ICFP 2010; "The Design and Implementation of Typed Scheme", POPL 2008). The system threads two propositions per expression — what holds when it evaluates true (`ψ+`) and when false (`ψ−`) — and `and`/`or`/`if` propagate them:

> "Each expression is associated with two propositions, describing the facts that hold when the expression evaluates to a true value and to a false value, respectively. ... For `(if e1 e2 e3)`, we type-check `e2` in an environment extended with the *then*-proposition of `e1`, and `e3` in an environment extended with the *else*-proposition of `e1`." (POPL 2008, § 3, "the logic of occurrence typing")

Precept **takes** the then/else environment split wholesale: `if C then T else E` reasons about `T` under `facts⁺(C)` and `E` under `facts⁻(C)`, and `A and B` is the desugaring `if A then B else false` so `B` is reasoned under `facts⁺(A)`. Precept **diverges** in that its "type refinement" is a `NumericInterval` / presence / relational fact (the divisor-safe `Y != 0` hole, a half-line bound), not a set-theoretic type — because Precept's totality obligations are interval/predicate-shaped, not type-membership-shaped; and Precept threads the facts in a single non-iterated pass (no fixpoint), licensed by §0.4.1 (no loops) and §0.4.3 (no reconverging flow), where Typed Racket's general setting needs the full propositional logic.

**TypeScript — control-flow narrowing** (TypeScript Handbook § Narrowing, microsoft.github.io/TypeScript/docs/handbook/2/narrowing.html, accessed 2026-06-07):

> "TypeScript follows possible paths of execution that our programs can take to analyze the most specific possible type of a value at a given position. ... `&&` and `||` ... TypeScript takes advantage of short-circuiting here. In the right operand of a `&&`, the left operand is known to be truthy."

This is the exact rule Precept adopts (the right operand of `and` is reasoned under the left's positive facts), and TypeScript states the same soundness basis — the narrowing is licensed by short-circuit. Precept **diverges** only in that TypeScript's narrowing is best-effort (unsound under aliasing/closures it cannot track), whereas Precept's purity (§0.4.6, no aliasing, no closures, no mutation inside an expression) makes the intra-expression narrowing *complete* for the cases it covers — there is no escape hatch by which a narrowed fact can be falsified at the site.

**Flow** (Facebook) and **refinement / liquid types** (Rondon/Kawaguchi/Jhala, "Liquid Types", PLDI 2008) corroborate the same shape: a path condition refines a base type into `{v : τ | predicate}`, and the refinement is sound because the branch gating the refined expression's evaluation guarantees the predicate. Precept's `Y != 0`-narrows-the-divisor is a degenerate liquid refinement `{v : integer | v ≠ 0}` on the divisor's value environment.

### Precept-specific application

- **§0.4.2 (No control-flow branches, :162)** — touched and *relied upon*. The spec already commits if/then/else to "both branches type-checked, exactly one is evaluated." This design (a) makes the same single-evaluation commitment explicit for `and`/`or` via the desugaring `A and B ≡ if A then B else false` / `A or B ≡ if A then true else B`, and (b) exploits the single-evaluation guarantee for narrowing. No conflict: short-circuit produces a single value with no reconverging flow (consistent with §0.4.3).
- **§0.4.6 (Expression purity, :170)** — the linchpin. Because expressions cannot mutate state or observe anything outside their evaluation context, the boolean *result* of `A and B` is identical eager-or-lazy; short-circuit's only effect is fault-reachability. This is what makes short-circuit safe to commit and makes the narrowing sound.
- **§2.1 / §3.6** — `and`/`or`/`not` precedence and `boolean,boolean → boolean` typing are unchanged; this adds no operator and no precedence change. The `boolean→boolean` typing is the grounding for the strict-boolean BRANCH_FALSE decision.

## Audience and Teachability

**Worked example** (financial domain — a per-unit cost rule on a bill-of-materials line):

```precept
field TotalCost as money
field UnitCount as integer

# A line's unit cost is only meaningful when there are units; the rule
# asserts the per-unit cost stays within an acceptable band — but only
# where UnitCount is nonzero, expressed inline rather than hoisted to a guard.
rule UnitCount != 0 and TotalCost / UnitCount <= 1000.00
  because "per-unit cost may not exceed the ceiling once units exist"
```

Today this rejects with PRE0083 ("Division is unsafe: `UnitCount` can be zero") even though `TotalCost / UnitCount` is evaluated *only* when `UnitCount != 0` is true (short-circuit). After this design, the divisor obligation discharges from the dominating `UnitCount != 0` conjunct, and the rule compiles clean. The author writes the condition where it reads naturally — next to the division — instead of being forced to restructure into `rule TotalCost / UnitCount <= 1000.00 when UnitCount != 0`.

**Error message** (the misuse: author puts the safety condition on the WRONG side of `or`, or after the division):

```
PRE0083  Division is unsafe: 'UnitCount' can be zero while evaluating rule at index 0
         The condition 'UnitCount != 0' does not guard this division. In
         'A or B', the right side runs only when A is FALSE — so 'UnitCount != 0
         or TotalCost / UnitCount <= 1000.00' evaluates the division exactly when
         UnitCount IS zero. Put the safety condition on the left of 'and'
         (it then guards the right), or move it to a 'when' guard.
```

The wording serves the domain expert by naming the *evaluation-order* reason in business terms ("the right side runs only when A is false") rather than compiler-internal vocabulary (no "narrowing," "obligation," or "discharge"), and points at the concrete fix.

**10-minute teaching path** (≤10 min for a competent domain author):
1. `samples/` — any sample using a `when` guard on a rule (e.g. a transition row with `when X is set`) — 3 min, to see the existing cross-clause form.
2. `docs/language/precept-language-spec.md` § 2.1 (precedence table) + the new short-circuit paragraph — 3 min, to learn that `and`/`or`/`if` short-circuit left-to-right.
3. The worked example above (the spec's conditional-totality note) — 4 min, to see the inline form and the or-side pitfall.

## Semantic Rules

This design adds (a) the short-circuit reduction rules for the boolean connectives and conditional, and (b) the path-sensitive narrowing rules over the proof obligations those sub-expressions carry. It adds no new proof *obligation kind* and no new expression form.

### Short-circuit reduction rules (spec semantics — intent-recovery)

Notation: `⇓` = "evaluates to". Evaluation is left-to-right (matching §2.1 precedence: `or` 10 left, `and` 20 left, `not` 25 prefix).

```
A and B :  evaluate A.  if A ⇓ false → result false, B NOT evaluated.
                        if A ⇓ true  → result is the value of B.        (B evaluated ⟺ A true)
A or  B :  evaluate A.  if A ⇓ true  → result true,  B NOT evaluated.
                        if A ⇓ false → result is the value of B.        (B evaluated ⟺ A false)
not A   :  evaluate A; result is its boolean negation.                  (unary — no short-circuit)
if C then T else E :  evaluate C.  if C ⇓ true → result T, E NOT evaluated.
                                   if C ⇓ false → result E, T NOT evaluated.
                                                  (the §0.4.2:162 "exactly one is evaluated" rule)
```

**Desugaring anchor** (the leg that makes short-circuit a *consequence* of already-locked semantics, not a new rule): `A and B ≡ if A then B else false` and `A or B ≡ if A then true else B`. Since §0.4.2 already commits `if/then/else` to evaluating exactly one branch, short-circuit `and`/`or` is the derived consequence of that locked rule applied to the desugaring.

**Result-invariance under purity** (why short-circuit is safe to commit and is purely about fault-reachability): because expressions are pure (§0.4.6:170), the boolean *result* of `A and B` is identical whether `B` is eagerly or lazily evaluated. Short-circuit changes nothing about the value — it changes only whether a fault-prone sub-expression in `B` (a division, sqrt, overflow-prone op) is *reached*. So short-circuit's sole semantic content is the fault-reachability contract that licenses the narrowing below.

### Path-sensitive narrowing rules (proof engine)

A narrowing environment Γ maps fields/args to facts (a `NumericInterval`, plus presence and field-to-field relational facts — the same shape `BuildNarrowedIntervals` already produces and the discharge readers already consume). Γ starts as the enclosing `when` guard's conjuncts (or ∅ for unguarded rules/ensures/computed fields/defaults). The proof engine accumulates Γ top-down along the single root-to-site path during the existing obligation-collection walk. Notation: `facts⁺(C)` = facts a condition establishes when true; `facts⁻(C)` = when false; `⊕` = AND-compose (Intersect); `Γ ⊕ φ` = Γ refined by φ.

**Propagation rules** (which sub-position is reasoned under which refinement — the core, mirroring occurrence typing's then/else split). Each is sound *exactly because* of the corresponding short-circuit rule above:

```
N-AND :  in `A and B`, A is reasoned under bare Γ;  B under Γ ⊕ facts⁺(A).   [B runs only when A true — short-circuit]
N-OR  :  in `A or B`,  A is reasoned under bare Γ;  B under Γ ⊕ facts⁻(A).   [B runs only when A false]
N-IF  :  in `if C then T else E`,
            C is reasoned under bare Γ;                                      [the condition runs unconditionally]
            T under Γ ⊕ facts⁺(C);                                          [replaces today's Γ-shared UNION at Intervals.cs:135-139]
            E under Γ ⊕ facts⁻(C).
N-NOT :  facts⁺(not A) = facts⁻(A);  facts⁻(not A) = facts⁺(A).             [polarity flip — de Morgan over fact sets]
```

**Only the gated position receives the refined Γ (soundness-load-bearing — critic concern 3).** The **left operand** of `and`/`or` and the **condition `C`** of `if/then/else` are reasoned under **bare Γ**, NOT under their own facts — because an obligation inside `A` (or inside `C`) is evaluated *unconditionally*, before the short-circuit decision is even made. Narrowing `A` by `facts⁺(A)` would be circular and could manufacture a false `Proved` for a fault that lives in the left conjunct itself (e.g. a division *inside* `A`). The inseparability principle states the boundary exactly: **only positions whose evaluation is GATED by a condition may assume that condition.** `A`/`C` gate nothing; the right operand / taken branch is gated. A correct `WalkExpression` realizes this naturally (it refines Γ only on the recursion into the gated child — see Architecture Grounding line 206 item 2), but it is pinned here as an invariant the witness checker can re-confirm: a witness whose `AssumedConditions` includes a fact for a non-gated sibling is rejected. Acceptance 10 pins the tripwire — a fault in the LEFT operand (`X/Y > 0 and Y != 0`, divisor on the left) must STILL reject, because the right conjunct `Y != 0` does not gate the left.

**Compound-condition reduction (LOCKED — `facts⁻` is computed by structural de Morgan, NOT by leaf-wise negation through the AND-fold).** This is the soundness-load-bearing rule the red-team flagged; it is pinned here so the implementer has no discretion:

```
facts⁺(C1 and C2) = facts⁺(C1) ⊕ facts⁺(C2)          [conjunction → AND-compose: both facts hold]
facts⁺(C1 or  C2) = facts⁺(C1) ⊔ facts⁺(C2)          [GuardConstraint tier: GENUINE multi-branch set (branch-set concat, the `Or` arm of ExtractGuardBranchesCore :829-833) — discharged by "every branch must prove"; interval-dict tier: per-field OR cross-branch union w/ base back-fill, Intervals.cs:584-606]
facts⁻(C1 and C2) = facts⁻(C1) ⊔ facts⁻(C2)          [de Morgan: ¬(C1∧C2) = ¬C1 ∨ ¬C2  → a DISJUNCTION → forfeit single-field narrowing]
facts⁻(C1 or  C2) = facts⁻(C1) ⊕ facts⁻(C2)          [de Morgan: ¬(C1∨C2) = ¬C1 ∧ ¬C2  → AND-compose]
facts⁺(not A)     = facts⁻(A);   facts⁻(not A) = facts⁺(A)   [polarity flip applied recursively, NOT leaf-only]
```

**The `facts⁻` reducer is NET-NEW machinery, not verbatim reuse (blocker 1 — corrected).** Verified against source: the three existing extractors are **positive-polarity-only**. `ExtractGuardBranchesCore` (`Strategies.cs:823-855`) and `ExtractFieldToFieldBranchesCore` (`Strategies.cs:1182-1213`) have only `And`/`Or`/leaf arms and **no `not`/de-Morgan path**; `ExtractFieldToFieldLeaf` (`Strategies.cs:1240-1248`) has no negation at all; `ExtractGuardLeafConstraints`'s `not` arm (`Strategies.cs:945-967`) negates ONLY `not (single field-op-literal binary)` via `NegateOp`, never a compound `and`/`or` and never `not (presence)`. **There is no existing function that takes a condition and emits its negative-polarity fact set.** The earlier "reuses ExtractGuardBranches/NegateOp verbatim" framing was wrong and is retracted. The reducer must be specified as a new function:

```
// New function — the single trusted polarity leaf shared by prover AND checker (Decision 5).
ReduceFacts(condition : TypedExpression, polarity : Polarity) -> ReducedFactSet
```

**`ReducedFactSet` representation — LOCKED as the existing OR-branch shape (blocker 1 / red-team concern 3).** `ReducedFactSet` is **NOT a flat conjunction**. It is the **existing disjunctive branch shape `ImmutableArray<ImmutableArray<GuardConstraint>>`** (verified: `ExtractGuardBranches`/`ExtractGuardBranchesCore` already return exactly this, `Strategies.cs:794,823` — "a DISJUNCTION of conjunctive branches," documented at `:789-793`), extended with the parallel `ImmutableArray<ImmutableArray<FieldToFieldConstraint>>` for the relational tier (the shape `ExtractFieldToFieldBranches` returns, `Strategies.cs:1174`), **plus a distinguished `FORFEIT` (∅) sentinel** for disjunctive / unrepresentable negative results. Concretely: the outer array is an OR over branches; each inner array is an AND of constraints that all hold in that branch. A *single-conjunction* fact set (the common `Y != 0` case) is the singleton `[[Y≠0]]`; a *genuine disjunction* (`facts⁺(Y>0 or Y<0)`) is the two-branch `[[Y>0],[Y<0]]`; FORFEIT is the empty/no-narrowing sentinel `[[]]` (the "single no-constraints branch" `CombineAndBranches` already treats as pass-through, `:813-815`). Pinning this shape is what makes positive-OR facts (`facts⁺(C1 or C2)`) a genuine multi-branch set the "every OR branch must independently prove" reader (`Strategies.cs:763-784`) can discharge — NOT a flat conjunction that would AND-fold `{Y>0, Y<0}` into one unsatisfiable branch. The compose operators are the existing branch algebra:
- `⊕` (AND-compose) = `CombineAndBranches` cross-product (`Strategies.cs:807-821`) — preserves the per-branch "every branch must independently prove" discipline.
- `⊔` (per-field OR union) = branch-set concatenation `left.AddRange(right)` (the `Or` arm of `ExtractGuardBranchesCore`, `:829-833`) for the GuardConstraint tier; the interval-dict tier additionally uses the per-field cross-branch union with base back-fill (`Intervals.cs:584-606`).
- `FORFEIT` = the singleton no-constraints branch `[[]]`, which narrows nothing.

```
recursion (polarity = Positive):
  C1 and C2  -> ReduceFacts(C1,+) ⊕ ReduceFacts(C2,+)                 [AND-compose: cross-product branches]
  C1 or  C2  -> ReduceFacts(C1,+) ⊔ ReduceFacts(C2,+)                 [GENUINE multi-branch union — NOT a flat
                                                                       conjunction; each disjunct is its own branch,
                                                                       discharged by the "every branch must prove" reader]
  not A      -> ReduceFacts(A, Negative)                              [polarity flip — recurse, do NOT strip-and-stop]
  leaf       -> ExtractGuardLeafConstraints / ExtractFieldToFieldLeaf  (positive, REUSED verbatim — trusted)

recursion (polarity = Negative):
  C1 and C2  -> ReduceFacts(C1,−) ⊔ ReduceFacts(C2,−)  → DISJUNCTION  [de Morgan: ¬(C1∧C2)=¬C1∨¬C2]
                                                                       — see FORFEIT discipline below
  C1 or  C2  -> ReduceFacts(C1,−) ⊕ ReduceFacts(C2,−)                 [de Morgan: ¬(C1∨C2)=¬C1∧¬C2 → AND-compose]
  not A      -> ReduceFacts(A, Positive)                              [polarity flip]
  leaf (field-op-lit)   -> NegateOp(op) leaf (GuardConstraint); InvertOp on literal-op-field   [reuses NegateOp]
  leaf (field-op-field) -> NegateOp(op) leaf (FieldToFieldConstraint)  [NegateOp total over relations]
  leaf (X is set)       -> ∅ FORFEIT   [presence is positive-only — absence is not fact-bearing]
  leaf (X is not set)   -> ∅ FORFEIT   [IsNegated postfix — see presence-tier note; absence not fact-bearing here]
  leaf (F contains K)   -> ∅ FORFEIT   [key-presence positive-only]
```

**FORFEIT discipline for `facts⁻(C1 and C2)` (blocker 1 / red-team blocker 1 — the de-Morgan disjunction).** `facts⁻(C1 and C2) = facts⁻(C1) ⊔ facts⁻(C2)` is a genuine disjunction. The representation *could* carry it as the two-branch set `[branches⁻(C1)] ++ [branches⁻(C2)]` and let the "every branch must independently prove" reader discharge it — and where both disjuncts independently exclude the fault (the positive-OR dual, AC-9b below), that is sound and IS delivered. **But on the relational/numeric *negative* tier the two disjuncts typically constrain *different* fields** (`facts⁻(Y>0) = Y≤0` over `Y`; `facts⁻(W) = ¬W` over some other field), so requiring *every* branch to prove the obligation means the `¬W` branch — which says nothing about the divisor — fails, and the whole set forfeits. To make this **structural and discretion-free** rather than emergent, `ReduceFacts(·, Negative)` on a compound `and` collapses to `FORFEIT (∅)` **whenever the negated disjuncts do not all constrain the obligation's target** — i.e. the de-Morgan disjunction is admitted as a real multi-branch set only when every branch independently narrows (the dual of AC-9b), and forfeits otherwise. This is the load-bearing protection AC-4d/7c pin. Critically, `facts⁻` is **never** AND-folded leaf-wise through `CombineAndBranches` (which would compute the strictly-stronger `facts⁻(C1) ⊕ facts⁻(C2)`, the negation of a *disjunction* — a false-Proved hazard); the de-Morgan recursion produces a disjunction (union) and the FORFEIT collapse is its sound, conservative realization.

**Placement (Decision 3 / O-B).** `ReduceFacts` lives in `ProofEngine.Strategies.cs` alongside the existing extractors, callable from both the prover's `WalkExpression` Γ-refinement (`ProofEngine.cs`) and the soundness-arch checker. The positive leaf arms **do** reuse `ExtractGuardLeafConstraints`/`ExtractFieldToFieldLeaf` verbatim; the negative leaf arms reuse `NegateOp`/`InvertOp`; what is net-new is the **polarity-parameterized recursion** over `and`/`or`/`not` (which the existing `*BranchesCore` functions lack) and the **forfeit-on-disjunction** discipline. Inventory and Decision 3 are corrected to classify the recursion as net-new, not reuse.

The critical point this enforces: `facts⁻` of a **conjunction** is a **disjunction** (`facts⁻(C1) ⊔ facts⁻(C2)`), which forfeits (∅) for the common case where the arms constrain different fields. **`facts⁻` MUST be realized by `ReduceFacts(·, Negative)`'s structural de Morgan recursion, NOT by negating each leaf and AND-folding the results through `EffectiveGuard`/`CombineAndBranches`.** `CombineAndBranches` is an AND-fold (cross-product); feeding it leaf-wise-negated facts of a conjunction would compute `facts⁻(C1) ⊕ facts⁻(C2)` (the negation of a *disjunction*), which is **strictly stronger** than the true `facts⁻(C1 and C2)` and could manufacture a false `Proved` — the exact unsound direction. So `ReduceFacts` returns FORFEIT (∅) for `¬(compound-and)` and `EffectiveGuard` only ever receives an **already-reduced `ReducedFactSet`** (the disjunctive branch shape) — it never sees raw negated leaves of a compound to fold, and it cross-products branch sets (never flat-conjuncts a disjunction). A positive-OR `facts⁺` enters `EffectiveGuard` as a genuine multi-branch set and is discharged by the "every branch must independently prove" reader; a negative-of-conjunction arrives already FORFEIT-collapsed. This is verified-baseline-protected on **both** tiers: (numeric) the probe `(Y > 0 and W) or (X / Y > 0)` rejects today (PRE0083) and MUST stay rejected — `ReduceFacts((Y>0) and W, Negative)` forfeits, so the or-right divisor stays un-narrowed (Acceptance 7c-num); (relational) `(X >= Y and W) or sqrt(X - Y) >= 0` rejects today and MUST stay rejected — `ReduceFacts((X>=Y) and W, Negative)` forfeits despite `NegateOp` being total per-leaf (Acceptance 7c). The relational forfeit is the worst cell because `NegateOp` is total for every comparison and the `Equals→null` accident does NOT protect — the only thing preventing a false Proved is `ReduceFacts`'s forfeit-on-disjunction, not any leaf accident.

**Fact extraction** — what each condition leaf establishes on the `facts⁺` and `facts⁻` polarities. The two polarities feed **two distinct discharge machines with different expressive power** (this asymmetry is load-bearing — critic concern 2):
- the **GuardConstraint-branch readers** (`GuardInPath`, `KeyPresence`, `IndexBounds`) consume facts as `GuardConstraint`s, where a point-exclusion IS representable: `NegateOp(Equals) = NotEquals` (`Strategies.cs:1059`) yields `GuardConstraint(Y, NotEquals, 0)`, and `GuardSubsumes`/`NumericConstraintSubsumes` discharges a divisor obligation from it (`Strategies.cs:993,1003`).
- the **interval-dict reader** (`BuildNarrowedIntervals`/`IntervalOfNarrowed`) consumes facts via `NarrowByConstraint`/`NegateConstraintToInterval`, where a point-exclusion is NOT representable: `NegateConstraintToInterval(Equals) = null` (`Intervals.cs:836` — "X ≠ V isn't representable as a single closed interval") and `NarrowByConstraint(NotEquals) = current` unchanged (`Satisfiability.cs:276`). So on the interval-dict path, `facts⁻` of an equality is a **fail-to-narrow** (sound friction), strictly weaker than the GuardConstraint path.

**Presence and key-presence are positive-only (critic concern 4 / red-team blocker 2).** `facts⁺(X is set)` yields the presence fact; `facts⁻(X is set)` yields **nothing** — no absence fact is tracked. This is verified-sound by the discharge mechanism: the presence arm of `TryGuardInPathProof` (`Strategies.cs:777-781`) discharges a `PresenceProofRequirement` only when it finds a positive `IsPresenceCheck` `GuardConstraint`; a negated/absent presence establishes ABSENCE, which discharges nothing. The existing extractor confirms this is the only representable polarity: `ExtractGuardLeafConstraints` builds a presence `GuardConstraint` only for `TypedPostfixOp post when !post.IsNegated` (`Strategies.cs:935`), and its `not (…)` arm (`:945`) handles only `not (innerBinary)` — it does NOT handle `not (X is set)` (a `TypedPostfixOp` operand). So `not (X is set)` / `X is not set` are **not fact-bearing** for narrowing; "nested not over presence" is a *deliberate fail-to-narrow*, not an unhandled case. **`X is not set` is a DISTINCT AST shape and gets an explicit disposition (red-team nit — enumerate-the-whole-family).** `X is not set` is **not** `not (X is set)`: it is a single `TypedPostfixOp` with `IsNegated == true` (verified: `ExtractGuardLeafConstraints` gates presence on `!post.IsNegated`, `Strategies.cs:935`), whereas `not (X is set)` is a `TypedUnaryOp` wrapping a postfix. The `ReduceFacts` leaf table therefore lists `X is not set` as its own row. Its dispositions: `facts⁺(X is not set) = ∅` (absence is not fact-bearing); `facts⁻(X is not set) = presence(X)` — which is **genuinely SOUND** (in `X is not set or use(X)`, the or-right runs exactly when `X is not set` is FALSE, i.e. when X IS set, so `facts⁻` could supply the presence fact and discharge `use(X)`). **Decision: DEFERRED (forfeit-for-now), not delivered in this pass.** Rationale: delivering it requires a new negative-polarity presence leaf arm (`facts⁻(IsNegated-postfix) = presence`) that the existing positive-only presence machinery does not have, and the author-natural form is the *positive* `X is set and use(X)` (delivered by 6a); the `X is not set or use(X)` double-negative is a rare shape. The cell is **stated, not silent** — the family table carries the row with an explicit DEFERRED disposition rather than over-claiming a complete presence enumeration. **AC-6d** pins the deferred behavior: `(X is not set) or (X + 1 > 0)` **still rejects** today and stays rejecting under this pass (the sound narrowing is not yet delivered), so the table does not over-promise. Consequence for the rules: in N-OR `X is set or f(X)`, the right operand runs under `facts⁻(X is set) = ∅`, so `f(X)`'s presence obligation does NOT discharge — which is the **sound** verdict (the or-right runs exactly when X is absent). Acceptance 6b/6c pin this: `(X is set) or (X+1>0)` and `(not (X is set)) and X+1>0` must STILL reject. Same applies to `F contains K`: `facts⁻(F contains K) = ∅`, so `(F contains K) or use(F[K])` does not narrow and rejects (Acceptance 8b).

**Soundness direction** of every rule: each fact can only TIGHTEN the sub-position's interval (Intersect), never widen — so narrowing can only make MORE obligations discharge, never manufacture a rejection; and an empty Intersect is treated as ⊥/unprovable (never `Contains(⊥) ⇒ true`), matching the existing contradiction guards at `Intervals.cs:509` and `:651`.

### Proof-obligation interaction

No new `ProofRequirement` kind and no new `ProofStrategy` member. The obligation at a fault site inside `A and B` / a branch of `if` is the *same* obligation emission already produces (verified: probe (a)/(b) emit the divisor `NumericProofRequirement` today). The change is that the obligation now carries an **`AssumedConditions`** provenance — the conjunction of dominating short-circuit conditions on the path to its site — and the discharge readers consult `context-guard ⊕ AssumedConditions` rather than the context guard alone. The discharge is still credited `GuardInPath` (numeric/presence/key) or `FlowNarrowing` (relational); the cross-clause `when Y != 0` case becomes the special case where `AssumedConditions = ∅` and the context guard is the whole `when` clause. ### Soundness-preservation claim

- **Principle 7 (compile-time-first) & 11 (static completeness)** continue to hold and are strengthened: the narrowing only ADDS discharges (Intersect can only tighten), so no program that should be rejected becomes accepted, and the previously-rejected-but-provably-total probes become Proved. The single soundness *condition* is short-circuit: narrowing the divisor in `A and B` by `facts⁺(A)` assumes `facts⁺(A)` holds at B's evaluation point, which is true IFF B is evaluated only when A is true — exactly the short-circuit contract. **If the evaluator did NOT short-circuit (eager B), B could run with A false, the divisor could be zero, and the compiler's "Proved safe" would be a false Proved — the broken-guarantee direction.** Therefore compiler-narrowing and evaluator-short-circuit are ONE invariant; a divergence is a P11 break, guarded by the differential test (Acceptance Criteria) and, until the evaluator ships, an interim static builder-structural assertion.
- **Principle 10 (static semantic checking)** holds: re-verification can only over-reject (`spec §0.6 #1`), never introduce a false Proved.
- **Principle 3 (determinism)** holds: single-pass, no solver, no fixpoint (§0.4.1).
- **Single-pass holds for the DISCHARGE phase too, not just Γ-accumulation (blocker 2 — §0.4.1 load-bearing for P3).** The §0.4 "single-pass / no-fixpoint" claim is made for *two* phases and both are bounded:
  1. **Γ-accumulation (the `WalkExpression` down-pass)** is single-pass by construction — Γ threads top-down along the one root-to-site path, refined only on the recursion into the gated child, with no join and no re-visit.
  2. **Discharge (the per-obligation reader calls)** is also a single bounded structural pass, by this **invariant: narrowing adds no obligation-to-obligation dependency.** (a) `EffectiveGuard(obligation)` is a **pure function of the obligation's already-stamped `AssumedConditions`** — no obligation's narrowing reads another obligation's *disposition*, so there is no cross-obligation dependency and hence no fixpoint and no re-queuing (an obligation's disposition never changes another obligation's `AssumedConditions`). (b) `IntervalOfNarrowed`'s per-branch `ReduceFacts` re-derivation recurses over the **finite acyclic expression tree** (§0.4.1 forbids loops → the typed tree is finite and acyclic → the recursion is bounded by tree size), so the discharge walk is **O(tree size) per obligation** with no re-entry that grows the work. There is no obligation whose `AssumedConditions` changes mid-discharge and re-triggers another obligation's narrowing. So the discharge phase, like the accumulation phase, terminates in a single bounded structural pass — grep-checkable against §0.4 ("narrowing adds no obligation-to-obligation dependency; the discharge phase remains a single bounded structural pass"). The per-reader re-extraction (`EffectiveGuard` re-running `ExtractGuardBranches`, `IntervalOfNarrowed` re-running `ReduceFacts` per level) is *redundant work*, not *unbounded work* — it re-derives the same facts from the same finite tree, and project memory records the corpus compiles ~44ms, so this is not a perf concern; the load-bearing point is the *termination/determinism* guarantee, which the no-cross-obligation-dependency invariant secures.
- **Staleness (§0.6 item 7) — two distinct mechanisms, correctly attributed (red-team concern + critic concern 5).** Intra-expression narrowing is sound against staleness for two *separate* reasons depending on which discharge path delivers it, and the prior draft mis-stated the interval-dict half:
  - **Interval-dict path (`IntervalOfNarrowed`/`BuildNarrowedIntervals`) — soundness is PURITY, not a `ReassignedBefore` gate.** Verified: `ProofEngine.Intervals.cs` **never consults `ReassignedBefore`** (the gate lives only in `Strategies.cs` and `QualifierNarrowing.cs`). The earlier claim that the interval-path narrowing "rides the `ReassignedBefore` gate at `Strategies.cs:771,1105-1106`" was wrong — that gate is on the *Strategies* paths, not the interval dict. The correct reason the interval-path **intra-expression** if-narrowing is sound is **§0.4.6 purity**: the if-condition is re-evaluated at the obligation's own evaluation point *within the same pure expression*, so an intra-expression fact cannot be stale relative to its own sub-expression (there is no reassignment between the condition and the gated sub-expression). **Verified by probe:** `set Y = 50` then `set A = (if B <= 10 then B else 0)` does not over-prove A's bound — the conditional is re-evaluated at the assignment, not against a stale fact. **Honest caveat (suspected pre-existing gap, NOT confirmed, out of scope):** the interval-path code (`BuildNarrowedIntervals`/`IntervalOfNarrowed`) does not consult `ReassignedBefore` (verified by grep), so it is *structurally* staleness-blind for **context-guard** facts. The red-team flagged a suspected false-Proved on this path (a `when B <= 10` guard, then a mid-chain `set B = 50`, then `set A = B`). **A direct `precept_compile` probe of that exact shape did NOT reproduce a false-Proved** — the obligation came back `Unresolved` (the assignment-range path appears to source B's interval from declared bounds, not the stale guard) — so this is recorded as a **suspected gap requiring its own investigation, not a confirmed filed BUG.** Whether a constructible shape over-proves on the interval path is left as an out-of-scope follow-up (it shares the machinery this design reuses). **This design's own addition is sound regardless:** it adds only *intra-expression* facts to the interval path, and those are purity-protected (re-evaluated at use within the same pure expression) — so it does not widen any context-guard interval gap whether or not one exists. The GuardConstraint-path half of this design (the divisor/relational discharges) DOES ride the `ReassignedBefore` gate via `EffectiveGuard` (the filter above), where the staleness regression AC-11 lives.
  - **GuardConstraint path (`EffectiveGuard` → `TryGuardInPathProof`/`TryFlowNarrowingProof`) — the `ReassignedBefore` gate DOES apply and MUST cover `AssumedConditions` fields.** When the obligation sits in an action chain and the dominating condition's field was reassigned by an EARLIER action, the assumed fact is stale. `TryFlowNarrowingProof` already gates on `obligation.ReassignedBefore` per the *obligation's own operand fields* (`Strategies.cs:1105-1106`), and `TryGuardInPathProof`/`GuardSubsumes` filters per guard-fact field (`Strategies.cs:771`). **`EffectiveGuard` MUST subject each folded `AssumedConditions` fact to the SAME per-field `ReassignedBefore` drop-filter** that the context-guard branches receive — an assumed `Y != 0` whose `Y` is in `obligation.ReassignedBefore` is dropped before the fold, not AND-folded in. This is **not** "for free": `EffectiveGuard` is the new fold site, so the filter must be applied *there*, per assumed-condition field, against `obligation.ReassignedBefore`. AC-11 tests this **at the `EffectiveGuard` layer** (a `set Y = 0` then an `and`/`if` narrowed by an old `Y != 0` over the same field must still reject), not merely as an inherited behavior.
  - The witness carries the staleness sets so the checker re-applies `StalenessClean` (soundness-arch invariant 1, the five-path family — intra-expression narrowing adds the condition as a new *source* on the existing GuardInPath/FlowNarrowing witnesses, NOT a sixth staleness carrier).

## Architecture Grounding

### Precept-internal placement

**Layer placement.** Three layers, matching the three faces:
- **Spec semantics** — the short-circuit reduction rules live in the language spec (§0.4-adjacent prose + a §2.1 note). No catalog change — the operators already exist in `Operations`; this is semantics text, not a new catalog member.
- **Proof-engine narrowing** — pipeline code, inside the existing obligation-collection + discharge stages. It belongs in pipeline code (it is a *procedure*, the interval/fact walk) and pulls its ground truth from the catalogs (`Operations.GetMeta` for and/or/if classification, the existing fact extractors). No new ProofStrategy enum member, no new ProofRequirement kind — the discharge *mechanic* is unchanged; only the fact's *source* widens from "context guard" to "context guard ⊕ dominating intra-expression conditions."
- **Evaluator opcodes** — the BRANCH_FALSE/BRANCH_TRUE/JUMP lock + lowering contract live in the runtime docs (evaluator.md / precept-builder.md). No opcode is added — they exist since 004eede1; this locks their semantics and fixes notation.

**The engine realization (`AssumedConditions` + `EffectiveGuard`).** This is the load-bearing architecture decision and the reason it reaches *both* failing probes. Verified against source:
- Probe (a) `Y != 0 and X/Y` discharges the divisor's `NumericProofRequirement` through `TryGuardInPathProof` (`ProofEngine.Strategies.cs:713`), which reads the obligation's guard from a **four-arm** switch — `TransitionRowContext` / `StateHookContext` / `EventHandlerContext` / **`ConstraintContext`** (rule/ensure guards, `:728-733`) — NOT through `IntervalOfNarrowed`. So an edit confined to `IntervalOfNarrowed`'s TypedConditional case would fix probe (b) but leave probe (a) unfixed.
- Probe (b)'s divisor interval is computed through `IntervalOfNarrowed`'s TypedConditional case (`ProofEngine.Intervals.cs:135-139`), which today does `thenInterval.Union(elseInterval)` with the SAME `narrowed` dict for both branches — a union, not a condition-narrowed branch.
- `WalkExpression` (`ProofEngine.cs:275-365`) threads `ctx` (ObligationContext) unchanged into every child, including the TypedConditional arm (`:329-332`) and the binary arms (`:308-309`); it never records an assumed condition.

The realization: (1) `ProofObligation` (`ProofLedger.cs:24-32`) gains an `AssumedConditions` field carrying **PRE-REDUCED `ReducedFactSet` values — NOT raw `TypedExpression` conditions (O-B LOCKED — red-team category-a/c).** The field holds the `ReducedFactSet` (the disjunctive `ImmutableArray<ImmutableArray<GuardConstraint>>` / `…FieldToFieldConstraint` branch shape with FORFEIT sentinel) that `ReduceFacts` produced at *stamp time* during the walk — IsDefault-safe like the three existing staleness sets (`:34-82`), empty for every obligation outside an `and`/`or`/`if`. **Why pre-reduced, not raw (the soundness lock):** if `AssumedConditions` carried raw `TypedExpression`s re-extracted at each discharge reader, a `facts⁻` of a compound condition would be re-derived downstream — and the existing positive-only extractors (`ExtractGuardBranchesCore`/`ExtractFieldToFieldBranchesCore`/`ExtractGuardLeafConstraints`'s `not` arm, `Strategies.cs:823,1182,945`) have **no de-Morgan path**: they treat a top-level `not` over a compound as an atomic leaf and silently drop it to empty. That empty is *accidentally* safe for `not(C1 and C2)` (for the wrong reason — extractor blindness, not structural de Morgan) and would mask a real regression if those extractors were ever taught a `not(or)` arm. **Pre-reducing at stamp time guarantees every `facts⁻` flows through `ReduceFacts`'s structural de-Morgan recursion + FORFEIT — never through the positive-only extractors downstream** — so `EffectiveGuard` only ever receives already-reduced positive facts (or a FORFEIT-collapsed negative-of-compound), and is *structurally incapable* of computing a `facts⁻` itself. This causally ties AC-4d/7c (the de-Morgan tripwires) to `ReduceFacts`'s forfeit rather than to extractor blindness. (See Decision 3 / locked O-B; **AC-7e** asserts the fold input is a `ReducedFactSet` with an observable FORFEIT sentinel, so the forfeit is provably the reason 7c passes.) (2) `WalkExpression` threads a Γ parameter alongside `ctx`: at a `TypedBinaryOp` And/Or arm, walk the **left operand under bare Γ** and the **right operand under Γ ⊕ `ReduceFacts(left, Positive)` / `ReduceFacts(left, Negative)`**; at the `TypedConditional` arm, walk the **condition `C` under bare Γ**, **Then under Γ ⊕ `ReduceFacts(C, Positive)`** and **Else under Γ ⊕ `ReduceFacts(C, Negative)`**; each obligation is stamped `AssumedConditions = Γ` (the refined Γ at its site). **(Every facts⁺/facts⁻ on every arm — binary AND the conditional — is `ReduceFacts(·, ±)`, the single trusted leaf; the bare `facts⁺(C)` notation used in the Semantic Rules § propagation block is shorthand for `ReduceFacts(C, +)`, made explicit here so the conditional arm matches the rest of the spec and the checker's per-step re-derivation, which also calls `ReduceFacts`.)** The non-gated positions (left operand, condition) keep bare Γ — only the gated child is refined (soundness-load-bearing; see the propagation rules § "Only the gated position receives the refined Γ"). (3) One **`EffectiveGuard(obligation)`** helper = **`CombineAndBranches`-combine the context-guard branch set with the `AssumedConditions` branch set** (`Strategies.cs:807-821`, the existing event-ensure multi-source fold). **Branch algebra (blocker 1 — corrected from "AND-combine the conjunction of AssumedConditions"):** both operands are `ImmutableArray<ImmutableArray<GuardConstraint>>` branch sets (DISJUNCTIONS of conjunctive branches), and `EffectiveGuard` cross-products them — preserving the "every OR branch must independently prove" discipline the readers already enforce (`:763-784`). A single-conjunction `AssumedConditions` (the common `Y != 0` case) is the singleton branch `[[Y≠0]]` and cross-products into every context branch (sound — the assumed fact genuinely holds in every world reaching the gated site); a **positive-OR** `AssumedConditions` (`facts⁺(Y>0 or Y<0)`, a genuine two-branch set) cross-products as a disjunction, and the result discharges only if every resulting branch independently proves the obligation. The earlier "AND-combine the conjunction of AssumedConditions" phrasing was wrong — it implied a flat conjunction that would AND-fold a positive-OR's disjuncts into one (possibly unsatisfiable) branch; the corrected statement carries `AssumedConditions` as the same disjunctive branch shape the context guard uses. Every guard-reading site calls `EffectiveGuard` instead of reading the context guard directly. **Multi-branch-context × multi-branch-assumed cross-product soundness (red-team category-a).** When the context guard itself is an OR (`when (S == 'a' or S == 'b')`, a two-branch context set) AND `AssumedConditions` is *also* multi-branch (a `facts⁺(C1 or C2)` from a dominating OR'd condition), `CombineAndBranches` cross-products them into `|context| × |assumed|` branches, and the reader requires **every** resulting branch to independently prove. **This is sound because each `(context-branch, assumed-branch)` pair represents a genuinely co-reachable world:** the assumed facts are *dominating short-circuit facts* — they hold on the path to the gated site regardless of which context branch is taken — so a `facts⁺(C1 or C2)` disjunct co-holds with *every* context disjunct (the short-circuit condition `C1 or C2` was true on the path, independent of which `S==…` context branch selected the rule). The cross-product therefore does not manufacture an impossible world: every pair is a world where (some context disjunct holds) AND (some assumed disjunct holds), and both are independently reachable. The "every branch must prove" discipline then correctly requires the obligation to discharge in *all* such worlds — it cannot be satisfied by the wrong branch, because a branch that fails to narrow the obligation (e.g. an assumed disjunct that does not exclude 0) fails the whole set. **AC-9d** exercises this: an OR context guard AND an intra-expression `and` carrying a `facts⁺(or)` assumed fact, asserting the disposition matches a hand-checked truth table (not asserted by reuse-analogy alone). **Staleness filter (critic concern 5):** before folding, `EffectiveGuard` drops any `AssumedConditions` fact whose field is in `obligation.ReassignedBefore` — the same per-field drop the context-guard branches receive (`Strategies.cs:771,1105-1106`). This is applied at the `EffectiveGuard` fold site (it is the new source-combination point), not inherited; AC-11 tests it here. **Bound on `EffectiveGuard`'s fold (soundness — blocker 1):** the AND-fold is correct ONLY for `facts⁺` of conjunctions and for the *positive* dominating conditions accumulated along the gated path (which genuinely all hold). It must **never** be used to materialize `facts⁻` of a *compound* condition by leaf-wise negation: `facts⁻(C1 and C2)` is the disjunction `facts⁻(C1) ⊔ facts⁻(C2)` (de Morgan), and folding leaf-negations through `CombineAndBranches` would compute the strictly-stronger `facts⁻(C1) ⊕ facts⁻(C2)` (a false-Proved hazard). So **`facts⁻` is computed by the net-new `ReduceFacts(condition, Negative)` function** (Semantic Rules § compound-condition reduction — the polarity-parameterized de-Morgan reducer; this is the machinery that does NOT exist in the current positive-only extractors) *before* it ever reaches `EffectiveGuard` — `EffectiveGuard` receives an already-reduced fact set (a disjunctive facts⁻ of a compound arrives **already forfeited to ∅** out of `ReduceFacts`), never raw leaves to AND-fold. `ReduceFacts` is the single trusted polarity leaf shared by the prover here and the checker (Decision 5); `EffectiveGuard` is downstream of it and only ever AND-folds the positive context-guard ⊕ positive `AssumedConditions`. (4) `IntervalOfNarrowed`'s TypedConditional case additionally refines its per-branch dict by facts⁺(C)/facts⁻(C) before recursing (closing probe (b) at the interval site) — where `facts⁻(C)` on the interval-dict path uses `NegateConstraintToInterval`, so an `Equals`-negation is null (the else-branch divisor of `if Y == 0 then K else X/Y` does NOT narrow through the interval dict; it discharges, if at all, via the GuardConstraint path through `EffectiveGuard` — see Decision 4 and Acceptance 4c). Cross-clause narrowing is now literally the `AssumedConditions = ∅` special case.

### External architectural precedent

**TypeScript control-flow analysis** (TypeScript Handbook § Narrowing, microsoft.github.io/TypeScript, accessed 2026-06-07):

> "In the right operand of a `&&`, the left operand is known to be truthy. ... TypeScript follows possible paths of execution that our programs can take to analyze the most specific possible type of a value at a given position."

Precept **takes** the architecture of threading a per-position refinement down the expression tree gated by short-circuit semantics — the right operand of `and` analyzed under the left's positive facts, exactly as `EffectiveGuard ⊕ facts⁺(left)`. Precept **diverges** in placement and trust: TypeScript narrows during type-checking and trusts the result (no re-verification), and its narrowing is unsound under aliasing it cannot follow; Precept narrows during proof-obligation discharge, carries a *re-checkable witness* (the soundness-arch checker re-verifies dominance + the named facts), and is complete-not-best-effort for the cases it covers because purity (§0.4.6) admits no aliasing escape. The single-pass / no-fixpoint choice (vs. TypeScript's iterative CFA over loops) is licensed by §0.4.1 (no loops) + §0.4.3 (no reconverging flow), the same divergence the soundness-arch design grounds in §0.4.

## Decisions

### Decision 1: Treat conditional totality as ONE cross-component invariant (compiler-narrowing ⟺ evaluator-short-circuit), not two independently-shipped features

**Stakes**: high

- **Rationale**: Under expression purity (§0.4.6) short-circuit is result-invariant — its only content is fault-reachability — and the narrowing's soundness is conditioned exactly on short-circuit. Binding them as one invariant makes a divergence a *detectable* guarantee break (differential test) rather than a silent hollow-Proved.
- **Tradeoff accepted**: a consistency invariant + differential test must be maintained across the compiler and evaluator; the two halves can no longer evolve independently.
- **Pre-executor enforcement gap (red-team blocker 3 — corrected: option (b) is UNAVAILABLE today, not "partly blocked").** The mechanical enforcement of the invariant (the AC-14 differential test) is **blocked on the evaluator stub**. **Verified against source:** there is **no `ExecutionPlan`, no plan/opcode builder, and no opcode emission anywhere in `src/Precept`** (`grep -rl ExecutionPlan src/Precept/**/*.cs` returns ZERO hits; `Runtime/Evaluator.cs` is a 161-line stub throwing `NotImplementedException` at every entry; the opcode/lowering layer is **doc-only**, evaluator.md / precept-builder.md describe an unbuilt design). Consequences, stated honestly:
  - **Option (b) — a CFG-dominance structural assertion on the emitted plan — cannot run AT ALL today.** There is no plan to run dominance over. It is **not** "partly blocked"; it is fully unavailable until the builder/plan layer lands. So **option (a) is the mandatory interim posture**, not a choice between (a) and (b).
  - A mere "the builder emits a BRANCH_FALSE/BRANCH_TRUE opcode for every `and`/`or`" assertion would not close the divergence anyway — it checks opcode *presence*, not that the opcode skips the operand whose fault-site the narrowing assumed. (Decision 6 now LOCKS the `if/then/else` lowering — `[eval C][BRANCH_FALSE L_else]…` — so the `if` arm narrowing of Decision 4 has a named evaluator counterpart; the earlier gap where evaluator.md left the `if` opcodes unlocked is closed there, and the option-(b) dominance check keys to that locked contract.) But the opcode-presence point is moot for the interim: no opcode emission exists to assert against either.
  - **(a) Gate the author-visible narrowing behind the executor landing (MANDATORY interim).** The `and`/`or` *and* `if/then/else` narrowing (Decision 4) lands and is **unit-tested at the proof-engine disposition level** (the obligation flips to Proved in `ProofEngine` unit tests — AC 1–12 + the `ReduceFacts` unit tests are disposition-level and DO ship now; AC-13/13b are witness-CHECKER tests gated on the soundness-arch `ProofChecker`/`ProofWitness` DU, which does not exist yet), but **no author-facing program flips from reject to accept** until the differential test (AC-14) exists. No author can depend on a narrowed form compiling before the invariant is mechanically enforceable.
  - **(b) becomes available later** — when the builder/plan layer lands, the CFG-dominance structural assertion (for `A and B`, B's fault-site opcodes dominated by `BRANCH_FALSE(A)`; for `if C then T else E`, T unreachable when C false) becomes the interim guard between "plan exists" and "evaluator differential test exists," at which point the author-visible flip may ship. The plan sequences (a)→(b)→AC-14 differential as the executor matures.
  - **The witness checker cannot detect a compiler/evaluator divergence in this window.** The Decision-5 dominance re-walk confirms the *compiler half* is internally consistent (the narrowing's assumed condition really does dominate the site) and then **trusts** short-circuit — there is no evaluator to disagree with. So for the entire pre-executor window the central invariant has no *enforcing* check except the option-(a) gate (which withholds the author-visible flip precisely so nothing depends on the unverified premise).
  Until the executor lands, the narrowing's author-visible benefit is shipping on an **unverifiable premise**, which is why option (a) withholds it — stated explicitly here, in the Goal, in Acceptance 1/2/14, and in Falsifier 1.
- **Alternatives considered**: (a) Ship narrowing alone, assume the evaluator short-circuits, with only an opcode-presence assertion — rejected: leaves the soundness premise unstated and unguarded; an opcode-presence check passes a wrong-operand BRANCH lowering or an eager-`if` lowering, so every if-branch narrowing (Decision 4) is hollow-Proved through the entire pre-executor window. (b) Ship short-circuit alone — rejected: vacuous, the compiler already rejects exactly the programs where short-circuit would matter (verified: PRE0083 on both probe (a) and probe (b)).
- **Precedent**: occurrence typing couples the type narrowing to the language's actual control-flow / short-circuit semantics — the narrowing is unsound under eager evaluation (Tobin-Hochstadt & Felleisen, POPL 2008; TypeScript Handbook § Narrowing). The soundness-arch design's own "the engine may be arbitrarily buggy; soundness rests only on the checker" framing (`soundness-arch:104-114`) is the same discipline applied to the proof side.
- **Sources consulted for this decision**: `docs/language/precept-language-spec.md § 0.4.6:170` — "Expressions cannot mutate entity state, trigger side effects, or observe anything outside their evaluation context"; behavioral probes (precept_compile 2026-06-07) — probe (a) `Y!=0 and X/Y>0` → PRE0083 Unresolved, probe (b) `(if Y!=0 then X/Y else 1)>0` → PRE0083 Unresolved (the "vacuous if shipped alone" evidence); TypeScript Handbook § Narrowing — "In the right operand of a `&&`, the left operand is known to be truthy."
- **Strongest counter-evidence**: TypeScript narrows *without* a re-checkable invariant tying it to evaluation and ships successfully — arguing the binding is over-engineering. Response: TypeScript is best-effort/unsound-by-design (it accepts narrowing holes under aliasing); Precept's P11 makes a single false Proved a guarantee break, so the binding is exactly what distinguishes a prevention engine from a best-effort checker.
- **Reversibility**: Hard — once the spec states short-circuit and authors rely on a narrowed form compiling, eager evaluation cannot be reintroduced without breaking those programs.
- **Blast radius**: spec (§0.4/§2.1), proof engine (Strategies/Intervals/cs), evaluator.md + precept-builder.md, the soundness-arch witness DU; no author-facing diagnostic code change; no sample changes required (samples that hoist conditions into `when` still compile).

### Decision 2: Frame the short-circuit half as intent-recovery via the desugaring `A and B ≡ if A then B else false`, anchored on the already-locked §0.4.2

**Stakes**: high (authors will depend on the evaluation order once narrowing lets the inline form compile)

- **Rationale**: §0.4.2:162 already commits `if/then/else` to "exactly one is evaluated" (verbatim, verified — the prose says "*evaluated*," not "type-checked"); adopting the standard `A and B ≡ if A then B else false` desugaring is therefore **consistent with** the locked conditional semantics and is shown to be the **original implementation intent** by commit 004eede1 (the BRANCH_FALSE/BRANCH_TRUE opcodes already exist from it). **Honest scope of the claim (framing nit, red-team):** §0.4.2 governs the conditional *expression*; the spec is **silent** on `and`/`or` operator evaluation order (verified: zero `&&` usages, no and/or evaluation-order statement — silent, not contradictory). So this is *not* a zero-novelty recovery of an already-stated rule — it is **adopting a desugaring that §0.4.2 makes consistent and 004eede1 shows was intended**, which is a genuine (if low-novelty) evaluation-order **lock**. Because authors will depend on the order once narrowing lets the inline form compile (see Reversibility), this carries the deliberation weight of an irreversible semantic commitment — **surfaced to the owner as such**, not riding in as a pure notation/intent cleanup. The framing keeps deliberation weight concentrated on the genuinely-novel narrowing while being honest that the operator-order commitment is new.
- **Tradeoff accepted**: stating short-circuit as recovery forecloses re-litigating whether eager `and`/`or` might be preferable — that door is treated as closed by 004eede1 + §0.4.2; if the owner wanted eager, that is a separate conversation this design forecloses by recording the existing intent.
- **Alternatives considered**: Declare short-circuit as a fresh, independent semantic rule requiring full owner-conversation gate — rejected: overstates novelty (the opcodes predate the rename; §0.4.2 already commits if/then/else) and misses the clean derivation. Treat eager and/or as the default — rejected: makes the narrowing unsound AND contradicts the shipped opcodes.
- **Precedent**: commit 004eede1 (evaluator.md:720-721) wrote BRANCH_FALSE/BRANCH_TRUE "Short-circuit for `&&`/`||`"; §0.4.2:162; the standard and/or-as-if desugaring (Typed Racket, every short-circuiting language — C, Java, Python, SQL `AND`/`OR`).
- **Sources consulted for this decision**: `git show 004eede1:docs/runtime/evaluator.md` lines 720-722 (verified verbatim) — "| `BRANCH_FALSE(offset)` | pop 1 | Short-circuit for `&&` |", "| `BRANCH_TRUE(offset)` | pop 1 | Short-circuit for `||` |", "| `JUMP(offset)` | — | Unconditional (for `?:`) |" — all three short-circuit/conditional opcodes predate the `&&`→`and` rename, confirming short-circuit `and`/`or`/`if` was the original intent; `docs/language/precept-language-spec.md § 0.4.2:162` — "both branches are type-checked, exactly one is evaluated"; grep of spec for `&&` — zero hits (silent, not contradictory). **Spec-first-against-HEAD discipline:** the operator-order lock must be recorded in the spec on committed HEAD at promote time (not left implicit), so a later spec-first check finds it on canon rather than re-deriving from a working-tree edit.
- **Strongest counter-evidence**: the soundness-arch design's framing that "exactly one is evaluated" is stated for *type-checking* could be read as a type-checking-only note, not an evaluation-order guarantee. Response: the §0.4.2 prose explicitly says "exactly one is *evaluated*" (not "type-checked"), and the whole §0.4 section is titled execution-model *properties*, so it is an evaluation-semantics commitment; the desugaring derives and/or from it faithfully (the two forms type and evaluate identically under §3.6 boolean→boolean typing).
- **Reversibility**: Effectively-irreversible-post-ship — once authors rely on short-circuit (a narrowed inline form compiling), the evaluation order is locked.
- **Blast radius**: spec §0.4/§2.1, evaluator.md, precept-builder.md; no catalog change (operators exist); no sample changes.

### Decision 4: Replace the if/then/else Γ-shared UNION with per-branch-narrowed branch intervals (Then under facts⁺(C), Else under facts⁻(C))

**Stakes**: medium

- **Rationale**: the minimal local edit that fixes probe (b): today `IntervalOfNarrowed`'s TypedConditional case (`Intervals.cs:137-139`) computes `thenInterval.Union(elseInterval)` with the SAME `narrowed` dict for both branches, so the divisor `X/Y` in the then-branch is evaluated under un-narrowed Γ (Y can be 0). Refining the then-branch by facts⁺(C) makes `Y != 0` hold exactly where `X/Y` is evaluated, matching §0.4.2's "exactly one branch evaluated." The union of the two narrowed branch results stays — it is the correct join for the conditional's *result* interval.
- **Then-branch facts⁺ of a `!=` is also a dict fail-to-narrow — probe (b) routes through the GuardConstraint path, not the dict (critic concern 4).** The headline probe (b)'s then-branch condition is `Y != 0`. On the interval-dict path `facts⁺(Y != 0)` is the divisor-safe 0-hole `(−∞,0)∪(0,+∞)`, which is **not a single `NumericInterval`** — `NarrowByConstraint(NotEquals)` returns the current interval unchanged (`Satisfiability.cs:276`, cited in the facts-table). So the dict refinement (the edit this Decision centers on) does **not** by itself close probe (b)'s then-branch divisor for the `!=` case. The divisor instead discharges via the **GuardConstraint path**: `EffectiveGuard` carries `AssumedConditions = {Y != 0}` (`GuardConstraint(Y, NotEquals, 0)`) into `TryGuardInPathProof`/`GuardSubsumes` (`Strategies.cs:993,1003`), exactly like 4b/4c. The dict edit IS still necessary for the *representable* facts — half-line then-branches (`if Y > 0 then X/Y …`) DO narrow through the dict — but for `!=` the GuardConstraint route is the one that delivers. AC2 pins the credited strategy as GuardInPath so this is verified, not assumed.
- **Else-branch facts⁻ boundary (interval-dict vs GuardConstraint asymmetry — critic concern 2).** The else-branch dict refinement uses `NegateConstraintToInterval`, so `facts⁻(C)` of an **equality** is null (`NegateConstraintToInterval(Equals)=null`, `Intervals.cs:836`) — a sound fail-to-narrow on the interval-dict path. For `if Y == 0 then K else X/Y`, the else-branch divisor therefore does NOT narrow through the interval dict; it discharges (if at all) via the **GuardConstraint path** — `EffectiveGuard` carries `AssumedConditions = {Y != 0}` (the `NegateOp(Equals)=NotEquals` GuardConstraint) into `TryGuardInPathProof`/`GuardSubsumes`. Acceptance 4c pins which outcome occurs (Proved-via-GuardInPath if the else-branch GuardConstraint routes; documented Unresolved fail-to-narrow if only the dict refines). The half-line `facts⁻` (e.g. `facts⁻(Y > 0) = Y <= 0`) IS representable on the interval-dict path and narrows there normally; only the equality-negation point-exclusion is the dict's blind spot.
- **Tradeoff accepted**: the conditional's result interval is now branch-sensitive (tighter); a buggy fact-extraction could under-narrow (false Unresolved = friction) — acceptable per the soundness/completeness asymmetry, and caught by the witness checker if it ever over-narrows. A fault-prone op *consuming* the conditional's result is narrowed only by the (now tighter) union, not by C — correct, since the consumer runs regardless of C.
- **Conditional-as-divisor consumer — worked case with its actual fail-to-narrow consequence (critic concern 4).** The "narrowed only by the union" claim is sound but is NOT a discharge optimism — for the natural shape `Z / (if Y != 0 then Y else 1)` it leaves the consumer Unresolved, and the doc must show that rather than imply the conditional-divisor discharges. Trace: the then-branch is narrowed by `facts⁺(Y != 0)`, but on the interval-dict path `facts⁺(Y != 0)` is the 0-hole `(−∞,0)∪(0,∞)` which is **not a single `NumericInterval`** (`NarrowByConstraint(NotEquals) = current unchanged`, `Satisfiability.cs:276`) — so the then-branch dict **fails to narrow** and the then-interval stays the field's full declared range (which includes 0). The else-branch is the literal `{1}`. The **result union** is therefore `fullRange ∪ {1}` ⊇ `{0}` — it still includes 0. So the consumer divisor `Z / (…)` sees a divisor interval containing 0 and stays **Unresolved** (sound fail-to-narrow). The discharge that *would* work — knowing the conditional's result is never 0 — requires recognizing the result-level 0-exclusion, which the interval-dict union cannot express (it is the same point-exclusion-not-representable limit as the `!=` then-branch). **Expected disposition: Unresolved (documented fail-to-narrow), NOT Proved** — the consumer is *not* author-visible-deliverable in this design's interval-dict scope; only an obligation *inside* the then-branch (reasoned under the GuardConstraint route, e.g. `(if Y != 0 then X / Y else 1) > 0`, probe b) discharges, because the inside-branch divisor routes through `EffectiveGuard`/`GuardSubsumes` where the 0-hole IS representable as `GuardConstraint(Y, NotEquals, 0)`. This asymmetry (inside-branch divisor discharges via GuardConstraint; whole-conditional-as-divisor does not discharge via the interval union) is the concrete consequence of the GuardConstraint-vs-interval-dict expressive-power split. (No AC flip is claimed for the consumer shape; AC-4c pins the *inside-branch* else-divisor, which is the deliverable case.)
- **Alternatives considered**: Keep the result union un-narrowed and narrow only obligations inside branches via `AssumedConditions` — rejected: probe (b)'s divisor *interval* is computed through the dict TypedConditional case, so the dict must narrow per-branch or the interval-containment reader still sees Y∈[full]. Lower if/then/else to nested and/or before narrowing — rejected: `TypedConditional` is a distinct AST node the type checker already produces; the else-branch needs facts⁻(C), which a naive and/or desugar of a non-boolean-result conditional does not express.
- **Precedent**: occurrence typing's then/else environment split (Typed Racket, POPL 2008 § 3); the existing OR cross-branch union with base-interval back-fill (`Intervals.cs:584-606`).
- **Sources consulted for this decision**: `ProofEngine.Intervals.cs:135-139` — `var thenInterval = IntervalOfNarrowed(cond.ThenBranch, …, narrowed); var elseInterval = IntervalOfNarrowed(cond.ElseBranch, …, narrowed); return thenInterval.Union(elseInterval);` (same `narrowed` for both); `Intervals.cs:509,651` — the empty-Intersect-is-⊥ guards the per-branch narrowing must preserve.
- **Strongest counter-evidence**: N/A required (medium). Briefly: a result-interval that is *too* tight could under-discharge a downstream consumer — but tighter can only fail to discharge (friction), never over-discharge (the monotone direction), so it is sound.

### Decision 5: Carry the assumed-condition + dominance + short-circuit-justification on the existing GuardInPath/FlowNarrowing witnesses, reusing the shared StalenessClean family; route narrowing-derived intervals through the soundness-arch O-1 demote-to-Unresolved fallback

**Stakes**: high

- **Rationale**: a narrowing-derived Proved must be re-verifiable by the trusted checker (`soundness-arch:104-114`); the dominating-condition assumption + its polarity is exactly what the checker needs to re-confirm the narrowing was licensed by short-circuit. The staleness carrier is already mandatory on this witness family (invariant 1, five paths). And by routing narrowing-derived intervals through the soundness-arch O-1/invariant-3 bare-bounds demote-fallback, an intra-expression discharge the checker cannot cheaply re-certify becomes Unresolved (friction), never a false Proved — so even a buggy narrowing engine cannot produce a hollow Proved.
- **The dominance witness is concrete and re-checkable WITHOUT O-1 (red-team concern — AC-13 must be meetable when this design ships, not aspirational against an unbuilt checker arm).** The witness's dominance reference is **not** an opaque "a dominance check exists" — it is the **short-circuit path from the expression root to the obligation site, as an ordered sequence of `(node, branch-polarity)` steps** (e.g. `[(and@root, right), (if@inner, then)]` for a divisor inside the then-branch of an `if` that is the right operand of an `and`). The checker re-walks the typed tree along that exact path and confirms, at each step, that (i) the node is an `and`/`or`/`if`, (ii) the recorded polarity matches the gated child (right-of-and / right-of-or / then/else-of-if — never left/condition), and (iii) the `facts⁺`/`facts⁻` the witness stamped for that step are exactly what the step's condition extracts at that polarity. **The checker re-derives those facts by calling the SAME trusted `ReduceFacts(stepCondition, polarity)` function the prover used** (the single shared polarity leaf — net-new, sized into the soundness-arch trusted-base LOC ceiling alongside `ExtractGuardLeafConstraints`/`NegateOp`), **not** by replaying the prover's fact accumulation. This matters specifically for the OR-branch / NOT / else-branch facts: their `facts⁻` comes from `ReduceFacts(·, Negative)`, so the checker's re-derivation of a negative-polarity step depends on the same reducer — which is sound precisely because `ReduceFacts` is a trusted leaf shared by prover and checker, not the prover's own internal state (the Alethe/R2 re-run-the-prover trap the soundness-arch design forbids — invariant 3 / validate-hard). This is a **pure structural re-walk of the typed tree** invoking one trusted pure function per step — it needs no interval-contributor capture, so it **ships WITH this design and is NOT gated on O-1.** O-1 is reserved for the *interval-contributor* capture (the `FlowNarrowingWitness.Contributors` all-inputs requirement); the **dominance/polarity re-walk is a hard precondition of this design** and is what AC-13 exercises. Result: a planted witness that cites a non-gated position (a fact for a left operand), or a polarity mismatch (facts⁺(C) applied to the else-branch), or a condition that does not structurally dominate the site, is rejected by the re-walk independent of O-1.
- **The dominance-path leg attaches to the interval-containment witness too, not only GuardInPath/FlowNarrowing (critic concern — interval-dict contributor re-checkability).** Two discharge routes deliver conditional narrowing, and **both** must carry the re-walkable dominance leg:
  - **GuardConstraint route** (the `!=` then-branch / else-branch cases, the OR-branch `NegateOp` cases — `facts⁺(Y != 0)`, `facts⁻(Y == 0)`): discharge via `EffectiveGuard`→`TryGuardInPathProof`/`TryFlowNarrowingProof`, producing a `GuardInPathWitness`/`FlowNarrowingWitness` — the dominance leg attaches there (above).
  - **Interval-dict route** (the *representable* half-line then-branch cases explicitly called out at Decision 4 — `if Y > 0 then X / Y …`, where `facts⁺(Y > 0)` IS a single `NumericInterval` and DOES narrow through the dict): discharge via `IntervalOfNarrowed`'s per-branch refinement → an **interval-containment witness** (`TryIntervalContainmentProofNarrowed`, `Intervals.cs`), which produces interval-bounds provenance, NOT a GuardInPath/FlowNarrowing one. **Disposition (option (a) — the interval-containment witness ALSO stamps the dominance-path leg):** when `IntervalOfNarrowed`'s `TypedConditional` arm refines a per-branch interval by `ReduceFacts(C, ±)`, it records the same ordered `(node, branch-polarity)` dominance step onto the interval-containment witness's provenance (an additive leg on that witness shape, parallel to the GuardInPath/FlowNarrowing leg — the soundness-arch `ProofWitness` DU gains the leg on the interval-containment member too, not only the two narrowing members). The checker re-walks it **identically** — same structural `(node, polarity)` path re-walk, same `ReduceFacts(stepCondition, polarity)` re-derivation per step, asserting the per-branch interval refinement that licensed the containment was condition-licensed at the recorded polarity. So the representable half-line then-branch cases ARE author-visible-deliverable (subject to the Decision-1 option-(a) executor gate that defers *all* author-visible flips uniformly) and ARE re-checkable WITHOUT O-1, exactly like the GuardConstraint cases. **What rides O-1** is only the *all-contributor* capture (naming the sibling-reject + relational-half-line + base-bound inputs the interval Intersect composed) — the `FlowNarrowingWitness.Contributors` / interval-contributor requirement; the **dominance/polarity leg on every witness route is a hard precondition of this design**, not gated. This closes the gap where the doc previously specified re-checkability only for the GuardConstraint half: both halves carry the dominance leg and both are re-walked by the same checker arm. AC-13 plants its non-gated/polarity-mismatch witness on **both** routes (a GuardConstraint-discharged divisor and an interval-dict-discharged half-line then-branch) so the re-walk is exercised on each.
- **Same-extractor agreement, not byte-identical single-source (blocker 2 / red-team concern 2 — corrected).** The earlier draft claimed "exactly ONE derivation" of the per-branch facts (walk-stamped `AssumedConditions` also fed verbatim into the dict refinement). **Verified that claim is not realizable as stated:** `IntervalOfNarrowed` (`Intervals.cs:22`, signature `(TypedExpression, SemanticIndex, ImmutableDictionary<string,NumericInterval>?)`) runs in the *discharge* phase and recurses **structurally over arbitrary sub-expressions**, including conditionals nested inside other operands (`:135-139`, and via the binary/unary/call arms that re-enter `IntervalOfNarrowed`), where there is **no obligation-level `AssumedConditions` to consult** — so its per-branch refinement is **necessarily a second extraction** from `cond.Condition`. The two-derivation hazard is real and cannot be plumbed away by threading a per-obligation array (nested conditionals have no owning obligation at the dict site). **Resolution — accept two derivations, force them through ONE trusted extractor, and check agreement:**
  1. **Both sites call `ReduceFacts`.** The walk's `TypedConditional` arm computes `facts⁺(C)/facts⁻(C)` via `ReduceFacts(cond.Condition, ±)`; `IntervalOfNarrowed`'s `TypedConditional` arm computes its per-branch dict refinement via the **same** `ReduceFacts(cond.Condition, ±)` call (translated to a `NumericInterval` via `NarrowByConstraint`/`NegateConstraintToInterval`). Because both go through the identical pure trusted function on the identical `cond.Condition` node, they are **equal by construction** for any conditional that has an owning obligation, and well-defined (not a divergence surface) for nested conditionals that do not.
  2. **The checker re-derives, it does not trust the prover's accumulation.** The dominance-re-walk (below) re-runs `ReduceFacts` at each step and confirms the witness-stamped facts equal `ReduceFacts`'s output — so the witness carries facts the checker independently reproduces, never the prover's running accumulation (the Alethe/R2 "re-run the prover" trap the soundness-arch design warns against — invariant 3 / validate-hard).

### Decision 6: Lock the strict-boolean BRANCH semantics AND the `if/then/else` conditional-branch lowering contract — covering BOTH the `and`/`or` opcodes (resolving evaluator.md:993) AND the `if` arm that carries Decision 4's narrowing

**Stakes**: medium (raised from "the two in-scope opcodes" — the `if` lowering is the premise of the highest-risk narrowing, Decision 4)

- **Rationale (strict-boolean)**: `and`/`or` operands are type-checked `boolean,boolean → boolean` (§3.6), and the if-condition is boolean, so a BRANCH opcode's stack value is always a genuine boolean; the "numeric-zero falsy" sub-question of :993 cannot arise on a well-typed plan. Admitting numeric-zero falsiness would (a) contradict the type rule, (b) introduce an evaluator behavior with no compile-time counterpart, and (c) silently break the narrowing ⟺ short-circuit invariant in any future numeric context. Keeps the opcode total and unambiguous.
- **Rationale (`if/then/else` lowering — red-team category-b, the gap Decision 4 depends on)**: Decision 4's **then-branch narrowing** (Then reasoned under `facts⁺(C)`, Else under `facts⁻(C)`) is sound ONLY if the then-branch is **evaluated only when C is true** — i.e. `if C then T else E` lowers to a **conditional branch on C**, not eager evaluation of both arms. Verified against `evaluator.md:993-1008`: the pending-lock note enumerates `BRANCH_FALSE`'s numeric-zero question for `&&`/`||` only; the opcode table ties `BRANCH_FALSE`/`BRANCH_TRUE` to `&&`/`||` and shows `JUMP` only "(for `?:`)" — there is **NO locked conditional-branch opcode named for the `if` arm**, and Decision 1 itself flags "says nothing about if/then/else lowering … leaves the if opcodes unlocked." So Decision 6 **explicitly locks the `if` lowering**: `if C then T else E` lowers to `[eval C][BRANCH_FALSE L_else][eval T][JUMP L_end][L_else: eval E][L_end:]` — `C` is evaluated, `BRANCH_FALSE(C)` jumps to the else-block when C is false (skipping T entirely), `T` is evaluated and `JUMP`s over the else-block, `E` is evaluated only on the false path. The `BRANCH_FALSE` here is the **same strict-boolean opcode** locked above (C is a boolean condition, §0.4.2/§3.6), so the strict-boolean lock covers the `if` condition too; the `JUMP` is the existing unconditional opcode (re-noted as `if/then/else` not `?:` per Decision 7). This gives Decision 4's then-branch narrowing a **locked evaluator counterpart** — the then-block opcodes are dominated by `BRANCH_FALSE(C)` evaluating C true, exactly the dominance the witness records — rather than relying on an unenumerated `if` opcode.
- **Tradeoff accepted**: none material — closes the under-specified `BRANCH_FALSE` numeric-zero question in the only type-consistent direction, and locks the `if` lowering in the only single-evaluation-consistent direction (§0.4.2 "exactly one is evaluated"). (The other three :993 items — LOAD_ARG absent/null, RETURN fall-through, stack pooling — are out of scope and remain pending; the note is narrowed, not deleted.)
- **Alternatives considered**: Truthy/falsy numeric coercion (C-style) — rejected: Precept has no implicit bool coercion (§3.6), it would create an untyped evaluation path the compiler never reasons about, and the type checker already rejects numeric operands to and/or, so it has no author-facing benefit. Eager-`if` lowering (evaluate both T and E, select by C) — rejected: it would make a fault-prone op in the *untaken* branch reachable, breaking §0.4.2's "exactly one is evaluated" AND falsifying Decision 4's then-branch narrowing premise (the then-divisor could run with C false). Leave it pending — rejected: the narrowing's soundness depends on BOTH the BRANCH semantics and the `if` lowering being locked, so neither can stay open if narrowing ships.
- **Precedent**: `docs/language/precept-language-spec.md § 3.6` — `and`/`or`: `boolean | boolean → boolean`; `§0.4.2:162` — "both branches type-checked, exactly one is evaluated" (the locked single-evaluation rule the `if` lowering realizes); the evaluator's "no semantic reasoning, prebuilt plans only" identity (a coercion would be semantic reasoning at execution time); the universal `if`-as-conditional-branch lowering (every bytecode VM — CPython `POP_JUMP_IF_FALSE`, JVM `ifeq`, .NET `brfalse`).
- **Sources consulted for this decision**: `docs/runtime/evaluator.md:993` — "whether `BRANCH_FALSE` treats numeric zero as falsy or only `false`"; `evaluator.md:1006-1008` — the `BRANCH_FALSE`/`BRANCH_TRUE`/`JUMP` opcode rows (no named `if`-conditional-branch opcode — verified); `docs/language/precept-language-spec.md § 3.6` (the `and`/`or` row) — "| `and` `or` | `boolean` | `boolean` | `boolean` | No |"; `§0.4.2:162` — "exactly one is evaluated."

2. **Narrowing widens, not just tightens.** If any fact-extraction or branch-composition rule produces an interval WIDER than the unconditioned one (e.g. a mis-signed facts⁻ on an else-branch, or a leaf-negate-and-AND realization of `facts⁻` of a compound that over-strengthens it to the negation of a disjunction), narrowing could manufacture a false Proved. - **O-B (`AssumedConditions` representation) — DECIDED/LOCKED (red-team category-a/c): pre-reduced `ReducedFactSet`, NOT raw `TypedExpression`.** The obligation carries the **pre-reduced `ReducedFactSet`** that `ReduceFacts` produced at stamp time (the disjunctive branch shape with FORFEIT sentinel), **never** raw dominating `TypedExpression`s re-extracted at discharge. **Rationale:** raw-and-re-extract would route a `facts⁻` of a compound through the existing positive-only extractors (no de-Morgan arm — they drop a top-level `not(compound)` to empty by blindness, accidentally-safe for the wrong reason and a regression hazard if a `not(or)` arm is ever added). Pre-reducing forces every `facts⁻` through `ReduceFacts`'s structural de Morgan + FORFEIT and makes `EffectiveGuard` structurally incapable of computing a `facts⁻` itself — so the relational-tier soundness (AC-7c) is causally tied to `ReduceFacts`'s forfeit, not to extractor blindness. **Alternatives rejected:** raw-`TypedExpression`-re-extracted (the de-Morgan-blindness hazard above); a hybrid (raw for positive, reduced for negative) — rejected as a needless two-representation split that re-opens the question of which path a mixed condition takes. **Tradeoff accepted:** the walk must run `ReduceFacts` eagerly at stamp time (slightly more walk-phase work) rather than lazily at discharge — accepted because it is the only representation that guarantees the de-Morgan path and is bounded single-pass (blocker 2). **Precedent:** the soundness-arch checker's "re-derive via a trusted leaf, never replay the prover" discipline (validate-hard) — pre-reducing is the prover-side analogue (commit the trusted reduction once, carry its output). This is a LOCKED decision, no longer an open fork; the plan implements it. **AC-7e** pins it: a unit test asserts `EffectiveGuard`'s fold input is a `ReducedFactSet` (never a raw negated compound), with the FORFEIT sentinel observable on the `¬(compound-and)` case — so AC-7c passing is provably caused by the forfeit.
