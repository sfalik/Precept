# Compile-Time Niche Evidence — Defect-Class Inventory

> Every way a precept definition can be wrong, classified on: where it lives (Axis 1), when it manifests (Axis 2), who feels it (Axis 3), what reasoning catches it (Axis 4) — plus severity, governance/inspector coverage, universal-reasoning requirement, compile-catchability, and expressiveness cost. Probe-verified claims cite precept_compile results.

## Vantage: VALUE/DATA DEFECTS — wrong about values: bad defaults, contradictory rules/bounds, unit/currency/precision errors, wrong

*(full vantage description: VALUE/DATA DEFECTS — wrong about values: bad defaults, contradictory rules/bounds, unit/currency/precision errors, wrong computed formulas, vacuous or always-true rules, cross-field bound fights, interpolation errors in because-messages. Axis-1 homes 1, 2, 3, 4, 5, 13, 14 (+ one Axis-15 intersection found). Evidence: docs/philosophy.md, spec §0.1/0.4/0.6/0.7/0.8/3A, 16 precept_compile probes, corpus stats over samples/ (77 files, 151 rules, 139 interpolated because-messages, 36 computed fields, 275 business-domain-typed fields, 438 defaults, 46 maxplaces).)*

### Default violates its own declared band or modifier

- **Axes:** where=2 Field constraints & modifiers · when=compile · who=author · reasoning=concrete evaluation (constant fold of default against modifier)
- **Description:** A declared default literal lies outside the field's own min/max/sign/length/places band. Without the check, every Create would be refused.
- **Example:** `field A as integer default -5 nonnegative — caught: PRE0079. Also PRE0067 (maxplaces), PRE0135 (length).`
- **Severity:** medium — Would break every construction, but the failure is total and immediate — discovered the first time anyone creates an instance, never latent.
- **Governance catches:** immediately · **Inspector:** yes-easily · **Needs universal reasoning:** False
- **Compile-catchable:** today — Constant fold of the default against the desugared modifier rule (PRE0079/PRE0067/PRE0135, verified by probe).
- **Expressiveness cost:** None — pure win, already shipped.

### Defaults violate a global rule or initial-state ensure

- **Axes:** where=2 + 5 (defaults x rules/ensures) · when=compile · who=author; end user (every Create refused if unchecked) · reasoning=concrete evaluation (default-environment fold)
- **Description:** The default field configuration provably violates an unguarded rule or initial-state ensure — the entity is born invalid.
- **Example:** `field A as integer default 0; rule A > 10 because "..." — caught: PRE0164 'violated by the default field values (constraint fails when A=0)'. Initial-ensure half is PRE0115.`
- **Severity:** high — Without the check the precept ships and 100% of Creates refuse — a full outage of the entity type, though discovered at first Create, not latent.
- **Governance catches:** immediately · **Inspector:** yes-easily · **Needs universal reasoning:** False
- **Compile-catchable:** today — Shared default environment + constant-fold evaluator (spec §0.6 item 11; PRE0164 verified live by probe — note the §0.6 implementation-status table still says several proof items are 'specification-only'; drifted on this branch).
- **Expressiveness cost:** None.

### Born-invalid values the default-fold does not reach: choice default outside its value set; mincount>0 collection empty at birth

- **Axes:** where=1 + 2 + 3 (choice type, defaults, collection cardinality) · when=Create (construction) · who=author; end user; host developer · reasoning=concrete evaluation / membership check (exists for other positions, not applied here)
- **Description:** PROBED HOLE: field Status as choice of string("draft","active","closed") default "pending" compiles with zero errors (Probe16), while the same membership check fires elsewhere (PRE0086 catches when Status == "Active" in a guard — Probe24). Likewise list of string mincount 1 with no construction population compiles clean and even marks its CountContainment obligation 'Proved' (Probe34) although the collection is empty at birth — either every Create refuses or mincount is silently unenforced at birth; runtime is stubbed so which one is unverifiable, both are defects.
- **Example:** `field Status as choice of string("draft","active") default "pending"  # compiles clean today`
- **Severity:** high — Same outage profile as default-violates-rule (every Create refuses, or worse a silently out-of-vocabulary value persists and flows to downstream consumers). The Probe34 'Proved' disposition is a potential false-proof against Proof philosophy #1.
- **Governance catches:** immediately · **Inspector:** yes-easily · **Needs universal reasoning:** False
- **Compile-catchable:** solver-free-feasible — Trivial extension of existing machinery: apply the PRE0086 membership check at the default position; fold birth-time collection count (0 or default literal count) against mincount in the same default environment PRE0164 uses.
- **Expressiveness cost:** None — pure coverage gap.

### Legal-but-wrong sentinel default (semantically wrong default value)

- **Axes:** where=2 Field constraints & modifiers · when=production after specific input history · who=downstream data consumer; the business; audit/compliance · reasoning=none — requires domain knowledge no reasoning system has
- **Description:** A default that satisfies every declared constraint but is semantically a sentinel masquerading as data: default '0.00 USD' on RequestedAmount (loan-application.precept:19), default 300 on CreditScore (line 21). A report averaging credit scores ingests the 300s as real observations.
- **Example:** `field CreditScore as integer default 300 min 300 max 850 — a never-submitted score is indistinguishable from a real 300.`
- **Severity:** medium — Silent data corruption for consumers, but bounded: the language already has the honest alternative (optional + is set), so this is an authoring-idiom defect, and corpus authors often gate with state ensures (in Funded ensure ApprovedAmount > '0.00 USD').
- **Governance catches:** never · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** False
- **Compile-catchable:** undecidable — Intent is not declared. A heuristic lint ('default equals the band minimum on a non-optional business-domain field') is solver-free-feasible but is exactly the might-be-broken nagging Proof philosophy #2 forbids.
- **Expressiveness cost:** Full prevention would mean banning defaults on business-domain types and forcing optional — real ceremony; not warranted.

### Self-fighting bound pair on one declaration (min>max, minlength>maxlength, mincount>maxcount)

- **Axes:** where=2 + 3 (field and inner-type modifiers) · when=compile · who=author · reasoning=concrete evaluation (literal comparison)
- **Description:** The two ends of a single declared band are inverted, making the field unwritable (or the collection unfillable).
- **Example:** `field A as integer min 100 max 10 — caught: PRE0034 'min (100) cannot exceed max (10)'; mincount 5 maxcount 2 likewise (probes).`
- **Severity:** medium — Every write would refuse — total but immediate failure of that field.
- **Governance catches:** first-fire · **Inspector:** yes-easily · **Needs universal reasoning:** False
- **Compile-catchable:** today — Literal comparison at declaration site (PRE0034, verified for min/max, minlength/maxlength, mincount/maxcount).
- **Expressiveness cost:** None.

### Contradictory rules on one field (unconditional, or under a shared guard)

- **Axes:** where=5 Rules & ensures · when=compile (caught) / first Fire (felt if shipped) · who=author; end user (refusals); the business (stranded process) · reasoning=numeric interval + guard-scope intersection — universal over inputs
- **Description:** Two rules whose ranges are interval-incompatible: no value satisfies both, so every operation touching the field refuses. Probes show both the unconditional case (rule A>10 + rule A<5 → PRE0155) and the shared-guard case (two 'when Tier=="premium"' rules → PRE0155) are caught TODAY — but as WARNINGS: Probe19 returned success:true, so the contradictory definition ships. Overlap analysis across different-but-overlapping guards (when A>5 vs when A>10) is unverified depth.
- **Example:** `rule Limit <= 500 when Tier == "premium"; rule Limit > 600 when Tier == "premium" — PRE0155 warning, compile still succeeds.`
- **Severity:** critical — In production every premium-tier mutation refuses with two mutually-contradicting because-messages — the entity class is stranded in exactly the configurations the rules target, and the refusal text actively misleads (each message names a bound the other rule forbids).
- **Governance catches:** first-fire · **Inspector:** yes-easily · **Needs universal reasoning:** True
- **Compile-catchable:** today — Interval intersection per field per guard scope (PRE0155 live). POLICY FINDING: proven contradiction is warning-severity, so prevention is opt-in; also PRE0154/0155/0159 messages render the raw TypedBinaryOp record ToString — unreadable, violating spec §0.8 readable-diagnostics.
- **Expressiveness cost:** None for the check itself; promoting to error is consistent with 'proven violations only'.

### Cross-field relational contradiction (rules or modifier-expressions fighting across fields)

- **Axes:** where=2 + 5 (cross-field modifier expressions and relational rules) · when=first Fire / Update (constraint-time) — compile only when defaults expose it · who=end user; the business (feature permanently broken) · reasoning=relational (bounded difference-constraint closure) — universal over inputs
- **Description:** PROBED HOLE: field A as integer optional min B + 1 plus field B as integer optional min A + 1 compiles with ZERO diagnostics (Probe33) — once both fields are set, no value pair satisfies both, so every operation that sets both refuses forever. The defaults-fold catches the rule-form variant only when defaults exist to violate it (Probe12 fired PRE0164, not a relational proof). Spec §0.6 item 2's relational pass is deliberately single-pass and depth-bounded; it does not close this cycle.
- **Example:** `field A as integer optional min B + 1
field B as integer optional min A + 1  # compiles clean; unsatisfiable once both set`
- **Severity:** critical — The contradiction is invisible until the first user supplies both values, then is a permanent wall with confusing dual refusals; with optional fields and no defaults there is no compile-time signal at all.
- **Governance catches:** first-fire · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Bounded difference/octagon-style closure over declared relational constraints — deterministic, attributable, and tractable precisely because of §0.4 (no loops, finite fields, closed vocabulary). Spec §0.6 already commits to relational reasoning; this extends it to satisfiability of the constraint SET rather than per-obligation discharge.
- **Expressiveness cost:** None on authors; bounded closure depth keeps compile deterministic and fast (corpus compiles in ~44ms today).

### Vacuous (always-true) rule — silent non-protection

- **Axes:** where=5 Rules & ensures (+2, since modifiers desugar to rules) · when=latent-never · who=author (false confidence); the business; audit/compliance (a control that does not exist) · reasoning=numeric interval implication — universal over inputs; NO runtime or per-scenario reasoning can see it
- **Description:** A rule provably implied by declared constraints governs nothing: the author typed rule A >= 0 on a nonnegative field meaning to type >= 100, or a guard implies the body (rule A > 0 when A > 100). The protection the author believes exists does not. Caught today: PRE0154 (warning), including the guard-implies-body form (Probe9).
- **Example:** `field A as integer nonnegative
rule A >= 0 because "must stay positive"  # governs nothing — PRE0154`
- **Severity:** high — This is the purest universal-only class: governance NEVER fires (the rule never refuses anything), and the inspector is structurally blind — the defect is an ABSENCE of refusal, and per-scenario simulation cannot show that a refusal which should have happened didn't. An auditor reads a control that is dead text.
- **Governance catches:** never · **Inspector:** no · **Needs universal reasoning:** True
- **Compile-catchable:** today — Interval implication against declared constraints (PRE0154 live; warning severity is right here — vacuity is advisory). Same rendering bug as PRE0155.
- **Expressiveness cost:** None.

### Dead guarded rule (guard unsatisfiable under declared bounds)

- **Axes:** where=5 Rules & ensures · when=latent-never · who=author; audit/compliance · reasoning=guard satisfiability vs declared intervals — universal over inputs
- **Description:** The rule's when-guard can never be true given declared bounds, so the rule never applies — sibling of vacuity with the same silent-non-protection character. Caught today: PRE0159 'unsatisfiable under the declared bounds' (Probe28: rule B > 10 when A < 0 with A nonnegative).
- **Example:** `field A as integer nonnegative
rule B > 10 when A < 0 because "..."  # PRE0159 — never applies`
- **Severity:** high — Same as vacuity: governance never fires, inspector cannot show an absence. The declared control is unreachable.
- **Governance catches:** never · **Inspector:** no · **Needs universal reasoning:** True
- **Compile-catchable:** today — Guard interval satisfiability against declared field bounds (PRE0159 live, warning).
- **Expressiveness cost:** None.

### Write provably outside the target's declared band (assignment-range impossibility, all dimensions)

- **Axes:** where=2 + 3 + 13 (bands x writes x arithmetic; element writes included) · when=compile (caught) — otherwise Update/Fire constraint-time · who=author; end user (would see refusals) · reasoning=numeric interval with unit normalization — universal over all inputs reaching the write site
- **Description:** A set/append whose value interval is provably not contained in the target's declared band. Verified live across dimensions: event-arg band wider than field band (Probe13, arg [0..500] into [10..100] → PRE0078 + IntervalContainment witness), unit-normalized magnitude ('6000 g' into max '5 kg' → caught, Probe25), per-element bound (append Scores 50 into max 10 → caught, Probe32), computed expression vs own bound (A+B in [0..200] into max 100 → caught, Probe17), string-length and count bounds per spec §0.6.
- **Example:** `field F as integer min 10 max 100
event Go(N as integer min 0 max 500)
on Go -> set F = Go.N   # PRE0078: [0..500] ⊄ [10..100]`
- **Severity:** high — This is the carries-constraint discipline of §0.7 working: without it these surface as per-input runtime refusals; with it the author is forced to align bands before any entity exists. Universal over every input that will ever reach the site — the inspector can only sample.
- **Governance catches:** first-fire · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** True
- **Compile-catchable:** today — Interval containment obligations with UCUM normalization at extraction (live; structured IntervalContainment witnesses with declared/normalized bounds in the proof model). MESSAGE FINDING: the diagnostic text is wrong for this case — PRE0078 says 'Numeric computation exceeded the representable range' for what is actually band non-containment; the obligation witness is right, the prose misleads.
- **Expressiveness cost:** Real but acceptable: authors must declare matching bounds on sources (event args, source fields) — band ceremony that doubles as documentation. This is the cost §0.7 explicitly accepts.

### Unit / currency / dimension mismatch in arithmetic, assignment, and qualifier chains

- **Axes:** where=1 + 13 + 14 (qualifiers x operators x unit arithmetic) · when=compile · who=the business (silently wrong money otherwise); downstream data consumer · reasoning=type/qualifier checking — universal, type-level
- **Description:** Mixing currencies (USD + EUR), assigning across qualifiers, applying an exchange rate in the wrong direction (money EUR * rate USD→EUR), wrong dimension into a quantity field. All verified caught today: PRE0114 qualifier-combination, PRE0068 qualifier-on-assignment, PRE0069 dimension mismatch, QualifierChain obligation for rate direction (Probes 5, 7, 15, 21). Interpolated qualifier slots ({CurrencyCode}) are consistency-checked per type-checker doc.
- **Example:** `on Go -> set Converted = Amount * Rate  # Amount EUR, Rate USD→EUR: PRE0114 + QualifierChain 'from currency must match money currency'`
- **Severity:** critical — The alternative is the classic silently-wrong-money bug: a EUR amount times a USD rate produces a plausible in-band number that persists and propagates. No runtime governance would refuse it (the result is a 'valid' money value) and the inspector shows a number that looks right — this class is only catchable by universal type-level reasoning, and Precept catches it.
- **Governance catches:** never · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** True
- **Compile-catchable:** today — Catalog-driven qualifier axes resolved by the type checker + proof-engine qualifier-chain obligations (live). Counting-unit conversions (each vs box) are excluded by design — mismatch rejects, conversion requires an explicit field (§0.6 item 5).
- **Expressiveness cost:** Explicit conversion ceremony (a declared rate field and an explicit multiplication) — the honest cost of refusing implicit conversion; modest in corpus practice.

### Precision violation produced by arithmetic (maxplaces vs division/multiplication)

- **Axes:** where=2 + 4 + 13 (maxplaces x computed fields x arithmetic) · when=first Fire / Update constraint-time (or silent precision drift — runtime is stubbed, behavior unverifiable) · who=end user (refusals); the business (cent-level financial drift); audit · reasoning=decimal-places dataflow — universal over inputs
- **Description:** PROBED HOLE: field Share as decimal maxplaces 2 <- Total / Parts compiles clean (Probe22) though 10.00/3.00 = 3.333… exceeds 2 places. Either the sweep refuses every operation whose division yields >2 places (data-dependent stranding) or the value is silently rounded (violating Approximation honesty, Principle 8). Corpus exposure: 46 maxplaces uses, money/price/exchangerate fields throughout.
- **Example:** `field Share as decimal maxplaces 2 <- Total / Parts  # 10/3 → 3.333… — no diagnostic today`
- **Severity:** high — Financial precision is core to the product's domain (exchangerate maxplaces 8 in corpus); a data-dependent refusal that fires on 1/3 of inputs but not 1/4 of them is the worst kind of production surprise, and silent rounding would breach the honesty principle outright.
- **Governance catches:** first-fire · **Inspector:** yes-easily · **Needs universal reasoning:** True
- **Compile-catchable:** needs-language-change — Detection is solver-free-feasible (places-dataflow: division produces unbounded places → obligation at any maxplaces-bounded sink). But the FIX needs language surface: an explicit rounding form (a round-to-places function or assignment modifier) so the author declares intent instead of being forced to remove the bound. Unlockable via a small language change — sketch only, routes to /design.
- **Expressiveness cost:** Without rounding surface, rejecting unproven-places expressions would ban division into any maxplaces field — severe. With declared rounding, cost collapses to one explicit token per site.

### Arithmetic overflow on operands without declared bounds

- **Axes:** where=13 Functions & operators · when=production after specific input history (extreme values) · who=end user (fault); host developer · reasoning=numeric interval (overflow obligation) — universal over inputs
- **Description:** PROBED HOLE vs spec claim: set C = A * B with both operands max 2000000000 compiles with zero diagnostics (Probe14) — 2e9 × 2e9 overflows any integer representation. Principles 10/11 claim overflow is a discharged obligation ('A precept that compiles without diagnostics has no unproven arithmetic faults'); the obligation is not instantiated for this case. Spec-vs-impl drift on the spike branch.
- **Example:** `field A as integer default 2000000000 max 2000000000
on Go -> set C = A * B  # compiles clean; product overflows`
- **Severity:** high — It is a hole in the product's headline guarantee (the fault floor itself, Option 1's own floor) — not differentiating value for Option 2 but a breach to close either way. Business-range data rarely trips it, but money*quantity at scale can.
- **Governance catches:** production-later · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Interval arithmetic over declared bands with an overflow obligation at each multiplication/addition whose result interval exceeds the representable range; unbounded operands generate an obligation the author discharges by declaring max bounds — exactly the existing carries-constraint pattern.
- **Expressiveness cost:** Moderate ceremony: max bounds become effectively required on multiplied numeric fields. Consistent with the discipline the product already demands for divisors.

### Wrong formula, wrong operator, wrong constant — in-band semantic error

- **Axes:** where=4 + 13 + 5 (computed fields, operators, rule thresholds) · when=production after specific input history (silently persists) · who=the business (wrong data committed); downstream data consumer; audit · reasoning=concrete evaluation ONLY — no universal reasoning can know intent
- **Description:** OutstandingBalance <- LaborCharge + AmountApplied instead of minus (contractor-invoice-settlement.precept:46 has the correct minus); credit floor typed 608 instead of 680; TaxableAmount <- Subtotal + DiscountAmount. The value is type-correct, unit-correct, and in-band — every layer of the engine considers it valid, because it IS valid against the declared contract; the contract itself encodes the wrong arithmetic.
- **Example:** `field OutstandingBalance as money in 'USD' <- LaborCharge + AmountApplied  # should be minus; compiles, governs, persists`
- **Severity:** critical — The highest-business-impact class in this vantage: silently wrong money committed on every operation, fully governed, fully 'valid'. Crucially it is the class where the DECISION evidence cuts toward Option 1: governance never refuses it, universal reasoning cannot catch it (intent is not declared), and concrete per-scenario evaluation — the live inspector showing the computed number against the author's mental arithmetic — is the ONLY catch that exists in any system.
- **Governance catches:** never · **Inspector:** yes-easily · **Needs universal reasoning:** False
- **Compile-catchable:** undecidable — Undecidable in general. Compile-time can only shrink the escape space: dimensional analysis already removes wrong-unit formulas (caught today), and tight declared bands convert gross magnitude errors into the band-containment class above. Both subsets are already shipped; the residue is irreducibly semantic.
- **Expressiveness cost:** n/a — nothing to restrict; the mitigation is bounds discipline plus per-scenario evaluation.

### Percent-vs-fraction convention mismatch

- **Axes:** where=4 + 13 (computed formulas) · when=production after specific input history · who=the business; end user (wrong totals) · reasoning=numeric interval (bounds-mediated) — universal over inputs when bounds declared
- **Description:** The 100x cousin of wrong-formula, with a real corpus footprint: invoice-line-item.precept uses BOTH conventions in adjacent lines — DiscountAmount <- Subtotal * DiscountPercent / 100 (line 26, percent) and TaxAmount <- TaxableAmount * TaxRate (line 28, fraction). A maintainer applying the wrong convention produces a 100x error that is otherwise in-band for unbounded fields.
- **Example:** `field TaxAmount as money in '{CurrencyCode}' <- TaxableAmount * TaxRate  # if TaxRate is 7.5 meaning percent, total is 100x off`
- **Severity:** high — 100x money errors are existential for invoicing; mixed conventions inside one shipped sample show the trap is real, not hypothetical.
- **Governance catches:** never · **Inspector:** yes-easily · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Bounds-mediated: if rate fields carry their natural band (max 1 for fractions, max 100 for percents) and computed targets carry bands, existing interval containment flags the 100x blowout. Becomes the already-shipped band-containment check; without declared bounds it degrades to undecidable. A dedicated 'percentage' domain type (Principle 6: domain meaning over primitive convenience) would make the convention a type fact — unlockable via language change, sketch only.
- **Expressiveness cost:** Bounds discipline on rate fields — low; a percentage type adds vocabulary but removes a whole convention-error family.

### Unchecked interpolation in because/reject messages and default strings

- **Axes:** where=14 + 5 (interpolation x because clauses) · when=first Fire that triggers the specific refusal (production) · who=end user (broken refusal explanation); author · reasoning=type/qualifier checking + name binding (exists, not applied at these positions)
- **Description:** PROBED HOLE: {Missing} (undeclared identifier) and {A + true} (type error) inside a because-message compile with zero errors (Probes 9, 11); {Missing} in a default string is likewise unchecked (Probe8) — while the SAME expressions in a set-assignment string are caught (PRE0017, Probe10). The because-message is the product's end-user-facing refusal voice (mandatory rationale, Principle 9); the corpus has 139 interpolated because-messages plus interpolated reject texts (loan-application.precept:102). The broken hole is discovered exactly when the message is needed: at a refusal, in front of an end user — and may itself fault during rendering, inside the refusal path.
- **Example:** `rule A >= 1 because "Value is {A + true} bad"  # compiles clean today; set Note = "{Missing}" errors PRE0017`
- **Severity:** high — A refusal whose explanation crashes or renders garbage defeats the governance contract's promise of typed refusals carrying because-text; it fails at the worst moment (end-user-facing, error path) and is invisible until that path fires.
- **Governance catches:** first-fire · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** False
- **Compile-catchable:** solver-free-feasible — Reuse the existing interpolation bind/typecheck machinery (PRE0017 path) at because/reject/default-string positions — a coverage extension, no new reasoning. Independently valuable under either option.
- **Expressiveness cost:** None.

### Stale or contradicting because-text (prose disagrees with the rule)

- **Axes:** where=5 Rules & ensures (because clauses) · when=production (every refusal of that rule) · who=end user (misled); audit/compliance (rationale misstates the control) · reasoning=none — natural-language semantics
- **Description:** Rule changed to 3.5x income but the message still says '3x'; or the message states the inverse of the comparison. The engine enforces the rule and faithfully reports the wrong explanation.
- **Example:** `rule ExistingDebt <= AnnualIncome * 3.5 because "…exceeds the 3x income ceiling…"  # enforcement and explanation diverge`
- **Severity:** medium — Misleading refusals erode trust and create support load, but data integrity is intact.
- **Governance catches:** never · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** False
- **Compile-catchable:** undecidable — NL semantics. Structural mitigation already idiomatic in corpus: interpolate the governing values into the message ({AnnualIncome * 3.0} in loan-application.precept:38) so the text cannot go stale — an authoring-guidance/lint surface at best.
- **Expressiveness cost:** n/a.

### Clock-varying rule truth — now() in rules makes validity decay with no operation

- **Axes:** where=5 + 13 + 15 (rules x now() x clock as implicit input) · when=after clock time passes · who=end user; the business (entities strand en masse at a date); host developer · reasoning=universal over time — does not exist today; per-scenario simulation structurally cannot explore time
- **Description:** PROBED: rule now() < Deadline because "Past the deadline" compiles clean (Probe23). After Deadline passes, EVERY operation on every instance refuses — entities strand purely by clock, including operations needed to resolve the situation (the close-out transition refuses too, because rules are checked on every operation). No operation caused it; no Create/Fire history predicts it. The inspector evaluates at real now() — the per-keystroke round-trip paradigm has no time-travel control, so the author cannot even ask 'what happens to this entity next month?'.
- **Example:** `rule now() < Deadline because "Past the deadline"  # after the deadline, even Close refuses — entity stranded`
- **Severity:** high — Mass stranding at a date is a business-process outage with a thundering-herd profile; the structural fix (scope the rule with a guard or use a transition) is easy once seen, but nothing today makes the author see it. Also the cleanest UX-unlock evidence for the revisitable-paradigm freedom: a clock-input control or compile-time temporal warning is value the per-scenario inspector structurally cannot deliver.
- **Governance catches:** production-later · **Inspector:** no · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Pattern-level: flag now() inside an UNCONDITIONAL rule (truth decays monotonically with no escape) as a structural warning naming the guard/transition alternatives — pure syntax-plus-scope analysis, deterministic, attributable. Full temporal-path reasoning (which states can the entity occupy when the rule flips) is universal-over-time and harder, but the pattern catch covers the stranding case. Inspector-side: a simulated-clock input is a tooling change, not language.
- **Expressiveness cost:** None for the warning; authors keep now() with a deliberate guard or event-driven snapshot.

### Duration-vs-period mischoice (absolute vs calendar arithmetic)

- **Axes:** where=14 + 1 (temporal arithmetic x temporal types) · when=production after clock time passes (DST shifts, month-length edges) · who=end user; the business (off-by-hours/days deadlines) · reasoning=type checking catches mismatch; the mischoice itself needs domain intent
- **Description:** Adding '30 days' (period, calendar) where the domain means 720 absolute hours, or vice versa, across DST or month boundaries. The type system cleanly separates the types and rejects cross-type misuse (instant into date caught — PRE0018, Probe20); choosing the wrong-but-type-correct one is semantic.
- **Example:** `set ReviewBy = SubmittedAt + '30 days'  # calendar period; across DST the absolute interval differs from 720h intent`
- **Severity:** medium — Off-by-one-hour deadline bugs are real but bounded, and Precept's explicit duration/period split (temporal-type-system.md) already removes the ambiguity most platforms have.
- **Governance catches:** never · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** False
- **Compile-catchable:** undecidable — The distinction is already in the type system (today); the residual miscchoice is intent. Inspector with boundary-date scenarios is the practical catch — again gated on a clock control the current paradigm lacks.
- **Expressiveness cost:** n/a — the type split is already the right cost.

### Redeploy tightens a band or rule — persisted entities now hold out-of-band values

- **Axes:** where=15 x 2/5 (definition evolution x constraints) — value-defect face of the system axis · when=on redeploy/migration, felt at next operation per entity · who=system integrator/migration specialist; end user (refusal on unrelated edit); the business (fleet-wide stranding) · reasoning=cross-version reasoning — does not exist today
- **Description:** v2 raises min from 300 to 500, or adds rule ApprovedAmount <= 50000. Per §0.7, restore trusts persisted data and does NOT re-validate; the sweep on the NEXT operation checks every rule against the working copy — so an entity persisted with 350 refuses its next operation, whatever field that operation touched, with a because-message about a field the user never edited. At fleet scale this is mass latent stranding triggered by deploy, surfacing entity-by-entity over weeks. Migration is explicitly caller responsibility; nothing in the toolchain measures the blast radius before deploy.

### Doomed trajectory (accepted input forecloses every future completion)

- **Axes:** where=7 transitions & outcomes; 5 guards/rules interplay; 6 states · when=the dooming commit happens at Create or an early Fire (everything passes); the manifestation is production-later — a later mandatory step is unsatisfiable and it is too late to reject the input that caused it · who=end user (months later, the entity cannot progress and the cause is an input nobody can change); business (wrong commitments accepted); audit · reasoning=universal over paths AND inputs: backward weakest-precondition from terminal-reaching guards through the state graph — does not exist today
- **Description:** An operation is accepted — every rule and ensure passes — but the committed values place the entity in a configuration from which NO sequence of future operations can reach completion: every path to every terminal requires a predicate the carried values cannot satisfy, and the deciding fields are not writable on any reachable path (readonly baseline, no set actions, omit). The correct behavior is to refuse the dooming input AT COMMIT TIME; today nothing does. Generalizes class 5 from 'one state's envelope' to 'the future cone of the current configuration'. Example shape from the corpus: loan-application.precept accepts any CreditScore 300–850 at Submit; if Decline didn't exist (or were guard-restricted), a Score < 680 application would be accepted into a state whose only exits require Score >= 680 — Score is never writable again.
- **Example:** `Submit accepts Score=500 (all constraints pass). Only exits from UnderReview: `on Approve when Score >= 680 -> transition Approved` and `on Audit when Score >= 650 -> transition Audited`. Score has no later write site. The Create succeeded; the entity was dead on arrival.`
- **Severity:** critical — This is the defining gap between per-operation governance and whole-trajectory soundness: governance validates the present, the defect lives in the future; by the time it is felt, the contractually correct moment to refuse has passed. Highest business impact in the vantage (commitments accepted that cannot be honored).
- **Governance catches:** never · **Inspector:** no · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Two deliverables from one analysis: (a) compile-time — for each state, compute the 'progressable' predicate (disjunction over exit rows of guard ∧ recursively-progressable target, backward fixpoint from terminals over the interval/relational fragment); warn when an inbound row's established envelope provably lands outside it; (b) the stronger play is a RUNTIME/INSPECTOR claim: evaluate the precomputed progressable predicate against the concrete working copy at commit time and refuse/flag dooming inputs ('accepting this value makes Approved unreachable'). The predicate is finite (≤50 states, no loops in expressions; cycles handled by fixpoint over a finite lattice), witnesses are attributable per §0.6 philosophy 3/6. Substantial engineering — the most expensive class in this vantage — and conservative: non-interval guards make the predicate weaker (missed dooms), never false refusals... note the refusal direction needs care: refusing on a CONSERVATIVE doom check could refuse savable entities, so runtime use must gate on provably-doomed only.
- **Expressiveness cost:** Low-to-moderate: full value comes only for guards in the interval/relational fragment; heavy string/quantifier guard usage degrades coverage gracefully. No syntax loss; optionally a per-state `progressable` intent modifier (language change) to scope where the obligation is enforced.

### Monotonic trap (bounded budget exhausted on a retry cycle)

- **Description:** A cycle whose every traversal monotonically consumes a bounded budget (counter with max, collection with maxcount), where saturation makes every exit unsatisfiable. Today's proof engine MAKES the trap shape inevitable: ProbeK shows the unguarded `set Attempts = Attempts + 1` (max 3) is REJECTED (PRE0078, interval [1..4] ⊄ [0..3]) — correct fault-floor behavior forcing the author to add `when Attempts < 3`; but nothing then asks what happens at Attempts == 3. If the non-retry exits are data-dependent (need an approval that never comes) the entity is permanently trapped at saturation. The compile-time fault floor and the process trap are causally linked: the floor forces the guard, the guard creates the silent ceiling.
- **Example:** `ProbeK + the forced guard: `from A on Retry when Attempts < 3 -> set Attempts = Attempts + 1 -> no transition; from A on Pass when ExternalOk -> transition Done`. After 3 retries with ExternalOk false, A is a value-trap: Retry → Unmatched forever, Pass → Unmatched until external truth changes.`
- **Severity:** high — Retry/attempt budgets are a ubiquitous business pattern; the failure appears only after N real operations, is invisible to any single-scenario test, and presents to the end user as a button that silently stopped working.
- **Governance catches:** never · **Inspector:** no · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Detect cycles (state graph is tiny); per cycle, sign-classify the delta each traversal applies to bounded fields (transfer functions exist); at the saturated boundary value, re-run guard satisfiability on all exits from the cycle's states. ### Required-state bypass (dominates-some vs author-intended dominates-all)

- **Axes:** where=6 states & lifecycle modifiers (required); 7 transitions · when=production after specific input history — an entity completes via the alternate terminal without the mandatory step; compile-silent today · who=audit/compliance (mandatory review skipped on a completed entity); business; author (believes the modifier guarantees more than it does) · reasoning=graph dominators (universal over paths)

- **Example:** `ProbeG: `state Compliance required`; `from Draft on Review -> transition Compliance; from Compliance on Finish -> transition Approved; from Draft on Cancel -> transition Cancelled` — clean compile; entities complete via Cancelled having never been reviewed.`

- **Governance catches:** never · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** True

### Dead routing row via first-match shadowing (including dead reject prohibitions)

- **Axes:** where=7 transitions & outcomes (row ordering, reject rows) · when=compile-catchable; manifests in production as wrong routing on the first matching input (guard-time) · who=end user (wrong outcome for their case); business (special-case policy or PROHIBITION silently inert); audit (a declared reject that never enforces) · reasoning=guard implication / subsumption between rows (universal over inputs)

- **Governance catches:** never · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Tier 1 (trivial, syntactic): any row after an unconditional same-(state,event) row is dead — catchable with today's machinery, no proof needed. Tier 2: pairwise guard implication over the interval/relational fragment ('earlier guard ⊇ later guard ⇒ later row dead'), reusing existing interval comparison; conservative outside the fragment. Witnesses are legible (which earlier row shadows, on what range).
- **Expressiveness cost:** None; ordering remains the routing semantics — the compiler only proves when ordering makes a row unreachable.

### Guard-coverage hole (Unmatched limbo on a routed event)

- **Axes:** where=7 transitions & outcomes (guard sets per state×event) · when=Update/Fire guard-time, production after specific input history — the data condition falls between the declared guards · who=end user (neither success nor an explanatory refusal — outcome 5 'Unmatched' carries no because-text); host developer (must handle a verdict the author never thought about) · reasoning=guard-union completeness over the input/field space (universal over inputs)
- **Description:** Rows exist for a (state, event) but the guards jointly fail to cover the value space and no unconditional or reject fallback exists. Spec §3A.2 classifies this as outcome 5 'Unmatched — an instance data condition the caller can address' — but when the uncovered region is one the entity can legitimately occupy, the author has an unrouted hole: the operation silently does nothing actionable, and combined with class 5/7 dynamics the hole can be permanent. The loan sample handles this correctly (unconditional reject fallback after the guarded Approve row) — the defect class is forgetting that fallback.
- **Example:** ``from Review on Approve when Score >= 680 -> transition Approved` with no second Approve row: an entity with Score 500 gets Unmatched — no refusal reason, no route, nothing in the file says what Approve means for low scores.`
- **Severity:** medium — Frequent and annoying rather than catastrophic alone: the caller gets a typed non-answer instead of governed refusal with rationale; becomes severe only when it composes into a permanent trap (covered by classes 5/7).
- **Governance catches:** first-fire · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Interval-complement of the guard union per (state,event): if a representable region of the declared field/arg space matches no row, warn and name the uncovered range ('Score in [300..679] matches no Approve row — add a fallback or reject'). Exact within the interval fragment; conservative outside. Alternative surface decision: require an explicit fallback row per routed event (language change, total-routing rule).
- **Expressiveness cost:** Low: warning form costs nothing; a mandatory-fallback rule would add one line of honest ceremony per routed event.

### Missing event availability (partial coverage intended as universal)

- **Axes:** where=7 transitions; 10 events; 6 states · when=production — end user needs the operation in a state where it has no rows (outcome 6 UndefinedEvent, 'a definition gap'); deliberately compile-silent today (CC#21) · who=end user (cannot cancel/annotate at the moment it matters); business (forced out-of-band workarounds); form/UI designer (event button vanishes in some states with no design rationale) · reasoning=per-event incoming-coverage over the reachable state set (universal over states) — declared-intent check, does not exist today
- **Description:** An event the author intends to be available broadly (Cancel, AddNote, Reassign) has rows in only some states — the author forgot a state, or added a state later and missed the event matrix. The compiler is deliberately silent on partial coverage (graph-analyzer.md §6.5, CC#21: flagging it would violate 'proven violations only' — partial coverage is usually intentional). The defect is real but indistinguishable from intent WITHOUT a declaration; the roadmap's `universal` event modifier (graph-analyzer-roadmap.md) is precisely the missing intent surface, already designed as a deferred pure-graph check. Zero-coverage (event with no rows anywhere) IS caught (PRE0081/PRE0125, ProbeD).
- **Example:** `A precept gains `state OnHold` in a later edit; Cancel rows exist for Draft/Review but nobody adds `from OnHold on Cancel`. Customers on hold cannot cancel; support does it by database edit.`
- **Severity:** medium — Common in lifecycle evolution (new states added to mature precepts) and felt directly by end users; mitigated because the designed inspector surfaces per-state available events very visibly.
- **Governance catches:** never · **Inspector:** yes-easily · **Needs universal reasoning:** True
- **Compile-catchable:** needs-language-change — The `universal` modifier on the roadmap (fires from every reachable non-terminal state) turns intent into a checkable claim — incoming-edge cardinality analysis over the already-computed coverage entries (EventCoverageEntry exists; the check is a set difference). Analysis is trivial once the intent surface exists.
- **Expressiveness cost:** None — purely additive modifier; authors of genuinely partial events write nothing new.

### Hook firing-semantics mismatch (no-transition skips hooks; self-transition re-fires them and re-clears omit)

- **Axes:** where=9 state entry/exit actions; 7 outcomes (no transition vs transition Self); 8 omit interplay · when=production-later — wrong/missing audit data discovered downstream; constraint-time when an omit-clear wipes a value a rule needed · who=downstream data consumers (timestamps/counters wrong); audit (entry events double-counted or missing); end user (data they entered vanishes on a self-transition omit-clear) · reasoning=per-scenario simulation reveals each instance; the CLASS is a semantic-model comprehension issue — no reasoning category catches a wrong mental model, only surfacing the trace
- **Description:** Two dual authoring traps from locked semantics: (a) `no transition` outcomes execute mutations WITHOUT entry/exit hooks (spec §3A.2 outcome 2 — 'a deliberate design'), so an author who centralizes timestamping in `to State -> set ...At = now()` (the loan sample's advertised pattern) gets NO timestamp update on in-place mutations and may believe otherwise; (b) an explicit self-transition DOES fire exit+entry hooks and re-clears omit fields on re-entry (spec §2.2 rule 5: omit clears on ANY transition in, including self-transitions) — re-firing counters, double-stamping, and wiping omit-materialized data. Both compile clean by design; both are wrong-outcome-form-chosen defects.
- **Example:** ``to Review -> set ReviewCount = ReviewCount + 1` plus `from Review on Recheck -> set Notes = ... -> no transition` (count NOT incremented — author expected a re-review to count) vs `-> transition Review` (count incremented AND any omit-in-Review field wiped).`
- **Severity:** medium — Produces silently wrong operational/audit data rather than stuck processes; the semantics are locked and reasonable, but the failure is invisible until someone reconciles downstream numbers.
- **Governance catches:** never · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** False
- **Compile-catchable:** undecidable — Which behavior the author MEANT is not in the file — undecidable as stated. Unlockable via language change (kind sketch: explicit hook-applicability surface, e.g. hooks that declare whether they fire on re-entry/in-place, making intent checkable); short of that, the lever is inspector UX: the mutation trace must show 'hooks skipped (no transition)' / 'omit-cleared on re-entry' loudly.
- **Expressiveness cost:** None today; an intent surface would be additive.

### Terminal-yet-mutable (post-completion mutation surface)

- **Axes:** where=6 states (terminal); 7 transitions (no-transition rows, wildcards); 8 access modes (editable baseline) · when=production-later — a completed/audited entity changes after completion; compile-silent today · who=audit/compliance (completed records are assumed frozen); downstream data consumers (reports over 'final' data shift); business · reasoning=structural: outcome-type + access-mode analysis per terminal state (universal over states) — partially exists, not pointed at terminals
- **Description:** `terminal` bans only outgoing TRANSITION edges (StateModifierMeta.AllowsOutgoing). Three mutation surfaces survive in terminal states, all compile-clean: (a) explicit `from Done on Touch -> set ... -> no transition` rows (ProbeP: zero diagnostics); (b) `from any` wildcard no-transition rows expanding into terminals (ProbeH); (c) the field-level `editable` baseline, which keeps fields Update-writable in every state including terminals unless the author writes `in Done modify all readonly`. The domain-expert reading of 'terminal' is 'finished, frozen'; the actual guarantee is only 'no further lifecycle movement'. With 17/77 samples using wildcards, surface (b) is silently present across much of the corpus.
- **Example:** `ProbeP: `state Done terminal; from Done on Touch -> set Note = Touch.Text -> no transition` — clean compile; plus any `field X editable` remains caller-writable via Update while in Done.`
- **Severity:** high — Audit-grade defect: the whole value of a terminal state to compliance is immutability of the completed record; every surveyed mutation surface here is invisible in the file at the state declaration site.
- **Governance catches:** never · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Pure structural checks on existing data: warn on no-transition rows whose from-state is terminal, exclude terminals from wildcard expansion (or warn), and warn on editable-baseline fields with no terminal-state readonly override. All three are set lookups over StateGraph + access-mode tables. The real question is a SEMANTICS decision — should terminal imply frozen? — which may be a small language change (e.g., terminal implies modify-all-readonly unless opted out) rather than analysis.
- **Expressiveness cost:** Low: legitimate post-completion annotation (append an audit note) would need an explicit opt-out — honest ceremony that documents the exception.

### Expiring-exit trap (clock-monotonic dead-end)

- **Axes:** where=7 transitions (temporal guards); 15 clock time as implicit input; 6 states · when=after clock time passes — no operation occurs at the moment the entity becomes doomed; discovered on the next attempted Fire · who=end user (pickup/claim silently impossible); business (inventory/slots stranded in limbo states); host developer (writes sweep jobs to compensate) · reasoning=universal over time: monotonic falsifiability of temporal guards — no reasoning over now() exists today
- **Description:** Every completing exit from a state carries a guard of the form `now() <= Deadline` (monotonically falsifiable: once false, false forever), with no time-independent alternative exit. After the deadline, the state is a PERMANENT trap — strictly worse than class 5 because no future input can ever help, and the dooming 'event' is the passage of time, which fires no operation and triggers no governance. ProbeQ (modeled on the parcel-locker/waitlist/hold patterns in the corpus) compiles clean: Held's only completing exit is `on Claim when now() <= Deadline`; after Due, the entity can only receive no-transition Nudges forever. Only 1/77 samples textually guards on now() today — an indicative floor only; deadline-driven holds (reservations, offers, locker pickups, library holds) are core domain patterns the corpus authors mostly worked around precisely because the language gives no expiry surface.
- **Example:** `ProbeQ: `from Held on Claim when now() <= Deadline -> ... -> transition PickedUp` with no Expire row — after Deadline, Held is permanently stuck; Claim returns Unmatched with no explanation forever.`
- **Severity:** high — Time-dependent traps are invisible to every per-scenario check run 'now', strand real-world resources, and produce the most confusing end-user failure (an operation that worked yesterday returns Unmatched today with no rule violated and no refusal text).
- **Governance catches:** never · **Inspector:** no · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Syntactic-plus-monotonicity classification, no solver: classify each temporal guard as monotonically falsifiable (`now() <= D` shapes), monotonically establishable (`now() >= D`), or stable; warn when a state's every completing exit is monotonically falsifiable with no stable/establishable fallback ('this state needs an expiry path'). The matching fix likely wants a language surface for expiry transitions (kind sketch: a declared timeout/expiry row form) — flag: unlockable via language change. ALSO an inspector-paradigm finding: per-keystroke Inspect evaluates at the current clock and structurally cannot show 'permanently stuck in 31 days'; a what-if-time simulation axis is an option-2 UX unlock the round-trip paradigm cannot deliver.
- **Expressiveness cost:** None for the warning; an expiry surface is additive and would REPLACE host-side sweep-job code (expressiveness gain).

### Definition-evolution stranding (redeploy breaks persisted lifecycles)

- **Axes:** where=15 system-level definition evolution; 6 states; 7 transitions · when=on redeploy/migration — at Restore (state name no longer exists: invalid-input failure) or on the first post-restore operation (narrowed guards/new ensures: re-governance refuses, or no row matches the carried values ever again) · who=system integrator/migration specialist (migration is explicitly caller responsibility); business (entire persisted population stuck mid-lifecycle); end user; audit · reasoning=cross-version reasoning (old definition + persisted population envelope vs new topology) — does not exist today, in any tool surface
- **Description:** Editing a .precept and redeploying changes the world under persisted entities: (a) a state renamed/removed → restore returns invalid input (spec §3A.2 restoration outcomes — undefined state) and the entity cannot even be loaded; (b) exit rows from a mid-lifecycle state removed or guards narrowed → restored entities are instant semantic dead-ends under the new topology; (c) new entry/residency ensures stricter than the data written under the old contract → first operation gets ConstraintsFailed with no path to fix (the fields may be readonly in that state). §0.7 explicitly scopes restored state OUT of the guarantee (trusted as valid when persisted, re-governed on next operation) and §3A.2 defers migration to the caller — so this entire class is contractually outside both compile-time checking and governance TODAY, yet it is the highest-probability way a real deployment produces mass-stranded processes.
- **Example:** `v1 has `state PendingReview`; v2 renames it to `TriageReview` and tightens the Approve guard from Score >= 650 to >= 680. Every persisted PendingReview entity fails restore; every restored 660-score entity that does load can never be approved or declined under the new rows.`
- **Severity:** critical — One edit can strand the entire persisted population simultaneously — the blast radius is every in-flight entity, not one; and no surface today (compiler, governance, inspector) sees two versions at once.
- **Governance catches:** first-fire · **Inspector:** no · **Needs universal reasoning:** True
- **Compile-catchable:** needs-language-change — The reasoning is solver-free (diff two compiled StateGraphs: removed/renamed states, removed (state,event) rows, guard-interval narrowings, new/stricter ensures per state — all existing data structures), but it structurally requires a second artifact: the previous definition (and ideally a persisted-population state census). Kind of change: a version-linkage/migration surface (compile-against-previous, or declared state renames) — sketch only. Without that input the defect is undecidable from one file; with it, a high-value mostly-mechanical diff tool. Candidate niche: no comparator in the corpus's positioning set offers contract-evolution safety.
- **Expressiveness cost:** None to the language as used; the cost is workflow (supplying the prior version at compile time).

### Wrong-but-valid transition target (intent typo within declared states)

- **Axes:** where=7 transitions & outcomes · when=inspection-time / first Fire — the operation lands in the wrong lifecycle position immediately · who=end user; business (entity routed to the wrong process branch) · reasoning=concrete evaluation / per-scenario simulation — this class is the inspector's home turf
- **Description:** A transition row names a declared-but-wrong target (`transition Declined` pasted where `Approved` was meant). Type checker is satisfied (the name resolves); structural diagnostics fire only if the mistake happens to orphan the intended target (then PRE0080 catches it indirectly). Included for honesty about the boundary: this is a defect class where the live inspector paradigm is STRONG — the author inspecting the operation sees the resulting state instantly — and where no universal claim adds value, i.e., evidence FOR option-1 adequacy within this vantage.
- **Example:** ``from UnderReview on Approve when ... -> set ApprovedAmount = ... -> transition Declined` — compiles; first inspection of Approve shows 'outcome: Declined'.`
- **Severity:** medium — Immediate, loud, and caught by the first person who tries the scenario in the designed live-inspect authoring flow; severe only if authored without ever inspecting and shipped to production unexercised.
- **Governance catches:** first-fire · **Inspector:** yes-easily · **Needs universal reasoning:** False
- **Compile-catchable:** undecidable — Intent is not in the file. Partial heuristics exist (action chain sets approval fields then transitions to an error-tagged state — verdict-tag/action-content coherence lint), but the honest classification is undecidable; the mitigation is the inspector, which already covers it.
- **Expressiveness cost:** n/a

### State verdict-tag misclassification (success/warning/error modifiers)

- **Axes:** where=6 states & lifecycle modifiers (severity tags) · when=production-later — downstream consumers and UI render the wrong signal; latent until someone reads a dashboard · who=form/UI designer; downstream data consumers; end user (a declined outcome presented as success) · reasoning=none catches the wrong tag itself (intent); coherence lints possible (per-scenario simulation shows the tag in outcomes)
- **Description:** The success/warning/error state modifiers are semantic verdict metadata consumed by tooling/UX (the semantic-visual system renders them). A mis-tagged state (terminal Declined tagged success, or an operational hold tagged error) produces systematically wrong end-user signaling and wrong downstream aggregation, while violating no rule and faulting nothing. Lowest-stakes class in the vantage but real: it survives forever because nothing checks it.
- **Example:** ``state Declined terminal success` (copy-paste from the Approved line) — every declined application renders green and counts as a successful completion in verdict-grouped reporting.`
- **Severity:** low — Wrong presentation, not wrong data or stuck process; trivially fixed once noticed, but invisible to every automated surface today.
- **Governance catches:** never · **Inspector:** yes-easily · **Needs universal reasoning:** False
- **Compile-catchable:** undecidable — Intent. Cheap coherence lints are solver-free feasible (a terminal reachable ONLY via reject-adjacent paths tagged success; error-tagged initial states), but the general class is unknowable from the file.
- **Expressiveness cost:** n/a

**Regions examined and found empty:** States/lifecycle (Axis1=6) × Create/construction: examined and found COVERED today rather than empty — RequiredFieldsNeedInitialEvent, InitialEventMissingAssignments, AlwaysRejecting promoted to Error for initial events (spec §3A.5), InitialEventInTransitionRow, No/MultipleInitialStates; **Vantage summary:** PROCESS/LIFECYCLE VANTAGE — 18 defect classes enumerated, all four axes placed, 12 precept_compile probes run. THE SHAPE OF THE EVIDENCE: (1) Today's structural floor is real and broader than the spec admits — reachability (PRE0080), no-exit dead-ends (PRE0119), terminal/irreversible/required structural violations (PRE0109/110/111), always-rejecting events (PRE0125), and even bound-dead row guards (PRE0082 fires today despite spec §0.6's implementation-status table listing dead-guard detection as specification-only — doc drift to reconcile; the 0082 message also leaks a raw TypedBinaryOp dump, violating §0.8). (2) The uncaught families that define this vantage are all VALUE-, PATH-, or TIME-DEPENDENT process traps, and they share one signature: governance never refuses anything (every individual operation is valid), the live inspector structurally cannot see them (the defect lives in the future of the trajectory, in the Nth repetition, after a clock deadline, or across all inputs/paths at once), and the business feels them as stranded entities or silently disabled policy. The five strongest for the option-2 bar: PATH-DEPENDENT SEMANTIC DEAD-ENDS (ProbeN — clean compile, permanent trap; solver-free via per-state interval envelopes), DOOMED TRAJECTORIES (input accepted today forecloses every completion; the contractually correct refusal moment passes silently; backward weakest-precondition over the interval fragment — expensive but solver-free, and dual-usable as a runtime/inspector 'this value dooms the entity' claim), ENTRY-HOOK-VS-ENSURE CONTRADICTION (ProbeM — self-contradictory definitions compile; near-free catch reusing the shipped default-fold machinery), DEAD REJECT ROWS VIA FIRST-MATCH SHADOWING (ProbeE — an authored prohibition silently never fires; tier-1 catch is purely syntactic), and EXPIRING-EXIT CLOCK TRAPS (ProbeQ — permanent traps created by time passing with no operation to govern; monotonic-falsifiability classification is solver-free; also the cleanest inspector-paradigm counterexample, since per-keystroke Inspect evaluates at the current clock and cannot show 'stuck in 31 days'). (3) Cheap floor-adjacent wins exist regardless of the decision: no-terminal topology (fact already computed, diagnostic unwired), hook-guard 0082 coverage gap (ProbeR), terminal-yet-mutable surfaces (ProbeP — no-transition rows, wildcard expansion into terminals, editable baseline in terminal states), and wildcard-masked dead-ends (17/77 samples use from-any). (4) Honest option-1 evidence: wrong-but-valid transition targets and hook-semantics confusion are classes where per-scenario inspection is genuinely strong and universal reasoning adds little. (5) Language-change unlocks flagged (sketch-only, not designed): strict/argumented `required` semantics (dominates-ALL gap, ProbeG), the roadmap's `universal` event modifier (partial-coverage intent), an expiry-transition surface (clock traps), terminal-implies-frozen semantics, and a version-linkage surface for definition-evolution diffing — the last being the one class (critical severity, whole-population blast radius) that no surface today can see at all.

## Vantage: INPUT/CONTRACT DEFECTS — the event/edit surface: event declarations and args, event ensures, transition-row routing as t

*(full vantage description: INPUT/CONTRACT DEFECTS — the event/edit surface: event declarations and args, event ensures, transition-row routing as the event's effective contract, per-state access modes (modify/omit/editable), and the system-level evolution/clock facets of the input contract. Primary Axis-1 homes 8, 10, 5(event ensures); secondary 7 and 15 where they shape what callers may send. Grounded in: spec §0.1–0.8/§3A, docs/compiler/graph-analyzer.md, docs/runtime/result-types.md + runtime-api.md, samples/refund-request.precept, and six precept_compile probes (this session) establishing today's catch surface.)*

### Unconstrained event argument (missing arg constraints)

- **Axes:** where=10 — events & args (modifiers on args) · when=Update/Fire constraint-time when the arg feeds a constrained field; latent-never when it feeds an unconstrained field or only guards · who=End user (refusal attributed to a field, not their input); downstream data consumer (garbage values persisted) · reasoning=Type/qualifier checking + numeric interval (composition forcing); residual is intent knowledge no reasoning supplies
- **Description:** An arg declared bare (e.g. 'Amount as money' with no positivity, 'Note as string' with no maxlength) accepts any value the type admits. When the arg flows into a bounded field, the proof engine already forces the author to constrain it (interval-containment obligation — probe verified: arg [0..10] discharged a field's [0..100] bound). The residual defect: args feeding unconstrained fields or used only in guards accept garbage silently — oversized strings, absurd magnitudes — with no contract statement at the API surface.
- **Example:** `event Decline(Note as string)  # no maxlength — a 10MB Note is accepted and persisted; cf. samples/refund-request.precept which authors 'Note as string notempty' deliberately`
- **Severity:** medium — Bad data enters quietly and the refusal locus (if any) is a downstream field constraint attributed to the field, not the caller's input; but governance does catch the constrained-field cases at ingress with typed refusals.
- **Governance catches:** never · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** False
- **Compile-catchable:** today — Already partially forced: interval-containment obligations reject unconstrained args flowing into bounded fields (probe 3 evidence). The residual (no downstream constraint anywhere) is intent-undecidable — the compiler cannot know the domain's bound; a 'bare arg' lint is possible but violates proven-violations-only (§0.6 philosophy 2).
- **Expressiveness cost:** None for the implemented composition path; a mandatory-bounds rule would be severe ceremony and is not proposed.

### Event argument accepted then ignored (globally unused)

- **Axes:** where=10 — event args × 7 transition rows · when=first Fire (data silently dropped); discovered production-later by a downstream consumer · who=End user (their input vanishes with a success outcome); audit/compliance; downstream data consumer · reasoning=Static reference analysis (declared-vs-referenced walk); no semantic reasoning required
- **Description:** An arg declared on the event but referenced by no row action, guard, or ensure anywhere. The caller supplies data; the API accepts it; nothing stores or checks it. Probe 1 confirmed zero diagnostics today for an arg (Submit.Note) referenced nowhere. Silent data loss with audit implications — the user believes the note was recorded.
- **Example:** `event Submit(Note as string, Extra as integer) ... from Open on Submit -> set Amount = 1 -> transition Closed   # Note and Extra vanish; compiles clean (probe 1)`
- **Severity:** high — Silent data loss: end-user-supplied content is discarded with a success outcome. Detection typically happens far downstream (report missing the note), long after the inputs are unrecoverable.
- **Governance catches:** never · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** False
- **Compile-catchable:** solver-free-feasible — Trivial static reference walk: declared args minus the union of references in rows/guards/ensures/handlers for that event. Same family as the existing FieldNeverSet (PRE0158) — the dual for args. No interval machinery needed.
- **Expressiveness cost:** None; a deliberately-ignored arg has no legitimate use in a single-file language.

### Per-state arg consumption asymmetry (arg used in some rows, dropped in others)

- **Axes:** where=10 × 7 — args × per-(state,event) rows · when=first Fire from the non-consuming state; production after specific input history · who=End user (fills a form field this state ignores); form/UI designer (event-level DeclaredArgs hides the asymmetry); audit · reasoning=Static reference analysis per (state,event) row; universal over states only in the trivial enumerative sense
- **Description:** The same event consumes an arg in one state's row but ignores it in another's. EventInspection.DeclaredArgs is event-level and 'drives UX input form rendering' (result-types.md), so the form shows all args in every state — the user fills a field this state's row silently drops. The 'same input valid in one state and silently meaningless in another' defect, in its arg form.
- **Example:** `from Draft on Annotate -> set Notes = Annotate.Text -> no transition
from Review on Annotate -> no transition   # Text silently dropped in Review; same input form`
- **Severity:** medium — Partial silent data loss, state-dependent — harder to notice than global non-use because the happy state works; audit trail diverges by state.
- **Governance catches:** never · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** False
- **Compile-catchable:** solver-free-feasible — Per-(state,event) used-arg sets are a static enumeration; emit a lint when sets differ across rows of one event, and export the per-state arg contract as metadata so forms can render state-correct inputs.
- **Expressiveness cost:** None as a lint/metadata surface; intentional drops can be acknowledged via an explicit no-op convention if ever needed.

### Event ensure unsatisfiable under declared arg constraints (event can never succeed)

- **Axes:** where=5 (event ensures) × 10 (arg modifiers) · when=first Fire — every fire fails with ConstraintsFailed; authoring-invisible today · who=End user (no input can ever succeed); the business (stranded process when sole exit path); author · reasoning=Universal over inputs — numeric interval intersection of arg bounds with ensure predicates; does not run today over the arg environment
- **Description:** The arg's declared bounds and the event ensure contradict: no input exists that passes both. Probe 5 confirmed uncaught today: 'X as integer min 0 max 10' + 'on Apply ensure Apply.X > 20' compiles clean. The event is dead-on-arrival; if it is the sole exit from a state, entities strand there despite a clean state graph — the graph analyzer sees a healthy edge that data-level reasoning knows can never be taken.
- **Example:** `event Apply(X as integer min 0 max 10)
on Apply ensure Apply.X > 20 because "..."   # no X can ever satisfy both; compiles with 0 diagnostics (probe 5)`
- **Severity:** high — A permanently-refusing operation strands business processes; refusals carry because-text but no caller action can ever succeed, and the contradiction lives across two declaration sites the author reads separately. The project already treats the construction analogue (AlwaysRejecting on initial events) as Error.
- **Governance catches:** first-fire · **Inspector:** yes-easily · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Fold arg declared intervals against event-ensure predicates — the exact machinery PRE0082/PRE0153 already run against FIELD constraints (probe 2 verified live), extended to the arg environment. Deterministic interval intersection, no solver.
- **Expressiveness cost:** None — only provably-empty intersections reject, matching proof philosophy.

### Row shadowing / guard subsumption (order-dependent routing defects)

- **Axes:** where=7 Transitions (first-match row ordering) + 5 when-guards · when=Latent-never for the dead row; production-after-history for the wrong-row-fires variant (a reorder or added row silently changes which outcome applies) · who=Author (intent silently ignored), downstream data consumer and audit (entity took the wrong path but every committed configuration is 'valid'), end user · reasoning=Guard implication/subsumption over interval-representable guards — universal over inputs ('no input reaches row 2').

- **Expressiveness cost:** None — equality-rule fragment is decidable here; partial cases (sometimes-commits) remain runtime-governed without diagnostics.

### Guarded-rule scope drift — violation manufactured while the guard is false, refusal lands on the guard-flipping operation

- **Axes:** where=5 Guarded rules (when-clause scoping) + 8 editability windows · when=Production after specific input history: ops while guard false move the related fields freely; a later unrelated op flips the guard true and is refused · who=End user (their innocuous operation refuses, citing fields they never touched), author (wrong-scoping-form defect: a guarded rule where a to-State ensure or unconditional rule was meant), audit · reasoning=Universal over paths — which operation sequences can establish guard-true with the relation already broken. - **Compile-catchable:** solver-free-feasible — Conservative lint, solver-free: flag guarded rules whose subject fields are editable/assignable in configurations where the guard is provably false AND whose guard fields are themselves mutable — i.e., the drift-then-flip sequence is structurally constructible. - **Expressiveness cost:** None as a lint; as a hard requirement ('decaying guard groups must declare a fallback row') it imposes one extra reject row of ceremony — arguably good authoring anyway since it forces the expiry disposition to be explicit.

### Inspection staleness under clock decay (Inspect-to-act TOCTOU)

- **Axes:** where=13 now() + 15 clock + the inspection operation surface (§3A.6) · when=Inspection-time: the answer is honest at evaluation instant and wrong by act time; per-keystroke debounced Inspect re-evaluates now() so answers can flip between keystrokes near a boundary · who=End user operating the entity (clicks the action the UI said was Certain, gets refused/unmatched), form/UI designer (cannot distinguish stable answers from expiring ones), host developer · reasoning=Universal over time at the metadata level: knowing WHICH answers are time-sensitive and WHEN they flip requires now()-dependence analysis, not another concrete evaluation. Concrete evaluation is the cause, not the cure.
- **Description:** Spec §3A.6 guarantees the inspection result matches execution 'for the same inputs' — but the clock is an input no caller can pin (Locked Decision #9 accepts environment-relative determinism). The designed end-user experience (debounced Inspect per keystroke, semantic-visual-system + inspector-preview-v1.html, which has no clock control) presents these as fresh truth with no expiry marking. - **Example:** `# UI shows Submit: Certain (computed at 17:59). User clicks at 18:01.
# Guard `when now() < Deadline` flipped between inspection and fire -> Unmatched.`
- **Severity:** medium — No data corruption ever (the Fire outcome is correct); the cost is broken end-user trust in the product's signature 'the answer is always available and honest' promise, precisely on the entities where deadlines matter most.
- **Governance catches:** immediately · **Inspector:** no · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Solver-free now()-taint propagation per guard/rule/ensure at compile time, surfaced as static metadata on inspection results: each verdict carries timeSensitive=true plus, where the predicate is a simple threshold (now() vs field+const), the computable flip instant. UI renders expiring verdicts with a countdown/decay marker. This is an option-2 UX unlock the inspection paradigm cannot self-deliver — it is reasoning ABOUT the answer's validity over all time, not another sample of the answer.
- **Expressiveness cost:** None — additive metadata, no authoring restriction.

### Cross-operation timestamp ordering assumptions (clock skew / non-monotone wall clock)

- **Axes:** where=13 now() + 14 instant comparison + 15 system-level clock · when=Production after specific history: rule `DecidedAt >= SubmittedAt` over timestamps stamped by now() in different operations, possibly on different hosts or across a clock adjustment; violation surfaces at the stamping operation's sweep · who=Host developer/system integrator (multi-node deployments), audit (ordering invariants), end user (spurious refusal after a clock step) · reasoning=Universal over time plus an environment assumption (clock monotonicity across processes) that is outside the file boundary — no in-language reasoning can establish it (§0.6 philosophy #4: the proof engine's knowledge boundary is the file).
- **Description:** Authors encode event-ordering truth as instant comparisons between fields each stamped with now() in different operations. Under a monotone single-node clock this holds; across hosts, VM migrations, or NTP step-backs the second stamp can precede the first and the legitimate operation refuses. The definition is correct under an assumption the language cannot see or state.
- **Example:** `rule DecidedAt >= SubmittedAt when DecidedAt is set because "..."
# node B's clock is 3s behind node A: Decide fires 1s after Submit, refused`
- **Severity:** low — Rare, environment-dependent, self-describing refusal at the offending operation (governance catches it loudly and atomically); a retry usually cures it. Listed for completeness — it bounds what compile-time can promise about clock truth.
- **Governance catches:** first-fire · **Inspector:** no · **Needs universal reasoning:** True
- **Compile-catchable:** undecidable — Not catchable: the violated assumption (inter-process clock monotonicity) is an environment fact outside the single-file proof boundary. A lint could note 'rule compares two now()-stamped fields' but cannot decide validity.
- **Expressiveness cost:** n/a

### Same-event guard-discipline divergence across states (monotonicity/invariant enforced in N-1 of N states)

- **Axes:** where=7 transition rows across states + 5 wrong-scoping (a per-field invariant simulated by per-row guards)  · when=Production after specific input history: the unguarded state's row lets the invariant regress (e.g., a day-counter moves backward); damage surfaces later — or never — via downstream ensures · who=Author (copy-paste row sets drift as states are added), downstream data consumer (corrupted monotone history), audit · reasoning=Universal over states: 'event E preserves invariant I in every state that routes it' is a cross-row consistency claim no single-scenario evaluation makes.
- **Description:** The corpus's monotone-counter idiom (library-book-checkout AdvanceDay, lines 99-113: `when DayNumber > CurrentDay` guard + reject fallback, duplicated per state) enforces a field-level temporal invariant by hand-copying guards onto every row of every state. Adding a new state with an AdvanceDay row and forgetting the guard lets the counter regress, silently committing (the regression itself violates no declared constraint) and poisoning later guard decisions (`CurrentDay > DueDay` overdue routing). The invariant exists only as row-local guard discipline, not as a declared truth.
- **Example:** `from CheckedOut on AdvanceDay when AdvanceDay.DayNumber > CurrentDay ... # guarded
from Suspended on AdvanceDay -> set CurrentDay = AdvanceDay.DayNumber -> no transition # forgot guard: time goes backward`
- **Severity:** medium — Silent data corruption of ordering history with delayed or absent governance signal; bounded because a defensive author can (and the sample does) add rules — but the language makes the safe pattern manual and repetitive.
- **Governance catches:** never · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** True
- **Compile-catchable:** needs-language-change — Two routes. (a) Solver-free consistency lint today-shaped: within an event, detect that the same field-write is guarded by a comparable condition in some states and unguarded in others. (b) The cleaner unlock is already on the language's own roadmap: declared per-field cross-operation modifiers — `advancing`, `settling`, `writeonce`, `sealed after` are listed as deferred graph-analyzer modifiers in spec §0.5 — which turn the invariant into a declaration checked universally over all write sites. Language-change sketch only; routes to /design.
- **Expressiveness cost:** None for the lint; the modifier route is opt-in surface that REDUCES ceremony (deletes N copies of the guard+reject pair).

### Unintended re-fireability / unbounded accumulation (no-transition rows fired repeatedly)

- **Axes:** where=7 no-transition rows + 13 arithmetic accumulation + 10 event handlers · when=Production after repetition: each individual fire commits validly; the aggregate effect (double-applied discount, infinitely extended deadline) is the defect; surfaces at a declared bound if one exists, else never · who=The business (financial leakage, policy bypass via repetition), end user (can exploit or stumble into it), audit · reasoning=Universal over paths (operation sequences): 'this row can fire k times and the k-fold effect violates intent' — single-fire evaluation is structurally blind to it.
- **Description:** A `no transition` row is re-fireable arbitrarily from its state. When its actions accumulate (`set Due = Due + Extra`, `set Price = Price * 0.9`), firing twice is materially different from once, yet nothing in the language marks once-only intent. The corpus defends by hand: library-book-checkout caps renewals with a counter field + guard + rule (lines 24-30) — three coordinated declarations to express 'at most twice'. Forgetting any leg (or the counter reset on the next loan) reopens unbounded accumulation where every individual fire is constraint-valid.
- **Example:** `from Active on Extend -> set DueDay = DueDay + 30 -> no transition
# no cap declared: fire it 12 times, due date drifts a year; every fire commits`
- **Severity:** medium — Real financial/policy exposure (the repetition is available to whoever can fire events) but always author-defensible in today's language with the counter idiom; the defect is the fragility and ceremony of that idiom, not an enforcement hole.
- **Governance catches:** never · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** True
- **Compile-catchable:** needs-language-change — Today's compiler can already convert accumulation into refusals when a bound exists (interval delta vs max — count-bound machinery per §0.6 shows the pattern). The missing piece is intent surface: a once/limited-fire marker on rows or the deferred `writeonce`/`sealed after` field modifiers (spec §0.5 roadmap list) so the compiler can demand a cap on self-accumulating no-transition rows. A solver-free lint ('row adds an unbounded positive delta to a field with no max and no guard referencing it') is feasible without language change but noisy; the clean catch needs the declared intent.
- **Expressiveness cost:** Opt-in modifier: zero cost to non-users, removes the 3-declaration counter ceremony for users.

### Definition evolution — persisted-entity brick on redeploy (tightened rule vs trusted restore)

- **Axes:** where=15 System-level definition evolution + 5 rules + 8 access modes (the cure field may be readonly in the restored state) · when=On redeploy/migration, surfacing at the first post-restore operation (constraint-time); between restore and that operation the now-invalid configuration persists by design (trusted hydration, spec §0.7 boundary; runtime-api.md lines 266/889) · who=The business and migration specialist (fleet of stranded entities discovered operation-by-operation), end user (every action on their record refuses), host developer (no pre-deploy signal) · reasoning=Cross-version reasoning: old-definition-reachable configurations folded against new-definition constraints. Structurally impossible inside the one-file proof boundary (§0.6 philosophy #4).
- **Description:** The owner edits the .precept (tightens a rule, adds a required ensure, narrows a bound) and redeploys. Restore trusts persisted data without re-validation (locked design: hydration is a database-read analogue; migration is caller responsibility). Every pre-existing entity whose data violates the new rule becomes operationally dead: any Fire/Update sweep re-checks all rules and refuses — and when the offending field is readonly or omitted in the entity's current state, NO sequence of in-contract operations can cure it. Each half is by-design and documented; the composition is an unguarded production cliff with no tooling between 'edit file' and 'fleet bricked'.
- **Example:** `# v1: rule Amount >= 100; entity persisted with Amount = 150 in Review (Amount readonly there)
# v2 deploys: rule Amount >= 200
# restore OK (trusted); every subsequent operation -> ConstraintsFailed; Amount uneditable in Review: permanent`
- **Severity:** critical — Highest blast radius in the vantage: scales to the entire persisted population at once, is invisible until customers hit it one-by-one, and the readonly composition makes it unrecoverable without out-of-contract surgery — exactly what the product forbids.
- **Governance catches:** production-later · **Inspector:** no · **Needs universal reasoning:** True
- **Compile-catchable:** needs-language-change — Not catchable from one file by principle. Solver-free as a cross-version surface: a deploy-gate check taking old+new definitions that (a) diffs constraint envelopes per field/state — any tightening flags entities-may-violate; (b) composes tightenings with the new access-mode map to flag 'violating field uncurable in state S' as the brick-severity subset; optionally (c) given a data sample, counts affected entities. Interval-diff arithmetic only, fully attributable. Requires a new input surface (two definitions), i.e., a product/language-surface decision, not a solver.
- **Expressiveness cost:** None on the authoring language; adds a deploy-time ceremony surface (acknowledged migration story), which the runtime docs already say is the caller's responsibility — this gives that responsibility a checkable artifact.

### Definition evolution — silent routing/behavior drift across versions

- **Axes:** where=15 Definition evolution + 7 first-match row ordering + 5 guard edits · when=On redeploy: same event + same data now selects a different row/outcome; no refusal, latent in audit trails · who=Audit/compliance (decision criteria changed silently mid-population), downstream data consumers (same-shaped entities took divergent paths), the business · reasoning=Cross-version reasoning over routing semantics: 'for which input regions did the matched row change between v1 and v2' — a relational diff over guard partitions.
- **Description:** Because routing is first-match order-sensitive (§3A.1), inserting/reordering/loosening a row changes which outcome fires for input regions that previously matched a later row — with zero refusals (both versions commit valid configurations) and zero signal. Entities processed before and after the redeploy diverge for identical inputs. Determinism (§0.1 #3: same definition, same data, same outcome) is preserved per-version; nothing in the product covers the cross-version pair, and persisted history mixes both regimes.
- **Example:** `# v1: row A `when Amt > 1000 -> Review`; row B fallback -> AutoApprove
# v2 inserts `when Amt > 500 -> Review` above A
# Amt=700 entities: AutoApproved last week, Review today; no diagnostic anywhere`
- **Severity:** high — Pure audit/compliance exposure with the worst observability (nothing fails); for regulated domains (the corpus is dense with insurance/medical/lending) silent decision-criteria drift is a reportable event.
- **Governance catches:** never · **Inspector:** no · **Needs universal reasoning:** True
- **Compile-catchable:** needs-language-change — Same cross-version surface as the brick class: partition each (state,event) input space by guard intervals in both versions and report regions whose matched row differs — solver-free for the interval-guard fragment; presented as a routing-diff report the owner approves at deploy. Needs the two-definition input surface; analysis itself is today's interval machinery.
- **Expressiveness cost:** None on authoring; deploy-gate ceremony only.

### Vacuous protection — guarded rule/ensure whose activation is unattainable on any reachable path

- **Axes:** where=5 Guarded rules / state ensures + 7 reachability + 8 access modes · when=Latent-never: the rule never evaluates against any reachable configuration; the author believes a protection exists · who=Author and audit/compliance (the contract documents a control that is operationally inert), the business (the unprotected scenario eventually occurs ungoverned via a definition edit that 'should' have been covered) · reasoning=Guard satisfiability composed with universal-over-paths attainability — the same per-state attainable-fact machinery as the strand class, pointed at constraint guards instead of routing guards.
- **Description:** A guarded rule whose when-condition can never be true in any reachable configuration (guard field never written on any path, or guard range disjoint from every value any reachable write can produce) is dead protection — it silently never applies. Distinct from live PRE0082 (single-guard vs declared static bounds, verified firing) and from spec-only vacuity item 8 (rule always TRUE): this is the rule never being ACTIVATED, a path/flow property. The danger is asymmetric: nothing misbehaves while it sleeps; the cost lands when the author, auditor, or a future edit relies on the protection existing.
- **Example:** `rule Payout <= Limit when Status == "escalated" because "..."
# no transition row or editable window can ever write Status = "escalated": the rule is inert; compiles clean`
- **Severity:** medium — No direct runtime harm — the harm is epistemic (false confidence in a documented control) and deferred; for compliance-heavy domains a provably-inert declared control is itself a finding.
- **Governance catches:** never · **Inspector:** no · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Reuse the per-state attainable-fact dataflow (strand class): a guard whose satisfying region is disjoint from the attainable value/presence set in every reachable state marks the rule provably-inactive. Conservative: flags only proven inertness, per proof philosophy #2.
- **Expressiveness cost:** None — diagnostic only; deliberately-dormant rules (awaiting a future state) would need the author to acknowledge, which is arguably the point.

### Editable-window vs residency-constraint squeeze (permitted edit space provably empty or one-directional)

- **Axes:** where=8 Access modes (per-state modify editable) + 5 residency ensures + 2 field constraints · when=Update, constraint-time, repeatedly across the entity's residency in the state — every attempt at the intended edit refuses · who=Form/UI designer (renders an editable control whose every meaningful value refuses), end user (Kafkaesque edit loop), author (two correct-looking declarations interact) · reasoning=Numeric interval/relational intersection of the field's constraint range with the state's active ensures — universal over permitted values ('no committable value exists' / 'only values below the current one commit').
- **Description:** A field is declared editable in a state whose residency ensures leave no (or only degenerate) committable values — the editable window is structurally useless, discovered one refused Update at a time. The corpus contains a live near-miss: library-book-checkout declares `in Overdue modify DueDay editable` (line 49) alongside `in Overdue ensure CurrentDay > DueDay` (line 58) — every edit extending DueDay to or past CurrentDay (the natural staff action: cure the overdue) is refused; only edits keeping the book overdue commit. The fully-empty variant (ensure range disjoint from field constraint range) is a proven contradiction in the same family as the state-scoped contradiction class but on the Update surface.
- **Example:** `in Overdue modify DueDay editable
in Overdue ensure CurrentDay > DueDay because "..."
# staff edits DueDay forward to resolve the overdue: refused, always — the cure path doesn't exist in this state`
- **Severity:** medium — Each refusal is loud, immediate, and atomically safe; the damage is product-experience and process design (the intended cure operation does not exist), occasionally hardening into a strand when the edit was the only escape.
- **Governance catches:** immediately · **Inspector:** yes-easily · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — For each (state, editable-field) pair, intersect the field's declared range with the state's residency-ensure constraints on that field: empty intersection = proven-useless window (error-grade); intersection strictly one side of all reachable current values = directional-only window (info-grade). Interval arithmetic over declarations that all sit in one file.
- **Expressiveness cost:** None for the proven-empty case; the directional case must stay informational (sometimes intended, as arguably in the library sample where only backdating is meant).

**Regions examined and found empty:** Axis1=13 (now()) x Axis2=authoring/compile — temporal TYPE misuse around now(): instant/date/duration operator mismatches, datetime±duration bans (Decision #27), zone handling are fully caught by the shipped type checker today; no residual cross-event defect class lives at the typing layer.; Axis1=14 (duration/period arithmetic) x Axis2=cross-operation — period-vs-duration semantic confusion is compile-rejected by the type split, and degenerate constant comparisons get DegeneratePeriodComparison; the dangerous residue all flows through the now()-decay classes already enumerated; nothing additional found.; Axis1=13 (now()) x Axis2=intra-operation — drift between multiple now() evaluations within a single Fire is excluded by spec (temporal-type-system.md line 566: internal consistency within a single fire is guaranteed); examined, empty by design.; Axis1=6 (lifecycle modifiers required/irreversible) x Axis2=production-after-history — the structural overapproximation (spec §0.5) is SOUND for these universally-quantified modifiers: runtime guards only remove paths, so 'all structural paths visit S' / 'no structural path returns' survive guard pruning; no temporal defect class arises (the unsound direction — reachability optimism — is captured in the guard-locked-strand and decaying-guard classes).; Axis1=7 (transitions) x Axis2=Create — multi-operation stranding cannot originate at construction: construction is single-operation, structurally terminal in the initial state (grammar excludes transition), and AlwaysRejecting-at-Error guarantees a Created path; the only temporal hazard (now()-windowed construction guards making the entity uncreatable after a date) is folded into the decaying-guard class; otherwise empty.; Axis1=15 (evolution) x Axis2=Restore with structural mismatch — renamed/removed states or fields surface immediately at restore as the typed RestoreInvalidInput outcome (runtime-api.md); loud, immediate, well-governed; not a latent defect class (the latent classes are the semantic-drift ones enumerated).; Axis1=11 (quantifiers) x Axis2=cross-operation — each/any/no evaluate per-operation over the collection's current contents with no cross-operation memory; defects involving collection history (e.g., 'was ever above N') are inexpressible and thus cannot be authored wrongly; examined, empty (an expressiveness gap, not a defect class).; Axis1=12 (collection accessors) x Axis2=after-clock-time — no accessor's semantics reference the clock; accessor safety is per-operation and covered by the implemented non-empty/count-interval machinery; no temporal composition found.

**Vantage summary:** Enumerated 17 temporal/cross-event defect classes; 8 verified against the live compiler via precept_compile probes (all the probed hazard shapes compile with zero relevant diagnostics today). The vantage splits into four families. (1) Cross-declaration contradictions that make a transition, state, or edit window provably dead — exit-clear vs entry-ensure, inbound-assignment vs entry-ensure, state-scoped rule contradiction, never-committable rows, empty edit windows: all are universal-over-inputs claims, all are solver-free feasible with machinery the proof engine largely already has (interval folds, sequential action flow, relational rules), and governance catches them only as first-fire refusals that blame data for definition bugs. (2) Path/attainability defects — guard-locked strands and vacuous protection — which are never caught by governance (Unmatched is a legitimate verdict) and which the per-scenario inspector structurally cannot certify; the strand class directly gaps philosophy.md's 'no workflow trapped in a state it can never leave' claim, since shipped dead-end detection is structural-only. (3) Clock-decay defects — now() in rules (entity bricked by time alone, spec-endorsed syntax, probe compiles clean), now() in guards (silently closing windows/time-doomed states), and inspection staleness: the inspector is structurally blind here (no clock simulation exists in the design or prototype; answers are perishable with no expiry marking), making universal-over-time decay classification the clearest candidate differentiator in the vantage — solver-free via monotonicity taint over the closed temporal operator set. (4) Definition-evolution defects — persisted-fleet brick on tightened rules composed with trusted restore + readonly states, and silent routing drift across versions: critical/high severity, invisible to every existing surface, impossible within the one-file proof boundary by principle, but solver-free as a cross-version deploy-gate surface (interval diffs of constraint envelopes and routing partitions). Incidental findings: spec §0.6 implementation-status table lists dead-guard detection (PRE0082) as specification-only but the compiler emits it live (doc drift), and the live PRE0082 message renders a raw typed-AST dump instead of domain-readable text. Honest negatives: cross-host clock-skew ordering is undecidable in-language; re-fireability and cross-state guard-discipline classes need declared-intent surface (the spec's own deferred modifier roadmap — writeonce, sealed after, advancing — is the natural unlock); eight Axis1xAxis2 regions examined and found genuinely empty.

## Vantage: END-USER-EXPERIENCE DEFECTS — defects felt by the end user operating the entity through forms/UI (and the form/UI design

*(full vantage description: END-USER-EXPERIENCE DEFECTS — defects felt by the end user operating the entity through forms/UI (and the form/UI designer building on Inspect): unpredictable refusals, dead-end forms, unexplainable outcomes, operations that look available but always refuse, refusals citing rules the user cannot act on, incomplete-vs-blocked confusion. Grounded in design/system/semantic-visual-system-manifest.md, design/prototypes/inspector-preview-v1.html (debounced inspect, enabled/blocked/noTransition/notApplicable/undefined statuses with reason text), docs/runtime/result-types.md (EventOutcome/UpdateOutcome/Inspection types, Kleene Prospect model), spec §0.1/0.5/0.6/0.7/3A, samples corpus, and 2 live precept_compile probes.)*

### Permanently-dead success path (operation looks available, always refuses)

- **Axes:** where=7 Transitions/guards × 2 Field constraints (also 8 access modes feeding the unreachability) · when=Production after specific input history; degenerate constant-foldable cases manifest at first Fire · who=End user (button forever 'blocked'), business (process silently impossible), form/UI designer (renders a live affordance that is a lie) · reasoning=Guard satisfiability vs declared constraints — numeric interval + universal over inputs; does not exist today (spec §0.6 items 9/12 are specification-only per the implementation-status table)
- **Description:** A transition row's success guard is unsatisfiable against every value its referenced fields can actually hold (declared bounds, readonly-everywhere defaults, choice vocabularies). The event renders, the inspector says 'blocked' with the guard reason, governance refuses correctly each time — and nothing ever reveals that NO data evolution can ever satisfy it. The user reads 'blocked' as 'fix your data and retry'; the truth is 'never'.
- **Example:** `VERIFIED BY PROBE (compiles clean today, only an unrelated PRE0158 hint): field Score integer default 300, readonly in Review with no write site; row 'from Review on Approve when Score >= 680 -> transition Done'. Score can only ever be 300; the Approve success path is dead at definition time, yet the button shows 'blocked — Score >= 680' forever.`
- **Severity:** critical — This is the canonical dead-end form: the business process is structurally impossible while every individual refusal looks legitimate. Late detection cost is maximal — discovered only after real entities pile up unable to advance.
- **Governance catches:** never · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Fold guard atoms against the proof engine's existing field intervals/choice vocabularies/write-site facts (PRE0158 machinery already computes 'can only hold its default'). Empty intersection across all reachable values of guard-referenced fields = dead row. This is exactly spec §0.6 item 9 (UnsatisfiableGuard PRE0082, spec-only) sharpened with write-site reachability. Probe confirmed even the constant-foldable case is uncaught today.
- **Expressiveness cost:** Low. Conservative reporting (proven-dead only, per Proof philosophy #2) flags nothing intentional; rows gated on data the analysis can't bound stay silent. No surface change needed.

### Data-dependent dead-end configuration (stranded entity)

- **Axes:** where=7 Transitions × 5 Rules/ensures × 6 Lifecycle — cross-cutting · when=Production after specific input history · who=Business (stranded process — philosophy's named failure mode 'no workflow trapped in a state it can never leave'), end user (every button blocked), audit · reasoning=Universal over states/paths combined with interval/relational data reasoning; the shipped graph analyzer explicitly overapproximates (§0.5 Overapproximation rule: 'all edges traversable regardless of when guards'), so guard-induced dead-ends are structurally invisible to it
- **Description:** A reachable (state, data) configuration from which no outgoing row can ever succeed: each exit is guard-blocked for this data, rejects, or is doomed by an entry ensure on its target. The structural dead-end diagnostic passes because edges exist on paper. Differs from the previous class: no single row is dead; the CONJUNCTION of this data with all exits is dead.
- **Example:** `State Negotiation with exits 'on Accept when Price <= Budget' and 'on Counter when CounterCount < 3'. An entity reaching Negotiation with Price > Budget and CounterCount == 3 (Budget and CounterCount readonly there) is stranded forever; the graph analyzer sees two healthy edges.`
- **Severity:** critical — Philosophy.md sells 'business processes cannot get stuck' as a core guarantee; the guard-overapproximation hole means a whole family of stuck states ships clean. Discovered in production as aging stuck entities.
- **Governance catches:** never · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Per non-terminal state: is the disjunction of outgoing success-guards satisfiable for every data region the rules/ensures admit in that state? For interval/choice-representable guards this is interval emptiness over a partition — solver-free, deterministic, attributable. Full generality (arbitrary relational/string guards) degrades honestly to 'unresolved' per Proof philosophy #5; arbitrary expressions make the complete problem needs-solver/undecidable, but the interval fragment covers the corpus's guard idioms.
- **Expressiveness cost:** Low-to-moderate. Proven-stranded-region reporting costs nothing; if elevated to prove-or-reject it would push authors to add explicit timeout/escape rows — arguably the desired modeling discipline, but it is ceremony.

### Unsatisfiable editable field (no typeable value will ever commit)

- **Axes:** where=2 Field constraints/modifiers × 5 guarded rules · when=Update — constraint-time; also Fire when an action assigns it · who=End user (field accepts typing, every commit refuses), form designer (cannot render the field as a dead control) · reasoning=Numeric-interval contradiction + universal over inputs — spec §0.6 item 7 (contradictory rule detection) is specification-only today
- **Description:** An editable field whose effective constraint set under some active configuration is empty: declared bounds, a guarded rule, and a state ensure jointly admit no value. Unguarded contradictions surface at compile via default-folding (DefaultViolatesRule — implemented); guarded ones are live. The user retypes endlessly; the inspector shows a violation for each tried value but can never say 'no value works'.
- **Example:** `field Discount as decimal min 10 max 50; rule Discount < 5 when CustomerTier == "basic" because "…". For basic-tier entities the Discount control is a trap: every keystroke inspects red, every commit returns ConstraintsFailed.`
- **Severity:** high — Per-field dead-end form with maximal user frustration (active retry loop). Less severe than entity stranding only because scope is one field/configuration.
- **Governance catches:** never · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Interval-intersection emptiness across all constraints that can be simultaneously active for a field (bounds × guarded rules per guard region × state ensures per state). The proof engine already extracts all these intervals; the missing piece is the cross-constraint intersection pass — the already-specced §0.6 item 7.
- **Expressiveness cost:** None — a provably-empty value set is never intended.

### Unestablishable ensure (refusal citing a truth no available operation can make true)

- **Axes:** where=5 Ensures × 8 Access modes × 9 Entry actions × 10 Events — cross-construct · when=First Fire of the transition into the ensured state (constraint-time), every retry thereafter · who=End user (refusal names a field they cannot reach: 'Done requires a note' with no way to set Note), business (state unenterable) · reasoning=Universal over paths: write-site/editability reachability composed with the graph — pieces exist (PRE0158 write-site facts, graph analyzer) but are not composed
- **Description:** A to/in-state ensure (or mincount on a collection) whose subject cannot be established by any operation sequence available before/at entry: the field has no write site on any inbound path, is readonly in all prior states, or no event adds the required elements. Every attempt to enter the state fails constraints with a because-text about a field the user has no affordance for — the purest 'refusal citing rules the user cannot act on'.
- **Example:** `VERIFIED BY PROBE: 'in Done ensure Note is set because …' where Note has no write site — compiles successfully; only the generic PRE0158 ('Note has no write site') fires, and nothing connects it to the consequence that Done is unenterable and every Approve will return ConstraintsFailed. Collection variant: 'in Review ensure Reviewers.count >= 2' with no event that adds reviewers.`
- **Severity:** critical — Combines a stranded process with an actively misleading refusal: the user is told what must be true but the definition provides no path to make it true. The probe shows the compiler already half-knows (write-site facts) and stays silent about the consequence.
- **Governance catches:** first-fire · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Compose existing facts: for each to/in-S ensure subject, require some establishment site (assignment in an inbound row/entry action, editability in a state on some initial→S path, or a satisfying default). Pure graph walk × write-site/editability map — no value reasoning needed for 'is set'/count-floor cases; interval reasoning extends it to value ensures.
- **Expressiveness cost:** Low. Could over-warn when establishment is intended via a future definition edit; pre-release with zero users this is irrelevant, and proven-impossible cases are never intended.

### Unwinnable or understated argument contract (incomplete-vs-blocked conflation)

- **Axes:** where=10 Event args × 7 Transition guards · when=Inspection-time (the misreport) and Fire guard-time (the refusal); Create variant for initial-event args · who=End user (form says 'provide an amount' when no providable amount can succeed), form designer (renders incomplete when truth is blocked — the manifest's incomplete-vs-blocked normalization is built on this sand) · reasoning=Numeric interval over DECLARED arg ranges intersected with guard requirements + universal over inputs; the runtime's Kleene model (result-types.md) treats a missing arg as bare Unknown, never consulting its declared constraints
- **Description:** The arg's declared constraints are the form's validation contract, but acceptance is actually gated by guards that impose tighter or even disjoint requirements. Two manifestations: (a) form validates green, engine refuses (two-stage refusal whiplash); (b) the worst case — given current entity data, NO in-contract arg value can match any row, yet InspectFire reports Prospect.Possible (Unknown arg) and the surface dutifully renders 'incomplete'. The user types every plausible value into a dead form.
- **Example:** `VERIFIED BY PROBE (compiles silently): event Tweak(NewAmount as integer min 0 max 50); row 'when Tweak.NewAmount > 100'. No legal argument can ever fire the row, yet the inspector's Kleene evaluation yields Possible → the UI shows the event as awaiting input. Data-dependent variant: 'when Approve.Amount <= RequestedAmount' with RequestedAmount currently 0 and arg declared positive.`
- **Severity:** high — Directly corrupts the one signal the designed UX paradigm leans on hardest — the incomplete/blocked distinction the manifest mandates surfaces must communicate. Dead input forms with active user effort.
- **Governance catches:** never · **Inspector:** no · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Static half: intersect each arg's declared interval/choice set with every guard atom referencing it — empty intersection = dead row (probe case is one multiplication); strictly-tighter guard bound = diagnostic suggesting the constraint be carried on the arg (which then also fixes the runtime signal, since governance validates args at ingress). Runtime half: make Kleene Unknowns range-bounded by declared arg constraints so Possible can collapse to Impossible — solver-free interval propagation in the existing inspection pass.
- **Expressiveness cost:** None for the empty case. The tighter-bound lint must tolerate deliberately data-relative guards (Amount <= RequestedAmount) — report only statically-decidable emptiness, leave the rest to the range-bounded inspection.

### Fallback-reject reason divergence (refusal text drifts from the real failing conditions)

- **Axes:** where=7 Reject rows × 14 String interpolation in because/reject messages · when=First Fire and forever after; latent until a user hits the fallback for an unlisted reason · who=End user (told 'requirements A, B, C' while actually failing unlisted D — satisfies A-C, refused again with identical text), audit (recorded refusal reason is wrong) · reasoning=None that exists or could: text-vs-guard semantic equivalence is not mechanical; the structural fix is conjunct-level failure attribution (richer per-scenario simulation witness), which Precept's deterministic guard evaluation can compute trivially but the language has no surface to express
- **Description:** A guarded success row with an unconditional reject fallback: the fallback's hand-written message must re-narrate the success guard's conjuncts, and drifts — omitting conjuncts, or surviving stale after the guard is edited. The refusal is the user's ONLY explanation, and it is wrong. The corpus's flagship sample exhibits it.
- **Example:** `FROM samples/loan-application.precept: the Approve success guard has five conjuncts (documents, score >= 680, income >= 2x debt, request < income/2, Approve.Amount <= RequestedAmount); the fallback reject message lists only the first three. A user with verified docs, a 700 score and 2.5x income coverage who requests slightly more than half their income is refused with a message listing three conditions they already satisfy.`
- **Severity:** high — Unexplainable-outcome in its most corrosive form: an explanation IS given and it is false, defeating the manifest's 'reasons must remain visible' commitment and Precept's whole explainability positioning. Already present in a hand-polished demonstration sample — real authors will do worse.
- **Governance catches:** never · **Inspector:** no · **Needs universal reasoning:** False
- **Compile-catchable:** needs-language-change — The free-text divergence itself is undecidable. Unlockable via language change: a structured refusal surface that derives per-conjunct failure attribution from the preceding rows' guards (the evaluator already evaluates every conjunct deterministically), e.g. a reject form that references the failed guard rather than re-narrating it. A weak solver-free lint (fallback message interpolates none of the guard's referenced fields) catches some drift today.
- **Expressiveness cost:** None to negative — removes a forced duplication (guard logic re-stated as prose) that is itself the defect's cause.

### Reasonless structural denials (access-mode, omit, undefined-event refusals carry no because)

- **Axes:** where=8 Access modes & structural presence × 10 Events (undefined surface) · when=Update — access-mode-rejection stage; Fire — UndefinedEvent · who=End user (locked/missing field, vanished operation, no rationale), form designer (manifest demands reasons for blocked affordances; the contract has none to give) · reasoning=None needed — this is a language-surface asymmetry, visible to plain structural checking once the surface exists
- **Description:** Principle 9 makes because mandatory on every rule and ensure, but the OTHER refusal lanes have no rationale slot at all: UpdateOutcome.FieldNotEditable carries only (FieldName, ActualMode); omit declarations and undefined (state,event) pairs carry nothing. The manifest states 'a rule, rejection, or blocked action without an understandable reason is semantically incomplete' — yet for these lanes the definition cannot supply one even when the author wants to. Every surface gets bare 'DecisionNote is read-only here'.
- **Example:** `samples/loan-application.precept: 'in UnderReview when DocumentsVerified modify DecisionNote editable'. Before verification the user's update returns FieldNotEditable(DecisionNote, Readonly) — the domain truth ('the underwriter cannot draft a rationale before the file is complete', present as a comment in the sample!) has no place in the contract and never reaches the user.`
- **Severity:** high — Systemic: every access-mode refusal in every precept is unexplainable by construction. The sample's author had the reason and could only put it in a code comment — direct evidence the surface is missing, not the intent.
- **Governance catches:** immediately · **Inspector:** yes-easily · **Needs universal reasoning:** False
- **Compile-catchable:** needs-language-change — Not a proof problem: add a rationale clause to modify/omit declarations (kind of change: extend the because requirement to access-mode surfaces, with generated fallbacks like constraint modifiers get) and an explicit forbidden-event disposition. Then mandatory-rationale checking is the same parser-level enforcement rules already have.
- **Expressiveness cost:** Pure ceremony cost (one clause per access declaration), mitigated by generated default rationales exactly as constraint modifiers already do under Principle 9.

### Guard-row shadowing (right scenario, wrong outcome via first-match order)

- **Axes:** where=7 Transition rows/outcomes (first-match routing, §3A.1) · when=Production after specific input history — silent until a discriminating case arrives · who=End user (qualifying case takes the generic/wrong path: wrong target state, wrong mutation, or generic reject instead of intended approval), business (wrong data committed — worse than a refusal), audit · reasoning=Relational guard subsumption/overlap between rows + universal over inputs; does not exist today
- **Description:** An earlier row's guard subsumes a later, more specific row's guard, so the specific row is unreachable (or reachable only on a sliver the author didn't intend). Routing is first-match by design (§3A.1) — correct rows in the wrong order are a silent semantics bug. Unlike refusal classes, this commits a WRONG SUCCESS: the user sees an accepted outcome that is not the one the definition's author intended for their case.
- **Example:** `from Open on Quote when Amount > 1000 -> set Tier = "standard" -> transition Quoted (written first) shadows from Open on Quote when Amount > 10000 -> set Tier = "premium" -> transition Quoted. Every premium-sized request silently books as standard tier.`
- **Severity:** high — Silent wrong data beats a refusal for business damage — nothing refuses, nothing explains, the entity is valid under the rules but wrong under intent. Detection in production requires someone noticing the wrong outcome.
- **Governance catches:** never · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Pairwise row analysis per (state,event): if row_j's guard region (interval/choice representation) is contained in the union of earlier rows' regions, row_j is unreachable — report with the witness region. Same interval machinery as dead-guard detection (§0.6 item 9's natural sibling); arbitrary non-interval guards degrade honestly to unresolved (full generality needs-solver).
- **Expressiveness cost:** None for proven-full-shadow (never intended). Partial-overlap warnings would need care — overlap is the legitimate idiom first-match exists for, so report only total subsumption.

### Implicit prohibition via omission (undefined vs forbidden indistinguishable to the user)

- **Axes:** where=7 Transitions × 10 Events — the (state,event) coverage matrix · when=First Fire (UndefinedEvent outcome) · who=End user (an operation available yesterday vanishes in this state with no reason), form designer (state diagram shows the event exists; per-state surface cannot explain its absence) · reasoning=Graph (state,event) coverage classification — the analyzer already computes outcome classifications today (§0.5 item 6); the missing piece is a completeness/explicit-disposition requirement
- **Description:** Spec §3A.2 carefully distinguishes Unmatched (data condition) from UndefinedEvent ('a definition gap the author should address') — but undefined pairs compile clean, so author forgetfulness and deliberate prohibition are indistinguishable in the shipped artifact. The user who could Decline from UnderReview finds Decline simply gone from Approved: no rows, no reject reason, no contract-carried rationale. Per the spec's own words this outcome is a definition gap, yet it ships.
- **Example:** `samples/loan-application.precept declares Decline but only routes it from UnderReview. From Approved, Fire(Decline) → UndefinedEvent. Is declining an approved-but-unfunded loan forbidden, or unmodeled? The definition cannot say; neither can any surface.`
- **Severity:** medium — Each instance is a confusing absence rather than active damage, but the class is dense (most corpus precepts have many reachable undefined pairs) and it structurally blocks the manifest's requirement that blocked paths carry reasons.
- **Governance catches:** first-fire · **Inspector:** yes-easily · **Needs universal reasoning:** False
- **Compile-catchable:** today — The graph analyzer already enumerates per-(state,event) classifications. A diagnostic listing reachable undefined pairs is a trivial derivation TODAY; making prohibition first-class (an explicit forbid/reject-with-reason disposition so omission becomes a checkable gap — the spec's own 'explicitly forbidden' concept from philosophy.md has no per-state surface) is the needs-language-change upgrade that gives users a reason.
- **Expressiveness cost:** Ceremony: large precepts have many intentionally-irrelevant pairs; needs an honest default posture (e.g., warn only for events the user-facing surface would render) or a cheap bulk disposition.

### Hidden-mutation refusals (entry/exit actions and computed fields violate constraints the user never touched)

- **Axes:** where=9 State entry/exit actions × 4 Computed fields × 5 Rules · when=First Fire — constraint-time, after a hidden mutation · who=End user (supplied valid args, refused with a violation about a field the event surface never showed them), form designer (cannot map the violation back to any input control — ConstraintResult.FieldNames points at fields outside the form) · reasoning=Interval/relational reasoning through entry-action chains under each inbound row's guard context — partially exists today (assignment-range impossibility + sequential proof flow catch the provable-always cases); the data-dependent residue needs the relational narrowing already locked in design
- **Description:** A transition's user-visible contract is its args and guard, but entry/exit hooks and computed-field recomputation mutate additional fields after row selection; when one trips a rule or target-state ensure, the ConstraintsFailed violation cites fields and rules outside the user's mental model and control. §3A.3 explicitly declines to reverse-map rules through mutations, so attribution lands on the hidden field.
- **Example:** `to Premium -> set AnnualFee = BaseFee * 1.5 entry hook, plus rule AnnualFee <= 10000. A user firing Upgrade with perfectly valid args is refused: 'AnnualFee exceeds 10000' — a field that appears nowhere on the Upgrade form and that they cannot edit.`
- **Severity:** high — Refusal-citing-unactionable-rules with extra disorientation: the user cannot even see the causal chain (their event → hidden hook → violated rule). Compile-time provable cases ARE rejected today, so the live residue is precisely the data-dependent band — late, confusing, intermittent.
- **Governance catches:** first-fire · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Extend the implemented assignment-range/sequential-proof pass: for each inbound row into S, propagate the row's guard-narrowed intervals through entry-action chains and check against every rule/ensure active in S — reject when violation is provable for some admissible input region, surface as obligation when unresolvable (prove-or-reject per §0.7, never defer). The relational-rules design (locked) supplies the multi-field half.
- **Expressiveness cost:** Moderate: prove-or-reject on data-dependent hook arithmetic forces authors to add bounds/guards that make hooks provably safe — exactly the Principle 10/11 posture, but it is the one class here where the obligation burden lands on common idioms (derived fees, counters).

### Temporal dead-ends and time-driven truth drift (now() changes the answer with no operation)

- **Axes:** where=15 System-level clock time × 7 Transition guards × 13 now() function · when=After clock time passes (also inspection-time: the keystroke-debounced answer is stale by commit) · who=End user (event available this morning silently refuses this afternoon; no surface warned of the deadline), business (entities strand themselves by pure clock with zero operations), form designer (point-in-time inspection cannot render 'expires at T') · reasoning=Universal over time — does not exist today in any form; the inspector is structurally point-in-time
- **Description:** Guards comparing now() make availability a decaying truth. Two defect shapes: (a) deadline-gated states whose every success exit is time-upper-bounded — after T the entity is stranded with no operation having occurred (the graph and even a data-aware dead-end analysis at deploy time miss it, because the doom arrives by clock); (b) inspect/fire divergence — the ONLY sanctioned break in §3A.6's 'inspection matches execution' guarantee, since now() differs between the debounced inspection and the user's submit. The user experience is the most 'unpredictable refusal' in the inventory: nothing they did changed, yet the answer changed.
- **Example:** `FROM samples/lab-test-order-results.precept: 'from Ordered on CollectSpecimen when CollectionDueBy is set and now() > CollectionDueBy -> reject …'. An Ordered entity whose deadline passes flips CollectSpecimen from enabled to rejecting with no operation; if cancellation paths were also deadline-gated the entity would be clock-stranded. The inspector preview rendered at 09:00 shows 'enabled'; the 09:01 Fire after the deadline refuses.`
- **Severity:** critical — Time-stranded entities defeat the 'processes cannot get stuck' guarantee through a channel no existing analysis even models; and the silent availability decay is invisible to the entire designed UX paradigm (debounced inspection answers only 'now').
- **Governance catches:** production-later · **Inspector:** no · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Classification, not liveness proof: syntactically recognize now()-upper-bounded guard atoms; flag states where every success exit is time-upper-bounded and no time-unbounded escape row exists — pure structural pass over guard trees. The UX half (surfacing 'valid until CollectionDueBy' instead of a point answer) is unlockable via language change — a declared deadline/expiry surface the runtime can expose as inspection truth (kind of change: first-class temporal-window declaration rather than raw now() comparison). Proving general temporal liveness is undecidable; the classification fragment is not.
- **Expressiveness cost:** Low for the structural flag. The language-change route trades free-form now() arithmetic in guards for a declared-window construct on the flagged patterns — a constraint, but one that converts invisible decay into surfaceable truth.

### Definition-evolution strandings (redeploy breaks the user's working entity)

- **Axes:** where=15 System-level definition evolution — interacting with every other region · when=On redeploy/Restore, manifesting at the next operation (restore itself fails on structural mismatch; constraint tightening defers to the next operation's sweep per §0.7 boundary) · who=End user (the entity they were mid-process on now refuses everything, citing rules about fields they never touched, or fails to load at all), business, system integrator/migration specialist, downstream data consumer · reasoning=Cross-version reasoning — does not exist today in any form; migration is explicitly caller responsibility (§3A.2 restoration outcomes)
- **Description:** Edit the .precept and redeploy: persisted entities restore under the new definition. Structural mismatches (removed state, renamed field) fail restoration outright; semantic tightenings (raised min, new unguarded rule, narrowed choice vocabulary, new entry ensure) restore fine — restored state is trusted per §0.7 — then ambush the user at their NEXT operation, whose collect-all sweep reports violations the user's edit didn't cause, phrased as if they did. Yesterday's valid entity becomes today's unexplainable refusal generator, with refusal text blaming data the user cannot relate to their action.
- **Example:** `v1 ships 'field CreditScore min 300'; entities persist with CreditScore 450. v2 raises a rule floor to 600. A restored 450-score entity loads fine; the user then edits an unrelated DecisionNote field and receives ConstraintsFailed: 'Credit score too low' — on an Update that never touched CreditScore. Removed-state variant: restore returns invalid-input and the entity is simply gone from the user's view.`
- **Severity:** critical — Population-scale: one definition edit can strand every in-flight entity simultaneously. The blame-misdirection (violation surfaced on an unrelated edit) is the worst explainability failure in the inventory, and no surface in the designed UX has any concept of it.
- **Governance catches:** production-later · **Inspector:** no · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Cross-version compatibility check (new compiler input: the prior definition, or its envelope summary): per field, is the old admissible region contained in the new one; per state, does it still exist with a forward path; per choice, vocabulary containment. Interval/set containment — same machinery as existing bounds proofs, applied across versions. Proven-incompatible regions list exactly which persisted configurations will strand. General semantic equivalence is undecidable; envelope containment covers the tightening/rename/removal family that causes the damage. Requires infrastructure (versioned input), not a solver.
- **Expressiveness cost:** None on the language; it constrains the EDIT workflow (a tightening edit gets a named diagnostic instead of silence), which is precisely the protection wanted. Solo-dev/pre-release: no compat burden today, but the defect class is inherent to the product's deployment story.

### Guarded-editability whiplash (data-dependent access silently revokes the form under the user)

- **Axes:** where=8 Access modes (guarded modify) × 2 field-level editable baseline · when=Update — access-mode-rejection stage, after an intervening data change · who=End user (field was editable when the form rendered; submit refuses with FieldNotEditable), form designer (manifest §data-form names 'conditionally editable' as a missing public contract — surfaces cannot even render the condition) · reasoning=Per-scenario simulation answers the point query; 'under what conditions is this field editable / is it EVER editable' needs universal over states+inputs (editability-envelope computation, does not exist today)
- **Description:** Guarded access modes ('in S when G modify F editable') make editability itself a function of data. Legitimate and expressive — but it creates a refusal lane where the affordance the user is touching evaporates because of an earlier change (theirs or another actor's), and the refusal (class: reasonless, see FieldNotEditable) cannot explain what condition G would restore it. Degenerate compile-catchable case: a field whose editability guard is unsatisfiable (never editable anywhere) — a control that renders locked forever.
- **Example:** `samples/loan-application.precept: DecisionNote editable in UnderReview only when DocumentsVerified. A user drafts a note (editable), a re-verification event resets DocumentsVerified=false, their save returns FieldNotEditable(DecisionNote) with no reason and no path back visible. Degenerate: 'in Review when Score > 900 modify Note editable' with Score max 850 — Note is never editable, silently.`
- **Severity:** medium — Confusing and reason-starved but recoverable and localized; the never-editable degenerate overlaps the dead-path family but with lower business cost (a locked field, not a stranded process).
- **Governance catches:** immediately · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Editability-envelope pass: per field, the set of (state, guard-region) pairs where it is editable — interval fold of access-mode guards against field constraints. Empty envelope on a non-readonly-intended field = never-editable diagnostic (same interval machinery as dead guards). The envelope itself is also the public contract the manifest says the data form lacks — one analysis serves both the diagnostic and the UX.
- **Expressiveness cost:** None — proven-never-editable is never intended; the envelope is derived metadata.

### Quantified/collection refusals without element attribution

- **Axes:** where=11 Quantifiers × 12 Collection access × 3 inner-type constraints · when=Update/Fire — constraint-time on collection-bearing entities · who=End user (told 'each line item must have a positive quantity' over 200 rows, not WHICH row), form designer (ConstraintResult.FieldNames attributes the collection field, no element index — per result-types.md there is no slot for one) · reasoning=Concrete evaluation with a richer witness — no universal reasoning; the evaluator already visits the violating element and discards the index
- **Description:** A violated 'each'-quantified rule or per-element inner-type constraint reports the rule, its because-text, and the collection field — but not the offending element(s). §3A.1 mandates collect-all because 'partial feedback is useless to callers,' yet at element granularity the feedback IS partial: the user must binary-search their own data. This is a result-shape/UX-capability defect class traceable to the contract design, not an authoring mistake.
- **Example:** `rule each Item in LineItems satisfies Item.Quantity > 0 because 'Every line needs a quantity'. An invoice with 180 lines refuses with that one sentence; the user scrolls 180 rows hunting the empty quantity.`
- **Severity:** medium — High-friction but honest and recoverable; severity scales with collection size, and collections are exactly where domain experts put their bulk data.
- **Governance catches:** immediately · **Inspector:** yes-easily · **Needs universal reasoning:** False
- **Compile-catchable:** needs-language-change — Not a compile catch — a runtime contract extension: element-indexed violation witnesses on ConstraintResult/ConstraintViolation (the evaluator computes the per-element truth values already; this is keeping, not discovering, the index). Kind of change: result-type surface, mechanical, solver-free.
- **Expressiveness cost:** None — pure witness enrichment.

### Invisible success (committed change the user cannot perceive)

- **Axes:** where=7 No-transition outcomes × 8 omit/readonly visibility × 9 entry hooks · when=Production — every successful Applied whose mutations are off-surface · who=End user (clicked, 'nothing happened', clicks again or distrusts the system), form designer (the manifest open-question 'how should successful no-transition outcomes read as meaningful change rather than anticlimax' is unanswerable when the definition makes the change invisible) · reasoning=Static visibility analysis: mutation-target set × per-state omit/access map — trivial set intersection, does not exist today
- **Description:** A no-transition row (or stateless handler) whose entire mutation set lands on fields omitted or otherwise invisible in the user's current-state surface: state unchanged, visible fields unchanged, outcome Applied. The success is real but unobservable — indistinguishable from a no-op, inviting double-fires (which may then refuse or double-mutate counters) and distrust. Definition-level defect: the author made an event's only effects invisible in the very state where the event is offered.
- **Example:** `from Open on Ping -> set LastContactedAt = now() -> no transition, with 'in Open omit LastContactedAt'. The user's Ping button produces no perceptible change ever; firing it twice double-stamps.`
- **Severity:** low — Erodes trust and invites repeated fires, but commits no wrong data and strands nothing; mitigations (host-side toasts from the Mutations diff) exist outside the definition.
- **Governance catches:** never · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** False
- **Compile-catchable:** today — Per (state,event) no-transition row: mutation-target set ∩ visible-field set for that state == ∅ → diagnostic. All inputs (targets, omit map, access map) exist in the compiled model now; a one-pass derivation.
- **Expressiveness cost:** None — warning-tier; deliberate audit-stamp events can suppress or carry a disposition.

### No static acceptance envelope (the round-trip paradigm cannot tell users what WOULD be accepted)

- **Axes:** where=Cross-cutting: 10 Event args × 2 Field constraints × 7 Guards × 5 Rules — the whole input surface · when=Inspection-time — structurally, at every keystroke, forever · who=Form/UI designer primarily; end user (discovers constraints by being refused, one probe at a time, instead of being shown the acceptable region upfront) · reasoning=Universal over inputs — interval/region projection of the joint constraint+guard system onto each input; does not exist today. The designed paradigm (debounced InspectFire/InspectUpdate per result-types.md and the prototype) is point-wise by construction: it answers 'would THIS value work', never 'WHICH values would work'
- **Description:** The capability inverse of the refusal classes: even with a perfect live inspector, the form can only react to typed values — it cannot pre-render a slider's true range, disable the dropdown options no guard accepts from this configuration, show 'amount must be between 1 and RequestedAmount (currently 5,000)' before typing, or distinguish 'incomplete' from 'no completion exists' (the universal twin of the Kleene class). Every constraint discovery costs the user a refusal or a red flash. A compile-time acceptance-envelope per (state, event, arg) — the satisfiable input region given the entity's current data shape — is UX the per-scenario round-trip structurally cannot deliver, and it is the same interval computation the dead-path diagnostics need (envelope empty = those defect classes; envelope non-empty = render it).
- **Example:** `loan-application Approve: the true acceptance region for Approve.Amount from a given UnderReview entity is (0 .. RequestedAmount] intersected with the guard's affordability terms. Today's designed UX: the user types 60,000, waits the debounce, sees blocked, types 50,000, waits… An envelope-aware form renders the slider 0–47,500 immediately with the binding constraint named.`
- **Severity:** high — This is the principal end-user-experience UPSIDE at stake in the option decision: it converts the product's existing compile-time interval machinery into a visibly different form experience (constraints as affordances, not refusals), and it is the one capability where 'the inspector covers any scenario the author tries' is structurally beside the point.
- **Governance catches:** never · **Inspector:** no · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Project the conjunction of declared arg constraints, guard atoms, and post-state rules/ensures onto each input dimension as an interval/choice-subset, parameterized by current field values (a runtime-instantiated symbolic envelope: compile computes the shape, runtime substitutes today's data). Conjunctive interval/choice guards — the corpus's dominant idiom — are exact; disjunctions yield unions; non-interval atoms degrade honestly to 'checked on submit' per Proof philosophy. Same engine as classes 1/3/5/8/13.
- **Expressiveness cost:** None on authors. Honest-degradation discipline required on surfaces: envelopes must render only what is proven (no approximate region presented as exact, per Principle 8).

**Regions examined and found empty:** Axis1-1 (field declarations & type system) × all runtime stages — type/qualifier mismatches, out-of-vocabulary choice literals (PRE0086, probe-verified), and unit-dimension mismatches are compile-caught today; nothing reaches the end user beyond the fault floor. The ~string case-variant 'wrong sensitivity chosen' idea was examined and found intent-dependent — no mechanically checkable defect, lint-at-best.; Axis1-2 (defaults) × Create — defaults violating rules/initial ensures are compile-caught today (DefaultViolatesRule, UnsatisfiableInitialState per spec §0.6 item 11, verified implemented); residue (defaults dooming guards) is covered by the dead-path classes, not a separate region.; Axis1-3 (collection inner-type constraints) × Update/Fire — per-element value refusals are ordinary governance with because-text; ascending/descending violations likewise; the only end-user-felt gaps fold into the unsatisfiable-field and element-attribution classes. Nothing region-specific found.; Axis1-10 (initial event/construction) × Create — always-rejecting construction is an Error today (AlwaysRejecting promoted for initial events, §3A.5); missing required-field assignment family is compile-caught (RequiredFieldsNeedInitialEvent etc.); arg-contract residue folds into the unwinnable-argument class. Probe confirmed PRE0125 fires for always-reject events.; Axis1-12 (presence & collection accessors) × all runtime stages — empty-access/key-presence/index-bounds are the Option-1 fault floor (Principle 10 obligations, implemented); no end-user defect found beyond the floor plus element attribution (reported as its own class).; Axis1-13 (functions & operators) × runtime stages — div-by-zero/overflow/sqrt obligations are the fault floor; ternary and string functions produced no end-user-visible defect class beyond message quality (folded into reject-divergence).; Axis1-14 (string interpolation & unit arithmetic) × runtime — interpolated-expression faults are covered by totality (Principle 10); unit normalization is compile-side (§0.6 item 5); raw-value formatting in messages was examined and judged a host rendering concern, not a definition defect.; Axis1-6 (state severity modifiers success/warning/error) × all — pure presentation intent; a 'wrong severity chosen' defect is not mechanically checkable against anything. Examined, empty.; Axis1-4 (computed fields) × inspection-time — transitive unresolvability propagation is already a binding design requirement (result-types.md OQ section), so 'computed field shows stale/wrong value during partial inspection' is designed-away; residual computed-field defects fold into hidden-mutation refusals.; All Axis-1 regions × authoring/compile (Axis-2) — definitionally outside this vantage: the end user feels only what survives compilation; authoring-stage manifestations belong to the author-vantage inventory.; Axis1-5 (wrong-scoping-form-chosen, e.g. global rule where state ensure intended) × runtime — examined: the end-user symptom is always one of the already-enumerated classes (over-broad refusal = unsatisfiable field/unestablishable ensure; under-broad = wrong success, host-data vantage); no distinct end-user-facing class beyond those.

**Vantage summary:** From the end-user/form vantage, 16 defect classes were found; the dominant pattern is that GOVERNANCE IS ALWAYS LOCALLY CORRECT AND GLOBALLY SILENT: every refusal is individually right, individually reasoned (where the surface has a reason slot), and collectively incapable of telling the user 'never' vs 'not yet'. The classes split into four families. (1) Dead-path family — permanently-dead success rows, data-dependent strandings, unsatisfiable editable fields, unestablishable ensures, unwinnable argument contracts, never-editable fields: all require universal-over-inputs/paths reasoning, all are invisible to the debounced inspector by construction (it answers point queries; two were probe-verified to compile clean today), and all are solver-free-feasible on the same interval/choice/write-site machinery the proof engine already runs — several are literally the spec's own §0.6 items 7/9/12 still marked specification-only. (2) Explanation family — fallback-reject text divergence (present in the flagship sample), reasonless access-mode/omit/undefined denials (the sample author had to put the reason in a code comment), element-less quantifier violations: these are language/contract-surface gaps (needs-language-change), cheap, and they directly service the manifest's 'reasons must remain visible' commitment. (3) Silent-wrong-outcome family — guard-row shadowing and invisible success: worse than refusals because something commits. (4) System-level family — temporal dead-ends/time drift (the one sanctioned inspect/fire divergence; corpus witness in lab-test-order) and definition-evolution strandings (population-scale, blame-misdirecting): no existing analysis even models these axes (universal-over-time, cross-version). The headline Option-2 UX finding is the acceptance-envelope class: the per-keystroke round-trip paradigm structurally cannot render 'what WOULD be accepted' (true slider ranges, dead dropdown options, incomplete-vs-impossible), and the same solver-free interval projection that powers the dead-path diagnostics yields that surface as derived metadata — one engine, both the defect catches and the UX unlock. Evidence only; the right-sizing verdict is the owner's.

### Tightened constraint strands persisted entities (constraint-envelope shrink)

- **Axes:** where=15 (definition evolution), interacting with 2 (modifiers), 5 (rules/ensures) · when=production after specific input history — manifests at the NEXT operation's constraint-time sweep after redeploy, on entities whose stored values fall outside the tightened envelope · who=end user (refused for data they didn't touch and may not be able to edit), the business (stranded in-flight processes en masse), host developer (must write emergency migration) · reasoning=cross-version reasoning — universal claim 'every value satisfying the v1 envelope satisfies the v2 envelope' (interval/set containment between two definitions). Does not exist today.
- **Description:** Author tightens a bound (max 100 from max 200), adds a rule, or strengthens an ensure, and redeploys. Restore is trusted hydration (spec §0.7) so all v1 entities load fine — but spec §3A.4's sweep checks EVERY constraint against the whole working copy on every operation. Every entity holding a now-out-of-range value gets every operation refused, including operations on unrelated fields. If the stale field is readonly in the current state (axis 8 interplay), the entity is permanently inoperable through the contract — only out-of-band host migration can fix it. Governance 'catches' this only by stranding: the refusal is the symptom, not protection.
- **Example:** `LibraryBookCheckout v1: `rule RenewalCount <= 2`. v2 tightens to `<= 1`. A persisted loan with RenewalCount = 2 restores fine, then EVERY operation — even `AdvanceDay`, which touches only CurrentDay — returns ConstraintsFailed citing the renewal rule. RenewalCount is not editable in CheckedOut, so the patron-facing app dead-ends for every such loan.`
- **Severity:** critical — Fleet-wide: one line of tightening can strand thousands of in-flight entities simultaneously, discovered only as production refusals. The discard-the-working-copy model converts a migration oversight into total entity inoperability, and the refusal message blames a field the operator cannot change.
- **Governance catches:** production-later · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Not catchable from one definition — needs a definition-DIFF surface (old + new). The check is solver-free and mechanical: for each field/rule, old envelope ⊆ new envelope (interval containment for numeric bounds, set inclusion for choice vocab, implication for the rule forms the proof engine already represents — the octagon/relational machinery from §0.6 item 2 is exactly the right engine). Verdict per change: compatible / migration-required / stranding-risk-with-readonly-interaction. The interaction with access modes (readonly field holding a now-invalid value = unfixable) is also statically derivable from the diff plus the new definition's access declarations.
- **Expressiveness cost:** None — a deploy-time diff gate restricts nothing the author can express; it only forces an explicit migration acknowledgment when the envelope shrinks.

### Removed or renamed state orphans persisted instances

- **Axes:** where=15, interacting with 6 (states) · when=Restore (rehydration) after redeploy — RestoreInvalidInput on every load of an affected instance · who=host developer (exception-grade failure path), end user (entity unloadable), the business (every instance in that state bricked until manual migration) · reasoning=cross-version reasoning — set difference of state inventories between two definitions. Trivial once a diff surface exists.
- **Description:** v2 deletes or renames a state. The persistence envelope stores the state as a string (Restore(string? state, JsonElement fields), runtime-api.md:226); every persisted instance in that state fails state resolution at Restore. Rename is indistinguishable from remove+add — there is no mapping surface. Unlike the tightened-bound class this fails at load, not at next operation, so even read paths break.
- **Example:** `v1 has `state Overdue`; v2 renames it to `Delinquent` for vocabulary cleanup. Every book persisted in Overdue now returns RestoreInvalidInput("undefined state") — the host's list-my-loans page throws for those records.`
- **Severity:** critical — Hard failure on load (not even inspection works), affects every instance in the state at once, and the most innocent-looking edit (a rename) is the most common trigger. The graph analyzer guarantees reachability within one definition but nothing guards the persisted-state vocabulary across definitions.
- **Governance catches:** production-later · **Inspector:** no · **Needs universal reasoning:** True
- **Compile-catchable:** needs-language-change — Diff surface: removed-state detection is trivial set difference, solver-free. Distinguishing rename from remove+add needs an authored mapping annotation (a small language/deploy-manifest surface — e.g., a rename declaration the diff tool consumes), hence needs-language-change for the rename half; pure removal detection is solver-free-feasible.
- **Expressiveness cost:** None for detection. A rename-mapping annotation adds one small declaration at deploy time; it does not constrain the live language.

### Removed or renamed field — restore failure or silent data loss

- **Axes:** where=15, interacting with 1 (field declarations) · when=Restore (rehydration) after redeploy (unknown stored key), or latent-never (value silently dropped, business datum lost) · who=host developer, downstream data consumer (the datum vanishes from all egress), audit/compliance (historical value unrecoverable through the engine) · reasoning=cross-version reasoning — field-inventory diff. Trivial.
- **Description:** Stored JSON carries v1 field names. v2 renames BorrowerId to PatronId: the stored key is unknown (spec §3A.2 lists 'unknown fields' as structural-mismatch input → RestoreInvalidInput) and the new field is unset. Whether the engine hard-fails or drops the unknown key, the outcome is restore breakage or silent loss of a business value. Same rename-vs-remove ambiguity as states.
- **Example:** `v2 renames `field BorrowerId` to `field PatronId`. Persisted loans carry {"BorrowerId": "P-1042"}. Restore either rejects the envelope or hydrates PatronId as unset — then `in CheckedOut ensure BorrowerId is set` (now PatronId) fails on the next operation's sweep with no way to supply the value if PatronId isn't editable in CheckedOut.`
- **Severity:** high — Renames are routine vocabulary hygiene for a domain-expert author; the language gives no signal that a rename is a persistence-breaking change. Loss is silent in the drop interpretation — the worst failure mode for a governance product.
- **Governance catches:** production-later · **Inspector:** no · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Diff surface: field-set difference + per-field type comparison, solver-free. Rename mapping needs the same small annotation surface as state renames.
- **Expressiveness cost:** None.

### Added required field without default — pre-existing entities cannot satisfy it

- **Axes:** where=15, interacting with 1, 2 (optional/default modifiers) · when=first operation after Restore (constraint-time: `is set` ensure or required-field sweep), or Restore-time fault if a computed field reads the unset slot · who=end user (refused), host developer (migration debt), the business (stranded entities) · reasoning=cross-version reasoning — 'added non-optional field with no default' is a one-line diff classification
- **Description:** v2 adds `field ApprovalCode as string` (non-optional, no default). New entities supply it at construction (initial event). Persisted v1 entities restore with the slot unset; any ensure/rule touching it fails the sweep on every subsequent operation, and any expression reading it can hit the unset-access backstop fault. The compiler proved the definition safe assuming construction-time governance that v1 entities never went through.
- **Example:** `v2 adds `field ConditionGrade as choice of 'A','B','C'` plus `in Returned ensure ConditionGrade is set because ...`. Every book persisted in Returned under v1 refuses its Shelve event forever — ConditionGrade was never collectable for them.`
- **Severity:** high — This is the single most common schema evolution (add a field) and the failure is guaranteed for 100% of pre-existing entities in the affected scopes, yet nothing at authoring or compile time hints at it.
- **Governance catches:** production-later · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Diff rule, fully solver-free: any added field that is neither optional nor defaulted, referenced by any constraint scoped to a state that existed in v1, = migration-required. The fix prompt is also mechanical: 'add a default, mark optional, or migrate'.
- **Expressiveness cost:** None.

### Type/qualifier change reinterprets stored values (tagged → backstop fault; untagged → silent corruption)

- **Axes:** where=15, interacting with 1 (in/of/to qualifiers), 14 (currency/unit arithmetic) · when=Two manifestations: production after redeploy (unit-mismatch backstop fault on first arithmetic touching the value) for self-describing wire formats; latent-never (silently wrong business data) for bare scalars · who=downstream data consumer and the business (wrong numbers propagate), host developer (Faulted outcomes), audit/compliance · reasoning=cross-version reasoning for the declaration diff; concrete evaluation only ever sees the symptom
- **Description:** Money/quantity/price wire formats are self-describing ({amount, currency} — runtime-api.md:595ff), so changing `money in 'USD'` to `in 'EUR'` leaves USD-tagged values in an EUR-proven field: compile-time unit proofs assumed EUR, and the first cross-value arithmetic hits exactly the out-of-contract [StaticallyPreventable] backstop path runtime-api.md:658 documents ('state restored under a different definition'). For bare integers/decimals there is no tag: changing the semantic unit (hours→days, cents→dollars) or integer→decimal reinterprets every stored value silently — no fault, no refusal, just wrong data forever.
- **Example:** `v1: `field FineAmount as money in 'USD'`; v2 switches the library to `in 'EUR'`. Persisted {"amount":12.50,"currency":"USD"} restores into the EUR field; `FineAmount + '5.00 EUR'` faults at runtime — the proof engine had proven that addition unit-safe. Untagged variant: v1 `field DueDay as integer` counts days; v2 reinterprets it as hours. Every restored entity is now due ~24x early, with no error anywhere, ever.`
- **Severity:** critical — The untagged variant is the worst defect shape in this vantage: undetectable at any runtime stage, propagates wrong business data to every consumer, and directly contradicts the determinism/prevention identity. The tagged variant turns a 'cannot happen' fault class into a guaranteed production fault.
- **Governance catches:** never · **Inspector:** no · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Declaration-level diff catches every type and qualifier change solver-free (the catalog knows both type identities). Semantic reinterpretation of an unchanged `integer` declaration is undecidable from any artifact — but the diff tool can force the author through an explicit 'unchanged meaning' attestation for fields whose constraints changed shape. Tagged-value mismatch could additionally be caught at Restore by checking the wire tag against the declared qualifier — a cheap runtime check the trusted-hydration decision currently skips wholesale.
- **Expressiveness cost:** None for the diff. A restore-time tag check trades a few comparisons per load against the 'hydration is fast' commitment — negligible.

### Computed-field formula change silently rewrites derived values across the fleet

- **Axes:** where=15, interacting with 4 (computed fields) · when=Restore (rehydration) — Restore recomputes computed fields (runtime-api.md:266), so the rewrite happens at load; inspection-time and downstream egress show the new value with no event explaining the change · who=downstream data consumer (stored/reported derived values disagree with re-derived ones), audit/compliance (a number changed with no operation in the log), form/UI designer (displayed value shifts under the user) · reasoning=cross-version reasoning (formula diff); universal over inputs to characterize which entities change value
- **Description:** Restore recomputes computed fields under the current formula. Change the formula and every persisted entity's derived value silently shifts at next load — there is no operation, no audit record, no refusal. Additional hazard: the FromJson hydration primitive does NOT recompute (evaluator.md 'Computed Field Freshness': stale stored values survive), so the two documented hydration paths give different answers for the same envelope — a host using the primitive sees v1-stale values, a host using Restore sees v2-recomputed ones.
- **Example:** `v1: `field TotalDue <- FineAmount` ; v2: `TotalDue <- FineAmount + ProcessingFee`. A regulator-facing statement generated from v1 says 12.50; the entity restored under v2 inspects as 17.50. Nothing in any log explains the discrepancy.`
- **Severity:** medium — No stranding and no fault, but audit-grade inconsistency: derived values are exactly what downstream reporting consumes, and the change is invisible because it rides on a load, not an operation.
- **Governance catches:** never · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Formula diff is trivially solver-free (expression-tree comparison; the builder already has canonical typed expressions). The valuable output is a deploy-time warning: 'computed field X changes value for restored entities; consumers of X include constraints A, B'. Constraint-impact is derivable today from the existing dependency expansion (spec §3A.3 transitive expansion).
- **Expressiveness cost:** None.

### Transition/guard surface change strands in-flight entities mid-lifecycle

- **Axes:** where=15, interacting with 7 (transitions/guards), 10 (events) · when=first Fire after redeploy (guard-time: Unmatched; or Stage 1: UndefinedEvent for removed events); 'production after specific input history' for guard-tightening cases · who=end user (the promised next step vanishes), the business (process cannot complete), host developer (UndefinedEvent on a call site that worked yesterday) · reasoning=cross-version reasoning + guard satisfiability against the restored entity's concrete frozen data; universal over states/paths for the 'no escape route remains' claim
- **Description:** v2 removes an event, deletes a transition row, or tightens a guard. The graph analyzer proves no dead-ends per definition (spec §0.5), but its overapproximation treats guards as traversable and it only ever sees ONE definition. Cross-version, an entity restored mid-lifecycle can face: (a) its only outbound event removed → UndefinedEvent forever; (b) all remaining guards unsatisfiable for its concrete stale data, where the guard's driving fields are readonly in its state → Unmatched forever. The state is structurally fine for new entities and a permanent trap for old ones.
- **Example:** `v1: `from Overdue on Renew when RenewalCount < 2 -> ...`. v2 deletes the Renew event entirely (policy change) and adds a new `Escalate` path gated on `ConditionNote is set` — but ConditionNote is omitted in Overdue. Persisted Overdue entities can fire nothing that transitions; they sit in a guard-proof trap the analyzer certified as dead-end-free.`
- **Severity:** high — Strands processes at exactly the awkward mid-lifecycle points, and falsifies the product's own structural certificate from the user's point of view ('the compiler proved no dead ends' is true per-definition, untrue per-fleet).
- **Governance catches:** production-later · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Conservative tier is solver-free on the diff: removed events, removed rows, and syntactically-tightened guards on states that existed in v1 → 'in-flight entities in state S may lose path P' warnings. The precise tier ('does some reachable v1 data-state strand') needs entity data — feasible as an offline corpus audit tool (run the new definition's guard satisfiability against each persisted envelope; the engine's existing inspection machinery already evaluates exactly this per entity), not as pure compile.
- **Expressiveness cost:** None — warnings on the diff; the conservative tier may over-warn on guard rewrites, acceptable at deploy frequency.

### Retroactively-false structural claims (irreversible / required added after the fact)

- **Axes:** where=15, interacting with 6 (state lifecycle modifiers) · when=latent-never at runtime — nothing fails; the falsehood lives in what audit/compliance reads off the definition · who=audit/compliance (reads `irreversible`/`required` as facts about all data; they are facts only about post-v2 operations), the business · reasoning=cross-version reasoning; would need history data for full verification (out of scope of any compile)
- **Description:** v2 marks Approved `irreversible` or Inspection `required`. The analyzer proves these via reverse-reachability and dominator analysis (spec §0.5 items 4-5) — over the NEW graph only. Entities that lived under v1 may have histories that violate the claim (already reverted out of Approved; reached terminal without visiting Inspection). The definition now makes a compliance-grade structural assertion that is silently untrue for the existing fleet, and no runtime stage ever notices because the modifiers are compile-time-only claims with no per-instance check.
- **Example:** `After an audit finding, the author adds `state Approved irreversible`. A v1 entity that did Approved→Draft→Approved last quarter still exists; the compliance officer cites the modifier as evidence reversal is impossible. The evidence is false for that record.`
- **Severity:** medium — No operational breakage, but it corrupts exactly the artifact Precept positions as the auditable single source of truth — the definition over-claims about persisted history.
- **Governance catches:** never · **Inspector:** no · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — The diff tool can flag it solver-free: 'structural claim strengthened — holds only for operations after this deploy' on any added/strengthened irreversible/required/terminal. Full retroactive verification needs entity history, which the engine does not persist — flagging is the honest, achievable catch.
- **Expressiveness cost:** None.

### Restore-time recompute fault under new-definition proofs

- **Axes:** where=15, interacting with 4 (computed fields), 13 (operators) · when=Restore (rehydration) — the fault fires during the recompute step itself, before any operation · who=host developer (load path faults), end user (entity unviewable, not just unoperable) · reasoning=cross-version reasoning; the per-definition proof was numeric-interval and is correct — the gap is that its precondition (governed ingress) is false for v1 data
- **Description:** v2 adds a computed field whose fault-safety the proof engine discharged against a v2 constraint (spec §0.7: operand carries `nonzero`, proof complete). v1 entities never passed that constraint's ingress; Restore recomputes computed fields on load (runtime-api.md:266) with the stale operand → division-by-zero/overflow backstop fault at load time. This is the concrete, guaranteed-reachable instance of the documented out-of-contract backstop path (runtime-api.md:658) — the strongest single demonstration that the compile-time guarantee's boundary is exactly the evolution seam.
- **Example:** `v2 adds `field RenewalRate <- FineAmount / RenewalCount` plus `field RenewalCount ... nonzero` (constraint added in the same edit; compiler accepts — operand carries the constraint). Every v1 entity persisted with RenewalCount = 0 faults during Restore. The entity cannot even be loaded for migration through the engine.`
- **Severity:** high — A Faulted/throwing load path is worse than a refusal: it breaks read-only surfaces, and it converts the product's headline claim ('compiles clean ⇒ cannot fault') into a production fault via a perfectly ordinary two-line edit.
- **Governance catches:** production-later · **Inspector:** no · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Solver-free diff rule: any v2 proof obligation discharged by a constraint that is NEW in v2 (or tightened), on a field that existed in v1, = the proof's precondition is unestablished for persisted data → migration-required. The proof ledger already records which carrier discharged each obligation (§0.6 item 6 attribution), so this is a join between the ledger and the diff — no new reasoning engine.
- **Expressiveness cost:** None — it names exactly the entities/fields to migrate.

### Restore as governance backdoor (fabricated or tampered envelopes)

- **Axes:** where=15 (host integration), interacting with 8 (access modes — explicitly bypassed) · when=Restore (rehydration), then latent until the fabricated state influences a decision; possibly latent-never · who=the business and audit/compliance (an entity 'reached' Approved without satisfying any rule), host developer (the colleague who took the shortcut) · reasoning=none in the engine — requires provenance/integrity reasoning the contract deliberately excludes (spec §0.7 boundary)
- **Description:** Restore validates nothing and bypasses access modes by design (runtime-api.md:266, 272). Any host code can therefore fabricate an arbitrary envelope — state 'Approved', fields set to whatever — and obtain a fully-armed Version indistinguishable from one that earned its state through governance. The envelope carries no integrity marker, no provenance, no definition fingerprint. 'One file, complete rules / not bypassable' is true of Fire/Update/Create and structurally false of the restore door; the guarantee is only as strong as host-side code review of every Restore call site.
- **Example:** `A host developer under deadline writes `precept.Restore("Approved", fabricatedJson)` to unblock a stuck record instead of firing the approval event chain. It works, persists, and is forensically indistinguishable from a legitimate approval.`
- **Severity:** high — Defeats the product's central claim through a documented, supported API — the attack is one line and looks like normal hydration code in review.
- **Governance catches:** never · **Inspector:** no · **Needs universal reasoning:** False
- **Compile-catchable:** undecidable — Undecidable from the .precept (the defect is in host C#). Mitigations are engine-surface, not compile: signed/HMAC envelopes (Restore accepts only what a prior commit emitted), or a host-side Roslyn analyzer flagging Restore calls outside designated repository classes. Worth noting: this class is evidence-neutral between Option 1 and Option 2 — no amount of definition-level compile checking touches it.
- **Expressiveness cost:** Envelope signing costs hydration speed and key management; it trades against the 'hydration is fast, like a database read' commitment in §0.7.

### Wrong-definition restore — no identity binding between envelope and Precept

- **Axes:** where=15 (host integration) · when=Restore (rehydration) — RestoreInvalidInput when shapes clash; latent-never (silent garbage) when field names coincidentally align · who=host developer, downstream data consumer (cross-contaminated data), the business · reasoning=cross-version/cross-definition identity reasoning — does not exist anywhere in the system
- **Description:** The envelope is (state string, fields JSON) with no definition name, hash, or version. precept-builder.md:931 states two Precepts from different Compilations are never 'compatible' — but nothing enforces it: the host can restore an envelope persisted under definition A (or under last month's revision of A) into Precept B, and detection depends entirely on field names failing to line up. Two precepts sharing vocabulary (Status, Amount, CustomerId are ubiquitous) hydrate each other's data silently.
- **Example:** `Host loads rows from the wrong table partition after a refactor; ApartmentRentalApplication envelopes hydrate into HiringPipeline (both have Status/SubmittedDate/Notes). Restore succeeds; rules evaluate against another entity's data.`
- **Severity:** medium — Lower probability than the other classes (requires host wiring error) but silent when it hits, and the engine has explicitly documented the incompatibility while providing zero enforcement of it.
- **Governance catches:** production-later · **Inspector:** no · **Needs universal reasoning:** False
- **Compile-catchable:** solver-free-feasible — Not a compile question — an engine-surface fix: stamp a definition fingerprint (name + content hash) into the persistence envelope at egress and verify at Restore. Solver-free, cheap, and it is also the enabling substrate for every diff-tool class above (you cannot diff against 'the definition this data was written under' unless the envelope says which one that was).
- **Expressiveness cost:** None at the language level; envelope grows by one hash field.

### Stale-snapshot concurrency — lost update through immutable Versions

- **Axes:** where=15 (host integration) · when=production after specific input history — two interleaved operations on the same persisted entity · who=end user (their committed change silently vanishes), the business (wrong data with each individual operation fully governed), host developer · reasoning=none in the engine — per-entity linearization reasoning; the engine's atomicity is per-operation, not per-entity-stream
- **Description:** Version is an immutable snapshot; operations return new instances (runtime-api.md:663). Two host threads each Restore the same entity, each Fire a valid event, each persist: last write wins and one operation's effects vanish — despite both passing governance and both satisfying every rule. §3A.4's atomicity guarantees no invalid configuration persists, but a VALID configuration that silently discards another valid operation's effects persists fine. Optimistic concurrency is entirely the caller's job and nothing in the API (no etag/sequence token on Version or the envelope) even supports it.
- **Example:** `Patron renews online while the librarian adjusts DueDay at the desk. Both Fire against the same restored snapshot; both get Transitioned; the second persist erases the renewal. RenewalCount in storage now disagrees with what the patron was shown and charged for.`
- **Severity:** high — Every concurrent host hits this eventually; the loss is silent and produces business data that no single operation ever created — a determinism-adjacent wound ('same definition + same data' was never the situation).
- **Governance catches:** never · **Inspector:** no · **Needs universal reasoning:** False
- **Compile-catchable:** undecidable — Undecidable from the definition (host architecture). Engine-surface mitigation is standard and cheap: a monotonic sequence/etag on Version carried through the envelope, with Restore-then-persist compare-and-swap left to the host but made possible. Evidence-neutral between Option 1 and Option 2.
- **Expressiveness cost:** None at language level; one token field on Version and the envelope.

### Outcome mishandling — non-exhaustive variant handling and persisting inspection results

- **Axes:** where=15 (host integration), interacting with 10 (event outcome space) · when=Update/first Fire (the mishandled outcome occurs immediately; the damage persists as wrong stored state) · who=end user (told 'saved' when refused, or vice versa), the business, host developer · reasoning=none in the engine — host-language exhaustiveness checking (a Roslyn concern, not a precept concern)
- **Description:** EventOutcome/CreateOutcome/RestoreOutcome are sealed DU hierarchies (result-types.md) but C# does not force exhaustive handling. Failure shapes observed as risks: host matches only Transitioned and silently drops Applied (the stateless/hook success variant) so successful operations never persist; host treats Rejected's presence of FiredArgs as success-ish and logs-and-continues; host persists the Version embedded in an EventInspection (inspection shares the commit pipeline by design, evaluator.md §12 — its snapshots look exactly like committed ones) writing never-committed state to storage.
- **Example:** `switch (outcome) { case Transitioned t: Save(t.Result); break; default: return Error(); } — a stateless precept's Applied outcomes all hit default; every successful update is reported as an error and never saved.`
- **Severity:** medium — Common integration bug shape; the inspect-vs-commit confusion is elevated here specifically because Precept's design makes inspection results deliberately indistinguishable in shape from commit results.
- **Governance catches:** never · **Inspector:** no · **Needs universal reasoning:** False
- **Compile-catchable:** today — Not .precept-compile territory. Feasible today as shipped host-side tooling: a Roslyn analyzer (the repo already has an analyzer project, test/Precept.Analyzers.Tests/) enforcing exhaustive outcome matching and flagging persistence of inspection-sourced Versions (type-distinguishable if inspection snapshots get a distinct wrapper type — an API-surface change).
- **Expressiveness cost:** None; an inspection-result wrapper type adds one unwrap call at host sites.

### Hydration-path divergence — FromJson keeps stale computed values, Restore recomputes

- **Axes:** where=15 (host integration), interacting with 4 (computed fields) · when=Restore (rehydration) — divergent values visible immediately after load depending on path taken · who=host developer (two documented paths, two answers), downstream data consumer · reasoning=concrete evaluation exposes it only if someone compares the two paths; otherwise canon-level reasoning
- **Description:** evaluator.md ('Computed Field Freshness in Restored Versions') documents that FromJson populates computed slots from persisted values without recomputation — freshness is a caller concern — while entity-level Restore recomputes computed fields first (runtime-api.md:266, Precept.cs:117 remarks). Two sanctioned hydration paths produce different field values for the same envelope whenever the formula or its inputs drifted. A host mixing paths (bulk import via the primitive, interactive load via Restore) gets fleet-internal inconsistency with no error.
- **Example:** `Nightly ETL rehydrates via the FromJson primitive (stale TotalDue = 12.50 from storage); the web app restores via Restore (recomputed TotalDue = 17.50). The two surfaces show different balances for the same record on the same day.`
- **Severity:** low — Real but narrow: requires both paths in one host plus computed drift. Worth recording because it is a contract-internal inconsistency, not a host error.
- **Governance catches:** never · **Inspector:** no · **Needs universal reasoning:** False
- **Compile-catchable:** today — Resolvable today by an engine contract decision, no reasoning needed: either exclude computed fields from the canonical envelope (always recompute) or make both paths recompute. The current split is design debt, not an inherent limit.
- **Expressiveness cost:** Excluding computed fields from the envelope loses the ability to audit 'value as persisted' — minor, and arguably correct.

### Dormant-entity temporal stranding — clock-dependent truth decays while persisted

- **Axes:** where=15 (clock time as implicit input) intersecting restore, 5 (rules), 13 (now()) · when=after clock time passes — entity restores fine (trusted), then constraint-time refusals on every operation because a now()-referencing constraint went false during dormancy · who=end user, the business (long-dormant records become inoperable in bulk, e.g. after a system outage or seasonal lull) · reasoning=universal over time — 'is this constraint's truth monotonically decreasing in now(), over a field set the entity cannot edit in its state'; does not exist today
- **Description:** A constraint comparing a stored temporal field against now() (spec §1599: now() → instant) is true at persist time and false after enough wall-clock passes. No operation occurred; the entity just aged. On the next operation §3A.4 sweeps ALL constraints, including the decayed one, and refuses — even for operations unrelated to the temporal field. If the temporal field is readonly/omitted in the current state, the entity is permanently stranded by the calendar. Corpus note: samples mostly model time as explicit day-counter fields (corpus is a floor, not a ceiling — real authors will reach for now()-style deadlines).
- **Example:** ``rule ResponseDeadline > now() because "an open ticket must have a live deadline"` with ResponseDeadline editable only in Triage. A ticket persisted in InProgress sleeps over a holiday week; afterwards every operation — even adding a comment — returns ConstraintsFailed, and the deadline cannot be edited in InProgress.`
- **Severity:** high — Strands entities with zero operations and zero deploys — purely by time passing — and the refusal blocks even remediation operations. It is also invisible at authoring: the definition is satisfiable at every instant, just not by aging data.
- **Governance catches:** production-later · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** True

### Access-mode tightening orphans stored values and blocks remediation

### Event-contract drift versus host call sites — no typed binding between host code and definition

### Dead quantified guard — quantifier predicates excluded from guard-satisfiability reasoning

- **Axes:** where=11 Quantifiers & binding × 7 Transitions, guards & outcomes × 3 Collection inner-type constraints · when=compile (catchable with existing interval machinery, not caught today) — otherwise production after specific input history: the row never matches (Unmatched forever) and the target state is semantically unreachable · who=End user (operation that should complete the entity never fires), the business (stranded process — sole terminal unreachable, entity trapped permanently), author (ships believing the lifecycle completes) · reasoning=Guard satisfiability over quantifier bodies via numeric interval on the declared element band + count interval — DOES NOT EXIST TODAY. PRE0082/PRE0159 fold scalar field constraints only; PROBE-VERIFIED that quantifier predicates are never analyzed: 'from Open on Close when any y in Items (y > 100)' with Items 'set of integer max 50 maxcount 10' and the only write source an arg bounded [0..50] compiles success:true, ZERO diagnostics, IntervalContainment AND CountContainment both Proved — yet the guard is provably unsatisfiable and Done (the only terminal) is unreachable. The always-empty variant (collection with no write site anywhere ⇒ 'any' identically false) also compiles clean drawing only the incidental PRE0158 warning.
- **Description:** A transition guard containing a quantifier whose predicate is refuted by the collection's declared element band (or whose collection is provably always empty) is permanently dead. The runtime never errors — the event is simply Unmatched on every fire, forever — so the defect presents as a mysteriously stuck entity, not a refusal with because-text. The corpus has ZERO real quantifier usage (grep over all samples: both hits are prose comments), which is exactly why all five prior vantages skipped this region — corpus bias, not evidence of low value: quantified guards over collections ('approve when any line item exceeds the threshold') are a natural domain-expert idiom the moment quantifiers see real use.
- **Example:** `field Items as set of integer max 50 maxcount 10
event AddItem(Value as integer min 0 max 50)
from Open on AddItem when Items.count < 10 -> add Items AddItem.Value -> no transition
from Open on Close when any y in Items (y > 100) -> transition Done   # band is [0..50]; guard provably never true; Done is the only terminal`
- **Severity:** critical — Stranded-process defect: the sole terminal is unreachable and the entity is a permanent trap, with no runtime signal of any kind (no refusal, no fault, no diagnostic — just Unmatched forever). Late detection means deployed business processes that structurally cannot complete, discovered only after entities pile up stuck.
- **Governance catches:** never · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Extend the existing satisfiability scan (PRE0153/0154/0155/0159 family) to descend into QuantifierExpression: fold the predicate against the element interval already computed for IntervalContainment (declared inner-type bounds ∪ write-site arg bands) and the count interval (emptiness). 'any' folds false when the predicate is band-refuted for every element OR the collection is provably always empty; 'each'/'no' fold dually. Single interval comparison per predicate — the same solver-free machinery PRE0082 uses today, pointed at a new expression position. Per-scenario note: the inspector shows the symptom (Close unmatched) on any attempted scenario, but cannot display the universal fact 'no reachable collection content EVER satisfies this guard' — the author sees 'not yet', not 'never'.
- **Expressiveness cost:** None — pure additional analysis on existing syntax; flags only provably-dead guards, rejects no currently-meaningful program.

### Vacuous quantified rule — silent non-protection over empty or band-implied collections

- **Axes:** where=11 Quantifiers & binding × 5 Rules & ensures (+ 3 Collection inner-type constraints for the band-implied variant) · when=latent-never (the rule never constrains anything across the entity's whole life); also Create — every collection without population is default-empty, so 'each' passes vacuously at birth and the entity is born 'valid' · who=The business and audit/compliance (a believed, documented protection that has never once evaluated against an element), author (false confidence), downstream data consumer (data assumed rule-governed is not) · reasoning=Vacuity reasoning over quantifier bodies and collection emptiness (quantified twin of scalar PRE0154 vacuity) — DOES NOT EXIST TODAY. PROBE-VERIFIED: 'rule each x in Items (x > 0) because ...' with Items having no write site anywhere compiles success:true with only the incidental PRE0158 no-write-site warning; PRE0154's fold never enters quantifier bodies.
- **Description:** A quantified 'each' rule over a collection that is provably always empty — or whose predicate is already implied by the declared inner-type band (e.g. inner 'positive' with predicate x > 0) — is vacuously true on every constraint sweep, including at Create. The mandatory because-text documents an invariant the engine never enforces. PRE0158 is only an adjacent warning and disappears the moment ANY write site exists, even one on an unreachable path. Corpus has zero quantifier usage, so all prior vantages skipped the cell — corpus bias. - **Example:** `field Items as set of integer
rule each x in Items (x > 0) because "Every item must be positive"   # no write site anywhere: vacuously true on every sweep, forever; compiles success:true (PRE0158 only)`
- **Severity:** high — Silent non-protection: the author and auditors believe an invariant is governed when it has never evaluated against a single element. No business data is corrupted by the rule itself, but the protection gap it masks is invisible until the day real elements arrive through a path the author never wired — at which point the rule may also be wrong, untested by construction.
- **Governance catches:** never · **Inspector:** no · **Needs universal reasoning:** True
- **Compile-catchable:** solver-free-feasible — Same fold as the dead-quantified-guard class, applied at rule/ensure positions: 'each' over a provably-always-empty collection (no write site, or count interval pinned to [0..0]) ⇒ vacuous-rule diagnostic; predicate implied by the element band ⇒ the quantified twin of the existing PRE0154 always-true fold. - **Expressiveness cost:** None — warning-class diagnostics on existing syntax; authors who genuinely want a forward-looking rule over a not-yet-populated collection see a suppressible warning at worst.

### Qualifier-source field mutation reinterprets dependent stored values (dynamic qualifier in '{X}')

- **Axes:** where=1 Field declarations (single-component interpolated qualifier bases) + 14 qualifier chains × 8 editable/set surface × 7 transition actions · when=Update / Fire — the qualifier-source write commits cleanly at constraint-time; felt in production-later as silently wrong business data, or as a backstop fault on the next arithmetic touching the dependent field (which branch is unspecified in canon) · who=The business (silently wrong money/quantity data — magnitudes meaning a different currency/unit than written), downstream data consumer, audit/compliance, host developer (unexplained backstop fault far from the causal write) · reasoning=Qualifier-dependency reasoning over writes: a static obligation on any write targeting a field that serves as a qualifier base of dependent stored fields — DOES NOT EXIST TODAY for the write direction. The ingress direction IS proof-gated (PRE0141 verified live: depositing a value into 'money in {CurrencyCode}' demands a narrowing guard). PROBE-VERIFIED asymmetry: 'set CurrencyCode = Switch.NewCode' while Amount holds money in '{CurrencyCode}' compiles success:true, ZERO diagnostics, QualifierCompatibility obligation Proved.

- **Governance catches:** production-later · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** False

### Semantic accessor mischoice — .first/.last vs .min/.max vs .peek across collection ordering semantics

- **Axes:** where=12 Presence & collection access (accessors) × 1 Collection kinds (list insertion-order / ordered value-sort / queue-by priority ordering semantics) · when=production after specific input history — the wrong-but-in-band element feeds a guard, computed field, or assignment, and every constraint sweep passes · who=End user (wrong element drives a wrong refusal or wrong transition), the business (wrong data committed in-band), author (intent mismatch invisible to every check) · reasoning=Concrete evaluation / per-scenario simulation — the live inspector DOES catch the symptom whenever the author constructs a history where the chosen accessor and the intended one diverge (.first ≠ .min). - **Description:** Type-correct, band-correct, in-band wrong: '.first' on an insertion-ordered list where the author means the smallest value (.min); '.peek' on a 'queue of T by P' assumed FIFO when it is priority-ordered; '.last' as 'most recent' on an 'ordered' (value-sorted) collection where sort order broke the recency correlation. Every sweep passes because the retrieved element is a legitimate member within all declared bounds. Honest scoring against the bar: this class FAVORS Option 1 — it is the inspector paradigm's sweet spot (a distinguishing two-element scenario exposes it immediately) and compile-time reasoning is structurally unable to help beyond authoring-surface mitigation.
- **Example:** `field Requests as queue of integer by Priority
from Triage on Serve when Requests.peek > 0 -> ...   # author assumes FIFO arrival order; .peek returns highest-priority — type-correct, in-band, wrong element`
- **Severity:** medium — Real wrong-data/wrong-routing impact, but bounded: every other declared constraint still holds over the wrong element, the wrongness is confined to ordering-sensitive logic, and a single distinguishing inspection scenario reveals it.
- **Governance catches:** never · **Inspector:** only-if-author-tries-right-scenario · **Needs universal reasoning:** False
- **Compile-catchable:** undecidable — Intent mismatch — not statically decidable.
