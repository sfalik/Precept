No exception is stated. The schema's defined-cell conditional (cell.schema.json:396) requires `["id","label","coordinates","disposition","citations","obligation","applicablePremiseClasses","dischargeContract","witnesses","respellability"]` — `suggestions` is absent from the list. In the data, `wf1/preservation-reads-written-decrease` and `wf1/preservation-reads-written-increase` carry no `suggestions` key at all. The README codifies the deviation ("`suggestions` — … Recorded only where the matrix states it", README.md:30) — but the matrix's Vocabulary states the per-class suggestion schemas generally ("add a guard normal-form-equal to `⟨WP⟩`"; "bound the args…"), and Base A's data already instantiates exactly those Vocabulary texts, so Bases B and C are derivable the same way. Fix: add `suggestions` (minItems 1) to the defined non-structural required list, populate B and C, and delete the README sentence.

**2. [HIGH — blocking] The witness-triple minimum is neither schema-enforced nor claimed by the README's validator-ownership list — several matrix-mandated validator checks are currently unowned.**
Matrix, "The cell" item 4: "**Witnesses** — at least one concrete triple: Base … Discharge addition(s) … Near-miss, one per discharge addition." The schema's `witnesses` object has no required properties and `discharges` has no `minItems` — a defined rule-write cell with `"witnesses": {}` validates. That permissiveness is fine **only if** the validator owns the check, and the task's own criterion is that the README must say which invariants the validator owns vs the schema. README.md:38 lists exactly three validator-owned rules ("near-miss-per-addition pairing, disposition totality over the full axis product, citation resolution") — omitting: base presence and ≥1 discharge on defined cells (with the establishment standing-discharge exception the author correctly flagged as ambiguity), contract-entry coverage of every class in `applicablePremiseClasses`, cell-id uniqueness within and across files, `respelling` required when the resolved verdict is yes and a `bandMember` is stated (the schema itself says "required in spirit", cell.schema.json:341 — "in spirit" is not an owner), evidence/corpusMeasurement consistency, and three checks the matrix's Storage ruling explicitly assigns to the day-one validator: axis values cross-checked against built catalogs, validity-argument presence per cited rule, and **WP recomputation where mechanized** (the `canonicalKey` hook exists precisely for this, yet the README never names recomputation as a validator duty). As written, a deliberately-wrong cell (defined, empty witnesses) passes the schema and no documented check catches it. Fix: extend the README's validator-owned list to be exhaustive against the matrix's Storage checklist plus the schema's known permissive spots; optionally add cheap schema tightenings (`minItems: 1` on `dischargeContract` for defined cells).

**3. [MEDIUM] Provenance scope is ambiguous on discharges whose expected outcome contradicts their built status.**
Data, `wf1/preservation-reads-args` discharge `guard-nf`: `"expected": { "outcome": "accept" … }` with `"builtStatus": "unresolved-today"` and `"provenance": { "mark": "live-verified", … }`. The live run at `ed57d7fd` demonstrated the engine does **not** prove this addition — what was live-verified is the *unresolved-today status*, not the acceptance. The schema's description ("How this record was verified", cell.schema.json:71) lets a cell→test generator read `live-verified` + `outcome: accept` as an already-verified green — the exact false-green failure mode the matrix's test-basis discipline exists to prevent. The matrix's ✓v mark attaches to the status text ("Unresolved today ✓v"); the schema flattened that attachment away. Fix: state in the provenance description (or an explicit field) that on a discharge witness, provenance attests the `builtStatus` claim, while `expected` is committed-power under the model.

**4. [MEDIUM] Citation `ref` is a single free-text field mixing resolvable paths and unresolvable prose anchors — the ratification protocol requires citations "present **and resolving**".**
Schema: `"ref": "…a repo path with an optional :line suffix, or a section name inside the cited document"` (cell.schema.json:56). Data instances like `"docs/Working/obligation-discharge-matrix-2026-07-19.md § Vocabulary (sound-but-unprovable band)"` and `"§ Witness Family 1 (respellability paragraph)"` name parenthetical sub-locations that are not headings in the matrix (Vocabulary's band ruling is a bullet, not a section) — no machine can decide whether such a ref resolves or is a typo, so the validator's "citation resolution" duty (README.md:38) is undischargeable for roughly half the refs, and at 3,500 cells this is the dominant citation form. Fix: split into structured fields (`path`, optional `line`, optional `anchor` drawn from a pinned anchor list), or pin a machine-checkable anchor convention now, before 3,500 cells are authored against the free-text form.

**5. [MEDIUM] `validityArgument`, `derivation`, and `strategy` are free strings where finite named vocabularies already exist.**
The matrix's validity arguments are a closed, named set (its § Validity arguments headings); "Derivation class" is defined as "the closed 21-member `CertificateStepKind` vocabulary plus the 11 `CertificatePremise` kinds"; `strategy` is "the `ProofStrategy` enum". The schema types all three as bare `"type": "string"` (cell.schema.json:212-215). Consequences visible already in Family 1: the establishment contract rests on **two** named validity arguments ("Literal constant-fold for defaults" and "Establishment over defaults") but the single-string field carries one, demoting the second to a citation note — and the ratification gate ("a validity argument present for every rule the cell's derivation cites") becomes string-matching against prose. The matrix's Storage ruling does accept an interim before catalog anchors land, but the validity-argument names and ProofStrategy members exist *today*. Fix: make `validityArgument` an array of names validated against an enumerated list (maintained in the schema or a sidecar vocabulary file), and note the intended enum anchors on `derivation`/`strategy`.

**6. [MEDIUM] Minting-dependency markers have no structured representation on defined cells.**
Matrix, minting rule: "A change to any ⧖ part changes which cells exist; **the matrix records the dependency** instead of absorbing an answer" — and Base B's validity argument names S4/Q5/computed-transitivity as load-bearing open dependencies of premise (d) ("a missed write site voids the hypothesis for every cell that consumes premise (d)"). The schema records ⧖ items only via `disposition.citations` on *open/deferred* cells; a **defined** cell's dependency on an open item lands in free-text `notes` at best — and the Base B cell's notes don't record the S4/Q5 dependency at all (they record the class-(c) ambiguity only). When an ⧖ ruling lands, the affected defined cells cannot be found mechanically across 3,500 records. Fix: an optional `openDependencies` array of Q/S identifiers on the cell (and on contract entries), populated for Base B now.
