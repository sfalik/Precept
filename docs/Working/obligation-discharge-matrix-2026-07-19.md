**Premise reviews applied**: `obligation-discharge-matrix-2026-07-19-reviews/` (review-1 factorization-soundness, review-2 definition-fitness, review-3 field-precedent). Their amendments are folded into the text below; the reviews are not restated here.

## Purpose

**The exhaustive definition of the proof engine** — cell by cell, with no silent cells. For every combination the proof surface admits, the matrix carries an explicit written answer to "what must the compiler do here?" A cell with no answer is a definition gap by construction. The want doc put this on the right path: it supplies the model the drafting starts from, and the matrix is the form the finished definition takes — not a commentary on the want doc.

A matrix of examples is not a definition. What makes this one a definition is that a small, finite set of written rules determines every cell's answer. Those rules — the Vocabulary, the case shapes, the minting rule, and each cell's schema and discharge contract — are what this document calls the **generative sections**: the finite rules from which every cell's answer must be derivable. The witnesses are their worked instances. If a cell's answer cannot be derived from the generative sections, a rule is missing and must be authored **here** (owner-ruled) — never asserted ad hoc in the cell.

The matrix is structured top-down from the full language surface. Every axis is sourced from a catalog, the spec, or the want doc, or is explicitly marked as a prose taxonomy pending a catalog anchor. No axis is generalized from a worked example. The numeric single-field slice that seeded rev 1 survives below as Witness Family 1, retyped as witnesses of cells — not as the source of the structure.

A second use is as a test basis — every defined cell converts mechanically into reject/discharge/near-miss tests — but that follows the definitional pass; see the final section.

## Authority

(Restated under the owner's 2026-07-19 ruling on this document's destiny.)

- **During drafting: the want doc defines; the matrix drafts against it.** Every defined cell's answer must be derivable from the want doc plus this document's own generative sections. A conflict between a cell and the want doc routes to the owner — it is never resolved silently in either direction.
- **At ratification: the matrix becomes the canonical proof-engine definition.** The want doc is superseded for the proof-engine surface, and subsequent conflicts elsewhere in canon are corrected *to the matrix*. Ratification is an owner act (the promotion lifecycle), not a drafting outcome.
- **Generative sentences over cell assertions.** If a cell's answer cannot be derived from the generative sections (Vocabulary, case shapes, minting rule, discharge contracts), that is a missing rule to author here with an owner ruling — never a bare answer written into the cell. This keeps the definition generative: finite rules determining unboundedly many programs. That property is what earns a matrix the name "definition" at all.
- **Citation duty during drafting**: every defined cell cites the want-doc sentence(s) — or the owner ruling — that its obligation and premise availability derive from. Edge cells already carry this duty. At ratification these citations become the record of derivation.

## Vocabulary

Two working terms used throughout, defined up front:

- To **discharge** an obligation is to satisfy and close it — the proof for it is finished.
- A premise or spelling is **licensed** when one of the written derivation rules accepts it. "Licensed" never means anything looser than that.

The terms of the definition:

- **Constraint** — the umbrella term for everything the engine must keep true of the data. Precept has five constraint forms, and the term "constraint" covers all of them; "rule" means the specific `rule` construct only, never the general sense (owner ruling, 2026-07-20 — see Constraint kinds below).
- **Obligation family** — what must be proven. Three families come from the want doc: constraint establishment (want :18), constraint preservation (want :19), and fault prevention (want :104). (The want doc says "rule" where it means the general sense; that wording is corrected in the canon-correction pass.) The constraint families are *not* catalog-enumerated today: the `ProofRequirement` DU (`docs/compiler/proof-engine.md:529-543`) carries numeric/presence/dimension/modifier/qualifier/containment/key-presence/index-bounds/dimensional-product/assignment-qualifier kinds, and has **no constraint-establishment or constraint-preservation subtype**. Those catalog entries are to be added when the constraint-obligation machinery is designed (packet §(a)1). The fault family, by contrast, *is* catalog-enumerated (same DU; `docs/compiler/soundness-and-coverage.md` §3.1 carries the per-FaultCode enumeration). Establishment's site set is construction (defaults + initial events, want :18) **and every entry into a state carrying a residency ensure** (owner ruling, 2026-07-20 — the engine establishes residency ensures over the initial state only today, which is narrower than the definition; see Constraint kinds).
- **Premise classes** — where a proof is allowed to get its facts. There are **four**, all from the want doc (want :19): (a) field modifiers, (b) arg constraints, (c) the handler's guard, (d) all constraints holding in the pre-state (the inductive hypothesis). Each is a fact the author wrote that a derivation *consumes*. The evaluation of the applicable constraint set at an editable-field write (want :143) — which earlier revisions labelled a fifth class "(e)" — is **not** a premise class (owner ruling, 2026-07-20): nothing consumes it, because it *is* the discharge. It is a discharge mechanism, listed with the others below.
- **Discharge mechanisms** — the named ways an obligation gets closed. They include constant folding, interval derivation over declared bounds, guard matching and substitution, and — added by the 2026-07-20 ruling — **ingress evaluation**. Ingress evaluation is the governance that runs at a door where a value enters the entity and checks it against the applicable constraints before it can be committed. The event door and the editable-field door are the same mechanism at two places: the spec already unifies all ingress under governance (`docs/language/precept-language-spec.md` §0.7, :262-272). This is why the event door is not a premise class either — it is the mechanism that *makes* premise (b) true, and by the same symmetry the editable-field door makes premises (a) and (d) true for that field downstream.
- **Governance discharge is a complete compile-time proof, not a deferral.** When ingress evaluation discharges an obligation, the compiler proves *at compile time* that the write site is governed by an ingress check sufficient for the constraint — a finite set-equality check over the definition's own text (Family 3, below). Nothing about the obligation is left for runtime to decide. Reading this as deferral would be a misreading: no-deferral forbids shipping an unproven obligation, and here the obligation is proven.
- **Obligation schema** — an obligation written with placeholders instead of specific names. The placeholders (metavariables) stand for the field, the bound, the arg, the expression shape; matching is done under the normalization below. Two programs sit in the same cell iff — exactly when — their minted obligations unify with the same schema, differing only in how the placeholders are filled in. This is a syntactic criterion: it can be checked without running the prover.
- **Normalization** — two spellings count as the same when they are equal after the stated rewriting steps. The steps stated so far: flip the comparison direction (`a <= b` ≡ `b >= a`), and reorder the operands of commutative operators. Schema matching and guard-fact matching are defined up to this normal form, and "verbatim" is replaced by **normal-form-equal** — equal after those rewriting steps — throughout. The full normal form (beyond these two rules) is an open item for the canonical doc. A cell's *base* is a representative of the schema class under this normalization; diagnostics that quote source quote the author's text, not the representative's.
- **Discharge contract** — the exact statement of when an obligation counts as proven, stated per premise class. The contract is **exact**: an obligation discharges **iff** a premise instantiating an applicable class lets a defined strategy/step-kind derivation close the proof condition (owner ruling, 2026-07-19). In plain terms: the compiler accepts a program only when a fact the author wrote lets one of the defined derivations finish the proof — and it accepts exactly those programs, no more. The contract is relative to the premise class and the strategy, not to any particular added line of source. And it pins the accepted set exactly, not as a floor: a compiler that accepts a program the contract does not license is nonconforming, even if the program is semantically sound. Rationale: a floor-only contract lets a smarter build accept more sound programs than the definition names, so two conforming compilers (or two versions) disagree on which files compile — breaking determinism and the uniform guarantee through the back door. Proof power is *defined*, not bounded below. **Each contract must also name its decision procedure or search bound** (owner-approved 2026-07-19): the concrete finite check that decides "no licensed derivation exists" — e.g. normal-form match against the row's guard set, interval arithmetic over declared bounds, bounded enumeration of applicable premises. Without one, the reject side of the contract cannot be tested even in principle.
- **Sound-but-unprovable band** — the programs that are actually safe but that none of the written rules can prove. Precisely: the programs in a cell's class that are semantically sound but that **no defined derivation** licenses. Membership is judged against the cell's full derivation set, not against any single derivation: a guard that fails whole-condition matching may still discharge by another defined derivation — per-term bound conjuncts (`term op constant`) feed the same interval arithmetic that discharges arg-modifier bounds, wherever they are spelled (owner ruling, 2026-07-19). What lands in the band is spelling that no bounded derivation covers — algebraic rearrangement (a term moved across the inequality, both sides scaled) — not alternate spellings of covered premise shapes. Under prove-or-reject the band is rejected by design. It is the cell's honest measure of what proof power costs.
- **Respellable** — a verdict on the sound-but-unprovable band: can every safe-but-unprovable program be rewritten into a form the rules do prove? The verdict is stated **once per contract family** and inherited by every cell the family's contracts govern; a cell may override the family verdict only with a more specific one (owner-approved 2026-07-19). The verdict is **yes** iff every sound program in the band has a provable respelling within the surface — a spelling of the same business intent that the contract licenses, typically the suggestion schema's output. Respellable: yes means the power gap costs authoring friction only, which the want doc deliberately embraces ("forces authors to be more explicit," want :137). Respellable: no means the power gap is an expressiveness loss — a surface-shrink decision routed to the owner, since the guarantee is non-negotiable and the surface is the negotiable part (want :190). The evidence standard is the corpus measurement in the ratification protocol (layer 4, below): a family verdict ratifies only when it agrees with the classified sample corpus, never on paper argument alone.
- **Suggestion schema** — what the diagnostic must suggest when the proof fails, stated per applicable premise class and as a schema, not a constant ("add a guard normal-form-equal to `⟨WP⟩`"; "bound the args such that the interval combination satisfies `⟨WP⟩`"). When several classes can discharge, the diagnostic names **all applicable classes**. **Owner ruling 2026-07-19**: an author-invoked editor quick-fix that inserts the suggested premise **counts as the author writing it** — the language server's code-action pipeline may carry these suggestions as one-click fixes. What the want doc's "never inserts the premise itself" (want :179) forbids is *silent or automatic* insertion; the sentence is scoped accordingly in the canon-correction pass.
- **Witness** — a concrete example recorded in a cell: a base program, a discharge addition, or a near-miss. The examples illustrate the rules; the rules decide. A witness is never itself the definition.
- **Near-miss** — a discharge addition deliberately weakened past the point of sufficiency: a bound loosened past the arithmetic, a guard on the wrong condition. Required outcome: the compiler still rejects, naming the **same obligation**. Both verdict polarities — must-accept and must-reject — are first-class.
- **Write plan** — the row's action sequence, which may contain more than one write. Obligations are defined over the **whole write plan** and never per individual write (owner ruling, 2026-07-20): a constraint's preservation obligation runs from the pre-state to the post-state, and the intermediate states between individual writes are unobserved. The reason is the runtime's own commit model — the handler mutates a working copy that is committed atomically (`precept-language-spec.md:1967`), so no reader, no later handler, and no persistence ever sees a mid-handler state. A mid-handler state is not a reachable configuration, and the induction that premise (d) rests on ranges over reachable configurations only. Consequences: the weakest precondition of a multi-write plan is computed by **backward substitution through the writes in reverse order** — defined mechanics, not an open question; cells are keyed **per handler**, carrying the combined condition, not one cell per write. Carrying a guard fact through the prior writes of a plan is a real derivation step (a certificate step, not a matrix column). Separately and unchanged: an expression later in a plan does see the results of earlier writes (`precept-language-spec.md:164`), and its own fault obligations are minted per evaluation site — that is a fault-family question about where values come from, not a decomposition of the preservation obligation. **Known divergence to correct**: the shipped compiler checks preservation per individual write, which is stronger than this definition licenses — it can reject a plan whose intermediate state breaches a constraint the post-state restores. Under the exact-power contract, accepting *or* rejecting differently from the definition is nonconforming, so this is corrected when implementation resumes. One thing the ruling does not settle, and which is not a definitional question: how a failed multi-write proof reports — whether the diagnostic can point at an individual write inside the plan, or names the handler. That is diagnostic quality, decided when the diagnostic is built.
- **Derivation class** — the certificate step kinds a proof may be built from: the closed 21-member `CertificateStepKind` vocabulary plus the 11 `CertificatePremise` kinds (`docs/Working/certificate-steps-membership-2026-07-12.md`, Decisions 1 and 4, :333/:389). The §1a/§1b boundary (`proof-engine-mvp-and-proof-phases-2026-07-12.md` §1a/§1b) is retained as a **capability-tier annotation** on a cell, not as the derivation vocabulary.
- **Strategy** — the predicate that realizes a discharge (`ProofStrategy` enum, `src/Precept/Pipeline/ProofLedger.cs:100`). The built/unbuilt status of the required strategy separates "provable under the model" from "proven today."

## Constraint kinds — the five forms the proof surface covers (owner ruling, 2026-07-20)

Precept has five constraint forms, and **all five are proof surface**. They are peer forms on their own axes, not spellings of one another: `docs/Working/ensure-vs-rule-analysis-2026-07-20.md` establishes, with a live compile, that the supposed rewrite `rule X when state is S` is **inexpressible** — `state` is a reserved keyword and the expression grammar has no state-test operator. So ensures must **not** be modelled as conditional rules over a state coordinate; that framing is refuted, and any cell written against it is wrong.

| Surface form | Constraint kind | When it must hold | Obligation shape |
|---|---|---|---|
| `rule` | Invariant | always, after every mutation | established at construction; preserved by every write site of every mentioned field |
| `in S ensure` | StateResident | while resident in `S` | **established at every entry into `S`** — not only the initial state — and preserved by every write that happens during residency |
| `to S ensure` | StateEntry | on the transition into `S` | a transition-moment obligation on the entering row: the post-transition configuration must satisfy it |
| `from S ensure` | StateExit | on the transition out of `S` | a transition-moment obligation on the leaving row |
| `on E ensure` | EventPrecondition | against `E`'s arguments before any mutation | ingress-class: the same door governance that makes premise (b) true, applied to a whole condition over the args |

Two things this changes from earlier revisions. First, residency establishment is broader than what ships: today the engine folds residency ensures against defaults for the **initial state only** (`ProofEngine.Analysis.cs`, per the analysis doc's § 3), which is narrower than the definition, and that gap is implementation work, not a definitional limit. Second, the "activation sites" question — whether a no-write transition into a state whose ensure the unchanged data violates carries an obligation — is answered **yes**, by the establishment-at-every-entry rule. There is no open marker left on it.

The kinds also carry distinct attribution (`rule` → fields and definition scope; state ensures → fields plus the anchor state; event ensures → args plus the event), which is why collapsing them would lose provenance. Attribution is a diagnostic property, not a proof-power property, but the matrix records it because a cell's required rejection names the obligation, and the obligation is anchored.

## The cell

A **defined cell** is:

1. **Obligation schema** — the site's proof condition with metavariables, under the stated normalization. For the constraint families this is the constraint's **weakest precondition (WP)** through the whole write plan: the condition that must be true before the plan's writes run for the constraint to hold after them (computed by backward substitution through the writes in reverse order when there is more than one). For the fault family it is the catalog-declared safety precondition at the evaluation site (see case shapes below).
2. **Discharge contract, per applicable premise class** — which classes can discharge the obligation, and by which strategy/derivation class. The applicable-class set is a per-cell fact derived from the axes (see the read-set axis).
3. **Suggestion schema, per applicable premise class** — naming all applicable classes when several can discharge.
4. **Witnesses** — at least one concrete triple:
   - **Base** — a representative program the compiler must flag. It rejects naming the schema's obligation and the missing premise classes, with no other diagnostics (base minimality: the base rejects *only* for the target obligation).
   - **Discharge addition(s)** — instances of the discharge contract. Base + addition compiles clean via the expected strategy, premise list recorded.
   - **Near-miss, one per discharge addition** — the addition weakened past sufficiency. Still rejects, same obligation named.
5. **Respellability** — the `respellable: yes/no` verdict the cell resolves to: inherited from its contract family unless the cell states a more specific override (Vocabulary), with a representative band member and — if yes — its licensed respelling. `respellable: no` routes to the owner as a surface decision.

The cell triple (theorem, premises, derivation) is deliberately the same shape as the certificate record the want doc specifies (want :199). **Scoping**: the cell triple is the certificate's *schema and index* — same theorem, same premise list, same step-kind vocabulary. The certificate additionally carries the fine-grained step-by-step derivation (want :206) that the cell only names. The matrix must never be read as fixing the certificate's payload granularity.

**The matrix as the measure of proof power.** Under no-deferral, "what the engine proves" and "what an author can write" are the same boundary, and the exact discharge contracts draw that boundary cell by cell. Power is measured from both sides: the contract from below (must prove exactly these), the near-miss rows from above (must not accept these). The sound-but-unprovable band between them is the cost, kept honest per cell by the respellability verdict. The contracts state *committed* power — what the definition obliges. The witness status column tracks *built* power separately. The two are never conflated.

**Verification asymmetry** (owner-approved 2026-07-19): the two halves of the exact contract are verified by different machinery. The accept half is certificate-verified — every acceptance carries a walkable derivation, checked at both call sites. The reject half is **not certifiable**: a rejection carries no certificate of non-derivability, so nothing at load or in production ever confirms a rejection was correct, and a compiler that silently under-proves (rejects licensed programs) passes every certificate check. Reject-side conformance is verified **only** by the cell-generated test matrix — base, near-miss, and deletion rows run against the named decision procedures. The cell→test conversion is therefore part of the definition's verification machinery, not a convenience, and its coverage bar is set accordingly.

## Axes

Each axis names its source. No axis is induced from an example.

### 1. Obligation family (want-derived; catalog entries pending)

Establishment / preservation / fault prevention — want :18, :19, :104, as defined in Vocabulary. The structural family is deliberately **not** on this axis; it gets its own case shape (below), and the completeness claim is scoped accordingly.

### 1b. Constraint kind (source: the `Constraint` catalog — five `ConstraintKind` members)

`rule` (Invariant) / `in S ensure` (StateResident) / `to S ensure` (StateEntry) / `from S ensure` (StateExit) / `on E ensure` (EventPrecondition), per the section above. Applies to the constraint families only. Unlike the structure axis below, this one **is** catalog-enumerated (`Constraint.cs`).

### 2. Constraint structure (prose taxonomy — catalog anchor pending)

Single-field / relational / conditional (`when`-activated, want :40) / quantified (`collection-types.md:796`; ⧖ Q10 — whether quantified constraints are proof surface at all is open) / non-linear (want :105, :135) / temporal (want :219; ⧖ Q14a — whether time-referencing constraints exist at all is deliberately open). Constraint conditions are authored expressions, not catalog members, so this axis has no catalog enumeration today. The anchor should eventually be the expression-shape classification the constraint-obligation design produces. Applies to the constraint families only, and is orthogonal to the constraint-kind axis above: a residency ensure can be relational, a `rule` can be conditional.

### 3. Write-site category (source: `precept-language-spec.md:1971` + packet §(c)9)

The spec's mutation-surface enumeration ("event-driven transitions, stateless event hooks, direct field updates, and state entry/exit actions"), unpacked per the packet's confirmed write-site sweep:

- handler `set` (transition rows and stateless event hooks)
- **editable-field edit** (the second ingress point, want :141 — the write-site kind rev 1's cell class structurally could not contain)
- entry hook / state action (state entry/exit)
- collection action (the `Actions` catalog, 15 members — `Actions.cs`; mutating actions are write sites for constraints mentioning the collection)
- computed-field transitive (`<-`: every write to an input is a write site for constraints mentioning the computed field — settled by the mention-set ruling, 2026-07-20)

This axis is orthogonal to RHS shape; RHS shape applies only where an authored expression exists.

**No-write rows** are not one value but three: reject rows (no data obligation; inapplicability-vs-refusal semantics, want :154 — though reject-row *interpolations* are fault evaluation sites, see case shapes), transition-only rows (which **do** carry obligations: entering a state establishes its residency ensures and fires its entry ensures even when no field is written — owner ruling, 2026-07-20), and unmatched inapplicability (not a row at all).

### 4. RHS read-set shape (replaces rev 1's overwrite/RMW axis)

For sites with an authored expression, classify the right-hand side by what it reads: {nothing (constant) / args only / the written field / other mentioned fields / unmentioned fields} — combinations permitted. Whether premise (d) is available **derives from the RHS read-set intersected with the constraint's mention set**: pre-state constraint facts are available exactly over the fields the plan reads pre-state, plus the mentioned fields it leaves unwritten. Rev 1's claim that "overwrite excludes premise (d) structurally" is false in general. Counterexample: `set Total = Cap` under `rule Total <= Cap` — an overwrite that premise (d) closes. Overwrite-vs-RMW was the special case where the only interesting read is the written field. The three numeric witnesses below survive as three read-set classes.

### 5. Type family (source: the four language type docs + the `Types` catalog)

Primitive (`docs/language/primitive-types.md`) / temporal (`temporal-type-system.md`) / business-domain (`business-domain-types.md`) / collection (`collection-types.md`). Members are enumerated by the `Types` catalog (32 members, `Types.cs`; queryable via `precept_types`) — the matrix references the families, the catalog owns the membership.

**Establishment pre-configuration**: establishment WP is taken over the **default configuration** for fields the initial event does not write (want :18, :106).

**Scope of the completeness claim**: the schema/contract machinery covers the data half of the want's promise; the structural half is covered by the weaker case shape only (want :149: "the proof engine's half of the promise governs data; the graph analyzer governs shape"). The claim below quantifies over both, each under its own case shape.

### Dead rows are an error (owner ruling, 2026-07-20)

A transition row whose guard can never be true **rejects the file**. It is an error, not a warning. This overrides the 2026-07-12 structural-severity ruling, which predates the want doc.

Why: a definition that asserts something false about itself does not ship. The row says "when this condition holds, do this"; if the condition cannot hold, the author has written something they did not mean, and the file's own text misrepresents the entity's behaviour. Warning severity would also create exactly the two-tier trustworthiness the want doc forbids — a file that compiles but whose guarantee has an asterisk on it.

Two riders come with the ruling:

- **The satisfiability scan folds constraints, not just field bounds.** Today the contradiction check runs over declared field bounds only, so a guard that contradicts a *constraint* compiles clean — a live escape from the ruling. The scan is extended to fold the applicable constraints into the check. This is the point where the structural family consumes the matrix's own premise vocabulary.
- **Unreachability propagates.** A state whose only inbound rows are all dead is unreachable, and the existing unreachable-state error applies to it. Deadness is computed first; reachability is then computed over the surviving rows.

## The minting rule — an explicit input

A site **mints** an obligation when the rules require a proof obligation at that (constraint, site) pair. Which pairs mint obligations is **prior to** the matrix: "no silent cells" is only as strong as the rule that generates the cell candidates. The minting function's parts, each now settled:

- **Symmetric attachment**: a constraint's obligations attach to every write site of every field the constraint mentions (want :20; settled).
- **Mention-set definition** (owner ruling, 2026-07-20 — all three legs adopted): a constraint **mentions** a field when the field appears in any of —
  - (a) the constraint's **condition** — the part that must be true;
  - (b) the constraint's **activation guard** — the `when` part. A write that flips a dormant constraint active around otherwise unchanged data must carry the obligation, because after that write the constraint is live and nothing else checked it;
  - (c) **transitively through a computed field** — if a constraint mentions a computed field, then every write to that computed field's inputs is a write site for the constraint, following the dataflow all the way through chained computed fields.

  **Desugared cross-field modifiers count.** `field Floor as decimal max Ceiling` desugars to a constraint mentioning **both** fields, so a write to `Ceiling` carries the obligation just as a write to `Floor` does.

  *Tradeoff accepted*: the inclusive definition mints more obligations than a condition-only reading would, so more write sites need premises and more programs need an explicit guard or bound to compile. That is the cost of the hypothesis being sound — a mention leg left out is a write site the induction never covers.
- **Activation sites** (owner ruling, 2026-07-20): attachment extends to constraint-*activation* sites. A residency ensure is established at **every** entry into its state, including a transition-only row that writes nothing, so a transition into a state whose ensure the unchanged data violates mints an obligation and is rejected if undischarged. See Constraint kinds, above.
- **Computed-field transitivity** (owner ruling, 2026-07-20): every write to a `<-` input is a write site for constraints mentioning the computed field — leg (c) of the mention set.
- **Fault minting**: catalog-stamped at evaluation sites (`proof-engine.md` § Catalog-Driven Obligation Instantiation, :515; settled and shipped for the fault family). Each evaluation site in a plan mints its own fault obligations, including sites in expressions that read the results of earlier writes in the same plan.

A change to any part of the minting rule changes which cells exist, so any future amendment to it re-opens every cell the change reaches — it is amended under the amendment rules below, never adjusted in passing.

## Rule validity — the definition argues its own soundness (owner-approved 2026-07-19)

("Rule" in this section means a **generative rule of this definition** — a discharge contract, a step kind's recompute rule, a transport rule. It is not the `rule` construct, and not the general "constraint" sense.)

The certificate checker verifies that proofs *replay* the rules; nothing downstream verifies the rules themselves. And under the exact contract, a defective rule is not a bug a compiler may conservatively decline to implement — the definition mandates implementing it. The definition is therefore the trusted computing base, and it must argue its own soundness:

- **Every generative rule carries a validity argument.** This covers each discharge contract, each certificate step kind's recompute rule, and each transport rule (guard-fact transport through prior writes, vacuity-by-activation, sign reasoning). The argument is a short written case that the rule is truth-preserving with respect to the evaluator's actual runtime semantics (arithmetic, rounding, presence, ordering) — or a citation to one. Precedent: Event-B ships its obligation-generation rules with published soundness meta-theory. Intent citations (the want doc) establish what a rule is *for*, not that it is *true*.
- **Ratification gate**: no cell ratifies whose derivation cites an argument-less rule. The validator checks argument *presence* per cited rule; argument *adequacy* is reviewed like any generative sentence — owner-read, adversarially checkable.
- A validity argument found wrong after ratification is precisely the **soundness-correction** amendment case (Amendments, below). The witness program demonstrating the unsoundness accompanies the correction.

### Validity arguments — the rules this revision states

The arguments the gate above requires, for every generative rule stated so far. Each argues that following the generative rule cannot license a program that violates its constraint at runtime, judged against the documented runtime semantics. Where an argument depends on something unbuilt or unsettled, the dependency is named inside the argument — an honest dependency is part of a valid argument, not a footnote to hide.

**Guard normal-form match (Witness Family 1, Bases A and C, class (c)).** The WP has the shape `⟨RHS⟩ ⟨cmp⟩ ⟨bound⟩`, and the licensed premise is a guard conjunct normal-form-equal to it. Why this is truth-preserving: a row's actions execute only if its guard evaluated true (guards select — `precept-language-spec.md:1897`). The guard reads the same pre-state and args the first action reads — each assignment sees the state left by preceding assignments (`precept-language-spec.md:164`), and for a single-write plan there are none. Evaluation is pure (`precept-language-spec.md:170`) and deterministic (`precept-language-spec.md:96`). So the RHS, re-evaluated at the write, produces the same value the guard compared, and the written field satisfies the rule's comparison outright. The two normalization steps preserve this: a comparison-direction flip is the definition of the converse operator, and operand commutation preserves the evaluated value in every numeric lane (`decimal` arithmetic is exact, `primitive-types.md:230`; IEEE addition is commutative even though approximate, `primitive-types.md:265`). Note the argument needs determinism and purity only — not exactness — so it holds uniformly across the three lanes. **Open dependency**: this is stated for the single-write plan. A guard fact consumed after a prior write in a multi-write plan routes through the transport rule. The write-plan ruling settles the *mechanics* — the WP of a multi-write plan is the backward substitution through the writes in reverse order, and the guard is compared against that WP — but the transport rule has not been written out as a generative rule here, and it owes its own validity argument when it is.

**Arg-bound interval arithmetic (Witness Family 1, Base A, class (b)).** Governance enforces every declared constraint on every value entering as an event arg, before any computation derives from it (`precept-language-spec.md:268`). So `Amount1 <= 250` and `Amount2 <= 750` are true of the values the handler evaluates. Decimal addition is exact and checked (`primitive-types.md:230`, `:236` — overflow is an error, i.e. a fault, for which the fault family mints its own obligation, and which never commits a value). So the runtime sum is the mathematical sum, and addition is monotone over `<=`: `a <= 250` and `b <= 750` give `a + b <= 250 + 750 = 1000`. The compile-time bound sum runs over exactly-extracted bounds (`business-domain-types.md:426` — extraction is exact, bounds never round). The same argument carries the guard-spelled variant — the per-term bound conjuncts the band ruling licenses. When the row fires, its guard evaluated true (`precept-language-spec.md:1897`), so each per-term bound conjunct holds of the very values the RHS reads (by the purity, determinism, and single-write reasoning of the guard-match argument), and the identical monotone sum applies. Only the source of the bound facts differs: guard truth at the row, instead of ingress governance. **Open dependencies**: three. First, the analyzer's bound arithmetic must implement the same decimal semantics as the evaluator's — the known analyzer-matches-evaluator identity item, unverified today. Second, the argument covers the exact lanes (`integer`, `decimal`) only: on the `number` lane runtime addition rounds (IEEE 754, `primitive-types.md:265`), so extending the rule there requires an outward-rounding side condition on the computed bound, not yet stated. Third, an RHS containing division rounds even in `decimal` (28-digit quotient, `primitive-types.md:239`), so division shapes sit outside this rule as stated.

**Inductive hypothesis plus sign monotonicity (Witness Family 1, Base B, classes (d)+(b)).** Premise (d) supplies `Total_pre <= 1000`. That fact is valid over reachable configurations because the induction ranges over exactly those: establishment covers construction, every handler carries a preservation obligation, mutation atomicity discards any working copy that fails (`precept-language-spec.md:1967`), and the persistence boundary admits only state that was governed when written (spec §0.7). Premise (b) supplies `Amount >= 0` at ingress (`precept-language-spec.md:268`). Decimal subtraction is exact (`primitive-types.md:230`), so `Total_pre - Amount` is the mathematical difference (or an overflow fault — a separately-minted obligation, never a committed value). Subtracting a nonnegative cannot increase a value: `x - a <= x` whenever `a >= 0`. Transitivity of `<=` over the decimal total order closes `Total_pre - Amount <= 1000`. **Open dependency**: the hypothesis is only as sound as the minting rule is complete. It quantifies over every write site of every mentioned field, so the mention set is load-bearing here — a missed write site voids the hypothesis for every cell that consumes premise (d). The 2026-07-20 rulings settle the three parts that were open (the mention set's three legs, activation sites, computed-field transitivity); what remains is verifying that the implementation's site sweep matches them. Host-injected values outside the contract are excluded by canon (spec §0.7 boundary), not by this argument.

**Literal constant-fold for defaults (Witness Family 1, standing establishment obligation).** The `default` surface takes a literal value, and construction builds the hollow version with defaults applied (`precept-language-spec.md:2036`), so the runtime value of a field no construction row writes is the very literal the declaration states. Decimal literals denote exact base-10 values (`primitive-types.md:230`), and the fold compares that literal against the rule's bound under the comparison semantics the evaluator uses — a commitment spec §0.6 item 11 already makes (`precept-language-spec.md:213`: one default environment, one constant-fold evaluator). Truth-preservation therefore reduces to compile-time literal parsing and runtime literal materialization agreeing on the value — a single-representation dependency. The day defaults admit non-literal expressions, the fold inherits the full analyzer-matches-evaluator arithmetic dependency named above.

**Establishment over defaults (the pre-configuration rule).** Taking the establishment WP over the default configuration, for fields the firing construction row does not write, is valid because actions write only their target fields: a row is a flat assignment sequence (`precept-language-spec.md:164`), under one uniform working-copy model (`precept-language-spec.md:1967`). So a field no action of the row writes carries into the post-construction configuration exactly the default the WP was evaluated over (`precept-language-spec.md:2036`). The rule is per construction row: rows are first-match and may write different field sets, so the unwritten set is computed against the row that fired — per write plan, consistent with obligations being defined over write plans. The default configuration is total over that unwritten set: a required field with neither a default nor an initial-event assignment is already a compile error (`RequiredFieldsNeedInitialEvent` / `InitialEventMissingAssignments`, spec §3A.5), so the WP never falls through a hole in the configuration.

**Guard-fact substitution for relational rules (Family 2, the ReduceLimit shape).** The plan writes only `OverdraftLimit`, so post-state `Balance` equals pre-state `Balance` (actions write their targets only — `precept-language-spec.md:164`, `:1967`). The written value is the same arg the guard read: args are caller-supplied, and nothing in a plan can write them (expression purity, `precept-language-spec.md:170`). Substituting the written value into the rule therefore yields, in the post-state, precisely the fact the guard tested in the pre-state — `Balance >= -NewLimit`, negation being exact in the decimal lane (`primitive-types.md:230`). The row fired only if that guard was true (`precept-language-spec.md:1897`), so the rule holds after the write. **Open dependency**: same as guard matching — stated for the plan whose only write is the substituted one; earlier writes in a multi-write plan route through the backward-substitution mechanics, whose transport rule is not yet written out here.

**Vacuity by activation (Family 5, conditional rules).** The language defines a guarded rule as applying only when its guard is true — "the engine ensures the rule holds in every configuration where its guard is satisfied" (`precept-language-spec.md:1866`). So a post-state in which the activation condition is false cannot violate the rule, by the construct's own semantics rather than by an analyzer approximation. A sound derivation of that post-state falsity therefore discharges the obligation with nothing further to prove. The entire soundness burden moves onto the falsity derivation itself, which must be a licensed derivation carrying its own validity argument. For the presence case: `set`/`clear` are full-value-replacement and sequential flow invalidates prior facts (spec §0.6 Sequential proof flow); presence is tested with `is set`/`is not set` (`precept-language-spec.md:610`). **Open dependency**: the analyzer's post-state presence model must agree with the evaluator's presence semantics for `optional` fields — the analyzer-matches-evaluator identity item again, on the presence axis rather than the arithmetic one.

Every cell of the product — not just the non-empty ones — carries exactly one of:

- **Defined** — schema, contracts, suggestion schemas, and witnesses stated; **cites the want-doc sentence(s) it derives from**.
- **Deferred** — provable under the model, but the machinery is deliberately out of scope — cited (e.g. §1b, ⧖ Q7).
- **Open** — the model has not decided — cited (a want open question or a packet Q-item). Rev 1's "structural gap" label is retired; those cells are **open (Q10)** and so on.
- **Empty** — the cell is pruned, with a required **one-line pruning derivation** written in the cell (e.g. "empty: no-write reject row × preservation — writes nothing and changes no state, so it frame-preserves every data constraint; note this is *reject* rows only, since a transition-only row does mint entry and residency-establishment obligations"). Pruned cells are written, not absent — an incorrectly-pruned cell must be findable, never a silent gap wearing an "empty" badge.
- **Conflicted** — two canon sources answer differently: cite both, route to owner (e.g. `omit` × constraints — canon asserts both reset-to-default and structurally-absent semantics; packet G5, ⧖ Q13). A matrix that cannot record the canon-asserts-both-answers state cannot detect its recurrence.

**Completeness claim (scoped)**: the proof engine is exhaustively defined when every cell of the family-indexed product carries a disposition — data cells under the schema/contract shape, structural cells under the weaker shape — with content or citation. Cells the enumeration produces that neither the want doc nor this document's generative sections can answer are the definition gaps, found mechanically and routed to the owner.

## Composition check — the deletion method retained

Cells are defined in isolation; the compiler is defined on whole files. The addition framing is stronger *per cell* — it pins rejection, suggestion, and fix together. But it does not subsume the want doc's deletion method, which exercises every obligation with all the other premises co-present. The two framings are complementary; no strict-superiority claim is made.

- **Compositionality input**: "obligations are minted and discharged per site; premises are scoped per handler; no cell's disposition depends on any other cell" is a want-doc-level claim the matrix consumes — currently implied, not stated; flagged for the canonical doc to state and cite.
- **Per family, one composed exemplar file** with a deletion pass (the want's own §"What must not compile" table, want :110-131, is the constraint-family exemplar), alongside the per-cell witnesses. Interaction defects — an addition discharging one obligation while breaking another, a new guard creating a dead row — are caught here, not per cell.
- **Global note — the consumed/unconsumed-premise asymmetry** (want :129): a premise appearing in no cell's premise list is unconsumed — enforced at its ingress, load-bearing for nothing; deleting it weakens the spec without breaking any proof. This is a derived per-file property (the certificate's load-bearing marking, want :210), noted once — not a cell.

### Witness Family 1 — numeric single-field, handler `set` (live-verified slice)

Cell coordinates: preservation × single-field × handler `set` × (three RHS read-set classes) × primitive numeric. Derives from want :19 (premise classes), :20 (attachment), :22 (`max` desugars to `rule Total <= 1000`). Setting (stateless precept):

```precept
field Total as decimal max 1000 default 0.0
```

**Standing base-case obligation** (establishment × defaults): `default 0.0 ⊨ Total <= 1000`. Discharged by constant folding (`Literal`). **Proven today ✓v.** (No initial event exists in this slice; the establishment half over initial events is vacuous here.) A fold that evaluates false, or cannot complete, leaves the obligation undischarged: reject.

Obligation schema: WP `Amount1 + Amount2 <= 1000`. The read set does not intersect the mention set and the written field is not read, so premise (d) has nothing to instantiate — availability is derived per the read-set axis, not from "overwrite." Applicable classes: (b), (c). The suggestion schema names both.

Decision procedure — class (c) has two licensed derivations. First: normal-form match of the WP against the row's guard conjuncts (a finite set). Failing that: collect the guard's per-term bound conjuncts (`term op constant`) over the WP's terms and run the same exact-decimal interval combination as class (b) — a term with no bound conjunct, or a combined bound exceeding the rule bound, fails the derivation. Class (b): exact-decimal upper-bound sum over the args' declared `max` bounds; an arg with no upper bound, or a computed sum exceeding the rule bound, fails the class. If all derivations fail, reject, naming both classes.

Either lookup failing rejects.

### Sketch witnesses (model-derived; no ✓v; no compile results claimed)

Every witness family below is anchored on a `rule`. The four ensure-anchored case shapes — residency establishment at a state entry, residency preservation during residency, an entry/exit transition-moment obligation, and an event precondition — have case shapes but no witnesses yet; they are owed by the population pass, one witness triple per shape.

**Family 2 — relational two-field rule, symmetric write site** (preservation × relational × handler `set`; want :103). `rule Balance >= -OverdraftLimit`; site `set OverdraftLimit = ReduceLimit.NewLimit` (writes the *other* mentioned field). **Family 3 — editable-ingress cell** (preservation × {editable edit}; want :106, :141, :143). `field DailyWithdrawalLimit as decimal positive max 10000.0 editable`; `in Active modify DailyWithdrawalLimit editable`. Obligation: every write satisfies the field's modifier-constraints plus every constraint mentioning the field. Discharge: **ingress evaluation** — a discharge mechanism, not a premise class (owner ruling, 2026-07-20), and a complete compile-time proof: the compiler shows that the edit door's evaluation set covers exactly the constraints the obligation names, so nothing is left for runtime to decide. Near-miss: an ingress that evaluates the modifier-constraints but omits a mentioning constraint — must refuse the edit that breaks that constraint (this near-miss is a *runtime-surface* obligation; its compile-time shadow is the certificate marking the ingress check load-bearing, want :129). Decision procedure — compute the field's mention set by a finite syntactic scan of the definition's constraints, and require the ingress evaluation set to equal the field's modifier-constraints plus that mention set. The compile-time check is equality of finite sets, recorded load-bearing in the certificate — which is why the mechanism was never a fact source: the set equality *is* the derivation.

**Family 4 — fault family, arg-constraint discharge** (fault × division; want :104). Base: `set MonthlyRepayment = -Balance / PlanRepayment.Months` with `Months as integer` unconstrained — rejects: divisor can be zero. Addition: `Months as integer positive` → (b), divisor interval excludes 0. Near-miss: `Months as integer nonnegative` — zero still admitted; must still reject, same obligation. Decision procedure — compute the divisor's interval from its declared modifiers and in-scope guard facts (a finite set per site); zero inside the interval, or no bound excluding it, rejects.

**Family 5 — conditional rule, vacuity by activation** (preservation × conditional; want :40). `rule MonthlyRepayment <= Cap when MonthlyRepayment is set`; a write plan that leaves `MonthlyRepayment` unset in the post-state discharges vacuously (activation condition false) — a non-arithmetic derivation with no name in the §1a/§1b taxonomy, named instead by the certificate step kinds. Near-miss: a plan under which `MonthlyRepayment` may remain set — vacuity unavailable; must still reject, same obligation. Decision procedure — attempt to derive the activation condition's post-state falsity from the write plan's finite presence/value facts; if not derivable, the rule is treated as active and its obligation mints normally (vacuity is never assumed, only derived).

**Family 6 — structural cell, weaker case shape** (`ReachabilityFact`; want :125, :151). Flagged base: `state Suspended` with no inbound row → required rejection (unreachable state). Fixing structural edit: any inbound row → clean. No premise/strategy columns; both polarities still present (the near-miss analogue: a dead inbound row does not make the state reachable — it is itself an error, and the state it points at stays unreachable). Decision procedure — first decide row deadness by the satisfiability scan, folding the applicable constraints as well as the declared field bounds; then traverse the declared transition graph over the surviving rows (reachability from `initial`, spec §0.5). Both are finite: the state and row sets are statically declared, and the scan's fact set is the file's own constraints and bounds, so there is no derivation search to bound.

## Storage (owner-accepted 2026-07-19)

Per the independent evaluation in `obligation-discharge-matrix-2026-07-19-reviews/review-5-cell-storage-evaluation.md`:

- **Cells are structured data, never compiled into `src/`.** One data file per family/case-shape (JSON; in-repo precedent: `exhaustive-gap-analysis-2026-07-14/assembled/*.cells.json`), stable cell IDs as citation anchors, beside this document — promoted with it at ratification. The compiler never looks a cell up (it derives from the generative rules), so cells in the catalog would be a hand-maintained parallel copy of content derivable from those rules — the failure the catalog principle exists to prevent.
- **Human-readable cell tables are generated from the data** and never hand-edited (the `tmLanguage` discipline), drift-checked by a test.
- **A cell validator runs from day one** (`DiagnosticCoverageScanner`-shaped): disposition totality over the product, citation present per cell, axis values from named vocabularies (cross-checked against built catalogs where anchors exist), one near-miss per discharge addition, respellability verdict resolvable per cell (a family-level verdict with per-cell overrides), WP recomputation where mechanized. The definition-version stamp for certificate coupling rides in the data.
- **The generative layer enters the C# catalogs at constraint-obligation design time** (the trigger this document already names): establishment/preservation `ProofRequirement` subtypes, premise classes, `CertificateStepKind`/`CertificatePremise`, the expression-shape classification, contract and suggestion metadata. ## Amendments (owner-approved 2026-07-19)

Two amendment classes, and only two — every change to the licensed set (the set of programs the written rules accept) is one of them:

- **Power-widening** — a new licensed derivation: a new spelling that proves. Definition-edit-first: the derivation enters this document (and, once they exist, the catalogs) with an owner ruling before any compiler implements it. Monotone: everything previously licensed stays licensed. Minor definition version; previously issued certificates remain valid. Candidate pipeline: cells' sound-but-unprovable bands are the standing inventory — a band member that authors keep hitting in real precepts is the signal to consider licensing it.
- **Soundness-correction** — a licensed derivation discovered to be semantically unsound: it accepts a program that can violate its constraint at runtime. Shrinking the licensed set is permitted **only** under this class. Always a major definition version; always breaks certificate replay for affected cells; always routed to the owner with the **witness program** demonstrating the unsoundness. Never folded silently into a widening or a refactor.

A compiler change that alters the accepted set without a corresponding definition amendment is nonconforming in either direction — that is the exact-power contract doing its job.

## Ratification protocol (owner-approved 2026-07-19)

What "ratified" means for a definition too large to read line-by-line — four layers, all required:

1. **The owner reads the generative sections in full** — Vocabulary, case shapes, minting rule, discharge contracts, amendment rules. These are the rules of the game; they determine every cell.
2. **Machines verify every cell** — the day-one validator (Storage, above): disposition totality, citations present and resolving, axis-value validity, near-miss pairing, respellability verdicts resolvable (family-level with per-cell overrides), a validity argument present for every rule the cell's derivation cites (Rule validity, above), a decision procedure named per contract, WP recomputation where mechanized. No cell ships unchecked.
3. **Spot-checks** — cells the owner picks, cells picked at random, and every cell an adversarial review pass flags. Note that `respellable: no` and `conflicted` cells reach the owner as decisions by their disposition rules regardless of this layer.
4. **Respellability is measured, not asserted** (owner-approved 2026-07-19, hard gate): before any family ratifies, its discharge contracts are run against the real sample corpus (the 59 rule-bearing files in `samples/`, plus the ensure-bearing files the constraint-kind ruling brings into scope), and every constraint × site obligation in those files is classified — licensed as written / needs a respelling (record it) / no licensed respelling exists. A family's respellability verdicts must agree with what the corpus shows, or the disagreement routes to the owner. Paper-only verdicts do not ratify.

The owner's ratification therefore certifies the generative rules and the checking regime — an honest statement of what a human sign-off over hundreds of agent-populated cells can be. Bulk cell content is never presented as owner-read.

## Eventual use — test basis

After the definitional pass, every defined cell converts mechanically into tests: base → expected diagnostic naming the obligation and all applicable missing-premise classes, **and no other diagnostics**; base + each addition → clean compile via the expected strategy, premise list recorded; base + each near-miss → still rejects, same obligation. Per family, the composed exemplar gets its deletion pass. Discipline carried over from the failed 2026-07-14 probe: every assertion reads **diagnostic codes / obligation records from `precept_compile`**, never prose summaries; each cell's expected outcome is stated by the definition before the run; edge cells are ledgered, not asserted.

**State**: the conversion machinery is built and run for Witness Family 1 — `tools/Precept.MatrixTools` converts a cell file into a test manifest and executes it through the pipeline, verdicting each row from proof-ledger records and diagnostic codes (see the cells folder's README for the artifacts and their regeneration commands). Two halves of the base/discharge contract are carried but **not verifiable at HEAD** and are recorded as such per row: the diagnostic naming all applicable missing-premise classes, and the premise list recorded on acceptance. The composed exemplar's deletion pass, and conversion beyond Family 1, still wait on the definitional pass.
