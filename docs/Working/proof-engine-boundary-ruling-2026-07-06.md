# Proof-Engine Boundary Ruling — Revision 3

> **This is a re-derivation, not a defense.** Shane raised two substantive corrections to v1: (1) *constraint modifiers and rules are the same construct* (`precept-language-spec.md:1135`), so they cannot receive opposite dispositions by spelling; and (2) the "no deferrals" directive was a *process safeguard against agents punting scope*, **not** a language-design mandate that the compiler must never defer to the runtime — so "compiler-never-defers" is to be decided on its own merits. I re-reasoned the whole question from the philosophy, the spec, and the code outward. Every load-bearing claim carries a `path:line` I re-confirmed first-hand at HEAD `a6922fd8`. Where the conclusion holds, I show it holds under the corrected premises; where the *derivation* moved, I say so plainly. The prior ruling is not privileged.

---

## 1. Executive ruling

**Precept is governed by the Hybrid model, and the model choice does not move under either correction — but the boundary is re-drawn where the corrections put it.** The compiler is **total over the fault surface** — *with one owner-parked exception, representational overflow, carved out below.* Every fault-prone operation over a *definition-derived* value in the **live-enforced fault set** — division, `sqrt`/`pow` non-negativity, empty-collection/index access, and the containment of a *computed result* within a declared `min`/`max` bound (`OutOfRange` / assignment-range impossibility, `precept-language-spec.md:208`; "no result outside a declared bound") — is compile-time **prove-or-reject**, discharged from carried constraints or else the definition is rejected naming the carrier. **Representational overflow is the single exception:** `NumericOverflow` — a computed decimal/money/temporal value exceeding what the **type itself** can represent (`Diagnostics.cs:690`, "Numeric computation exceeded the representable range") — is **owner-parked** (D1: `decision-index.md:19`; plan §2 D1, `compiler-readiness-plan-2026-06-16.md:188`). It is a **disclosed, defense-in-depth known-fault backstop with no live compile-time guarantee** — *not currently prove-or-reject*, temporary, and **no doc may claim it prevented**. The fault surface is therefore **two-tier**: the *live-enforced faults* above (prove-or-reject), versus the *parked overflow lane* (disclosed, not prevented). Crucially, representational overflow (`NumericOverflow`, type-range) is a **different fault** from declared-bound containment (`OutOfRange`, a value outside a *declared* `min`/`max`) — "`OutOfRange` remains a separate concern for non-arithmetic bound violations" (`overflow-prevention-design-analysis.md:516`) — and declared-bound containment **stays live**. The language is **not** limited to the statically-decidable fragment (pure Model B is rejected): a declared constraint — *modifier or rule, they are one construct* — is simultaneously (a) a compile-time **proof premise** that discharges those operations to the extent it is decidable, and (b) a runtime-**governed** obligation enforced on the raw external values entering the fields it reads, at ingress, on a working copy that is discarded if it fails. **Governance is not fault-deferral** — the fault is fully proven at compile time and only its precondition (that the value carries its constraint) is enforced at ingress (`precept-language-spec.md:270`, the Composition clause). The one-line boundary: *a raw external value at its own ingress slot is **governed**; any value a Precept expression has derived from it is **proven-or-rejected** (for the live-enforced fault set) or, for representational overflow only, **carried by the disclosed park**; the surface spelling of a constraint — `max 100` vs `rule x <= 100` — never changes a disposition, and what a constraint's **decidability** decides is whether a prove-or-reject obligation **discharges or the definition is rejected**, never whether the obligation is proven or governed.* Model A (bounded compiler + defer-the-rest to a runtime fault-trap) is rejected — but on `philosophy.md:57` and Principles 7/10/11 (`precept-language-spec.md:104`/`:110`/`:112`), which are independent of the now-clarified "no deferral" clause; pure Model B is rejected because it would refuse legitimate nonlinear governance rules (balance identities, ratios, product rules — 21 of 77 sample files use products) that governance already enforces honestly without deferring any fault.

**The conclusion held; two pillars of the derivation were wrong and are replaced.** v1 reached Hybrid, rejected Model A, rejected pure-B. Revision 2 reaches the same three verdicts. ### 2.1 Challenge 1 — "constraints are sugar for rules" — corrected the *boundary*, not the *model*

**v1's error, stated plainly.** v1 spoke as though a *constraint* carries a disposition: "bounds → prove-or-reject; a `rule` is a governance constraint" (v1 §2 Leg 2, §3 nonlinear-rule row). That is false. `precept-language-spec.md:1135` — "**Constraint modifiers are shorthand for rules**" — and `:1138` — "`min 5` and `rule X >= 5` are **interchangeable to the proof engine** … proof participation is a function of a constraint's **decidability**, not its syntactic form." The code agrees at two layers: every constraint modifier in `Modifiers.cs` carries **both** a `ProofSatisfactions` premise **and** `DesugarsToRule: true` (e.g. `Max`, `src/Precept/Language/Modifiers.cs:150`–`:163`), and the runtime `ConstraintKind` enum has **no "band" member** — a modifier bound is an `Invariant` (`= rule`) in the constraint sweep (`src/Precept/Language/ConstraintKind.cs:10`). The project's own bug tracker states it outright: "a field-reference bound is a relational constraint (§2.4 — `min Floor` ≡ `rule Amount >= Floor`)" (`docs/Working/bugs.md:196`). So a disposition keyed on *modifier-vs-rule* is incoherent.

**The correction.** Disposition is not a property of a constraint at all — it is a property of the **obligation** a value participates in. Every constraint (modifier or rule) plays *two roles at once*: a governed-at-ingress obligation on its fields' raw external inputs (`:268`) **and** a compile-time proof premise (`:203`, `:1138`). The **prove-or-reject** disposition attaches to *fault-prone operations over derived values*, which are routed identically no matter how the target bound was spelled. This makes `max 100` and `rule x <= 100` structurally indistinguishable in disposition, as the spec demands — and it fixes v1's second error: v1's §3 predicate declared decidability "never a routing criterion," which contradicts `:1138`. The truth is subtler and is the crux of §4: **decidability is not the router (routing by effort would slide to Model A), but it is the discharge-oracle for each prove-or-reject obligation.** Both statements are now true simultaneously. See §4.

### 2.3 The sharper distinction the two corrections jointly produce

Putting them together yields the load-bearing insight v1 lacked: **there are two different things people call "runtime checking," and only one is "deferral."**

1. **Governance** = the runtime enforcement of a *declared constraint* on a *raw external value* at ingress (`:268`). The fault is proven **complete at compile time**; governance only makes the carried precondition true (`:270` Composition: "proven by the compiler, its precondition discharged by governance, nothing left to a runtime check"). This is **not** deferral — nothing about a *fault* is postponed.
2. **Deferral (Model A)** = punting the *proof of a fault-prone operation* to a runtime fault-trap, so an unproven fault compiles clean. This **is** deferral, and it is what `philosophy.md:57` forbids.

v1 conflated the ban on (2) with a ban on (1)-flavored language, and leaned on `:266` to enforce the conflation. The corrected model bans (2) on the principles and embraces (1) as the mechanism that lets undecidable-but-legitimate constraints exist without a rewrite. Challenge 1 supplies the vocabulary (constraints are governed *and* premises; operations are proven), Challenge 2 supplies the honest grounding (the ban on (2) is the principles, not a clause).

## 3. Q1 — The model choice (four legs, reached freshly)

### The three models, re-stated under the corrected premises

| Model | Compiler over derived-value faults | Undecidable / not-statically-safe case | "Compiles clean" means |
|---|---|---|---|
| **A — Bounded + defer** | Partial. Unprovable faults are deferred to a runtime fault-trap. | Compiles clean; runtime detects & discards. | "Proven what I could; the rest is watched at runtime." |
| **B — Total + limited surface** | Total. | **Inexpressible** — author rewrites into the decidable fragment. | "Totally proven; nothing undecidable admitted." |
| **Hybrid (RULED)** | **Total over the fault surface** — no fault deferred. | **Admitted as a governed constraint** (not a deferred fault); a fault-prone *operation* it feeds is still prove-or-reject. | "Every derived-value fault proven; every declared constraint governed at ingress and used as a proof premise." |

### The ruling: **Hybrid** — total over faults, full constraint surface via governance.

### Leg 1 — Rationale (why, not what)

The guarantee is stated in two voices and Hybrid is the only model under which both are literally true. The **precise** voice: "A definition that compiles without diagnostics has no unproven evaluation faults, no unreachable business process states, and no structural dead ends" (`philosophy.md:57`). The **absolutist** voice: "Prevention, not detection … these configurations and workflows cannot exist" (`philosophy.md:49`). The spec operationalizes them as "two distinct mechanisms; keeping them distinct is what makes the guarantee precise rather than magical" (`precept-language-spec.md:264`): **fault prevention**, "established entirely at compile time … there is no deferral" (`:266`), and **governance**, "enforced at runtime on external input … before any computation derives from it" (`:268`), with the **Composition** clause tying them: for a runtime-supplied value, "the proof is … complete at compile time and the fault never occurs — proven by the compiler, its precondition discharged by governance" (`:270`).

Hybrid makes `philosophy.md:57` hold **unqualified** — every fault over a derived value is proven, so "no unproven evaluation faults" is exact — while governance makes `philosophy.md:49` hold **by prevention** — an invalid external configuration is discarded on the working copy before it persists (`:268`, `§3A.4:1965`), so "these configurations cannot exist." The boundary between the two mechanisms is the spec's own line at `:268`: *"before any computation derives from it."* A raw external value at ingress is governed; the moment a Precept expression derives from it, the result is a definition-internal value and is proven. That line is a dataflow fact — origin/derivation, decidable from the typed IR without a solver — which is exactly why it is "precise rather than magical" and why it cannot slide (§4). Crucially, under Challenge 1 this boundary is **syntax-blind**: it never asks whether a constraint was a modifier or a rule; it asks whether the *value being checked* is raw-at-ingress or derived.

### Leg 2 — Alternatives considered and rejected

**Model A — rejected on the principles, independent of the "no deferral" clause.**
This is the disposition most affected by Challenge 2, so I re-argue it from scratch without the clause. A clean compile guarantees "no unproven evaluation faults" (`philosophy.md:57`) and Principle 11 makes runtime fault checks "defensive redundancy, never … the primary enforcement mechanism" (`precept-language-spec.md:112`). Model A makes a runtime fault-trap the *primary* enforcement for the deferred set — the exact inversion Principle 11 forbids and the identity Principle 1 defines Precept against ("prevention … not caught after the fact," `:92`). This holds with `:266` struck from the record entirely. Three independent corroborations, none of which is the process directive:
- The **owner shipped the opposite** at the nearest scope: count-bound "Reading A, prove-or-reject" (`c27a382b`, author `sfalik`, 2026-06-03), which rejects even the *merely-unprovable* cardinality case rather than deferring it (`Diagnostics.cs:1303`: "a provable violation, **or merely unprovable**"). That is a genuine owner *language* decision, not a process safeguard.
- The project's **bug tracker classifies silent deferral as a defect**: BUG-017 "proof engine silently skips the result-bound check when the result interval is unbounded (Principle-10/11 soundness hole)" (`bugs.md:171`), BUG-021 (min-only lower bound, `bugs.md:203`), BUG-020 (field-reference bound inert, `bugs.md:188`). The three *are* Model-A-shaped behaviors, and the project treats them as holes to close, not policy.
- The **red-team** (adversarial, instructed to steelman A) concluded A "survives as a general software-engineering argument, but it fails specifically against Precept's non-negotiable `philosophy.md` [line 57] … Model A's rejection is justified by product philosophy, not by runtime limitations" (`verify-1-redteam-modelA.md` §2, §4).

*What the runtime-can't-enforce argument is and isn't.* v1 correctly declined the "the runtime has no band representation, therefore A is impossible" argument as circular — `ConstraintKind` has no band member (`ConstraintKind.cs:6`–`:24`) *because* HEAD implements prove-or-reject; choosing A would mean *building* that surface. I keep that honesty: the missing runtime surface is A's **price** (design and ship a runtime fault-deferral-and-discard channel that does not exist), not A's **defeater**. A is defeated by `philosophy.md:57`; it is merely *also* expensive.

**Pure Model B — rejected on expressiveness, and this is where Challenge 1 sharpens the argument.**
Pure-B refuses every construct not statically decidable-safe, *including genuinely nonlinear governance rules*. Under the corrected vocabulary the refusal is clearly wrong: a nonlinear **invariant** — `rule TotalInventoryCost == AverageCost * QuantityOnHand` — is a *governed constraint*, not a *fault-prone operation*. Governance already enforces it: the runtime constraint sweep covers "global rules, state ensures … AND event ensures" (`result-types.md:121`), discarding any operation that violates the identity (`§3A.4:1965`). Pure-B would either refuse the rule (needless loss) or pretend to prove it (impossible for a genuine product). The cost is not an edge case: **21 of 77 sample `.precept` files contain product expressions** (re-confirmed first-hand at HEAD — `grep -l '\*' samples/*.precept | wc -l` = 21, total 77), spanning loan debt ratios, rent-to-income, inventory cost, invoice subtotal/tax, lease overage, and OEE; a 77-sample corpus audit put ~89% of invariants in-fragment, with a recurring out-of-fragment balance identity `A + B == C` across four precepts (`precept-guarantee-specification-2026-06-05.md` §7, via `verify-2`). Hybrid keeps every one of these expressible (governed) while their arithmetic sub-expressions remain subject to the live fault floor (declared-bound containment, division-by-zero, `sqrt`/`pow`, empty/index access — representational overflow itself is parked per D1, a disclosed gap). Pure-B mistakes "governed as a rule" for "a deferred fault" — Challenge 1's correction is exactly that these are different obligations on the same construct.

### Leg 3 — Precedent / prior art

- **Precept's shipped code is already this shape.** Fault-class violations reject at compile time — `OutOfRange` (`:697`), `DivisionByZero` (`:821`), `SqrtOfNegative` (`:829`), `LengthBoundViolation` (`:1281`), `CountBoundViolation` (`:1293`) are all `Severity.Error`, and `CountBoundViolation` fires on the merely-unprovable case (`:1303`). `NumericOverflow` (`Diagnostics.cs:690`) is also `Severity.Error`, **but its live scope is narrow under D1**: it rejects the compiler-self-protection case (constant-literal representability, e.g. `default 9999999999999999999`, plan `:201` — *not* parked) and otherwise survives only as a disclosed defense-in-depth backstop with **no live `[StaticallyPreventable]` guarantee** for *derived* multi-field representability (parked, plan `:199`). Governance runs on external input via the post-mutation constraint sweep (`result-types.md:114`/`:121`). The running compiler is nowhere Model A *by design* — the three exceptions are logged as bugs (`bugs.md:171`/`:188`/`:203`).
- **Owner-ratified narrow precedent, at the exact structural scope.** Count-bound "Reading A" carries explicit owner sign-off — "OQ3 — RESOLVED: Reading A confirmed by owner … 'yes, unproven divisor'" (`count-bound-discharge-semantics-2026-06-03.md:297`), shipped `c27a382b`. This is the structurally identical decision (prove-or-reject, no fault deferral, forced author guard) decided the Hybrid way, by the owner, as a language decision.
- **`:266` already treats modifier and rule as one carrier.** The fault-prevention clause discharges "an obligation that each operand *carries* a sufficient constraint — a declared **modifier or rule**, an author guard, or a statically-known safe value" (`:266`). Challenge 1's reconciliation is not an invention on top of the spec; it is the spec's own carrier list read literally.
- **External field.** SPARK/GNATprove use a lightweight interval bound-propagation pass and require "the author supplies the missing precondition or the proof doesn't discharge" — total sound bounds-checking, placing Precept "in the company of Astrée, Frama-C, and GNATprove" (`interval-vs-value-evaluation-prior-art-2026-06-05.md:47`/`:151`, via `verify-2`). Nickel — "evaluate contracts against concrete values / defer to runtime" — is cited *only to be rejected*. Terraform (`resource` vs `data`), SQL DDL (triggers vs `CHECK`), and DDD (entities vs value objects) ground the "one language, both stateful and stateless" posture that governance-without-deferral preserves (`philosophy.md:39`).

### Leg 4 — Tradeoff accepted

**Soundness over completeness on the fault surface, deliberately (`precept-language-spec.md:221`, Proof philosophy #1).** The conservative prover will sometimes reject a safe-but-unprovable derived-value computation — the author must add the carrying constraint (a source bound, a guard, or a rewrite). This is a real, named ergonomic cost: "a one-time author guard-tax … authors lose the 'unguarded add silently compiles' ergonomic; they gain a structurally-prevented overflow" (`count-bound-discharge-semantics-2026-06-03.md:196`). We take it because it is the price of `philosophy.md:57` being *unqualified*. The corpus says the tax is small (~89% in-fragment; count-bound in-transition corpus cost ~zero; the string-length forced-rewrite already ships as `Severity.Error`, `Diagnostics.cs:1281`), and the escape valve for the genuinely-undecidable residual is **governance, not rejection** — so pure-B's austerity is avoided. The *new* honesty Challenge 2 adds: this tradeoff is a **default**, not a theorem — an explicit author-visible trust construct could later soften it without becoming Model A (§7, flagged, not decided).

## 4. The boundary / admissibility rule (re-derived so identical constraints get identical dispositions)

This is the section Shane valued in v1. I keep its concreteness and fix its logic. v1 routed a *checked value* by four legs and declared decidability irrelevant to routing. That was right about the *slide* and wrong about *decidability's role*. Here is the corrected device.

### The Obligation-Role Rule

Disposition is a property of an **obligation**, not of a construct. There are exactly two obligation *families*, and one oracle.

> **A. Every declared constraint `C` — modifier or rule, indistinguishably — generates two obligations, always, regardless of decidability or spelling:**
>
> 1. **Governance (runtime, at ingress).** For each field `C` reads, whenever a **raw external value** enters that field — construction input, event argument bound directly to it, or direct field edit — `C` is enforced on the resulting working copy, which is discarded if `C` fails (`:268`, `§3A.4:1965`). Operation-blind. This is **not** the deferral of a fault; it is the enforcement of a declared contract on raw input.
> 2. **Premise contribution (compile-time).** `C` contributes its provable fact to the proof engine's interval/relational knowledge (`:203`; `:1138`), **to the extent it is decidable in context** — a literal bound always; a relational constraint only insofar as its referenced fields are themselves bounded. This premise is what *discharges* obligations in family B.
>
> **B. Every fault-prone operation `O` over a definition-derived value carries one obligation: compile-time prove-or-reject (`:266`) — with a single owner-parked exception (representational overflow).** `O` ranges over the **live-enforced fault set**: division, `sqrt`/`pow` non-negativity, empty-collection/index access, **and** the containment of a *computed result* within a declared `min`/`max` bound (`OutOfRange` / assignment-range impossibility, `:208`). `O` is routed to prove-or-reject **by the origin/shape of the value it consumes** — a value a Precept expression has derived is definition-internal (`:268` "before any computation derives from it") — **never by how hard `O` is to prove.** `O` discharges iff the family-A premises **decide** it safe; otherwise the definition is **rejected**, naming the carrier that would discharge it. **The one carve-out: representational overflow.** Arithmetic whose *result may exceed the type's own representable range* — `NumericOverflow` (`Diagnostics.cs:690`) — is **owner-parked** (D1, `decision-index.md:19`; plan §2 D1, `compiler-readiness-plan-2026-06-16.md:188`–`:199`) and is **not** currently a prove-or-reject obligation. `NumericOverflow` survives as a disclosed defense-in-depth backstop with **no live `[StaticallyPreventable]` guarantee** (plan `:199`); no doc may claim it prevented. This is a genuinely narrower guarantee here (an honesty-about-approximation carve-out, plan `:197`), **not** prevention relocated elsewhere — contrast declared-bound containment, which stays live above. Note the two are *different faults*: representational overflow is value-vs-**type-range** (`NumericOverflow`); containment is value-vs-**declared-`min`/`max`** (`OutOfRange`) — "`OutOfRange` remains a separate concern for non-arithmetic bound violations" (`overflow-prevention-design-analysis.md:516`). *GATE-O edge cases* — integer-conversion overflow and non-finite (∞ / NaN) values — sit inside the parked lane's ambiguity and are **pending owner disposition** (`decision-index.md:55`; "fold into the park / new fault lane owed prevention / own explicit park"); this ruling invents no rule for them.
>
> **The oracle: decidability.** For each **live-enforced** family-B obligation, decidability selects the outcome — **discharge** (provably safe), **reject-violated** (provably unsafe), or **reject-unprovable** (neither — the merely-unprovable case, `Diagnostics.cs:1303`). Decidability is the *discharge oracle*, not the *router*. Routing by effort would make every newly-hard case a deferral candidate (Model A's slide, `verify-2:62`); routing by origin cannot slide. (The parked overflow lane sits outside this oracle: it is not decided at compile time at all — it is a disclosed gap, not a discharged obligation.)

**The one-line boundary:** *a raw external value at its own ingress slot is **governed**; any value a Precept expression has derived from it is **proven-or-rejected**; `max 100` and `rule x <= 100` are the same construct and get the same treatment; **decidability decides whether a prove-or-reject obligation discharges or the definition is rejected — never whether it is proven or governed.***

### Why this reconciles constraint = rule *and* "proof participation is a function of decidability"

- **Identical dispositions by spelling.** A constraint is never "routed" — it always does both A.1 (govern) and A.2 (premise). The *disposition* (reject vs clean) lives on family-B operations, which read the field's *constraint range* (built from its bounds *and* rules alike — `:208` assignment-range impossibility; `:213` default-fold covers `DefaultViolatesRule` on rules). So `max 100` and `rule x <= 100` produce the same family-A obligations and feed the same family-B checks. `min Floor` ≡ `rule Amount >= Floor` (`bugs.md:196`) is the same relational premise either way.
- **Decidability restored to its correct job.** `:1138` says proof *participation* is a function of decidability — i.e., whether `C` (as a family-A.2 premise) can *discharge* a family-B obligation. A decidable literal discharges; an undecidable relational premise (unbounded reference, nonlinear product) cannot, so the family-B operation it was meant to carry **rejects** (author strengthens the carrier). This is `:1138` and the anti-slide device *composing*, not conflicting: origin routes the obligation; decidability grades the premise.
- **Why the nonlinear rule is "governed."** Not because "undecidable ⇒ govern" (all constraints are governed). It is governed because it is a *constraint* (A.1). Its *undecidability* means it cannot **also** be discharged as vacuous/contradictory and cannot serve as a family-A.2 carrier for other obligations — so governance is the *only* enforcement mechanism left for it, and that is precisely why admitting it costs no soundness (the live faults inside it — declared-bound containment where the result feeds a bound, division safety, etc. — are still family-B prove-or-reject; its *representational* overflow is parked per D1, a disclosed gap, not a deferred fault). Challenge 1's phrasing "governed only because it is undecidable" resolves to: *governance is the only available enforcement for an undecidable invariant; undecidability removes the compile-time-proof option, it does not route to governance.*

## 5. Downstream dispositions (resolved under the ruled model)

### Q5 — Proven-violation severity: **reject as Error (definition incoherence).**
A provably-always-violating, reachable assignment of a *derived* value to a **declared bound** is a definition that can never produce a valid configuration on that path. It is family-B (live-enforced), provably-violated → **Error** (`Diagnostics.cs:697` `OutOfRange`; `:208` assignment-range; `:867` `UnsatisfiableInitialState`). *(Scope: this is **declared-bound containment** — `OutOfRange`, live — **not** representational overflow. `NumericOverflow` is parked under D1 and does not participate in this reject; a `NumericOverflow` reference was removed here in Rev 3 to avoid conflating the two faults.)*
- **Rationale (clause-independent):** a certain reachable violation is incoherence; Principle 1 (`:92`) makes prevention structural; a compile-time certainty must not be demoted to runtime advice — the "false sense of security" the owner named. `philosophy.md:57` scopes it directly.
- **Alternatives rejected:** (i) **Warn-and-govern (D2)** — a warning is a clean compile, so it lets a *known* fault ("no result outside a declared bound," `:266`) compile clean, contradicting `philosophy.md:57`; and there is no runtime band representation distinct from a rule to govern it with (`ConstraintKind.cs`, no band member). Under Challenge 1 the "non-carries-proof band" category D2 rests on **does not exist** — a bound is a rule; the derived-value containment is always a family-B fault. (ii) **Silent accept** — the prevention-vs-detection failure Precept exists to prevent, and a logged bug (BUG-017, `bugs.md:171`).
- **Precedent:** HEAD rejects (above); owner-shipped count Reading A (`c27a382b`).
- **Tradeoff:** none material — a *provable* always-violation is never a safe program.

### Q6 — Default-vs-set-action consistency: **consistent — both internal, both prove-or-reject, both Error; and spelling-invariant.**
Position does not change disposition and neither does syntax. `default 150` on `max 100` → `OutOfRange`/`DefaultViolatesRule` (`Diagnostics.cs:697`/`:877`); `set X = 150` → `OutOfRange`/assignment-range (`:697`; `:208`) — **a declared-bound violation, not representational overflow** (`NumericOverflow`, `:690`, is parked and does not apply: `150` exceeds the *declared* `max 100`, not the type's representable range). Both are definition-internal values (neither is raw external ingress), both family-B (live-enforced), both `Severity.Error`. Substituting `rule X <= 100` for `max 100` changes nothing — `DefaultViolatesRule` folds *rules* against defaults (`:213`, `:877`) and the assignment-range check reads the field's *constraint range* built from bounds and rules alike. The differing diagnostic **codes** are a subject partition for legibility, not a disposition difference (`diagnostic-system.md:180`, "Fault-prevention obligations block; structural-soundness diagnostics report"). Row 2 is the honest edge: an *unfoldable* default is clean at compile time (`:213`) and governed by the construction sweep — decidability (foldability), not syntax, moves it.

### Q7 — The merely-unprovable case: **reject (Error), name the carrier — for the live-enforced fault set only.**
A **live-enforced** family-B obligation that is *merely unprovable* (neither provably-violating nor provably-safe) is rejected, naming the carrier that would discharge it. This is precisely cardinality's shipped behavior — `CountBoundViolation` fires on "a provable violation, **or merely unprovable**" (`Diagnostics.cs:1303`). **Representational overflow is exempt:** it is parked (D1), so a merely-unprovable *overflow* does **not** reject — it is a disclosed gap, not a named-carrier rejection. The reject-the-merely-unprovable discipline applies to division, `sqrt`/`pow`, empty/index access, and declared-bound containment.
- **Rationale (clause-independent):** `philosophy.md:57` says "no **unproven** evaluation faults" — a merely-unprovable fault is an *unproven* fault; admitting it is exactly what a clean compile must not contain. Principle 7 (`:104`): the compiler "does not guess."
- **Alternatives rejected:** (i) **Defer to runtime (A)** — Model A, rejected in §3. (ii) **Infer a weaker satisfiable bound** — unsound; invents a constraint the author did not declare (Proof #1, `:221`).
- **Owner precedent:** count Reading A, "yes, unproven divisor" (`count-bound-discharge-semantics-2026-06-03.md:297`) — the owner chose reject-the-merely-unprovable at this exact scope, as a language decision.
- **Reconciliation with §0.6 item 11 (structural coherence over *known* configurations):** a *foldable default* that is merely-unprovable is **clean** (`:213`), because a fixed known value that is not provably-violating is not a fault; a *family-B operation* over runtime-varying values that is merely-unprovable **rejects**, because there exists an admissible runtime value that faults. Same oracle (decidability), two obligation families, two correct outcomes. This is the distinction Proof philosophy #5 draws — "diagnostics classified by proof outcome" (`:229`) — applied per family.
- **Honest exit surfaced by Challenge 2:** the *only* place the verdict could move is here, and it moves **only** if the owner authorizes an explicit author-visible trust construct (§7 R4) — a *language* change, not a silent deferral. Absent that, reject.

### Q8 — Carries-proof bounds: **prove-or-reject; and the fragile split dissolves.**
A bound consumed by a fault obligation (a `max` that also bounds an index; a relation from a rule — `:258`, "a divisor over a *subtraction* of two related fields … is provably non-zero … and discharges") is family-B prove-or-reject. Under the Obligation-Role Rule this is **subsumed**: *all* declared constraints are uniformly A.1-governed + A.2-premises, and *all* derived-value operations are family-B. There is no "carries-proof vs non-carries-proof" partition to keep honest — the instability v1 (rightly) flagged is gone because the category never existed once constraint = rule is taken seriously.
- **Tradeoff:** a declared bound that feeds no *current* obligation is still governed at ingress and still a premise — slightly stricter than trying to relax "pure documentation" bounds, accepted for the stability gain.

### Q9 — False-promise / legibility: **ship the per-obligation disposition surface; no DEFERRED state.**
The two-mechanism boundary must be legible. Under Hybrid nothing internal is deferred, so "compiles clean" = "every derived-value fault proven." What remains is to make the boundary visible *per obligation*. This is **required**, not a concession: Principle 4 (`:98`, "what the engine could not prove must all be surfaceable"); Proof #6 (`:231`, "proof results flow as structured data, not parsed prose"); Principle 8 (`:106`, the proven/approximate line "must be visible").
- **Ruling:** a per-obligation surface rendering, for each obligation, **PROVEN** (compile-time, with source attribution) or **GOVERNED** (runtime, at the named ingress slot), on `precept_proofs` (MCP) + LS hover. **No "DEFERRED" state** — Hybrid contains no deferred-internal bucket; a "deferred" entry would be a false category.
- **Challenge-1 refinement:** because one constraint generates *both* an A.1 governed obligation and A.2 premise contributions, the surface is genuinely **per-obligation, not per-constraint** — a single `max 100` may appear as GOVERNED (on its field's ingress) *and* as a PROVEN carrier (discharging a derived-value containment). v1's per-obligation framing was right; the constraint=rule correction makes *why* it must be per-obligation explicit.

### Q11 — Taxonomy + adjacent D1/D3: **three diagnostic categories + a non-diagnostic governance disposition.**
