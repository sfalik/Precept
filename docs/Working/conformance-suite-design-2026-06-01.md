# Spec-Conformance Test Suite

> Design for a test suite whose oracle is Precept's **specification** (catalogs + `docs/language` + `docs/runtime`), not the implementation — the executable, permanent form of the Phase 7 conformance sweep, plus the acceptance spec the v1 runtime will be built against.

## Goal

When done, a maintainer can point to any catalog member or spec section and find a conformance test whose pass/fail is decided by the spec — and a meta-test fails when a declared catalog member, diagnostic code, or proof requirement has no such test. The price×quantity headline example (A1) and the counting-unit silent-cancel (E4) are the kind of gap this suite surfaces *by construction* rather than by chance.

## Scope

- **In scope**: structure, derivation method, completeness mechanism, organization, and run model for one new conformance test project (compiler and runtime facets co-located by feature, distinguished by a `component` trait); the `[SpecRef]`/`[Covers]` attribute pair and the coverage meta-test; the feature-AC-sheet method; the negative-coverage assertion style; the combinatorial-reduction discipline; the own-lane / allowed-red / feature-by-feature run model; a **fence-annotation convention** for `docs/language` precept examples + the one-time sweep that applies it (Decision 8).
- **Out of scope**: fixing the specific gaps the suite finds (each found gap is its own Phase 7 fix slice, per the existing one-at-a-time cadence); building the runtime (the runtime facet is its acceptance spec, executed by the future runtime phase); changing any language surface.
- **Ruled out (owner, 2026-06-01)**: refactoring the prose spec toward RFC-2119 normative phrasing — the spec *prose* stays as-is; the judgment-walk (edge-2b) is the chosen extraction path, not a stopgap pending a rewrite. *(Annotating spec **examples** — Decision 8 — is distinct from prose refactoring and IS adopted; the ruling is about prose only.)* A quantitative spec-coverage percentage is likewise not pursued (member-completeness + AC census is the completeness measure; the field has no percentage metric either).

## Architecture Grounding

### Precept-internal placement

**Layer placement.** One new test project under `test/` (compiler and runtime facets co-located by feature/domain; the `component` trait, not a project boundary, separates them), plus three small pieces of derivation infrastructure: (a) the `[SpecRef]`/`[Covers]` attributes (test-assembly metadata, not catalog metadata — kept off the catalog records so no public-surface/grammar/MCP flow occurs); (b) a coverage meta-test that reflects over the catalog `.All` enumerations; (c) a spec-example harvester that reads `docs/language/*.md`. The suite *reads* catalogs and spec docs; it does not mutate either. The `[Covers]` coverage checklist belongs in the test layer (not the catalog) because it is an assertion *about* the catalog, and putting a "is this tested?" field on catalog records would couple the language spec to its test suite — the wrong direction.

**Cross-component propagation.**
- Runtime (parser, type checker, evaluator, diagnostics): **None** — the suite consumes `Compiler.Compile` output and (eventually) runtime operations; it changes no pipeline code. The runtime facet *describes* the unbuilt runtime's required behavior — the runtime is the **builder** (compile-to-runtime transformation: descriptor tables, dispatch indexes, execution plans) **plus** the **evaluator** (executes the four operations), not the evaluator alone — but adds no runtime code.
- Tooling (syntax highlighting, completions, hover, semantic tokens): **None** — no catalog member names change; nothing flows to grammar/completions.
- MCP (vocabulary, DTOs, tool output): **None** — `[SpecRef]`/`[Covers]` are test-only; they do not appear in MCP catalog projections.

**Breaking changes.** None. No public contract, API surface, diagnostic code, or catalog member name changes.

### External architectural precedent

Using the catalog as the coverage checklist is **novel** (see Decision 2 counter-evidence and Falsifiers): the survey found *no comparator with a machine-readable spec* — every surveyed suite traces to prose or to another implementation [research survey § Open Questions — "no comparator has a machine-readable spec like Precept's catalogs … is a genuine novelty or a known anti-pattern is unresolved — the survey found no precedent either way"]. For the parts that are **not** novel, the design takes directly from the field:
- **Per-test spec anchor over directory-by-section** — Test262: *"esid … is required for all new feature tests … the project is currently transitioning from a naming system based on specification section numbers … instead encode this information using the esid frontmatter key"* [research/references/conformance-testing/test262.md]. Precept's `[SpecRef]` is the same move; domain folders replace section-number directories.
- **Traceability-not-proof completeness** — ACATS: *"it is not possible to exhaustively test for conformity"* yet ships *Coverage Documents* mapping objectives→rules; Kotlin colors every spec sentence green/gray. Precept's `[Covers]` meta-test is the Coverage-Document idea made executable.
- **Specific-diagnostic-at-stage negatives** — ACATS Class B: *"each indicated error in the test is detected and reported, and no other errors are reported."* Precept asserts `PRE####` at a named stage and asserts no spurious diagnostics.
- **Own allowed-red lane** — ACATS and Test262 are run *against* an implementation as separate suites, not wired into the implementation's own build gate; a conformance suite is expected to have failures (the gaps it exists to find).

Precept *diverges* from the field's dominant negative-capture mechanism (Rust `--bless`/TypeScript baselines) deliberately — see Decision 5.

## Decisions

### Decision 1: One feature-organized suite in its own lane (allowed red); `component` (compiler/runtime) and `feature` are per-test traits, worked feature-by-feature to green

**Stakes**: medium

- **Rationale**: a feature is a coherent whole — its compiler facet (does `price × quantity` cancel to type `money`, no PRE0114?) and its runtime facet (does it evaluate to `12.51 USD`?) are two assertions about the *same* feature and belong together, often in one test class. The suite runs in its **own lane, not the default `dotnet test` gate the existing 7000 use**, so it is *allowed to be red* — which fits its purpose (it exists to surface gaps). You work **feature by feature**: `--filter "feature=X&component=compiler"` is the active target, driven green by fixing the gaps it reveals; `component=runtime` tests are `Skip`'d-with-reason (a clean "not yet," un-skipped feature-by-feature when the v1 runtime is built). Two orthogonal traits do two jobs: **`feature`** is the work unit (what you drive green); **`component`** (`compiler`/`runtime`) separates *actionable* red (compiler — your worklist) from *expected* not-yet (runtime). The existing 7000 stay green-gated, so regression detection survives untouched.
- **Tradeoff accepted**: the suite is not a single green/red signal — you read it through filters (`component=compiler` = worklist; per-feature = the green unit), not as one monolithic pass/fail. Accepted because feature-by-feature-to-green is precisely a filtered workflow, and for a solo/pre-release project the per-filter view is more useful than a gate; the green gate that *does* matter (the 7000) is protected by keeping the suite out of it.
- **Alternatives considered**: (a) **suite in the main gate, green-required** — rejected: forces a compiler skip-baseline + manifest to keep the gate green (ceremony to protect a gate you don't need), and mixing conformance red into the 7000 destroys their regression signal (you can't tell a new break from a known gap). The own-lane model deletes that ceremony — gap #1 of the review dissolves. (b) **two projects** split compiler/runtime — rejected: fragments every dual-facet feature across two assemblies, fighting feature cohesion. (c) **defer the runtime facet** until the runtime exists — rejected: authoring it now from the locked `docs/runtime` designs front-loads the acceptance spec (the point of one spec-walk producing both facets).
- **Precedent**: WebAssembly co-locates static and runtime assertions in the *same* `.wast` files, distinguishing them by assertion vocabulary (`assert_invalid` vs `assert_trap`) [research survey, WASM row]; ACATS and Test262 are run *against* an implementation as separate, allowed-to-fail suites, not wired into the implementation's own green build gate [ada-acats.md, test262.md].
- **Sources consulted for this decision**: `src/Precept/Runtime/Evaluator.cs` — 13 `NotImplementedException` markers (runtime calls throw → `Skip`); `docs/runtime/README.md` — *"all operation bodies throw NotImplementedException … the runtime ships with v1"*; `research/references/conformance-testing/webassembly-spec-tests.md`. Grepped `docs/language/precept-language-spec.md` for test-suite structure — spec is silent on test-infra methodology (infra against locked spec, not a spec decision).

### Decision 2: Three-edge coverage model (Catalog↔Impl, Spec↔Impl, Spec↔Catalog)

**Stakes**: medium

- **Rationale**: a catalog-*derived* obligation matrix (edge-1) proves only that the implementation matches the catalog — it *ratifies the catalog's own drift from the spec*. The A2 exchangerate case is the proof: the catalog's `UsageExample` carried the `to`-form while the prose said slash; a catalog-derived test would assert the `to`-form compiles and go green, never noticing the slash form was unimplemented. So the model needs a spec-anchored witness that does **not** route through the catalog: edge-2a (mechanized harvest of spec examples) and edge-2b (judgment census of prose claims with no example), plus edge-3 reconciling catalog `UsageExample`s back to the spec text they should match. The three edges box in divergence from every side.
- **Tradeoff accepted**: edge-2b and edge-3 carry an irreducible human-judgment core (prose is not an enumeration), so their completeness is bounded by walk thoroughness, not provable. Bounded — not eliminated — by claim-census counts, verbatim cites, and adversarial re-walk (two independent extractions diffed).
- **Alternatives considered**: (a) edge-1 only (catalog-derived matrix alone) — rejected: blind to catalog⊊spec, the A2 class. (b) edge-2a only (harvest examples) — rejected: examples cover ≤~40% of normative claims (≈234 harvestable cases vs ≈584+ claim phrases in 11,102 spec lines), so "all examples green" is a false-confidence floor, not the coverage checklist. (c) Spec→Impl only, drop the catalog coverage checklist — rejected: forfeits the one machine-checkable coverage checklist Precept uniquely has.
- **Precedent**: Kotlin's per-sentence green/gray traceability is the working precedent for edge-2b (prose-claim census with a relinking tool for drift) [research survey, Kotlin row]. **Strongest counter-evidence**: the survey's central caution — *"no comparator has a machine-readable spec like Precept's catalogs … is a genuine novelty or a known anti-pattern is unresolved — the survey found no precedent either way"* [research survey § Open Questions]. Response: edge-1 is the novel leg; edges 2–3 are well-precedented (Test262/Kotlin/ACATS), so the novelty is hedged — if the catalog-coverage approach proves an anti-pattern (Falsifier F1), edges 2–3 still stand as the spec-anchored backbone.
- **Sources consulted for this decision**: `docs/Working/spec-conformance-audit-2026-05-30.md` A2 — *"slash form … 9 occurrences … → PRE0076, does not parse … to form … compiles clean … impl matches the catalog"*; `src/Precept/Language/Types.cs` — entries carry `UsageExample` + `QualifierShape`; `docs/language/collection-types.md:524–543` ✓/✗ tables; research survey. Grepped spec for prior settlement of conformance methodology — silent.

### Decision 3: Three orthogonal organization axes — domain folders, `[Covers]` coverage checklist, `[SpecRef]` anchor, feature trait

**Stakes**: medium

- **Rationale**: coverage-proof, navigation, and behavior-grouping are different jobs and a single axis can't serve all three. Domain *folders* (stable doc-file level, not volatile §-section numbers) give navigation and match the author's mental model; `[Covers(catalogMember)]` is the machine-checkable *reverse-direction backstop* — not the source of the feature list (that's the spec, per Decision 4), but the guarantee that every catalog member also got a test (a meta-test fails on any uncovered member, catching the catalog-member-with-no-feature orphan); `[SpecRef(doc, section, quote)]` gives per-test traceability to the authority; `feature` as a `[Trait]` gives the cross-cutting behavior view (and the work unit) without forcing a test into one folder. **The `[SpecRef]` anchor is content-addressed, not line-addressed** — `doc` is the file, `section` is a heading hint for navigation, and the load-bearing anchor is `quote`: a verbatim substring of the spec claim the test enforces. `SpecRefValidationTests` asserts that quote still exists in the doc (within the section when given); a vanished quote turns red and forces a re-link. **Line numbers are deliberately excluded** — they rot on every doc edit below the cite and drift silently (a stale line still resolves to *some* line, so the rot is invisible); a quote either resolves or it doesn't. The existing 7000 are organized by pipeline *stage* (the implementer's view); the conformance suite is organized by spec *domain* (the spec's/author's view) — the organization mirrors the inverted authority.
- **Tradeoff accepted**: a test now carries two-to-three attributes (`[SpecRef]`, `[Covers]`, the `feature`/`component` traits) — authoring overhead and drift risk (a quote can be reworded in the spec, turning the validation red until re-linked). Accepted because a red re-link prompt is exactly the desired drift signal (the spec changed under a test); the failure is loud, not silent. Mitigated by `SpecRefValidationTests` (every test resolves its quote or is explicitly `derived`); the heading hint narrows the re-link search.
- **Alternatives considered**: (a) **line-number anchor** (`doc:line`) — rejected: rots on every edit below the cite and drifts *silently* (a stale line still resolves to some line). (b) directory-by-spec-section — rejected: section numbers/headers rot under spec edits (Test262 is actively abandoning this), and a behavior spans sections. (c) directory-by-catalog-member — rejected: scatters cross-member behaviors (cancellation touches price+quantity+money+operator) across single-member folders. (d) feature-as-folder — rejected: "feature" has no complete enumerable list and has fuzzy membership; demoted to a trait, where it gains multi-tagging and a query filter and loses nothing.
- **Precedent**: Kotlin anchors tests to *sentence text* (section path + paragraph + sentence — content, not line) with a relinking tool for drift; Test262's `esid` is a stable spec anchor explicitly *not* a section number — *"transitioning from a naming system based on specification section numbers … instead encode this information using the esid frontmatter key"* [research/references/conformance-testing/test262.md]; ACATS keeps the mapping in separate Coverage Documents, not directory names [ada-acats.md]. Content-addressing over position-addressing is the field's settled answer.
- **Sources consulted for this decision**: `test/Precept.Tests/ModifiersTests.cs` — `All_ContainsEveryKindExactlyOnce` compares `Enum.GetValues<ModifierKind>()` to `Modifiers.All` (the code-anchored blind spot the conformance axis inverts); research survey C1 (*"field favors per-test spec-anchoring … over directory-by-clause organization"*). Grepped spec — silent on test organization.

### Decision 4: Feature AC-sheet as the unit of acceptance-criteria definition, with stated/derived tagging; derivation is spec-first, catalog-reconciled

**Stakes**: medium

- **Rationale**: acceptance criteria are not lying in the prose to be extracted — many are *implied by the feature* and spread across a table, two paragraphs, and an example (the A1/E4 class). They emerge only from reasoning about the feature as a coherent whole. So the unit of *analysis* is the feature: per feature, reason out the complete AC set across {catalog-defined, positive-compiles, negative-rejected-with-correct-diagnostic, prevention-guarantee, runtime-outcome}. Each AC is tagged **stated** (spec-cited) or **derived** (the analysis concluded it must hold, no cited spec text). Derived ACs with no cite are the high-value findings — a spec gap or an untested implied behavior — and route to the owner, never silently baked.
- **Derivation is spec-first, catalog-reconciled (the catalog is a cross-check, not the source).** Features are identified by **deep-reading the spec domain** — the behaviors, constructs, and rules the prose describes — *independent of the catalog*; then **reconciled against the catalog**. Deriving features *from* the catalog would inherit the catalog's blind spots (a spec feature the catalog never encoded would never become a feature → never be tested — catalog⊊spec at the feature level, the exact failure edge-2/edge-3 exist to kill). The reconciliation is **bidirectional and both orphan directions are findings**: a spec feature with **no catalog member** → a catalog gap (undeclared/unimplemented) = a finding; a catalog member with **no spec feature** → drift or a spec gap = an owner ruling (the A2 class). This is edge-3 operating at the feature-list level. Consistent with Phase 7's locked authority rule (spec + catalog both source of truth; a prose-vs-catalog conflict is an owner ruling, not a silent pick).
- **Tradeoff accepted**: "feature" is not natively enumerable, so the feature *list* could be incomplete. Bounded by bidirectional reconciliation: every spec section AND every catalog member must be claimed by ≥1 feature; an orphan in either direction is a missing feature (or a drift finding). That makes the feature list auditable, not provable — and grounds it in the spec, with the catalog as a backstop rather than the authority.
- **Alternatives considered**: (a) sentence-level claim extraction as the primary unit — rejected: misses implied/cross-cutting ACs (exactly the A1/E4 bugs); kept as edge-2b *input*, not the AC-definition unit. (b) keyword extraction of normative sentences ("shall"/"must") — rejected: Precept's spec has no RFC-2119 discipline (claims appear as ✓/✗ table cells, definitions, plain declaratives), so keywords give false negatives (the dangerous kind) and false positives; normativity is semantic, not lexical. Keyword sweep retained only as a recall aid / census floor. (c) catalog-first feature derivation — rejected: inherits the catalog's blind spots (above).
- **Precedent**: Kotlin primary/secondary sentence linking is the closest field analog to per-claim AC sheets [research survey, Kotlin row]; the category-partition method (Decision 6) is the per-feature AC-decomposition discipline (Ostrand–Balcer).
- **Sources consulted for this decision**: `docs/Working/spec-conformance-audit-2026-05-30.md` E4 — *"PRE0137 … gated on both operands being TypeKind.Quantity … the price-cancellation path skips it … cancels silently"* (a derived AC the spec never stated outright); research survey synthesis (a) mechanizable-vs-judgment. Grepped spec — silent.

### Decision 5: Negative coverage = specific diagnostic at a specific stage, hand-asserted (not `--bless`/baseline)

**Stakes**: medium

- **Rationale**: "the program was rejected" is a weak oracle; conformance requires the *right* diagnostic (`PRE####`) at the *right* pipeline stage, and *no spurious* diagnostics. Critically, the suite must NOT capture expected output by snapshotting the implementation (`--bless`/baselines), because that drifts the oracle toward "what the compiler currently emits" — which is precisely the impl-anchored trap the existing 7000 tests already are. Negatives are hand-asserted against the spec's named diagnostic.
- **Tradeoff accepted**: hand-asserting exact diagnostics couples tests to diagnostic codes/wording, raising maintenance cost when wording changes. Mitigated by asserting the *code* + *stage* (stable) and tolerating message-substring matching, not full-message equality.
- **Alternatives considered**: (a) `--bless`/baseline snapshot (Rust/TS) — rejected: ergonomically superior but shifts the oracle to the implementation; the survey names this hazard explicitly. (b) exit-code/"compiles-or-not" only — rejected: insufficient (ACATS fails tests that report *spurious* errors; we want the same both-directions check).
- **Precedent**: ACATS Class B — *"each indicated error … is detected and reported, and no other errors are reported"*; Test262 `negative: {phase, type}`; WASM `assert_invalid`/`assert_malformed`/`assert_trap` [research survey rows]. **Strongest counter-evidence**: blessing is the field's *dominant* mechanism (Rust/TS/Go/WASM-prefix) — i.e. most suites do the thing we're rejecting [rust-compiletest.md]. Response: those suites' spec post-dated their code (no spec oracle available), so blessing was their only option; Precept has a spec-first oracle and the explicit goal of escaping impl-anchoring, so the field's majority choice is inapplicable to our constraint.
- **Sources consulted for this decision**: research survey C3/C4 (*"a blessed baseline encodes what the implementation emitted, so a wrong-but-stable diagnostic gets blessed as correct"*); `docs/language/precept-language-spec.md § 0.1.1` prevention. Grepped spec — silent on assertion mechanism.

### Decision 6: Combinatorial control = category-partition equivalence classes + all-pairs; catalog-generated `[Theory]` data; full cross-product only for the interacting axes

**Stakes**: medium

- **Rationale**: the input space (type × qualifier × modifier × operator × operand × context × valid/invalid) is effectively infinite. The compiler treats inputs by rule, not by value, so one representative per spec-distinguished equivalence class suffices; category-partition with `[error]`/`[single]`/`[if]` constraints prunes the frame set, and all-pairs covers axes the spec treats as independent. Full cross-product is reserved for the genuinely-interacting axes (dimension/unit/operator — the A1/E4 cluster). Positive-case data is generated as `[Theory]` `MemberData` from catalog `UsageExample`/`QualifierShape`; negatives by one-axis mutation off the legal forms — so "a lot of combinations" is catalog-emitted data, not hand-written files.
- **Tradeoff accepted**: equivalence-class partitioning can miss interaction bugs *between* classes; all-pairs catches pairwise but not higher-order interactions. Accepted because full cross-product is intractable and the interacting cluster gets the full product anyway.
- **Alternatives considered**: (a) exhaustive cross-product everywhere — rejected: intractable and unnecessary (`[single]`/`[error]` choices need one test each). (b) generative/differential at scale (sqllogictest) — rejected: needs a non-prose oracle (another engine), which Precept doesn't have, and it says nothing about *which* diagnostic.
- **Precedent**: Ostrand–Balcer category-partition (CACM 1988) — *"FIND example explodes to 1,944 frames, pruned to 125 via constraints"*; all-pairs as further reduction [research/references/conformance-testing/methodology-and-lighter-comparators.md].
- **Sources consulted for this decision**: `src/Precept/Language/Operator.cs` — `OperatorMeta(… ResultType, ResultTypePolicy, … UsageExample)` (the legality + example metadata that drives generation); `src/Precept/Language/Types.cs` — `QualifierShape` per type; research survey C5. Grepped spec — silent.

### Decision 7: Runtime facet carried as `Skip`'d not-yet tests, un-skipped feature-by-feature when the runtime is built

**Stakes**: medium

- **Rationale**: the runtime — the **builder** (compile-to-runtime transformation) plus the **evaluator** (the four operations) — is unbuilt; every operation throws `NotImplementedException`, so runtime-facet tests can't pass. Each carries `[Trait("component","runtime")]` + a structured skip reason (`Skip = "runtime unbuilt — evaluator.md Fire (v1)"`). `Skip` (not red) keeps them a clean *not-yet* signal, visually distinct from compiler-facet red (which is *actionable*). When the v1 runtime is built, you un-skip feature-by-feature and drive those green — the same loop as the compiler facet, later; un-skipping a test *is* the act of starting TDD on that runtime area. Because the suite runs in its own allowed-red lane (Decision 1), no skip-manifest / ratchet / leak-guard gate ceremony is needed — there is no green gate for a mis-tagged runtime test to break; a mistake fails loudly in the lane and is caught at review.
- **Tradeoff accepted**: skipped tests don't run, so they can rot (reference a since-renamed construct) until un-skipped. Mitigated: the skip reason cites the `docs/runtime` design section, and runtime areas are reviewed at the slice boundary when the runtime phase opens them. Without a leak-guard, a runtime test mistagged `component=compiler` would simply fail in the lane (not silently pass) — acceptable since the lane tolerates red and the per-feature filter surfaces it.
- **Alternatives considered**: (a) skip-manifest + ratchet + leak-guard to keep a green gate (the earlier draft, when the suite was in the main gate) — rejected with Decision 1: there is no gate to protect, so the ceremony is dead weight for a solo/pre-release project. (b) leave runtime tests *red* rather than skipped — rejected: their red is long-lived (until v1) and would bury the small, actionable compiler-facet red even under filtering; `Skip` is the cleaner not-yet marker. A burndown view, if wanted, is just `--filter` (features with green `component=compiler` / total) — no manifest required.
- **Precedent**: the runtime designs (`runtime-api.md`, `evaluator.md`, `precept-builder.md`) are the acceptance spec these `Skip`'d tests encode; field precedent for authoring-before-implementation / red-by-design is the survey's Open Question on the topic [research survey § Open Questions].
- **Sources consulted for this decision**: `docs/runtime/README.md` — *"the runtime ships with v1"*; `src/Precept/Runtime/Evaluator.cs` (operations throw `NotImplementedException`). Grepped spec — silent.

### Decision 8: Spec examples carry fence annotations declaring their expected outcome; the harvester (edge-2a) reads them, and an un-annotated ` ```precept ` fence is a lint failure

**Stakes**: medium

- **Rationale**: edge-2a's "scrape every example and assert its outcome" is not mechanical as the spec stands — most ` ```precept ` blocks are *fragments* (no `precept` header / undeclared states, e.g. `business-domain-types.md:210` declares `from Pending` but never declares `Pending`), many are *illustrative anti-examples* with no conformance claim (the "Before" block at `:196`), the outcome marker is non-uniform (inline `✓` in a comment here, a ✓/✗ table column in `collection-types.md`), and ✓/✗ rows are type-expressions, not programs. A **fence-annotation convention** makes harvest deterministic and high-coverage: `` ```precept expect=ok `` (must compile clean), `` ```precept expect=PRE0114 `` / `expect=PRE0114@type` (must reject with that code, optionally at that stage), `` ```precept fragment expect=ok `` (a fragment — the harvester wraps it in a minimal scaffold before compiling), `` ```precept illustrative `` (no claim — skipped). **Every ` ```precept ` fence must carry exactly one annotation**; an un-annotated fence fails a doc-lint test — so the one-time sweep is provably complete and future omissions are loud, not silent. ✓/✗ tables carry the verdict (+ `PRE####` where applicable) in a parseable column; the harvester synthesizes a precept around the row's type expression. (Runtime value-outcomes stay in runtime-facet tests / AC sheets, not fence annotations — fences cover compile-outcomes only.) A side benefit: every `expect=ok` example becomes self-verifying — if it stops compiling, the harvest goes red.
- **Tradeoff accepted**: a one-time annotation sweep of `docs/language` (~120 ` ```precept ` blocks + the ✓/✗ tables) plus ongoing discipline (new examples carry an annotation, enforced by the lint). And it is a spec-*docs* change — but a **scoped, owner-approved exception** to "leave the spec as-is" (2026-06-01): it annotates *examples*, it does not reword *prose* (the RFC-2119 refactoring that remains ruled out). The info-string is safe — no repo tooling parses markdown ` ```precept ` fences (verified: the LS/grammar operate on `.precept` files, not doc fences), and markdown renderers/highlighters key on the first token, ignoring the rest.
- **Alternatives considered**: (a) heuristic harvester + denylist (Option B) — rejected: fragment-detection and normative-vs-illustrative classification are guessy; a misclassified anti-example yields meaningless green. (b) scope edge-2a to only the cleanly-realizable subset and lean on edge-2b for the rest (Option C) — rejected: leaves real example-coverage on the table and keeps edge-2a a sketch; annotation makes edge-2a a first-class, near-complete harvest. (c) leave the convention undefined and harvest later — rejected: the ambiguity is exactly what makes "scrape and run" fail; resolving it is the point.
- **Precedent**: Rust **doctest fence attributes** — `` ```rust,compile_fail ``, `` ```rust,no_run ``, `` ```rust,ignore ``, `` ```rust,should_panic `` — info-string annotations on documentation code-fences that tell the test harness how to treat the example; this is precisely the pattern, applied to ` ```precept `. WebAssembly `.wast` wraps each example with its expected outcome (`assert_invalid`/`assert_return`) [research/references/conformance-testing/webassembly-spec-tests.md].
- **Sources consulted for this decision**: `docs/language/business-domain-types.md:192-218` (the "Before"/"After" pair — a fragment + an illustrative anti-example + an inline-`✓` outcome, all in one place); `docs/language/collection-types.md:524-543` (✓/✗ outcome tables); the fence-consumer check (`grep` over `tools/`, `test/` — no markdown-fence parser that the info-string would break). Grepped `docs/language/precept-language-spec.md` for an example-annotation convention — silent (this defines one).

### Decision 9: Runtime-facet determinism — invariant culture + pinned TZDB + an injectable per-fire clock; the clock seam is a recorded v1 runtime requirement

**Stakes**: medium

- **Rationale**: runtime-facet tests assert computed *values*, which must be deterministic (Principle 3). The spec already closes two of the three leak sources by design — string ops are **invariant culture** and comparison is ordinal (`primitive-types.md:668-669, :493`), and `now()` is **UTC-always** with zone-awareness always explicit (`temporal-type-system.md:564`) — so the suite *verifies* those rather than fighting them. The live requirement is `now()`: it is **"environment-relative determinism" (Locked Decision #9)** — *"different results when fired at different times … same inputs, same outputs within a single fire … cannot freeze the clock"* (`temporal-type-system.md:566`). Two things follow: (1) within one `Fire`, every `now()` must see **one** instant (sampled once per operation), and (2) to conformance-test any `now()`-bearing rule deterministically, the test must fix that instant — which is on-spec, since the injected instant is just "an input." Both require the runtime to resolve `now()` through an **injectable per-operation clock seam** (NodaTime `IClock`/`FakeClock`), not a hardcoded `SystemClock` call. The runtime designs don't yet specify that seam, so this design **records it as a v1 runtime requirement** while the runtime is still on paper. TZDB version is pinned because the `timezone` type is *"bounded by the TZDB version"* (`temporal-type-system.md:260`).
- **Tradeoff accepted**: the suite carries a determinism fixture (invariant culture, pinned TZDB, fixed per-fire instant) that every runtime-facet value test runs under — minor harness weight; and it imposes a constraint on the unbuilt runtime (`now()` routes through an injectable clock, not a hardcoded system-clock read). Accepted because the constraint is already implied by the spec's within-fire consistency requirement and is standard NodaTime practice — capturing it now is far cheaper than retrofitting clock injection at v1.
- **Alternatives considered**: (a) read the system clock directly in the evaluator — rejected: makes every `now()`-bearing rule untestable, and re-reading mid-fire would violate the spec's "same inputs, same outputs within a single fire." (b) drop `now()`-bearing rules from runtime conformance — rejected: `now()` is a locked language construct (`precept-language-spec.md:1562`, `temporal-type-system.md:558`); leaving its runtime behavior untested abandons a real surface. (c) impose culture/zone pinning but skip the clock seam — rejected: the clock is the only one of the three the spec hasn't already closed.
- **Precedent**: NodaTime `IClock` / `FakeClock` — the standard injectable-clock pattern for deterministic temporal testing; `docs/runtime/runtime-api.md:345` already shows the host passing time *as data* (`SystemClock.Instance.GetCurrentInstant()` into a `.Set<Instant>`), and this extends the same time-as-input discipline to `now()`.
- **Sources consulted for this decision**: `docs/language/temporal-type-system.md:558-566` (now() UTC-always; Locked Decision #9 environment-relative determinism; "same inputs, same outputs within a single fire"), `:260` (`timezone` bounded by TZDB version); `docs/language/primitive-types.md:668-669, :493` (invariant culture, ordinal compare); `docs/runtime/runtime-api.md:345` (host time-as-data); `docs/runtime/evaluator.md` — no `now()`-resolution / clock-seam spec (the gap this records). Grepped runtime designs for `clock`/`IClock` — silent on the seam.

## Method — per-area workflow and sequencing

The suite is built **one spec domain at a time** (the domain folders of Decision 3 = the sub-slice units), and within an area you work **feature by feature**. Each area starts with *reading*, not coding:

1. **Deep-read the spec domain** → identify features from the prose (Decision 4, spec-first).
2. **Feature inventory** → the area's feature list, each feature with its draft AC set (stated/derived).
3. **Catalog reconcile** → map features ↔ catalog members; bidirectional orphans recorded as findings (catalog gap / drift-owner-ruling).
4. **AC sheets** → per feature, the complete AC set across the five legs (compiler + runtime facets).
5. **Tests, feature by feature** → for each feature, realize its ACs, then drive `feature=X&component=compiler` to green (fixing the gaps it reveals — each fix is a Phase 7 slice); its `component=runtime` ACs are authored and `Skip`'d as the v1 acceptance spec. The compiler-facet red that remains is simply the features not yet green — the live worklist — held in the suite's own allowed-red lane (Decision 1); no baseline/manifest is needed to manage it.

Steps 1–3 are the **planning deliverable**: they size the area (feature count) and surface its gaps *before* any test is written, which is what makes the program's total scope knowable instead of guessed. The whole suite is therefore **owner-paced and incremental** — it does not require building all ~150 features up front.

**Sequencing.** Areas are ranked by where features and bugs both cluster, not walked alphabetically. Working order (refine in `/plan`): **BusinessDomainTypes** and **TemporalTypes** first (highest feature count — ~30 each — and the home of A1/A2/A3/A4/E4 and the B/C-class register rows), then PrimitiveTypes / CollectionTypes / Expressions, then Constructs / Lexical / Grammar / Diagnostics / Stateless / Proof. The phase has no fixed end-count; it runs area-by-area until the owner judges the language matches its spec (Phase 7's locked exit criterion), pausing for review at each area boundary.

**Scale, stated honestly.** At ~150 features × {positive × equivalence-classes, negative-with-diagnostic, guarantee, runtime}, the suite is on the order of **~3,000–5,000 cases** built over a sustained, owner-paced program — roughly doubling the existing suite over time. This is a multi-area program, not a single slice; the area-by-area, feature-by-feature cadence is what keeps it tractable and reviewable.

## Falsifiers

- **F1 (the catalog-coverage approach is an anti-pattern).** If, after building the compiler facet, the catalog-derived edge-1 obligations produce a materially higher false-finding rate (tests that fail for catalog-internal reasons unrelated to any spec claim) than the spec-anchored edges 2–3, OR generating obligations from `UsageExample`/`QualifierShape` proves to require more per-member hand-correction than hand-authoring would have — then driving coverage from the catalog is net-negative and edge-1 should be demoted to a coverage *ledger* only (keep `[Covers]`, drop generation), with edges 2–3 as the primary suite. (This is the novelty the field gave no precedent for.)
- **F2 (the prose census doesn't converge).** If two independent edge-2b walks of the same spec area diff by more than ~20% of claims after one reconciliation pass, the judgment core is too unstable to call "auditable," and edge-2b needs either spec normative-refactoring (the ruled-out owner decision, reopened) or a tighter extraction protocol before it's trustworthy.
- **F3 (blessing was right after all).** If hand-asserting diagnostics causes conformance tests to churn on every benign diagnostic-wording change to the point that maintainers routinely "fix" tests to match new output without checking the spec, the hand-assert discipline has collapsed into de-facto blessing, and the negative-assertion granularity (code+stage vs full message) needs to drop further toward code-only.
- **F4 (the coverage checklist is hollow).** If a catalog member can sit `[Covers]`-green with a single trivial test while a real spec behavior of that member is untested and ships broken, the "green = covered" signal is misleading enough that `[Covers]` needs an adequacy floor (≥N ACs per member, or stated+derived AC-sheet completeness) rather than ≥1 test.

## Operational dimensions

- **Security** (touches source-text ingestion — the harvester feeds spec-extracted `.precept` text through `Compiler.Compile`): the input is first-party repo content (`docs/language/*.md`), not untrusted external input, so no new attack surface; the harvester must still fail safe on a malformed fence (skip + report, never hang) — a pathological-input guard, asserted by a harvester unit test.
- **Observability** (touches the diagnostic surface): conformance failures must report the `[SpecRef]` (doc § section + quoted claim) and, for negatives, the expected-vs-actual `PRE####` and stage — so a red test points the maintainer at the exact spec claim and diagnostic, not just "assertion failed."
- **Evolvability** (depends on the spec-doc markdown conventions + one external standard — the TZDB): (a) the harvester depends on the Decision-8 fence-annotation convention in `docs/language`. Under-collection is guarded structurally — `FenceAnnotationLintTests` fails on *any* un-annotated ` ```precept ` fence, so a new (or convention-drifted) example can't be silently dropped; it must be classified `expect=…`/`fragment`/`illustrative` to pass the lint. (b) Runtime-facet temporal conformance is bound to a **pinned NodaTime TZDB version** (the `timezone` type is "bounded by the TZDB version"); a TZDB bump is a deliberate, reviewed change, and the determinism fixture (Decision 9) pins the version so a bump can't silently shift a zone-conversion result.
