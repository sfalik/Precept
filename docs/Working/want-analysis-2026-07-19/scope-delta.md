# Scope Delta — the Want Doc vs. the v3 Readiness Plan

**Status**: Draft analysis - 2026-07-19 (agent-authored; evidence only; rulings remain the owner's)

**Question answered** (owner's words): "does this materially change the compiler scope vs the previous attempts? What is added / removed"

**Inputs compared.**

- **The want doc** — `docs/Working/what-i-want-2026-07-16.md` (authoritative; the owner's statement of what the compiler and runtime should be).
- **The previous attempt** — the v3 readiness plan `docs/Working/compiler-readiness-plan-2026-07-12.md` and its companions: the Stage-0b architecture (`compiler-readiness-plan-2026-07-12-architecture.md`), the proof-engine practicality roadmap (`proof-engine-mvp-and-proof-phases-2026-07-12.md`), and the decision ledger (`proof-engine-decision-ledger-2026-07-12.md`). The 2026-07-13 meta-plan (`compiler-readiness-meta-plan-2026-07-13.md`), which re-widened v3's proof-engine-MVP scope back to the whole compiler, is treated separately in § 4 because it changed methodology and denominators, not the proof-engine build content — it explicitly kept the v3 slices intact (meta-plan § 9 item 6, `:872-876`).

**Terms used below** (defined once). An **obligation** is a single check the compiler must prove ("this divisor is never zero", "this rule still holds after this write"). A **premise** is a declared fact a proof may use (a field modifier, an argument constraint, a handler guard, a rule assumed to hold in the pre-state). **Single-hop** is the current engine's locked discipline of using one cross-field fact at a time and never chaining a second fact through it (v3 ledger #3). A **certificate** is the show-your-work record attached to a verdict; a **checker** is a small component that replays a certificate's steps and confirms each one.

**One-line answer**: yes — the want doc materially expands compiler scope on four axes (a new obligation family: rules proven as invariants at every write site; proof machinery that combines premises in ways v3 deliberately deferred; a live certificate checker at two call sites where v3 shipped a format only; a defined runtime contract where v3 scoped no runtime at all), moves two explicitly-deferred items back into scope, removes almost nothing from v3's build list (all seven v3 slices survive as substrate), and retires two author-facing framings that were folded into v3's ruling #1.

## 2. Which deltas are material, and why

### 2.1 The obligation surface inverts: rules become theorems, not just premises (rows 1, 2, 4)

This is the largest scope change. In v3 and its companions, obligations come from declared bounds and faultable operations (division, sqrt, length, count, qualifiers), and rules are *inputs* the engine may read to discharge them. The want doc makes every rule itself a proof obligation at every write site of every field it mentions, plus an establishment obligation at every initial event, plus an ingress-premise closure for editable-field writes. The companion roadmap verified live that today "the compiler generates zero checks" for a `nonnegative` on a computed money field (`proof-engine-mvp-and-proof-phases-2026-07-12.md:273`) and that write-site obligation generation "is Phase 5 readiness-plan work" (`:76`) — work that is in **no** v3 slice. The meta-plan's prevention denominator does not cover it either: its creation-completeness axis is defined over *faultable positions* ("a division, an array index, an overflow-prone arithmetic step", `compiler-readiness-meta-plan-2026-07-13.md:53-57`), not rule-preservation obligations. So the want adds an obligation family that neither prior attempt enumerated, and it multiplies the obligation count roughly by (rules × write sites of mentioned fields) — the denominator any completeness machinery must now range over.

### 2.2 The inductive step needs premise combination that v3 locked out (rows 3, 22)

The want's own worked example makes the tension concrete. `Deposit`'s proof combines the inductive hypothesis (`Balance >= -OverdraftLimit` held in the pre-state) with the arg constraint (`Amount >= 0`) to conclude the post-state rule holds (`what-i-want-2026-07-16.md:95`). `OpenAccount` combines two arg constraints (`:94`). Adding one inequality to another is exactly what the companion roadmap defines as §1b territory — "machinery that adds inequalities together" (`proof-engine-mvp-and-proof-phases-2026-07-12.md:53`) — and the ledger ruled: "DEFER §1b... `spec:256` override: NOT authorized — build nothing that requires it" (`proof-engine-decision-ledger-2026-07-12.md:51`), a fence v3's Definition of Done restates ("Out of scope stays out — §1b... not built", `compiler-readiness-plan-2026-07-12.md:532-533`). Additionally, the engine's shipped rule-reading is restricted to bare `field op field` shapes — "The moment you write `MonthlyPayment * 3` instead of a bare field name, the rule becomes invisible" (`proof-engine-mvp-and-proof-phases-2026-07-12.md:297`) — while the want's flagship rule (`Balance >= -OverdraftLimit`) carries a negation on one side.

This is not a hole in the want on its own terms — the want doc is authoritative and does not bind itself to single-hop. But it means one of two things for scope: either ledger #3's deferral (and the single-hop rail it protects) is revised for the restricted, structured combination the inductive step requires — the want doc itself is arguably the ledger's own "revisit trigger" arriving — or the proof engine gets an inductive-step prover that is a new machinery class outside both §1a's syntactic matcher and §1b's general solver. Either way it is a build the v3 plan explicitly does not contain, and it is the single most feasibility-sensitive item the follow-on study has to price. (The want anticipates this: "the practicality of this proof is exactly what the follow-on study has to establish", `what-i-want-2026-07-16.md:123`.)

### 2.3 The checker goes live, and grows a second call site in the runtime (rows 12-14)

v3's Decision B retracted the checker from the MVP: format only, "no live re-checker, no checker-gated mint" (architecture § 1.3), with §5b priced Large and deferred as builder-side assurance. The accepted tradeoff was explicit: "a strategy bug that also corrupts its own certificate would ship uncaught until §5b lands" (architecture § 1.3, `:50`). The want reverses the deferral — one small checker, two call sites — and adds a call site no prior document scoped at all: a runtime load-time gate that refuses to govern under an unverified certificate (`what-i-want-2026-07-16.md:189-192`). It also gives the certificate a consumption semantics v3 never had: the premise list becomes the runtime's validation surface, derived rather than maintained in parallel (`:198`). Two consequences for scope: the §5a certificate-format design pass (still owed under v3 — the `CertificateSteps` membership is unruled) now has a second, harder consumer to design for (a machine gate, not just hover rendering); and the checker itself moves from "later phase, optional" to load-bearing for the guarantee ("rooted in verification the runtime performed itself", `:192`).

Interaction worth noting: this materially changes the meta-plan's honest-limits story. The meta-plan names discharge soundness as a residual that "cannot be closed... until a discharge oracle exists to test against" and surfaces "is soundness-modulo-a-searched-residual an acceptable handoff bar?" as an owner decision (`compiler-readiness-meta-plan-2026-07-13.md:976-981`, `:1000-1005`). A live checker that replays every derivation step is precisely the independent confirmation whose absence created that residual — it shrinks the residual to "bugs shared by prover and checker" plus "wrong certificates the checker's step semantics cannot catch." The want does not eliminate the residual, but it changes the decision the meta-plan surfaces.

### 2.4 The runtime acquires a defined contract (rows 15-18)

Prior attempts deliberately scoped no runtime: v3 is a compiler plan, and the meta-plan's denominator C is a closed *contract spec*, "not running code" (`compiler-readiness-meta-plan-2026-07-13.md:935-938`). The want fills in the contract's content: evaluation-time work is the declared premises only (arg ingress, editable-write ingress, guards); fault checks are omitted at evaluation time; rules are never re-evaluated post-mutation; ingress is exactly two points and restore is trusted; load-time is where verification happens. Two prior-canon artifacts are retired by this: the per-proof PROVEN/GOVERNED author-facing surface and the fault-scoped reading of "no deferral", both folded into ledger ruling #1 (`proof-engine-decision-ledger-2026-07-12.md:24`) — under a uniform guarantee with no deferral there is no GOVERNED-instead-of-proven category for a per-proof label to name. The want itself flags the one philosophy sentence this collides with (Fire "evaluates all applicable constraints against the resulting configuration") as owner-gated rewording (`what-i-want-2026-07-16.md:203`) — consistent with the standing rule that philosophy edits await the owner.

### 2.5 Medium deltas

- **Missing-premise computation (row 9).** v3 deliberately shipped only the cheap reporting half (numbers + one breaking example) and deferred the derived-safe-condition half as Large with a stated readability risk (`proof-engine-mvp-and-proof-phases-2026-07-12.md:242`, `:504`). The want's Clear Explanations section demands it — every rejection in the mutation table names the missing premise, and the compiler "computes the guard or arg constraint that would close the proof and shows it" (`what-i-want-2026-07-16.md:167`). A deferred-Large item is now core UX.
- **Modifiers-as-sugar unification (row 10).** v3's engine architecture keeps declared bounds and rules as separate fact sources with separate folds (the whole reason §6 exists). The want mandates one underlying constraint mechanism. This is less new capability than an architectural constraint on how the premise machinery is built — but it dissolves a class of asymmetry bugs (the §6 gap was exactly "bounds readable, equivalent rule not") by construction, and any build plan derived from the want should treat the unification as load-bearing, not cosmetic.
- **Dead rows (row 20).** The want demands compile-time rejection of never-true-guard rows, with the guard checked against declared constraints *including rules*, and unreachability propagated to consequent states (`what-i-want-2026-07-16.md:117`, `:143`). The ruled structural-severity family keeps `UnsatisfiableGuard` and `AlwaysRejecting` at Warning (`compiler-readiness-plan-2026-07-12.md:139-140`). This is a genuine severity-and-detection delta against a 2026-07-12 owner ruling — smaller than the headline items, but it is a place where the want and a prior ruling give different answers and the owner may want to re-affirm one.
- **Acceptance frame (row 26).** v3's shippability bar is "the corpus's house style compiles"; the want's bar is "every premise-deletion mutation rejects with a teachable message" (`what-i-want-2026-07-16.md:103-121`). These are complementary (acceptance side vs rejection side), but a plan rebuilt from the want owes a rejection-side test matrix of a kind v3's DoD does not have — the mutation table is effectively a new class of acceptance criteria.

### 2.6 Non-deltas worth stating (so the delta reads neutral)

The want does **not** expand everything. Unchanged and directly reusable: prove-or-reject itself and the no-escape-hatch ruling (ledger #1, #9); the certificate admissibility criterion (legible / performant / right-sized / earns-its-place, ledger #2 — the want's "small checker" and proof-carrying-code precedent sit squarely inside it); the three-way verdict DU and certificate-on-every-verdict (Decision A); the §5a certificate format's shape (span-cited premises, recomputable steps); the witness gate (§4a); the reachability/dead-end/terminal Error flips; the single-precept boundary; and the deferrals of aggregates, compute-then-check, and the Presence/KeyPresence configuration witness, on which the want is silent. Overflow stays what ledger #7 said it was: the intended end-state, staging unaddressed by the want. And nothing v3 planned to build is dropped — the delta is expansion plus two reversed deferrals, not replacement.

### 2.7 The meta-plan interaction

The 2026-07-13 meta-plan had already re-widened v3 from a proof-engine MVP to the whole compiler (`compiler-readiness-meta-plan-2026-07-13.md:12-15`, § 9.1) — so "the previous attempt" is really two nested scopes: v3's build content inside the meta-plan's completeness methodology. The want changes the *content* both range over, in three ways: (a) the prevention denominator widens — creation completeness must now enumerate rule × write-site preservation obligations and initial-event establishment obligations, not only faultable positions (§ 2.1 above); (b) denominator C's runtime contract acquires its content from the want (premises-only evaluation, load-time gate, ingress model) instead of being reconciled out of self-contradicting canon — the meta-plan's Stage-0 boundary-consistency pass (`:180-187`) would now reconcile *to the want doc*; and (c) the discharge-soundness residual and its owner decision point are altered by the live checker (§ 2.3 above). The meta-plan's machinery itself (spec freeze, five-angle enumeration, the three creation-completeness build checks, TDD discipline) is orthogonal to the want and survives; nothing in the want contradicts it.

### 2.8 The two open questions, as scope contingencies (not resolved here)

- **Time-referencing rules** (`what-i-want-2026-07-16.md:207`). Scope impact is binary: if rules may reference the current moment, the inductive model needs a step nothing in either prior attempt sketches (no event, no ingress, no write); if time belongs only in guards, the delta is a language-surface restriction plus a rejection diagnostic for time-referencing rules — cheap. Until ruled, the obligation-family denominator (§ 2.1) is not fully enumerable.
- **Cross-precept promise** (`:208`). No MVP scope impact — the single-precept boundary matches v3's implicit scope. It becomes a scope question only when message passing / saga precepts are designed.

## 3. Bottom line

Measured, not assumed: the want doc **materially expands** compiler scope relative to the v3 plan and its companions. **Added**: rule-preservation and rule-establishment obligations at every relevant write site (the induction model); premise-combination machinery of at least a bounded form v3 locked out; a live certificate checker with a compiler-stage call site; a runtime load-time verification gate; the certificate-derived runtime validation surface; the defined runtime evaluation contract and two-point ingress model; the modifiers-rules unification; rule-aware dead-row rejection. **Moved from deferred to demanded**: the missing-premise computation (§4b) and the checker (§5b, extended). **Removed**: nothing from v3's build list; retired are the per-proof PROVEN/GOVERNED author-facing surface and the fault-scoped no-deferral reading. **Unchanged**: prove-or-reject, the certificate criterion, the verdict/certificate/witness substrate, the structural Error flips, the single-precept boundary, and the untouched deferrals (aggregates, compute-then-check, §1b-as-general-solver remains ruled-out as such, overflow staging).
