# Comprehensiveness — the want doc's proof model tested against the full language surface

**Status**: Draft analysis - 2026-07-19 (agent-authored; evidence only; rulings remain the owner's)

## Question and method

The owner asked: the worked example in `docs/Working/what-i-want-2026-07-16.md` is illustrative, not exhaustive — proof for collections, for example, is not included. *What is missing, and is it just "more of the same" or are there significant gaps?*

This report enumerates the actual language surface and tests the want doc's model against each area. The model under test is: proof by induction over reachable configurations, with four premise classes — (a) field modifiers, (b) arg constraints, (c) the handler's guard, (d) all rules holding in the pre-state — plus symmetric write-site obligations, exactly two ingress points (event args, editable-field writes), the fault family handled by the same premises, and certificates recording each closed proof.

The surface inventory is derived from:

- The catalog inventory — 15 catalogs, of which 12 define the language (`docs/language/catalog-system.md` § Completeness Principle): Tokens (138), Types (32), Functions (23), Operators (21), Operations (201), Modifiers (29), Actions (15), Constructs (15), ExpressionForms (15), Constraints (5), ProofRequirements (13), Outcomes (3).
- The nine per-unit coverage inventories from the 2026-07-14 exhaustive enumeration (`docs/Working/exhaustive-gap-analysis-2026-07-14/coverage/*.md`), which walk every block of the canonical type docs and the spec (4,592 cells total across primitives, collections, temporal, business-domain, parser, type-check, semantics/proof, and the proof-engine prevention doc).
- The canonical type docs themselves at specific load-bearing lines, and six representative samples (`inventory-item`, `global-meeting-scheduler`, `hotel-reservation-management`, `insurance-claim-adjudication`, `saas-customer-success`, `saas-customer-onboarding`).

Disposition vocabulary:

- **COVERED** — the worked example's pattern applies directly; nothing new to prove.
- **MECHANICAL EXTENSION** — same premise-classes pattern, more plumbing; what extends is stated.
- **STRUCTURAL GAP** — needs proof theory or model concepts the want doc does not describe; what is missing is stated in the per-gap prose below.

Bottom line for the owner's question: **roughly four-fifths of the surface is "more of the same."** The premise-class model generalizes cleanly across scalars, strings, presence, non-quantified collections, static business-domain qualifiers, ensures, computed fields, and the extra write-site categories — the existing docs and the 4,592-cell corpus already frame those obligations in prove-or-reject shape with guard/modifier discharge. But five areas are structural: they need proof theory or model concepts the want doc does not currently describe. They are detailed next.

## Structural gaps

### G1 — Quantified collection rules (and what modifiers-are-sugar entails)

**What canon says.** `docs/language/collection-types.md:796` (the Element-level constraints callout): a per-element bound can be spelled two ways — "(1) an **inner-type value modifier** — `queue of string maxlength 200` — declares a static per-element type bound the proof engine reads at write- and read-sites; (2) a **quantifier predicate** — `rule each x in C (x > 0)` — is a **runtime governance rule** over the current elements … the inner-type modifier carries a bound back to a read-site … a quantifier does not." The Quantifier Predicates section (collection-types.md:800-861) is a locked design, not yet implemented, covering `each`/`any`/`no` in rule and guard position over all nine collection kinds.

**Why this is structural under the want.** Two independent reasons:

1. *The runtime-governance classification is deferral.* A `rule each x in C (x > 0)` that is enforced only by runtime evaluation over current elements is precisely "a business rule whose enforcement the compiler cannot prove complete … handed to the runtime" — which the want doc's No-deferral section forbids. Under prove-or-reject, the compiler must prove every collection write site preserves the quantified rule, or reject.
2. *The modifiers-are-sugar ruling makes the proof theory unavoidable even if the `each` keyword never ships.* The want doc rules that a modifier is "a compact spelling of a rule" (what-i-want-2026-07-16.md § The compiler's promise). An element value modifier like `queue of string maxlength 200` can only desugar into a universally quantified rule over the queue's elements. So the one-constraint-mechanism claim forces the rule language's semantic core to contain quantified element constraints, and the proof engine to reason about them — whether or not the surface syntax exists.

**What is missing from the want doc's model.** The four premise classes prove scalar facts by substitution and interval reasoning. Quantified invariants additionally need:

- **Frame reasoning per collection action.** Proving `enqueue x` preserves `each i in Q (i > 0)` requires knowing that `enqueue` adds exactly `x` and touches nothing else — so the obligation reduces to `x > 0` (from classes a/b/c) plus the inductive hypothesis for existing elements. Each of the 15 cataloged actions needs a declared preservation frame ("what this action can change about a quantified fact"). This is analogous to the substitution step for `set`, but the want doc never states that the action catalog is a premise source.
- **Quantifier instantiation at read sites.** The existing element-modifier machinery already does the concrete version: `elemmod/read-peek-samebound-destination-accept` (collection coverage, § Element value modifiers block) shows `.peek` carrying the element bound into a destination field. Generalizing that to arbitrary quantified rules (e.g., `Q.min >= 0` follows from `each i in Q (i >= 0)`) is instantiation logic, a proof step kind the doc's derivation vocabulary (substitution, interval bounds) does not include.
- **Existential (`any`) and negated (`no`) preservation.** `any` facts are *destroyed* by `remove`/`dequeue` (removing the witness), not preserved — the inductive step for existentials is asymmetric in a way universal facts are not, and nothing in the doc's model addresses it.

**Assessment.** The concepts fit the induction shape (this is standard invariant-preservation reasoning), so the gap is in the *described model*, not necessarily in feasibility. But it is not "more plumbing" — it is new proof-step kinds and a new premise source (action semantics as frame axioms), and the certificate format must be able to record those steps.

### G2 — The temporal fault family has no premise vocabulary

**What canon says.** `docs/language/temporal-type-system.md:624` (instant Overflow note): "`Instant.Plus(Duration)` can overflow … NodaTime throws `OverflowException` at runtime. The compiler cannot catch this statically because field values are only known at runtime. **This is an accepted edge case**." The primitive-types doc's integer-conversion note (primitive-types.md:658) similarly designates `floor(1e20)` a runtime fault, "statically preventable when the proof engine can bound the expression range."

**Why this is structural under the want.** The want doc says faults "get the identical premise-and-certificate treatment" and the runtime omits fault-prevention checks entirely ("no overflow guards … the evaluator just computes"). "Field values are only known at runtime" is exactly the situation the want's induction is *for* — the divisor in `PlanRepayment` is also runtime-known, and the proof closes from the arg constraint. The instant-overflow obligation would close the same way — *if a bounding premise could be declared*. It cannot:

- The constraint vocabulary **rejects** `min`/`max` on `instant` (temporal coverage, added cells `temporal/instant/constraint-min-rejected`, `max-rejected`), on `zoneddatetime`, on `datetime`, and on `timezone`. `duration` and `period` accept `nonnegative`/`nonzero` but not magnitude bounds usable to bound a sum against the NodaTime representable range.
- So for `set X = SomeInstant + SomeDuration` where both are fields or event args, none of the four premise classes can supply a bound: no field modifier exists to declare one, no arg constraint exists to declare one, and a guard would have to compare against temporal extreme literals that the surface has no idiom for.

**Consequence.** Under prove-or-reject with the current surface, every `instant ± duration` (and the large-value integer-conversion family on `number`/`decimal` → `integer`) is an obligation that cannot close → the compiler must reject all such arithmetic, which would gut the temporal surface (49 of 78 samples call `now()`; 53 declare temporal fields). The want doc's own escape hatch applies — "where it doesn't [deliver tractable proof], the surface is the negotiable part" — but the *specific* missing piece is premise vocabulary: either bound modifiers for temporal magnitudes, or a declared-safe-range axiom (e.g., the compiler assumes values within NodaTime's representable range and bounds durations), or an explicit owner decision that this fault class is out of the guarantee. Any of these is a model decision the want doc does not currently make.

### G3 — Time-referencing rules: consequences of the open question (not resolved here)

The want doc leaves open whether rules may reference the current moment, or whether time belongs only in guards. Mapping what the corpus and the model imply, without resolving it:

1. **The corpus already exercises the guard-side resolution.** No sample has a `rule` or *state* ensure referencing `now()` (grep over `samples/*.precept`), but two have **event-anchored** ensures that do: `saas-customer-success.precept:104` (`on InitiateOutreach ensure InitiateOutreach.ScheduledDate > now() …`) and `saas-customer-onboarding.precept:92`. Event ensures are preconditions evaluated at event time — they behave like guards, and fit the "time only at event evaluation" resolution cleanly. So the guard-only answer is corpus-compatible today.
2. **Even under the guard-only resolution, `now()`-derived facts must be barred from the inductive hypothesis.** A guard `Expiry > now()` is a sound premise for what happens *inside that handler*, but if the proof engine forwarded it as a persisted fact (the way it forwards `Balance >= 0` facts), the fact decays as time passes with no event to invalidate it. The model needs an explicit rule: premises mentioning `now()` are event-instant-scoped and never enter class (d). The want doc does not state this.
3. **Proofs over `now()`-sourced fields need a clock axiom.** The dominant corpus pattern is `to Scheduled -> set ScheduledAt = now()` entry hooks (e.g., `global-meeting-scheduler.precept:184-187`, `hotel-reservation-management.precept:140-182`). A natural rule like `CheckedOutAt >= CheckedInAt` over two such fields is provable only from "a later event's `now()` ≥ an earlier event's `now()`" — clock monotonicity, which is none of the four premise classes and is not even true of wall clocks under NTP adjustment. Either such cross-field temporal rules are inexpressible/rejected, or the model gains a monotonic-time axiom (and the runtime a monotonic clock guarantee). This is the sharpest downstream consequence of the open question.
4. **If the resolution instead admits time-referencing rules** (`ExpiryDate > today`), the induction needs a step for the passage of time — a "tick" transition with no ingress — which contradicts the ingress ruling (args + editable writes only) as stated. The doc's own framing already recognizes this; noting for completeness that no third option surfaced in this analysis.

### G4 — Dynamic (interpolated) qualifiers make types configuration-dependent

**What the surface does.** Business-domain qualifiers can interpolate *other fields*: `field TotalInventoryCost as money in '{CatalogCurrency}'`, `field QuantityOnHand as quantity of '{StockingUnit.dimension}'`, `field StockingUnitsPerPurchaseUnit as quantity in '{StockingUnit}/{PurchaseUnit}'` (`samples/inventory-item.precept:45-60`). Tier-2 dynamic resolution with guard narrowing is specified in `docs/language/business-domain-types.md` (§ Declaration-position interpolation, § Resolution semantics tiers, lines ~1473-1558). In the sample, the qualifier-source fields (`CatalogCurrency`, `StockingUnit`, …) are themselves **editable** in the `Unlisted` state (inventory-item.precept:94).

**Why this is structural under the want.** The want doc's model is entirely value-level: rules relate field values, premises bound values, writes change values. Interpolated qualifiers add a second level: **a field's type is a function of the configuration**. That creates obligations the model has no vocabulary for:

- *A write to a qualifier-source field is a type-level write site for every dependent field.* Editing `CatalogCurrency` from `'USD'` to `'EUR'` changes the declared type of `TotalRevenue`, `GrossProfit`, `AverageCost`, and five others — while their stored magnitudes (accumulated in USD) do not change. The symmetric-obligation principle ("obligations attach to every write site of every field the rule mentions") has an analogue here — obligations should attach to every write site of every field a *type* mentions — but the want doc never states it, and under the no-post-mutation-re-evaluation ruling nothing re-validates the dependent fields after the edit.
- *The editable-ingress rule under-covers this case.* The want doc says an editable write evaluates "the field's modifier-rules and every rule that mentions the field." A write to `CatalogCurrency` mentions no rule of `TotalRevenue`; the dependency runs through the type text, not through any rule. So the stated ingress check would pass an edit that silently re-denominates every money field in the entity.
- *Qualifier-compatibility proofs become flow-sensitive in a new way.* Two fields both declared `in '{CatalogCurrency}'` are same-currency *only while `CatalogCurrency` is not written between their uses* — the existing narrowing machinery tracks reassignment invalidation for guard-derived facts, but declaration-level sameness through a shared interpolated source is a different fact kind.

**Mitigating observation.** The sample restricts qualifier-source edits to the pre-listing state where the dependent accumulators are still at their zero defaults — a discipline that makes the edit harmless. That discipline is currently authorial convention, not a checked obligation. A plausible closure is a compile-time obligation that qualifier-source fields are only editable while every dependent field provably holds a qualifier-neutral value (zero/default), or are never editable after construction — but choosing that is a design decision, and the want doc as written does not contain the concept needed to state it.

### G5 — `omit`: state-scoped field absence vs. "a rule holds, period"

**What the surface does.** The `omit` access mode removes fields from existence in named states: `in UnderReview, Investigation omit PaymentAmount, PaymentMethod, …` (`samples/insurance-claim-adjudication.precept:79-81`; 25 of 78 samples use `omit`). Reading an omitted field in an omitted state is a compile error (`OmittedFieldReadInState`), and `OmittedFieldSetInTargetState` polices writes (spec-parser coverage, access-mode block; spec-typecheck coverage §3.5).

**Why this is structural under the want.** The want doc's uniformity claim is "a rule holds, period." A global `rule PaymentAmount >= 0` in a precept where `PaymentAmount` is omitted in `UnderReview` has no evaluable meaning in that state — the field is structurally absent, not merely null. The model needs one of: (i) rules mentioning a field are implicitly scoped to the states where all mentioned fields exist (vacuous elsewhere — which quietly turns "holds, period" into "holds where applicable"); (ii) such combinations are compile-time rejections (a rule may only mention fields that exist in every state — which interacts with the symmetric-obligation sweep: is a transition *into* an omit state a write site that "unsets" the field, and does re-entry to a non-omit state re-establish it from default, needing a base-case-style proof?); or (iii) omit is redefined as presence (an `optional`-like unset) rather than absence. Each option changes what the inductive hypothesis (premise class d) contains per state. The want doc contains no concept of state-indexed rule applicability, so this is a model gap, not plumbing — though a small one compared to G1–G4, since the resolution is a semantics ruling rather than new proof machinery.

## Notable mechanical-extension burdens (medium findings)

**M1 — Non-finite `number` posture conflict.** `docs/language/primitive-types.md:650-660` specifies runtime faults when NaN/±∞ reach rounding functions and says "the proof engine *may* be able to prove non-finiteness is impossible … but the runtime must handle it defensively." Under the want's no-deferral and runtime-omits-fault-checks rulings, "defensively" is not an available posture: finiteness must be an obligation proven from operand bounds (interval reasoning — mechanical), and unbounded `number` fields feeding `floor`/`round`/comparisons must reject. The mechanism exists; the canon sentence and the fault-catalog posture need to flip from detection to prevention.

**M2 — Integer overflow doc self-contradiction blocks the fault enumeration.** primitive-types.md:81 (Approximation Stance): integer is "arbitrary-precision … no overflow"; primitive-types.md:197: "Overflow is a type error"; :203: "Checked overflow." Three mutually inconsistent claims (already flagged in `coverage/primitive-types.md` § stopAndFix). Until one is canonical, the integer arm of the fault family — which the want's identical-premise-treatment ruling requires enumerating — cannot be specified. (If arbitrary-precision wins, the obligation vanishes; if checked-overflow wins, it becomes an interval obligation like M1.)

**M3 — Collections plumbing is large but shape-true.** Nine collection kinds × 15 actions × accessors produce the bulk of the enumerated surface (~3,400 cells in the collection unit alone). Every obligation kind already exists in the ProofRequirements catalog (emptiness via Numeric on `.count`, CountContainment, LengthContainment on elements, KeyPresence, IndexBounds), and discharge sources are already specified: guards, `mincount 1` static discharge, sibling-row negation, count-band tracking, sequential invalidation (`coll-dequeue-after-shrink-invalidates`). The `log of T by P` uniqueness design is a model exemplar, not a violation: uniqueness is "a precondition on `append`, not a runtime fault … the proof engine raises `UnguardedCollectionAccess` if the guard is absent" (`collection-types.md`, Uniqueness enforcement, ~L431) — i.e., guard-premise-or-reject, exactly the want's shape.

**M4 — State-scoped ensures multiply the induction, and add mid-lifecycle establishment.** With `in State ensure …` / `to` / `from` anchors (66 of 78 samples use `ensure`), the single global invariant set becomes a state-indexed map. The inductive step's premise class (d) becomes "all constraints applicable in the source state," and — the genuinely new bookkeeping — every transition row and entry hook targeting a state is an **establishment site** for that state's ensures, a base-case-style obligation occurring mid-lifecycle. The want doc's base case covers construction only. Same proof shapes (this is classic typestate reasoning), but the certificate and diagnostic surfaces need the establishment-obligation category.

**M5 — Additional write-site categories must enter the symmetric sweep.** The want doc enumerates handler `set` writes and editable edits. The surface also writes via: entry hooks (`to Scheduled -> set ScheduledAt = now()`, global-meeting-scheduler.precept:184-187), state actions and stateless event hooks (spec-parser coverage, 2.2-state-action / 2.2-stateless-event-hook blocks), and all 15 collection actions. Purely an enumeration-completeness burden — miss one category and the symmetric-obligation guarantee is silently unsound.

**M6 — Computed fields extend substitution transitively.** `field GrossProfit as money … <- TotalRevenue - TotalReturns - …` (inventory-item.precept:76) means every write to any input is a write site for every rule mentioning `GrossProfit`; chains require transitive closure. Cycle rejection and non-writability are already compile checks (spec §3.8). Mechanical, but interacts with G4 when the computed field's type carries an interpolated qualifier (as in the sample).

**M7 — Small ambiguities already flagged upstream** that a prove-or-reject spec must settle: the `pow` negative-exponent lane scoping (primitive-types.md:613; `coverage/primitive-types.md` stopAndFix #2) and the `maxplaces`-on-division-results precision question (mechanically covered by the three-tier enforcement scope, business-domain-types.md:1581-1584).

## Answer in one paragraph

Most of what the worked example omits is genuinely "more of the same": the four premise classes, symmetric write sites, and ingress checks generalize without new theory to strings, presence, choices, non-quantified collections, static business-domain qualifiers, ensures, computed fields, and every extra write-site category — the burden is enumeration discipline, not invention, and the existing docs largely already frame those obligations in prove-or-reject shape. The significant gaps are five: (G1) quantified collection rules — which the modifiers-are-sugar ruling makes mandatory, not optional — need frame axioms and quantifier instantiation the model doesn't describe, and canon currently classifies them as runtime governance, i.e. deferral; (G2) the temporal fault family has no declarable premise that can bound an instant, so prove-or-reject as stated would reject the temporal arithmetic half the sample corpus uses; (G3) the time open question has concrete downstream costs — `now()`-derived facts must be barred from the inductive hypothesis, and cross-field rules over `now()`-sourced timestamps need a clock-monotonicity axiom the premise classes don't contain; (G4) interpolated qualifiers make field types configuration-dependent, creating type-level write-site obligations the value-level model cannot express; and (G5) `omit` makes rule applicability state-dependent, which the "a rule holds, period" guarantee doesn't yet have vocabulary for.
