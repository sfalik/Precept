# Soundness, Uniqueness, Value, Philosophy — Analysis of the Want Statement

**Status**: Draft analysis - 2026-07-19 (agent-authored; evidence only; rulings remain the owner's)

**Input under analysis**: `docs/Working/what-i-want-2026-07-16.md` ("the want doc") — the owner's statement of what Precept's compiler and runtime should be. Treated as authoritative over the rest of the docs corpus throughout; where the corpus disagrees with it, the corpus is compared against it, never the reverse. Its settled rulings (inductive proof over reachable configurations; modifiers as sugar for rules; no deferral; ingress = event args + editable-field writes; certificates with one checker at two call sites; no post-mutation re-evaluation; guarantee non-negotiable, surface negotiable) are taken as design, not questions. The question asked here, verbatim from the owner: *"What am I missing? Is this sound? Is this unique? Is this valuable? Does it align and deliver what the philosophy promises?"*

**Method**: the want doc and `docs/philosophy.md` read in full; claims checked against the language spec, runtime API doc, proof-engine source, and the repo's existing research corpus (per project rules, repo research first). Every claim below carries a citation. Where something was not observed, it is marked UNKNOWN.

---

## 1. Is it sound?

**Verdict: SOUND at its core, with five findings — two of which (S1, S2) must be closed for the guarantee to be exactly what the doc says it is.** None of the findings invalidates an owner ruling; each is closable inside the model as designed. The inductive structure itself — base case over defaults and initial events, inductive step over handlers from four premise classes, symmetric obligations at every write site (want doc, "The compiler's promise") — is the standard invariant-preservation shape (the same proof-obligation shape Event-B generates per event; see § 2), and I found no case where the induction fails on data that entered through the two declared ingress points under the current definition. The holes are at the model's edges: what enters *outside* the two ingress points, what the certificate checker can and cannot see, and two constructs the language has that the doc's operational rules do not yet name.

### S1 (high) — Restore-is-trusted rests on an assumption whose only backstop the want removes

The want doc: *"Restore/rehydration is not ingress — data coming back from persistence is trusted and unchecked, because it was governed when it was written"* (`what-i-want-2026-07-16.md:129`), with schema evolution named as a post-MVP expansion of the restore path.

The problem is that the current canon justifies exactly this trust by a mechanism the want removes. `docs/runtime/runtime-api.md:266`: Restore *"does **not** re-validate constraints: restored state is trusted as valid at the time it was persisted … **a stale value is re-governed by the next operation's post-mutation constraint sweep** (spec §3A.4)."* Under the want there is no post-mutation sweep (`what-i-want-2026-07-16.md:153, 187`) — so the backstop that made restore-trust safe in canon no longer exists, and nothing replaces it.

Why this matters on the model's own terms: the inductive step's premise class (d) is *"all rules holding in the pre-state"* (`what-i-want-2026-07-16.md:19`). For a restored instance whose data violates a rule, that hypothesis is false — and every subsequent proof for that instance is vacuous. Concretely, the doc's own `Deposit` handler is proven *"only if the rule held before the event"* (`what-i-want-2026-07-16.md:95`); fired against a restored account with `Balance` below `-OverdraftLimit`, `Deposit` carries the violation forward, silently, forever. No guard fails, no ingress check fires, no certificate is violated — the invalid configuration persists, which is the one thing the philosophy says cannot happen (`docs/philosophy.md:49`).

The trust premise "it was governed when it was written" fails in two known ways:

1. **Definition change.** Data persisted under an older definition, restored under a strengthened one (a new or tightened rule): the new rule was never established for that configuration — the base case ran under a different theory. The want doc's parenthetical names "schema evolution — data written under an older definition" as post-MVP restore work (`:129`); read broadly this covers rule changes too, but the doc's wording ("schema") suggests field-shape changes, and the consequence — *the guarantee for a restored instance is conditional: rules are preserved only if they held at restore* — is nowhere stated.
2. **Out-of-band writes.** Any write to the store that did not go through Precept (raw SQL, another service, a migration script) produces data that was *never* governed, and restore trusts it. The philosophy itself names this exact bypass shape as the flaw in ORM validation: *"any code path that bypasses the ORM (raw SQL, bulk operations, another service) bypasses the rules"* (`docs/philosophy.md:71`). The restore-trusted stance imports that same flaw unless the guarantee's scope is honestly stated.

**What closes it without changing the ruling**: bind each persisted `Version` to the identity of the definition (and certificate) that governed it, so the load-time gate can detect when the trust premise fails (definition mismatch → the restore path's post-MVP validation, or refusal); and state the guarantee's honest scope — structural impossibility holds for configurations whose history ran under the current definition through Precept, and restore-trust is a declared boundary assumption, not a proven fact. This is a completion of the certificate machinery, not a new mechanism.

### S2 (high) — The certificate checker as described verifies proof *soundness* but not proof *coverage*

The want doc's checker *"simply walks those steps and confirms each one"* (`what-i-want-2026-07-16.md:194`), and on that basis the runtime claims *"no unproven, tampered, or stale definition can ever govern"* (`:192`).

A checker that walks the steps recorded in the certificate can catch a *wrong* proof. It cannot catch a *missing* one: if the proof engine has a bug that fails to emit an obligation at all (a write site it never visited, a construct it never enumerated), the certificate contains no step for it, the walk succeeds at both call sites, and an unproven definition governs. "Unproven" is precisely the word the claim uses, and step-walking does not deliver it.

This is not a new observation — the repo's own soundness-architecture research states it as a locked conclusion: *"witness-checking does NOT address generation-completeness … a missed obligation … is a coverage hole the checker is blind to. Coverage is a catalog-enumeration property … distinct from witness-soundness"* (`research/architecture/compiler/witness-checking-soundness-architecture-survey.md`, conclusion C3, lines 172–176).

The fix is also already implied by the want doc's own cited precedent. In proof-carrying code (Necula & Lee, cited at `what-i-want-2026-07-16.md:201`), the consumer does not trust the producer's list of obligations — the consumer's trusted base includes its own verification-condition generator; the supplied proof is checked against obligations the *consumer* derives. (The repo survey's PCC leg is flagged as training-data-grounded rather than primary-fetched — `witness-checking-soundness-architecture-survey.md:94, 143` — but the same conclusion is Primary-grounded there via the certifying-algorithms and Verasco sources.) For the load-time gate to be the sole runtime trust root, **obligation enumeration must be inside the trusted checker**: the checker re-derives *what needed proving* from the definition, then confirms the certificate discharges each item. Since Precept's obligations are catalog-driven, the enumerator can plausibly stay small — but it must be named as part of the checker, and the want doc currently describes only the step-walk. This also disposes of the stale/mismatched-pair question the owner raised: a checker that enumerates from the definition in hand structurally cannot pass a certificate built for a different definition; a checker that only walks recorded steps can.

### S3 (medium-high) — The obligation-attachment rule misses constraints activated by a pure state transition

The want doc's symmetric-obligation rule: *"A rule's obligations attach to every write site of every field the rule mentions"* (`what-i-want-2026-07-16.md:19`). The language, however, has **state-scoped constraints**: `in State ensure …` and the entry-gate form `to State ensure …` (`docs/language/precept-language-spec.md:327, 341, 342`); the philosophy names ensures as first-class (*"state- or event-scoped constraints that must hold in specific contexts"*, `docs/philosophy.md:15`). The want doc never mentions `ensure` at all.

A transition row can change *which* constraints apply without writing any field. In the doc's own example, `Freeze` transitions `Active → Frozen` with no `set` (`what-i-want-2026-07-16.md:77–79`). Add `in Frozen ensure Balance >= 0` and the counterexample is immediate: `Freeze` fired at `Balance = -100` writes nothing, so under write-site attachment it carries no obligation — yet it enters a state whose active constraint the unchanged data violates.

The doc's broader sentence — *"Every handler preserves every rule"* (`:19`) — can absorb the fix (obligations attach to every row whose **post-state activates** a constraint, in addition to write sites), and nothing in the rulings resists it. But the operational attachment rule as written leaks, the worked example cannot surface it (it contains no ensures), and the doc's scope sentence "proves or rejects all business rules" (`:14`) leaves the ensure family's membership undeclared.

### S4 (medium) — The editable-write "mention set" must be computed after desugaring, over guard positions, and across derived-field dependencies

The induction at an editable-field write closes by evaluating *"the field's modifier-rules and every rule that mentions the field"* (`what-i-want-2026-07-16.md:131`): only one field changed, every rule either mentions it (evaluated at ingress) or does not (truth-value unchanged, held by hypothesis). That argument is correct — **provided "mentions" is defined precisely enough**, in three specific ways:

1. **Guard-position mentions.** A guarded rule (`docs/philosophy.md:33`; spec `:147`) whose *guard* mentions the edited field can flip from inapplicable to applicable without its body mentioning the field. Example: `rule Balance >= 0 when AccountType == "Savings"` — editing `AccountType` to `"Savings"` while `Balance = -50` violates the rule, though the rule's body never mentions `AccountType`. Sound only if "mentions" includes occurrences anywhere in the rule, guard included.
2. **Cross-field modifiers.** Modifier value expressions may reference *other fields* — `A min B` is legal and is rule shorthand with full field scope (`docs/language/precept-language-spec.md:1352–1354`). Editing `B` threatens `A`'s modifier-rule. The owner's "modifiers are sugar for rules" ruling handles this exactly — desugared, `A min B` is a rule mentioning `B` — but only if the ingress set is computed over the *desugared* rule set, not over the edited field's own modifiers plus literal `rule` statements. Worth one sentence in the doc; an implementation that reads the rule literally reintroduces the leak the sugar ruling closes.
3. **Derived fields.** The language has computed fields (`<-`), present across the sample corpus (e.g. 6 in `samples/invoice-line-item.precept`; 32 across 77 files per `research/architecture/compiler/fragment-boundary-corpus-validation-2026-06-05.md:10–14`), and the runtime recomputes them on restore (`docs/runtime/runtime-api.md:266`). The want doc never mentions them. Editing field `A` implicitly changes every derived field computed from `A`; a rule mentioning derived `C` but not `A` must be in `A`'s edit-evaluation set (transitively), and a handler's recomputation of `C` is an implicit write site for symmetric obligations. The research finding that derived fields *"are computed, not constrained, and therefore need no preservation proof at all"* (`fragment-boundary-corpus-validation-2026-06-05.md:14`) covers the derived field's own value — it does not cover *rules that read* the derived field, which is where this leak lives.

### S5 (medium) — Certificate soundness is relative to the proof theory; nothing in the model checks the theory against the evaluator

The checker (S2 fixes included) establishes that the proof is a valid derivation *in the proof engine's arithmetic model*. If that model does not faithfully describe the runtime evaluator's actual arithmetic, a fully-verified certificate is still unsound at runtime — and under the want, the runtime has deliberately dropped the checks that would have caught it (*"fault-prevention checks are omitted at evaluation time … the evaluator just computes"*, `what-i-want-2026-07-16.md:153`).

This is not hypothetical; a live instance exists at HEAD. `number` is IEEE 754 double by spec (`docs/language/primitive-types.md:265`). The proof engine's interval transfer for `number` multiplication and division widens results outward by a relative-error margin (`src/Precept/Language/Operations.cs:179, 188` → `NumberMultiplyTransfer`/`NumberDivideTransfer`, `:1340–1358`), but `number` **addition and subtraction use the exact-decimal transfer with no outward widening at all** (`Operations.cs:171, 175` → plain `AddTransfer`/`SubtractTransfer`, `:1332–1334`). A float sum can land just outside an interval the engine proved, and under the want no runtime check remains to notice. The repo's own survey of this exact question concludes: *"no surveyed system concretely evaluates an expression at compile time while leaving an unrelated runtime evaluator free to disagree — that combination is exactly the empirically-demonstrated drift pole"* (`research/architecture/compiler/static-vs-runtime-expression-evaluation-survey.md:171`, with GCC's "constant folding must emulate the target machine's arithmetic" at `:123`).

The want doc should state the missing requirement explicitly: the proof theory's semantics and the evaluator's semantics are one semantics — shared core, or mandated-equal with a conformance oracle (the two sound postures the survey names at `:171–175`). This is a stated-assumption gap, not a design flaw; but "lighter runtime, with confidence" is earned only over ground the theory actually models.

### Candidates examined and found NOT to be holes

- **Overlapping guards on multiple rows for one event.** Row selection is first-match in declaration order (`docs/language/precept-language-spec.md:1904`), so execution of a row entails its own guard held — using only the row's own guard as a premise is sound regardless of overlap (it is strictly weaker than guard ∧ ¬(prior guards), and weaker premises can only make proofs harder, never unsound). Determinism is preserved by the ordering. No hole.
- **The deliberate-omission paragraph** (`what-i-want-2026-07-16.md:119`, unconsumed modifiers on `DailyWithdrawalLimit`). Verified correct, including its subtlest claim: the modifiers *are* consumed — by their own preservation proof (default checked in the base case; editable ingress evaluates them; no other write path), which is why the certificate marks the ingress check load-bearing while no *other* proof depends on them. Deleting them weakens the spec without breaking a proof. The asymmetry is stated exactly right. No hole.
- **Defaults-under-constraints.** The classic vacuity breach (a default violating a modifier makes every downstream inductive proof vacuous) is closed by construction: the base case checks defaults against modifier-rules, and the mutation table makes it a rejection row (*"Change the default to 20000.0 → Default value violates max 10000.0"*, `what-i-want-2026-07-16.md:114`). Closed.
- **Editable windows and versioning.** Edits are single-field, state-gated (`in Active modify … editable`), and every operation returns a new immutable `Version` (`what-i-want-2026-07-16.md:151`; `docs/runtime/runtime-api.md:89`). Firing against a non-latest `Version` creates a branch of valid configurations — per-configuration integrity holds on every branch; lost-update concerns are outside the integrity guarantee. No hole beyond S1's restore findings.

### The two open questions, on their consequences (not resolved here)

- **Time-referencing rules** (`what-i-want-2026-07-16.md:207`). The blast radius is larger than the `ExpiryDate > today` example. Date-ordering rules over timestamp *fields* written from `now()` — a dominant corpus pattern (`set …At = now()` entry hooks; `fragment-boundary-corpus-validation-2026-06-05.md:116`, and every date-ordering rule the survey classes as provable rides on it) — cannot close from the four premise classes alone: proving `CompletedAt >= CreatedAt` after `set CompletedAt = now()` needs the fact that `now()` at this event is ≥ the `now()` that wrote `CreatedAt`. That fact is either (a) a clock-monotonicity axiom in the proof theory — whose truth the runtime does not control (wall clocks step backwards under NTP; `today` shifts with timezone/DST) — or (b) an author-written guard (`when now() >= CreatedAt`), which is expressible and consistent with the "time belongs only in guards" branch of the open question, at some ergonomic cost. Under no-deferral there is no third option: unresolved, these rules must *reject*. So the open question decides the provability of a large existing rule family, not an edge case — worth knowing before the feasibility study prices it. Additionally, whichever branch is chosen, the model needs a single-instant semantics: one time snapshot per atomic operation, so a guard's `now()` and an action's `now()` cannot disagree across a midnight/second boundary inside one operation. No incoherence found — but "prove or reject, coherently" is available only after the resolution, exactly as the doc says.
- **Cross-precept** (`what-i-want-2026-07-16.md:208`). At MVP scope the model is coherent as-is: the single-precept boundary means inter-entity data can only ever arrive as event args, which are already ingress — a receiving precept's guarantee never depends on the sender's. The future capability is where the question has teeth: a saga-level invariant spanning two precepts has no single-precept induction to live in, and message passing creates ordering/interleaving questions the atomic-operation model doesn't currently face. Deliberately open; nothing at MVP scope contradicts the rulings.

## 2. Is it unique?

**Verdict: UNIQUE as a combination; no single ingredient is novel — and the want doc correctly cites its own lineage rather than claiming otherwise.** The claim that matters is whether *domain-expert-authored DSL + induction over reachable configurations + no-deferral + certificate-gated lighter runtime* exists elsewhere as one artifact. Across the repo's research corpus and the comparator families examined, it does not. Checked family by family:

**Formal-spec verifiers (Alloy, TLA+, Event-B, Z).** The repo's dedicated survey (`research/philosophy/formal-spec-languages-comparators.md`) finds Event-B's abstract machine *"structurally identical"* to Precept's model — *"The mapping is exact"* (§4) — and Event-B generates exactly the per-event invariant-preservation proof obligations the want doc's inductive step describes. The category gap the survey names is deployment: these tools verify designs and produce no governing runtime (§3 capability tables — no runtime enforcement, no inspection API, formal-methods audience). The want doc's model is precisely the thing that survey's one-sentence distinction says nobody has: Event-B-style proof obligations *plus* a production enforcement engine, joined by a certificate so the runtime's trust in the proof is verified, not assumed. Alloy and TLC additionally check *bounded* scopes (counterexample finding), where the want demands unbounded proof or rejection. Distinct.

**Program verifiers (Dafny, SPARK, Whiley, F*, Liquid Haskell, Frama-C).** All are developer-audience and all discharge obligations through SMT solvers (Dafny→Boogie→Z3, SPARK→Why3→CVC5/Z3/Alt-Ergo, etc. — `research/architecture/compiler/type-proof-stage-contract-survey.md:47–49` and its comparator table). Precept's posture is deliberately solver-free with legible witnesses (`research/philosophy/formal-spec-languages-comparators.md` §6, "Opaque solver rejection"; the R1 requirement throughout `solver-free-static-analysis-techniques-survey.md`), which also buys determinism a solver-backed compiler cannot promise (a compile verdict that varies with solver version/platform is a determinism breach; the philosophy's determinism promise at `docs/philosophy.md:22` makes this load-bearing, not aesthetic). Second axis: these systems ship justification/assumption mechanisms (Dafny `assume`, SPARK justification pragmas, Liquid Haskell `assume` — general knowledge, not repo-research-grounded, flagged as such); the want ships none — its pressure valve is shrinking the language surface (`what-i-want-2026-07-16.md:125, 177`), the move of total-by-construction languages (Dhall's single normalizer and restricted surface appear in `static-vs-runtime-expression-evaluation-survey.md:175` and `interval-vs-value-evaluation-prior-art-2026-06-05.md`). Distinct on audience, on solver posture, and on the no-escape-hatch bet.

**Inductive-invariant verifiers (Ivy and kin).** Not covered by any repo research file (checked `research/INDEX.md` — no entry; UNKNOWN beyond general knowledge, flagged): Ivy's discipline — the user supplies invariants, the tool checks inductiveness in a deliberately decidable fragment, and undecidable constructs are pushed out of the language rather than at the solver — is the closest methodological cousin to the want's "author supplies the premises; the language stays small enough to decide." The distinction is the same as above: Ivy verifies protocol models for engineers; it is not a governance runtime, not certificate-gated, not domain-expert-facing.

**Design-by-contract (Eiffel, .NET Code Contracts).** The closest *historical* analog for structurally-enforced, entity-bound invariants, and the repo's positioning brief flags it as under-cited (`docs/Working/precept-identity-thesis-supporting-2026-07-11/research-r3-positioning.md` §1.5). Two real differences: DbC *checks contracts at runtime* on every call — the want *proves* them and removes the runtime re-check (a step DbC never took); and DbC contracts are authored by developers in the host language with enforcement that is configurable/strippable, where Precept's is an external domain-expert DSL with non-optional enforcement. The overlap that matters is the market history, not the mechanism — carried into § 3.

**Statecharts/state-machine frameworks, business-rules engines, validators, DB constraints, policy engines.** Already positioned in `docs/philosophy.md:63–77`: none claims compile-time proof of anything (XState/Stateless have no data-constraint model; Drools/NRules cannot verify satisfiability or non-contradiction at compile time; validators run when called; CHECK constraints have no lifecycle or inspectability; OPA/Cedar evaluate at request time — with the honest exception that Cedar offers formal policy-level verification, `research-r3-positioning.md` §1.4, though of policies, not entity lifecycles). The want *widens* the existing gap: today's positioning says "structurally enforced, not called"; the want adds "and proven before any instance exists," which no tool in these categories claims at all. The "empty cell" conclusion of `research/product/entity-governance-landscape.md:13, 430` supports this — flagged per its own framing note as company-commissioned positioning research (`research-r3-positioning.md`, framing note), so treated as corroborating rather than independent.

**Proof-carrying code — is the citation faithful?** Structurally yes: producer does the expensive proof search once; consumer re-verifies with a small trusted checker; the generation–checking asymmetry is why the checker stays small and fast (`witness-checking-soundness-architecture-survey.md:94, 135`). The want doc claims exactly this and no more (`what-i-want-2026-07-16.md:194, 201` — "small-trusted-kernel discipline"). Two honest deltas to keep in view: PCC's consumer generates its own verification conditions rather than trusting the producer's list — the fidelity point that S2 turns on; and PCC's setting was an *adversarial* producer (untrusted mobile code), where Precept's is its own compiler — which makes the want's "does not blindly trust the compiler either" (`:187`) a *stronger*-than-necessary discipline borrowed from a more hostile setting, a point in its favor, not against.

**The honest limit of the uniqueness verdict**: "no system combines these four properties" is supported by everything the repo has surveyed and everything checked here; it is a universal claim over a field no survey exhausts. UNKNOWN whether an unstudied system exists. What can be said with evidence: none of the surveyed comparator families — across roughly a dozen dedicated research files — occupies the combination, and the nearest neighbors each lack at least two of the four properties.

## 3. Is it valuable?

**Verdict: VALUABLE — the steelman against adoption survives as a *risk register*, not a refutation; the strongest single entry is market precedent, not technical cost.** The steelman, constructed as strongly as the evidence allows, then answered on the merits:

**Steelman 1 — Ship the narrower guarantee instead.** *A fault-freedom floor (no division-by-zero, no overflow, structural graph checks) plus runtime rule-checking is buildable sooner, and most buyers can't tell the difference.* Answer: the delta between that floor and prove-or-reject is precisely the category claim. Runtime rule-checking is what validators already do; a Precept without rule proof is a better-integrated validator — the thing the philosophy explicitly positions against (*"This is not a smarter validator … That is a different category entirely"*, `docs/philosophy.md:57`). The want doc's uniform-guarantee property (*"no author-facing distinction between compile-time-checked rule and runtime-governed rule … no tiers of trustworthiness"*, `what-i-want-2026-07-16.md:161`) is only available under prove-or-reject; any deferral reintroduces tiers. The narrower guarantee is cheaper because it buys less of exactly the thing that is different. Rebutted.

**Steelman 2 — The proof burden falls on the wrong person.** *The primary author is a domain expert (`docs/philosophy.md:92`); making files provable means writing premises until an induction closes, which is verification engineering, not domain authoring.* Answer, on measured evidence: (a) ~89% of the existing corpus's explicit invariants (122/149 rules, 515/565 ensures across 77 files) are already inside the cheap solver-free fragment *as written* (`fragment-boundary-corpus-validation-2026-06-05.md:199`) — the fragment "was designed to the right shape, not a toy subset" (`:184`); (b) the premises the model demands are mostly things authors write for business reasons anyway — the want doc's own `Withdraw` guard *is* the business behavior, and its proof role is a bonus (`what-i-want-2026-07-16.md:96`); the genuinely unintuitive case (`ReduceLimit`, the symmetric write site) is the one the doc singles out as the compiler *teaching* the author something true about their domain (`:97`); (c) the compiler computes and shows the missing premise rather than leaving the author to find it (`:167`). Honest caveats that keep this from being a full rebuttal: the corpus is self-authored samples, not third-party domain experts — the false-rejection rate for real authors is UNKNOWN and unmeasured (no published study exists for this class of DSL); and the out-of-fragment residue is real: 4 three-field balance identities (`A + B == C`), 7 non-unit-coefficient rules, and assorted non-numeric relations (`fragment-boundary-corpus-validation-2026-06-05.md:187, 202`) which under no-deferral *reject* unless the engine extends (Karr's affine-equality domain is the named solver-free, polynomial extension covering exactly the balance-identity gap — `solver-free-static-analysis-techniques-survey.md`, conclusion C1) or the author restructures (derived fields carry no preservation obligation — `fragment-boundary-corpus-validation-2026-06-05.md:14` — and a balance identity is often a derived field wearing a rule's clothing). Mostly rebutted; residual risk owned by the feasibility study the want doc itself commissions.

**Steelman 3 — "Prove one more class" has no stopping point.** *Every rejected file generates pressure to extend the prover; the engine grows forever toward SMT.* Answer: two principled stopping rules already exist. Technically, the repo's capability survey draws a hard cost line — everything up to octagon/Karr/two-variable-per-inequality expressiveness is polynomial and predictable per keystroke; convex polyhedra and beyond are exponential worst-case and disqualified (`solver-free-static-analysis-techniques-survey.md`, the R2 boundary and its C4 "AVOID" ranking). Policy-wise, the want doc states the rule itself: when proof and expressiveness conflict, *the surface shrinks* — "the guarantee is non-negotiable; the surface is the negotiable part" (`what-i-want-2026-07-16.md:177`). Pressure to extend resolves as a bounded menu (Karr, coefficient extension) plus surface decisions, not an open-ended slide. Rebutted.

**Steelman 4 — The market already rejected this shape.** *Structural, entity-bound, non-bypassable contracts were tried in this exact ecosystem: Eiffel never crossed into the mainstream, and Microsoft's own .NET Code Contracts was discontinued* (`research-r3-positioning.md` §1.5, §86 — agent-authored brief, external claims from training knowledge, flagged there as such). This is the strongest entry because it attacks demand, not feasibility, and no amount of proof engineering answers it. Partial rebuttal on the merits: the brief itself leaves open whether the failure mode was the idea or the ergonomics/tooling (§86), and the want's shape differs on every axis that plausibly killed Code Contracts — external DSL rather than in-language annotations, mandatory rather than strippable enforcement, a domain-expert author rather than a developer adding ceremony, and compile-time teaching rather than silent runtime assertion. But "differs on the axes that plausibly killed it" is a hypothesis, not evidence. This survives as the real adoption risk, and the want doc does not engage it (nor claims to — it is scoped to the ideal, with feasibility explicitly deferred, `:10`). Survives as risk.

**The value side of the ledger, for completeness**: the compiler finds violations at authoring time — *"the real advantage is not runtime economy: the compiler finds problems at the time when it's cheapest to fix them"* (`what-i-want-2026-07-16.md:155`); rejection messages that name the missing premise teach the domain model (`:167`); the certificate gives inspect provenance ("no check needed here — proven from these premises", `:199`) — an explainability surface no comparator offers; and the premise list *is* the runtime's validation surface, derived rather than parallel-maintained (`:198`), which retires an entire class of enforcement-drift bugs.

## 4. Does it deliver what the philosophy promises?

**Verdict: ALIGNED, and on most promises *strengthening* — the want doc is largely the philosophy's mechanism finally specified. Three flags, none resolved here.** Promise by promise against `docs/philosophy.md`:

| Philosophy promise | Verdict under the want | Evidence |
|---|---|---|
| Data and rules primary; states the mechanism (`:33, 37`) | **Delivered, strengthened** | Rules become proven theorems over every reachable configuration (`what-i-want:24`); lifecycle is the induction's coordinate system, exactly the philosophy's framing |
| Invalid configurations structurally impossible (`:7, 43, 49`) | **Strengthened in-process; falls short on the restore path until S1 is closed** | Proof replaces post-hoc checking (stronger); but restored/out-of-band data can instantiate an invalid configuration no mechanism touches (§1 S1; `runtime-api.md:266`; philosophy's own bypass critique at `:71` applies) |
| Guarantee 1 — every rule enforced on every operation, atomically (`:51`) | **Delivered by changed mechanism; wording change owner-gated** | The rule *holds* on every operation because it is a theorem plus premise-checks; it is no longer *evaluated* on every operation.
