# Relational-subject resolution for fault-prone-operator discharge (Slice 2c-i amendment)

> **Amendment provenance.** The core design (`relational-narrowing-core-design-2026-06-03.md`, Locked 2026-06-04) is correct in its representation, extraction, composition, and isolation decisions — they all STAND. What it got wrong was a single ground-truth assumption baked into its S4 consumer table and acceptance matrix: that the demonstrator divisor `(OnHand − Reserved) != 0` already reaches `GuardRelationImpliesObligation` through `TryFlowNarrowingProof`. A `Compiler.Compile`-level probe falsifies that. This amendment specifies the one missing seam — **resolve the obligation Subject to the divisor sub-expression before the relational strategy runs** — that makes the demonstrator (and the sqrt/modulo/overflow family) discharge, and corrects the falsified claim. It is the design-side of read-before-asserting: a route the locked design asserted, the probe denied.

## Goal

When done, a fault-prone operator obligation whose discharge-relevant operand is a **relational sub-expression** `(X arith-op Y)` — the divisor of `Z / (X − Y)`, the operand of `sqrt(X − Y)`, the dividend of `(X − Y) % k`, an overflow/range obligation over `(X − Y)` — discharges from a declared relation `X rel-op Y`, whether that relation is sourced from a row/hook/handler/rule guard OR from an unconditional `rule`. Demonstrated by: the reorder precept where `rule OnHand > Reserved` (both fields `nonnegative`) makes `BatchCost / (OnHand − Reserved)` provably non-zero and compiles clean, the divisor obligation reporting `ProofStrategy.FlowNarrowing`; and the same shape under a `when OnHand > Reserved` guard discharging identically.

## Scope

- **In scope**:
  - **The subject-resolution seam (Decision A).** `TryFlowNarrowingProof` resolves the obligation's `NumericProofRequirement.Subject` against `obligation.Site` (via the existing `ResolveSubject`) to recover the *discharge-relevant sub-expression* — for a divisor obligation, the `(X − Y)` subtraction node — before applying the subtraction gate and the relational truth-table. This is the seam the core design assumed already existed.
  - **Threading the unconditional-rule relation into the same path (Decision B).** Restructuring the `guard is null` early-return at `Strategies.cs:1093` so an unguarded-row obligation falls through to a rule-sourced `FieldToFieldConstraint` lookup, while preserving the `ReassignedBefore` staleness gate at `:1107`. (This is the same restructure the core design's Inventory step already named at `Strategies.cs:1078`; this amendment specifies *what gets fed* once the fall-through is reached.)
  - **The soundness argument that `(X − Y) != 0` follows from `X > Y` without knowledge of Y's sign** (Decision C / § Semantic Rules S3), resolving the proof-engine.md:1343 "requires knowledge of B's sign" caveat head-on and bounding exactly which divisor shapes the relation discharges (subtraction divisors, NOT bare-field divisors).
  - The blast-radius analysis showing this is strictly additive on the value-discharge side and touches no satisfiability scan.
- **Out of scope** (locked upstream — cited, not re-decided):
  - All four core-design Decisions: 1 (`FieldToFieldConstraint` reuse, no new record), 2 (guarded relational/magnitude rule DROP filter on the shared `Composition.cs` rule→fact loop; closes BUG-023), 3 (`NumericInterval.Intersect` into the discharge-time `narrowed` dictionary, depth-1 by bare `ExtractFieldInterval`), 4 (satisfiability-scan isolation: relational narrowing must never reach the bare `ExtractFieldInterval` the satisfiability/vacuity/contradiction scans read). This amendment composes with all four and preserves Decision 4's isolation invariant (its change is on the `GuardRelationImpliesObligation` / sign-set discharge path; it touches no satisfiability scan).
  - Parent Decision 2 (= B, relation-as-fact) and Decision 4 (single-pass, depth-bounded, no fixpoint).
  - The **interval/sign-set narrowing of `X` and `Y` themselves** (R-NARROW-GE/LE into `narrowed[X]`) — that is the core design's Decision 3 and feeds range/overflow obligations on the *operand fields*. **Tradeoff detail (Principles 1/7/10/11 — load-bearing).** This seam sits on the prevention guarantee. The single soundness-critical question is *which divisor shapes a relation discharges*. ## Semantic Rules

### S1 — The defect, stated precisely

A fault-prone binary operator declares its obligation **on a parameter**, not on the whole node. From the catalog (`Operations.cs:119-166`):

```
IntegerDivideInteger / DecimalDivideDecimal (and the Modulo siblings):
    ProofRequirements: [ NumericProofRequirement(ParamSubject(divisorParam), NotEquals, 0, "Divisor must be non-zero") ]
```

The type checker stamps this obligation with `Site = the Divide node` (`ProofEngine.cs:305-307`: `new ProofObligation(req, bin, ctx, …)`). So for `Z / (X − Y)`:

```
obligation.Site        = TypedBinaryOp(Divide, Left = Z, Right = TypedBinaryOp(Minus, X, Y))
obligation.Requirement = NumericProofRequirement(Subject = ParamSubject(divisorParam), NotEquals, 0)
```

The **discharge-relevant sub-expression** is `obligation.Site.Right = (X − Y)`, recoverable by the existing catalog-driven bridge `ResolveSubject(ParamSubject(divisorParam), Site)` → `ResolveParamInBinaryOp` → `bin.Right` (`ProofEngine.cs:852-890`). Every other numeric strategy resolves the Subject this way first (`TryLiteralProof` at `Strategies.cs:15`; `TryCompositionalConstraintProof` at `Composition.cs:18`; `ApplyTrustedRuleFacts` at `Composition.cs:98`).

`TryFlowNarrowingProof` does **not**. It reads `obligation.Site` raw (`Strategies.cs:1095`: `if (obligation.Site is not TypedBinaryOp binaryOp) return false;`), then (`:1098`) `if (!IsSubtractionOp(binaryOp.ResolvedOp)) return false;`. For a divisor obligation `binaryOp` is the **Divide** node, the subtraction gate fails, and the function returns before any relation is consulted. The relation `X > Y` — guard-sourced or rule-sourced — is never reached. Probe-confirmed: both `rule OnHand > Reserved` and `when OnHand > Reserved` leave `(OnHand − Reserved) != 0` Unresolved (PRE0083).

### S2 — Why interval/sign-set narrowing of the operands cannot substitute

One might hope the core design's Decision-3 narrowing (`narrowed[X]`, `narrowed[Y]`) discharges this. It cannot. The divisor subject is the *compound* `(X − Y)`, and its sign/interval computed from the operands loses the correlation:

```
IntervalOf(X − Y) = IntervalOf(X) − IntervalOf(Y) = [0,∞) − [0,∞) = [−∞, ∞]   (admits 0)
SignSet(X − Y)    = AddSignSets(SignSet(X), Negate(SignSet(Y)))
                  = AddSignSets(Nonnegative, Nonpositive) = Unknown            (ResolveBinarySignSet, Composition.cs:358)
```

Interval subtraction and sign-set addition are *non-relational* — they discard the fact that `X` and `Y` move together. The survey states this directly for the non-relational-interval domains: "a relation `x>=y` can only be *used* to narrow `x` via the branch/guard, not stored *as* a relation … relations between variables are **lost**" (`relational-constraint-representation-survey.md:36`). Proving `(X − Y) ≥ 1` (hence `≠ 0`) from `X > Y` **requires applying the relation to the subtraction directly** — the octagon/relation-as-fact step — which is exactly what `GuardRelationImpliesObligation` does, and exactly what the unresolved Subject prevents it from reaching. This is why the seam (resolve the subject, then consult the relation) is the *only* sound discharge, not a convenience.

### S3 — The B-sign caveat resolved: `X > Y ⇒ X − Y > 0` holds for every sign of Y

proof-engine.md:1343 states "Division is NOT covered — proving `A != 0` from `A > B` requires knowledge of B's sign." This conflates two distinct shapes:

- **Bare-field divisor `Z / A` with `A > B`** (the doc:1356 row, `A > B | B / A | divisor != 0 | ❌`): correct that `A > B` does NOT prove `A ≠ 0` — `A` could be 0 with `B` negative. The resolved subject here is a `TypedFieldRef` (`A`), fails the subtraction gate, stays Unresolved. **Soundly not covered.**
- **Subtraction divisor `Z / (A − B)` with `A > B`** (the demonstrator): `A > B ⟺ A − B > 0` by translation-invariance of `>` over an ordered field — subtract `B` from both sides. This holds **regardless of either operand's sign**: no knowledge of `B`'s sign is needed, because the subtraction *is* the difference the relation directly bounds. `A − B > 0 ⇒ A − B ≠ 0`.

So the doc's stated reason ("requires knowledge of B's sign") is true for the *bare-field* divisor and false for the *subtraction* divisor. The seam covers exactly the second shape — which is the shape `GuardRelationImpliesObligation` was already built for (its rows are all `A − B`/`B − A` subtraction expressions) but which the unresolved Subject made unreachable. **The strict/non-strict boundary is load-bearing and preserved by reuse:** `X > Y ⇒ X − Y > 0 ⇒ ≠ 0` (table row `(>, !=, 0) → true`); `X >= Y` admits `X == Y ⇒ X − Y == 0`, so it must NOT discharge `!= 0` (table row `(>=, !=) → false`, the absent row). The truth-table already encodes this; the seam changes only *reachability*, not the table.

### S4 — Reduction (the discharge rule)

```
  obligation.Requirement = NumericProofRequirement(Subj, ⊕, t)     ⊕ ∈ {>, >=, <, <=, !=}
  s = ResolveSubject(Subj, obligation.Site)                        s = TypedBinaryOp(Minus, X, Y)
  X, Y are field refs        X, Y ∉ obligation.ReassignedBefore
  ∃ relation R = FieldToFieldConstraint(X, relop, Y)               R from context guard OR unconditional unguarded rule
  GuardRelationImpliesObligation(R, s, X, Y, requirement) = true
  ─────────────────────────────────────────────────────────────────────────────────────── (R-SUBJECT-DISCHARGE)
        obligation ⇝ Proved (ProofStrategy.FlowNarrowing)
```

The only change to the discharge *rule* is the first premise: the binary op fed to the subtraction gate and the truth-table is `s = ResolveSubject(Subj, obligation.Site)` (the resolved divisor sub-expression), **not** `obligation.Site` raw. (Decision B additionally supplies the relation source for the *unguarded* case: the headline rule-sourced demonstrator hits the `guard is null` return at `:1093` *before* the site read, so it needs the fall-through too — Decision A alone suffices only for the guard-sourced case.) Everything downstream — the `IsSubtractionOp` gate, the `GetFieldName` extraction of `X`/`Y`, the `ReassignedBefore` staleness gate, the per-OR-branch guard decomposition, and the `GuardRelationImpliesObligation` truth-table — is unchanged.

When `s` is not a `TypedBinaryOp` (e.g. a bare `TypedFieldRef` divisor, or a function-call subject), or `s` is a non-subtraction binary op, the function returns false exactly as today — the obligation stays Unresolved and rejects.

### S5 — Proof obligations

This amendment adds **no new `ProofRequirement`, no new `ProofRequirementKind`, no new `ProofStrategy` member**. It changes *which expression* an existing strategy reasons over (the resolved subject, not the raw site) and *which sources* feed it (guards plus unconditional rules). Discharge attributes via the existing `ProofStrategy.FlowNarrowing`.

### S6 — Soundness preservation claim (named, per-axis)

Principles threatened: **1** (prevention), **7** (compile-time-first), **10** (totality), **11** (static completeness, both directions).

- **Subject-resolution sound (Principle 1).** `ResolveSubject(divisorParam, DivideSite)` returns exactly `bin.Right`, the actual divisor expression, by `ReferenceEquals` against the catalog's `Rhs` ParameterMeta (`ProofEngine.cs:886`). The resolved expression IS the operand whose `!= 0` the obligation requires — so discharging the relation against it discharges the true obligation, not a proxy. No over-prove from resolving the wrong sub-expression.
- **Translation-invariance sound (Principle 1, the B-sign axis).** `X > Y ⇒ X − Y > 0` for all operand signs (§ S3); the truth-table row `(>, !=, 0)` is therefore sound for the subtraction subject. The non-strict `>=` row is *absent* from the table, so `X >= Y` does not discharge `!= 0` — the `X == Y ⇒ 0` boundary is respected.
- **Bare-divisor stays unresolved (Principle 1).** A `Z / X` divisor with `X > Y` resolves to a `TypedFieldRef`, fails `is not TypedBinaryOp`, returns false → Unresolved → rejection. The doc:1356 "❌" outcome is preserved.
- **No table change, no new over-prove (Principle 11 safe-direction).** The seam feeds the existing truth-table a subject it previously couldn't reach; it adds no row, weakens no row. Any (relation, obligation) pair the table rejected before, it rejects after.
- **Single-pass / depth-bounded (Principle 3, §0.4).** Resolution is one structural lookup; the truth-table is a value switch; the rule-source lookup is linear in declared rules. No iteration to fixpoint, no recursion into a third field. Inherits the core design's depth-1 envelope unchanged.
- **Satisfiability isolation preserved (Principle 11 reject-direction).** The seam lives entirely in `TryFlowNarrowingProof` (a discharge strategy) and the `GuardRelationImpliesObligation` truth-table. It reads neither the bare `ExtractFieldInterval` nor the `narrowed` dictionary; it adds nothing the satisfiability/vacuity/contradiction scans consume. Core-design Decision 4's invariant is untouched — those scans remain byte-identical.
- **Staleness preserved (Principle 1, sequential proof flow §0.6.7).** The `ReassignedBefore` gate at `Strategies.cs:1107` stays: a relation about an operand reassigned earlier in the chain is stale and must not discharge. The rule-source fall-through must route *through* this gate, not around it (Decision B).

## Architecture Grounding

### Precept-internal placement

**Layer placement.** Pipeline code (the proof engine's discharge stage), not catalog metadata. The defect is that one discharge strategy (`TryFlowNarrowingProof`) skipped the Subject-resolution step every other numeric strategy performs; the fix restores that step. The catalog already declares *what* must be proved (the divisor obligation with its `ParamSubject` divisor) and already carries the Subject→operand mapping (`ResolveParamInBinaryOp`); the strategy is *how*. This respects the catalog rules: no enum-identity dispatch (the operator-implication remains the value truth-table `GuardRelationImpliesObligation`, not a `*Kind switch`); no new record (Decision A of the core design — `FieldToFieldConstraint` — is reused). It is the inverse of the smell: the divisor obligation is generic (`ParamSubject(divisorParam)`), and resolving it generically is exactly the metadata-driven shape the Obligation Generation Contract (proof-engine.md:495-507) demands — "the discharge side already reads ProofSatisfactions broadly," and this brings the one strategy that didn't into line.

**Cross-component propagation:**
- **Runtime (parser, type checker, evaluator, diagnostics):** Proof engine — `TryFlowNarrowingProof` resolves the Subject before the subtraction gate, and falls through to a rule-sourced `FieldToFieldConstraint` lookup when the context guard is null (preserving the `ReassignedBefore` gate). Parser / type checker / evaluator — **None** (no new node, no new typing rule, no runtime path; the divisor obligation and its `ParamSubject` already exist). Diagnostics — **None new** (the relational-unprovable case reuses the existing PRE0083 / sqrt / OutOfRange diagnostics with `FlowNarrowing` attribution; the diagnostic already renders the resolved subject `(OnHand − Reserved)`, probe-verified).
- **Tooling (highlighting, completions, hover, semantic tokens):** Hover proof-attribution — a previously-Unresolved divisor now reports Proved via `FlowNarrowing`, already a known strategy; **None** structural.

### External architectural precedent

The architectural problem: *a fault-prone operator's safety obligation targets a compound sub-expression over two related fields; how does the discharge engine bring a declared two-field relation to bear on that sub-expression by a bounded, legible operation?*

The canonical answer is the **relation-as-fact (B)** discharge of difference-bound-matrix / octagon domains: keep the relation `x − y ≤ c` as a stored fact, and discharge a property of the *difference* `x − y` against it directly — never by re-deriving the difference's range from the operands' independent ranges, which loses the correlation. The survey is explicit that the non-relational-interval domains *lose* exactly this:

> "**A** — each variable carries an interval `[lo,hi]`; a relation `x>=y` can only be *used* to narrow `x` via the branch/guard, not stored *as* a relation … relations between variables are **lost**" (survey:36, the non-relational-interval row)

> "**B** — the relation `±x ± y ≤ c` is a first-class element of a shared DBM … the closed form *is* a rule list" (survey:37, the octagon row)

**What Precept takes:** the B insight that a two-field relation must be applied to the *difference expression directly* (here: resolve the obligation Subject to the `(X − Y)` node, then consult the relation via the truth-table) rather than reconstructed from per-operand intervals — which § S2 proves yields `Unknown`. **What Precept deliberately diverges from:** the octagon domain runs an O(n³) Floyd–Warshall strong closure over a full DBM; Precept does a single resolution + a single truth-table lookup against the *specific* relation naming the two operands — "octagons minus the loop-widening step" (survey:76/133), restricted further to the one-hop, one-pair discharge the obligation needs. The divergence buys termination and a per-rule/per-guard witness at the cost of completeness (no transitive closure). The seam itself — *resolve the catalog-declared parameter Subject to recover the operand sub-expression before relational discharge* — has no external comparator (octagon engines work over a flat variable set, not a parameterized-operation obligation model); it is a Precept-specific consequence of the catalog-driven obligation architecture (obligations target `ParamSubject`s, and the `ResolveSubject` bridge is Precept's own), and is acknowledged as such. It is the in-tree-precedented shape: every other numeric strategy already resolves the Subject this way (`TryLiteralProof`, `TryCompositionalConstraintProof`).

## Decisions

### Decision A: Resolve the obligation's `NumericProofRequirement.Subject` against `obligation.Site` (via the existing `ResolveSubject`) to recover the divisor sub-expression, before the subtraction-shape gate and the relational truth-table

**Stakes**: high (the load-bearing correctness fix — a wrong call here either leaves the demonstrator broken, or, if it resolved the wrong sub-expression, over-proves a divisor that can be zero — a Principle-1 breach).

- **Rationale**: The divisor obligation is declared on the divisor *parameter* (`Operations.cs:124`: `ParamSubject(PInteger)`), and the proof engine's standard, catalog-driven way to recover the expression a `ParamSubject` denotes is `ResolveSubject(numeric.Subject, obligation.Site)` (`ProofEngine.cs:852-890`), which for a Divide site returns `bin.Right` — the `(X − Y)` subtraction. Every other numeric strategy already does this (`TryLiteralProof` :15, `TryCompositionalConstraintProof` :18, `ApplyTrustedRuleFacts` :98). `TryFlowNarrowingProof` is the lone strategy that reads `obligation.Site` raw (:1095), so it sees the Divide node, fails the `IsSubtractionOp` gate (:1098), and returns before the relation is consulted. The fix is to bring this one strategy into line with the others: resolve the Subject, then gate on the *resolved* expression's shape. The relation `X > Y` then reaches the unchanged `GuardRelationImpliesObligation` truth-table against the `(X − Y)` subtraction — the exact subtraction shape that table was built for. This is reuse, not new mechanism: the resolution bridge, the subtraction gate, the truth-table, and the strategy attribution all already exist.
- **Tradeoff accepted**: *On the flow-narrowing path*, the seam discharges only the *subtraction-divisor* shape (`Z/(X−Y)` from `X > Y`), not the bare-field-divisor shape (`Z/X` from `X > Y`): a bare-field divisor resolves to a `TypedFieldRef`, fails the subtraction gate, and stays Unresolved *via this strategy*. When `X > Y` does not constrain `X`'s sign (e.g. `Y` unconstrained), that Unresolved is the correct §0.6-soundness outcome (the doc:1356 "❌" row — `X > Y` alone does not prove `X ≠ 0`). The complementary case — `rule X > Y` with `Y` itself sign-constrained (`Y nonnegative` ⇒ `X > 0`) — discharges the bare `Z/X` via the *sign-set* path (`ResolveNumericSubjectSignSet`, core-design Decision 3), which is out of scope for this seam (§ Scope). So the boundary this seam draws is "the flow-narrowing path covers the subtraction divisor; the bare-field divisor is the sign-set path's job, and stays Unresolved here when no sign-set discharge applies" — not a claim that bare divisors never discharge. The author cost is only that a bare `Z/X` with no sign-decidable relation must constrain `X` directly (`nonzero`/`positive`/a guard), the established divisor-safety posture (§0.6 item 3).
- **Alternatives considered**:
  - *(Move the divisor obligation's `Site` to point at the subtraction sub-expression at emission time, so `TryFlowNarrowingProof` reads it raw and works unchanged)* — rejected: it would desynchronize `Site` from the operator node that carries the `ProofRequirements`, breaking every *other* consumer that reads `obligation.Site` expecting the operator node (diagnostics render `on event … from state …` keyed on the Divide site; `ResolveSubject` itself dispatches on the site being the operation; the OutOfRange/sqrt families all assume Site = the carrying node). The Subject already encodes "which operand" — moving the Site re-encodes that information in the wrong place and forks the obligation model. Resolution at discharge time is the architecture's intended seam (the Subject is *for* this).
  - *(Special-case the divisor: in `TryFlowNarrowingProof`, if the site is a Divide, descend into `.Right`)* — rejected: hardcodes the Divide/Right relationship the catalog already expresses via `ParamSubject` + `ResolveParamInBinaryOp` (which checks Rhs-before-Lhs precisely so the divisor resolves correctly). A Divide-specific descent is a parallel copy of catalog knowledge (CLAUDE.md violation) and would not generalize to sqrt/modulo/other parameterized obligations; `ResolveSubject` generalizes for free.
  - *(Discharge the subtraction divisor through the sign-set path instead — teach `ResolveBinarySignSet`'s Minus arm to consult the relation)* — rejected as the primary mechanism: it would require the sign-set fold to carry relational facts into a *per-operand* computation that is structurally non-relational (`AddSignSets(Nonnegative, Nonpositive) = Unknown`, § S2), i.e. re-introducing the correlation the sign-set domain discards — a larger and less-precedented change than reusing the relation-as-fact truth-table that already exists for exactly this shape. (The sign-set path remains the right home for the *operand-field* sign contributions in the core design's Decision 3; it is the wrong home for the *compound subtraction* subject.)
- **Precedent**: In-tree, `TryLiteralProof` (`Strategies.cs:15`), `TryCompositionalConstraintProof` (`Composition.cs:18`), and `ApplyTrustedRuleFacts` (`Composition.cs:98`) all open with `ResolveSubject(numeric.Subject, obligation.Site)` and reason over the resolved subject — this seam makes `TryFlowNarrowingProof` consistent with the established pattern. `ResolveParamInBinaryOp`'s Rhs-before-Lhs check (`ProofEngine.cs:883-887`) exists specifically so a divisor `ParamSubject` resolves to `bin.Right`. External: the relation-as-fact (B) octagon/DBM discharge applies the relation to the *difference* directly (survey:37) rather than reconstructing it from operand intervals (survey:36, which "loses" it).
- **Sources consulted for this decision**: `src/Precept/Language/Operations.cs:119-166` — the divisor obligation's `ParamSubject(divisorParam)` Subject; `src/Precept/Pipeline/ProofEngine.cs:305-307` — Site = the binary-op node; `:852-890` — `ResolveSubject` / `ResolveParamInBinaryOp` returning `bin.Right`; `src/Precept/Pipeline/ProofEngine.Strategies.cs:10-37` — `TryLiteralProof`'s resolve-first shape; `:1095-1098` — `TryFlowNarrowingProof`'s raw-Site read and subtraction gate; `:1213-1238` — the unchanged truth-table; `src/Precept/Pipeline/ProofEngine.Composition.cs:18,98,346-363` — the other resolve-first strategies and the non-relational `ResolveBinarySignSet` Minus arm; `docs/compiler/proof-engine.md:1356` — the `B / A | ❌` bare-divisor row; `research/architecture/compiler/relational-constraint-representation-survey.md:36-37`. Grepped the canonical spec — §0.6 item 2 (relational reasoning over multiple fields, line 204) and item 3 (divisor safety, line 205) declare this discharge as a *language-level commitment* to implement; the *mechanism* is delegated to `compiler-and-runtime-design.md` (§0.7 line 270 per the parent design). So this is implementation against locked spec, not a fresh language decision; the seam choice is the open implementation question the probe surfaced.
- **Strongest counter-evidence**: The core design (Locked 2026-06-04) asserts in its S4 consumer table and matrix #1 that this discharge already works through `TryFlowNarrowingProof` → `GuardRelationImpliesObligation` — i.e. a locked sibling design says there is no seam to add. Response: that assertion is falsified by the `precept_compile` probe (demonstrator and guard-sourced both emit PRE0083, divisor Unresolved) and by source (`TryFlowNarrowingProof` reads `obligation.Site` raw, never `ResolveSubject`, so a Divide site fails the subtraction gate). This amendment corrects the falsified claim; the correction is the doc-update obligation enumerated below. Looked in `Strategies.cs`, `ProofEngine.cs`, the core design's S4 and Inventory, and ran the probe; the source and the probe agree the seam is absent.
- **Reversibility**: Easy — the change is localized to `TryFlowNarrowingProof`; `ResolveSubject` is an existing private helper, no public surface, pre-release, no external consumer.
- **Blast radius**: `ProofEngine.Strategies.cs` (`TryFlowNarrowingProof` only). No catalog, no DTO, no other strategy, no satisfiability scan, no samples newly-red (strictly additive on value-discharge). One proof-engine stage doc (the :1343/:1356 correction) and the core design's S4/matrix correction.

### Decision B: Thread the unconditional-rule relation through the SAME resolved-subject path by falling through the `guard is null` early-return, preserving the `ReassignedBefore` staleness gate

**Stakes**: medium (reachability + a staleness-soundness gate; the over-prove risk is fenced by reusing the existing gate and truth-table).

- **Rationale**: `TryFlowNarrowingProof` reads the obligation's *own context guard* (`Strategies.cs:1080-1092`) and returns at :1093 if there is none. An unconditional `rule X > Y` provides no context guard, so the demonstrator (an unguarded row) hits :1093 and never reaches the field-to-field lookup. The fix is to fall through: when the context guard is null, look up a rule-sourced `FieldToFieldConstraint` for the resolved subject's `(X, Y)` pair (from the core design's `CollectRelationalFacts`, already gated by Decision 2's guarded-rule DROP filter so only *unconditional* rules contribute) and feed it to the same per-branch `GuardRelationImpliesObligation` loop. Crucially, the `ReassignedBefore` gate (:1107) must run on this path too: a rule-sourced relation about an operand reassigned earlier in the chain is exactly as stale as a guard-sourced one (§0.6.7 sequential proof flow), and must not discharge. Routing the fall-through *after* the gate (not around it) preserves staleness soundness.
- **Tradeoff accepted**: A guarded `rule X > Y when Flag` contributes NO unconditional relational fact (Decision 2 drops it from the global set), so it does not discharge a global subtraction divisor — only the in-scope (guard-sourced) path does. This is the path-sensitive correct behavior (the core design's Decision 2 soundness rule); the cost is that an author relying on a guarded relation for a divisor outside that guard's scope gets a rejection, and must either make the rule unconditional or guard the dependent operation into scope.
- **Alternatives considered**:
  - *(Add a separate rule-sourced discharge strategy parallel to `TryFlowNarrowingProof`)* — rejected: it would duplicate the resolved-subject resolution, the subtraction gate, the `ReassignedBefore` gate, and the truth-table — exactly the fork the core design's Decision 1 avoided at the data level. One strategy, two sources (guard, unconditional rule) feeding one truth-table is the reuse shape.
  - *(Feed rule-sourced relations through the `narrowed`/sign-set path only)* — rejected for the subtraction subject for the § S2 reason (the sign-set Minus arm yields Unknown); the rule-sourced relation must reach the truth-table for the compound subtraction, same as the guard-sourced one.
- **Precedent**: In-tree, `TryFlowNarrowingProof`'s existing context-guard read (`Strategies.cs:1080-1092`) is the established field-to-field discharge; this extends its *source set* to unconditional rules while reusing its body. The core design's Inventory already names this fall-through (its `Strategies.cs:1078` bullet, "restructure the :1093 gate to fall through … while preserving the ReassignedBefore staleness gate at :1107"); this decision adopts that and binds it to the resolved subject. External: flow-sensitive interpreters attach a guard-conditioned relation to the program point where the guard holds and treat an unconditional invariant as globally available (survey's EVA/InferBO note) — unconditional rule = globally available fact, guarded rule = point-scoped, exactly Decision 2's drop-from-global + discharge-in-scope.
- **Sources consulted for this decision**: `src/Precept/Pipeline/ProofEngine.Strategies.cs:1080-1093` — the context-guard read + the `guard is null` early-return; `:1107-1109` — the `ReassignedBefore` staleness gate; `:1111-1128` — the per-OR-branch decomposition and the truth-table loop; `docs/Working/relational-narrowing-core-design-2026-06-03.md § Inventory` (the `Strategies.cs:1078` bullet, the `:1093` fall-through enumerate-step) and § Decision 2 (the guarded-rule DROP filter that gates which rules `CollectRelationalFacts` yields); `docs/language/precept-language-spec.md §0.6.7` — sequential proof flow / reassignment invalidation. Grepped the core design — the fall-through is already named there; this decision specifies that the resolved subject (Decision A) is what the fall-through feeds, and that the staleness gate is on-path.
- **Strongest counter-evidence**: One could route the rule-sourced relation *before* the `ReassignedBefore` gate to maximize discharge reach. Response: that would be unsound — a relation about a reassigned operand is stale regardless of source; the gate must run for both. Looked in `Strategies.cs:1104-1109` (the gate's own comment: "the narrowing relies on a guard relating the two operands … if either operand was reassigned earlier … that relation is stale and must not discharge") — the comment's reasoning applies verbatim to a rule source.
- **Reversibility**: Easy — the fall-through is additive and gated; removing it restores today's guard-only behavior.
- **Blast radius**: `ProofEngine.Strategies.cs` (`TryFlowNarrowingProof` — the fall-through and the shared resolution tail). Consumes the core design's `CollectRelationalFacts` (Decision 2). No catalog, no DTO, no satisfiability change, no newly-red samples.

### Decision C: Correct the proof-engine.md "Division is NOT covered — requires knowledge of B's sign" caveat to distinguish the bare-field divisor (genuinely not covered) from the subtraction divisor (covered, no sign knowledge needed)

## Falsifiers

- **Never-over-prove (Principle-1 falsifier, load-bearing).** If a precept whose only divisor-safety source is a relational subtraction discharge compiles clean and a runtime divide-by-zero (or sqrt-of-negative) then fires on it, the resolved-subject + truth-table reuse is unsound — immediate redesign. The most important falsifier: the seam must never discharge a subtraction divisor whose relation is non-strict (`>=`) for a `!= 0` obligation.
- **Bare-divisor leak (flow-narrowing path).** If `Z / X` with `rule X > Y` ever discharges **via `TryFlowNarrowingProof`** — the resolved subject is a `TypedFieldRef`, not a subtraction, yet the subtraction-shape gate accepted it — the gate leaked; immediate redesign. (This falsifier is specific to the flow-narrowing path's subtraction gate. It is NOT a claim that a bare divisor never discharges: a bare `Z/X` with `Y nonnegative` legitimately discharges via the *sign-set* path per core-design Decision 3, and that is correct, not a leak.)
- **Strict/non-strict boundary.** If `rule X >= Y` discharges `(X − Y) != 0`, the truth-table's absent `(>=, !=)` row was effectively added — the `X == Y ⇒ 0` case is reachable and being mis-proved. Standing test (matrix #8).
- **Satisfiability interference.** If, after this seam, any precept that compiled clean before now emits `UnsatisfiableGuard`/`VacuousRule`/`ContradictoryRule`/etc. *because* of the relational subtraction discharge, the change leaked into a satisfiability scan (it must not — the seam touches only `TryFlowNarrowingProof` and the truth-table). Core-design Decision 4's regression fixture (adversarial, matrix #11) is the standing guard.
- **Staleness leak.** If a relation about an operand reassigned earlier in the action chain discharges a later subtraction-divisor obligation, the `ReassignedBefore` gate was bypassed on the rule-sourced fall-through — §0.6.7 sequential-proof-flow violation. Standing test.
- **Subject-resolution drift.** If `ResolveSubject(divisorParam, DivideSite)` ever returns `bin.Left` (the dividend) instead of `bin.Right` (the divisor), the Rhs-before-Lhs ordering in `ResolveParamInBinaryOp` regressed and the seam would prove the wrong operand safe. The demonstrator test (matrix #1) plus a dividend-side negative control guard this.
