# Relational-contradiction discharge guard — rejecting an empty/contradictory subject narrowing instead of vacuously proving safe (Slice 2c-i soundness amendment)

> **Amendment provenance.** The core design's representation (Decision 1), extraction/guard-filter (Decision 2), and satisfiability-scan *isolation intent* (Decision 4) are correct and STAND. What its Decision-3 folds got wrong is a missing consistency check: they narrow `X` from `Y`'s interval without verifying the result is consistent with `X`'s *own* declared bounds. When the relation contradicts those bounds, the intersection is empty (⊥), and the discharge readers — by `NumericInterval.Contains(empty) => true` — read ⊥ as "every obligation discharges." That is a false "proved safe," the worst outcome (Principle 1). This amendment makes the discharge engine treat a ⊥-narrowed subject as **infeasible → reject**, reproducing the octagon/DBM "empty zone = unsatisfiable" discipline, and surfaces the contradiction as an Error-level rejection — **without** feeding any tighter interval to the satisfiability scans Decision 4 deliberately isolated.

## Goal

When done, a `Compiler.Compile` of a precept whose unconditional relational rule `rule X op Y` contradicts `X`'s own declared bounds (so `⟦X⟧ ⊓ relational-half-line = ∅`) **rejects at Error severity** — naming the contradiction and citing the rule — instead of compiling clean while a downstream fault-prone operation on `X` silently over-proves; AND a relational rule that merely *tightens* `X` to a non-empty interval still compiles clean and still discharges, with the satisfiability scans (VacuousRule/ContradictoryRule/UnsatisfiableGuard) byte-identical to today (Decision-4 isolation preserved).

## Scope

- **In scope**:
  - **The discharge-side contradiction guard (Decision 1).** Detect, on the discharge path, when a relational fold drives the subject's narrowed interval empty (or its relational sign-set to `None`/empty after intersection with declared bounds), and convert that from a vacuous "proved safe" into an explicit **unprovable/reject** outcome — covering BOTH the interval fold (`RelationalHalfLine` → empty `narrowed[X]`) and the sign fold (`TryRelationalSignForField` → a sign the subject's own bounds forbid).
  - **The rejection diagnostic and where it is detected (Decision 2).** Which diagnostic the contradiction emits, at what severity, and the seam where the empty-narrowing is observed so the rejection reaches a check without feeding a tighter interval to the satisfiability scans.
  - **The magnitude-vs-relational convergence decision (Decision 3).** Whether the relational contradiction path and the magnitude path (`rule X >= 10`, `X max 5`) converge on one diagnostic/severity — including the verified finding that the *existing* magnitude path is itself only a Warning and ALSO over-proves the divisor.
  - The soundness-preservation proof for each axis: the over-prove closes; no false rejection is introduced for a non-empty (legitimately satisfiable) relational narrowing; Decision-4 isolation is untouched; single-pass / depth-1 / determinism preserved.
- **Out of scope** (locked upstream — cited, not re-decided):
  - Core-design Decisions 1 (`FieldToFieldConstraint` reuse), 2 (guarded-rule DROP filter, BUG-023), 4 (satisfiability-scan isolation INTENT). This amendment preserves all three; it only refines Decision 4's *completeness* claim and adds the missing discharge-side guard the folds lacked.
  - The subject-resolution amendment (`relational-subject-resolution-discharge-2026-06-04.md`, Decisions A/B) — orthogonal; untouched.
  - The `RelationalHalfLine` / `TryRelationalSignForField` *narrowing arithmetic itself* (how the half-line/sign is computed from `⟦Y⟧₀`) — correct; this amendment adds a consistency check on the *result*, it does not change how the half-line is derived.
- **Out of scope — adjacent, flagged not fixed**:
  - **The magnitude path's Warning-not-Error over-prove (a verified pre-existing soundness hole, possibly a new BUG).** The probe shows `rule X >= 10` with `X max 5` and `100/X` emits ONLY `UnsatisfiableRule` (Warning), `HasErrors=False`, and the divisor over-proves (no `DivisionByZero` Error). This means the magnitude contradiction path *already* lets a fault through a building precept — the brief's premise that "magnitude correctly rejects" is falsified. Whether to (a) escalate the magnitude path to Error here, or (b) file it as a sibling bug and converge both paths, is **Decision 3** — but the magnitude-side *root* (an unsatisfiable rule's bound still folding as a discharge fact) is a broader emission/blocking question this discharge-side amendment scopes carefully (see Decision 3 and Open Questions).
- **Deferred to future**: none for the relational-contradiction case. Detection, the reject outcome, and the diagnostic are complete here.

**Tradeoff detail (Principles 1/10/11 — load-bearing).** This amendment sits on the prevention guarantee in BOTH soundness directions. (1) The over-prove it closes is a Principle-1 breach: a false "proved safe" lets a runtime divide-by-zero / overflow / out-of-range through a clean compile — the worst possible outcome. (2) The hazard it must NOT re-open is Decision 4's: feeding a tighter (even empty) relational interval into the `ExtractFieldInterval` the satisfiability scans read would make `VacuousRule`/`ContradictoryRule`/`UnsatisfiableGuard` fire on precepts whose *non-relational* bounds are satisfiable — a false REJECTION (Principle 11, opposite direction). The resolution is that the genuine-contradiction case (empty intersection) is detected **on the discharge path** — where the narrowing already lives (the `narrowed` dict / the sign-set fold) — and converted to a reject there, while the satisfiability scans continue to read the bare `ExtractFieldInterval` and stay byte-identical. The empty intersection is *not* a "tighter interval that might falsely flag a satisfiable rule" — it is a proven contradiction (the relation cannot hold given declared bounds), so rejecting it is prove-or-reject-correct, not a false rejection. This is exactly the octagon/DBM distinction: a *tighter non-empty* zone is a refinement; an *empty* zone is infeasibility (survey:84).

**Companion commitments.** *Stateless-first-class*: the contradiction is field-scoped (declared bounds vs a field-only rule), applies identically to stateless precepts. *Domain-expert-primary-author*: the author who writes `rule X >= Y` with `X max 5` and `Y min 10` has written a self-contradictory contract; the rejection tells them so in their own terms (the rule cannot hold given the field's bounds), which is more honest than silently "proving" a division safe that will fault.

## Audience and Teachability

The amendment changes one author-observable behavior — a self-contradictory relational precept now rejects instead of silently compiling — so a brief audience note is warranted even though no language surface is added.

**Worked example (the contract a domain expert would write, and the contradiction they'd commit):**

```precept
precept DiscountTier
field Floor as money in 'USD' min '10 USD' max '50 USD' default '10 USD' editable
field Ceiling as money in 'USD' min '100 USD' max '200 USD' default '100 USD' editable
field PerUnit as money in 'USD' <- Floor / Ceiling   # illustrative; the point is Floor's bounds
rule Floor >= Ceiling because "a floor that meets or exceeds the ceiling collapses the tier"
state Open initial terminal
```

`rule Floor >= Ceiling` with `Floor max '50 USD'` and `Ceiling min '100 USD'` is self-contradictory: no value of `Floor` in `[10,50]` can be `>= Ceiling ∈ [100,200]`. Today this compiles clean and `Floor` silently "proves" properties it cannot hold. After this amendment it rejects, pointing at the rule.

**Error message (exact wording for this misuse):**

```
PRE0159: Rule 'Floor >= Ceiling' cannot hold — field 'Floor' is bounded to at most 50 USD, but the rule requires it to be at least 100 USD (the lowest value 'Ceiling' can take). Widen 'Floor's bound, tighten 'Ceiling's, or remove the rule.
```

Why this serves the domain expert, not the developer: it names the two fields and the *concrete bound conflict* in the author's vocabulary ("at most 50 … at least 100"), and offers the three real fixes — never mentions `narrowed` dictionaries, `Intersect`, or `⊥`.

**10-minute teaching path:** (1) `docs/language/precept-language-spec.md §0.6` items 2/7 (relational reasoning; contradictory-rule detection) — 4 min; (2) the `samples/` reorder precept using `rule OnHand > Reserved` (the *valid* relational case, for contrast) — 3 min; (3) the PRE0159 diagnostic entry in `docs/compiler/diagnostic-system.md` — 2 min. Total ≤ 9 min.

## Semantic Rules

### S1 — The defect, stated precisely

For an unconditional `rule X op Y`, the core design's Decision-3 folds compute (verified at `Intervals.cs:628-640` and `Composition.cs:479-489`):

```
interval fold:  narrowed[X] := ExtractFieldInterval(X) ⊓ RelationalHalfLine(op, ExtractFieldInterval(Y))
sign fold:      signSet(X)  := signSet(X) & TryRelationalSignForField(rule, X)   # from ⟦Y⟧₀'s decidable-sign bound
```

Neither checks the result against `X`'s own declared interval for *consistency*. For the repro `rule X >= Y`, `X min 0 max 5`, `Y min 10 max 20`:

```
RelationalHalfLine(>=, ⟦Y⟧₀=[10,20]) = [10, +∞)
narrowed[X] = ⟦X⟧₀=[0,5] ⊓ [10,+∞) = [10,5]   ⟹  IsEmpty (Max 5 < Min 10) = ⊥
TryRelationalSignForField(X >= Y, Y.Min=10 > 0) ⟹ Positive          # X claimed Positive
```

The discharge readers then read ⊥ / `Positive` as **safe**:

```
TryIntervalContainmentProofNarrowed:  resultInterval=[10,5]; for many targets passes the
   Min>=DeclaredMin && Max<=DeclaredMax test vacuously, and NumericInterval.Contains(⊥) => true
   (NumericInterval.cs:127) — every containment obligation discharges.   ⟹ false "proved safe"
sign-set divisor:  signSet(X)=Positive ⟹ X ≠ 0 ⟹ 100/X discharged.    ⟹ false "proved safe"
```

This is the over-prove: a `100/X` divisor (or an assignment-range / sqrt / overflow obligation on `X`) discharges, the precept compiles clean, and at runtime `X` holds its valid `default 0`, so `100/0` faults.

### S2 — Why this is a genuine contradiction (reject-correct), NOT a false rejection (the Decision-4 distinction)

The empty intersection `⟦X⟧₀ ⊓ half-line = ∅` is a **proof that the relation cannot hold given declared bounds** — there is no value of `X` in its declared range that satisfies `X op Y` for any `Y` in `Y`'s declared range that the half-line was derived from. Rejecting it is prove-or-reject-correct (Principle 10), the contradiction class §0.6 item 7 names.

This is categorically different from the case Decision 4 guarded against. Decision 4 prevents a *non-empty but tighter* relational interval from reaching the satisfiability scans, where it would make a *satisfiable* guard/rule wrongly flag `VacuousRule`/`ContradictoryRule`/`UnsatisfiableGuard`. The distinction is exactly the octagon/DBM one (survey:84): a tighter non-empty zone is a *refinement* (must not trigger a rejection on its own); an *empty* zone is *infeasibility* ("the constraints are not satisfiable, and thus that the zone is empty"). The amendment rejects only the empty case, and detects it on the discharge path — so the satisfiability scans' inputs are unchanged and the non-empty refinement case is wholly unaffected.

### S3 — The discharge guard (the reduction rule)

```
  rule X op Y declared, guard(rule)=∅, X≠Y                       (the Decision-2-filtered relational fact)
  h = RelationalHalfLine(op, ExtractFieldInterval(Y), type(X))
  ⟦X⟧₀ ⊓ h = ∅                                                   (empty — proven contradiction)
  ─────────────────────────────────────────────────────────────────────────────── (R-CONTRA-REJECT)
        emit a contradiction REJECTION (Error) attributing to the rule + field X;
        the relational fact contributes NO discharge narrowing (no entry into narrowed[X], no sign)
```

Two coupled obligations the rule discharges:
1. **Suppress the over-prove.** A relational fact whose narrowing of `X` is empty must NOT be written into `narrowed[X]` nor folded into `signSet(X)` — so the discharge readers see `X`'s un-narrowed (or otherwise-narrowed) state and the dependent obligation stays subject to its real proof, not a vacuous ⊥-discharge. Equivalently/more strongly: a discharge reader that observes an empty `narrowed[X]` treats it as *unprovable*, never as Contains-true.
2. **Surface the contradiction.** The proven contradiction is reported as an Error-level rejection naming the rule and `X` (Decision 2 fixes which code).

The sign fold's analogue: `TryRelationalSignForField` must not contribute a sign that `X`'s own declared interval forbids. Concretely, the relational sign for `X` is admitted only if it is consistent with `signSet(⟦X⟧₀)` — i.e. the relation's claimed sign intersected with the sign `X`'s declared bounds already imply is non-empty. For `rule X >= Y`, `Y min 10`, `X min 0 max 5`: the relation claims `Positive`, but `⟦X⟧₀=[0,5]` admits `0` (Nonnegative, includes Zero), and the *combination* `X >= 10` is empty against `[0,5]` — the same emptiness test as the interval fold, computed once and shared.

### S4 — Soundness preservation claim (named, per-axis)

Principles threatened: **1** (prevention), **10** (static semantic checking), **11** (static completeness, both directions).

- **Over-prove closed (Principle 1).** When `⟦X⟧₀ ⊓ h = ∅`, the relational fact contributes no narrowing and the dependent obligation falls back to its real proof state; with no other safe carrier it stays Unresolved → the fault-prone op rejects. The `100/X` repro rejects.
- **No false rejection for the non-empty case (Principle 11, reject-direction — the Decision-4 guarantee).** The emptiness test fires ONLY when the intersection is empty. A relation that tightens `X` to a non-empty interval (the legitimate reorder demonstrator: `rule OnHand > Reserved`, both `nonnegative`) produces a non-empty `narrowed[X]`, the guard does not fire, and the precept compiles clean and still discharges. The satisfiability scans never receive the relational interval (Decision 4 untouched), so no `VacuousRule`/`ContradictoryRule`/`UnsatisfiableGuard` is added on any precept.
- **Contradiction detection is discharge-path-local (Principle 11 + Decision 4).** The emptiness is observed in the `narrowed`-dict fold and the sign fold — both discharge-time structures. `ExtractFieldInterval` is not modified; the satisfiability scans read it bare, byte-identical to today.
- **Single-pass / depth-1 / determinism (Principle 3, §0.4).** The guard is a pure `IsEmpty` test on an already-computed `Intersect`; `⟦Y⟧₀` is still read one hop via bare `ExtractFieldInterval(Y)`. No new iteration, no fixpoint. Inherits the core design's depth-1 envelope unchanged.

## Architecture Grounding

### Precept-internal placement

**Layer placement.** Pipeline code (the proof engine's discharge stage), not catalog metadata. The defect is that two discharge-time folds (interval at `Intervals.cs:628-640`, sign at `Composition.cs:479-489`) narrow `X` from `Y` without checking the result against `X`'s declared bounds; the fix is a consistency check on the fold's *result*, co-located with the fold. The catalog already declares *what* must be proved (the fault-prone op's obligation) and *what* the field's bounds are; the contradiction is *reasoning over* that metadata, which is the proof engine's job. This respects the catalog rules: no enum-identity dispatch (the emptiness test is `NumericInterval.IsEmpty`, a value property); no new record (reuses `FieldToFieldConstraint`, `NumericInterval`); the contradiction diagnostic is data-classified (proof outcome = "proved dangerous"), not syntax-shape-classified (§0.6 proof philosophy 5).

**Cross-component propagation:**
- **Runtime (parser, type checker, evaluator, diagnostics):** Proof engine — the interval fold and the sign fold gain a consistency check that suppresses the empty contribution and routes the contradiction to a rejection; the discharge readers treat an empty `narrowed[X]` as unprovable rather than Contains-true. Parser / type checker / evaluator — **None** (no new node, no new typing rule, no runtime path; the rule and field bounds already parse and bind). Diagnostics — a contradiction rejection at Error severity (Decision 2 picks the code; likely the existing PRE0159 escalated/extended to the field-op-field shape, OR an existing divisor/range Error — Decision 3 resolves the convergence).
- **Tooling (highlighting, completions, hover, semantic tokens):** Hover proof-attribution — a previously-(falsely)-Proved obligation becomes a rejected/Unresolved one citing the contradicting rule; **None** structural.
- **MCP (vocabulary, DTOs, tool output):** **None** if the diagnostic reuses an existing code; if Decision 2/3 introduces a new code, `docs/tooling/mcp.md` and the diagnostic catalog gain one entry (flagged in Decision 2). Both fact records stay private; no DTO change.

**Breaking changes.** A precept that compiled clean *because* a relational rule contradicting declared bounds falsely discharged a fault-prone op will **newly REJECT** at Error severity — this is the §0.7 soundness tax (a latent over-prove surfaced), the same shape BUG-019's and BUG-023's fixes paid. Expected and correct; the corpus check triages each newly-red sample. No legitimately-safe precept newly-reds (the guard fires only on a proven empty intersection).

### External architectural precedent

The architectural problem: *a relational constraint, narrowed into a variable's range, produces an empty (contradictory) result; should the engine treat the empty result as "everything proves" (vacuous truth) or as "infeasible" (reject)?*

The canonical answer in relational abstract domains is **empty = infeasible (⊥) = reject**, never "everything proves." The octagon/DBM literature is explicit (survey:84, *Difference bound matrix*, Wikipedia, accessed 2026-06-02):

> "It suffices to apply the Floyd–Warshall algorithm to the graph and associates to each entry (a, b) the shortest path from a to b in the graph. If this algorithm detects a cycle of negative length, this means that **the constraints are not satisfiable, and thus that the zone is empty.**"

A negative-weight cycle in the constraint graph (the discrete analogue of `⟦X⟧ ⊓ half-line = ∅`) is *the* signal of unsatisfiability; the domain reports infeasibility, it does not silently admit every goal. **What Precept takes:** the empty-intersection-is-infeasible discipline — a contradictory relation rejects, it does not vacuously discharge. **What Precept deliberately diverges from:** the DBM detects infeasibility by a global O(n³) negative-cycle search over the full closed matrix; Precept detects it locally, one relation at a time, by the `IsEmpty` test on the single `Intersect` the depth-1 fold already computes — "octagons minus the loop-widening step" (survey:76), restricted to the one-hop, one-pair discharge. The divergence buys termination and a per-rule witness at the cost of completeness (no transitive contradiction detection). **Precept-specific novelty (acknowledged):** mainstream relational domains conflate narrowing and consistency-checking in one closed structure, so "empty zone" is *automatically* infeasible there. Precept's discharge readers, by contrast, inherited a *vacuous-truth* convention (`NumericInterval.Contains(⊥) => true`, `:127`) — sound for the non-relational containment it was built for, but an over-prove vector once a relation can *make* the interval empty. The amendment's contribution is to reconcile the two: the contradiction must be observed and rejected at the fold, because the downstream Contains-true reader cannot distinguish "empty because contradictory" from "empty because trivially-true." That reconciliation has no off-the-shelf comparator (it arises from Precept's discharge-reader semantics) and is defended as warranted: it is the minimal change that re-imposes the universal ⊥-is-infeasible rule on a reader that locally violates it.

## Decisions

### Decision 1: Treat an empty relational narrowing (`⟦X⟧₀ ⊓ half-line = ∅`, on either the interval or the sign fold) as a proven contradiction — suppress the discharge contribution AND reject — rather than admitting the empty/contradictory narrowing as a vacuous "proved safe"

**Stakes**: high (the load-bearing soundness fix — the wrong call either leaves the over-prove open, a Principle-1 breach, or rejects a satisfiable precept, a Principle-11 breach).

- **Rationale**: The empty intersection is a *proof* the relation cannot hold given `X`'s declared bounds (S2) — the octagon/DBM "empty zone = unsatisfiable" signal (survey:84). The discharge readers inherited a vacuous-truth convention (`Contains(⊥) => true`, `NumericInterval.cs:127`; and an empty `[10,5]` passing the Min/Max bound checks in `TryIntervalContainmentProofNarrowed`) that is sound for non-relational containment but becomes an over-prove vector once a *relation* can drive the interval empty. The fix is to detect the emptiness where it arises (the fold) and (a) withhold the empty contribution from the discharge so the dependent obligation is judged on its real proof state, and (b) surface the contradiction as a rejection. Detecting on the discharge path — not by feeding the relational interval to the satisfiability scans — is what preserves Decision 4: the empty case is a *proven contradiction* (reject-correct), categorically distinct from the *non-empty tighter* case Decision 4 protected (which must not trigger a rejection and is wholly unaffected because the guard tests only emptiness).
- **Tradeoff accepted**: The guard catches only the *single-relation, one-hop, declared-bounds* contradiction — a contradiction that needs transitive closure (`X >= Y`, `Y >= Z`, `Z`-bounds making `X` impossible) is NOT detected (the depth-1 envelope, inherited from core Decision 4 / §0.4). Accepted: that is a *missed* contradiction (false negative on detection) which degrades to the dependent obligation staying Unresolved → the fault-prone op rejects anyway (sound — no over-prove, only less-precise attribution), never a false positive. The author cost is only that a transitive contradiction surfaces as "divisor unprovable" rather than "rule contradicts bounds" — a worse message, not an unsound outcome.
- **Alternatives considered**:
  - *(Feed the relational narrowing into the satisfiability scans so the existing UnsatisfiableRule/ContradictoryRule machinery catches it)* — rejected: this is precisely the hazard Decision 4 isolated. The satisfiability scans read the bare `ExtractFieldInterval`; routing the relational interval there would make a *non-empty tighter* relation flag a *satisfiable* guard/rule as `VacuousRule`/`ContradictoryRule`/`UnsatisfiableGuard` — a false rejection of a valid precept (Principle 11). The over-prove and the contradiction must be handled WITHOUT widening the scans' inputs.
  - *(Extend `ExtractGuardConstraints` to emit a constraint for `field op field`, so the self-unsat pre-pass `ComposeRulePredicateWithFieldBounds` catches `rule X >= Y` against `X`'s bounds)* — rejected as the *primary* mechanism: `ExtractGuardConstraints`/`GuardConstraint` carries a `decimal? Value` (a field-op-*constant* shape, `ProofEngine.cs:31-39`); a `field op field` relation has no constant, so representing it there is the nullable-shape-papering CLAUDE.md forbids, and feeding it to the *satisfiability* scans (`Satisfiability.cs:431`) re-opens the Decision-4 false-rejection hazard for the non-empty case. The contradiction belongs on the discharge path where the relational fact already lives. (A future, separate enhancement *could* surface relational contradictions in the satisfiability scan — but only with the same emptiness-only discipline, and that is not this amendment.)
  - *(Leave the over-prove and rely on runtime governance)* — rejected: governance enforces declared constraints on *external input*, but `X` here holds its *valid default 0* — governance does not fire, and the `100/0` is an internal computation, not an ingress check. §0.7 is explicit: fault prevention is "established entirely at compile time … no deferral." A runtime check is exactly the "second line of defense" `philosophy.md:55` forbids.
- **Precedent**: External — the octagon/DBM negative-cycle = empty-zone = unsatisfiable rule (survey:84); a relational domain reports infeasibility on an empty zone, never admits every goal. In-tree — the satisfiability self-unsat pre-pass already treats an empty composed interval as a rejection (`Satisfiability.cs:292-302`: `if (!interval.IsEmpty) continue; … emit UnsatisfiableRule`) — this amendment applies the *same* "empty interval ⇒ contradiction" judgment to the relational fold, on the discharge side. `NumericInterval.IsEmpty` (`:11`) is the existing emptiness primitive both use.
- **Sources consulted for this decision**: `src/Precept/Pipeline/ProofEngine.Intervals.cs:628-640` (the interval fold, no emptiness check), `:489-512` (the containment reader that discharges on the empty interval), `:11`/`:125-128`/`:143-150` of `NumericInterval.cs` (`IsEmpty`, `Contains(⊥)=>true`, `Intersect` returns Empty); `src/Precept/Pipeline/ProofEngine.Composition.cs:479-489` (the sign fold, no consistency check), `:521+` (`TryRelationalSignForField`); `src/Precept/Pipeline/ProofEngine.Satisfiability.cs:292-302` (the existing empty-interval ⇒ UnsatisfiableRule judgment, the in-tree precedent), `:431`/`:857-969` of `Strategies.cs` (`ExtractGuardConstraints` is field-op-constant only — why the relational case is invisible to the scans); `research/architecture/compiler/relational-constraint-representation-survey.md:84,86`. Grepped the spec: §0.6 item 2 (relational reasoning) + item 7 (contradictory-rule detection) make this a *language-level commitment*; §0.1 Principle 10/11 and proof-philosophy 1 (soundness over completeness) make rejecting a proven contradiction mandatory, not optional. So this is implementation against locked spec (the contradiction class is named); the open question the probe surfaced is the *mechanism* (discharge-path detection), not whether to reject.
- **Strongest counter-evidence**: The core design's Decision 4 asserts "the satisfiability isolation guarantees no new false rejection either" and frames isolation as *sufficient* for soundness; its § Breaking changes claims the value-discharge side is "strictly additive … never over-prove in either direction." A locked sibling design says the soundness is already complete. Response: that completeness claim is falsified by the `Compiler.Compile` probe (CONTRA → zero diagnostics; INTERVAL-ONLY → zero diagnostics) and by source (the folds at `Intervals.cs:628-640` / `Composition.cs:479-489` have no consistency check; `Contains(⊥)=>true` makes the empty result discharge). Decision 4's *intent* (no false rejection from the scans) is preserved here; its *completeness* claim is the one this amendment corrects, on the discharge side it didn't cover. Looked in the core design's Decision 4, § Breaking changes, § Falsifiers, the two folds, the containment reader, and ran the probe; source and probe agree the guard is absent.
- **Reversibility**: Easy — the consistency check is a localized `IsEmpty` test in two folds plus one reader guard; `private` to `ProofEngine`, pre-release, no external consumer. Removing it restores today's (unsound) behavior.
- **Blast radius**: `ProofEngine.Intervals.cs` (interval fold + containment reader), `ProofEngine.Composition.cs` (sign fold). No catalog change, no DTO change. Samples: any sample currently leaning on a relational-contradiction over-prove newly-reds (expected soundness tax; corpus-triaged). The legitimately-safe non-empty case is untouched. One proof-engine stage doc; the core design's Decision-4 completeness-claim correction (promote-stage).

### Decision 2: Detect the empty narrowing on the DISCHARGE path and surface it as an Error-severity contradiction diagnostic; do NOT route the relational interval through the satisfiability scans

**Stakes**: medium (the seam placement + diagnostic choice; the soundness is fenced by Decision 1, this fixes *where* and *which code*).

- **Rationale**: The emptiness is computed inside the discharge-time folds (`BuildNarrowedIntervals` for intervals, `ResolveNumericSubjectSignSet` for signs) — both already have `⟦X⟧₀`, the half-line, and the `Intersect` result in hand. Observing `IsEmpty` there is a one-line test at the point of computation, and keeps the relational interval *out of* the satisfiability scans' bare-`ExtractFieldInterval` reads (Decision 4 preserved). The contradiction is then surfaced as an **Error** because §0.7 requires fault prevention to *reject* (not warn) — a contradiction that makes a fault-prone op's safety unprovable cannot be a recoverable Warning if the op would otherwise over-prove. The diagnostic names the rule and the field (inspectability, §0.6 item 6). Reusing the existing contradiction vocabulary — PRE0159 `UnsatisfiableRule` (the rule cannot hold given the field's bounds) is the closest semantic match — keeps the author-facing model uniform, but PRE0159 is currently a *Warning* and currently *blind to field-op-field* (it fires from the self-unsat pre-pass which `ExtractGuardConstraints` can't feed for relations). The clean resolution: the *discharge-path* contradiction emits an Error that attributes to the rule; whether that Error reuses an escalated PRE0159 or an existing fault-prone-op Error (DivisionByZero/AssignmentRange) depends on the convergence call in Decision 3.
- **Tradeoff accepted**: Detecting on the discharge path means the contradiction is found per-obligation (where the narrowing is built) rather than once globally in a dedicated scan — a bounded recompute (the corpus compiles ~44ms; project memory: compiler is fast). Accepted over the alternative (a global relational-contradiction scan) because a global scan that reads relational facts would be a new structure adjacent to the satisfiability scans, risking the Decision-4 hazard if it ever shared their interval reads; the discharge-path placement reuses the fold that already exists and is structurally isolated from the scans.
- **Alternatives considered**:
  - *(Emit the contradiction from a new global scan, parallel to `ScanRules`)* — rejected: a new scan reading relational facts sits next to the satisfiability scans and invites the exact interval-sharing that Decision 4 forbids; the discharge-path fold already computes the emptiness, so a separate scan is duplication with a soundness footgun.
  - *(Emit only the suppression — no diagnostic — and let the dependent fault-prone op reject with its own DivisionByZero/AssignmentRange)* — rejected as the *sole* behavior: it closes the over-prove (sound) but the author gets "divisor unprovable" pointing at `100/X`, not "your rule contradicts X's bounds" pointing at the rule — a worse diagnostic that hides the real cause (§0.6 item 6 attribution). The suppression is necessary; the attributed contradiction diagnostic is the quality bar on top. (If Decision 3 converges on the fault-prone-op Error as the *primary* signal, the contradiction attribution becomes a related-diagnostic enrichment, not a separate code.)
- **Precedent**: In-tree — `Satisfiability.cs:292-302` emits `UnsatisfiableRule` on an empty composed interval (the same emptiness judgment, on the magnitude side); `DiagnosticCode.cs:401` `UnsatisfiableRule` is the existing "rule cannot hold given the field's bounds" code. The discharge-path strategies already classify outcomes as proved-dangerous / proved-safe / unresolved (§0.6 proof philosophy 5) — a contradiction is "proved dangerous." External — octagon/DBM reports the negative cycle (the contradiction) as the diagnostic, attributing to the constraint set, not to a downstream consumer (survey:84).
- **Sources consulted for this decision**: `src/Precept/Pipeline/ProofEngine.Satisfiability.cs:292-302` (the empty ⇒ UnsatisfiableRule emit; the precedent), `:420-433` (`ComposeRulePredicateWithFieldBounds` — why it can't see field-op-field); `src/Precept/Language/DiagnosticCode.cs:392-401` (PRE0159 semantics + "Warning" severity); `src/Precept/Language/Diagnostics.cs:814` (`Severity.Warning`); `src/Precept/Pipeline/ProofEngine.Intervals.cs:498-512` (`BuildNarrowedIntervals` / containment reader — the discharge-path fold to instrument); `docs/language/precept-language-spec.md §0.6` items 7/8 (contradictory/vacuous-rule), §0.7 (no deferral, reject not warn). Grepped the spec: §0.6 item 7 names contradictory-rule detection but lists items 7/8/9/10 as **Specification-only / Phase 5** (`precept-language-spec.md:241-245`) — so the *magnitude* contradiction scan being a Warning is consistent with item 7 not yet being a hard error; the *fault-prevention* obligation (§0.7, item 3 divisor safety, IMPLEMENTED) is the one that mandates an Error when the contradiction makes a fault-prone op unprovable. This severity tension is the crux of Decision 3.
- **Strongest counter-evidence**: PRE0159 is deliberately a Warning ("recoverable … compilation continues", `DiagnosticCode.cs:398`) — escalating it to Error for the relational case would make the *same diagnostic code* carry two severities, which is a catalog smell. Response: the relational contradiction's Error-ness comes not from the rule being unsatisfiable per se (that *is* recoverable as a warning) but from a *fault-prone op depending on the contradicted field* — the Error is the fault-prone-op obligation's, not PRE0159's. So the convergence (Decision 3) likely keeps PRE0159 a Warning *and* lets the dependent op reject at Error, rather than re-severitying PRE0159. Looked in `DiagnosticCode.cs`, `Diagnostics.cs`, §0.6 implementation-status table, and §0.7; the severity model is consistent if the Error is sourced from the fault-prevention obligation, not the contradiction-detection diagnostic.

### Decision 3: Converge the relational and magnitude contradiction paths on the SAME observable outcome — the dependent fault-prone operation REJECTS at Error severity — and file the verified magnitude-path over-prove (Warning-only, divisor still discharges) as a sibling soundness bug

**Stakes**: medium (a convergence + scope-boundary call; reversible, no public-surface lock-in beyond the diagnostic choice fenced by Decision 2).

- **Rationale**: The probe established that the magnitude path is NOT the clean control the brief assumed: `rule X >= 10` with `X max 5` and `100/X` emits ONLY `UnsatisfiableRule` (Warning), `HasErrors=False`, and the divisor over-proves (no `DivisionByZero` Error) — the precept *builds* and `100/0` faults. So today the magnitude and relational paths *already converge* — on the WRONG outcome (both over-prove the fault-prone op; magnitude merely also warns). The correct convergence target is: in BOTH cases, a fault-prone op whose only safety source is a field contradicted by a rule must **reject at Error** (§0.7 fault prevention — no deferral). For the *relational* path, this amendment (Decisions 1-2) delivers that directly. For the *magnitude* path, the root is the same class of defect — an unsatisfiable rule's bound still folding as a discharge fact (`CollectTrustedNumericFacts` does not block a self-unsatisfiable rule's `ScopedNumericFact`) — but its fix lives on the magnitude fact-collection side, not the relational fold, so it is filed as a sibling bug (BUG-NNN) and fixed under the same principle (a self-unsatisfiable rule contributes NO discharge fact), with the relational amendment as the precedent. Convergence is on the *outcome* (both reject at Error), achieved by two co-principled fixes; this amendment ships the relational half and names the magnitude half.
- **Tradeoff accepted**: This amendment does NOT fix the magnitude over-prove (it scopes to the relational fold). Accepted: the magnitude fix touches `CollectTrustedNumericFacts` / the `ScopedNumericFact` collection (a different surface), and bundling it would widen the slice past the relational defect the adversarial review surfaced; filing it as a sibling bug with the shared principle keeps each fix reviewable and lets the corpus soundness-tax be measured per-fix. The cost is that the magnitude over-prove persists until its bug is fixed — flagged loudly to the orchestrator as a pre-existing hole this work *uncovered*, not introduced.
- **Alternatives considered**:
  - *(Make the relational path emit a Warning to match today's magnitude behavior)* — rejected: that would converge on the *unsound* outcome (a building precept that faults). §0.7 mandates rejection, not a warning, for a fault-prone op that cannot be proved safe. The convergence target is the sound one (Error reject), and the magnitude path must rise to it, not the relational path fall to the magnitude path's hole.
  - *(Fix both magnitude and relational in this slice)* — rejected for *this amendment's* scope (the adversarial review surfaced the relational fold; the magnitude `ScopedNumericFact`-from-unsat-rule is a distinct surface) — but explicitly flagged so the orchestrator can choose to fold it in. This is a scope call, not a soundness call: both fixes share the principle "a self-unsatisfiable rule contributes no discharge fact."
  - *(Treat the magnitude Warning as acceptable / by-design)* — rejected: a building precept that faults at runtime is a Principle-1/11 breach regardless of an accompanying warning; "warns but builds" is not "rejects." Calling it acceptable would be redefining the bar.
- **Precedent**: In-tree — BUG-023 (guarded magnitude/sign rule leaks as unconditional fact) and the new relational arm were recognized as the *same* asymmetry closed by one filter; this is the analogous recognition that the *self-unsatisfiable* magnitude rule and the *self-contradictory* relational rule are the same "a rule that cannot hold must not contribute a discharge fact" principle. The `Satisfiability.cs:292-302` empty-interval judgment is the shared emptiness primitive. External — a verification engine reports infeasibility uniformly whether the contradiction is between a variable and a constant or between two variables (the DBM does not distinguish; survey:84).
- **Sources consulted for this decision**: the MAGNITUDE / NO-RULE / CONTRA / INTERVAL-ONLY probe results (2026-06-04, throwaway, deleted — recorded verbatim in frontmatter `sources-consulted`); `src/Precept/Language/Diagnostics.cs:814` (`UnsatisfiableRule` = Warning); `src/Precept/Compiler.cs:40` (`HasErrors` = any Error) + `src/Precept/Runtime/Precept.cs:37` (Build refuses only on HasErrors — so Warning-only builds); `src/Precept/Pipeline/ProofEngine.Composition.cs:116-149` (`CollectBlockedConstraints` / `CollectTrustedNumericFacts` — blocks a rule whose *obligation* is Unresolved, but a self-unsatisfiable rule's obligation is not necessarily Unresolved, so its `ScopedNumericFact` is not blocked — the magnitude root); `docs/language/precept-language-spec.md §0.7` (no deferral, reject); `docs/Working/bugs.md:30-44` (BUG-023, the same-asymmetry precedent). Grepped the spec §0.6 items 7/8 implementation-status (Specification-only, Phase 5) — confirming the *contradiction-detection diagnostic* is not yet a hard requirement, while §0.7 *fault prevention* (implemented) is — which is why the convergence is on the fault-prone-op Error, not on the contradiction diagnostic's severity.

## Falsifiers

- **Never-over-prove (Principle-1 falsifier, load-bearing).** If the BUG-024 repro (`rule X >= Y`, `X max 5`, `Y min 10`, `100/X`) compiles with `HasErrors=False` after this amendment, the guard did not close the over-prove — immediate redesign. Likewise the interval-only channel (`rule X <= Y`, `X min 10`, `Y max 5`, `Q min 0 max 3 <- X`) must reject.
- **False-rejection regression (Principle-11 falsifier, the Decision-4 guarantee).** If any precept that compiled clean before — with a *non-empty* relational narrowing — now rejects (the legitimately-safe reorder demonstrator `rule OnHand > Reserved`, both `nonnegative`, must STILL compile clean and discharge), the emptiness test is firing on a non-empty interval — immediate redesign.
- **Satisfiability interference.** If, after this amendment, any precept emits `VacuousRule`/`ContradictoryRule`/`UnsatisfiableGuard`/etc. *because* a relational rule's interval reached a satisfiability scan, the contradiction detection leaked into the scans (it must not — it lives only in the discharge folds). The Decision-4 adversarial byte-identity fixture is the standing guard.
- **Empty-as-true leak at the reader.** If `TryIntervalContainmentProofNarrowed` ever discharges (returns true) on an empty `resultInterval`, the `Contains(⊥)=>true` over-prove vector is still open at the reader — the reader-side guard is missing.
- **Magnitude convergence.** If, after the sibling magnitude bug is fixed, `rule X >= 10` (`X max 5`, `100/X`) still builds with `HasErrors=False`, the magnitude path did not converge on the Error-reject outcome — the convergence (Decision 3) failed.
- **Attribution drift.** If the relational contradiction rejects but the diagnostic points only at the downstream `100/X` (not at the contradicting rule + field), the inspectability obligation (§0.6 item 6) is unmet — the witness names the wrong cause.
