# Shared-core numeric-model treatment — design evaluation

## 1. The question

The shared-expression-evaluation-core design (`shared-expression-evaluation-core-2026-07-06.md`) unifies the compile-time proof fold and the future runtime evaluator behind one catalog-attached value-executor so that "a definition's proved-against value and its runtime-computed value are the same by construction" (design `:26`). Its **Decision 3** goes further and pins the numeric model concretely:

> "**Decision 3: Number-model pin — the shared core fixes one `decimal`-based value representation** … The shared core, by being one function, makes the fold's and the runtime's numeric representation *the same object*, not two independently-chosen `decimal`s that could later diverge" (design `:169`, `:173`).

The question this evaluation answers, neutrally: **is pinning `decimal` the right treatment for this design, or should it be something else?** Four options were on the table — (A) pin decimal now; (B) pin only "one shared model" and defer the concrete choice to the parked number-model decision (readiness plan D1); (C) pin decimal-for-exact-ops plus a defined scheme for what decimal can't do exactly (sqrt/trig/log); (D) pin float/IEEE-754. The design's one hard requirement is soundness: **the fold must compute the same value the runtime will** — that is the whole point of one core.

## 2. The independent verdict

**Option B, in a refined form — decisively over C and D, and by a narrower (decision-hygiene, not correctness) margin over A.**

Where the evidence is decisive:

- **C and D are rejected on verified facts, not preference.** The fold computes no value that `decimal` cannot compute exactly. `FoldValue` (`ProofEngine.Analysis.cs:249-345`) has cases for literal, field-ref, binary, unary, conditional, postfix, and interpolated — and a `default → UnknownSentinel` (`:342-343`). There is **no function-call case** in the value fold, so `sqrt`/`pow` fold to unknown. `EvaluateBinaryOp` (`:351-405`) normalizes operands with `left switch { decimal d => d, int i => i, long l => l, _ => null }` (`:360-361`) — a `double` falls through to `null` and the whole numeric branch returns `UnknownSentinel`. So the fold makes **zero IEEE-754 prediction and zero transcendental prediction**. Option C settles a scheme for operations the shared core never performs (scope creep); Option D repoints the exact lane at `double`, breaking `0.1 + 0.2 == 0.3` for money/counts and reintroducing exactly the floating-point drift the grounding survey names as the unsound pole (survey `:82`, the C++ `[expr.const]` FP carve-out; survey `:120`, GCC "must emulate the target's arithmetic"). D is the most build cost for the worst soundness.

- **The soundness invariant is "one shared model," not "the model is `decimal`."** `fold(e) = runtime(e)` requires that both phases dispatch through **one** evaluation implementation over **one** numeric model — whatever that model is. That property is already secured by **Decisions 1 and 2** (one function ⇒ one rounding ⇒ one overflow boundary), not by a separate `decimal` word. Decision 3's stated worry — "two independently-chosen `decimal`s that could later diverge" (design `:173`) — is answered by 1 and 2: two kernels can diverge; one kernel cannot, whatever its type. The only content Decision 3 adds beyond 1 and 2 is the concrete word `decimal`, and that word is **inherited** from locked canon, not decided here.

Where the evidence honestly splits (A vs B):

- **Option A (pin decimal as written) is NOT unsound.** With `decimal` as the model today, `fold == runtime` holds; the kernel is written over `System.Decimal` either way; and Decision 3 already discloses its dependency on the parked number-model decision via its own Falsifier 1. A reasonable owner could ship A as-is. The case against A is therefore **decision-hygiene, not correctness**: A restates a fact that is already settled elsewhere, and it couples this design's stated validity to a decision (D1) that is deliberately parked to stay off other work's critical path (readiness plan `:194`, "the only fault-floor item gated on an undecided number model").

- **Option B is strictly cleaner and costs zero build effort.** It asserts exactly the design's own soundness content — one shared model — and no more; it keeps `decimal` as the concrete build target (so buildability is untouched — A and B compile the same bytes); and it removes the latent landmine whereby resolving a parked decision falsifies a locked, possibly-already-built design.

The refinement (folding the three judges' best corrections):

1. **Bind, don't decouple.** Pin one shared model as a **binding constraint on the parked D1**: D1 may later re-pick the numeric representation, but it must re-pick it for **both phases atomically**. (One candidate framed B as "decouple the design's validity from D1"; on the soundness lens that is loose — decoupling risks removing the very constraint that keeps the two phases on one model. Decouple the design's *validity* from D1's *type choice*; keep the two phases' *models* bound.)
2. **Pin semantics, inherit representation.** What is locked is base-10-**exact semantics** (`0.1 + 0.2 == 0.3` is true; primitive-types.md `:390`); what D1 parks is `System.Decimal`'s concrete **representation** (its ~7.9e28 range; the parked fix is "arbitrary-precision numerics," readiness plan `:165`). Pin the semantics; record `System.Decimal` as today's realization; route representation-permanence to D1.
3. **Exactness is not the bar — sameness is.** `System.Decimal` division *rounds* (`dl.Value / dr.Value`, `:370`; 1m/3m → 28–29 digits, not mathematically exact), yet `fold == runtime` still holds because both phases call the identical deterministic operator. The design's Principle-8 row justifies the pin as "keeps the exact lane exact" (design `:47`) — that subtly conflates *exactness* with *sameness*, and it is the conflation that makes the concrete `decimal` pin *look* load-bearing when Decisions 1 and 2 already secure the sameness the guarantee needs.
4. **Scope the pin beyond numeric.** `fold == runtime` also depends on shared **string-comparison** semantics — the fold uses `string.Equals(sl, sr, StringComparison.Ordinal)` (`:387`) — and shared boolean semantics. A runtime that honored the `decimal` pin could still pick culture-sensitive string comparison and break equivalence on string equality. "One shared model" must mean one evaluation model spanning numeric representation, string-comparison (Ordinal), and boolean semantics.

## 3. The transcendental reality (verified) and how much it bears

Three checkable facts, each verified against source or flagged for external confidence:

- **(a) IEEE-754 does not require correctly-rounded transcendentals.** IEEE-754 mandates correct rounding for `+ − × ÷` and `sqrt`, but only *recommends* it for `sin`/`cos`/`exp`/`log`/`pow`; the "table maker's dilemma" means implementations vary across platforms and libm versions, producing genuine cross-platform last-ULP drift. *External fact — high confidence (standard IEEE-754 knowledge).*
- **(b) .NET `System.Decimal` has no transcendentals.** `System.Math.Sqrt` takes and returns `double`; there is no `Decimal.Sqrt`/`Sin`/`Log` in the BCL. The spec itself records this: "`sqrt` is `number`-lane only — `.NET Math.Sqrt` has no `decimal` overload" (primitive-types.md `:697`). *High confidence.*
- **(c) Precept barely uses transcendentals, and the fold uses none.** `FunctionKind.cs` lists only `Pow = 11` and `Sqrt = 12` among power/root functions — **no** trig/log/exp entries. `sqrt` is typed `(number) → number` (Functions.cs `:200-206`, input `PSqrtNumber = new(TypeKind.Number …)`) and is **number-lane-only** — "`sqrt(decimal)` is a type error — use `sqrt(approximate(value))`" (primitive-types.md `:613`); it never touches `decimal`. `pow` always takes an **integer** exponent (`PPowIntExp = new(TypeKind.Integer, "exp")`, Functions.cs `:32`), with overloads `(integer,integer)→integer`, `(decimal,integer)→decimal` (Functions.cs `:192` — this decimal-base overload exists and is exact via repeated multiplication), and `(number,integer)→number`. So `pow` is not a transcendental. `log`/`sin`/`cos`/`exp` do not exist yet — "Future functions (`log`, `sin`, `cos`, `exp`) will also be number-lane-only" (primitive-types.md `:284`).

**How much it bears: almost nothing, for this design.** The transcendental question is already answered by the **type system**, not the number model — every inexact operation is fenced into the IEEE-754 `number` lane, which is "Approximate by design" (primitive-types.md `:83`), and the fold never folds a `number`-lane value. Cross-platform `double` drift is therefore a *runtime* determinism/honesty concern (Principle 3 / Principle 8), not a *shared-core fold-vs-runtime* concern. This is the decisive reason **Option C is rejected**: the shared core owes no transcendental scheme because its fold-vs-runtime divergence surface for transcendentals is empty. (A future decision that makes the runtime actually *fold* functions would reopen this — see §8.)

## 4. Does pinning a specific model prejudge the parked D1?

**Yes — mildly, and demonstrably — as Decision 3 is currently written; and the prejudgment is avoidable at zero soundness cost.**

The parked thing is specific. Readiness plan D1 parks "The number-model redesign. The number model is the choice of how Precept represents numeric values; redesigning it (for example, moving to arbitrary-precision numerics) is the unmade decision the representability-overflow build was gated on" (readiness plan `:165`), and "the number-model redesign that prevention would depend on is itself parked … arbitrary-precision numerics — that is a number-model redesign, and the redesign is parked" (`:194`). So the parked variable is the runtime's numeric **representation** and any migration of it — not base-10 semantics.

Decision 3 reaches into that. It pins the runtime's model to `decimal` and calls it "structural" (design `:169`, `:184` "a later non-`decimal` runtime representation would force re-deriving fold↔runtime equivalence"). Its defense — "the `decimal` *choice itself is already settled* … not a fresh number-model choice" (design `:180`) — is **half-true**: `proof-engine.md:110` settles `decimal` for the **fold**, and even there only in a narrow scope — the `:110` note is explicitly "When proof obligations depend on UCUM quantity normalization or interval scaling." The general fold-decimal claim lives in §7.7 ("numeric operands (`decimal`, `int`, `long`) are normalized to decimals," proof-engine.md near `:1882`), and the *runtime's* decimal is a stub-design choice (`evaluator.md` `PreceptValue` payload) that D1 explicitly parks. Extending the fold's settled-decimal to the runtime and calling it "structural" is the reach.

The tell is Decision 3's own **Falsifier 1**: "If the runtime executable-model design fixes a non-`decimal` numeric representation … Decision 3 is falsified and the fold↔runtime equivalence must be re-derived — likely reopening the CompCert/WASM differential fallback" (design `:207`). That is a locked design declaring itself **falsifiable by a parked decision** — resolving D1 (if it picks non-decimal) retroactively invalidates this design. And it is spurious: if D1 later redesigns the model and the redesign lands *inside the shared core* (which Decisions 1 and 2 force both phases to adopt), `fold ≡ runtime` is preserved by construction — only the incidental `decimal` label changes. The design's actual soundness goal survives any D1 outcome; only Falsifier 1's over-broad wording does not.

## 5. Four-leg rationale for the recommended treatment (Option B, refined)

**Recommendation:** Reword Decision 3 to pin *one shared evaluation model* (binding on D1, spanning numeric + string + boolean semantics), record `System.Decimal` base-10 semantics as today's realization, and reword Falsifier 1 to fire on *different models*, not on a type change. Keep `decimal` as the build target.

- **Rationale.** The design's sole hard requirement is `fold(e) = runtime(e)`, and that is a *sameness* property, not an *exactness* or a *specific-type* property. Decisions 1 and 2 already deliver sameness structurally. Stating the invariant as "one shared model" asserts exactly that and nothing more; stating it as "pin `decimal`, structural" asserts that plus a commitment to a representation that D1 owns and parks. Pinning the smaller, true thing is the honest scope.
- **Alternatives considered and rejected.**
  - *Option A (pin `decimal` as written)* — not unsound, and shippable, but restates an inherited fact and couples the design's stated validity to a deliberately-parked decision, creating the "resolving-D1-falsifies-a-locked-design" landmine. Rejected as the *worse-hygiene* of two correct options, not as incorrect.
  - *Option C (settle a transcendental scheme now)* — solves a problem the shared core does not have: the fold folds no functions and no `number`-lane value, so the transcendental divergence surface is empty (§3). Rejected as scope creep against a locked type-system answer.
  - *Option D (pin float/IEEE-754)* — discards the locked exact lane, breaks `0.1 + 0.2 == 0.3`, and reintroduces the FP drift the survey identifies as the unsound pole. Rejected as actively unsound for the exact lane.
  - *B-as-"decouple from D1"* — the soundness-loose reading; rejected in favor of B-as-"binding on D1," which keeps the two phases' models bound while freeing the design's validity from D1's concrete type choice.
- **Precedent.** Rust shares one MIR interpreter between CTFE and Miri so "a fold-vs-runtime mismatch is structurally unrepresentable" (survey `:105-110`, cited in design `:105`) — the guarantee rides on *sharing one implementation*, not on *which numeric type* it uses. C++ `constexpr` mandates equivalence but carves out FP as "unspecified" (survey `:82`) — the one place it abandons sharing is exactly the non-exact-numeric operand class Precept keeps out of the fold. Both precedents locate the guarantee in the sharing, not the type — supporting a pin on "one model" over a pin on "`decimal`."
- **Tradeoff accepted.** "One shared model" is a weaker-sounding claim than "`decimal`, structural" and defers the concrete-representation permanence to a decision (D1) that has no scheduled resolution — so a reader who wants the design to *state* the numeric type must follow the "decimal today" annotation rather than read it as locked-forever. Accepted because the alternative (stating it as locked-forever) is not true — D1 can still move it — and asserting more than is true is the exact over-reach this refinement removes. Second, minor: the reword is documentation churn on an already-locked design, against an owner who has flagged fatigue with doc/plan meta-loops — accepted because the change is a surgical two-clause edit to Decision 3 and Falsifier 1, not a re-open of the design.

## 6. What this means for Design 1's Decision 3

**Loosen it — surgically. Do not reject the design; do not settle a transcendental scheme; do not touch Decisions 1, 2, or 4 (they are sound).** Concretely:

- **Decision 3 headline/rationale:** change "the shared core fixes one `decimal`-based value representation" to "the shared core binds the fold and the runtime to **one** evaluation model — one numeric representation, one string-comparison semantics (Ordinal), one boolean semantics. That model is `System.Decimal` base-10 today; the parked number-model decision (readiness plan D1) owns whether the numeric representation stays `decimal`, and if it changes it must change for both phases atomically." Keep the `decimal`-today realization citation, but cite proof-engine.md §7.7 (the general fold-normalization claim) for the blanket statement rather than `:110` (which is UCUM/interval-scoped).
- **Falsifier 1:** reword to fire on the real hazard — "if the fold and the runtime end up on **different** numeric models" — not on "the runtime fixes a non-`decimal` representation." A synchronized non-`decimal` migration inside the shared core is *not* a falsifier; a divergence between the two phases is.
- **Principle-8 row (design `:47`):** correct "pinning `decimal` … keeps the exact lane exact" to "one shared model keeps the fold's proved value and the runtime's computed value the **same** value; the exact lane's base-10 semantics are preserved" — removing the exactness/sameness conflation.
- **Inventory / Decision 2 scope note (see §7 red-team):** state whether the shared core extracts *all* fold value-arithmetic or only `EvaluateBinaryOp`. If only the latter, the "one model" guarantee does not yet cover the affine unit-conversion arithmetic the fold performs inline (`(mag + offset) * scale`, `:314-315` and `:332-333`) — that out-of-core decimal arithmetic must be either pulled into the shared core or explicitly named as covered by the binding.

**Buildability is unaffected either way** — the kernel is written over `System.Decimal` today under A or B; the change is doc-honesty, not a build-target change. Every acceptance criterion (design `:214`) remains verifiable with the runtime stubbed.

## 7. Red-team — what would change this conclusion

- **If the owner intends `decimal` as the permanent answer and treats D1 as "parked in build, decided in direction."** Then A-as-written costs nothing, Falsifier 1's coupling is to a decision that will resolve to `decimal` anyway, and the reword is pure churn on a locked doc — against a documented owner preference to stop doc meta-loops. In that world the honest call is **leave Decision 3 as-is** and record here that the pin is safe because D1's direction (not just its build) is settled toward decimal. *This is the strongest case for A, and it turns entirely on a fact only the owner holds — whether D1's* representation *direction is actually open or only its* build *is.*
- **If the shared core is scoped to extract all fold arithmetic (including affine conversions and interpolation magnitude math).** Then the out-of-core hole (§6 last bullet) closes and the numeric-only framing is complete; the string/boolean-scope point remains, but the "one model has holes" rider dissolves. If the core extracts only `EvaluateBinaryOp` (as the design's Inventory currently reads — it names `EvaluateBinaryOp` and "the inline unary arithmetic," design `:118`/`:216`, not the interpolation/affine arithmetic), the rider stands and is load-bearing.
- **If string/boolean sharing is considered self-evidently required and not worth stating.** Then §2 point 4 is pedantic. But P11 soundness on string equality genuinely depends on the runtime picking `StringComparison.Ordinal` (`:387`), and "one model" that silently means "one *numeric* model" is exactly the kind of under-scoping that lets a later runtime author pick a culture-sensitive comparison in good faith. The point is cheap to state and closes a real hole.
- **If a future runtime is designed to fold functions (evaluate `sqrt`/`pow` at compile time into proved values).** Then the transcendental question stops being moot and Option C's concern becomes live — but for a *different* design, not this one. This conclusion (C rejected) is scoped to the shared core as it exists: a fold that folds no functions.

Nothing in the verified evidence supports C or D under any of these branches. The live disagreement is only A vs B, and it collapses to a single owner-held fact: **is D1's numeric-representation *direction* open, or only its *build*?**

## 8. What this did NOT settle

- **It did not settle D1** — what Precept's number model *should* be (decimal vs arbitrary-precision vs other), or the maxplaces/overflow work gated on it. That stays parked under owner decision D1; this evaluation only says the shared-core design should not *pre-decide* it.
- **It did not settle whether the shared core extracts the fold's out-of-core arithmetic** (affine unit conversions `:314-315`/`:332-333`; interpolation magnitude math). That is Decision 2's scope question, flagged here as a completeness rider, not resolved.
- **It did not re-open Decisions 1, 2, or 4** — the share-one-core architecture, the catalog-executor placement, and the OD-1 reclassification are sound and out of scope for this numeric-model question.
- **It did not settle transcendental handling for a future function-folding runtime** — if the runtime is ever designed to fold `sqrt`/`pow`/`log` into proved values, a fresh decision (and possibly Option C's scheme) is owed *then*.
- **It did not address the Principle-8 overflow carve-out** (D1's "documented known fault, never claimed prevented," readiness plan `:194`) — that philosophy implication is separately owner-gated and unrelated to the fold-vs-runtime sameness question here.

## Orchestrator-leaning check

The orchestrator's prior leaning was "loosen/defer the decimal pin." This independent evaluation **REFINES** that leaning — it confirms the *direction* (loosen Decision 3 from a concrete `decimal` pin to a shared-model pin) but corrects it on three counts, so the owner sees it was not rubber-stamped:

1. **Not "defer/decouple" — "bind."** The correct loosening keeps "one model" as a *binding constraint on D1* (both phases move together), not a decoupling that could let the two phases drift. "Defer the choice to D1" is right for the *concrete type*; "decouple" is wrong for the *sameness constraint*.
2. **Keep `decimal` as the build target and pin the semantics.** The loosening is doc-honesty only — `System.Decimal` stays the realization today; base-10-exact *semantics* are locked; only the *representation-permanence* routes to D1. Buildability is untouched.
3. **Honest about A.** Pinning `decimal` as-written is **not unsound** — it is a decision-hygiene issue, not a correctness bug. If the owner holds that D1's numeric direction (not just its build) is already settled toward decimal, leaving Decision 3 as-is is a defensible call and the reword is avoidable churn.
