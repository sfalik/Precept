# Corpus measurement, classified — fault-family obligations vs. the authored discharge contracts

**Status**: Draft — 2026-07-21. This is the ratification-protocol layer-4 measurement (`docs/Working/obligation-discharge-matrix-2026-07-19.md` § Ratification protocol, item 4) run against the **fault family's** re-authored per-requirement-kind cell files in this folder (`Numeric.cells.json`, `LengthContainment.cells.json`, …). It supersedes nothing — `../corpus-measurement-fault-family.md` (the ledger-tally measurement: minted/proved/unresolved by kind, context, strategy) is a prerequisite this file consumes and does not restate.

**What this file adds over the ledger tally**: the ledger tally says *what HEAD minted and whether HEAD proved it*. This file adds the classification the ratification protocol actually asks for — for every obligation the corpus mints, is the discharge HEAD actually used one the authored contract in this folder **licenses as written**, does it need a **respelling** to become licensed (and what is that respelling), or is there **no licensed respelling** on record for that coordinate. Read `../corpus-measurement-fault-family.md` first; the scoping paragraph there (four load-bearing limits) applies here unchanged and is not repeated in full.

**Hold this measurement to the same standard stated up front, twice, because it is the one most likely to be misread**: agreement with the corpus is **necessary, not sufficient**, and **the corpus is never citable as coverage**. A "licensed" count below is existence-proof-plus-agreement, not a soundness certificate for the family, and a "no licensed respelling" count is a definitional-gap count, not a claim that no safe program can reach that coordinate.

## Method

1. Every fault-family obligation the shipped compiler mints across `samples/*.precept` was read off `Compilation.Proof.Obligations` (`tools/Precept.MatrixTools -- measure-corpus-faults`, unchanged mechanism from the ledger tally). The tool was extended with one additive field, `ContextDetail`, so a `ConstraintContext` obligation records whether it sits in a `rule` condition or an `ensure` condition (and which ensure kind) — the plain `ObligationContext` runtime type collapses both to `ConstraintContext`, which is too coarse to match against the cell files' `evaluationSiteCategory` axis. No existing field was renamed or removed, and no test referenced the old shape (`grep` returned no hits), so this is a pure addition.
2. Every distinct `(RequirementKind, ContextDetail, Strategy)` triple was tallied. This is the same granularity the matrix's own vocabulary uses for cell identity ("two programs sit in the same cell iff their minted obligations unify with the same schema") — instances differing only in field name, literal threshold, or file are the same schema instance and are counted together, not classified one-by-one. 1,045 obligations reduce to 28 distinct triples this way, which is what made a by-hand classification tractable at all.
3. Each triple's `ContextDetail` was mapped to the fault cell files' `evaluationSiteCategory` vocabulary (`transition-row-action-operand`, `rule-condition`, `event-ensure-condition`, …) via the actual mint sites in `src/Precept/Pipeline/ProofEngine.cs` / `ProofEngine.Analysis.cs` (`TransitionRowContext` → transition-row-action-operand, `EventHandlerContext` → stateless-hook-action-operand, `ConstraintContext(RuleIdentity)` → rule-condition, `ConstraintContext(EnsureIdentity{Kind=StateResident})` → state-ensure-condition, `ConstraintContext(EnsureIdentity{Kind=EventPrecondition})` → event-ensure-condition, `FieldExpressionContext` → computed-field-expression, `StateHookContext` → state-hook-action-operand, `FieldDefaultContext` → field-default-value-expression, `ArgDefaultContext` → event-arg-modifier-value-expression).
4. Each triple was looked up against the matching `<Kind>.cells.json` file's cell at that `evaluationSiteCategory` (and, where the file distinguishes it, type family): is the coordinate `defined`, and if so, does its authored `dischargeContract` list the observed strategy among its licensed derivations?
5. Classification:
   - **licensed as written** — the coordinate is defined, and the observed strategy matches a discharge the cell's contract names (or the observed strategy is a compile-time constant fold, which is licensed as a general, definition-wide mechanism regardless of which coordinate the specific literal happened to land at — see the Numeric notes below for the handful of cases where the authored file hadn't caught up to record the trivial sub-case).
   - **respell-needed** — the coordinate's current discharge rests on a mechanism the fault case-shape's own discharge column does not license (the `CompositionalConstraint` strategy, which the matrix's own case-shape table restricts the fault family to premise classes (b)/(c)/(a), not (d) — see Compiler-hole check), or the program as written is genuinely unresolved at HEAD but a licensed respelling exists on the record. Every row in this bucket carries the specific respelling.
   - **no licensed respelling** — the coordinate is `open` in the authored file (no discharge contract has been written for it at all), or the specific strategy HEAD used is not among the coordinate's authored discharges. This bucket is a **definitional-gap** count, explicitly *not* a claim that the program is unsound or that no safe respelling could exist — it means the written contract does not yet answer this coordinate, which is exactly the "no silent cells" property the matrix's own § The cell requires reporting on rather than papering over.
6. **Compiler-hole check** (corrected input, honored before any `GuardInPath`-discharged row counted as licensed): the matrix's own § Rule validity records a verified soundness defect — the shipped `GuardInPath` strategy does not check that no construct on the route between a guard's evaluation and the fault site writes a field the guard depends on (state-exit actions run *before* the row's own action chain, per `precept-language-spec.md` § 3A.4, and can silently invalidate a guard fact the site then wrongly trusts). A second, related hole is `BUG-033` — an action's `into` binding target is a write site nothing registers, so a guard fact about that target can be carried past a write to it undetected. Both holes are **real defects in the shipped engine**, not authoring artifacts, and a clean compile through `GuardInPath` is not by itself evidence the specific obligation is sound.

   This measurement checked corpus exposure directly rather than discounting every `GuardInPath` row on suspicion: only three sample files declare a state-exit hook with an action (`library-hold-request.precept:58`, `restaurant-waitlist.precept:64`, `trafficlight.precept:29` — a `from S -> action` block with no `on`, the structural precondition for the first hole), and every transition row leaving the hooked state in those three files was read directly. None reads the exit-hook-cleared field again in its own action chain after the hook fires, so none of the `GuardInPath`-discharged obligations in this corpus is exposed to that hole **as it stands today**. The `into`-binding hole was checked the same way: every `into` binding in the corpus (`warranty-repair-request.precept:75`, `restaurant-waitlist.precept:52`, `library-hold-request.precept:89,99,137`) was read, and none of the surrounding rows re-reads the `into` target after writing it. **This is a targeted structural check of the corpus as it exists, not a proof that the holes are harmless in general** — both remain live defects the shipped compiler does not build-enforce, and a differently-shaped sample (or a future one) could trigger either. The corpus's own filtering limit applies here with full force: a program built specifically to demonstrate the hole would not survive the "every sample compiles" gate this corpus is drawn from.

## Every distinct (kind, evaluation site, strategy) triple, with its classification and reasoning

The full 28-row table (kind, context detail, strategy, count, mapped evaluation-site category, verdict, reasoning) is committed as data in `corpus-measurement-classification-rows.json` beside this file — that JSON is the artifact a future validator or a landed ruling should sweep against, not this prose. The prose below groups the rows worth reading in full; the JSON has all 28.

### The largest gap this measurement found: 70 `QualifierCompatibility` obligations with no authored coordinate

`ConstraintContext(EnsureIdentity{Kind=EventPrecondition})` — a currency/unit qualifier check inside an `on E ensure` condition — is minted 70 times across the corpus (6.7% of everything this measurement classified), and `QualifierCompatibility.cells.json` has no cell at `event-ensure-condition`. The file authors `transition-row-action-operand`, `state-hook-action-operand`, `stateless-hook-action-operand`, `rule-condition`, `state-ensure-condition`, and `computed-field-expression` — six of the seven positions a qualifier check can occur at — and stops one short of the seventh. The parallel `state-ensure-condition` cell's citation-duty argument (a declared qualifier is immutable, so the preserving-obligation set is provably empty on every route) reads like it would extend to `event-ensure-condition` unchanged, since an event-ensure condition has no residency to reason about at all — but that extension is not written anywhere, and per the matrix's own discipline ("if a cell's answer cannot be derived from the generative sections, that is a missing rule to author here — never a bare answer written into the cell"), this measurement records the gap rather than filling it. This is the single highest-value authoring gap the measurement surfaces: one small addition to `QualifierCompatibility.cells.json` reclassifies 70 obligations.

### The known false-proof hazard, live in the corpus: 6 `Numeric` obligations via `CompositionalConstraint`

`samples/*.precept` contains six divide-by-zero obligations discharged through the `CompositionalConstraint` strategy (`transition-row-action-operand`, primitive and business-domain lanes). The fault family's own case-shape row in the matrix restricts the discharge column to premise classes **(b)/(c)/(a)** — **not (d)**, a business rule holding in the pre-state — and the verified false-proof witness the matrix records under § The cell (`rule PlannedQuantity > 0`, divided by in one handler, set to zero in another, compiles clean, reports `Proved`/`CompositionalConstraint`) is exactly this shape. These six are not licensed as written under the family's own stated discharge column, regardless of what the authored `Numeric.cells.json` file's `(b)` entry happens to name the strategy for its arg-bound case (the same strategy tag is reused by the engine for a materially different, unlicensed premise source — see the tool source, `ProofEngine.Composition.cs`, `TryCompositionalConstraintProof`, which resolves the divisor's own sign set — pulling in whatever rule and modifier facts sign-set resolution finds — before falling back to a whole-file scan of every assignment to the field).

**Respelling** (licensed, per Family 4 in the matrix and the arg-bound contract already authored for the `(b)`-premise transition-row cell): replace the whole-file rule-premise argument with an explicit modifier (`nonzero` or `positive`) on the divisor's own declaration, or an explicit guard `when <divisor> != 0` (or a per-term bound conjunct) in the row that performs the division. Both are licensed (b)/(c) derivations that do not depend on the unproven premise-(d)-via-composition path.

### The corpus's one deliberately-failing case, and its respelling: 2 `IntervalContainment` obligations

Both unresolved obligations in the entire corpus are in `samples/Test2.precept` — the one sample kept deliberately failing. They are the two obligations on `Add1`'s row: `on Add1 when Add1.Amount1 + Add1.Amount2 <= 1000 -> set Total = Add1.Amount1 + Add1.Amount2`. This is Witness Family 1 Base A exactly, and the matrix already records its status: provable under the model via guard normal-form match, but the multi-term guard-match derivation is not built at HEAD. **Respelling** (already licensed and already stated in the matrix's own Base A notes): per-term bound conjuncts discharge through the same interval derivation as arg bounds — `when Add1.Amount1 <= 500 and Add1.Amount2 <= 500` — spelled in the guard instead of on the args. `Add2`'s sibling row in the same file (`Amount1 max 250, Amount2 max 750`, no guard at all) already compiles clean via the arg-bound path, confirming the respelling family is live at HEAD today.

### Coordinates the authored files leave open, exercised anyway: 4 `Numeric` + 1 `IntervalContainment` + 3 `IndexBounds`

- Three single-instance `Numeric` obligations (`DeclarationAttribute` and `CollectionGrowth` strategies, both at `transition-row-action-operand`) use strategies the authored cell's contract for that coordinate does not enumerate (only `(b)` `CompositionalConstraint` and `(c)` `GuardInPath` are listed) — an authoring gap in the cell file, not a soundness finding.
- One `Numeric` obligation sits at `state-ensure-condition`, which is `open` in `Numeric.cells.json` (alongside `rule-condition` and `computed-field-expression`, also open for Numeric — the three constant-fold instances landing there were still classified `licensed` on the general constant-fold principle, since folding a literal against a threshold is sound by construction independent of which coordinate it occurs at; that is a judgment call this measurement makes explicitly rather than silently, and it should be checked against whoever authors the eventual ruling).
- One `IntervalContainment` obligation sits at `computed-field-expression`, open for both primitive and business-domain in `IntervalContainment.cells.json`.
- All three `IndexBounds` obligations sit at `transition-row-action-operand`, and **every one of the five coordinates in `IndexBounds.cells.json` is open** — this file punts on the whole kind, consistent with the matrix's own missing-rule item ("two-sided index-bounds discharge is not covered by any written decision procedure": proving `0 <= i < count` needs both an interval fact on the index and a cardinality fact on the collection, and nothing licenses combining them yet). These three obligations compile clean at HEAD; the definition has not caught up to say why that's licensed.

## What this measurement does not do

- It does not re-derive whether the 77 "no licensed respelling" obligations are actually sound — several almost certainly are (the `QualifierCompatibility` event-ensure gap in particular reads as a one-line authoring omission, not a live soundness question). The bucket records what the **written** contract answers today, which is what the ratification protocol asks this layer to measure.
- It does not attempt to verify every one of the ~115 `GuardInPath`-discharged obligations individually against the transport hole and `BUG-033` — it checked the structural precondition for each hole (state-exit hooks with actions; `into` bindings) across the whole corpus and found the precondition unmet everywhere it occurs. That is real evidence, bounded to this corpus, not a general soundness proof of `GuardInPath`.
- It does not touch the `CompositionalConstraint` question's real fix (whether the fault family should admit premise class (d) at all, and under what preservation obligation) — that is one of the two questions `slice-3-boundary-report.md` already routes to the owner as blocking essentially every defined cell in the family. This measurement's job was to say how much of the corpus that question actually touches (6 obligations, directly; an unknown further share of the "licensed as written" bucket indirectly, since `CompositionalConstraint`'s sign-set path can also draw on rule facts even where the ledger's own strategy tag does not surface as `CompositionalConstraint` — this measurement did not attempt to detect that quietly, and flags it as a residual risk the strategy tag alone cannot rule out).

```
dotnet run --project tools/Precept.MatrixTools -- measure-corpus-faults samples/ corpus-measurement-raw-obligations.json corpus-measurement-raw-obligations.md
```

(`tools/Precept.MatrixTools/FaultCorpusMeasurement.cs` gained one additive field, `ContextDetail`, to distinguish a rule condition from an ensure condition — both otherwise collapse to the same `ConstraintContext` runtime type. No prior field changed shape.) The by-hand classification against the authored cell files (`corpus-measurement-classification-rows.json`) is not yet mechanized; the day-one cell validator's "evidence consistency" check (`README.md` § Validation) is the natural home for automating this once the per-kind cell files converge on one schema shape (they do not today — `Numeric`/`Presence`/`IntervalContainment`/`QualifierChain`/`AssignmentQualifier` use `id`/`coordinates`/`disposition.status`; `LengthContainment`/`QualifierChain`... uses `cellId`/`occasion`/`disposition`-as-string; `DimensionalProduct` and `Modifier` use yet other field names again; `QualifierCompatibility` records no disposition field at all. That inconsistency is itself worth a note for whoever next authors or validates these files.)
