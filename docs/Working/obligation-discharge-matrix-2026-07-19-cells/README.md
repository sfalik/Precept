# Cell data for the obligation-discharge matrix

**Status**: Draft — 2026-07-20. Companion to `docs/Working/obligation-discharge-matrix-2026-07-19.md` (the matrix). Promoted with the matrix at ratification.

This folder holds the matrix's cells as structured data — one JSON file per witness family, validated by `cell.schema.json`. Per the matrix's Storage ruling, cells are data beside the definition, never compiled into `src/`: the matrix's written rules (its "generative sections") determine every cell's answer, and these files record the instances. A cell whose answer cannot be derived from those rules marks a missing rule to author in the matrix — never an answer to invent here.

The precedent for the file shape is `docs/Working/exhaustive-gap-analysis-2026-07-14/assembled/*.cells.json`, from which this schema keeps stable path-style IDs, per-record source citations, and expected-outcome fields; it adds the structure the matrix requires that the precedent's flat records could not carry (contracts, witness triples, dispositions, respellability).

## The file, in ordinary words

Each `.cells.json` file describes one **witness family** — a group of related worked examples sharing one setting (for family 1: a decimal field with a maximum of 1000).

**File-level fields:**

- `familyId` / `title` — a stable identifier and the human name of the family.
- `caseShape` — which of the matrix's four cell kinds this file's cells belong to: `rule-write` (business rules at ordinary write sites), `fault` (faults like division by zero at evaluation sites), `editable-ingress` (direct edits of an editable field), or `structural` (graph-shape checks like unreachable states). The kinds carry different coordinate axes, so each is validated against its own shape.
- `definitionVersion` — which revision of the matrix these cells were written against. Certificates and amendments key off this stamp.
- `citations` — where the family's content comes from: lines in the want doc, spec sections, or dated owner rulings. Every claim in a cell must trace to one of these; the schema requires a date on every owner ruling. A citation's `ref` takes one of three machine-checkable forms: a repo path, a path with a `:line` suffix, or `path § anchor` where the anchor must be a substring of exactly one markdown heading in the cited file. Anything finer-grained — a bullet, a paragraph, a table row — goes in the citation's `note`, so the validator can decide every ref mechanically.
- `respellability` — the family-wide answer to "can every safe program these rules reject be rewritten into a form they accept?" (`verdict`: yes or no). `evidence` says whether that answer is so far only argued on paper (`model-derived`) or measured against the sample corpus (`corpus-measured`); a verdict only ratifies once measured, so `corpusMeasurement` tracks that gate. `licensedNonBandExamples` records spellings that look like they'd be rejected but are in fact accepted by a written rule — kept so the boundary is findable. Every cell inherits this verdict unless it states a more specific override of its own.

**Each cell (`cells[]`) carries:**

- `id` — a stable path-style anchor (e.g. `wf1/preservation-reads-args`). Once cited anywhere, it is never renamed.
- `label` — the name the matrix doc uses ("Base A — RHS reads args only").
- `coordinates` — the cell's position on the matrix's axes. The fields differ by `caseShape`: rule cells carry the obligation family (establishment = the rule holds after construction; preservation = every handler keeps it holding), the rule's structural kind, the kind of write site, what the written expression reads (`rhsReadSet` — absent when there is no authored expression), and the type family. Fault, editable-ingress, and structural cells carry their own axis sets.
- `disposition` — the cell's one-word standing: `defined` (fully answered), `deferred` (answerable, deliberately out of scope, cited), `open` (undecided, cited), `empty` (pruned — requires the one-line derivation of why), or `conflicted` (two canon sources disagree — both cited, routed to the owner). Nothing is ever silently absent.
- `obligation` — what must be proven, written with placeholders (`metavariables`) so that any program differing only in names and constants lands in the same cell. For rule cells the statement is the **weakest precondition**: the condition that must hold before the write so the rule holds after it. `wp.canonicalKey` is the mechanized normal-form key computed by `tools/Precept.MatrixTools` where it can reach, with `canonicalKeySource` saying which test or run pins it. `normalization` cites the rewriting rules matching is done under.
- `applicablePremiseClasses` / `premiseAvailability` — which fact sources can discharge this obligation and the derivation of why. The classes are the want doc's: (a) field modifiers, (b) arg constraints, (c) the handler's guard, (d) rules holding in the pre-state, (e) rule evaluation at an editable-field edit.
- `dischargeContract` — one entry per way the obligation can be closed: the premise class(es) consumed (empty when no authored premise is needed, as with constant folding over defaults), the named derivation, the proof strategy where one exists today, the named **validity arguments** (the matrix's written cases that the derivation is truth-preserving — the ratification gate requires one per cited rule, and a derivation may rest on more than one; the schema validates the names against the matrix's § Validity arguments list), and the **decision procedure**: the concrete finite check that decides no licensed derivation exists, without which rejection could not be tested even in principle.
- `suggestions` — what the failure diagnostic must suggest, per applicable premise class, as a schema over the placeholder `<WP>` — never concrete constants. A required component of every defined non-structural cell (the matrix's cell definition, item 3): empty exactly when the cell's applicable-class set is empty (no authorable premise exists), non-empty otherwise.
- `witnesses` — the concrete examples. `base` is a program the compiler must reject, naming exactly this obligation and the missing classes and nothing else. Each entry in `discharges` is source text added to the base that makes it compile, with the derivation, the model-vs-built status kept separate (`modelStatus` = provable under the definition; `builtStatus` = what the shipped engine does today), and `provenance`: `live-verified` (a real `precept_compile` run, with tool, date, and commit) or `model-derived` (worked out from the documents, no run claimed). On a discharge, provenance attests the **built-status claim** — a `live-verified` mark beside `builtStatus: unresolved-today` records a run demonstrating the engine does *not* yet prove the addition; the `expected` block is the definition's committed power under the model, never something the run verified. `application` states how an addition mechanically applies to the base (a guard appended to a named row; named arg declarations replaced), so the cell→test conversion can generate the modified source without per-cell hand-coding. Each `nearMisses` entry weakens one named addition past sufficiency and must still be rejected with the same obligation — one near-miss per addition, except standing discharges with no addition to weaken.
- `respellability` — how this cell resolves the family verdict: `family-inherited`, or `cell-override` with its own verdict. Where the matrix states one, `bandMember` is a representative safe-but-rejected spelling and `respelling` the accepted rewrite of the same intent.
- `openDependencies` — the open ⧖ items (packet Q/S identifiers) a cell's or contract entry's answer is load-bearing on, recorded structurally per the matrix's minting rule ("the matrix records the dependency instead of absorbing an answer") so that when a ruling lands, every affected cell is mechanically findable.
- `citations` — the want-doc sentences and rulings this cell's content derives from (the matrix's citation duty).
- `notes` — honest records of what the source documents leave unstated or ambiguous for this cell. Never a place to answer them.

## Validation

`cell.schema.json` (JSON Schema, draft 2020-12) *states* field shapes, the per-case-shape coordinate arms, dated owner rulings, provenance completeness on live-verified claims, validity-argument names drawn from the matrix's stated list, conflicted cells citing at least two sources, and the disposition rules (pruned cells need their derivation; open/deferred/conflicted need citations; defined cells need their full content — obligation, contract entries and at least one, suggestion schemas, witnesses with at least one discharge, respellability; structural cells under the weaker shape without obligation/contract columns; suggestion lists non-empty whenever the applicable-class set is non-empty).

**How much of the schema is machine-executed, honestly**: no JSON Schema evaluator runs over these files. The validator executes the schema's **conditional (`allOf`) arms** itself — the defined-cell requirements above — over the keywords those arms use (`required`, `properties`, `minItems`, `const`, `enum`, `type`); any arm using a keyword outside that set is reported as a named skip at each cell, never silently passed. Everything else the schema states — per-field types, `additionalProperties`, citation-`kind` enums, the dated-owner-ruling rule, provenance completeness, the validity-argument name list — is **not machine-checked today**; it is enforced by a schema-aware editor and by review. That gap is recorded here rather than left to be discovered.

Everything the schema cannot express belongs to the day-one cell validator the matrix's Storage section calls for. A first build of that validator exists: `tools/Precept.MatrixTools/CellValidator.cs` (tests: `test/Precept.MatrixTools.Tests/CellValidatorTests.cs`, with deliberately-broken fixture files under `test/Precept.MatrixTools.Tests/Fixtures/cells/`). It reads its closed vocabularies from `cell.schema.json` rather than duplicating them, and reports findings (errors/warnings) plus **named skip records** — every check it cannot run at a cell states the specific reason (e.g. the WP calculator's multi-write refusal naming the open write-plan decomposition decision); nothing is skipped silently or answered with a generic "not supported". The full checklist the validator owns, with each item's build status:

- **Disposition totality** over the full axis product — every cell of the product carries exactly one disposition; no silent cells. *Built in part: each recorded cell's disposition is checked present and from the closed set; totality over the axis product awaits the product enumeration, which does not exist yet.*
- **Citation resolution** — every `ref` decides under the three pinned forms: the path exists, the `:line` is in range, the `§ anchor` matches exactly one markdown heading in the cited file. *Built: missing file or unresolvable/ambiguous anchor is an error; an out-of-range line is a warning (the cited text moved).*
- **Axis-value validity** — coordinate values cross-checked against the built catalogs where anchors exist (types, actions, ProofRequirements), and file-local extensions (e.g. `construction-defaults`) tracked as open vocabulary items. *Built in part: values are checked against the schema's per-case-shape vocabularies (including the cell/file case-shape agreement); the catalog cross-check is pending.*
- **Defined-cell completeness** — a defined cell carries every component the matrix's cell definition names (obligation, contract with at least one entry, suggestion schemas, witnesses with at least one discharge, respellability, citations). *Built: the validator executes the schema's defined-cell arms, so a cell claiming `defined` while carrying none of them is an error, not a silent pass.*
- **Standing-discharge polarity** — a discharge with no `addition` is the standing default-constant-fold case and owes no near-miss; any other kind with the addition absent or null is an error, because its must-reject near-miss would silently disappear. *Built.*
- **Witness-triple minimum** — a defined non-structural cell carries a `base`; the one recorded exception is the standing establishment cell, whose base-less shape is a flagged ambiguity, not a rule. *Pending: base presence is not required by the schema's defined-cell arm, so the completeness check above does not cover it.*
- **Near-miss pairing** — exactly one near-miss per discharge addition, each `pairsWith` resolving to a discharge id in the same cell; standing discharges (`addition: null`) owe none. *Built.*
- **Contract coverage** — every class in `applicablePremiseClasses` appears in some discharge-contract entry, and the suggestion schemas name every applicable class the diagnostic must offer (where a class supplies no authorable premise — the standing inductive hypothesis — the cell must record why it is omitted). *Pending; the validator does check that every contract entry names its decision procedure.*
- **Cell-id uniqueness** — within a file and across all files (ids are citation anchors and are never renamed). *Pending.*
- **Validity-argument presence per cited rule** — every name a contract's `validityArguments` carries has a written argument in the matrix's § Validity arguments (the ratification gate). *Pending (the schema's enum pins the names; the presence-in-matrix check is not built).*
- **Respellability resolvability** — every cell resolves to a verdict (family-level with per-cell overrides), and `respelling` is present whenever the resolved verdict is yes and a `bandMember` is stated. *Built.*
- **Evidence consistency** — the family verdict's `evidence` and `corpusMeasurement` agree (`corpus-measured` iff the measurement is `done`); a family ratifies only when measured. *Pending.*
- **WP recomputation where mechanized** — recompute each cell's `wp.canonicalKey` through `tools/Precept.MatrixTools` and compare against the recorded key; the `canonicalKeySource` names the pin. *Built: the base witness program is compiled through the real pipeline (its expected rejection diagnostics do not block recomputation), the write plan is located from the witness applications, and every shape the calculator declines yields a named skip carrying the calculator's specific reason. The definition-version stamp's presence is checked alongside.*
- **Open-dependency resolution** — every `openDependencies` identifier names a ⧖ item the matrix or packet actually carries. *Pending.*

Known vocabulary gap, recorded rather than absorbed: the establishment-over-defaults cell sits at a write-site value (`construction-defaults`) the matrix's write-site axis does not list; the schema admits it and flags it as an open axis-vocabulary item.

## What else lives in this folder, and how to regenerate it

Every file beside the cell data is generated from it. None is hand-edited; each is reproduced by the command below, and the tests fail if a committed artifact and its regeneration disagree.

| File | What it is | Regenerate with |
|---|---|---|
| `generated/<family>.md` | the human-readable cell table (the matrix's Storage ruling: tables are generated from the data, drift-checked by a test) | `dotnet run --project tools/Precept.MatrixTools -- render-cells docs/Working/obligation-discharge-matrix-2026-07-19-cells` |
| `<family>.manifest.json` | the test manifest: one row per base, discharge, and near-miss, each carrying the structural obligation key the runner matches ledger records against | `dotnet run --project tools/Precept.MatrixTools -- convert-cells docs/Working/obligation-discharge-matrix-2026-07-19-cells/<family>.cells.json docs/Working/obligation-discharge-matrix-2026-07-19-cells/<family>.manifest.json` |
| `<family>.manifest-results.json` | what HEAD actually does with each manifest row | `dotnet run --project tools/Precept.MatrixTools -- run-manifest docs/Working/obligation-discharge-matrix-2026-07-19-cells/<family>.manifest.json docs/Working/obligation-discharge-matrix-2026-07-19-cells/<family>.manifest-results.json` |

The validator runs over the whole folder with `dotnet run --project tools/Precept.MatrixTools -- validate-cells docs/Working/obligation-discharge-matrix-2026-07-19-cells .` (exit 1 on any error).

Two requirements the manifest carries but **cannot check at HEAD**, recorded per row (`unverifiableAtHead`) rather than dropped: the rejecting diagnostic naming all applicable missing-premise classes (diagnostics carry no premise-class structure), and the accepting compile recording its premise list (`ProofObligation` carries no premise list). A results reader sees these named as unverified.

One further limit of the manifest, stated rather than assumed away: obligation identity is (constraint, **site**), and the manifest's structural key carries field, bound kind, bound, and context class — not the site. Where a witness program mints matching obligations at more than one site, the runner reports the ambiguity and fails the row instead of accepting a different site's rejection as "the same obligation".
