# Buildability Review — Compiler Readiness Plan Flagship Slices

**Status:** Review report — 2026-07-02. Produced by the ultra buildability workflow (wf_1384a7e7-59f); slices 2.3/3.1/5.1/6.4 detail recovered from the workflow journal after a synthesis-input truncation.

## 1. Bottom line

All eight flagship slices came back buildable — no slice replicated a needs-design verdict, and no obstacle anywhere in the set requires reopening a locked decision. Slice 1.3, which downgrades the band-containment diagnostics to a proven-violation-only warning, and Slice 2.1, which adds the ChildExpressionPositions catalog projection, were both adjudicated up to buildable-as-specified after skeptics showed the investigators' proposed adjustments were already answered inside the plan's own text. Slice 2.2, which makes the obligation-creation walk total, also lands at buildable-as-specified. The remaining five land at buildable-with-adjustments, each on a concrete, executor-resolvable item: Slice 1.4's registry trim fails the build under the PRECEPT0002 analyzer as literally written (`src/Precept.Analyzers/Precept0002FaultCodeMustHaveStaticallyPreventable.cs:20-22`, Error severity, wired into the compiler build via `src/Precept/Precept.csproj:28-30`), with the analyzer outside the slice's named touch set; Slice 2.3's named reuse machinery is enum-keyed while its subject is DU-subtype-keyed; Slice 3.1's plan text aims the staleness gate at a strategy arm that is already gated at HEAD while omitting the three readers that actually hold the hole; Slice 5.1's first exit criterion demands a rejection the locked design provides no mechanism for; and Slice 6.4's zero-carve-out arithmetic is broken by five additional stage disagreements live at HEAD, one of them a genuine dual-emission no single fix can satisfy. On the dependency side, the plan's claimed hard edge — registry honest before the Phase-2 checker — was independently confirmed, but the plan's "exactly one hard cross-phase ordering" claim was **not** confirmed as literally worded: the plan's own text names at least two more hard orderings (Slice 0.4 before all Phase-1+ work; the Phase-6 register merge before the Phase-7 conformance census) that its red-team never surveys. None of this forces re-sequencing — every hard candidate is already satisfied by the existing phase order.

### Slice 1.3 — Band reclassification for non-proof-carrying fields (buildable as specified)

**Mechanism.** All three band-containment families route their diagnostic code through a single catalog metadata field (`src/Precept/Language/ProofRequirement.cs:343-358`) consumed at one emission helper (`src/Precept/Pipeline/ProofEngine.Diagnostics.cs:21`), so the downgrade is a catalog-touch plus emission-arm edit rather than a scattered rewrite. Severity is stamped per-code from catalog metadata (`src/Precept/Language/Diagnostics.cs:1350-1357`), warnings do not set `HasErrors` (`src/Precept/Compiler.cs:40`), and the proof engine already runs discharge-then-emit as two separate passes (`src/Precept/Pipeline/ProofEngine.cs:121-178`), so the compiles-clean/warns exit criteria are mechanically reachable. The slice also splits PRE0078 so the "exceeded the representable range" message detaches from the band check, and fixes the PRE0135 `?` placeholder (`src/Precept/Pipeline/ProofEngine.Diagnostics.cs:131`).

**Verified assumptions worth knowing.** The mincount `count>0` carries-proof arm discharges a `NumericProofRequirement` in the collection access-safety family — never a band-containment kind (`src/Precept/Pipeline/ProofEngine.Strategies.cs:192-201`) — and sign-modifier facts fold only in the operand-interval read path (`src/Precept/Pipeline/ProofEngine.Intervals.cs:208-213`), so preserving them while downgrading the band lane is structurally clean. `OutOfRange` was never in the bijective set, so its removal there is a no-op (`src/Precept/Language/StaticallyPreventableMap.cs:28-37`).

**Surviving items (minor, in-scope work, not plan adjustments).** The interval prover must be extended from a two-way `bool` to the proved / provably-violating / merely-unprovable trichotomy: `TryIntervalContainmentProofNarrowed` at `src/Precept/Pipeline/ProofEngine.Intervals.cs:489` collapses both failure modes into one `false` (line 504: `if (resultInterval.IsUnbounded) return false;`). This is behavior the slice text explicitly specifies ("proven-violation warning ... stop rejecting merely-unprovable intervals"), and the sibling `bool?` provers already model the exact shape (`src/Precept/Pipeline/ProofEngine.Lengths.cs:25` and `:333`). Trivial drift: `CollectComputedFieldBoundObligations` sits at `ProofEngine.Analysis.cs:538` rather than the plan's :534, and BUG-017/BUG-018 are already marked Fixed in `docs/Working/bugs.md:171/:236` — the "dissolve as floor items" bookkeeping works identically over Fixed entries.

**Why the investigator's downgrade was overturned.** Two of its three obstacles were misreadings the adjudicator and two of three skeptics refuted from the plan's four corners: the per-instance-severity obstacle assumed a per-field Error/Warning split within one band code that no exit criterion requires (the plan's D2 compiler half reclassifies the codes wholesale, plan snapshot line 81, and the carve-out arms reject through their own codes); the fact-consumption-tracking obstacle assumed a per-field carries-proof membership predicate the plan replaces with a closed enumeration, with the underlying staleness soundness explicitly owned by Slice 3.1, the section-11 deferred-enforcement ledger (plan line 1208), and the BUG-021 re-file to Phase 3 (plan line 266).

### Slice 2.1 — ChildExpressionPositions catalog projection (buildable as specified)

**Mechanism.** A new catalog-style projection declares, for every expression-bearing DU subtype in the semantic index, which child positions an obligation-creation walk must recurse into, plus a reflection-based test asserting declared positions match each record's actual child-expression-typed members. It has no pipeline consumer until Slices 2.2/2.3, so it cannot change compile behavior. The derived-projection pattern (`src/Precept/Language/Constructs.cs:226-230`, `Constructs.ByLeadingToken`) and the reflection-shape-test precedent (`test/Precept.Tests/Language/Track2PhaseATokenCatalogTests.cs:14`) both exist; there is no Language-to-Pipeline layering blocker.

**Verified assumptions worth knowing.** The fail-open evidence motivating the projection is exactly true at HEAD: `TypedMemberAccess.Arguments` (`src/Precept/Pipeline/SemanticIndex.cs:113`) is never walked (`src/Precept/Pipeline/ProofEngine.cs:319-323` recurses `ma.Object` only — BUG-032); no guard is ever passed to `WalkExpression`; `AccessModes` is never iterated by the proof engine (zero grep hits); and the walk switch has no default arm (`ProofEngine.cs:282-364`).

**Surviving items (all minor).** Plan line citations into `SemanticIndex.cs` have rotated (:571/:582/:592/:600 now point at different records), and `Guard` sits on the abstract row bases (`SemanticIndex.cs:526/:612`) so the Reject subtypes inherit it — the mandated every-subtype reflection test forces the correct cataloguing without any spec change. The exit criterion's phrase "child-TypedExpression-typed members" does not literally capture the `InterpolatedTypedConstant.Slots` wrapper (`SemanticIndex.cs:177-184`); the implementer must treat the slot's Expression path as a catalogued position. One skeptic additionally found that `TypedPostfixOp.Operand` (`SemanticIndex.cs:227`) is a deliberately-not-walked child (recursing would create a spurious presence obligation), so the projection needs a declared-exclusion vocabulary — implementation care inside the specified mechanism, not a design change. The plan's record counts are stale (66 records at HEAD, not 41) but never used as acceptance numbers, and catalog canon forbids by-count references (`docs/language/catalog-system.md:13`).

**Why the investigator's downgrade was overturned.** Its two adjustment-class obstacles were scope misattributions: the reject-row guard cataloguing is already forced by the slice's own "every subtype present" exit criterion (plan line 346), and the non-DU entry-point roots (rule/ensure guards, default interiors) are Slice 2.2's ten enumerated walk entry points (plan lines 355-357) plus Slice 2.3's totality layer — walk entry points are a different mechanism from the child-recursion positions this projection catalogues.

**Verified assumptions worth knowing.** BUG-031 and BUG-032 are Active at HEAD with behaviorally-confirmed repros matching the exit criteria (`docs/Working/bugs.md:30/:49`), and BUG-031's O-8 walk-vs-restrict fork is documented as owner-gated exactly as the slice's pre-build gate states. The skeptic detail for this slice, recovered from the workflow journal, resolves the earlier truncation and confirms the as-specified verdict on stronger ground than the investigator granted: the left-to-right direction the guard-slot context must implement is specified by the slice's own bundle bullet (plan snapshot line 359 — "intra-guard short-circuit conjunct narrowing so a left-conjunct `X is set` narrows the right conjunct"), and the exit criteria pin both sides behaviorally (the BUG-031 repros must reject; `when X is set and X > 5` must still compile clean), so the unnamed `ObligationContext` subtype is implementation altitude the canonical contract already frames (`docs/compiler/proof-engine.md:279/:287`) — the executor note above stands as guidance for building it correctly, not as a spec gap. ### Slice 2.3 — Three-layer creation-exhaustiveness checker (buildable with adjustments)

**Mechanism.** Slice 2.3 builds the build-time checker that makes a fail-open obligation position structurally impossible going forward: (1) every expression-bearing DU subtype is enumerated in the Slice-2.1 ChildExpressionPositions projection, (2) every `WalkExpression` arm recurses into exactly its catalogued child positions (no hand-picked subset, no missing default arm), and (3) every obligation family a position can raise is enrolled there — so `dotnet build` fails whenever the declared-positions-minus-walked-positions set is non-empty. The fail-open shape it targets is real and verified at HEAD: `WalkExpression` is a defaultless `switch (expr)` (`src/Precept/Pipeline/ProofEngine.cs:282-364`, cases ending at `TypedListLiteral` with no `default:` arm) that recurses into hand-picked children — `TypedMemberAccess.Object` but never `.Arguments` (`ProofEngine.cs:322`; the Arguments member at `src/Precept/Pipeline/SemanticIndex.cs:113`). The architecture offers exactly the extension points the slice assumes: a Roslyn analyzer project wired into the core build as an analyzer reference (`src/Precept/Precept.csproj:28-29`), the shipped catalog-exhaustiveness family (`src/Precept.Analyzers/Precept0019PipelineCoverageExhaustiveness.cs:20`, `Precept0029ModifierAxisDisjoint.cs:33`, `DiagnosticCoverageScanner.cs:28` — note the project is `src/Precept.Analyzers/`, not `tools/`), and a reflection-based catalog-capability meta-test layer mirroring analyzer invariants over the live catalog (`test/Precept.Tests/CatalogCapability/ModifierCatalogCapabilityTests.cs:11-17` plus shared helpers and eight sibling files). The element-entry-path fold has substance: those obligations are already generated catalog-mediated inside the walk (`ProofEngine.cs:473-489`, deriving from the Actions catalog's growing/establishes-value effect; entries at `src/Precept/Language/Actions.cs:78-164`), so representing them as catalogued families in the one checker is wiring, not new mechanism.

**Verified assumptions worth knowing.** All three ordered prerequisites are outstanding at HEAD, exactly as the plan's sequencing expects: the Slice-1.4 registry repartition has not landed (the `_ => FaultCode.DivisionByZero` backstop is live at `src/Precept/Pipeline/ProofEngine.Diagnostics.cs:490`, and no `ProofStrategy.Vacuous` exists), and the Slice-2.1 projection / Slice-2.2 total walk do not exist (a grep for `ChildExpressionPositions` across src/, tools/, test/, and canonical docs/ returns nothing). The checker must therefore be written against the post-repartition FaultCodes, not today's routing. The doc-touch targets exist (`docs/compiler/proof-engine.md:501` "Obligation Generation Contract"; `docs/compiler/diagnostic-system.md:82` names the analyzer family's home), and the DU shapes match the plan's position enumeration (15 `TypedExpression` subtypes at `SemanticIndex.cs:30-237`; guards at `:526/:592/:612`; three action shapes at `:324-338`).

1. *The adjustment the verdict rests on:* the named reuse machinery is enum-keyed, but the checker's subject is DU-subtype-keyed. `HandlesCatalogExhaustivelyAttribute` takes "the catalog enum type whose members must all be handled" (`src/Precept/HandlesCatalogExhaustivelyAttribute.cs:22-25`), and `DiagnosticCoverageScanner` scans specifically for the DiagnosticCode enum (`src/Precept.Analyzers/DiagnosticCoverageScanner.cs:50` — `FindDiagnosticCodeEnum(compilation)`), while ChildExpressionPositions enumerates positions per sealed record subtype of `TypedExpression`. Building the checker in the family therefore means extending the attribute/analyzer pattern to DU base types (Roslyn can enumerate sealed derived records in a compilation) or pairing a lighter analyzer with the reflection meta-test layer — a modest new sibling analyzer either way, not a literal drop-in. The plan's "same analyzer family … do not fork a parallel mechanism" intent is satisfiable; the literal machinery names are not. One skeptic argued this is not an adjustment at all — the plan's own usage of "reuse the machinery" in Slices 6.4/6.5 licenses a new sibling analyzer reusing the enumeration/walking machinery, and the enum restriction lives only in the shipped analyzer's guard clause — but the adjudicated verdict retained buildable-with-adjustments: the DU-subtype-aware variant is real analyzer work the slice text does not enumerate, and the executor must build it rather than find it.

The plan's own 2.2 text already picks the data-driven shape.

### Slice 3.1 — Write-aware tier-2 discharge, intra-chain only (buildable with adjustments)

**Mechanism.** Slice 3.1 adds the write-awareness rule to tier-2 discharge: a standing constraint (a declared modifier fact or an unconditional rule/ensure fact) may discharge a fault obligation only if no same-transaction prefix write to the constrained field is unaccounted for — the compiler rejects the now-unprovable case; committed-state (cross-event) discharge is admitted with its enforcement deferred to the runtime per the plan's scope boundary. The slice extends an existing, shipped staleness discipline rather than building one: `ProofObligation` carries `ReassignedBefore`/`CountEstablishedBefore`/`CountInvalidatedBefore` (`src/Precept/Pipeline/ProofLedger.cs:51/:65/:78`), the `WalkActions` prefix-effect pass stamps them onto every obligation per action (`src/Precept/Pipeline/ProofEngine.cs:409`, stamping at `:516-523`, covering the RHS expression-walk obligations), the write classification is catalog-driven via `ActionMeta.Effect` / `ActionEffectClass` rather than ActionKind identity (`ProofEngine.cs:525-534`; effects declared per entry in `src/Precept/Language/Actions.cs`), and the guard-sourced, relational, and qualifier-narrowing arms already consult the stamps and decline stale facts (`src/Precept/Pipeline/ProofEngine.Strategies.cs:1105-1107` and `:423/:678/:771`; `src/Precept/Pipeline/ProofEngine.QualifierNarrowing.cs:141-143`). The new code is adding the same consult to the un-gated tier-2 standing-fact readers, all of which receive the obligation (with its stamps) at the call site — a thin per-field consult plus minor parameter plumbing.

**Verified assumptions worth knowing.** The exit-criteria test pattern already exists — `test/Precept.Tests/ProofEngine/ReassignmentInvalidationTests.cs:27-49` tests the exact `when X != 0 -> set X = 0 -> set R = 100 / X` idiom plus the no-write control — and every doc-touch target section exists (`docs/compiler/proof-engine.md:1247` sequential proof flow, `:1421` Strategy 4; `docs/runtime/evaluator.md:1326` §7.6 and `:1660` §10; `src/Precept/Runtime/Evaluator.cs:80` confirms the runtime-stub premise). Nothing else already closes the hole — the fact-blocking logic in `CollectBlockedConstraints` (`src/Precept/Pipeline/ProofEngine.Composition.cs:128-169`) covers only unresolved-own-obligation circularity and self-unsatisfiability, not prefix writes.

**Surviving obstacles.**

Implementation of the plan, not a correction to it.
3. *Gate input (minor):* whether the modifier arm needs the consult at all is the GATE-B shape (i)-vs-(ii) fork the plan already dispositioned with a buildable conservative default (plan line 444: shape (ii), the reuse path; GATE-B routed to this slice at plan line 520). ## 4. Dependency re-derivation

The claimed edge — the fault registry must be honest (Slice 1.4, refined by Slice 1.3 landing first) before the Phase-2 creation-exhaustiveness checker builds — was **independently confirmed as hard**, on the correct criterion: the checker is a build gate that freezes fault routing into a structural guarantee, and built pre-repartition it would pass green over the dishonest routing (the `_ => FaultCode.DivisionByZero` backstop is live at `src/Precept/Pipeline/ProofEngine.Diagnostics.cs:490` at HEAD) — silent enshrinement, not a self-evidencing red. The re-derivation also sharpened the producer side: the "no live obligation behind NumericOverflow" premise the checker inherits becomes true only after Slice 1.3 removes the live band obligation stamped by `CollectComputedFieldBoundObligations`, so the honest registry requires 1.3 *and* 1.4, slightly more than the plan's naming of 1.4 alone.

However, the plan's claim that this is the **only** hard cross-phase ordering was **not confirmed as literally worded**. Sixteen candidate edges were examined. Three additional hard orderings surfaced from the plan's own text:

1. **Slice 0.4 (grounding-research reconciliation) before every Phase-1+ slice.** The plan itself labels this a "hard internal ordering," and its claimed mirror in the sequencing red-team is absent — the red-team never mentions Slice 0.4.
2. **Slice 1.4 before the Phase-6 liveness sweep (Slice 6.2).** The plan's Phase-6 dependency text says running the sweep before the registry is honest "would chase codes mid-flight" — the same asserter-over-registry failure family as the confirmed edge, with the same producer. This directly contradicts the red-team's uniqueness rationale ("the checker being the only phase that proves a structural property over the registry's shape"). It is softened by being attribute-derived and self-correcting on re-run, with five phases of slack, but by the red-team's own hardness criterion it is a second instance.
3. **Phase-6 register merge (Slice 6.7) before the Phase-7 conformance census (Slice 7.1).** The plan's Phase-7 header names this hard in so many words, and Slice 7.1's exit criterion (read the one merged register, do not stand up a second tracker) is unsatisfiable before 6.7 exists.

Additionally, the red-team's blanket claim that Phase-0 gates are soft because a conservative default exists overreaches for GATE-F/Slice 1.5: a Tier-3 owner-approved spec amendment has no conservative default and cannot land without recorded approval.

The other candidates examined all resolved soft, agreeing with the red-team where it looked: Phase 1 → Phase 3 (rework visible in red tests, over-rejection is the safe direction); Slice 2.2 → Slice 3.3 (must-sequence-to-pass but self-evidencing); Phase 3 → Phase 4 (reuse-not-parallel discipline, not corruption); the pow-fix land-once coordination between 1.4 and 4.3; Phase 2 → Phase 5 registration; the GATE-M → Slice 6.4 carve-out count (a parameter, not an ordering); Phases 4/5 → the 6.1 emit-or-retire sweep (mechanically self-enforcing — the stale-allowlist analyzer PRECEPT0029 exists at HEAD, `src/Precept.Analyzers/Precept0027DiagnosticEmissionCoverage.cs:12`); the 1.2 ↔ 5.1 unconsumed-artifact coupling (the one edge whose information flows backward against phase order, converted by the plan into an owner decision with a safe co-defer default); and the 0.1(b) → 2.3 conditional omit-join fold. The intra-slice 2.2 closure-plus-narrowing bundle is genuinely hard but not cross-phase.

**Net outcome:** the claim survives in its operational spirit — among Phases 1-7, registry-before-checker is the only hard ordering that constrains otherwise-parallelizable adjacent work and whose violation silently corrupts. Every other hard candidate is satisfied trivially by the existing phase numbering, so no re-sequencing is needed. The defect is in the red-team's completeness and the plan's internal count ("exactly one hard ordering constraint" in §1/D3/Stress 1), which the plan's own Phase-6 and Phase-7 text contradicts. That count should be corrected in the plan so a future re-sequencing decision does not rely on it.
