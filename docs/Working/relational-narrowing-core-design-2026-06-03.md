# Relational narrowing core (Slice 2c-i) — the field-to-field rule → provable interval/sign engine

> **Merge provenance.** This doc is the authoritative merge of two independently-derived designs — A (review-informed, `relational-narrowing-core-design-2026-06-03.md`, this path) and B (blind/clean-room, `…-INDEPENDENT-…`). They converged on the soundness core; that convergent core is kept as corroborated. The two divergences (injection mechanism; fact-record shape) were decided **on the merits against source ground truth** (`Compiler.Compile`-level reads, MCP treated as stale), not by defaulting to either author. The decisions and the source facts that drove them are in § Decisions.

## Goal

When done, a declared **unconditional** field-to-field rule `rule X >= Y because "…"` (and its `>`, `<=`, `<` siblings) contributes a provable bound to `X`'s discharge-time interval and sign-set — sourced from `Y`'s already-established (un-narrowed) interval, single-pass and depth-1 — so a downstream **value-discharge** obligation on `X` (divisor, overflow, out-of-range, sqrt, interval-containment) discharges, **while** (a) guarded relational rules do not leak as unconditional global facts, (b) reading `⟦Y⟧` never transitively chases a third field, and (c) the diagnostic-emitting satisfiability/unreachability/tautology/contradiction scans are *structurally isolated* from the narrowing so it cannot manufacture a false `UnsatisfiableGuard` / `UnreachableRowFact` / `TautologicalGuard` / `VacuousRule` / `ContradictoryRule` / `UnsatisfiableRule`.

**The guarded-rule DROP filter is applied to the shared rule→fact loop (`Composition.cs:144-151`), closing BOTH arms of that loop in one filter.** The same `Rules[i].Guard is null → skip` gate (mirroring the `ensure` path at `:169`) that drops a guarded *relational* `FieldToFieldConstraint` from the global fact set ALSO drops a guarded *magnitude/sign* `ScopedNumericFact` — the **pre-existing** leak filed as **BUG-023** (a guarded `rule X >= 5 when Flag` today folds as an unconditional fact and falsely discharges a global `100 / X` divisor; probe-confirmed against `Compiler.Compile`). The relational arm is the *new* instance of the asymmetry; the magnitude arm is the *live, pre-existing* one. Because both facts are produced inside the one loop that reads no `.Guard`, a single guard-null filter on that loop is the natural and complete shape, and this slice applies it once — closing the new relational arm AND BUG-023 together. BUG-023's fix is therefore **in scope here, not a separate slice**: it closes when 2c-i lands. Demonstrated by: the reorder precept where `rule OnHand > Reserved` (both fields `nonnegative`) makes `BatchCost / (OnHand - Reserved)` provably-non-zero and compiles clean with no author-added guard; and every soundness repro behaving correctly (guarded-rule case rejects, unbounded-`Y` case rejects, transitive chain stops at one hop, satisfiability diagnostics byte-identical with and without the relation).

**Tradeoff detail (Principles 1/7/10/11 — load-bearing).** This core sits exactly on the prevention guarantee. It must never over-prove in *either* direction. (1) On the **value-discharge** side, over-proving = manufacturing a bound the relation doesn't license → a false "proved safe" → a runtime fault on a compiled-clean precept (the Principle-1 breach). The mechanism prevents this by `⊓`-tighten-or-identity (Decision 3): `Intersect` against a `±∞`-sentinel half-line is the identity, so an unbounded or guarded source contributes nothing. (2) On the **diagnostic-scan** side, over-proving = feeding a tighter interval to `UnsatisfiableGuard`/`VacuousRule`/`ContradictoryRule` so they fire on a guard/rule that is actually satisfiable → a false **rejection** of a valid precept (a Principle-11 breach in the opposite direction). The mechanism prevents this by the *structural* consumer isolation (Decision 4): the diagnostic scans read the **bare** `ExtractFieldInterval` and never receive the relational `narrowed` dictionary. We accept false-negative friction (author must bound `Y` or drop the guard for narrowing to help) and extra wiring (thread the narrowed read to value-discharge readers) to guarantee neither over-prove.

**Companion commitments.** *Stateless-first-class*: the fact is field-scoped, derived from rules that apply identically to stateless precepts; `FieldToFieldConstraint` carries no state anchor. *Domain-expert-primary-author*: invisible to the author — no new vocabulary; the already-natural `rule X >= Y because "…"` does the proof work.

## Semantic Rules

### S1 — The fact shape (Decision 1)

A field-to-field relational fact is the record that **already exists** at `ProofEngine.cs:45-48`:

```
FieldToFieldConstraint(string LeftField, OperatorKind Comparison, string RightField)
```

— today produced only from guard decomposition (`ExtractFieldToFieldLeaf`, `Strategies.cs:1203-1211`). The representation decision is to *route declared unconditional rules of shape `Xfield op Yfield` into this same record*, not invent a parallel one. This is the relation-as-fact (B) shape: the fact is about the **pair** `(LeftField, RightField)`, holding neither field's value — the difference-bound-matrix `x − y ≤ c` element form (survey: "the relation `x − y ≤ c` is the stored fact"). `ScopedNumericFact` (`ProofEngine.cs:88-93`) carries a `decimal Value` and is structurally the `field op constant` shape, incapable of `X op Y` — which is precisely why a sibling record is correct rather than extending it with nullable fields (CLAUDE.md DU discipline). Two disjoint records for two disjoint facts.

The fact carries **no event-arg orientation and no state/event anchor**, because the source is an *unconditional rule*, and a rule **cannot reference an event arg** by locked spec (§ line 1866 verbatim: "Rules operate in field scope. They cannot reference event arguments — this ensures reusability across all events.") and an unconditional rule has no context scope. `FieldToFieldConstraint(string, op, string)`'s field-only, anchor-free shape is therefore exactly the rule-sourced relation's shape. (The ensure-sourced / arg-relating case — which would need an anchor and `Field | Arg` orientation — is out of scope; see Decision 1 tradeoff and Open Questions.)

### S2 — Extraction (rule-sourced, with the guarded-rule filter, Decision 2)

A new extraction arm in `Composition.cs` yields a `FieldToFieldConstraint` from a declared rule whose condition is `fieldRef op fieldRef` with `op ∈ {>=, >, <=, <}`. This is the symmetric counterpart to `TryGetNumericConstraintFact`'s field-op-constant extraction (`Composition.cs:180-208`), where today both operands being field references makes both `TryGetStaticNumericValue` arms fail and the rule produces *nothing*.

**The guarded-rule filter (the load-bearing extraction rule).** A `rule X >= Y when SomeFlag` holds **only under** `SomeFlag`; it is NOT an unconditional fact about `X`. The existing `ScopedNumericFact` extraction already enforces this for *ensures* — `TryGetNumericEnsureFact` returns `false` when `ensure.Guard is not null` ("Guarded ensures are conditional — they must NOT become unconditional numeric facts", `Composition.cs:163-169`) — but the **rule loop at `Composition.cs:144-151` applies no such filter** (it calls `TryGetNumericConstraintFact` directly, ignoring `semantics.Rules[i].Guard`). For the relational fact this asymmetry is a soundness hole: folding a guarded relation into `X`'s *global* interval/sign would discharge obligations on paths where the guard is false → false "safe". The extraction rule is therefore:

```
  rule X op Y  declared    guard(rule) = ∅    X, Y are field refs    X ≠ Y    op ∈ {>=,>,<=,<}
  ──────────────────────────────────────────────────────────────────────────────────────── (R-EXTRACT)
        emit FieldToFieldConstraint(X, op, Y) into the rule-sourced relational fact set
```

A **guarded** relational rule produces **no global relational fact** — it is **dropped** from the global fact set (see Decision 2 for drop-vs-row-scope rationale). Its discharge remains available to obligations *in its own row/guard scope* through the existing guard-sourced path (`TryFlowNarrowingProof`, `Strategies.cs:1078-1092`, which reads the obligation's OWN context guard) — that path is unchanged and already correctly row-scoped. A **self-relation** (`X >= X`, `X == Y` after resolution) is dropped (vacuous). The extraction also inherits the existing `CollectTrustedNumericFacts` discipline: a rule whose own obligation is `Unresolved` is blocked from contributing a fact (`Composition.cs:119-151`).

### S3 — R-NARROW composition and depth-1 control (Decision 3)

The narrowing is realized by contributing a relational half-line into `Y`'s/`X`'s discharge-time read. Let `⟦Y⟧₀` denote `ExtractFieldInterval(Y)`'s **non-relational** result (declared bounds + `FlagLowerBound`, exactly today's body). For each unconditional `FieldToFieldConstraint(X, op, Y)`:

```
  rule X >= Y  (or X > Y)      ⟦Y⟧₀ = [ylo, yhi]
  ──────────────────────────────────────────────────────  (R-NARROW-GE)
        narrowed[X] := narrowed[X] ⊓ [ylo, +∞)

  rule X <= Y  (or X < Y)      ⟦Y⟧₀ = [ylo, yhi]
  ──────────────────────────────────────────────────────  (R-NARROW-LE)
        narrowed[X] := narrowed[X] ⊓ (−∞, yhi]
```

where `⊓` is `NumericInterval.Intersect` (`NumericInterval.cs:143`), `±∞` are the `decimal.MinValue`/`decimal.MaxValue` sentinels, and the seed for `narrowed[X]` is `narrowed[X] ?? ExtractFieldInterval(X)` (so a pre-existing guard/sibling narrowing on `X` conjoins, and a fresh entry seeds from `X`'s own declared interval).

**Strict vs non-strict (`>` vs `>=`).** For the **interval** fold, `X > Y` contributes the same closed half-line `[ylo, +∞)` as `X >= Y`: on `decimal` there is no representable ε, and `X >= ylo` is a sound (weaker) over-approximation of `X > Y` — it can only *fail* to discharge a boundary obligation, never *falsely* discharge one. (Type-aware integer strictness — `X > Y` ⇒ `X ≥ ylo + 1` for integer `X` — is available via `NarrowByConstraint`'s existing integer-vs-decimal dispatch (`Intervals.cs`), and SHOULD be applied for an integer subject to gain the +1; the decimal floor is `ylo`. This is a precision refinement, not a soundness one — the closed `ylo` floor is sound for both.) The strict divisor/`!= 0` obligation on a *subtraction* (`X - Y != 0` from `X > Y`) is discharged by the existing subtraction path (`GuardRelationImpliesObligation`, `Strategies.cs:1226-1235`), which already treats `>` strictly; the interval narrowing here is the floor that feeds range/sqrt/overflow.

**Identity degradation (the never-over-prove floor).** When `ylo = decimal.MinValue` (R-NARROW-GE) or `yhi = decimal.MaxValue` (R-NARROW-LE), the half-line is effectively `[−∞, +∞)` on the relevant side and `Intersect` leaves `narrowed[X]`'s relevant bound at its prior value — `X` gains nothing, and any obligation depending on `X`'s narrowed bound stays `Unresolved`. **Pin (`NumericInterval.cs:13-17`):** `IsUnbounded` is a construction-time *flag*, not derived from `Min/Max == sentinel`. The half-lines we build (`new(ylo, decimal.MaxValue)`, `new(decimal.MinValue, yhi)`) are constructed with `isUnbounded: false`, so `Intersect`'s `if (IsUnbounded) return other` short-circuit does NOT fire on them; the identity comes from the **sentinel arithmetic** in `Intersect`'s `Math.Max(Min, other.Min)` / `Math.Min(Max, other.Max)` — intersecting `[a, b]` with `[decimal.MinValue, +∞)` yields `[max(a, MinValue), min(b, MaxValue)] = [a, b]`. The identity is a property of the *sentinel value* in the half-line, not of the `IsUnbounded` flag.

**Depth-1 control (the concrete mechanism).** `⟦Y⟧₀` is `Y`'s **non-relational** interval — `Y`'s declared/flag bounds, NOT a `Y`-narrowed-from-a-third-field interval. The hazard: `IntervalOfNarrowed`'s `TypedFieldRef` case (`Intervals.cs:67-76`) consults the `narrowed` dict first (`:68-69`) and otherwise recurses into `ExtractFieldInterval` (`:76`); if the relational contribution for `Y` were *also* placed in the same `narrowed` dict that `Y`'s read consults, reading `⟦Y⟧` while computing `⟦X⟧` could chase `Y`'s relations transitively (fixpoint-shaped, violating §0.4). **The control is structural: the related field's bound is read via the bare `ExtractFieldInterval(Y)` (= `⟦Y⟧₀`), never via the `narrowed` dict.** `BuildNarrowedIntervals` computes `narrowed[X]` from `ExtractFieldInterval(Y)` — one hop, by construction. Self-reference (`X >= X`, dropped at extraction) and mutual reference (`X >= Y` + `Y >= X` → each reads the other's *non-relational* interval, conjoining to `X == Y` without re-entry) terminate by construction — no fixpoint, no visited-set needed because the read of `Y` does not consult the relational narrowing.

### S6 — Soundness preservation claim (named, per-axis)

Principles threatened: **1** (prevention), **7** (compile-time-first), **10** (totality), **11** (static completeness — in BOTH directions: no false "safe" AND no false rejection). Each axis is proved, not asserted:

- **Strict-weakening sound.** `X > Y` contributes the closed `[ylo, +∞)` (or `ylo + 1` for integer `X`), the *weaker* claim, so it can only fail to discharge a boundary obligation, never falsely discharge one. Principles 1/10/11(safe-direction) hold.
- **Identity-degradation sound.** When `⟦Y⟧₀`'s relevant bound is the `±∞` sentinel, the half-line's bound is the sentinel and `Intersect`'s `Math.Max`/`Math.Min` leaves the narrowed interval unchanged (S3 pin, `NumericInterval.cs:147-149`). No coverage is added that `X` didn't already have. Principle 1 holds.
- **Depth-1 termination.** `Y`'s bound is read via bare `ExtractFieldInterval(Y)`, never the relational `narrowed` dict, so the contribution is not re-entered; the read graph has depth exactly 1 and cannot cycle. Principle 3 (determinism/termination) holds; §0.4 (no fixpoint) preserved.
- **Guarded-rule scoping sound.** A guarded relational rule emits **no global fact** (R-EXTRACT requires `guard = ∅`), so it cannot discharge an obligation on a guard-false path. Its row-scoped discharge stays on the existing guard-sourced path. Principle 1 holds.
- **Satisfiability non-interference sound.** The three diagnostic scans read the bare `ExtractFieldInterval` and never receive the relational `narrowed` dictionary. Their dispositions are a function of declared/flag bounds only — **byte-identical to today** on relationally-narrowable fields. Principle 11 (no false rejection of a valid program) holds.
- **Sign-set fold-composition (Q1 — argued sound, build-probed).** When a subject `X` carries BOTH a magnitude `ScopedNumericFact` AND a relation-derived sign contribution in the same context, the `&=` fold at `Composition.cs:392` intersects both sign sets. `&=` only *removes* signs each constraint independently proves impossible; both contributions are true implications, so their intersection is a true tighter sign set — sound. This rests on a *fold-composition* argument (two facts combine), not a single-fact argument, so it is carried as an explicit build-time adversarial probe (Falsifiers / Acceptance), not a silent assumption.

## Architecture Grounding

### Precept-internal placement

**Layer placement.** Pipeline code (the proof engine), **not** catalog metadata. The fact record (`FieldToFieldConstraint`), the R-NARROW fold, the `narrowed`-dictionary contribution, and the trusted-fact-stream contribution are *reasoning over* catalog-declared obligations — the layer where the guard-sourced Strategy-4 machinery and `BuildNarrowedIntervals` already sit. The catalog declares *what* must be proved (the `ProofRequirement` DU); the strategy is *how*. A relational fact is per-precept analysis state, not language metadata, so it is correctly `private` to `ProofEngine`. This respects the CLAUDE.md catalog rules: no enum-identity dispatch (the operator-implication is a value truth-table in `GuardRelationImpliesObligation`, not a `Kind switch`); the DU rule is honored by a sibling record for a disjoint shape, not nullable-field papering.

**Cross-component propagation:**
- **Runtime (parser, type checker, evaluator, diagnostics):** Proof engine — adds the rule-sourced extraction arm (with the guard filter), the relational contribution to `BuildNarrowedIntervals`, the trusted-fact-stream sign contribution, the rule-sourced extension of `TryFlowNarrowingProof`, and the threading of the relational-narrowed read to the bare-`IntervalOf` value reader at `Strategies.cs:64`. Parser / type checker / evaluator — **None** (no new node, no new typing rule, no runtime path). Diagnostics — **None new from this core** (the relational-unprovable case reuses the existing divisor/range diagnostics with `FlowNarrowing` attribution; new wording for the unbounded-`Y` case is owned by Slice 2c-ii). Critically, the consumer isolation guarantees the *existing* satisfiability diagnostics are **unchanged** on relationally-narrowable fields.
- **Tooling (highlighting, completions, hover, semantic tokens):** Hover/proof-attribution — the narrowed interval is attributed to `ProofStrategy.FlowNarrowing`, already known; no new tooling surface. **None** structural.
- **MCP (vocabulary, DTOs, tool output):** **None.** Both fact records are `private` to `ProofEngine` and never serialized; the obligation DTO reads only `IntervalContainmentProofRequirement.DeclaredMin/Max`, left byte-identical. No DTO, no `CatalogFormatters` change.

**Breaking changes.** None to public contract. `FieldToFieldConstraint` is an existing private record; `ProofStrategy.FlowNarrowing` is an existing member. A program that previously failed a value-discharge obligation may now discharge it (more proving power) — strictly additive on the value-discharge side. The satisfiability scans gain **no** new behavior (the isolation withholds narrowing). The only *new rejections* are the parent design's emit-unconditionally fixes (BUG-017/018/019), not this core.

### External architectural precedent

The architectural problem: *what concrete object represents a two-field relation in a constraint engine's fact store, and how does it discharge by a bounded, legible operation without leaking into the engine's consistency scans?* The canonical answer is the **difference-bound matrix (DBM) / octagon** element (`research/architecture/compiler/relational-constraint-representation-survey.md`):

> "**Octagons** … **B** — the relation `±x ± y ≤ c` is a first-class element of a shared DBM (difference-bound matrix) … the closed form *is* a rule list." (survey, A-vs-B classification)

> "§0.4's 'bounded relational closure' maps to an established domain operation … octagon **strong closure** — a O(n³) Floyd–Warshall pass over a fixed variable set, total and terminating *without* widening … §0.4 is naming 'octagons minus the loop-widening step.'" (survey, Implication 1)

> "allows us to represent invariants of the form (±x ± y ≤ c) … This algorithm … runs in O(N³) time … **a widening operator to compute least fixpoint approximations**" (Miné, octagon paper, Abstract — closure and widening are *distinct*; widening is only for loops). Mirrored at `research/references/octagon-domain/`.

**What Precept takes:** the relation-as-fact (B) shape (`FieldToFieldConstraint` is the discrete named-field analogue of a DBM `x − y ≤ c` entry) and the `⊓`-via-`Intersect` narrowing as the discrete closure step. **What Precept deliberately diverges from:** the DBM closes a *full matrix* by an O(n³) Floyd–Warshall pass; Precept does a single, depth-1 hop (read `⟦Y⟧₀`, `⊓` into `narrowed[X]`) — "do the closure once, do not iterate" (survey, Implication 5). The divergence buys termination and a legible per-rule witness at the cost of completeness. **Precept additionally diverges on consumer isolation, where the survey offers no off-the-shelf precedent:** a verification system's octagon domain is the *single* source of truth, so narrowing and consistency-checking read the same closed DBM. Precept instead keeps relational narrowing *out of* its consistency scans (UnsatisfiableGuard / ContradictoryRule), because those scans are author-facing *diagnostics* whose soundness direction is opposite to discharge — a design constraint that arises from Precept being a *prevention* engine that emits rejections, not a *verification* engine that only proves goals. Confining the narrowing to the discharge-time `narrowed` dictionary (which the consistency scans structurally never read) is the novel-but-warranted mechanism for that isolation; it is acknowledged as a Precept-specific point not drawn from the survey, and it follows the in-tree precedent of `BuildNarrowedIntervals` (guard/sibling narrowing already lives in a discharge-time dictionary, never in `ExtractFieldInterval`).

## Decisions

### Decision 1: Carry the rule-sourced relational fact in the existing `FieldToFieldConstraint` record (sibling to `ScopedNumericFact`), not in a new `ScopedRelationFact` over `NumericSubjectRef (Field | Arg)`

**Stakes**: medium (internal vocabulary; reversible pre-release; no public DTO).

- **Rationale**: The merge's two inputs diverged here — A reuses the existing field-only `FieldToFieldConstraint`; B introduces a new `ScopedRelationFact(NumericSubjectRef Subject, op, NumericSubjectRef Related, AnchorState, AnchorEvent)` whose `NumericSubjectRef` admits `Field | Arg` and which carries an anchor. The deciding question (per the merge brief and skill guard 17) is **whether a rule condition can reference an event arg**. The locked spec answers it directly: §6/Rules line 1866 — *"Rules operate in field scope. They cannot reference event arguments — this ensures reusability across all events."* — and §3.5 line 1350/1376 — a rule condition's scope is "All field names"; "a bare identifier always names a field … never an arg." Since this slice is the **rule** source, the relation's two operands are *always two fields*, and the fact needs *no anchor* (an unconditional rule has no context scope). B's arg-capability and anchor are therefore **YAGNI for the rule source**, and A's reuse is the cleaner call: zero new type, and the rule-sourced fact is *literally the same record* the guard-sourced path already produces (`ExtractFieldToFieldLeaf`, `Strategies.cs:1203-1211`, which is itself field-only — both sides must be `TypedFieldRef`), so the operator-implication core (`GuardRelationImpliesObligation`) is shared by construction, realizing parent Decision 2's "share the guard core" at the data level. The source thus decides this, not aesthetics.
- **Tradeoff accepted**: An **ensure**-sourced relational fact — which *can* be event-anchored and *can* relate an arg (ensures, unlike rules, see args) — cannot reuse the anchor-free, field-only `FieldToFieldConstraint`; it would need the richer `ScopedRelationFact` shape B sketched. This core deliberately scopes to the rule source and defers ensure-sourced / arg-relating relational facts to a clean follow-on (Open Questions). Accepted: building B's general record now to serve an ensure case this slice does not cover is speculative generality; the rule source is the demonstrator and the floor. If/when the ensure case lands, introducing the richer record then is additive (Easy, pre-release) and does not disturb the rule-sourced reuse.
- **Alternatives considered**:
  - *(B's `ScopedRelationFact` over `Field | Arg` with anchors)* — rejected for the rule source: the arg orientation is unreachable (rules are field-only, §1866) and the anchor is meaningless (unconditional rules have no scope), so the extra shape is dead capability that also forks the data away from the guard-sourced `FieldToFieldConstraint` the implication core already consumes.
  - *(Extend `ScopedNumericFact` with nullable `string? OtherField` + discriminator)* — rejected: textbook nullable-shape-papering, forbidden by CLAUDE.md; `Value` becomes meaningless for the relational case and breaks the sign-set consumers that assume `Value` is meaningful.
  - *(New `ScopedFact` base with `ScopedNumericFact` + `ScopedRelationalFact` subtypes)* — rejected as premature: no polymorphic dispatch site consumes a `ScopedFact` base; the relational fact is already named by `FieldToFieldConstraint`. Introduce a base *if* a unified consumer appears (Easy, pre-release).
  - *(A third, brand-new relational record alongside `FieldToFieldConstraint`)* — rejected: maximal duplication, splits the operator-implication core across two records.
- **Precedent**: In-tree, `FieldToFieldConstraint` (`ProofEngine.cs:45-48`, `Strategies.cs:1203-1238`) is the existing relation-as-fact record, and `ExtractFieldToFieldLeaf` is already field-only. External, the DBM/octagon element is the canonical relation-as-fact (B) representation — a record about the *pair*, holding no per-variable value (survey: "`x − y ≤ c` is the stored fact"). The survey's caution — A-vs-B orthogonal to bounded-vs-fixpoint, so the pick turns on blast radius / witness uniformity — favors reuse.
- **Sources consulted for this decision**: `docs/language/precept-language-spec.md` line 1866 — "Rules operate in field scope. They cannot reference event arguments"; §3.5 line 1350 — rule-condition scope = "All field names"; line 1376 — "a bare identifier always names a field … never an arg"; `ProofEngine.cs:88-93` — `ScopedNumericFact(… decimal Value …)`; `ProofEngine.cs:45-48` — `FieldToFieldConstraint(string LeftField, OperatorKind Comparison, string RightField)`; `ProofEngine.Strategies.cs:1203-1211` — `ExtractFieldToFieldLeaf` (both-sides-`TypedFieldRef`, field-only); `CLAUDE.md § Catalog System` — "Use discriminated unions for varying shapes. Don't paper over shape differences with nullable fields on a flat record"; `research/architecture/compiler/relational-constraint-representation-survey.md` — "`x − y ≤ c` is the stored fact". Grepped parent design Decision 2 — locks **B (relation-as-fact)** and "share the guard core … NO public-DTO change … named-rule witness" but leaves the concrete internal shape to the build. Grepped `precept-language-spec.md §0.6/§0.7` — they specify the relational-reasoning *contract*, not the C# record; spec silent on concrete representation.
- **Strongest counter-evidence**: B's general record is the right shape *if the relation source were ensures or args*, and the merged design must eventually serve ensure-sourced relations. Response: true, but this slice's locked scope is the rule source, where §1866 makes args unreachable and anchors meaningless; building the general shape now is speculative generality that also forks the data from the field-only guard core the implication table consumes. The ensure/arg case is named as out-of-scope follow-on, and reaching it later is additive. Looked in §1866, §3.5, the parent design, the survey, and `ExtractFieldToFieldLeaf`; no source argues the rule-sourced fact needs arg orientation or an anchor.
- **Witness-provenance shape (resolved — lookup-by-pair, not a `RuleIndex` field).** The witness must name the contributing rule (§0.6 item 6). This is resolved **in favor of recovering the rule at witness-build time from the `(LeftField, op, RightField)` pair by lookup into `semantics.Rules`**, NOT by adding a `RuleIndex` field to `FieldToFieldConstraint`. Adding a `RuleIndex` would fork the shared record: the guard-sourced producer `ExtractFieldToFieldLeaf` (`Strategies.cs:1203-1211`) has no rule index, so a `RuleIndex`-bearing record would either be wrong/sentinel for the guard source or split into two record shapes — directly undercutting this decision's reuse thesis (one record, shared `GuardRelationImpliesObligation` core). Lookup-by-pair keeps the field-only, anchor-free, index-free record uniform across both producers; the rule is recoverable because the pair + operator uniquely identifies the contributing unconditional rule (a self/duplicate rule is dropped at extraction, R-EXTRACT). The inspectability falsifier (§ Falsifiers) guards the recovery. This keeps the `FieldToFieldConstraint` shape final and identical to today's guard-sourced record.
- **Reversibility**: Easy — `FieldToFieldConstraint` is `private` to `ProofEngine`, pre-release, no external consumer; introducing `ScopedRelationFact` later for the ensure case is a mechanical addition.
- **Blast radius**: `Composition.cs` (extraction + sign fold), `Intervals.cs` (narrowed-dict fold), `Strategies.cs` (shared leaf-extractor + `TryFlowNarrowingProof` extension). No catalog, no DTO, no samples, no external consumer; one proof-engine stage doc.

### Decision 2: A guarded relational rule produces NO global relational fact — it is dropped from the global fact set; its discharge stays on the existing row-scoped guard path

**Stakes**: high (the load-bearing soundness rule — a wrong call here is a Principle-1 prevention breach visible to every author whose precept compiles "safe" when it isn't).

- **Rationale**: A `rule X >= Y when SomeFlag` is true only on the `SomeFlag` path; it is not a fact about `X`'s global interval/sign. The existing `ScopedNumericFact` extraction already enforces exactly this for ensures (`Composition.cs:169`: guarded ensures "must NOT become unconditional numeric facts"), but the rule loop (`:144-151`) has no such filter — the asymmetry both designs flagged. Folding a guarded relation into `X`'s *global* read would discharge a divisor/range obligation on a path where `SomeFlag` is false → a runtime fault on a compiled-clean precept (the §0.7 / Principle-1 breach). **Drop, don't row-scope-into-the-global-narrowing.** The drop-vs-row-scope choice is real, but row-scoping is already served: `TryFlowNarrowingProof` (`Strategies.cs:1078-1092`) reads the obligation's OWN context guard (row/hook/handler/rule-or-ensure) and discharges row-scoped relations through the guard-sourced path. So a guarded relational rule's in-scope discharge is *already available*; adding it to the global path would (a) duplicate that capability and (b) risk the global leak the filter exists to prevent. Drop is the minimal sound choice.
- **Tradeoff accepted**: A guarded relational rule does not contribute to *global* value-discharge — an obligation outside the guard's scope that "feels" dischargeable by the guarded relation is not discharged by it (the author either makes the rule unconditional, or guards the dependent operation so it lands in scope). Accepted: this is the precise, path-sensitive behavior; the alternative (global leak) is unsound.
- **Alternatives considered**:
  - *(A) Drop guarded relational rules from the global fact set* (chosen) — minimal, sound, reuses the existing row-scoped guard path for the in-scope case.
  - *(B) Row-scope the global narrowing: carry the rule guard on the fact and narrow only obligations whose context entails the guard* — rejected: re-implements `TryFlowNarrowingProof`'s context-guard reading inside the global-narrowing path; the capability already exists there; doubling it invites divergence and the global-leak bug.
  - *(C) Fold guarded relational rules unconditionally (the current rule-loop behavior, extended to relations)* — rejected: the exact Principle-1 over-prove hole; discharges obligations on guard-false paths → false "safe."
- **Precedent**: In-tree, the ensure-path guard filter (`Composition.cs:163-169`) is the established pattern for "a guarded conditional constraint must not become an unconditional fact"; this applies the same filter to the rule path's relational extraction. `TryFlowNarrowingProof`'s context-guard read (`Strategies.cs:1078-1092`) is the established row-scoped discharge. External: flow-sensitive abstract interpreters attach a relation to the program point where its guard holds (the survey's EVA/InferBO note: a relation used to narrow via the branch/guard, not stored as a global relation) — guard-conditioned relations are point-scoped, exactly drop-from-global + discharge-in-scope.
- **Sources consulted for this decision**: `ProofEngine.Composition.cs:144-151` — the rule loop with NO guard filter (verified: calls `TryGetNumericConstraintFact(semantics.Rules[i].Condition, …)` without reading `.Guard`); `:163-169` — `TryGetNumericEnsureFact` with the guard filter; `ProofEngine.Strategies.cs:1078-1092` — `TryFlowNarrowingProof` reading the obligation's own context guard; `docs/language/precept-language-spec.md` line 1864/1866 — "A guarded rule applies only when its guard is true … conditional constraint scoping"; §0.7 — fault-prevention "no deferral"; `philosophy.md` line 55 — "not a second line of defense". Grepped §0.6/§0.7 — path-sensitivity of guarded constraints is implied by governance-operation-blindness + no-deferral; the existing ensure filter is the in-tree settlement of the unconditional-vs-conditional fact question.
- **Strongest counter-evidence**: Row-scoping (B) is *strictly more powerful* — it would discharge in-scope obligations where drop relies on the separate guard path. Response: the guard path (`TryFlowNarrowingProof`) ALREADY discharges those in-scope obligations; drop loses nothing the engine could otherwise prove, while B duplicates that capability and reintroduces the global-leak risk. Looked in `Strategies.cs`, the parent design, and §0.7; found no obligation class that drop fails to cover that B would cover.
- **Reversibility**: Hard-ish — if a future need for *global* guarded-relation narrowing appears, it requires the guard-aware global path (B); but reversing *toward* B is additive (the drop is the conservative floor). Pre-release, no external author depends on the discharge being absent.
- **Pre-existing magnitude-arm sibling (BUG-023) — IN SCOPE, closed by this same filter.** The asymmetry this decision corrects — the rule loop (`Composition.cs:144-151`) applies no guard filter while the ensure loop (`:169`) does — is **already live today** for the *magnitude* fact: a guarded `rule X >= 5 when Flag` is folded as an unconditional `ScopedNumericFact` and discharges a global `100 / X` divisor (probe-confirmed against `Compiler.Compile`; the unguarded control discharges, the no-rule control rejects). - **Blast radius**: `Composition.cs` (the guard filter on the rule loop — covering both the new relational extraction arm and, per BUG-023, the pre-existing magnitude arm in the same loop). No catalog, no DTO. The relational arm adds no newly-red. The both-arm falsifier and the corpus check (§ Falsifiers, § Acceptance) verify this. The unchanged guard path carries the in-scope case.

### Decision 3: Compose the relation via `NumericInterval.Intersect` into the discharge-time `narrowed` dictionary, reading the related field's NON-relational interval one hop; depth-1 is enforced structurally by reading `Y` via bare `ExtractFieldInterval`

**Stakes**: medium.

- **Rationale**: `Intersect` (`NumericInterval.cs:143`) is the `⊓` meet R-NARROW calls for and is sentinel-safe — giving identity-degradation for free. The depth hazard (transitive chase) is real: `IntervalOfNarrowed`'s `TypedFieldRef` case consults the `narrowed` dict before falling through to `ExtractFieldInterval` (`Intervals.cs:67-76`). The control is structural: the related field `Y`'s bound is read via **bare `ExtractFieldInterval(Y)`** (= `⟦Y⟧₀`), never via the `narrowed` dict — so computing `narrowed[X]` cannot recurse into `Y`'s relational narrowing. One hop by construction — no visited-set needed because the read of `Y` does not consult the relation stream. `BuildNarrowedIntervals` already reads `ExtractFieldInterval(field)` for each guard field (`:552/:587/:613`), so the depth-1 read is the established in-tree shape.
- **Tradeoff accepted**: `BuildNarrowedIntervals` today returns `null` when there is no guard/sibling-reject (`:534`); the relational case must populate the dict even without a guard, so the early-return is conditioned on "no guard AND no sibling AND no relational fact." Slightly more branching in that builder. Accepted: it is the minimal change that lands the narrowing in the dict the discharge path already consults, keeping `ExtractFieldInterval` (and thus the satisfiability scans) untouched.
- **Alternatives considered**:
  - *(A's shared-function `applyRelational` flag on `ExtractFieldInterval`)* — see Decision 4; rejected in favor of the dictionary placement for structural satisfiability-safety.
  - *(A visited-set guarding recursion instead of the bare-read structural cap)* — rejected as heavier: a visited-set permits depth > 1 (it only stops cycles), so it does NOT enforce the depth-1 §0.4 bound; the bare-`ExtractFieldInterval(Y)` read caps depth at one hop exactly.
  - *(Recursively narrow `Y` from a third field before reading `⟦Y⟧`)* — rejected: the fixpoint/transitive-chase §0.4 forbids.
- **Precedent**: `BuildNarrowedIntervals`' existing per-field `ExtractFieldInterval` reads (`Intervals.cs:552/587/613`) are the in-tree precedent for "seed a narrowed entry from a field's declared interval, one hop." `GuardRelationImpliesObligation` (`Strategies.cs:1213-1238`) is the operator-implication core. External: octagon strong closure propagates a DBM bound into a variable's range via the meet, single-pass (survey Implication 5).
- **Sources consulted for this decision**: `ProofEngine.Intervals.cs:16-21` — `IntervalOf` → `IntervalOfNarrowed(…, null)`; `:67-76` — the `TypedFieldRef` case consults `narrowed` first, else bare `ExtractFieldInterval`; `:514-621` — `BuildNarrowedIntervals` (returns `null` at `:534`; reads `ExtractFieldInterval` per field at `:552/587/613`; consumed only by `TryIntervalContainmentProofNarrowed`); `NumericInterval.cs:13-17,143-150` — `IsUnbounded` is a construction flag; `Intersect` sentinel-safe. `docs/Working/relational-rules-and-bounds-design-2026-06-02.md § Semantic Rules` — R-NARROW-GE/LE. Grepped §0.4 — single-pass/no-widening locked; this composition implements it. Spec silent on the concrete fold/dictionary mechanism.
- **Strongest counter-evidence**: The `narrowed` dict is built per-obligation in `TryIntervalContainmentProofNarrowed`, so the same relational fold is recomputed per obligation rather than once globally. Response: the corpus compiles in ~44ms (project memory: compiler is fast, no incremental); the relational scan is linear in rule count and the read is not on a hot inner loop. If profiling shows it, a per-precept relational-fact index is a trivial memoization (Easy). Looked at the dispatch (`ProofEngine.cs:1088`) and the builder; no correctness issue, only a bounded recompute.
- **Reversibility**: Easy — the narrowed-dict contribution is additive and gated; removing it restores today's behavior.
- **Blast radius**: `Intervals.cs` (the `BuildNarrowedIntervals` extension), `Composition.cs` (the fact collection). No catalog, no DTO.

### Decision 4: Inject narrowing into the discharge-time `narrowed` dictionary + trusted-fact stream and leave `ExtractFieldInterval` UNTOUCHED, rather than adding an `applyRelational` flag to the shared `ExtractFieldInterval` — and thread the narrowed read to the value-discharge readers that today take the bare `IntervalOf(null)` path

**Stakes**: high (a wrong call here ships a false *rejection* of valid precepts — a Principle-11 breach in the opposite direction, author-visible).

- **Rationale**: `ExtractFieldInterval` is read by two consumer classes with **opposite soundness directions** under a tighter interval. The merge's two inputs both keep the diagnostic scans non-narrowed; they diverge on *how*. A adds an `applyRelational` boolean to the shared `ExtractFieldInterval` (default `false`; discharge readers pass `true`, satisfiability passes `false`). B leaves `ExtractFieldInterval` untouched and injects only into the discharge-time `narrowed` dictionary (which `IntervalOfNarrowed` consults) plus the trusted-fact stream. **Source ground truth decides for B's mechanism.** The three satisfiability scans call the **bare** `ExtractFieldInterval` and **never pass a `narrowed` dictionary** (`Satisfiability.cs:96`, `:183`, `:269` — verified; none thread a narrowed dict). Under B, the relational narrowing lives in a code path (the `narrowed` dict) the scans *structurally do not enter*, so a future satisfiability call site is safe-by-default — it, too, will call bare `ExtractFieldInterval` and receive no narrowing, *without anyone having to remember a flag value*. Under A, the relational capability is placed *inside the very function the scans call*, and their soundness depends on every such site (present and future) passing `applyRelational: false`. Both default to the safe direction, but A enlarges the hazard surface — a refactor that flips the default, or a value-discharge helper that internally calls a satisfiability helper, can re-open the Principle-11 hole; B makes the hole structurally unreachable. For a soundness *boundary* (no false rejection), structural unreachability beats a default-safe flag. B's cost — threading the narrowed read to the value-discharge readers that today use the bare `IntervalOf(null)` path (`Strategies.cs:64` OutOfRange/overflow; the IntervalContainment reader at `Intervals.cs:489` already uses the narrowed path) — is bounded and enumerable, and is the merge-surfaced work Decision 4 owns.
- **Tradeoff accepted**: A's flag reaches *all* value-discharge readers through one shared-function parameter; B requires explicitly threading the narrowed read to the value readers that currently bypass the `narrowed` dict (notably `Strategies.cs:64`). If a value-discharge reader is *missed* in the threading, it silently fails to get narrowing — a **false negative** (an obligation that should discharge doesn't), which is the *safe* direction (no false "safe"), surfaced by the acceptance tests (overflow/OutOfRange direction tests must discharge). Accepted: a missed-threading false-negative is sound and test-caught, whereas A's missed-`false` would be a false rejection (unsound). The asymmetry favors B.
- **Alternatives considered**:
  - *(A) `applyRelational` flag on the shared `ExtractFieldInterval`, default `false`* — rejected on the merits: places the relational capability inside the function the satisfiability scans call, making their soundness depend on a per-call-site flag value rather than on structure; larger hazard surface for a Principle-11 boundary.
  - *(B) Inject into the discharge-time `narrowed` dictionary + trusted-fact stream, leave `ExtractFieldInterval` untouched* (chosen) — the satisfiability scans never consume the `narrowed` dict, so the hole is structurally unreachable; follows the in-tree `BuildNarrowedIntervals` precedent.
  - *(A separate non-relational `ExtractFieldIntervalRaw` for the scans, leaving `ExtractFieldInterval` always-relational)* — rejected: inverts the default to unsafe (a new value reader that calls `ExtractFieldInterval` gets narrowing it may not want, and a new scan that forgets `Raw` gets a false rejection); strictly worse than B.
- **Precedent**: In-tree, `BuildNarrowedIntervals` (`Intervals.cs:514-621`) already confines guard/sibling-reject narrowing to a discharge-time dictionary that `IntervalOfNarrowed` consults, explicitly *not* in `ExtractFieldInterval` — this design follows that established split exactly. The satisfiability scans' bare `ExtractFieldInterval` reads (`Satisfiability.cs:96/183/269`) are the precedent that the scans deliberately read the un-narrowed interval. External: a verification system's octagon domain is a single source, so the survey offers no off-the-shelf split; this consumer-isolation is a Precept-specific point (acknowledged in Architecture Grounding) warranted by Precept being a prevention engine that emits rejections.
- **Sources consulted for this decision**: `ProofEngine.Satisfiability.cs:89-117` — `IsConstraintProvablyTrue` reads bare `ExtractFieldInterval` at `:96`, returns `true` on a tighter interval → feeds `VacuousRule`/`TautologicalGuard`; `:178-183` — `BranchHasEmptyFieldInterval` reads bare `ExtractFieldInterval` at `:183` → feeds `UnsatisfiableGuard`/`UnreachableRowFact`; `:267-269` — `BoundedFieldInterval` wraps bare `ExtractFieldInterval` → feeds `ContradictoryRule`/`UnsatisfiableRule`; **none pass a `narrowed` dict**; `ProofEngine.Intervals.cs:16-21` — `IntervalOf` passes `null` for `narrowed` (the bare obligation-site read); `:489-512` — `TryIntervalContainmentProofNarrowed` is the live narrowed consumer; `:514-621` — `BuildNarrowedIntervals` consumed only by it; `ProofEngine.cs:1088`/`:143` — the dispatch sites; `ProofEngine.Strategies.cs:64` — `TryDeclaredBoundProof` reads bare `IntervalOf(site)` (the value reader that must be threaded); `Lengths.cs:176` — the other bare-`IntervalOf` reader (string-length, non-numeric-relational, no threading needed); `docs/language/precept-language-spec.md §0.1` Principle 11 — no false rejection. Grepped all `ExtractFieldInterval` / `IntervalOf` call sites — the value/diagnostic partition is complete and source-verified.
- **Strongest counter-evidence**: The focused design argued a tighter operand interval "can only make a contradiction *more* detectable, never mask one (sound either way)." Response: this confuses *more detectable* with *correctly detectable*. For a **goal-proving** consumer (discharge), tighter = more proving, sound. For a **rejection-emitting** consumer (UnsatisfiableGuard / ContradictoryRule), "more detectable" means *firing the rejection on inputs that don't warrant it* — a false positive, a wrong rejection of a valid precept. Verified by tracing each scan's emit condition (`IsEmpty → emit`, `provably-true → emit`): a tighter interval drives `IsEmpty`/`provably-true` MORE often. This is exactly why the narrowing must be withheld from the scans, and B's structural withholding is the soundest way to do it.
- **Reversibility**: Easy on the discharge side (the narrowed contribution is additive); the *isolation* direction (scans read bare `ExtractFieldInterval`) is the sound one and unlikely to reverse.
- **Blast radius**: `Intervals.cs` (`BuildNarrowedIntervals`), `Composition.cs` (sign-set fold), `Strategies.cs` (`:64` threading + `TryFlowNarrowingProof` extension); **zero** change to `Satisfiability.cs`; no catalog, no DTO, no samples (satisfiability output unchanged by construction). External consumers: none.

## Falsifiers

This core ships the soundness-critical discharge mechanism and, via the isolation, guards an author-visible rejection surface, so the never-over-prove falsifiers are load-bearing in BOTH directions:

- **Never-over-prove, value-discharge (load-bearing — Principle-1 falsifier).** If a precept whose only relevant bound is a relational fact compiles clean and a runtime trap (`OutOfRange`, divide-by-zero, overflow) then fires on it, the `⊓`-tighten-or-identity claim (S6) is false and the mechanism is unsound — immediate redesign.
- **Never-over-prove, diagnostics (load-bearing — Principle-11 falsifier).** If, after this core ships, any precept that compiled clean before now emits `UnsatisfiableGuard`/`TautologicalGuard`/`VacuousRule`/`ContradictoryRule`/`UnsatisfiableRule`/`UnreachableRowFact` *because* a relational rule tightened a field's interval in a satisfiability scan, the isolation leaked (the narrowing reached the bare `ExtractFieldInterval`) and a valid precept is being wrongly rejected — immediate redesign. Standing guard: the satisfiability-non-interference regression test, whose fixture is **adversarially chosen** so the relation WOULD flip a `VacuousRule`/`ContradictoryRule`/`UnsatisfiableGuard` disposition under leakage — byte-identity then proves non-leak rather than passing vacuously.
- **Sign-set fold-composition (Q1 — build probe, not silent).** If a subject `X` carrying BOTH a magnitude `ScopedNumericFact` AND a relation-derived sign in the same context yields a sign set that drops a *reachable* sign (e.g. claims `Positive` when 0 is reachable) → a false divisor-safe, the `&=` fold (`Composition.cs:392`) composition argument is wrong. The build's adversarial diff review MUST construct and trace a magnitude-plus-relation-on-one-subject case; a green claim without this probe is not accepted (the per-consumer proof leans on a fold-composition argument here, not a single-fact argument).
- **Guarded-rule leak (both arms).** If a `rule X >= Y when SomeFlag` (relational arm) OR a `rule X >= 5 when SomeFlag` (magnitude arm, **BUG-023**) discharges a *global* (guard-false-reachable) obligation on `X`, the guard filter (Decision 2) leaked. Immediate redesign. The magnitude arm is the pre-existing instance (today's rule loop reads no `.Guard`); both are closed by the same `Rules[i].Guard is null` filter on the shared loop, so a falsifier hit on EITHER arm indicts the same fix.
- **Corpus soundness tax — the EXPECTED tightening (NOT a falsifier; distinct from the over-reject falsifier below).** Closing the live BUG-023 over-prove tightens what compiles: a corpus sample that compiles clean *today* **because** a guarded magnitude rule falsely discharges a fault-prone op will **newly REJECT** after the magnitude-arm filter. This newly-red is **correct and expected** — each such sample was relying on an unsound "safe" and must carry a real unconditional constraint or guard the dependent op into scope (the §0.7 soundness tax, the same shape BUG-019's 20-sample fix paid). **The discipline is the inverse of the reach falsifier:** here a newly-red sample is a *genuine latent over-prove to fix at the sample* (add a constraint/guard), **NOT a reason to revert the filter**. This is explicitly *not* the over-reject case — it does not arise from too-weak relational reach (an identity-narrowing that should have tightened); it is the deliberate removal of a leak. The build-time corpus check: run `SampleCompilesCleanTests` after the magnitude-arm filter; triage each newly-red sample — if it relied on a guarded magnitude rule discharging globally, fix the sample (constraint/guard); only if a newly-red sample is *not* explainable by the closed leak does it indict the relational reach (the falsifier below).
- **Depth-1 broken.** If a transitive chain `X >= Y`, `Y >= Z`, `Z min 0` propagates `Z`'s bound all the way to `X` (i.e. `⟦Y⟧` was read *with* relational narrowing), the bare-`ExtractFieldInterval(Y)` read leaked and depth exceeds 1 — §0.4 violated. The transitive-chain standing test is the guard.
- **Identity-degradation broken.** If `rule X >= Y` with `Y` unbounded ever narrows `X`'s lower bound to anything other than `X`'s pre-existing lower bound, the sentinel handling is wrong; verify `Intersect` of `⟦X⟧` with the `[decimal.MinValue, +∞)` half-line is the identity.
- **DTO leak.** If realizing this core requires any change to `IntervalContainmentProofRequirement`, `CompileToolDtos.cs`, or `CatalogFormatters.cs`, the parent Decision-2 no-DTO invariant is breached — flag loudly. (Verified false at design time: both fact records are private; the DTO reads only `DeclaredMin/Max`.)
- **Reach (depth cap under-proves) — the OVER-REJECT case, distinct from the soundness tax above.** If the depth-1 cap under-proves a transitive relation chain in **two or more** `samples/` — i.e. a genuinely-safe sample newly-reds *because the relational narrowing was too weak to discharge it* (an identity-narrowing that should have tightened) — raise the bounded depth to a fixed small N (still no fixpoint); if no fixed N suffices without a sample needing genuine fixpoint reasoning, the §0.4 envelope is being stretched and scope is wrong. **This is the opposite of the soundness-tax newly-red:** here the fix is to strengthen the reach (or the precept genuinely needs a bound); there the fix is to add the missing constraint/guard at the sample because the prior compile was unsound. Triage every newly-red sample into exactly one of these two buckets before acting — a soundness-tax newly-red must never be "fixed" by widening reach, and a reach-gap newly-red must never be "fixed" by adding a constraint that masks a real under-prove.

## Acceptance criteria

- **Design demonstrator** — a precept with `rule OnHand > Reserved` and both fields `nonnegative` makes `BatchCost / (OnHand - Reserved)` discharge — **compiles clean** — and the divisor obligation's disposition reports `ProofStrategy.FlowNarrowing`. (`RelationalNarrowingCoreTests`)
- **Unbounded-`Y` rejects** — the same shape with `Reserved` unbounded in the relevant direction (and division by bare `OnHand`) **fails to compile** (obligation stays `Unresolved`); identity-degradation manufactures no bound. (`RelationalNarrowingCoreTests`)
- **Overflow / OutOfRange direction (the threaded reader)** — `rule X <= Y`, `Y max 100`, an overflow/OutOfRange obligation on `X` **discharges** (R-NARROW-LE), proving the relational-narrowed read reached `TryDeclaredBoundProof`'s reader at `Strategies.cs:64`. (`RelationalNarrowingCoreTests`)
- **Guarded-rule rejects — relational arm (the guard filter)** — a precept where the ONLY relation is `rule X >= Y when SomeFlag` and a *global* (guard-false-reachable) obligation depends on `X >= Y` **fails to compile**; and the same relation *in the guard's scope* discharges via the existing guard path. (`RelationalNarrowingCoreTests`, two cases)
- **Guarded-rule rejects — magnitude arm (the SAME guard filter, BUG-023) — MUST-PASS acceptance (matrix row #13).** A precept where the ONLY constraint is a guarded *magnitude* rule `rule X >= 5 when Flag` and a global divisor obligation `<- 100 / X` depends on `X != 0` **MUST fail to compile** (`DivisionByZero`) after the fix — this is the BUG-023 repro and a required acceptance, not a recommendation. The unguarded `rule X >= 5` control **MUST still discharge** clean (the legitimate unconditional fact must continue to reach and discharge — the fix tightens only the guarded path); the no-rule control **also rejects**. This is the **pre-existing** instance of the identical guarded-rule leak that the new relational arm fixes — `TryGetNumericConstraintFact`'s rule loop (`Composition.cs:144-151`) reads no `.Guard`, while the relational arm this design adds DROPs guarded rules. The shared-loop guard filter (the `Rules[i].Guard is null` gate this build adds to that loop) covers **both** arms at once: applied to the rule loop, it filters the magnitude `ScopedNumericFact` and the relational `FieldToFieldConstraint` together. BUG-023 is **in scope for this slice** and closes when 2c-i lands; this acceptance cell does not move to a separate slice. (`RelationalNarrowingCoreTests`)
- **Transitive-chain stops at one hop** — `X >= Y`, `Y >= Z`, `Z min 0`, divisor on `X`, `Y` unbounded: `X` gains `Y`'s (non-relational) bound only, NOT `Z`'s transitively; the obligation **fails to compile** and the chain **terminates** (no hang). Standing regression. (`RelationalNarrowingCoreTests`)
- **Satisfiability non-interference (the isolation — adversarially load-bearing)** — the standing byte-identical-diagnostics regression must use an **adversarially chosen** precept in which the relational rule WOULD flip a satisfiability disposition *if it leaked into the bare-`ExtractFieldInterval` scan*, so the isolation is the only thing preventing a false rejection and the test cannot pass vacuously. Concretely: a precept where field `X` carries declared bounds plus a guard/rule such that `X`'s **non-relational** interval leaves a guard satisfiable / a rule non-vacuous / a constraint non-contradictory, BUT the relational rule `rule X >= Y` (with `Y` bounded so it genuinely tightens `X`) would, *if* folded into the scan's interval, drive that guard/rule to `UnsatisfiableGuard`/`VacuousRule`/`TautologicalGuard`/`ContradictoryRule`/`UnsatisfiableRule`. The acceptance assertion: the emitted satisfiability-diagnostic set is **byte-identical with and without** the relational rule present — and, because the relation is adversarially chosen to flip a disposition under leakage, a byte-identical result is *positive evidence* the narrowing never reached the scan (a vacuous precept where the relation couldn't flip anything would make the test pass even if the isolation were broken, and is rejected as the test fixture). Standing regression. (`RelationalNarrowingCoreSatisfiabilityTests`)
- **Sign-set fold-composition probe (Q1)** — a subject `X` carrying BOTH a magnitude fact (`rule X >= 3`) AND a relation (`rule X >= Y`, `Y` bounded) in one context produces a sign set that drops no reachable sign; an adversarially-constructed case where 0 is reachable is **not** proved divisor-safe. (`RelationalNarrowingCoreTests` + build diff-review trace)
- **Conjunction** — two relational facts on one field (`X >= Y`, `X >= W`, both bounded) narrow `X`'s lower bound to `max(Ylo, Wlo)`, verified by a range obligation that discharges iff the conjoined bound covers it. (`RelationalNarrowingCoreTests`)
- **Mutual / self terminate** — `A >= B` + `B >= A` (conjoin to `A == B`) and `X >= X` (vacuous, dropped at extraction) **compile and terminate** — no hang, no stack growth. (`RelationalNarrowingCoreTests`)
- **No new vocabulary** — no new `ProofRequirement`, `ProofRequirementKind`, or `ProofStrategy` member (verified by diff). (review gate)
- **No DTO change** — a literal-bound-only precept produces a byte-identical `precept_compile` obligation DTO before/after. (`RelationalNarrowingCoreTests` snapshot)
- **Shared core** — `FieldToFieldConstraint` extraction is exercised from BOTH a guard source and a rule source through the shared leaf-extractor. (`RelationalNarrowingCoreTests` + existing guard-narrowing tests)
- **Corpus soundness-tax check (build-time, MUST run after the magnitude-arm filter).** Run `SampleCompilesCleanTests` immediately after the BUG-023 magnitude-arm guard filter lands. **Triage every newly-red sample into exactly one bucket:** (a) *soundness-tax* — the sample relied on a guarded magnitude rule falsely discharging a fault-prone op (divisor/range/overflow); this is a genuine latent over-prove, fixed **at the sample** by adding a real unconditional constraint or guarding the dependent op into scope, NOT by reverting the filter; or (b) *reach gap* — a genuinely-safe sample under-proved by too-weak relational reach (fixed by strengthening reach, § Falsifiers). The two are not conflated: the relational arm adds **zero** newly-red (strictly additive), so any newly-red in this slice is the magnitude-arm soundness tax (bucket a) unless it is explainable only by relational under-prove. A newly-red sample is NOT a reason to revert the filter.
- `dotnet test` green across all four projects; numeric-constant golden snapshots byte-identical; `SampleCompilesCleanTests` green **after the soundness-tax triage** (every newly-red sample either fixed as a soundness-tax latent over-prove or, if a reach gap, fixed by strengthening reach — never by reverting the BUG-023 filter).
