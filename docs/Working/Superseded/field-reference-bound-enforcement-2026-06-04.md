# Field-reference modifier-bound enforcement (Slice 2c-ii) — desugar, length/count band-relational discharge, and the rich author message

> **Provenance.** This slice closes the *enforcement* half of BUG-020: a bound modifier whose value is a **field reference** (`min Floor`, `minlength MinLen`, `mincount Limit` — for length/count the referenced field is an integer whose value is the required length/count) parses and type-checks but is silently dropped — the bound does nothing. That is a Principle-10/11 soundness hole (a declared bound that does not participate in proof). The slice consumes the 2c-i discharge core (`relational-narrowing-core-design-2026-06-03.md` + its contradiction-reject and subject-resolution amendments, all Locked 2026-06-04) and realizes the parent design's D1/D2/D5/D6/D7 (`relational-rules-and-bounds-design-2026-06-02.md`, Locked) for the modifier surface. It does NOT re-open whether the field-reference bound form should exist — §2.4/§3.5 make it spec-legal and the parent design locked its admission; this slice makes it *enforced*. The *binder* half of BUG-020 (an undeclared-name reference in a bound is silently swallowed, no PRE0029) is a distinct gap and is scoped in below (Decision 1 covers it, because the desugar is exactly where the name must resolve).

> **Amendment provenance (2026-06-05).** An adversarial `precept-reviewer` pass (2026-06-05), with source evidence, confirmed three soundness/semantics errors in the original Locked-2026-06-04 design. This amendment corrects them and re-locks; the sound architecture (the six decisions, the desugar model, the band-edge DU, the contradiction guard, identity-degradation) is unchanged. The three corrections:
> 1. **Numeric default-containment mechanism (Decision 2 / S2).** The original said the numeric default check reads "X's narrowed interval." That cannot reject the headline BUG-020 case (`Floor default 10` unbounded + `Amount min Floor default 5`): when `Floor` is unbounded, 2c-i's narrowing identity-degrades, so X's narrowed interval has no lower bound and "default 5 ∈ narrowed interval" is trivially clean. The correct mechanism is spec **Principle 11** — the desugared `rule Amount >= Floor` is folded against default field values (5 ≥ 10 is false → reject). Global rules are **not** folded against defaults today; that capability is **BUG-027** (`ScanRulesAgainstDefaults`, extending the ensure-fold in `CheckInitialStateSatisfiability`), a now-explicit **prerequisite** for the numeric default enforcement. (The *dependent-op* discharge — divisor/range, e.g. `100/Amount` — stays the 2c-i reuse, unchanged.)
> 2. **Length/count semantics (Decision 3 / S1, S3, worked + error examples).** The original desugared `minlength Y ⇝ X.length >= Y.length` (treating Y as a string and comparing lengths, resolving via `StringLengthIntervalOf(Y)`). That misreads the modifiers: `minlength`/`maxlength`/`mincount`/`maxcount` take an **integer** value whose VALUE is the required length/count (`Modifiers.cs:165-223` — `Accessor('length'/'count') <op> DeclarationValue()`, NO projection on the bound side; `TypeChecker.Validation.Modifiers.cs:573/594` — "must be a non-negative integer"). So `field X as string minlength Y` means `X.length >= Y` with `Y` an **integer field** whose value is the required length, and the band edge resolves from `Y`'s **`NumericInterval`** (`ExtractFieldInterval(Y)`), NOT its length interval. The desugar shape, the band-edge resolution source, the worked example, and the length error-message example are all corrected to integer reference fields. `minlength Y` with `Y as string` is a **type error** (a string is not a valid integer length value).
> 3. **Decision 2 stakes.** Reclassified `medium → high`: the confirmed default-containment hole makes Decision 2 load-bearing (and now carries an external dependency on BUG-027), so it gets the high-stakes legs (strongest counter-evidence, reversibility, blast radius).

## Goal

When done, every bound modifier with a field-reference value participates in compile-time proof identically to the equivalent rule (§2.4): a `Compiler.Compile` of `field Amount as number min Floor` (numeric), `field Name as string minlength MinLen` (length, `MinLen` an integer field whose value is the required length), or `field Tags as set of T mincount MinCnt` (count, `MinCnt` an integer field) **emits the obligation and discharges-or-rejects** — provable→clean, unprovable→reject with a rich author-facing message naming the referenced field, contradiction→reject, unbounded-reference→reject — while a literal bound (`min 5`, `minlength 3`, `mincount 2`) is byte-identical to today, and self/mutual references terminate. Demonstrated by: (numeric) `field Floor as number default 10` + `field Amount as number min Floor default 5` now rejects the `default 5` against `Amount >= Floor` — via BUG-027's rule-vs-default fold (the desugared `rule Amount >= Floor` evaluated against the default environment: 5 ≥ 10 is false), today clean; (length) `field MinLen as integer min 4` + `field Name as string minlength MinLen default "ab"` (length 2) rejects the short default against the resolved required length 4; (count) `mincount MinCnt` with a default count below `MinCnt`'s value-floor rejects; and an undeclared `min Nonexistent` emits a name-resolution diagnostic instead of being swallowed.

**Tradeoff detail (Principles 1/7/10/11).** The mechanism is deliberately *incomplete but sound*: it discharges only the bounds whose referenced field has a decidable bound in the relevant direction (one hop, §0.4), and declines the rest — the author bounds the referenced field or writes a guard. This accepts false-negative friction (an author may have to add `min 0` / `minlength 3` / `mincount 1` to the referenced field) to guarantee the engine never emits a false "proved safe," which would be a runtime fault and a prevention breach. This is the §0.6-item-1 posture, applied uniformly to all three modifier families.

**Companion commitments.** *Stateless-first-class*: bound modifiers are field-scoped data constraints; the desugar produces unconditional field-only rules fully applicable to stateless precepts; nothing depends on a state machine. *Domain-expert-primary-author*: the feature requires no new vocabulary — a domain expert who writes `min Floor` / `minlength MinLen` already expresses the intent; this slice makes that already-natural bound do the proof work it currently doesn't, and the rich message speaks in the author's field names.

## Language Design Grounding

This slice introduces **no language surface** — the six bound modifiers and the field-reference bound form are spec-defined (§2.4, §3.5) and parse today. The general-language-design grounding for *making a relational constraint participate in proof* (CUE lattice-narrowing taken, Zod/Pydantic no-propagation diverged-from, the §0.4 single-pass-not-fixpoint divergence) is established in the parent design's § Language Design Grounding and the 2c-i core's, and is not repeated. What follows is the slice-specific application.

**The desugar is the field's established model for "modifier ≡ rule."** §2.4 lines 1133-1138 state the constraint modifiers "desugar to the equivalent `rule` with a generated rationale" and "participate in compile-time proof identically to the equivalent rule." This is the standard GHC-style *desugaring pass* model: surface sugar is rewritten to a smaller core (here, a `TypedRule`) before the analysis that matters runs over the core, so the analysis need not know the sugar. GHC desugars `do`-notation and list comprehensions to core `>>=`/`concatMap` before the optimizer runs; Precept desugars `min Floor` to `rule X >= Floor` before the proof engine runs. Precept *takes* the desugaring-pass model and the rationale-generation §2.4 already specifies; it *diverges* from a hypothetical "the proof engine special-cases each modifier kind" approach (which would re-encode in the proof engine the modifier↔rule equivalence the catalog already declares — the CLAUDE.md "never switch on `*Kind` to dispatch per-member behavior" violation). The numeric family proves the model: once desugared, the synthetic `rule X >= Floor` flows through the *existing* relational path with zero proof-engine knowledge of "this came from a modifier."

**The length/count divergence — why a band-relational requirement, not a desugared rule into the relational path.** The numeric relational path (`TryGetRelationalFact`) requires both operands to be *bare field references* (`ProofEngine.Composition.cs:229`). `X.length op Y` and `C.count op Y` have a projection (`TypedMemberAccess` over a `FixedReturnAccessor` returning `Integer`, `Types.cs:172-173`) on the *subject* (left) side — `Y` itself is a bare integer field, not a projection — so the relation is not bare-on-both-sides and cannot enter that path. More fundamentally, the length/count discharge does not narrow a *subject's interval* the way numeric does — it compares an assigned value's *length/count interval* against the field's *declared band* (`TryLengthContainmentProof`/`TryCountContainmentProof` read scalar `req.DeclaredMinLength`/`DeclaredMinCount`). A field-reference length/count bound makes the *band itself* relational: `minlength MinLen` (where `MinLen` is an integer field) means "the band's lower edge is the required-length *value* `MinLen` carries — its `NumericInterval`, resolved at discharge." This is the octagon/DBM relation-as-fact shape applied to the *band edge* rather than to a numeric subject — the same conceptual operation (read the referenced field's *value* interval via `ExtractFieldInterval`, take the demanded edge, identity-degrade on unbounded, reject on empty), realized in the integer length/count band domain. The divergence from numeric is structural (different discharge architecture), not philosophical (same soundness spine).

**Precept-specific application.** Touches §0.6 item 1 (interval reasoning), item 2 (relational reasoning), item 6 (assignment-range impossibility = compile-time error — the length/count band violation IS an assignment-range impossibility on the length/count axis). Risks conflicting with §0.4 if length/count narrowing were a fixpoint — the design forbids it (depth-1, read the referenced field's *non-relational* band). No principle in §0.1 is overridden; the field-reference bound form is already permitted by §2.4/§3.5 (no Tier-3 spec conflict).

## Audience and Teachability

**Worked example** (a discount-tier configuration entity — a plausible config/reference domain; a stateless precept):

```precept
precept DiscountTier

field MinUnits as integer min 1 max 100 default 10
field MaxUnits as integer min MinUnits max 1000 default 50
field MinCodeLength as integer min 2 max 8 default 3
field DisplayCode as string minlength MinCodeLength default "STANDARD"
```

`min MinUnits` on `MaxUnits` declares the relation `MaxUnits >= MinUnits` — the floor of the larger tier is the smaller tier's value, resolved from `MinUnits`'s own `[1,100]` bound. `minlength MinCodeLength` on `DisplayCode` declares `DisplayCode.length >= MinCodeLength` — the display code's length is at least the integer value `MinCodeLength` carries, resolved from `MinCodeLength`'s own `[2,8]` *value* bound (an integer length, not another field's length). Both are constraints a domain expert reasons about naturally ("the max tier can't be below the min tier"; "the display name's length must be at least the configured minimum"), and after this slice both are *enforced*: a `default "X"` on `DisplayCode` (length 1) against `MinCodeLength`'s ceiling of 8 (the most-demanding required length — see S3-soundness) would reject.

**Error message** (the misuse: a field-reference bound whose referenced field is unbounded in the relevant direction). A domain expert writes `field Floor as number` (no bound) and `field Amount as number min Floor`, then nothing else bounds `Amount`:

```
PRE0079 (OutOfRange): Cannot prove the default of 'Amount' stays at or above its 'min Floor' bound.
  'Amount' is bounded by 'min Floor', but 'Floor' has no declared lower bound,
  so 'Amount >= Floor' does not establish a provable floor.
  Add a lower bound to 'Floor' (e.g. `min 0`), or replace 'min Floor' with a literal bound.
```

The length analogue (the referenced field is an **integer** whose value is the required length; here it is unbounded *above*, so the required length is unprovable — see S3-soundness, the required length is the referenced field's MAXIMUM value):

```
PRE0135 (LengthBoundViolation): Cannot prove the default of 'DisplayCode' meets its 'minlength MinCodeLength' bound.
  'DisplayCode' must be at least 'MinCodeLength' characters long, but 'MinCodeLength' has no declared maximum value,
  so the required minimum length cannot be established.
  Add a 'max' to 'MinCodeLength' (e.g. `max 8`), or replace 'minlength MinCodeLength' with a literal length.
```

This serves the domain expert (not the compiler engineer) because it names the *business field* whose missing constraint is the real cause (`Floor`/`MinCodeLength`), states the relation in the author's own terms (`Amount >= Floor`; "at least 'MinCodeLength' characters long"), and offers two concrete repairs in DSL syntax — never "obligation unresolved at site" or "narrowed interval empty." It reflects §0.7's "names what would make the operation provably safe."

## Semantic Rules

### S1 — Desugar (the reduction)

Each field-reference bound modifier rewrites to a synthetic unconditional `TypedRule`, span-tagged to the modifier so attribution lands on `min Floor` (not a phantom rule). `Y` denotes the resolved referenced field:

`Y` is an **integer** field whose VALUE is the required length/count for the length/count families (per `Modifiers.cs:165-223` — the bound side is `NumericBoundSource.DeclarationValue()`, an integer value, with NO projection; `TypeChecker.Validation.Modifiers.cs:573/594` — "must be a non-negative integer"). The projection (`.length`/`.count`) is on the SUBJECT side only:

```
field X as T min Y         ⇝   field X as T  +  rule X >= Y          because "<gen>"   [span = the `min Y` modifier]
field X as T max Y         ⇝   field X as T  +  rule X <= Y          because "<gen>"   [span = the `max Y` modifier]
field X as string minlength Y  ⇝  field X as string + rule X.length >= Y because "<gen>"  [span = the modifier]   (Y an integer field; Y's VALUE is the required length)
field X as string maxlength Y  ⇝  field X as string + rule X.length <= Y because "<gen>"
field C as coll of T mincount Y ⇝ field C + rule C.count >= Y           because "<gen>"   (Y an integer field; Y's VALUE is the required count)
field C as coll of T maxcount Y ⇝ field C + rule C.count <= Y
```

Numeric (`min`/`max`): the synthetic rule's condition is `TypedBinaryOp(TypedFieldRef X, op, TypedFieldRef Y)` — exactly the bare-field-ref shape `TryGetRelationalFact` recognizes. **No further proof wiring** for the *dependent-op* discharge; the *default-containment* enforcement rides BUG-027's rule-vs-default fold (S2). Length/count: the synthetic rule's condition has a projection on the subject side (`X.length`/`C.count`) against an integer field `Y`; it does NOT enter `TryGetRelationalFact` and instead drives the band-relational requirement (S3), whose band edge resolves from `Y`'s **`NumericInterval`** (its declared *value* bounds), not `Y`'s length/count.

**Type-validity (the bound's value type).** `minlength`/`maxlength`/`mincount`/`maxcount` require their value to be a **non-negative integer** (`TypeChecker.Validation.Modifiers.cs:573/594`). A field-reference bound therefore requires `Y` to be an **integer** field; `minlength Y` with `Y as string` (or any non-integer type) is a **type error** — a string is not a valid integer length/count value. (The numeric `min`/`max` families inherit the comparison's §3.6 lane rules instead — Decision 5 / D5.)

**Where it lives (Decision 1).** The desugar happens at the field-stamp boundary in the type checker (`TypeChecker.cs` field construction / `TypeChecker.Validation.Modifiers.cs`), where the bound value is already being inspected. A field-reference bound is detected (the modifier value is an `IdentifierExpression`, not a literal/typed-constant), the referenced name is resolved against the field table (emitting a name-resolution diagnostic if absent — the BUG-020 binder half), and a synthetic `TypedRule` is appended to `ctx.Rules` carrying the modifier span. The scalar band stamp (`DeclaredMinLength` etc.) is left `null` for a field-reference bound (it has no magnitude), so the literal path is byte-identical.

### S2 — Numeric: 2c-i reuse for dependent ops; BUG-027 rule-vs-default fold for defaults

A numeric field-reference bound's synthetic `rule X >= Y` is a bare-field-ref relation. It has **two** distinct enforcement obligations with **two distinct discharge mechanisms**:

**(a) Dependent-op discharge — pure 2c-i reuse (unchanged, proven).** For a fault-prone op over `X` (a divisor/range, e.g. `100/X`), the 2c-i core already:
- collects the rule as a `FieldToFieldConstraint` (`CollectRelationalFacts`/`TryGetRelationalFact`), dropping it if `Y` is the same field (self-ref, vacuous) or the rule is blocked;
- narrows `X` from `Y`'s non-relational interval (`RelationalHalfLine` into `narrowed[X]`, depth-1);
- rejects when the narrowing contradicts `X`'s own declared bounds (`RelationContradictsSubjectBounds` — empty intersection);
- identity-degrades when `Y` is unbounded in the relevant direction (the half-line's sentinel edge makes `Intersect` the identity → `X` gains nothing → the dependent obligation stays unresolved → rejects).

**PROBE-CONFIRMED at the discharge level**: an explicit `rule X >= Floor` (Floor bounded) already discharges a dependent `100/X` divisor today (2c-i shipped). This half needs only the desugar (S1) — no new discharge path.

**(b) Default-containment enforcement — BUG-027's rule-vs-default fold (the corrected mechanism).** The headline BUG-020 case is `field Floor as number default 10` + `field Amount as number min Floor default 5`: the default configuration (`Amount=5`, `Floor=10`) violates `Amount >= Floor` and MUST reject (Principle 11). The mechanism is **NOT** "default ∈ X's narrowed interval" — that is unsound: when `Floor` is unbounded the narrowing identity-degrades, so `Amount`'s narrowed interval has no lower bound and "default 5 ∈ narrowed interval" is trivially clean (it never rejects). And in the headline case `Floor` carries only a `default`, not a `min`, so it is unbounded for narrowing purposes regardless — the narrowed-interval route cannot reject the headline at all.

The correct mechanism is spec **Principle 11**: a rule evaluated against default field values. The desugared `rule Amount >= Floor` is folded against the default environment (`Amount=5`, `Floor=10` ⟹ `5 >= 10` is false ⟹ reject). This does **not** depend on `Floor` being bounded — it reads `Floor`'s *default value* (10), not its narrowed interval. Global rules are **not** folded against defaults today: `CheckInitialStateSatisfiability` (`ProofEngine.Analysis.cs:47-113`) ConstantFolds only initial-state **ensure** conditions against defaults; global `semantics.Rules` are walked for sub-expression obligations but their *truth* is never evaluated against the default environment. That capability is **BUG-027** (`ScanRulesAgainstDefaults`, the ensure-fold extended to unguarded global rules) — a now-explicit **prerequisite** for this numeric default enforcement. Because the synthetic `rule X op Y` lands in `semantics.Rules` (Decision 1), once BUG-027 folds global rules against defaults the field-reference bound's default violation rejects for free — no field-reference-bound-specific default check is added; it rides the general fold.

So the numeric work is desugar (S1) + (for defaults) gating on BUG-027's rule-vs-default fold; (for dependent ops) the proven 2c-i reuse. **No narrowed-interval default check.**

### S3 — Length/count: the band-relational requirement (the new mechanism)

The length and count requirements carry their bound as a **scalar** band (`int? DeclaredMinLength` / `int? DeclaredMinCount`). A field-reference bound makes one edge of the band relational. The mechanism:

**Requirement extension.** `LengthContainmentProofRequirement` and `CountContainmentProofRequirement` gain a relational band-edge: an optional referenced-field reference per direction (e.g. `string? MinLengthRefField`, `string? MaxLengthRefField` on the length requirement; `string? MinCountRefField`, `string? MaxCountRefField` on the count requirement). When a field-reference bound is declared, the scalar edge is `null` and the relational edge names the referenced field. (Per CLAUDE.md DU discipline this is a *band-edge source* — a scalar OR a field-reference — and is modeled as a small `LengthBandEdge` / `CountBandEdge` DU `{ Scalar(int) | FieldRef(string) | Unbounded }` rather than parallel nullable fields, so the discharge switches on the *subtype shape*, not on a nullable-field combination.)

**Discharge-time band resolution.** `TryLengthContainmentProof` / `TryCountContainmentProof` gain `SemanticIndex` access (the count proof takes none today — it must) so that, for a relational band edge, they resolve the referenced **integer** field `Y`'s **value** interval — `Y`'s required-length/required-count value, NOT `Y`'s own length/count:
- length: resolve `⟦Y⟧` = `ExtractFieldInterval(Y, semantics)` (`ProofEngine.Intervals.cs:202-220`) — `Y`'s declared `[min, max]` value bounds (plus the flag-modifier lower-bound fold). NOT `StringLengthIntervalOf(Y)` — `Y` is an integer field whose VALUE is the required length, so its length-as-a-string is irrelevant. `⟦Y⟧` is the interval of required-length *values* `Y` can take.
- count: resolve `⟦Y⟧` = `ExtractFieldInterval(Y, semantics)` — the integer field `Y`'s value `[min, max]`, the interval of required-count values `Y` can take.

The relational band edge resolves to: for a `minlength Y` / `mincount Y` (lower edge), the *ceiling* of `⟦Y⟧` — the **maximum** required length/count value `Y` can hold (`Y`'s declared `max`, or +∞ if `Y` is unbounded above); for a `maxlength Y` / `maxcount Y` (upper edge), the *floor* of `⟦Y⟧` — the **minimum** required-max value `Y` can hold (`Y`'s declared `min`, or 0 if unbounded below). The soundness direction is load-bearing and is stated precisely in S3-soundness below.

**S3-soundness (the load-bearing direction rule).** A field-reference band edge must use the referenced field's **value** bound in the direction that makes the proof sound for *every* value the referenced field can take, exactly as numeric `R-NARROW` reads `Y`'s relevant declared edge:

```
minlength Y   (X.length >= Y must hold for all values Y can take):
    the required minimum length for X is Y's MAXIMUM possible VALUE (Y's declared max).
    If Y has no max, the required minimum is +∞ → identity-degrades to UNPROVABLE → reject.
maxlength Y   (X.length <= Y must hold for all values Y can take):
    the allowed maximum length for X is Y's MINIMUM possible VALUE (Y's declared min, or 0 if unbounded below).
    If Y has min 0 (unbounded below), the allowed maximum is 0 → only the empty string proves; otherwise reject.
mincount Y / maxcount Y: symmetric on the count band, reading Y's value interval ⟦Y⟧.
```

This mirrors numeric R-NARROW-GE/LE exactly: `rule X >= Y` narrows `X`'s lower bound to `Y`'s lower bound `ylo`; here the *minimum required length* of `X` is read from `Y`'s value interval `⟦Y⟧`, BUT because the assigned-value-vs-band check is "the assigned value's length interval ⊆ [requiredMin, allowedMax]", the *requiredMin* edge that the assigned value must clear must be the **most demanding** value `Y` can impose. For `X.length >= Y` to hold universally over all values `Y` can take, `X.length` must be ≥ `max(⟦Y⟧)` — `Y`'s maximum value. (Identical to how numeric `X >= Y` with `Y ∈ [ylo,yhi]` only proves `X >= ylo`, the *weakest* lower bound — but the length band check is the dual: it proves the *assigned value* meets the band, so it needs the *strongest* requirement. The implementation MUST verify this dual against the 2c-i numeric reuse so the two domains do not silently use opposite edges. This is the single most adversarial point in the design — see Falsifiers.)

> **Resolution of the dual (locked).** The two domains read *different edges* of the *same field-value interval* `⟦Y⟧` for a *consistent reason*: numeric narrowing produces the subject's *provable* interval (weakest sound bound → `ylo`); length/count produces the *requirement* the assigned value must satisfy (strongest sound requirement → `Y`'s max value for a `>=`/`minlength`/`mincount` band edge). Both read `Y`'s value interval (`ExtractFieldInterval`); they differ only in which *edge* of it they take, and both are the §0.6-philosophy-1 sound direction in their own architecture. The build's failing-test matrix MUST include a case where the two edges differ and assert each domain rejects the genuinely-unprovable case and clears the genuinely-provable one; a green claim without this cross-domain edge test is not accepted.

**Empty-intersection contradiction guard (preserved from 2c-i).** When the relational band edge contradicts `X`'s *own* declared band — `minlength Y` resolves a required-min (= `Y`'s max value) above `X`'s own declared `maxlength` (no length is simultaneously `>= requiredMin` and `<= X.maxlength`) — the band is empty (⊥). Per the contradiction-reject amendment, an empty band is a *proven contradiction*, not a vacuous pass: the requirement contributes no discharge and the dependent obligation rejects at the requirement's own Error (`LengthBoundViolation`/`CountBoundViolation`). The length/count discharge readers must NOT treat an empty band as "everything proves" (the `Contains(⊥)=>true` over-prove vector the numeric amendment closed must not reopen in the integer band domain): an empty resolved band returns `false`/unresolved.

**Identity-degradation (preserved from 2c-i).** When the referenced integer field is unbounded in the demanded direction (`minlength Y` with `Y` having no declared `max` value), the resolved required edge is `+∞` → no assigned value can be proved to clear it → the obligation stays unresolved → rejects. This is the never-over-prove floor: an unbounded reference contributes nothing, exactly as a numeric unbounded `Y` does.

### S4 — Reduction rules (the discharge)

```
  minlength Y on X declared, Y an integer field, Y resolves, X≠Y (self vacuous, dropped at desugar)
  reqMin = ceiling(⟦Y⟧)   (Y's declared max VALUE; +∞ if Y unbounded above)
  reqMin ⊓ ⟦X.length⟧-declared = ∅          (empty — proven contradiction)
  ─────────────────────────────────────────────────────────────────────── (L-CONTRA)
        the bound contributes no discharge; the length obligation rejects at LengthBoundViolation

  minlength Y on X, reqMin finite, assigned value's length interval [vmin, vmax]
  vmin >= reqMin                                                            (provable)
  ─────────────────────────────────────────────────────────────────────── (L-DISCHARGE)
        the length obligation discharges

  minlength Y on X, reqMin = +∞ (Y unbounded above)  OR  vmin < reqMin (unprovable)
  ─────────────────────────────────────────────────────────────────────── (L-REJECT)
        the obligation stays unresolved → LengthBoundViolation emits (rich message, S5)
```

where `⟦Y⟧ = ExtractFieldInterval(Y)` is `Y`'s declared *value* interval (`Y` an integer field), NOT `Y`'s own length. `maxlength`/`mincount`/`maxcount` are the dual/count analogues (reading the opposite edge of `⟦Y⟧`). Self-reference is moot at the type level — `minlength X` on a string `X` references `X` itself, but `minlength` requires an integer value and a string `X` is a type error (S1 type-validity); for a numeric self-reference (`min X` on `X`) the desugar produces `X >= X`, vacuous, dropped at desugar (no requirement edge produced), so it neither rejects nor hangs (mirrors §3.5 line 1352). Mutual reference between two integer fields used as length bounds reads each *other* field's *non-relational* declared value interval (depth-1, no re-entry), so it terminates.

### S5 — Proof obligations and the rich message

- Numeric: reuses `IntervalContainmentProofRequirement` (computed/set sites) for *dependent-op* discharge (2c-i path) — no new requirement kind. The *default-containment* enforcement does NOT add a field-reference-bound-specific obligation reading a narrowed interval; it rides **BUG-027's rule-vs-default fold** (the desugared `rule X op Y` evaluated against the default environment — `5 >= Floor`'s default `10` → false → reject; S2). The literal `min`/`max` default OutOfRange obligation is unchanged; the field-reference default rejection comes from the general global-rule-vs-default fold, not a narrowed-interval read.
- Length: `LengthContainmentProofRequirement` gains the band-edge DU (S3); `ProofRequirementKind.LengthContainment` and `DiagnosticCode.LengthBoundViolation` (PRE0135) unchanged.
- Count: `CountContainmentProofRequirement` gains the band-edge DU; `CountBoundViolation` (PRE0136) unchanged.

**Rich message composition.** The message is composed from (the unprovable obligation) + (the modifier span — so it points at `min Floor`/`minlength MinCodeLength`) + (the referenced field's value-boundedness in the relevant direction — for numeric "`Floor` has no declared lower bound"; for length/count the referenced **integer** field's missing value bound, e.g. "`MinCodeLength` has no declared maximum value" — because the required length is `MinCodeLength`'s maximum *value*, not its length). It reuses the existing diagnostic codes (no new code): numeric default → `OutOfRange` (PRE0079); numeric computed/set → `NumericOverflow` (PRE0078); length → `LengthBoundViolation` (PRE0135); count → `CountBoundViolation` (PRE0136); a dependent divisor over a field-reference-bounded field → `DivisionByZero` (PRE0083) via the 2c-i path. The *attribution* (which referenced field, which direction of its *value* is unbounded) rides the existing related-diagnostic / message-arg surface — no new code, structured for hover (§0.6 item 6), never parsed from prose. (Note the length/count message names an **integer reference field** and its missing *value* bound — a consequence of correction ②; it must not say "no declared minimum length" of the referenced field.)

### S6 — Soundness preservation claim (named, per-axis)

Principles threatened: **1** (prevention), **7**, **10**, **11**.

- **Numeric — inherited sound.** The numeric family adds no discharge logic. The *dependent-op* half reuses 2c-i's `RelationalHalfLine` (strict-weakening sound), `RelationContradictsSubjectBounds` (empty → reject), and identity-degradation (unbounded → no narrowing). The *default-containment* half rides BUG-027's rule-vs-default fold: the desugared `rule X op Y` is evaluated against the default environment, which strictly *adds* a rejection where today there is none (the bound was inert) and can never remove one — and, unlike a narrowed-interval check, it rejects the headline case even when `Y` is unbounded (it reads `Y`'s *default value*, not its narrowed interval). Principles 1/10/11 hold by inheritance (and gate on BUG-027 for the default half).
- **Length/count — never over-prove (Principle 1).** The relational band edge resolves to the *most-demanding* sound edge of the referenced integer field's **value** interval (S3-soundness): `requiredMin = Y`'s maximum *value*, `allowedMax = Y`'s minimum *value*. The assigned value's length/count interval must clear the demanded edge for *every* value `Y` can take, so a discharge is sound for all `Y`. An unbounded reference resolves to `+∞`/`0` → unprovable → reject (identity-degradation). An empty band (relational edge contradicts `X`'s own declared band) returns `false`, never `Contains(⊥)=>true` (the contradiction guard, re-imposed in the integer band domain). No false "safe."
- **Length/count — no false rejection / no under-enforce (Principle 11).** The requirement is emitted *unconditionally* for a field-reference bound (Obligation Generation Contract, `proof-engine.md:495-507`) — a desugared length/count bound is never silently dropped (the exact hole this slice closes). Discharge returns `true` only when provable; a literal bound is byte-identical (the scalar edge path is unchanged). The length/count satisfiability scans are not involved (length/count have no `ExtractFieldInterval` satisfiability dependency — the Decision-4 isolation hazard is numeric-only), so no false rejection is introduced.
- **Determinism / depth-1 (Principle 3, §0.4).** The band-edge resolution reads the referenced field's *non-relational* declared band one hop (no re-entry into a relationally-narrowed band), so it is single-pass and terminating; self/mutual references terminate by construction.

## Architecture Grounding

### Precept-internal placement

**Layer placement.** Two layers, matching the parent design's emission/discharge split:
1. *Desugar + emission* (type checker — `TypeChecker.cs` field stamp / `TypeChecker.Validation.Modifiers.cs`): detect the field-reference bound, resolve the referenced name (BUG-020 binder fix), append the synthetic `TypedRule`, and stamp the obligation with the relational band edge instead of dropping the bound. This is metadata-driven (the modifier↔rule equivalence is §2.4 catalog truth; the desugar is the mechanical rewrite, no per-modifier-kind behavior switch).
2. *Discharge* (proof engine): numeric reuses the 2c-i relational path unchanged; length/count extend `TryLengthContainmentProof`/`TryCountContainmentProof` to resolve a relational band edge. This belongs in pipeline code (reasoning over catalog-declared obligations), exactly where Strategy 9/10 already sit.

The CLAUDE.md catalog rules are honored: no enum-identity dispatch (the band-edge is a DU subtype — `Scalar | FieldRef | Unbounded` — switched on shape, not a `ModifierKind` switch); the band-edge DU follows "use DUs for varying shapes, don't paper over with nullable fields"; the synthetic rule is the §2.4 desugar, not a parallel modifier-knowledge encoding.

**Cross-component propagation:**
- **Runtime (parser, type checker, evaluator, diagnostics):** Parser — **None** (the field-reference bound already parses as an `IdentifierExpression` modifier value). Type checker — the desugar + name resolution + relational-band-edge stamp; `TryGetComparableModifierValue` gains a field-reference arm that routes to the desugar (instead of returning `null`). Proof engine — numeric dependent-op: **None** (pure 2c-i reuse); numeric default-containment: **rides BUG-027** (the rule-vs-default fold in `CheckInitialStateSatisfiability` / `ScanRulesAgainstDefaults`, `ProofEngine.Analysis.cs`) — this slice adds no numeric default-check of its own, the synthetic rule in `semantics.Rules` is folded by BUG-027's general extension; length/count: the band-relational discharge extension (resolving the referenced integer field's value interval). Evaluator — **None** (governance + the existing length/count fault traps enforce at runtime; §0.7). Diagnostics — `LengthBoundViolation`/`CountBoundViolation`/`OutOfRange`/`NumericOverflow` become reachable for the field-reference bound case (richer attribution); BUG-020's undeclared-name case gains a name-resolution diagnostic (reuse `PRE0029`/the existing unresolved-field-reference code).
- **Tooling (highlighting, completions, hover, semantic tokens):** Hover/proof-attribution gains the referenced-field provenance for a field-reference bound (the obligation cites the referenced field). No grammar/token/completion change. The field-reference identifier in a bound position should resolve for go-to-definition (it now binds) — a latent tooling improvement, not required for the soundness fix.
- **MCP (vocabulary, DTOs, tool output):** The length/count obligation DTO projection gains the relational band edge if the DTO surfaces `DeclaredMinLength`/etc. — **check `CompileToolDtos.cs`**: today it projects scalar length/count bounds; a field-reference bound must project as a referenced-field reference (or the obligation description string already carries it). No new tool, no vocabulary change. The numeric path is unaffected (it reuses the relational fact, which is private to the proof engine — 2c-i Decision 1).

**Breaking changes.** None to public contract. No new diagnostic code, no keyword/modifier, no catalog rename. `LengthContainmentProofRequirement`/`CountContainmentProofRequirement` gain a band-edge field — a *DTO-internal* shape change (the records are constructed in the pipeline; the MCP projection must be checked). A program that *previously compiled* because a field-reference bound was silently inert may now correctly fail to compile — the intended soundness fix (BUG-020 enforcement half), the §0.7 soundness tax, not a guarantee breaking-change (the prior behavior was the guarantee *violation*).

### External architectural precedent

The architectural problem: *a declared bound references another field; how does the requirement carry and discharge a band edge that is not a compile-time constant but another field's bound, without a general solver?* The numeric half is answered by the octagon/DBM relation-as-fact (taken from `relational-constraint-representation-survey.md` via 2c-i). The length/count half — a band edge sourced from another field's band — has its closest comparator in **CUE's struct field references in constraints**:

> CUE permits a field's constraint to reference another field (`b: >=a`); the reference is resolved by unifying against the referent's value, and an unresolvable/contradictory reference yields ⊥ (bottom), which propagates as an error rather than a vacuous success. (CUE spec, "References" / "Bottom"; https://cuelang.org/docs/references/spec/ — accessed 2026-06-04.)

**What Precept takes:** the "constraint references another field, resolve against the referent's declared bound, contradiction → ⊥ → error (not vacuous success)" model — exactly the empty-band-rejects rule (S3, L-CONTRA). **What Precept deliberately diverges from:** CUE resolves to a *fixpoint* over the whole struct (a reference chain `c: >=b`, `b: >=a` propagates `a`'s bound to `c`); Precept reads the referenced field's *non-relational* band one hop (depth-1, §0.4) — `minlength Y` reads `Y`'s declared length band, never `Y`'s relationally-narrowed band. The divergence buys termination and a per-bound witness at the cost of completeness (a transitively-bounded reference will not prove), the standard Precept trade, identical to the numeric divergence the 2c-i core already defended.

**Precept-specific novelty (acknowledged, warranted).** Mainstream relational domains carry one closed structure for numeric *and* "length/count"-style derived quantities; Precept's length and count discharge are a *separate* prove-or-reject band-containment architecture (Strategy 9/10) distinct from the numeric `narrowed`-interval architecture (Strategy 8). Making the length/count *band edge* relational — rather than forcing length/count through the numeric relational path — is the warranted divergence: it keeps each family's discharge in its own established architecture (numeric narrows a subject interval; length/count check a value interval against a band), and re-imposes the universal ⊥-is-infeasible rule (the contradiction guard) in the integer band domain. The alternative (lower `X.length`/`C.count` to numeric facts and route through the numeric relational path) is enumerated and rejected in Decision 3 — it would require the projection (`.length`/`.count`) to become a first-class numeric subject in the relational fact store, a far larger and more speculative change than extending the band edge the length/count requirement already carries.

## Decisions

### Decision 1: Desugar each field-reference bound to a synthetic span-tagged `TypedRule` at the field-stamp boundary; resolve the referenced name there (closing the BUG-020 binder half); leave the scalar band edge null

**Stakes**: medium

- **Rationale**: §2.4 lines 1133-1138 lock the modifier↔rule equivalence and "participate in compile-time proof identically to the equivalent rule" — the desugar is implementation against that locked spec, not a fresh choice. The numeric reuse PROOF (S2) only works because the desugared form is the exact bare-field-ref shape `TryGetRelationalFact` recognizes; producing the synthetic `TypedRule` is what makes the existing relational path apply with zero new wiring. Doing it at the field-stamp boundary is where the bound value is already inspected (`TryGetComparableModifierValue`) and where the referenced name must resolve — so the BUG-020 binder half (undeclared `min Nonexistent` swallowed today, `TypeChecker.Validation.Modifiers.cs:462-480` returns `null` and the null is dropped) closes in the same pass: a field-reference that resolves to no field emits the unresolved-field-reference diagnostic. Span-tagging the synthetic rule to the modifier is required so the rich message (Decision 4) points at `min Floor`, not a phantom rule the author never wrote.
- **Tradeoff accepted**: A synthetic `TypedRule` enters `ctx.Rules` that the author did not write — it must NOT surface in author-facing rule listings as a real rule, and its generated `because` is generic. Accept a synthetic-rule tag (or a desugar-origin marker on the rule) so tooling/diagnostics can distinguish it; the parent design already accepts the generated-rationale tradeoff (§2.4).
- **Alternatives considered**:
  - *(A) Special-case each modifier kind in the proof engine* (the proof engine learns "a `min` with a field-ref value means narrow from that field") — rejected: re-encodes the §2.4 modifier↔rule equivalence in the proof engine as per-`ModifierKind` behavior, the CLAUDE.md "never switch on `*Kind` to dispatch per-member behavior" violation; and forks the numeric path away from the rule-sourced relational path it could reuse for free.
  - *(B) Desugar to a `TypedRule` (chosen)* — the §2.4 model; numeric reuses the relational path with zero wiring; the binder fix lands in the same pass.
  - *(C) Stamp a relational band edge for ALL families (numeric too) without a synthetic rule* — rejected for numeric: numeric already has a working rule-sourced relational path (2c-i); routing numeric through a new band-edge requirement would duplicate it and discard the contradiction-guard/sign-fold machinery 2c-i built. (The band-edge IS used for length/count — Decision 3 — because they have no equivalent relational path.)
- **Precedent**: GHC's desugaring pass (surface sugar → core before analysis); §2.4 line 1133 ("desugars to the equivalent rule"); 2c-i's `CollectRelationalFacts` consuming `semantics.Rules` (the synthetic rule lands in exactly the stream 2c-i reads).
- **Sources consulted for this decision**: `precept-language-spec.md §2.4` lines 1133-1138 (modifier desugars to rule; participates identically); `§3.5` line 1352 (modifier-value scope = all field names, self vacuous, mutual satisfiable); `TypeChecker.Normalization.cs:86-121` (PopulateRules handles only explicit rule constructs — the synthetic rule must be appended somewhere; the field-stamp is the natural site); `TypeChecker.Validation.Modifiers.cs:462-480` (TryGetComparableModifierValue literal-only, returns null for a field-ref → dropped, the BUG-020 root); `ProofEngine.Composition.cs:205-241` (CollectRelationalFacts reads semantics.Rules; TryGetRelationalFact recognizes bare-field-ref `X op Y`). Grepped §2.4/§3.5 — the desugar is spec-locked; this is implementation against it (the *where/how* of the synthetic rule and the binder-fix coupling is the genuine design content).

### Decision 2: The numeric `min`/`max` family — 2c-i reuse for the dependent-op half; BUG-027's rule-vs-default fold for the default-containment half; no new numeric discharge

**Stakes**: high (the default-containment half is the headline BUG-020 case, and the original narrowed-interval mechanism was unsound — it could not reject the headline; the corrected mechanism carries an external dependency on BUG-027)

- **Rationale**: A numeric field-reference bound desugars to `rule X >= Y` (bare field refs). It has two enforcement obligations with two discharge mechanisms. (a) *Dependent-op* (a divisor/range over `X`): 2c-i already collects, narrows, contradiction-checks, and identity-degrades the synthetic rule — PROBE-CONFIRMED that an explicit `rule X >= Floor` (Floor bounded) discharges a dependent `100/X` today, so this half is shipped and needs only the desugar (Decision 1). (b) *Default-containment* (the headline `Amount min Floor default 5` with `Floor default 10`): the rejection comes from spec **Principle 11** — the desugared `rule Amount >= Floor` folded against default field values (`5 >= 10` is false → reject). It is NOT a narrowed-interval check: narrowing identity-degrades when `Floor` is unbounded (and in the headline `Floor` has only a `default`, no `min`, so it is unbounded for narrowing) → `Amount`'s narrowed interval gains no lower bound → "default 5 ∈ narrowed interval" is trivially clean and never rejects. Global rules are not folded against defaults today; **BUG-027** builds that fold (`ScanRulesAgainstDefaults`, extending `CheckInitialStateSatisfiability`'s ensure-fold to unguarded global rules). Because the synthetic `rule X op Y` lands in `semantics.Rules`, once BUG-027 lands the field-reference default rejection comes for free — no field-reference-specific default check. This avoids forking a numeric discharge path and inherits both 2c-i's soundness spine (dependent ops) and the general Principle-11 fold (defaults).
- **Tradeoff accepted**: The numeric family's *dependent-op* reach is exactly 2c-i's reach (depth-1, no transitive chains); an author with a transitively-bounded reference gets friction. The *default-containment* half **gates on BUG-027** — this slice's numeric default enforcement cannot ship until BUG-027's rule-vs-default fold exists. Accept the external dependency: BUG-027 is an independent Principle-11 soundness gap that must be closed regardless, and routing the field-reference default through it (rather than a bespoke narrowed-interval check) is both sound and the smaller change.
- **Alternatives considered**:
  - *(A) A new numeric band-edge requirement (mirroring length/count)* — rejected: numeric already has the relational narrowing path for dependent ops; a parallel band-edge would duplicate it and lose the sign-fold / subtraction-divisor discharge 2c-i built.
  - *(B-orig) Reuse 2c-i + stamp the OutOfRange default obligation against X's narrowed interval* — **rejected (the original, now-corrected mechanism)**: unsound for the headline. When the referenced field is unbounded (the exact headline shape — `Floor` with only a default), the narrowing identity-degrades and the default check is trivially clean. It cannot reject the BUG-020 headline it was meant to fix. Confirmed by the adversarial review and recorded in BUG-027.
  - *(B-corrected) Reuse 2c-i for dependent ops; route default-containment through BUG-027's rule-vs-default fold (chosen)* — minimal, sound for the headline (reads `Floor`'s default value, not its narrowed interval), and reuses a fold BUG-027 must build anyway.
- **Precedent**: 2c-i `relational-narrowing-core-design-2026-06-03.md` (the shipped numeric relational path for dependent ops); the existing ensure-vs-default fold in `CheckInitialStateSatisfiability` (the machinery BUG-027 extends to global rules); spec §0.1 Principle 11 / §0.6 item 11 ("rules checked against defaults").
- **Sources consulted for this decision**: `relational-narrowing-core-design-2026-06-03.md` (CollectRelationalFacts / RelationalHalfLine / depth-1); `relational-contradiction-reject-2026-06-04.md` (RelationContradictsSubjectBounds); `ProofEngine.Composition.cs:229` (TryGetRelationalFact requires bare TypedFieldRef — the desugared numeric form matches); `ProofEngine.Analysis.cs:47-113` (CheckInitialStateSatisfiability folds ENSURES against defaults at :113, NOT global rules — the BUG-027 gap); `bugs.md` BUG-027 (the rule-vs-default fold; explicit prerequisite, and records the narrowed-interval route as unsound); `precept_compile` NumProbe (field-ref `min Floor` inert today). Grepped §0.6 items 1/2/6/11 — numeric interval + relational + assignment-range-impossibility + rules-vs-defaults are the locked obligations; this is implementation against them.
- **Strongest counter-evidence**: A reviewer could expect the default-containment to reuse the *same* narrowed-interval machinery the dependent-op discharge uses (one mechanism for both), and reading a different mechanism (the rule-vs-default fold) for the default half could look like an inconsistency. Response: the two are *different proof questions* — the dependent-op asks "is `X` provably nonzero/in-range across its whole admissible interval" (a narrowing question, answered by 2c-i), while the default-containment asks "does the *specific default configuration* satisfy the rule" (a constant-fold-against-defaults question, answered by Principle 11). The narrowed-interval mechanism is *unsound* for the latter (it cannot reject the unbounded-reference headline), which is precisely why the original design's choice was wrong and the review flagged it. The mechanisms differ because the questions differ; both are sound in their own lane. The build's failing-test matrix MUST include the headline `Floor default 10` + `Amount min Floor default 5` rejecting *via the rule-vs-default fold* (not a narrowed read) as the standing guard.
- **Reversibility**: Medium. The desugar (Decision 1) is shared and reversible; the default-containment routing is just "the synthetic rule is in `semantics.Rules`, BUG-027 folds it" — no field-reference-specific default code to revert. The hard external coupling is the **BUG-027 prerequisite**: if BUG-027 is descoped, the numeric default-containment half cannot ship (the dependent-op half still can). Pre-release, no external author depends on the current inert behavior.
- **Blast radius**: For the dependent-op half — none beyond Decision 1 (pure 2c-i reuse). For the default-containment half — entirely within BUG-027's surface (`CheckInitialStateSatisfiability` / `ScanRulesAgainstDefaults` in `ProofEngine.Analysis.cs`); this slice adds *no* numeric default-check code of its own. The synthetic rule entering `semantics.Rules` (Decision 1) means BUG-027's general fold covers the field-reference default for free. No new diagnostic code (the fold emits the existing default-violates-rule diagnostic).

### Decision 3: Length/count carry the bound as a relational band-edge DU resolved at discharge — NOT lowered into the numeric relational path

**Stakes**: high (the load-bearing new mechanism; a wrong call either under-enforces — a desugared length/count bound silently ignored, the exact soundness hole — or over-proves a false length/count "safe," a runtime fault)

- **Rationale**: `X.length op Y` / `C.count op Y` cannot enter the numeric relational path (`TryGetRelationalFact` requires bare `TypedFieldRef` both sides; `ProofEngine.Composition.cs:229`), and the length/count discharge architecture is fundamentally different — it checks an assigned value's length/count interval against a *band*, not a subject's narrowed interval. The minimal sound change is to make the *band edge* relational: the length/count requirement carries, per direction, a band edge that is a scalar OR a referenced (integer) field; at discharge the referenced field's **value** interval (`ExtractFieldInterval`) is resolved (one hop, S3-soundness direction — `Y` is an integer field whose VALUE is the required length/count, so the band edge reads `Y`'s value interval, NOT `Y`'s own length/count), with the empty-intersection contradiction guard and identity-degradation re-imposed in the integer band domain. This keeps each family in its established architecture and re-uses the contradiction/identity discipline 2c-i locked, rather than forcing a projection (`.length`/`.count`) to become a first-class relational-fact subject. The band-edge is a DU (`Scalar | FieldRef | Unbounded`), honoring the CLAUDE.md DU-over-nullable rule.
- **Tradeoff accepted**: The length/count requirement records change shape (the `int?` band becomes a band-edge DU), touching the requirement construction, the discharge readers, and the MCP projection. Accept the localized shape change over either (a) under-enforcing (drop the bound — the current soundness hole) or (b) the much larger change of making `.length`/`.count` numeric relational subjects. The count discharge must also gain `SemanticIndex` (it takes none today) to resolve the referenced field — a signature change confined to the proof engine.
- **Alternatives considered**:
  - *(A) Lower `X.length`/`C.count` to numeric facts and route through the numeric relational path* — rejected: requires the projection accessor to become a first-class numeric subject in the `FieldToFieldConstraint` store (today field-only), a far larger and more speculative change; and the length/count discharge is value-vs-band, not subject-narrowing, so the numeric path's output (a narrowed subject interval) does not match the length/count discharge's input (a band to check a value against).
  - *(B) Band-edge DU on the length/count requirement, resolved at discharge (chosen)* — localized to length/count, reuses the contradiction/identity discipline, keeps each family's architecture.
  - *(C) Bake the referenced field's band into a scalar at stamp time* — rejected: it captures the referenced field's band at *declaration*, but the spec scope (§3.5 line 1352) allows referencing a field declared *later*, and the contradiction/identity semantics need the resolved band at discharge against the *assigned value*; a stamp-time scalar cannot express "unbounded → reject" vs "empty → reject" distinctly and would silently lose the relation.
  - *(D) Drop length/count field-reference bounds (reject the form)* — rejected: contradicts §2.4 (the modifier family explicitly includes minlength/maxlength/mincount/maxcount) and §3.5 line 1352; a Tier-3 override with no owner authorization.
- **Precedent**: CUE field-reference constraints with ⊥-on-contradiction (External precedent); 2c-i's `RelationContradictsSubjectBounds` (the empty → reject discipline, re-imposed here in the band domain); the existing length/count prove-or-reject readers (`TryLengthContainmentProof`/`TryCountContainmentProof`) which already discharge against a scalar band — this extends the band, not the discharge skeleton.
- **Sources consulted for this decision**: `ProofEngine.Composition.cs:229` (TryGetRelationalFact requires bare TypedFieldRef — length/count projection excluded); `ProofEngine.Lengths.cs:25-46` (TryLengthContainmentProof reads scalar req.DeclaredMinLength; StringLengthIntervalOf takes no narrowed dict — no seam today); `ProofEngine.Lengths.cs:333-350` (TryCountContainmentProof reads scalar req.DeclaredMinCount, takes no SemanticIndex); `ProofRequirement.cs:206-235` (the scalar `int?` band records); `Types.cs:172-173` (CollectionCountAccessor returns Integer — `.count` is a member access); `ProofEngine.Intervals.cs:202-220` (ExtractFieldInterval reads a field's value `NumericInterval` — the correct source for `⟦Y⟧`, since `Y` is an integer field whose VALUE is the required length/count, per `Modifiers.cs:165-223` / `TypeChecker.Validation.Modifiers.cs:573/594`; NOT `StringLengthIntervalOf(Y)`, which reads `Y`'s own length-as-a-string and is the wrong source); `relational-contradiction-reject-2026-06-04.md` (the empty=reject discipline to re-impose); `precept_compile` LenProbe/CntProbe2 (field-ref length/count bounds inert today). Grepped §0.6 item 6 (assignment-range impossibility = compile-time error — covers the length/count band axis); §2.4 (minlength/maxlength/mincount/maxcount are bound modifiers). Spec is silent on the *concrete discharge mechanism* (§0.7 line 270 defers mechanism to compiler-and-runtime-design.md) — this is a genuine mechanism decision.
- **Strongest counter-evidence**: The S3-soundness *edge direction* (a `minlength Y` band edge resolves to `Y`'s *maximum* value, not its minimum) is the inverse of the numeric narrowing edge (`rule X >= Y` narrows `X`'s lower bound to `Y`'s *lower* bound) — both reading the same field-value interval `⟦Y⟧` (`ExtractFieldInterval`) but taking opposite edges — a reviewer could read this as an inconsistency that signals a bug. Response: the two read different edges of `⟦Y⟧` for a *consistent* reason — numeric narrowing produces the subject's *provable* interval (weakest sound bound), while length/count produces the *requirement the assigned value must meet for all values of Y* (strongest sound requirement); both are §0.6-philosophy-1's sound direction in their own architecture (S3-soundness, locked). The cross-domain edge test (Falsifiers / Inventory) is the standing guard that the two domains do not silently use the wrong edge — this is the single most adversarial point and is explicitly test-gated.
- **Reversibility**: Hard — the band-edge DU is a requirement-record shape change consumed by the discharge readers and the MCP projection; reverting means restoring the scalar `int?` and re-dropping the bound (the soundness hole). Pre-release, no external author depends on the current inert behavior.
- **Blast radius**: `ProofRequirement.cs` (band-edge DU), `ProofEngine.Lengths.cs` (both discharge readers + count gains SemanticIndex), `ProofEngine.Analysis.cs` (requirement construction), `ProofEngine.Diagnostics.cs` (message), `CompileToolDtos.cs` (projection check). No catalog member rename, no new diagnostic code, no keyword. Samples: any precept relying on an inert field-reference length/count bound newly-reds (the soundness tax) — triage per the corpus check.

### Decision 6: Self-reference is dropped at desugar (vacuous); mutual reference conjoins and terminates by depth-1 non-relational reads — all three families

**Stakes**: low

- **Rationale**: §3.5 line 1352 locks the semantics: self-reference is vacuous (`min X` ⟹ `X >= X`), mutual reference is satisfiable (`A min B` + `B min A` ⟹ `A == B`), "not a cycle." The desugar drops a self-referential synthetic rule (numeric: `TryGetRelationalFact` already rejects same-field, `ProofEngine.Composition.cs:231-232`; length/count: the band edge naming the same field is vacuous and is not recorded). Mutual reference terminates because each band edge / relational fact reads the *other* field's *non-relational* declared band/interval one hop (depth-1, the 2c-i and S3 structural cap) — no re-entry, no fixpoint.

## Acceptance criteria

Per family (numeric / length / count), each demonstrated by a test:

- **Provable → clean.** A field-reference bound whose referenced field is bounded in the relevant direction, with an assigned/default value that clears it, **compiles clean**. (numeric: `Floor min 0`, `Amount min Floor`, `Amount` default ≥ Floor's floor; length: `MinLen as integer min 3 max 3`, `Name minlength MinLen` default length ≥ 3 — `MinLen` an integer field whose value is the required length; count: `Limit as integer`-bounded, `Tags mincount Limit` default count ≥ Limit's value-floor.)
- **Unprovable → reject with the rich message.** The same with the assigned/default value below the bound, or the referenced field unbounded in the demanded direction, **fails to compile** with a diagnostic that names the referenced field and offers a bound-or-guard repair (numeric → OutOfRange/NumericOverflow/DivisionByZero; length → LengthBoundViolation; count → CountBoundViolation). The headline BUG-020 regression: `Floor default 10` + `Amount min Floor default 5` **rejects via BUG-027's rule-vs-default fold** (the desugared `rule Amount >= Floor` evaluated against defaults: 5 ≥ 10 false — NOT a narrowed-interval check, which cannot reject this case; today clean).
- **Contradiction → reject.** A field-reference bound that contradicts the field's own declared band (numeric: `Amount max 5` + `min Floor`/`Floor min 10`; length: `Name maxlength 3` + `minlength MinLen`/`MinLen as integer min 10` — the required length 10 exceeds `Name`'s own maxlength 3) **rejects** — empty intersection, not a vacuous pass.
- **Unbounded-ref → reject.** A field-reference bound whose referenced field is unbounded in the demanded direction leaves the dependent/default obligation unresolved → **rejects** (identity-degradation, no false "safe").
- **Self / mutual → terminate.** `min X` (self, vacuous, dropped) and `A min B` + `B min A` (mutual, `A==B`) **compile and terminate** — no hang, no stack growth — all three families.
- **Cross-domain edge (the S3-dual adversarial test).** A numeric and a length bound that read the *same* referenced integer field's value interval `⟦Y⟧` but take *opposite* edges (numeric narrowing → `Y`'s min; length band → `Y`'s max): each **rejects** the genuinely-unprovable case and **clears** the provable case (proves the two domains do not silently use the wrong edge of `⟦Y⟧`).
- **Undeclared reference → name diagnostic.** `min Nonexistent` (no matching field) emits a name-resolution diagnostic (BUG-020 binder half), not silent acceptance.
- **Literal bounds byte-identical (regression).** A literal-bound-only precept (`min 5`, `minlength 3`, `mincount 2`) produces **byte-identical** obligations and diagnostics before/after — the field-reference path adds nothing to the literal path.
- **Full suite green** after sample remediation for any precept that newly fails (the soundness tax — triage each newly-red into "relied on an inert field-reference bound, add a real bound/guard" vs "reach gap").

## Falsifiers

- **Over-prove (Principle-1 falsifier, the most important).** If any precept with a field-reference length/count bound compiles clean and a runtime length/count fault (or a numeric fault for the numeric family) then fires on it, the band-edge S3-soundness direction or the identity-degradation is wrong — immediate redesign.
- **Under-enforce (the hole this slice closes).** If a desugared field-reference bound (any family) compiles clean while the assigned/default value provably violates it — i.e. the bound is still silently ignored — the desugar/emission did not wire (BUG-020 enforcement half not closed). The per-family "unprovable → reject" tests are the standing guard; the headline `Amount min Floor default 5` regression must reject.
- **Numeric default via the wrong mechanism (the corrected hole).** If the headline `Floor default 10` + `Amount min Floor default 5` is made to reject via a *narrowed-interval* default check rather than BUG-027's rule-vs-default fold, the mechanism is unsound: it will appear to pass the headline only if `Floor` happens to be bounded, and will silently re-clean as soon as `Floor` is unbounded (the exact headline shape). The default-rejection test must assert the rejection survives `Floor` being unbounded (default-only), which only the rule-vs-default fold delivers. If BUG-027 is not yet landed, the numeric default-containment half is **not** complete — do not claim it green against a narrowed-interval substitute.
- **Contradiction-in-each-domain.** If a field-reference bound that contradicts the field's own declared band compiles clean (the empty band read as a vacuous pass) — numeric OR length OR count — the contradiction guard was not re-imposed in that domain (the `Contains(⊥)=>true` over-prove vector reopened). Each domain's contradiction test is the guard.
- **False-reject.** If closing this slice forces explicit-constraint workarounds in **three or more** `samples/` precepts that a domain expert would consider obviously safe (a literal bound newly-reds, or a field-reference bound the reach should have proved), the mechanism over-rejects: a literal newly-red is a regression (the byte-identical guarantee broke); a field-reference reach gap means S3's edge resolution is too weak.
- **Cross-domain edge inconsistency.** If the cross-domain edge test reveals numeric and length/count discharging on *opposite* (one sound, one unsound) edges for the same logical relation, the S3-dual resolution is wrong — immediate redesign of the band-edge direction.
