# Spec-Conformance Test Suite Survey

> How do programming-language implementations build, organize, and ensure the completeness of test suites whose oracle is the language *specification* rather than the implementation? A balanced field survey across Test262, the WebAssembly spec tests, Ada ACATS, Rust compiletest, sqllogictest, the category-partition method, DO-178C, and lighter comparators — gathered to ground (not pre-decide) Precept's eventual conformance-corpus design.

## Background

Precept is a domain-integrity DSL whose *specification* is unusually machine-readable: catalogs (`Types`, `Operators`, `Modifiers`, `Constructs`, `Actions`, diagnostic codes) are "the language specification in machine-readable form" (CLAUDE.md § Catalog System). A conformance corpus for Precept would hold the runtime and compiler accountable to that spec. Before designing such a corpus, the team needs to know how the field actually does this — and crucially, whether the field's weight of practice supports or contradicts a catalog/metadata-driven, feature-organized, generate-from-spec approach. This survey reports the field on its own terms; the consumer (a `/design` pass) forms the opinion.

No prior research in `research/` covers conformance testing (checked `research/INDEX.md` 2026-06-01 — no section, no file; closest adjacencies are the runtime-evaluator and pipeline-architecture surveys, which are about implementation, not its conformance oracle). This is the first entry on the topic.

## Methodology

- **Research question:** Across mature language/DSL implementations, what is the *test-derivation method*, *organization axis*, *completeness/traceability mechanism*, *prose-to-acceptance-criteria handling*, *positive/negative coverage*, *combinatorial-explosion control*, and *static-vs-runtime split* of spec-conformance test suites — and what does the weight of practice favor?
- **Search strategy / venues:** Official spec repositories and their CONTRIBUTING/INTERPRETING/README docs (tc39/test262, WebAssembly/spec, Kotlin/kotlin-spec, golang/go, microsoft/TypeScript wiki); official project docs (rustc-dev-guide, sqlite.org); standards-adjacent docs (ada-auth.org ACATS User's Guide, ISO/IEC 18009 framing); the foundational testing-methodology paper (Ostrand & Balcer, CACM 1988); DO-178C requirements-based-testing vendor literature (Rapita, LDRA, Jama). WebSearch + WebFetch used throughout.
- **Inclusion criteria:** suites whose declared oracle is a normative specification (prose, formal semantics, or normative grammar), with public documentation of how tests are derived/organized/asserted. **Exclusion:** ordinary unit-test suites whose oracle is the implementation's own expected behavior (xUnit-style), and library-internal regression suites with no spec.
- **Source-grade mix:** Primary for Test262, WebAssembly, Rust compiletest, Kotlin spec tests, Go directives, TypeScript wiki, sqlite.org testing.html, Ostrand–Balcer. Secondary for Ada ACATS class-grading detail (search snippet of a PDF that timed out on direct fetch), sqllogictest modes (503 on the primary about.wiki, snippet substituted), DataFusion .slt format, DO-178C (all vendor docs — no public DO-178C text is freely fetchable). Tertiary: none load-bearing except the two snippet-substituted cases, flagged below.
- **Time bounds:** all fetches 2026-06-01. External docs evolve; access dates are recorded per source.

### Per-system prose

**Test262 — clause-anchoring without a hard denominator.** Test262 authors tests against the prose spec and tags each with an `esid` pointing at a spec anchor. The key is required: `esid` "is required for all new feature tests. This key identifies the hash ID from the portion of the ECMAScript draft which is most recent to the date the test was added ... E.g.: `esid: sec-typedarray-length`" [Primary; CONTRIBUTING.md; accessed 2026-06-01; mirrored `research/references/conformance-testing/test262.md`]. Tellingly, the suite is *abandoning* section-number organization: "The project is currently transitioning from a naming system based on specification section numbers ... contributors should ignore that approach when introducing new tests and instead encode this information using [the `esid` frontmatter key]" (same source). So the *organizing axis* moved away from spec-section numbering (brittle under spec edits) toward stable spec *anchors* carried as per-test metadata plus feature-readable file names. Negative tests are mechanically specific about *where* in the pipeline the error must occur: the `negative` attribute is "a YAML dictonary with two keys: `phase` ... valid phases are: `parse` ... `resolution` ... `runtime` ... `type` - the name of the constructor of the expected error" [Primary; INTERPRETING.md; accessed 2026-06-01]. There is no coverage *proof* — completeness is "did someone write an `esid`-tagged test," a process discipline, not a denominator.

**WebAssembly — the spec, the reference interpreter, and the tests in one repo.** "This repository holds the sources for the WebAssembly specification, a reference implementation, and the official test suite" [Primary; WebAssembly/spec README; accessed 2026-06-01; mirrored]. The negative-coverage vocabulary is partitioned by *pipeline stage*: `assert_invalid` = "assert module is invalid" (validation/type-check failure), `assert_malformed` = "assert module cannot be decoded" (parse failure), `assert_unlinkable`, plus runtime `assert_trap` and `assert_exhaustion` [Primary; interpreter/README.md; accessed 2026-06-01]. The reference interpreter is the executable oracle and even checks diagnostic strings by prefix: failure strings "exist for documentation purposes," and "the reference interpreter itself checks that the string is a prefix of the actual error message it generates." This is the cleanest example of *static-vs-runtime expressed in the assertion vocabulary itself*.

**Ada ACATS — certified conformance with a rule-traceability matrix and explicit humility about exhaustiveness.** ACATS is the strongest precedent for *certified* conformance. It is honest that completeness is unattainable: "the ACATS is a set of test programs intended to check broadly for correct implementation; it is not possible to exhaustively test for conformity" [Secondary; Wikipedia summarizing ada-auth/ISO; accessed 2026-06-01; mirrored]. Traceability is a first-class artifact: "The ACATS Coverage Documents record the mapping of test objectives and tests to Ada rules, making it possible to determine if individual rules are adequately tested." The static/runtime split is encoded in the *test-class filename prefix*: "Class A, C, D, and E tests are executable, while Class B tests are expected to produce compilation errors. Class L tests are expected to produce compilation or link errors" [Primary-origin, retrieved Secondary; ACATS UG via search snippet; accessed 2026-06-01]. Class B grading is exact about *both* directions of negative coverage: "An implementation passes a class B test if each indicated error in the test is detected and reported, and no other errors are reported" — i.e., it must reject the invalid construct *and* not over-reject. Required errors are marked inline with `-- ERROR:`.

**Rust compiletest — feature-organized, machine-captured expected output, no clause denominator.** Rust's suite predates a normative Rust spec, so it organizes by *feature directory* and captures expected diagnostics mechanically. Expected output lives in `.stderr`/`.stdout` snapshots "generated using the `--bless` CLI flag"; inline `//~ ERROR <substr>` annotations anchor diagnostics to lines, with relative-line variants (`//~^`, `//~|`, `//~v`, `//~?`) and embedded error codes (`[E0023]`) [Primary; rustc-dev-guide; accessed 2026-06-01; mirrored]. "Error and warning kinds require exhaustive line annotation coverage by default" — the completeness discipline is *exhaustive annotation of observed output*, not coverage of a spec denominator. This is the field's clearest example of a suite that deliberately does **not** organize by or trace to spec clauses, yet is treated as the de-facto conformance bar.

**sqllogictest — differential testing as the oracle, generation at scale.** SQLite's SLT sidesteps prose entirely: the oracle is *agreement across engines*. "The SQL Logic Test or SLT test harness is used to run huge numbers of SQL statements against both SQLite and several other SQL database engines and verify that they all get the same answers" [Primary; sqlite.org/testing.html; accessed 2026-06-01; mirrored]. It runs at generated scale (~6M queries) in two modes — completion (run prototype against a reference engine, record results) and validation (compare an engine-under-test against recorded results) — with large result sets reduced to a hash. Negative/diagnostic specificity is weak; the technique trades clause-traceability and error-message precision for volume and cross-implementation differential signal.

**Kotlin spec tests — sentence-level traceability, the strongest prose denominator found.** Kotlin links each test to spec *sentences*: a test connects to "one *primary* sentence, which is the main thing the test is checking, and zero or more *secondary* sentences"; "Sentences are identified by their section path plus their paragraph number plus their sentence number"; and crucially the rendered spec shows the denominator visually — "If a sentence have one or more tests linked to it (aka a *tested sentence*), it is highlighted in green; otherwise, it is highlighted in gray" [Primary; kotlin-spec CONTRIBUTING.md; accessed 2026-06-01; mirrored]. This is the field's most literal answer to "how do you define the denominator when the authority is prose": *make the prose itself the denominator, one sentence at a time, and color it.* A relinking-recommender tool manages drift when the spec changes.

**Go and TypeScript (lighter touch).** Go's `test/` uses a header directive to pick a mode (`// run`, `// compile`, `// errorcheck`, `// build`) and `// ERROR <regexp>` line annotations for expected diagnostics [Primary for the directive existence via go.dev/test/gc.go; Secondary for the annotation rule via golang/go #19577; accessed 2026-06-01]. TypeScript's `tests/cases/conformance` is feature/area-organized with a *baseline* model: expected output (`.errors.txt`, `.types`, `.js`) is captured and re-accepted on change; moving a test should change only "the path of the test they reference" [Primary; TS wiki; accessed 2026-06-01]. Both organize by feature, not clause; both capture expected output mechanically.

**Methodology layer.** The **category-partition method** (Ostrand & Balcer, CACM 1988) is the canonical answer to combinatorial explosion: decompose the spec into categories, partition each into choices ("different cases that are expected to be handled differently or perhaps may represent error-prone boundary conditions"), then enumerate constrained *test frames* — the FIND example explodes to 1,944 frames, pruned to 125 via `[if ...]`, `[error]`, `[single]` constraints; all-pairs is offered as a further reduction (4^20 → ~3,040) [Primary paper; Secondary course summaries; accessed 2026-06-01; mirrored]. **DO-178C** supplies the certified-traceability discipline: "you must demonstrate the trace-ability of your test cases to requirements via requirements-based coverage analysis" *and* structural coverage (up to MC/DC at DAL A) — a dual denominator (requirements covered + code covered) [Secondary; Rapita/LDRA; accessed 2026-06-01; mirrored].

## Threats to Validity

- **Unfetchable primaries, snippet-substituted (load-bearing).** Two load-bearing primary sources failed direct fetch and were substituted with web-search snippets of the same page: (1) the **ACATS User's Guide PDF** (timed out twice) — the Class A/B/C/D/E/L semantics and Class-B/L grading quotes come from a search snippet of that PDF, not a direct read; (2) the **sqllogictest about.wiki** (HTTP 503) — the completion/validation-mode and 6M-query scale quotes come from a snippet. Both are *origin-Primary* but *retrieved-Secondary/Tertiary*. The differential-oracle claim for sqllogictest is independently corroborated by a direct Primary fetch of sqlite.org/testing.html, so that core claim is solid; the mode-detail is the weaker leg. The ACATS class taxonomy is widely corroborated across GNAT docs and DTIC validation reports, lowering the risk, but the exact grading wording rests on a snippet.
- **DO-178C is entirely Secondary.** DO-178C itself is a paid RTCA document, not freely fetchable. All DO-178C claims rest on vendor (Rapita/LDRA/Jama) summaries. The requirements-based-testing and traceability concepts are uncontroversial and consistently described across vendors, but no Primary text was read.
- **Shallow comparators.** W3C web-platform-tests, Dart language tests, and Kotlin's *runtime* (vs spec-test) suites were not investigated; Go and TypeScript were treated lightly (directive/format level, not corpus-organization depth). Conclusions about the *field's dominant axis* weight the deeply-covered five (Test262, WASM, ACATS, Rust, sqllogictest) plus Kotlin.
- **Selection bias.** Comparators were chosen because they are the canonical, well-documented spec-conformance suites — which biases toward suites that *have* public methodology docs. Suites with strong clause-traceability are more likely to *document* that fact, possibly over-representing traceability in the survey relative to the silent majority that organize by feature.
- **Recency.** All fetches 2026-06-01; repo CONTRIBUTING/INTERPRETING docs change. The Test262 "transitioning away from section numbers" statement in particular is a moving target — it may have completed or reversed.
- **Domain mismatch.** Every comparator is a general-purpose language or SQL; none is a domain-integrity DSL with machine-readable catalogs as its spec. The closest structural analog (machine-readable spec → derivable tests) is *not* well-represented in the field, which is itself a finding (see Open Questions).

## Implications for Precept

Bridging the evidence to Precept's situation, without proposing a design:

- **Precept's spec is more machine-readable than any comparator's.** Every surveyed suite traces tests back to *prose* (Test262 anchors, Kotlin sentences, ACATS rules) or to *another implementation* (sqllogictest). Precept's catalogs already are the normative enumeration of types, operators, modifiers, constructs, actions, and diagnostic codes. Where the field's hardest problem is "define a denominator over prose," Precept may already *have* a denominator (the catalog enumeration) — a structural advantage the field largely lacks. The design pass should weigh whether the catalog is the natural denominator the way Kotlin made each sentence one.
- **The field is split on the organizing axis, and the split is principled.** Suites with a *stable, anchored* spec (Test262 via `esid`, ACATS via rules, Kotlin via sentences) trace to the spec. Suites whose normative spec post-dated the implementation (Rust, TypeScript, Go) organize by *feature* and capture expected output mechanically. The axis a project picks tracks *whether a stable spec existed first*. Precept's catalogs exist first — which places it nearer the Test262/ACATS/Kotlin end than the Rust/TypeScript end. The design pass must decide whether to exploit that.
- **Negative coverage is universally stage-partitioned and diagnostic-specific in the strong suites.** Test262 (`phase`), WASM (`assert_invalid`/`assert_malformed`/`assert_trap`), ACATS (Class B vs L vs C), Go (`// errorcheck` vs `// run`), Rust (`//~ ERROR [E0277]`) all distinguish *which stage* rejects an invalid program *and which specific diagnostic* fires. Precept's pipeline (lexer → parser → type checker → graph analyzer → proof engine → runtime) and its `PRE####` diagnostic codes map directly onto this pattern. The field strongly favors asserting *the specific diagnostic at the specific stage*, not merely "it failed."
- **Expected-output capture/blessing is the dominant negative-assertion mechanism — and it has a known hazard.** Rust `--bless`, TypeScript baselines, Go/WASM error-string matching all snapshot the implementation's output and re-accept it. This is ergonomically dominant but its oracle drifts toward "what the implementation currently emits" — the opposite of a spec oracle. ACATS/Test262 resist this by hand-asserting *required* errors against the spec, not the implementation's output. Precept's design pass faces this exact fork.
- **Differential and generative testing buy volume at the cost of clause-traceability and diagnostic specificity.** sqllogictest's 6M generated queries and cross-engine oracle are powerful for *result-value* conformance but say nothing about *which spec rule* or *which diagnostic*. For a prevention-focused engine whose value is specific, structural rejection, the generative/differential branch addresses a different question than clause-conformance.

## Conclusions

These are conclusions *about the field*, not Precept design decisions.

**C1. The field favors per-test spec-anchoring (metadata tags) over directory-by-clause organization — and actively migrates away from clause-numbered directories.**
- *Rationale:* spec section numbers are unstable under spec edits; stable anchors carried as per-test metadata survive renumbering. Test262 explicitly states it is "transitioning from a naming system based on specification section numbers" toward the `esid` anchor key, and `es6id` (section-number) is deprecated.
- *Alternatives rejected (by the field):* directory-by-section-number (ACATS partly uses class-prefix + objective IDs, but even ACATS traces via separate Coverage Documents, not directory names alone); pure feature-folder with no spec link (Rust/TS — but only because no stable spec existed first).
- *Precedent:* Test262 `esid`; ACATS Coverage Documents; Kotlin sentence IDs.
- *Tradeoff accepted:* metadata tags require discipline and tooling to keep current (Kotlin needs a relinking-recommender; Test262 allows `pending`), and a tag is not a proof of coverage — only a pointer.

**C2. Completeness against a prose authority is, in practice, *traceability* (a coverage matrix or per-unit "tested/untested" marker), not a *proof*; the strong suites are explicit that exhaustiveness is unattainable.**
- *Rationale:* prose has no finite, machine-checkable denominator; the field substitutes a human-curated mapping of spec units → tests and measures "are all units mapped." ACATS states outright it "is not possible to exhaustively test for conformity," yet ships Coverage Documents mapping objectives to rules. Kotlin makes the denominator literal (every sentence green/gray). DO-178C formalizes this as requirements-based coverage.
- *Alternatives rejected (by the field):* structural code coverage as the *conformance* denominator (DO-178C uses it as a *supplement*, not a substitute — requirements coverage is separate); "we wrote a lot of tests" with no mapping (the weaker suites' implicit position, which the certified suites reject).
- *Precedent:* ACATS Coverage Documents; Kotlin green/gray sentences; DO-178C dual coverage.
- *Tradeoff accepted:* a traceability matrix proves *mapping*, not *adequacy* — a sentence can be "green" with one shallow test. Completeness becomes a curation/discipline claim, not a theorem.

**C3. Negative conformance in the strong suites is asserted as a *specific diagnostic at a specific pipeline stage*, not as a bare rejection.**
- *Rationale:* "the program is rejected" is a weak oracle; conformance requires the *right* rejection at the *right* phase. Test262's `negative` carries both `phase` and `type`; WASM partitions `assert_invalid`/`assert_malformed`/`assert_trap`; ACATS Class B requires each indicated error detected "and no other errors ... reported."
- *Alternatives rejected (by the field):* exit-code-only / "compiles or not" testing (insufficient — ACATS explicitly fails tests that report *spurious* errors); message-substring-only without phase (Rust's `error-pattern` exists but is "less preferred than line annotations").
- *Precedent:* Test262 phase+type; WASM assertion taxonomy; ACATS Class B/L grading.
- *Tradeoff accepted:* asserting exact diagnostics couples tests to diagnostic wording/codes, raising maintenance cost (mitigated by substring matching and blessing).

**C4. The dominant *mechanism* for capturing expected negative output is snapshot/baseline blessing — which is ergonomically superior but shifts the oracle toward the implementation, away from the spec.**
- *Rationale:* hand-writing exact diagnostic output is tedious and error-prone; `--bless`/baselines auto-capture it. Rust, TypeScript, Go, and WASM (string-prefix) all do this. But a blessed baseline encodes *what the implementation emitted*, so a wrong-but-stable diagnostic gets blessed as "correct."
- *Alternatives rejected (by the field):* fully hand-authored expected errors against the spec (ACATS/Test262 do this for *required* errors but it does not scale to full output).
- *Precedent:* Rust `--bless`; TS baselines; Go/WASM error-string matching.
- *Tradeoff accepted:* baseline blessing trades spec-fidelity of the oracle for authoring throughput; teams that want a *spec* oracle must add a separate hand-asserted layer on top of (or instead of) blessing.

**C5. Combinatorial explosion is handled by equivalence-class / category-partition reduction with explicit constraints, not full cross-product; full cross-product appears only where generation is cheap and the oracle is differential (sqllogictest).**
- *Rationale:* the input space is effectively infinite; category-partition reduces it to constrained frames (FIND: 1,944 → 125), and all-pairs reduces further. Full cross-product is used only when a non-prose oracle (another engine) makes mass generation worthwhile.
- *Alternatives rejected (by the field):* exhaustive cross-product for clause-conformance (intractable and unnecessary — `[single]`/`[error]` choices get one test each).
- *Precedent:* Ostrand–Balcer category-partition; sqllogictest generative scale.
- *Tradeoff accepted:* equivalence-class partitioning can miss interaction bugs that lie *between* classes; all-pairs catches pairwise but not higher-order interactions.

## What would change these conclusions

- **C1/C2 falsifier:** if three or more well-documented modern conformance suites we didn't survey (e.g., web-platform-tests, Dart language tests, Swift's suite) turn out to organize *primarily by spec-section directory with no per-test anchor and no coverage matrix*, the "field favors anchoring + traceability matrix" claim weakens toward "the field is genuinely mixed with no dominant axis."
- **C3 falsifier:** if the deeply-surveyed suites are found to accept bare-rejection negative tests at scale (e.g., a large fraction of Test262 negatives omit `type`, or ACATS Class B commonly tolerates spurious errors in practice), the "specific diagnostic at specific stage" claim is overstated.
- **C4 falsifier:** if a Primary read of the ACATS UG or a large sample of Test262 negatives shows they too are *machine-blessed from implementation output* rather than hand-asserted against spec, then blessing is universal and the "spec-oracle layer resists blessing" distinction collapses.

## Open Questions

- **No comparator has a machine-readable spec like Precept's catalogs.** The field traces to prose or to another implementation. Whether a *catalog-as-denominator* approach (generate the conformance denominator from the same metadata that drives the grammar/completions) is a genuine novelty or a known anti-pattern is unresolved — the survey found no precedent either way. This is the single most important gap for Precept's design pass.
- **How do the strong suites manage red-by-design / authoring-before-implementation?** The survey touched expected-fail/baseline ratchets (TS baselines, Rust `--bless`, known-failures) but did not deeply investigate skip/expected-fail *ratchet* discipline (e.g., Test262's `features` gating, WPT's `.ini` expectations). A follow-up should cover how a suite is authored *before* the implementation and managed red.
- **Quantitative coverage denominators.** None of the surveyed prose-based suites reports a *percentage* coverage of the spec; ACATS and Kotlin report mapping existence, not adequacy. Whether any suite has attempted a defensible quantitative spec-coverage metric is unresolved.

## Synthesis (the three questions the topic demands)

**(a) What is mechanizable vs. irreducibly human in spec→test?** Mechanizable: expected-output *capture* (blessing/baselines), *re-checking* against captured output, anchor/tag *validation* (does every test carry an `esid`?), drift detection (Kotlin's relinking-recommender), large-result hashing, generative input production, and cross-product *reduction* (all-pairs tooling). Irreducible human judgment: deciding *which* spec unit a test targets and whether the assertion *means* what the prose requires (Test262's "citable normative text," Kotlin's primary-sentence choice), choosing equivalence classes and boundary choices (category-partition's categories/choices), and judging whether a blessed diagnostic is *correct* vs merely *current*. The field mechanizes the bookkeeping and the regression-checking; it does not mechanize the spec→intent mapping.

**(b) Is completeness provable when the authority is prose?** No — the field is explicit (ACATS: "not possible to exhaustively test for conformity"). What the field does instead is make the denominator *enumerable and visible*: a coverage-document matrix (ACATS), per-sentence tested/untested coloring (Kotlin), or per-test spec anchors (Test262). "Complete" becomes "every enumerated spec unit has ≥1 mapped test," a curation claim, not a theorem. DO-178C adds structural coverage as a *second* denominator but still treats requirements coverage as primary. Precept's catalog is the one place in this survey where the denominator could be *finite and machine-derived* rather than prose — but no comparator demonstrates that, so it is an open opportunity, not a proven path.

**(c) Which organizing axis does the field actually favor, and why?** There is no single winner, but the split is principled: **spec-anchor-per-test (metadata) layered over feature-readable file names** is favored by suites with a stable spec that predates or co-evolves with the implementation (Test262 `esid`, ACATS objective IDs, Kotlin sentence IDs), explicitly *over* directory-by-section-number, because section numbers rot under spec edits. Suites whose spec post-dated the code organize by **feature directory** with mechanically-captured output (Rust, TypeScript, Go). The deciding factor is *whether a stable, citable spec existed first* — which, for Precept (catalogs first), points toward the anchor/traceability end of the field rather than the feature-folder end. The design pass owns that decision; this survey only locates Precept on the field's map.
