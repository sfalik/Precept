## Whiley — verification architecture & VC generation

Source: David J. Pearce, "The Architecture of Verification in Whiley" (2013-06-26),
<https://whileydave.com/2013/06/26/the-architecture-of-verification-in-whiley/>. Accessed 2026-05-29. Secondary (named author, language designer).

Pipeline: Whiley source → WyC (compiler front-end) → WyIL (typed intermediate language) → WyAL (assertion language) → WyCS (theorem prover).

> "responsible for parsing and type checking whiley source files and generating (binary) wyil files" — (WyC compiler front-end)

> "To verify a Whiley source file is correct, it is first translated into a WyIL file, then into a WyAL file which, finally, is verified as correct (or not) by the WyCS theorem prover."

> "each Whiley function can generate multiple assertions (a.k.a verification conditions) in the generated WyAL file"

Source: David J. Pearce, "Generating Verification Conditions for Whiley" (2012-12-04),
<https://whileydave.com/2012/12/04/generating-verification-conditions-for-whiley/>. Accessed 2026-05-29. Secondary.

> "A verification condition is a logical expression which, if proved to be satisfiable, indicates an error in the program."

> "the VC generator performs a path-sensitive traversal accumulating assumptions" (through the program code)

> "to construct the VC, we combine the assumptions and assertion together using `==>` (i.e. an implication) to give our final verification condition."

> The generated verification conditions are "passed into the ATP which is responsible for deciding whether they are satisfiable or not."

Source: WhileyTheoremProver README, <https://github.com/Whiley/WhileyTheoremProver>. Accessed 2026-05-29. Primary (project README).

> "The Whiley Theorem Prover (WyTP) is an automatic and interactive theorem prover designed to discharge verification conditions generated by the Whiley Compiler. WyTP operates over a variant of first-order logic which includes integer arithmetic, arrays and quantification."

## Viper / Silver — intermediate verification language

Source: ETH Zürich Programming Methodology Group, "Viper" project page,
<https://www.pm.inf.ethz.ch/research/viper.html>. Accessed 2026-05-29. Primary (authoritative project page).

> "The Viper toolset can be used to implement verification techniques for front-end programming languages via translations into the Viper language."

> "New verification techniques can be implemented directly as translations to the Viper language, using either of the verifiers provided."

Two back-end verifiers:
- Boogie-based verifier: "a translation from Viper to the Boogie verification language" (relies on Boogie to discharge).
- Symbolic-execution verifier: "uses the Z3 SMT solver to discharge logical queries."

Front-ends targeting Viper: Gobra (Go), Nagini (Python), Prusti (Rust), Chalice, plus weak-memory and Vyper verifiers.

## Why3 — IVL platform with WhyML

Source: Why3 project home, <https://www.why3.org/>. Accessed 2026-05-29. Primary.

> "It provides a rich language for specification and programming, called WhyML, and relies on external theorem provers, both automated and interactive, to discharge verification conditions."

WhyML "as an intermediate language for the verification of C, Java, or Ada programs." Supported provers include Z3, CVC4, Alt-Ergo (automated) and Coq, Isabelle/HOL (interactive).

## F* — VC generation integrated into the type-and-effect system

Source: F* home, <https://www.fstar-lang.org/>. Accessed 2026-05-29. Primary.

> F* "combines the expressive power of dependent types with proof automation based on SMT solving and tactic-based interactive theorem proving."

Dijkstra-monad line of papers ("Verifying Higher-order Programs with the Dijkstra Monad", PLDI 2013; "Dijkstra Monads for Free", POPL 2017; "Dijkstra Monads for All", ICFP 2019) indicate weakest-precondition / effect-indexed VC generation is integrated into the type system rather than a separate stage.

## OutsideIn(X) — constraint-generation-then-solving (GHC)

Source: Vytiniotis, Peyton Jones, Schrijvers, Sulzmann. "OutsideIn(X): Modular type inference with local assumptions." Journal of Functional Programming, Vol 21, pp. 333–412 (2011). <https://simon.peytonjones.org/outsideinx/>. Accessed 2026-05-29. Primary (peer-reviewed).

> "OutsideIn(X) is parameterised over the particular underlying constraint domain X, in the same way as HM(X)" — common metatheory and inference algorithm via stratification.

Two-phase: a constraint *generator* walks the term producing constraints (including implication constraints), then a constraint *solver* for X canonicalises and simplifies them. "This constraint solver has been implemented and distributed as part of GHC 7."
